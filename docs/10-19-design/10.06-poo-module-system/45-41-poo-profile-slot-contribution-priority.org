#+title: POO Profile Slot Contribution Priority
#+subtitle: Exact precedence, inheritance boundaries, deterministic composition, and lazy shadowing
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative design module
- Semantic core :: =gerbil-poo= objects, prototypes, and native composition
- Composition entry point :: The ordinary =compose= function and the first-class =profiles= POO strategy object
- Design reference :: [[https://nickel-lang.org/user-manual/merging/][Nickel merge priorities]]

This module adopts the useful ideas behind Nickel priorities, =default=, =force=, and equal-priority recursive merge. It does not copy Nickel field syntax and does not describe the result as "Nickel style." Every public value and extension path remains POO-native.

* Core decision

#+begin_quote
Priority is exactly ordered POO metadata carried by a slot contribution. A Profile only provides an inheritable default; the =profiles= strategy interprets priority; =compose= itself owns no priority semantics.
#+end_quote

Priority only resolves precedence among candidates that have already passed identity, capability, authority-scope, and contract admission. It does not grant authority, enlarge capability, bypass contracts, or guarantee fixed-point termination.

* Priority domain

The canonical order is:

#+begin_src text
default < exact numeric priorities < force
#+end_src

- The ordinary numeric priority is =0=.
- A larger number has higher priority.
- =default= is the semantic lower bound.
- =force= is the semantic upper bound.
- Equal priorities enter native POO composition instead of being selected by appearance order.

Canonical numeric priorities are limited to Scheme exact integers and exact rationals. Floating-point values, =NaN=, floating infinities, and values whose comparison depends on platform rounding cannot participate in canonical priority identity.

=default=, numeric priorities, and =force= must be ordinary POO priority values or constructors. They are not macro keywords and do not introduce special branches in =compose=.

* Slot-contribution granularity

Canonical priority belongs to a slot contribution, not to a single whole-Profile override level:

#+begin_src text
Profile
`-- slot contribution
    |-- value or delayed POO computation
    |-- priority
    |-- provenance
    |-- identity
    |-- contracts
    `-- capability requirements
#+end_src

A Profile may provide an inherited priority. A slot contribution without an explicit priority inherits that value; an explicitly prioritized contribution overrides the inherited value only for itself.

A whole-Profile priority cannot replace slot-local priority. Different slots may require different precedence, and an unrelated slot must not become invalid merely because another slot changes priority.

* Inheritance and authority boundaries

Priority inheritance must prevent priority laundering:

- A parent Profile's high priority does not automatically raise the priorities of an imported Profile.
- An imported Profile preserves its contribution priorities and provenance.
- Prototype composition must not silently change contributions outside the current authority scope.
- A submodule participates in priority comparison only for semantic slots that it is admitted to provide.
- Priority cannot admit a candidate that failed capability, identity, authority-scope, or contract admission.
- A priority change cannot create new authority.

#+begin_src mermaid
flowchart LR
    P["Parent Profile inherited priority"] -->|"applies only to its own unannotated contributions"| O["Parent Profile slots"]
    I["Imported Profile priorities"] -->|"preserve their values and provenance across import"| A["Admitted slot candidates"]
    S["Submodule contribution"] -->|"passes identity, capability, authority, and contract admission"| A
    S -->|"fails admission and never enters priority comparison"| X["Structured admission failure"]
    A -->|"compare only within one semantic slot"| R["Priority resolution"]
#+end_src

* Resolution order

The canonical resolution of a demanded slot is:

1. Collect contributions for the semantic slot.
2. Validate identity, capability, authority scope, and contracts.
3. Compare priorities only among admitted candidates.
4. Select the highest-priority layer.
5. Use the contribution directly when that layer contains one candidate.
6. Deduplicate repeated occurrences of the same contribution identity.
7. Apply a native POO operation only when it is a canonical combination for the current values.
8. Produce structured conflict evidence when equal-priority candidates cannot be combined independently of operand presentation order.
9. Retain lower-priority candidates as dormant or shadowed contributions.

=compose= must not substitute operand order, list position, import order, or a host-language =case= for this resolution.

* Prototype construction and Profile resolution

Directional prototype construction and equal-priority Profile resolution are different operations.

An explicitly directional native operation may construct one Profile operand before that operand enters =compose=:

#+begin_src scheme
(def production
  (.mix base-profile
        production-extension))
#+end_src

The exact operation above is illustrative and must be validated against real =gerbil-poo= primitives. Its important property is that the user expresses the construction direction before Profile resolution.

After operands enter =compose profiles=, the strategy must not recover a hidden direction from their list order. It must not sort identities and then apply a directional primitive: such sorting would be reproducible, but it would let an incidental name or digest determine business semantics.

#+begin_src mermaid
flowchart LR
    B["Base prototype"] -->|"explicit directional native operation"| P["Constructed Profile operand"]
    X["POO extension"] -->|"explicitly extends the base"| P
    P -->|"enters as one ordinary operand"| C["compose profiles"]
    O["Other Profile operands"] -->|"enter as ordinary operands"| C
    C -->|"collect same-slot contributions"| R["Priority resolution"]
    R -->|"different priorities"| W["Higher-priority contribution"]
    R -->|"same contribution identity"| D["Identity-idempotent deduplication"]
    R -->|"canonical native combination exists for these values"| M["Canonical POO combination"]
    R -->|"only directional or non-confluent composition exists"| E["Structured conflict evidence"]
#+end_src

* Observable resolution laws

The =profiles= strategy must satisfy these laws without redefining the laws of every underlying =gerbil-poo= primitive:

- Observable permutation invariance :: Permuting =compose= operands produces the same semantic result or the same structured conflict.
- Observable regrouping invariance :: Regrouping Profile collections does not introduce presentation-order semantics.
- Identity idempotence :: Repeating the same contribution identity does not apply it twice.
- Dominance :: A higher-priority contribution stably shadows a lower-priority contribution.
- Canonical-combination restriction :: An equal-priority merge is admitted only when the selected native POO operation is canonical for the current values.
- Directional-operation isolation :: A directional native operation belongs to explicit Profile operand construction, not implicit equal-priority resolution.
- Equal-priority fail-closed behavior :: When no canonical combination exists, resolution produces one canonical structured conflict.
- Lazy shadowing :: Comparing priorities does not force the business value of a lower-priority candidate.
- Authority monotonicity :: Raising priority does not enlarge capability or authority.

These laws constrain the observable behavior of =profiles=. They do not declare every =gerbil-poo= primitive commutative or associative. A strategy that violates the observable laws is not a compatible extension of =profiles=.

* The boundary of =force=

=force= is only the precedence upper bound:

#+begin_src text
force is not capability
force is not authority
force is not a contract bypass
force is not a fixed-point termination guarantee
#+end_src

Two =force= contributions still enter equal-priority native POO composition. If they cannot be composed, resolution must report a conflict instead of silently selecting by operand order.

* Lazy shadowing and fixed-point evaluation

Priority resolution may force only the priority, identity, admission evidence, and static provenance required to establish candidate ownership. It must not evaluate the business value of a lower-priority contribution merely to choose a winner.

This is a fixed-point safety requirement. A recursive definition that will be shadowed must not trigger infinite recursion or abnormal evaluation cost merely because it participated in priority comparison.

#+begin_src mermaid
flowchart LR
    C["Admitted candidates for one slot"] -->|"read exact priority metadata"| H["Highest-priority layer"]
    H -->|"contains one candidate"| W["Active contribution"]
    H -->|"contains equal-priority candidates"| M["Canonical POO merge"]
    M -->|"native operation is canonical for these values"| W
    M -->|"only directional or non-confluent operation exists"| E["Deterministic conflict evidence"]
    C -->|"has lower priority; do not force business value"| D["Dormant contribution"]
    D -->|"retain identity, priority, and provenance"| R["Shadow receipt"]
    D -->|"activate after priority or admission changes"| F["Affected slot invalidation"]
    F -->|"changes dependency topology"| S["Current-generation SCC recomputation"]
#+end_src

A priority or admission change invalidates only the affected slot and the reachable downstream current-generation SCCs. It must not unconditionally recompute the entire Profile set.

* Evidence requirements

Every priority resolution must be able to explain:

- the semantic slot identity;
- all admitted candidate identities;
- each candidate's exact priority and provenance;
- admission evidence for rejected candidates;
- the winning priority layer;
- the native POO operation used for an equal-priority merge;
- why dormant candidates were shadowed;
- which contributions failed to compose;
- which slot and SCC invalidations followed a priority change.

Producing evidence must not force dormant business values.

* User-interface constraint

The public composition interface remains:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    base
    wendao-episteme
    production))
#+end_src

Priority is supplied through ordinary POO extension of a Profile or slot contribution. It does not add clauses to =user-composition=, turn =compose= into a macro, or encode precedence through operand order.

Concrete priority constructors and prototype operations must be based on verified native =gerbil-poo= interfaces. This RFC does not invent another object DSL.

* Implementation checklist

- [ ] Define =default=, exact numeric priority, and =force= as a canonical ordered POO domain.
- [ ] Reject inexact, =NaN=, and otherwise non-canonical priority values.
- [ ] Define Profile inherited priority and slot-local override.
- [ ] Preserve imported Profile priorities and provenance.
- [ ] Complete identity, capability, authority-scope, and contract admission before priority comparison.
- [ ] Verify observable permutation and regrouping invariance without redefining native primitive laws.
- [ ] Test identity idempotence for equal-priority contributions.
- [ ] Admit an equal-priority native operation only when it is canonical for the current values.
- [ ] Verify that directional prototype construction remains explicit and occurs before =compose profiles= resolution.
- [ ] Verify that sorting contribution identities cannot manufacture an implicit direction.
- [ ] Verify that a directional or non-confluent equal-priority case fails closed with canonical conflict evidence.
- [ ] Verify that dormant contributions are not forced.
- [ ] Verify that =force= cannot bypass capability, contract, or authority checks.
- [ ] Produce winning, shadowed, conflict, and invalidation evidence.
- [ ] Verify that a priority change invalidates only related slots and downstream current-generation SCCs.
- [ ] Validate the final object-construction interface against real =gerbil-poo= primitives.

* Non-goals

- Do not copy Nickel surface syntax.
- Do not encode priority through operand order.
- Do not expose host-language conditionals as the Profile-selection interface.
- Do not create a priority registry or a closed strategy enumeration.
- Do not turn priority into a capability or authority system.
- Do not reimplement =gerbil-poo= object-composition semantics.

#+title: POO-Native Slot Contracts and Algebraic Laws
#+startup: overview

* Status

Accepted design.

This document defines the semantic contracts that govern inherited slot
combination in the POO Module System.

It refines the native operation mapping in
[[file:45-27-native-poo-operations-as-module-semantics.org][45-27]] without
replacing =gerbil-poo= slot syntax or evaluation.

POO-native value precedence for slot contracts that explicitly adopt merge
priority is defined by
[[file:45-29-poo-merge-priority-and-recursive-override.org][45-29]].

* Problem

The native ==>= form guarantees that a slot computation receives its inherited
result through a combining function.  It does not imply one universal merge
law.

Treating every inherited value as a list to append would confuse:

- unordered Capability candidates with ordered refinements;
- authority attenuation with authority union;
- budget delegation with numeric addition;
- receipt continuity with collection concatenation;
- nested prototype refinement with data merge.

The POO Module System therefore requires each semantic slot family to carry an
explicit POO-native contract.

* Decision

A slot contract is a higher-order POO object.

It provides the semantic law required to interpret a native slot refinement,
including:

- the recursion base or absence behavior;
- the inherited combining operation;
- canonical identity construction;
- order sensitivity;
- duplicate semantics;
- validity conditions;
- ambiguity or conflict semantics;
- authority requirements;
- receipt construction;
- replay validation.

The contract is imported and inherited through ordinary POO Capabilities.  It
is not selected by =#:kind=, an enum, a symbol table, a Profile registry, or a
runtime dispatch token.

Native =gerbil-poo= still performs =.o=, =.def=, ==>=, ==>.+=, =.mix=, lazy
slot demand, and fixed-point instantiation.

* Contract identity

Every slot contract has canonical prototype-lineage and runtime object
identities.

Semantic evidence for a combined slot binds:

- the slot contract identity;
- the root and module-instance identities;
- the slot and Capability identities;
- the predecessor slot-state identity;
- the contribution identity;
- the canonical successor identity;
- the fixed-point generation;
- provenance.

Changing the contract creates a different semantic computation.  A contract
cannot be substituted merely because two combining functions print the same
name or currently return equal values.

Re-export and alias reachability of one canonical contract do not create
multiple contracts.

* Algebraic properties

A contract declares and evidences only the properties its slot semantics
actually possess.

Relevant properties include:

- identity: a valid recursion base exists;
- associativity: regrouping valid contributions preserves canonical result;
- commutativity: admission order does not affect canonical result;
- idempotence: repeating the same contribution identity does not change the
  result;
- monotonicity: a successor extends the permitted information order;
- attenuation: a successor cannot grant more authority than its predecessor;
- conservation: allocation successors cannot create semantic units;
- predecessor continuity: a transition must consume the exact state it names;
- deterministic canonicalization: equivalent inputs yield one identity.

No contract may claim a property solely because a test happened to pass.
The contract's prototype lineage defines the semantic family, the
implementation supplies the operation, runtime evidence checks concrete
transitions, and the harness performs property-oriented validation.

* Contract families

| Slot family | Required semantic law |
|-------------+-----------------------|
| Canonical contribution set | Associative, commutative, idempotent canonical union |
| Singleton Capability | Canonical candidate closure followed by cardinality validation |
| Ordered same-lineage refinement | Native prototype precedence; order is semantically significant |
| Authority | Attenuation or meet; ordinary combination cannot widen a grant |
| Observation budget | Partition, consumption, and conservation across generations |
| Receipt chain | Exact predecessor continuity and one canonical successor link |
| Nested module object | Native ==>.+= prototype refinement |
| Diagnostic evidence | Pure projection or canonical evidence-set accumulation |

These families are POO prototype lineages, not enum cases interpreted by a
central switch.

* Canonical contribution-set contract

A canonical contribution-set slot uses an identity-based set.

Its combination is:

- associative;
- commutative;
- idempotent by canonical contribution identity;
- independent of textual admission order;
- insensitive to alias and re-export reachability.

The recursion base may be the canonical empty set.

The set retains contribution identity, provider lineage, module-instance
identity, generation, and provenance.  It is not a plain list of values.

Native ==>= invokes the contract's set combination.  It does not append a
value to an order-sensitive Scheme list.

* Singleton-Capability contract

A singleton Capability does not use last-writer-wins override for unrelated
providers.

Its inherited accumulation first constructs a canonical candidate set.  At
demand:

- zero candidates produce the structured unavailable condition;
- one authorized candidate supplies the Capability;
- multiple unrelated candidates produce semantic ambiguity;
- multiple aliases of one contribution remain one candidate.

Resolution follows the immutable candidate-set and authority rules from 45-19.

A singleton contract may explicitly compose the 45-29 POO merge-priority
contract.  In that case the maximum-priority class is derived from the complete
candidate closure before cardinality validation:

- one strongest contribution may be selected with a priority proof;
- aliases of that contribution remain one candidate;
- tied unrelated strongest contributions remain ambiguous;
- weaker contributions remain suppressed evidence.

Without that explicit priority contract, singleton demand ignores priority
metadata.

A same-lineage prototype override remains distinct: it refines one contribution
before candidate cardinality is evaluated.

* Ordered same-lineage refinement contract

Some slots intentionally use native prototype precedence.

Their contract:

- preserves leftmost-more-specific =gerbil-poo= inheritance order;
- permits an inherited computation to delegate through =next=;
- distinguishes override from unrelated provider competition;
- records the exact prototype lineage and precedence;
- does not claim commutativity.

Reordering prototypes changes semantic identity for these slots.

This is appropriate for method-like behavior, policy refinement, diagnostic
specialization, and other same-lineage open computations.

It is not appropriate for unordered provider candidate sets.

* Authority contract

An authority slot follows attenuation.

Ordinary refinement may:

- reduce visible roots or submodules;
- reduce Capability or condition kinds;
- remove permitted dispositions;
- narrow generation or candidate scope;
- add stricter causal requirements.

Ordinary refinement may not union two grants into broader authority.

Creating a wider or combined grant requires a separately authorized
grant-construction object whose authority explicitly covers the successor
scope.

The base value may represent no authority.  It is not ambient administrative
authority.

* Observation-budget contract

An observation-budget slot uses the conservation model from 45-20 and 45-21.

Its operations include:

- immutable grant;
- attenuated delegation;
- consumption through semantic observation receipts;
- explicit reconciliation;
- successor-generation extension.

The contract does not use plain addition, maximum, or list union.

For each delegation generation:

#+begin_example
sum(child allocations) + parent retained allocation
  <= parent granted semantic units
#+end_example

Any extension or reallocation must bind explicit authority and predecessor
receipts.

* Receipt-chain contract

A receipt chain is an immutable causal transition structure.

A new receipt is valid only when:

- its predecessor identity is the current chain endpoint;
- its operation is authorized for that predecessor and generation;
- its successor identity is canonical for the operation evidence;
- no competing successor has silently committed.

Chain composition is not commutative.

Concatenation may be associative only for segments whose endpoints match and
whose generation and authority evidence validate.  Arbitrary list append is
invalid.

Repeated observation of the same canonical receipt is an alias and does not
advance the chain twice.

* Nested-module contract

Object-valued module and submodule slots use native ==>.+= refinement.

The contract preserves:

- the inherited child prototype;
- the overriding child refinement;
- native prototype precedence;
- the child's embedding-edge and causal-instance identities;
- demand-lazy child instantiation;
- parent-to-child Capability attenuation.

It does not merge child objects as dictionaries or copy them for alias
reachability.

Different embedding edges may create distinct child causal instances from the
same prototype.

* Diagnostic-evidence contract

Diagnostic evidence is either:

- a pure projection from immutable semantic evidence; or
- a canonical evidence set accumulated by identity.

Presentation ordering, log delivery, sampling, and UI rendering are outside
the semantic combination law.

Diagnostic combination cannot:

- resolve the condition being observed;
- acquire recovery authority;
- consume observation budget as semantic progress;
- make transport order causal.

* Defaults and contract identities

Native =?= is valid only when the contract defines a recursion base or explicit
absence behavior.

Examples include:

- canonical empty candidate or evidence sets;
- no-authority base;
- zero allocated child budgets under an enclosing grant;
- a structured unavailable-condition computation.

A default cannot be invented merely to prevent an error.  It must satisfy the
contract's identity or absence law.

An ordered contract without a lawful base may deliberately leave the slot
unbound until a more-specific prototype supplies it.

* General inherited computation

The explicit inherited-computation form may conditionally demand =next= only
according to the slot contract.

For example:

- a resolver contract may stop after a validated selection;
- a recovery contract may suspend before invoking inherited behavior;
- an authority contract may reject before delegating;
- a same-lineage policy may inspect evidence before continuing.

It cannot reinterpret =next= as provider search, skip candidate closure, or
violate conservation and predecessor continuity.

* Contract attachment

A semantic slot obtains its contract through ordinary POO composition and
Capability visibility.

The contract may be:

- inherited from a module prototype;
- supplied through an extra-slot requirement;
- refined by a more-specific contract prototype;
- projected and attenuated into a child object.

Contract attachment is part of canonical object identity.

Gerbil hygienic macros may eliminate repetitive attachment boilerplate, but
must expand directly to native POO object, slot, and import expressions.  No
runtime slot-contract registry is permitted.

* Conditions

Contract enforcement may produce structured continuable conditions:

- =slot-contract-unavailable= when a semantic slot lacks its required contract;
- =slot-contract-mismatch= when contribution and slot contracts are
  incompatible;
- =slot-successor-noncanonical= when a claimed successor identity does not
  match its evidence;
- =slot-predecessor-stale= when a transition names a closed predecessor;
- =slot-authority-insufficient= when the operation exceeds its grant;
- =slot-conservation-violation= when a budget successor creates units;
- =slot-cardinality-ambiguous= when a singleton candidate set has multiple
  unrelated members.

The condition carries the contract, slot, root, module-instance, predecessor,
generation, authority, contribution, and provenance identities as applicable.

The handler may recover only through dispositions authorized by that contract
and condition.

* Fixed-point progress

A native slot refinement counts as semantic progress only when its canonical
successor slot-state identity differs from its predecessor under the governing
contract.

Changes in:

- list insertion order;
- alias reachability;
- object pointers;
- closure identity;
- log delivery;
- handler retries;

do not count when the contract says the semantic state is unchanged.

This connects slot algebra directly to the observation-unit model from 45-20.

* Replay

Replay binds every slot transition to its contract identity and verifies:

- the lawful recursion base;
- contribution and predecessor identities;
- the declared combination law;
- canonical successor identity;
- cardinality, attenuation, conservation, or continuity constraints;
- authority and generation;
- receipt identity.

Replay does not look up a contract by string, execute a central enum switch, or
substitute a newer contract with a similar name.

* Runtime and ownership boundary

=gerbil-poo= owns native slot definition, inheritance, combination invocation,
and lazy fixed-point evaluation.

POO Flow owns the higher-order POO contract objects and their module-level
identity, Capability, authority, condition, evidence, and receipt semantics.

The runtime validates concrete transitions and preserves receipts.  It does not
choose slot algebra by runtime tag.

The harness performs algebraic and property-oriented validation.  It is not a
contract provider and does not define production semantics.

* Implementation checklist

- [ ] Represent every semantic slot contract as a POO object.
- [ ] Give each contract canonical prototype-lineage and runtime identities.
- [ ] Define recursion base or explicit absence behavior.
- [ ] Define the inherited combining operation.
- [ ] Declare only the algebraic properties the contract actually satisfies.
- [ ] Bind every successor to predecessor, contribution, contract, generation,
      and provenance.
- [ ] Use canonical-set contracts for unordered contributions.
- [ ] Separate singleton candidate closure from same-lineage override.
- [ ] Preserve native precedence for ordered refinement contracts.
- [ ] Enforce attenuation for authority slots.
- [ ] Enforce partition and conservation for budget slots.
- [ ] Enforce exact predecessor continuity for receipt chains.
- [ ] Use native ==>.+= for nested module contracts.
- [ ] Keep diagnostic evidence separate from presentation transport.
- [ ] Permit native =?= only for lawful contract bases.
- [ ] Count progress from canonical contract state, not host artifacts.
- [ ] Expand attachment macros directly to native POO expressions.
- [ ] Replay using canonical contract identities.
- [ ] Test algebraic properties and concrete transition failures.
- [ ] Verify that Mermaid edges explain the relevant state or transition
      without mechanical label prefixes.

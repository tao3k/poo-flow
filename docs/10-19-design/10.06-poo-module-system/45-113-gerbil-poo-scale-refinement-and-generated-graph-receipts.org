#+title: RFC 45-113 — gerbil-poo Scale Refinement and Generated Graph Receipts
#+status: Draft for discussion
#+language: en

* Status

This RFC defines the missing refinement boundary between the abstract,
scale-parametric proof in RFC 45-112 and executable graphs made from the unique
Scheme POO library, ~gerbil-poo~.

It does not admit the executable implementation.  It fixes the evidence that an
implementation must produce before POO Flow may claim that one
~use-composition~ safely operates hundreds or thousands of Modules.

* Decisions carried into this RFC

- ~gerbil-poo~ is the unique Scheme implementation of POO used by POO Flow.
- POO Flow reuses its object and prototype semantics; it does not implement a
  second fixed-point library.
- The public composition entry is ~use-composition~, not
  ~user-composition~.
- Modules, Profiles, imports, identities, capabilities, and receipts are
  POO-native objects or projections of POO-native objects.
- A generator may create executable evidence graphs, but it is not a second
  public Module language.
- Lean proves the abstract obligations.  Generated Gerbil runs establish the
  concrete refinement and resource envelope.  Neither substitutes for the
  other.

* Canonical public composition entry

The architecture has one public binding form:

#+begin_src scheme
(use-composition composition-name
  composition-expression)
#+end_src

It has exactly two operands after the macro name: one hygienic binding
identifier and one preserved Scheme expression.  The expression is evaluated
once and produces exactly one root instantiation.

There is no ~user-composition~ alternative, compatibility branch, legacy entry,
syntax-version token, deprecation period, source rewriter, or runtime adapter.
Because this is a new architecture, the proof model contains only the canonical
~use-composition~ constructor.

#+begin_src typst
$ E := { op("use-composition") } $

$ AdmittedEntry(e) iff e = op("use-composition") $

$ operands(op("use-composition")) = 2
  and eval-count(op("use-composition")) = 1
  and root-count(op("use-composition")) = 1 $
#+end_src

The synchronized Lean owners are:

- ~PooFlowProof.PooC3.ProfilePrototypeCorrespondence~, whose only
  ~CompositionEntryPoint~ is ~useComposition~;
- ~PooFlowProof.PooC3.MinimalUseCompositionSurface~, which admits the flat
  hygienic form and rejects nested or clause-DSL composition;
- ~PooFlowProof.PooC3.UseCompositionMacroContract~, which proves the thin macro
  boundary and direct replacement with no compatibility surface.

* Refinement boundary

** Abstract side

RFC 45-112 models a finite family of Modules with an index set ~Fin(n)~.  Each
Module contributes Profile selections, imports, and attenuating capability
constraints.  The abstract result is one composition root.

** Concrete side

The concrete witness is a finite graph whose nodes are native ~gerbil-poo~
objects:

- POO Flow declares a Module prototype whose native object slots project stable
  identity, imports, exported Profiles, and capability constraints;
- POO Flow declares a Profile prototype whose native object slots project
  stable identity and reachable responsibilities;
- an import edge refers to another Module identity;
- a final ~use-composition~ invocation selects the aggregate Profiles from
  which the reachable Module closure is computed;
- POO Flow declares receipt prototypes whose native object slots record the
  observed graph, closure, capability result, fixed-point outcome, resource
  attribution, and deterministic digest.

The concrete layer must not install Gerbil packages, resolve ~gerbil.pkg~
dependencies, or project a build-system graph.  Those concerns remain outside
this semantic refinement.

** Refinement relation

#+begin_src typst
#let refines(abstract, concrete) = (
  concrete.module_count == abstract.n
  and concrete.module_identities == abstract.module_identities
  and concrete.selected_profiles == abstract.selected_profiles
  and concrete.reachable_modules == abstract.reachable_modules
  and concrete.effective_capabilities == abstract.effective_capabilities
)

$ Refines(A_n, G_n) :=
    card(G_n.modules) = n
    and ids(G_n.modules) = ids(A_n.modules)
    and profiles(G_n.root) = profiles(A_n.root)
    and closure(G_n.root) = closure(A_n.root)
    and caps(G_n.root) = caps(A_n.root) $
#+end_src

Refinement is exact.  Matching only the final Profile count is insufficient:
identity, reachability, capabilities, and failure outcome must also agree.

* POO-native projection contract

The refinement adapter is internal.  It observes native objects without
introducing a competing public data model.

** Verified native ~gerbil-poo~ substrate

The local ~gerbil-poo~ checkout provides the following generic mechanisms:

- ~instantiate-proto~, ~identity-proto~, ~compose-proto~, and
  ~compose-proto*~ for functional prototype instantiation and composition;
- the native ~object~ representation with supers, direct slots, defaults,
  instance values, C3 precedence, computed slot functions, and the complete
  slot set;
- ~.def~ and the object construction macros for declarative object families;
- ~.@~ / ~.get~ for nested slot projection;
- ~.cc~ for a pure cloned object with explicit overrides;
- ~.putslot!~, ~.putdefault!~, and ~.put!~ as explicit mutation operations;
- native precedence computation that detects a circular precedence graph
  rather than silently recursing forever.

The scale refinement uses the functional and declarative route by default:
~compose-proto~ / ~compose-proto*~, declarative native objects, slot projection,
and pure ~.cc~ overrides.  Mutation operators are not the ordinary
~use-composition~ path; they remain behind explicit construction, runtime, or
observability boundaries.

The following concepts are not native domain concepts of ~gerbil-poo~:
~Module~, ~Profile~, ~imports~, ~capability~, ~receipt~, and
~use-composition~.  POO Flow defines them as prototypes, objects, slots, and a
thin hygienic projection over the verified native substrate.  It must not claim
that ~gerbil-poo~ itself owns those names or their policy.

In particular, stable Module/Profile identity is an explicit POO Flow slot.  It
must not be derived from an in-memory object address or treated as a
~gerbil.pkg~ package identity.

#+begin_src typst
$ project(m) := (
    identity: slot(m, "identity"),
    imports: slot(m, "imports"),
    profiles: slot(m, "profiles"),
    capabilities: slot(m, "capabilities"),
) $

$ op("use-composition")(p_1, dots, p_k)
    refine.eq
    op("instantiate-proto")(op("compose-proto*")(p_1, dots, p_k), b) $
#+end_src

The second equation states a refinement obligation, not the final Gerbil macro
expansion.  The hygienic ~use-composition~ form may project to ordinary
~gerbil-poo~ and functional code only after its exact expansion is approved.

** Domain projection table

| Abstract component | Concrete ~gerbil-poo~ witness | Required equality |
|-
| Module index | POO Flow ~identity~ slot on a native Module object | bijective identity map |
| Profile selection | POO Flow Profile object exported through a native slot | exact selected identity |
| import relation | POO Flow ~imports~ slot containing native Module objects | exact edge relation after identity projection |
| reachable closure | projected native Module objects | sound and complete identity set |
| capability meet | POO Flow capability object/slot | no capability amplification |
| fixed-point result | POO Flow observation over native evaluation | exact outcome |
| composition root | final ~use-composition~ native-object result | exactly one root |

#+begin_src typst
$ forall m in G_n.modules:
    project(m).identity = abstract(m).identity
    and project(m).imports = abstract(m).imports
    and project(m).profiles = abstract(m).profiles
    and project(m).capabilities subset.eq abstract(m).capabilities $
#+end_src

The adapter may normalize ordering for deterministic comparison.  It may not
invent missing identities, imports, Profiles, or authority.

** Ownership of the domain contract

RFC 45-93 owns ~Module~, ~Profile~, ~ProfileBundle~, ~imports~, ~profiles~,
identity projection, capability attenuation, and the constrained ~use-module~
boundary.  This RFC must refine those objects to the native substrate; it must
not redefine their domain meaning.

RFC 45-93 fixes those concepts at the object/projection level but does not yet
fix a public slot-level API.  The following is therefore a minimal candidate
projection for discussion, not an accepted new API:

| Object family | Candidate projected responsibilities |
|-
| Module | immutable native POO object; stable definition identity; exported stable Profiles; recursive imported Module objects; capability requirements; submodule relationships; revision/generation |
| Profile | immutable native POO value; stable Profile identity; owning Module identity; dependency projection; capability requirements; prototype lineage |
| ProfileBundle | immutable native POO value; Module definition and instance identities; selected Profile identities; selected dependency roots; capability requirements; revision/generation provenance; export-membership proof; admitted Profile-operand evidence |

The object graph retains native POO object references.  Stable identities are
projected at comparison, serialization, and receipt boundaries.  Replacing the
~imports~ edge with only a string or package coordinate would discard the POO
object graph and is not this refinement.

These rows are proof responsibilities, not a demand for one physical slot per
proposition.  An approved POO prototype may derive several proof
responsibilities from a smaller set of native slots and pure projections.

The corresponding negative boundaries are equally normative:

- a Module contains no live runtime authority, global registry entry, or
  package-installation behavior;
- selecting a Profile does not mutate its Module/Profile definition;
- a ProfileBundle contains only dependency roots reachable from its selected
  Profiles;
- ~use-module~ validates non-empty export membership and returns an independent
  ProfileBundle value;
- ~compose~ with the ~profiles~ strategy operates on admitted Profile values and
  ProfileBundles without changing their definition identities.

#+begin_src typst
$ imports(m) subset.eq G_n.modules $

$ op("receipt-imports")(m)
    := set(map(identity, imports(m))) $

$ op("receipt-imports")(m)
    = op("abstract-import-identities")(m) $
#+end_src

Before implementation, the owning RFC must either approve these slot
responsibilities or provide a smaller projection with the same refinement
information.

** Current User Interface evidence versus target surface

The four current User Interface cases — CrewAI, LangChain, LangGraph, and the
tool-calling agent loop — all use the correct outer name
~use-composition~.  They still exercise the old clause-parser implementation:

- one ~use-module~ clause selects a list of Profiles;
- a later ~compose~ clause repeats the same Profile identities;
- a ~stage~ clause separately carries graph, loop, proof, and handoff clauses.

This is implementation evidence, not the accepted target syntax.  The repeated
selection must not determine the new object model.

For one selected aggregate Profile, the target needs no redundant ~compose~
wrapper:

#+begin_src scheme
(use-composition crewai
  (use-module crewai as crew
    (profiles production)))
#+end_src

For several independent Profile or ProfileBundle values, ~compose~ remains a
pure value-level operation:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    base-profile
    (use-module crewai as crew
      (profiles production))
    observability-profile))
#+end_src

The ~production~ Profile owns the reachable low-level responsibilities.  The
outer form does not repeat them, parse their list, or inspect their semantics.

** Minimal physical slot proposal

The proof responsibilities can be refined from a small POO-native physical
surface:

| POO object | Physical slots proposed for discussion | Pure/computed projections |
|-
| Identity | definition, instance, revision, generation | stable digest and comparison identity |
| Module | identity, imports, profiles, capability | submodule closure, exported identities, provenance |
| Profile | identity, module, responsibilities, capability | dependency roots, prototype lineage evidence |
| ProfileBundle | module, profiles | identity, imports closure, effective capability, provenance, export-membership proof |

Here ~imports~, ~profiles~, ~responsibilities~, and ~capability~ contain
first-class POO values.  They are not raw strings, package coordinates, alists,
or policy records.

~ProfileBundle~ intentionally has only two physical slots.  Its other
obligations are computed from the selected native Module/Profile graph.  This
keeps ~use-module~ a pure projection instead of introducing a second materialized
graph that can drift from the Module definitions.

#+begin_src typst
$ bundle(m, P) := (
    module: m,
    profiles: P,
) $

$ op("bundle-imports")(bundle(m, P))
    := closure(union(map(op("dependency-roots"), P))) $

$ op("bundle-capability")(bundle(m, P))
    := meet(capability(m), meet(map(capability, P))) $

$ op("bundle-identity")(bundle(m, P))
    := digest(identity(m), op("ordered-map")(identity, P)) $
#+end_src

** Physical refinement proof

The confirmed proposal is modeled by
~PooFlowProof.PooC3.GerbilPooPhysicalRefinement~:

- ~PhysicalIdentity~ contains definition identity, instance identity,
  revision, and generation;
- ~PhysicalModule~ contains exactly identity, imported Module-object
  references, exported Profile-object references, and capability;
- ~PhysicalProfile~ contains exactly identity, owning Module-object reference,
  responsibility-object references, and capability;
- ~PhysicalProfileBundle~ contains exactly the Module object and selected
  Profile objects;
- ~ProjectionOps~ supplies pure projections for identity, imports, exports,
  dependency roots, capability meet, closure, and bundle digest;
- ~PhysicalBundleAdmission~ requires a non-empty selection, export membership,
  and preservation of the owning Module;
- ~BundleObservation~ is the receipt-facing identity/import/capability
  projection;
- ~RefinesPhysicalBundle~ is exact equality between the derived observation and
  the abstract observation.

The Lean theorems prove that the two physical ProfileBundle fields determine
the whole bundle and its observation, while imports, capability, and bundle
identity are derived.  No duplicate materialized dependency graph is required.

The Typst definitions in [[*Minimal physical slot proposal]] are the synchronized
mathematical surface for the Lean definitions
~useModuleProjection~, ~bundleImports~, ~bundleCapability~, and
~bundleIdentity~.

* Stable identity and deterministic digest proposal

One undifferentiated hash cannot safely serve definition equality, semantic
cache reuse, live root identity, and receipt identity.  The identity object
therefore separates four components:

| Component | Meaning | Must change when | Must not change when |
|-
| definition | semantic POO declaration identity | the declared prototype/object meaning changes | a lexical import alias changes |
| instance | one declared Module/Profile instance | a distinct instance is declared | its lexical binding is renamed |
| revision | one immutable semantic revision | content, contract, capability contract, or dependency revision changes | an equivalent live context observes it |
| generation | one activated runtime generation | a new activation is published | a semantic cache key is computed |

No component is a ~gerbil.pkg~ identity, filesystem path, transient object
address, or package-manager coordinate.

** Two derived bundle identities

~ProfileBundle~ derives two identities from its two physical fields:

- semantic identity is suitable for exact semantic comparison and cache keys;
- activation identity binds that semantic identity to one live generation.

The canonical semantic preimage contains:

1. a domain-separation tag;
2. Module definition identity;
3. Module instance identity;
4. selected Profile revision identities in declared composition order;
5. reachable import revision identities normalized as a set by stable identity;
6. the effective capability-contract identity.

Declared Profile order is semantic because POO prototype composition is
ordered.  Import traversal order is not semantic; the reachable import closure
is normalized before encoding.

#+begin_src typst
$ op("semantic-preimage")(b) := (
    "poo-flow/profile-bundle/semantic/v1",
    op("definition-id")(b.module),
    op("instance-id")(b.module),
    op("ordered-map")(op("revision-id"), b.profiles),
    sort(set(map(op("revision-id"), op("bundle-imports")(b)))),
    op("capability-contract-id")(op("bundle-capability")(b)),
) $

$ op("semantic-id")(b)
    := H(op("canonical-encode")(op("semantic-preimage")(b))) $

$ op("activation-preimage")(b, g) := (
    "poo-flow/profile-bundle/activation/v1",
    op("semantic-id")(b),
    op("generation-id")(g),
) $

$ op("activation-id")(b, g)
    := H(op("canonical-encode")(op("activation-preimage")(b, g))) $

$ op("observed-semantic-id")(b, g) := op("semantic-id")(b) $
#+end_src

** Required laws

#+begin_src typst
$ p_1 = p_2 => H(op("canonical-encode")(p_1))
    = H(op("canonical-encode")(p_2)) $

$ op("semantic-component")(op("rename-lexical")(x, n))
    = op("semantic-component")(x) $

$ op("semantic-id")(b_1) = op("semantic-id")(b_2)
    and op("semantic-preimage")(b_1)
      != op("semantic-preimage")(b_2)
    => op("fail-closed")("identity collision") $

$ op("observed-semantic-id")(b, g_1)
    = op("observed-semantic-id")(b, g_2) $

$ g_1 != g_2 => op("activation-id")(b, g_1)
    != op("activation-id")(b, g_2) $
#+end_src

The final line is an admission obligation over accepted generation identities,
not a mathematical claim that an arbitrary finite hash is globally injective.
The receipt retains the canonical preimage digest components so a detected
collision fails closed instead of merging semantic objects.

** Separation from existing identity owners

- ~CompositionIdentity~ owns lexical name, runtime root, content identity, and
  rename invariance.
- ~ProfileRevisionUpgrade~ owns immutable revisions, generation binding, source
  pin changes, and the prohibition on path-only cache reuse.
- ~SlotDemandIdentity~ owns the separation between semantic cache identity and
  live demand context.
- ~DependencySourceIdentity~ remains a source-resolution/build-boundary proof;
  it does not become the POO Module/Profile identity algorithm.
- this RFC owns only the deterministic ProfileBundle semantic/activation
  preimages used by the concrete refinement and its receipts.

* Generated graph families

Generated graphs exercise distinct semantic shapes rather than merely changing
one integer:

- wide graphs with many independent Module contributors;
- deep acyclic import chains;
- diamond graphs with heavily shared dependencies;
- nested submodule graphs representing arbitrary business hierarchies;
- productive cyclic graphs that reach a fixed point;
- non-productive cyclic graphs that suspend or fail closed;
- graphs with deliberately conflicting identities;
- graphs with deliberately attempted capability amplification.

Every graph is built from native ~gerbil-poo~ objects and reaches the ordinary
~use-composition~ entry.  Test-only graph constructors must not become an
alternative user interface.

* Receipt object family

The runtime-facing values are POO-native receipt objects.  Serialization is an
evidence boundary, not the public composition interface.

** Graph identity receipt

- schema identity and version;
- generator identity and deterministic seed;
- requested and observed Module counts;
- Module, Profile, and import-edge digests;
- graph-family identity;
- one final composition-root identity.

** Semantic refinement receipt

- abstract-model digest;
- concrete-object-graph digest;
- selected Profile identities;
- reachable Module identities;
- closure soundness result;
- closure completeness result;
- effective capability identities;
- refinement verdict and exact mismatch witnesses.

** Fixed-point and recovery receipt

- productive, suspended, or failed-closed outcome;
- evaluated object/slot identity;
- dependency path or strongly connected component identity;
- evaluation count and bounded-step limit;
- first-class recovery decision and continuation identity when recovery is
  offered;
- proof that recovery did not add authority or silently omit a Module.

** Resource attribution receipt

- wall and CPU time by named phase;
- process identifiers and process-tree identity;
- peak RSS plus PSS or platform footprint;
- largest process and phase at the observed peak;
- cache mode and incremental-reuse identity;
- limit verdict with the measured value and configured envelope.

* Scale matrix

The minimum admission matrix is cumulative:

| Scale | Required graph families | Purpose |
|-
| 100 Modules | wide, deep, diamond, productive cycle, failed cycle | focused correctness |
| 1,000 Modules | wide, deep, shared, nested submodules, cycles | ordinary scale admission |
| 10,000 Modules | wide, shared, nested submodules, bounded cycles | stress envelope evidence |

A smaller graph passing does not admit a larger scale.  A 10,000-Module wide
graph does not substitute for deep, shared, nested, or cyclic witnesses.

* Failure-closed admission

The executable claim is rejected when any required receipt is absent, stale,
non-deterministic, or mismatched.  In particular:

- a Lean theorem pass alone is not executable admission;
- a final Profile count alone is not refinement;
- a timeout without the evaluated object and dependency path is not a cycle
  receipt;
- summed process-tree RSS without phase and process attribution is not a
  resource receipt;
- silently dropping an unreachable-looking Module is not closure recovery;
- falling back to an ad hoc record, alist, or second composition language is
  not a ~gerbil-poo~ witness.

* Confirmed stable identity proof

This section closes the previously approved stable-identity proposal at the
proof boundary.  It does not select the canonical byte encoding or digest
algorithm, and therefore does not admit a concrete Gerbil implementation yet.

The proof owner is
=PooFlowProof.PooC3.ProfileBundleStableIdentity=.  It is adjacent to
=GerbilPooPhysicalRefinement=: the physical refinement owns the concrete
=Module=, =Profile=, and two-slot =PhysicalProfileBundle= projections, while
this new owner fixes the semantic and activation identity preimages.

** Identity boundary

A =ProfileBundle= has two derived identities:

- semantic identity is used for equality, comparison, and semantic cache
  addressing;
- activation identity adds the runtime generation and is used for a live root
  and its receipt.

Neither identity is a =gerbil.pkg= package identity, dependency-source
identity, filesystem path, lexical alias, process-local object address, or
package coordinate.  In particular,
=PooFlowProof.DependencySourceIdentity= remains the owner of source and build
boundary identity; it is not the POO object identity algorithm.

The semantic preimage contains exactly:

1. a domain-separation tag;
2. the Module definition identity;
3. the declared Module instance identity;
4. the selected Profile revision identities in declared order;
5. reachable import revision identities normalized as a set by stable
   identity;
6. the effective capability-contract identity.

Profile order is semantic.  Import traversal order is not semantic.  A lexical
rename cannot change semantic identity.  Runtime generation cannot change
semantic identity, but it is an explicit input to activation identity.

#+begin_src typst
#let semantic-preimage(definition, instance, profiles, imports, capability) = (
  domain: "poo-flow.profile-bundle.semantic.v1",
  definition: definition,
  instance: instance,
  profiles: profiles,
  imports: imports,
  capability: capability,
)

#let activation-preimage(semantic, generation) = (
  domain: "poo-flow.profile-bundle.activation.v1",
  semantic: semantic,
  generation: generation,
)

$ S(M, P, I, C) =
  H_s(semantic-preimage(M.definition, M.instance, P, norm-set(I), C)) $

$ A(S, G) = H_a(activation-preimage(S, G)) $

$ "Perm"(I_1, I_2) => norm-set(I_1) = norm-set(I_2) $

$ x != y and H_s(x) = H_s(y) => admitted(x, y) = false $
#+end_src

The third equation applies only to permutations of the reachable-import list;
the selected Profile list is intentionally not normalized.  The fourth
equation is the fail-closed collision rule.  No theorem assumes that an
arbitrary finite digest is injective.

** Confirmed canonical byte encoding

The canonical encoding is the core deterministic encoding from RFC 8949,
restricted further to definite-length arrays, byte strings, and unsigned
integers.  Maps, floating-point values, tags, indefinite-length items, Scheme
printer output, symbols, and lexical source names are outside the admitted
identity grammar.

The semantic preimage has the following fixed positional schema:

#+begin_src typst
#let semantic-v1(
  module-definition,
  module-instance,
  ordered-profile-revisions,
  normalized-import-revisions,
  capability-contract,
) = (
  "poo-flow/profile-bundle/semantic",
  1,
  module-definition,
  module-instance,
  ordered-profile-revisions,
  normalized-import-revisions,
  capability-contract,
)

#let activation-v1(semantic-identity, generation-identity) = (
  "poo-flow/profile-bundle/activation",
  1,
  semantic-identity,
  generation-identity,
)

$ bytes_s = "deterministic-cbor"(semantic-v1(M_d, M_i, P, norm(I), C)) $
$ bytes_a = "deterministic-cbor"(activation-v1(H_s(bytes_s), G)) $
#+end_src

The selected Profile revision list is ordered and duplicate-free.  Its order
is semantic because it records POO composition precedence; a duplicate is an
admission error rather than a silently normalized value.

The reachable import revision list has set semantics.  It is sorted
lexicographically by each complete canonical stable-identity byte string and
duplicates are removed.  It is never sorted by the enclosing bundle digest,
so import normalization does not introduce a circular digest dependency.

All nested identities are opaque canonical byte strings supplied by their
actual semantic owner.  This RFC does not convert lexical names, Unicode
spellings, filesystem paths, package coordinates, or Scheme object
representations into stable identities.

** Typed digest and immutable version family

The binary digest and its textual display are different values.  The semantic
value is a typed reference:

#+begin_src typst
#let digest-ref(algorithm, domain-version, digest-bytes) = (
  algorithm: algorithm,
  domain-version: domain-version,
  digest: digest-bytes,
)

$ "DigestRef" = (algorithm, domain_version, bytes_32) $
#+end_src

Hexadecimal or Base32 text is only a UI projection and never re-enters the
hashed preimage.  The concrete digest algorithm remains open until a real
Gerbil library owner and API are verified.  No new hash implementation or FFI
is admitted merely to satisfy this RFC.

Version policy is already fixed:

- a published version is never reinterpreted;
- any change to field meaning, field order, normalization, encoding, or digest
  algorithm creates a new identity family;
- there is no deprecation period, compatibility translator, or silent
  cross-version equality;
- cross-version semantic equivalence requires an explicit proof receipt and
  does not make the two identities equal.

** Collision-store admission

An identity store retains the canonical preimage bytes, or an immutable exact
artifact reference to those bytes, together with the digest.  A second digest
cannot establish collision safety because it merely moves the same assumption
to another function.

#+title: Resumption-Contribution Generation Closure
#+startup: overview

* Status

Accepted design.

This document refines multi-shot continuation recovery from
[[file:45-22-continuation-resumption-and-budget-generation.org][45-22]].
It defines how continuation invocations become immutable POO contributions,
how their candidate set closes, and when a semantic successor may commit.

It prevents host execution order from selecting fixed-point results.  It does
not restrict Scheme continuations to one shot and does not introduce a
scheduler, mutable candidate accumulator, or callback registry.

* Problem

A multi-shot continuation may be invoked again at any later host time.  If an
invocation directly committed a semantic successor, the first invocation to
finish could determine the fixed-point result before another valid invocation
became visible.

Wall-clock waiting cannot prove that no future invocation exists.  Runtime
quiescence, handler return order, thread completion, and timeouts are therefore
not semantic candidate-closure evidence.

* Decision

Invoking a continuation produces an immutable resumption contribution.  It
does not directly resume and commit the suspended Capability demand.

Contributions are admitted into an immutable resumption generation.  Native
=gerbil-poo= fixed-point evaluation closes the active contribution set for the
generation.  Only the closed set can authorize evaluation of a semantic
successor.

A host invocation observed after closure becomes an external causal input to a
successor resumption generation.  It does not reopen, invalidate, or mutate the
closed historical generation.

* Contribution identity

A resumption contribution has canonical causal identity derived from:

- the suspension identity;
- the root and module-instance identities;
- the Capability demand identity;
- the resumption generation;
- the canonical resume-input identity;
- the contributing POO policy identity;
- the contributor authority scope;
- causal provenance.

Host continuation address, thread identity, invocation ordinal, stack address,
wall-clock time, handler order, and scheduling order are excluded.

Two observations of the same canonical contribution identity are aliases of
one contribution.  They do not increase cardinality and do not consume
additional observation units.

Different resume inputs normally create different contribution identities.
They are not disguised as nondeterministic outputs from one contribution.

* Immutable generation construction

An open generation evolves through immutable candidate-set successor states.
Each state binds its predecessor set identity and the newly admitted canonical
contribution identity.

There is no mutable set shared by handlers.  Reordered admission of the same
canonical contribution closure produces the same candidate-set identity.

A generation closes from semantic fixed-point stabilization over the current
causal input closure.  Closure is evidenced by:

- the root and resumption-generation identities;
- the suspension and demand identities;
- the canonical unordered candidate-set identity;
- the fixed-point predecessor and stabilized successor identities;
- the observation-budget generation;
- causal provenance.

Closure is not inferred from elapsed time, absence of runnable threads, queue
emptiness, handler return, or process idleness.

The cycle and semantic-progress rules of
[[file:45-20-fixed-point-convergence-observation-budget.org][45-20]] apply while
the candidate set is being derived.

* Closed-set interpretation

For an ordinary singleton Capability demand:

- zero contributions preserve the suspended demand;
- one canonical contribution may resume the demand;
- more than one distinct contribution produces =resumption-ambiguity=.

For an explicitly declared multi-result Capability contract, the closed
canonical set may be passed as a set-valued semantic input.  Its meaning comes
from that Capability contract; insertion order and provider order remain
irrelevant.

Singleton ambiguity cannot be hidden by selecting the first contribution,
sorting by module name, comparing resume values, or using handler priority.

* Resolution

=resumption-ambiguity= carries the immutable closed candidate set, suspension
identity, demand identity, predecessor observation identity, budget generation,
and causal provenance.

Resolution is an explicit higher-order POO policy over the already discovered
candidate set.  For a singleton demand its dispositions are:

- =select(contribution-identity)=;
- =decline=.

The resolution proof binds the complete candidate-set identity and generation.
It is stale if either changes.  Resolution cannot synthesize a contribution,
merge arbitrary resume inputs, widen budget authority, or search for new
providers.

Decline preserves the suspension and propagates the condition.  It is not
cancellation and does not consume an observation unit.

* Deterministic evaluation and observation fork

After a singleton contribution has been selected and all generation evidence
has been revalidated, the suspended demand may evaluate.

The distinction between the two ambiguity classes is:

- =resumption-ambiguity=: multiple canonical input contributions exist in one
  closed resumption generation;
- =observation-fork=: one selected canonical input contribution claims
  different canonical semantic successors for the same predecessor.

Thus multi-shot inputs are closed and resolved before evaluation, while
genuine nondeterminism during evaluation remains visible as an observation
fork.

* Late contributions and successor generations

Once a generation is closed, its candidate-set identity and resolution proof
remain immutable.

A later host invocation creates a contribution for a successor generation.
Creating that generation requires an explicit causal boundary receipt binding
the closed predecessor generation and the new external input.

The successor generation revalidates:

- whether the suspension is still live;
- whether the predecessor semantic state remains current;
- whether cancellation or reconciliation has occurred;
- which budget generation authorizes further evaluation;
- whether a continuation rebase proof is required by 45-22.

A late contribution cannot retroactively consume an old allocation, invalidate
a historical receipt, or cause a previously closed candidate set to grow.

* Budget accounting

Creating, deduplicating, closing, selecting, or declining resumption
contributions does not itself consume a semantic observation unit.

An observation unit is consumed only when authorized semantic evaluation
commits an immutable predecessor-to-successor transition receipt.

The work required to derive candidate closure remains subject to the semantic
progress budget and host resource guard of 45-20.  These controls do not alter
candidate cardinality or select a contribution.

* Submodule boundary

A child module receives only the resumption contributions and authority
explicitly projected through its Capability boundary.

Parent and sibling handlers cannot inject ambient contributions into a child
generation.  Re-export and alias reachability do not duplicate a canonical
contribution.  Distinct child causal instances retain distinct contribution
identities.

* Replay

Replay reconstructs:

- immutable candidate-set successor states;
- the closed canonical candidate set;
- singleton or multi-result interpretation;
- ambiguity and resolution evidence;
- the selected contribution;
- semantic transition or fork evidence;
- successor generations created by late inputs.

Replay does not invoke the continuation, wait for additional contributions,
consult a live handler, or reopen a closed generation.

Historical contribution and resolution authority is evidence only.  It does
not authorize a live resumption.

* Runtime and ownership boundary

The runtime transports live continuation invocation across the explicit effect
boundary and preserves the resulting POO evidence.  It does not decide
candidate closure, selection, or fixed-point meaning.

Native =gerbil-poo= supplies the POO evaluation semantics.  POO Flow defines
the contribution identities, generation closure, conditions, authority
scopes, and receipts.

The harness validates candidate-set determinism, generation isolation, and
replay.  It is not a contribution provider, resolver, or scheduler.

* Implementation checklist

- [ ] Project every live continuation invocation into an immutable resumption
      contribution.
- [ ] Exclude host timing, address, thread, and ordinal data from canonical
      contribution identity.
- [ ] Deduplicate identical canonical contributions.
- [ ] Build candidate sets through immutable successor states.
- [ ] Close generations from semantic fixed-point evidence, never wall-clock
      quiescence.
- [ ] Interpret zero, singleton, and multiple candidates by Capability
      contract.
- [ ] Raise =resumption-ambiguity= before evaluating a singleton demand with
      multiple inputs.
- [ ] Bind resolution proofs to the complete candidate set and generation.
- [ ] Distinguish input ambiguity from evaluation-time
      =observation-fork=.
- [ ] Route late invocations into explicit successor generations.
- [ ] Revalidate suspension, predecessor, budget, cancellation, and rebase
      evidence for successor generations.
- [ ] Consume semantic budget only at committed observation transitions.
- [ ] Replay closed generations without live continuations or handlers.
- [ ] Test reordered admission, duplicate inputs, distinct inputs, resolution,
      decline, late invocation, cancellation, rebase, fork, and replay.
- [ ] Verify that Mermaid edges explain state and transition meaning without
      mechanical label prefixes.

* 10.06.163 Standard Module, Lazy Industry Packs, and Conformance Receipts

** 10.06.163.10 Decision

POO Flow SHALL provide one core =standards= module for declaring, selecting,
resolving, composing and verifying external standards.  Concrete Standard
Providers and immutable packs live in their owning vertical modules; Lambda
Episteme Healthcare owns the first FHIR Provider and pack composition.  Other
independent contributors may publish their own industry modules, domain
mappings, Profiles and Cases against the core Standards protocol.  Applications SHALL
select exact standard editions through Profiles and bind the resulting closed
standard bundle to a Case.

The Standard module is a capability owner, not a central copy of every
standard.  A catalog containing one thousand or ten thousand standards keeps
only lightweight immutable references resident.  Standard content is
materialized on demand from content-addressed packs, and only the transitive
artifact closure selected by the active Profile and Case may become a POO
object graph or executable validation closure.

External standard data is not automatically a Scheme module.  JSON, XML,
Turtle, schemas, tables, code systems and profile definitions SHALL remain
inert data artifacts.  A small stable set of Scheme modules owns resolution,
composition, validation and receipts.  Domain behavior or an actual language
grammar may have executable owners, but ordinary standard data SHALL NOT be
compiled into one permanently loaded Gerbil module per standard.

FHIR is the first planned concrete Standard Provider composed by Lambda
Healthcare on top of POO Flow Standards.  FHIR JSON and XML do not
create a =gerbil-parser= dependency: ordinary data readers preserve syntax,
while the Lambda Healthcare FHIR Provider owns FHIR conformance meaning.
An actual language embedded in the ecosystem, such as FHIRPath, may later use
a separately qualified parser-owned frontend without transferring FHIR,
Healthcare or national implementation-guide ownership to =gerbil-parser=.

** 10.06.163.20 Goals

- Make an external standard a versioned, source-bound, composable POO value.
- Let Profiles select standards without loading every catalog member.
- Let Cases bind exact editions and dependency closures without ambient
  =latest= resolution.
- Reuse the existing POO Flow source-ref, catalog, loader, fixed-point,
  observability and receipt boundaries.
- Support cross-industry composition without moving industry vocabulary into
  POO Flow core.
- Separate discovery, resolution, loading, materialization, conformance and
  application admission evidence.
- Keep startup and resident memory proportional to the catalog index plus the
  active closure, not to the total number of available standards.
- Permit deterministic eviction and generation replacement without changing
  the meaning of an already admitted Case.

** 10.06.163.30 Non-goals

- The domain-neutral Standards contracts do not interpret FHIR, US Core,
  AU Core, ISO 20022, ISA-95, NASA NPR 7150.2D or another concrete industry
  standard; separately owned Providers below the core module may implement
  those standards.
- The Standard module does not grant regulatory certification, clinical
  authority, release authority or permission to execute an external effect.
- Catalog discovery does not prove that content loaded or passed conformance.
- Parsing JSON or XML does not prove that the represented artifact conforms to
  an industry standard.
- The public API is not a raw alist DSL, a patch language or an ordinary
  =(lambda (self super) ...)= hook surface.
- Importing a Standard module or Profile does not perform network I/O, expand
  a terminology set, execute validation or activate an application.
- The first implementation does not need to support every representation,
  standard family or FHIR resource.
- This RFC does not introduce a second module loader, global package manager or
  mutable process-wide current-standard registry.

** 10.06.163.40 Ownership

| Owner | Owns | Must not own |
|-------+------+--------------|
| POO Flow =standards= core | Standard types, POO protocols, exact selection, dependency-closure rules, load/materialization contracts, validation-closure contracts, budgets and receipts | Application-domain vocabulary, ambient standard selection |
| POO Flow module system | Source refs, ordered load paths, loader admission, lazy-slot observability and module receipts | Interpreting a concrete standard artifact |
| Lambda vertical Standard Provider | Concrete industry Standard families, editions, machine-readable packs and conformance semantics | Core Standard protocol or generic loader semantics |
| Lambda Episteme | Vertical Provider modules, industry mappings, Profiles, Cases, authoritative domain Sources and use of admitted Standard bundles | Core Standard protocol or generic loader semantics |
| Standard pack publisher | Immutable artifacts, package index, dependency declarations, provenance and digest | Runtime activation or Case admission |
| Optional language parser owner | Lossless syntax and typed parse evidence for a real DSL such as FHIRPath | Domain conformance, terminology truth or application authorization |
| Runtime Provider | Bounded execution of an admitted validation closure and external terminology requests | Selecting an ambient version or mutating a standard bundle |
| Application | Profile, Case, Provider and exact lock selection | Reinterpreting a failed or stale receipt as success |

No reverse dependency from POO Flow to Lambda Episteme is permitted.  Mounting
or importing a contributor package does not activate any of its standards.

** 10.06.163.50 Vocabulary and object model

*** 10.06.163.51 =StandardFamily=

A stable family identity such as HL7 FHIR, ISO 20022 or NASA NPR 7150.2.  It
does not imply an edition, jurisdiction or artifact closure.

Required identity fields:

- canonical family identity;
- publisher/owner identity;
- semantic kind;
- permitted representation families;
- lifecycle and license metadata.

*** 10.06.163.52 =StandardEdition=

An immutable release of one Standard family.  Its identity SHALL include:

- canonical URI;
- exact version;
- optional package identity;
- applicable specification release;
- jurisdiction when part of standard identity;
- source digest or immutable source-set digest;
- lifecycle state and validity interval.

Two editions with the same human label but different content digests are not
the same edition.  Runtime selection SHALL NOT resolve a bare =latest= label.

*** 10.06.163.53 =StandardArtifactRef=

A lightweight reference to an atomic artifact.  It contains identity,
artifact kind, source location, digest, dependency summary, an explicit source
loader and a separate materializer, but not loaded source bytes, the parsed
artifact or an executable validation closure.

The source loader returns a typed =StandardArtifactSource= containing inert
payload, exact digest, representation and byte count.  Only after those facts
match the reference may the materializer project that source into a typed
=StandardArtifact=.  A successful =StandardLoadReceipt= therefore proves source
admission independently of materialization success; it is not synthesized from
a materialized artifact after the fact.

Examples include a FHIR =StructureDefinition=, a =ValueSet=, a specification
section, a normative table or a machine-readable conformance profile.

*** 10.06.163.54 =StandardConstraintProfile=

A declared refinement of one or more accepted base editions.  This name is
deliberately more precise than an unqualified =Profile=: a POO Flow Profile
selects capabilities for an application composition, while a
=StandardConstraintProfile= describes standard-level constraints and
refinement.

A refinement SHALL state:

- its own identity and exact revision;
- every accepted base identity and version range or exact edition;
- added, tightened or explicitly varied constraints;
- compatibility and conflict rules;
- artifact and terminology dependencies;
- provenance and qualification state.

Declaration order is not precedence.  A later profile cannot silently
overwrite an earlier constraint.

*** 10.06.163.55 =StandardBundle=

The immutable result of exact selection and dependency resolution.  A bundle
contains the selected roots, the ordered closed dependency graph, artifact
identities, source digests, terminology snapshot references, conflict result,
budget result and one closure digest.

The bundle is a pure value.  It is not a loaded Gerbil module, a validation
result or an application permission.

*** 10.06.163.56 =StandardValidationClosure=

A Provider-neutral, immutable closure compiled from one admitted Standard bundle
for a declared validation subject kind.  The closure identifies each constraint,
terminology request and dependency needed at execution time.  It carries no
ambient network handle and grants no effect capability.

A =StandardValidationClosure= is not a plan, DAG, execution graph or scheduler.
It owns no execution nodes, dependency edges, ready frontier, ordering, retry or
dispatch policy.  The Runtime Provider decides how to evaluate the closed set of
constraints and returns a =StandardConformanceReceipt=.  If validation execution
later requires a DAG, that is a separate =StandardValidationGraph= value with its
own graph contract and must not be hidden behind the closure name.

*** 10.06.163.57 Receipt families

The Standard module SHALL preserve the following separate evidence:

1. =StandardCatalogReceipt= -- which lightweight references were visible;
2. =StandardResolutionReceipt= -- how exact editions and dependencies resolved;
3. =StandardLoadReceipt= -- which immutable bytes were actually loaded;
4. =StandardMaterializationReceipt= -- which artifacts became typed POO values;
5. =StandardValidationClosureReceipt= -- which closed constraints formed a validation closure;
6. =StandardConformanceReceipt= -- which constraints passed, failed or could not
   be evaluated for one exact subject snapshot;
7. =StandardCaseAdmissionReceipt= -- whether an application Case accepted the
   conformance evidence alongside its other governance evidence.

No receipt may be substituted for a later receipt in this sequence.

*** 10.06.163.58 Mandatory Governance Interface and optional evidence

Every =StandardFeatureModule= SHALL carry one typed =governance= Interface and
the methods =.write-governance= and =.validate-governance=.  The Interface is
not optional metadata.  It declares four separate facts:

- =required-slots=: closed governance obligations owned by the Feature;
- =optional-slots=: admitted enrichment that cannot replace an obligation;
- =stage-requirements=: the status accepted for each required Slot at each
  lifecycle stage; and
- =bindings=: immutable, typed evidence currently written to those Slots.

For the core Migration Feature the required Slots are:

| Slot | Meaning |
|------+---------|
| =authority-provider= | exact authorization Provider and policy boundary |
| =human-authorization= | human-owned authorization Interface or admitted decision |
| =formal-model= | qualified transition-system evidence |
| =refinement-proof= | qualified proof refining the formal model |
| =impact-contract= | exact upstream-to-downstream digest and theorem impact |
| =conformance= | target Standard conformance evidence |
| =audit-receipt= | source, proposal, review and admission audit binding |

The optional Slots are =documentation=, =presentation-metadata=,
=reference-implementation= and =non-authoritative-analysis=.  Optional means
that absence does not block a stage.  It never means that an Agent may invent
an undeclared Slot or use optional evidence in place of a required Binding.

The lifecycle policy is staged.  =declaration= may describe the Interface
without materialized evidence.  =review= requires qualified formal-model,
refinement, impact and conformance Bindings.  =admit= requires all seven Slots
at =qualified= or =admitted=.  =cutover= requires all seven at =admitted=.
Thus a qualified Cedar human-authorization Interface is enough to evaluate a
migration admission, but only a fresh admitted Cedar human permit can satisfy
the cutover Slot.

An Agent writes governance only through =.write-governance=.  The method
rejects untyped Bindings, undeclared Slots, invalid vertical payloads and stale
impact digests, and returns a new immutable Interface.  It does not mutate a
process-wide registry.  =.validate-governance= returns a typed receipt listing
required, bound, missing and invalid-status Slots; callers SHALL NOT infer
success from Slot presence alone.

Vertical modules own the concrete Slot validator and evidence payloads.  A
Case retains the stable Interface identity and graph relationships, while the
vertical Standard Feature remains the sole owner of the executable Interface.
This avoids copying self-referential POO methods into Case evidence contexts.

** 10.06.163.60 Dependency and authority flow

#+begin_src mermaid
flowchart LR
    C["Lightweight Standard Catalog"]
    S["Profile / Case exact selection"]
    R["Resolver and bounded load closure"]
    P["Immutable Standard Packs"]
    M["Selected artifact materialization"]
    V["Provider-neutral validation closure"]
    H["Runtime Provider"]
    ADMISSION["Case admission"]

    C -->|"StandardRef only"| S
    S -->|"exact roots"| R
    R -->|"content-addressed refs"| P
    P -->|"selected transitive closure"| M
    M -->|"typed constraints"| V
    V -->|"explicit bounded handoff"| H
    H -->|"conformance receipt"| ADMISSION
#+end_src

Catalog discovery and semantic execution remain distinct.  Resolver and loader
work SHALL be explicit named operations; a normal POO slot reference SHALL NOT
hide filesystem, registry, package-download, terminology or network effects.

** 10.06.163.70 Lazy loading and scale contract

*** 10.06.163.71 Five lazy boundaries

The implementation SHALL distinguish:

1. *Lazy discovery*: catalog construction exposes =StandardRef= values only.
2. *Lazy package load*: an exact selected edition loads only its package index.
3. *Lazy artifact source load*: only selected inert artifact sources cross the
   explicit effect boundary and produce =StandardLoadReceipt= values.
4. *Lazy artifact materialization*: only the transitive artifact closure needed
   by the selected Profile/Case becomes typed POO values.
5. *Lazy validation-closure construction*: only constraints required by an actual validation
   subject become a Provider-neutral validation closure.

Wrapping a static import of every standard in a thunk does not satisfy this
contract.  Static imports, macro expansion, top-level object construction and
Gerbil module initialization SHALL NOT enumerate or realize all standard
content.

*** 10.06.163.72 Data packs, not one executable module per standard

Concrete standards SHALL normally be published as immutable Standard packs:

#+begin_example
standard-pack/
  package-metadata
  artifact-index
  dependency-edges
  artifacts-by-canonical-identity/
  source-digests
  optional-precompiled-closure-inputs/
#+end_example

The artifact index is small enough for bounded discovery and may be sharded.
Artifact bodies remain outside the resident index until selected.

Gerbil modules own generic code and contributed behavior.  They do not become
an append-only heap of every standard artifact ever observed.  Loaded artifact
values and validation closures SHALL therefore be held in explicit evictable cache
contexts rather than relying on unloading Gerbil modules.

*** 10.06.163.73 Closure granularity

Resolution occurs at artifact granularity.  Selecting one national Healthcare
patient profile may load its base patient definition, referenced data types,
extensions, invariants and required terminology references.  It must not load
every resource, code system or unrelated national guide in the same catalog.

Terminology expansion is independently lazy.  A =ValueSet= reference does not
require eager loading of an entire terminology distribution.  A closure records
the exact terminology snapshot or Provider request needed for evaluation.

*** 10.06.163.74 Cache identity

Caches SHALL be content addressed and context owned:

#+begin_example
SourceCacheKey       = source-digest
ParseCacheKey        = parser-id + parser-version + representation + source-digest
ArtifactCacheKey     = canonical-uri + exact-version + artifact-digest
ValidationClosureCacheKey = closure-digest + terminology-snapshot-digest + engine-version
#+end_example

Mutable global cache identity, a human display label or a bare version is
insufficient.  Failure caching SHALL be bounded and generation-aware so a bad
source cannot create an unbounded retry loop or permanently poison a corrected
generation.

*** 10.06.163.75 Concurrency and lifecycle

One cache context SHALL provide single-flight materialization: concurrent
requests for one exact key share one attempt and one terminal receipt.  The
observable lifecycle is:

#+begin_example
unresolved -> resolving -> loaded -> materialized -> compiled -> ready
                         \-> failed
ready -> stale | revoked | evicted
#+end_example

Cycle detection, strict re-entry, repeated graph digest, dependency growth and
budget exhaustion are typed failures.  Wall-clock timeout is an operational
watchdog, not the sole semantic convergence criterion.

Hot update creates a new immutable generation.  It cannot mutate an edition,
bundle, validation closure or receipt already bound to a running Case.

** 10.06.163.80 Resolution and composition rules

*** 10.06.163.81 Exact selection

A runtime selection SHALL resolve to an exact canonical identity, version and
digest before materialization.  Version ranges may be authoring input to a lock
or proposal tool, but a Case admission binds the exact resolution result.

*** 10.06.163.82 Conflict rules

Resolution fails closed for at least:

- two different contents claiming one canonical identity and version;
- incompatible editions of one identity in the same closed bundle;
- missing or cyclic dependencies;
- an unqualified refinement of an unaccepted base edition;
- namespace, artifact identity or terminology identity collision;
- an undeclared representation, source or Provider requirement;
- a withdrawn, revoked, expired or digest-mismatched artifact;
- a closure exceeding declared count, depth, byte or computation budgets.

There is no list-order overwrite, best-effort partial bundle or silent fallback
to another edition.

*** 10.06.163.83 Profile and Case semantics

A POO Flow Profile selects Standard requirements.  It does not copy full
standard content into its slots.  A Case composes Profiles, resolves the union
of selected requirements, rejects conflicts and binds the resulting exact
Standard bundle.

The intended POO-native surface is conceptually:

#+begin_src scheme
(.def (AustraliaHealthcareInteroperabilityProfile self HealthcareBaseProfile)
  (.requires-standard
   (.o fhir-r4: FHIRR4StandardRef
       au-base: AUBaseStandardRef
       au-core: AUCoreStandardRef
       aucdi: AUCDIStandardRef)))
#+end_src

The concrete constructor and slot names remain an implementation milestone.
They SHALL expand or dispatch to ordinary POO-native objects and pure
functional composition.  This RFC does not approve a new public macro DSL.

** 10.06.163.90 Four-layer module shape

The POO Flow implementation SHALL follow RFC 162's responsibility audit:

#+begin_example
modules/standards/
  types.ss       boundary types and typed failures
  objects.ss     POO prototypes and immutable constructors
  funs.ss        pure resolution, closure and composition algorithms
  contracts.ss   open Provider/subject conformance relationships when justified
  config.ss      concrete default budgets and empty catalogs
  interface.ss   narrow public facade
#+end_example

The domain-neutral core contains no FHIR branch.  A vertical Lambda module
inherits the POO Standards module prototype and composes its concrete Provider
bundles:

#+begin_example
packages/lambda-episteme/modules/healthcare/
  types.ss
  objects.ss
  funs.ss
  config.ss
  interface.ss
  standards/
    types.ss
    objects.ss
    funs.ss
    config.ss
    interface.ss
    fhir/
      types.ss
      objects.ss
      funs.ss
      config.ss
      reference.ss
      interface.ss
#+end_example

Provider x Standard-family dispatch requires two independently extensible axes
and an explicit CLOS method bundle; Provider-name =case= expressions in the
generic caller are prohibited.  The exact pack storage layout is subject to
source and license constraints.  POO Flow SHALL NOT absorb independently owned
or restricted standard content merely to satisfy a test fixture.

** 10.06.163.100 FHIR first vertical slice

*** 10.06.163.101 Boundary

FHIR is a concrete Standard family maintained by Lambda Healthcare through the
POO Flow Standards protocol.  POO Flow knows only Standard identities,
dependencies, validation closures, generic receipts and Provider dispatch.  Lambda owns FHIR
constraints, package identities, conformance semantics, Healthcare mappings
and Cases.

The first slice SHOULD bind one exact FHIR R4 edition and one exact Australian
implementation-guide closure selected by the existing Australia Healthcare
Region Profile.  Candidate resources are:

- =Patient=;
- =Practitioner= and =PractitionerRole=;
- =Organization=;
- =Encounter=;
- =Condition=;
- =Observation=;
- =MedicationRequest=.

Lambda's existing internal medication-order meaning need not be renamed.
Instead, the Healthcare mapping explicitly projects that domain object to the
selected FHIR =MedicationRequest= profile and retains both identities in the
conformance receipt.

*** 10.06.163.102 Parsing decision

FHIR JSON and XML are data representations, not a new POO Flow public DSL.
Their readers produce representation-level values and typed parse failures.
FHIR conformance comes from FHIR artifacts and the FHIR Provider's validation meaning,
not from treating JSON/XML parse success as Standard admission.

=gerbil-parser= is therefore not a production dependency of the first FHIR
slice.  FHIRPath 2.0.0 syntax is now owned by =gerbil-parser= and consumed
through a separate parse-artifact qualification boundary; its parser receipt
does not grant evaluator, terminology, model-navigation or conformance
authority.  FHIR Shorthand, CQL or another real language may follow the same
boundary.  The dependency direction must respect the existing fact that
=gerbil-parser= consumes POO Flow; POO Flow core
cannot introduce the reverse production edge.

*** 10.06.163.103 Conformance ladder

The first FHIR Provider SHALL keep these results distinct:

1. representation syntax valid;
2. base FHIR resource structurally valid;
3. selected =StructureDefinition= profile valid;
4. terminology bindings evaluated against the bound snapshot;
5. selected national implementation-guide closure valid;
6. Lambda Healthcare Case admission valid.

An earlier success never discharges a later obligation.  Unsupported slicing,
invariants, terminology or reference resolution produce typed
=not-evaluated= or failure results according to the selected conformance
policy; they do not silently pass.

*** 10.06.163.104 Initial constraint surface

The initial validation surface SHOULD include:

- cardinality;
- primitive and complex type identity;
- choice fields such as =value[x]=;
- fixed and pattern values;
- extensions and =modifierExtension= handling;
- base-definition and profile dependency resolution;
- reference target constraints;
- terminology binding identity and declared strength;
- invariant identity with explicit evaluation support state.

FHIRPath evaluation, slicing completeness, remote reference resolution and
large terminology expansion SHALL be claimed only after their own executable
acceptance receipts exist.

*** 10.06.163.105 AU Core Patient increment

The second Healthcare increment binds the canonical AU Core Patient 1.0.0
profile identity and adds a second Lambda-owned CLOS method specialized on that
Profile.  The FHIR Provider resolves Profile identity through an indexed
registry; it does not add a Provider-name or resource-name =case= expression.

This increment implements only four explicit constraints: =resourceType= and
the published =au-core-pat-01=, =au-core-pat-02= and =au-core-pat-03=
exclusive-or rules for identifier, name content and the FHIR Data Absent
Reason extension.  These are bounded named evaluators, not a general FHIRPath
implementation.  Full AU Core Patient conformance, terminology evaluation and
interoperability remain unclaimed until an identified reference validator has
been executed against retained positive and negative fixtures.

That bounded obligation is discharged by four retained Patient inputs and one
unmodified FHIR collection Bundle containing the corresponding
=OperationOutcome= resources.  HL7 Validator CLI =6.9.12=, whose JAR SHA-256
is fixed in the fixture receipt, executes FHIR =4.0.1= with
=hl7.fhir.au.core#1.0.0= and no terminology server.  Its outcomes are
=valid=, =valid=, =invalid= and =invalid= for the ordinary positive, Data
Absent Reason, incomplete, and content-plus-Data-Absent-Reason fixtures.  The
Lambda Provider agrees on all four.  This evidence qualifies the bounded
invariants only; it does not turn their subset into a claim of complete AU Core
or terminology conformance.

The external qualification path is executable, not documentary.  The root
=check-healthcare-fhir-reference-validator= recipe enters through =gerbil
test=, verifies the exact Validator JAR SHA-256, streams the Validator's native
progress, replays all four fixtures, and compares the complete decoded JSON
Bundle with the retained evidence.  JSON object member ordering is deliberately
not treated as semantic evidence.  The normal Lambda test path still performs
no Java execution, package download or network access.

Lambda publishes a POO-native FHIR capability manifest so qualification scope
cannot be widened by implication.  Named structural evaluation is
=native-bounded=; the four-fixture AU Core Patient comparison is
=reference-qualified=; the pinned FHIRPath 2.0.0 grammar and AU Core expression
corpus are =syntax-qualified=.  General FHIRPath evaluation, complete slicing,
terminology and remote reference resolution remain =not-evaluated=.  A
capability may move states only with its own executable receipt.

The canonical source set is seven byte-for-byte JSON artifacts retained by
Lambda Healthcare: the FHIR R4 package manifest and MedicationRequest
=StructureDefinition=, the AU Base package manifest and ImplementationGuide,
and the AU Core package manifest, ImplementationGuide and Patient
=StructureDefinition=. Their immutable upstream authority, byte counts,
SHA-256 values and package-archive SHA-256 values accompany the snapshots.
The source loader admits those bytes without parsing; the materializer uses
Gerbil =std/text/json= =bytes->json-object= directly over the admitted byte
vector and rejects a changed resource type, id, canonical URL, version,
constraint severity or supported expression.  The generated XHTML narrative
under =text.div= remains an opaque JSON string: no XHTML/XML parser is invoked,
and the materialized artifact retains only admitted identity fields and the
bounded supported constraints.  A Just qualification gate checks the retained
official JSON directly.  There is no derived projection and therefore no
second semantic authority. XML is not retained for this slice because it
carries the same canonical identities and constraint coverage. A second
representation is justified only by distinct required coverage, not by format
availability alone.

** 10.06.163.105 Legacy-interface migration Scenario

Australian healthcare deployments commonly retain HL7v2 messages, CDA
documents and national-service interfaces while adding FHIR endpoints.  This
RFC therefore treats migration as coexistence with an evidence-bearing cutover,
not as an implicit compatibility alias or a flag-day replacement.

The executable Lambda Healthcare Case is
=au-legacy-interface-fhir-migration=.  Its first bounded path maps a
parser-normalized HL7v2 =ADT^A08= patient subject into an AU Core Patient
candidate.  The Scenario also declares CDA and national-service inputs as
separate legacy interface families so later adapters do not collapse different
syntax, transport and authority boundaries into one generic legacy format.

Declaration is not admission.  HL7v2 is =qualified= by its parser receipt;
CDA and national-service interfaces are =declared-only=.  Migration admission
fails with =healthcare-migration-source-interface-unqualified= for either
declared-only family, even when the proposed FHIR candidate and human review
are otherwise valid.  Each family needs its own parser or service-adapter
qualification digest before it can enter the migration Case.

The =hl7v2-er7.v1= grammar, message-local MSH delimiter scanners, lossless ParseArtifact and
bounded ADT^A08 Patient projection are owned by =gerbil-parser=. A root Just
qualification runs =gerbil test= in that package environment and requires the
parser-owned source digest, grammar digest and projection receipt digest to
match the retained Lambda Case exactly. Lambda imports only the projection and
does not implement HL7 delimiters or positional PID parsing.

Migration is a FeatureModule below the POO Flow StandardsModule, not a sibling
domain module.  The composition chain is deliberately four levels:

#+begin_example
PooFlowStandardsModule
  -> PooFlowStandardMigrationFeatureModule
       -> HealthcareStandardMigrationFeatureModule
            -> AUHealthcareMigrationFixture
#+end_example

POO Flow owns only the generic FeatureModule shape and the migration extension
points: source adapter, mapping proposal, human review, conformance, admission
and fixture attachment.  Lambda Healthcare extends that FeatureModule with the
healthcare source-interface kinds and candidate/admission methods.  The AU
fixture then extends the feature with jurisdiction-specific landscape, Cases,
AI proposals and human reviews.  Therefore neither FHIR/HL7 semantics nor AU
fixtures leak into the domain-neutral Standards core, and =migration= does not
appear as an unrelated module beside =standards=.

Responsibility is explicit:

- Gerbil Parser or a service adapter owns source syntax and emits a
  snapshot-bound parser receipt;
- Lambda Healthcare owns the reviewed semantic field mapping and target FHIR
  Profile selection;
- the AI assistant may propose mappings and explain discrepancies, but remains
  =advisory-only=;
- an independent human reviewer authorizes the mapping;
- the FHIR Provider validates the exact candidate against the selected AU Core
  Profile; and
- migration admission binds source snapshot, parser receipt, mapping evidence,
  candidate digest and conformance receipt.

The AI-assisted path is itself a typed evidence product, not an opaque model
call.  Its immutable analysis binds the source interface and version, source
snapshot digest, exact target edition and Profile, mapping-evidence digest,
unmapped required fields, assessed risk codes, proposed cutover strategy and
the fixed workflow stages =inventory -> normalize -> map -> assess-risk ->
generate-candidate -> validate -> explain-conformance -> review ->
rehearse-cutover -> admit=.  The mapping proposal binds the analysis digest,
the human review binds the proposal digest, and the final migration receipt
retains both the analysis digest and ordered workflow stages.

=AustraliaHealthcareStandardMigrationProfile= owns the jurisdictional
migration Threats and gates.  It is intentionally separate from the general
Australia care-delivery Profile, whose Primary Care and Support at Home
evidence is irrelevant to a Standard conversion.  Case discovery remains
demand-loaded: the final user config discovers reusable Profiles and Scenario
declarations, while an explicit Case consumer imports and composes this Case.

Missing human review, AI decision authority, a target Profile mismatch, an
unbound candidate or failed conformance produces a typed fail-closed migration
receipt.  The old interface and its source snapshot remain available for
rollback until an application-owned cutover policy retires them.  POO Flow
does not parse HL7v2/CDA, infer a compatibility mapping or authorize cutover.

** 10.06.163.107 NASA software-engineering second-industry increment

Lambda Aitia owns the first non-Healthcare family,
=nasa/npr-7150.2=.  Its Provider projects the exact NPR 7150.2D edition and 130
reviewed software-engineering requirements through the unchanged
domain-neutral Standards contracts.  Six checked-in NASA NODIS HTML sources
totaling 198,644 bytes are bound by a generated =SourcesLock=; catalog import
and exact-edition resolution read none of those bytes.  Only explicit
materialization invokes the configured source Provider, verifies every locked
payload, and constructs the six Standard artifacts.

The Source Lock Feature is a reusable feature-system facility, not NASA
vocabulary and not a change to Standards core.  Lambda Aitia owns the concrete
source declarations, lock product, Provider, catalog, Profile and executable
test.  The focused Provider test proves deterministic lock regeneration, lazy
resolution, explicit materialization, tamper rejection and provider-neutral
validation-closure projection.

This increment does not justify a second CLOS dispatch axis.  The NASA source
store is one replaceable POO Provider slot, while the standard family and exact
edition remain ordinary immutable values; there are not two independently
extensible semantic axes at the validation call site.  Healthcare retains its
Lambda-local Provider x Profile generic because both of those axes vary
independently.  A new cross-industry CLOS generic is prohibited until an
executable second use case demonstrates two independently varying types and
methods that cannot be expressed by prototype composition plus the existing
Profile-specialized boundary.

*** 10.06.163.108 Cross-industry Profile Case qualification

Core exposes =poo-flow-standard-compose-profiles= as a pure domain-neutral
Case boundary.  It accepts ordered =PooFlowStandardConstraintProfile= values,
deduplicates exact edition and dependency identities through native hash
tables, preserves Profile order, invokes the existing exact resolver once, and
returns a =PooFlowStandardProfileCompositionReceipt=.  The receipt binds the
Case identity, exact Profile revisions, selected base editions, constraints,
artifact and terminology dependencies, resolution receipt, first typed
failures and a deterministic composition digest.  A duplicate Profile identity
with another exact revision fails as
=standard-profile-revision-conflict= before resolution.

The root-owned, mechanism-only qualification Case uses one Profile from Lambda
Healthcare and one software-engineering Profile from Lambda Aitia.  This pair
is deliberately not named as an application domain and makes no claim that
either Standard applies to the other's industry.  Its closure contains four
editions and ten artifact references while reading none of their source
bodies.  A shadow edition with the same canonical URI and version as the
selected software-engineering edition but a different digest is rejected by
the unchanged resolver as =standard-identity-conflict=.  Thus the composition
mechanism is core-owned, concrete vocabulary remains in its Lambda owners, and
conflict diagnostics are proven without inventing a mixed-industry application
namespace or introducing cross-industry CLOS dispatch.

** 10.06.163.110 Security and authority

- Standard packs are untrusted inert inputs until source, digest and shape
  admission succeeds.
- Loading a pack must never =eval= embedded Scheme or execute contributor code.
- Package resolution and network acquisition, when later supported, require an
  explicit Provider capability and separate receipt.
- A validation closure carries identities and constraints, not ambient
  credentials or network handles.
- Terminology and remote-reference requests are explicit Runtime effects with
  bounded request sets and snapshot identities.
- Conformance evidence does not grant clinical authority, regulatory
  certification, application activation or mutation permission.
- Revocation and expiry are checked at the handoff that consumes a receipt.

** 10.06.163.120 Observability

The Standard path SHALL emit structured observations for:

- catalog identity and member count without artifact realization;
- exact selection and lock identity;
- dependency edge discovery;
- cache hit, miss, wait, eviction and failure reuse;
- artifact bytes and count admitted against budget;
- materialization state and failure identity;
- validation-closure constraint counts and unsupported constraint kinds;
- terminology snapshot or request identity;
- closure digest and generation;
- conformance outcome and first typed root cause.

Observability projections are strict values.  Inspecting a Standard catalog or
receipt must not trigger lazy materialization or another runtime effect.

** 10.06.163.140 Qualification and scale gates

The implementation is not accepted until executable tests establish:

- constructing a catalog fixture of at least 10,000 =StandardRef= values loads
  zero artifact bodies and creates zero validation validation closures;
- listing, searching and presenting that catalog does not realize standards;
- selecting one leaf loads exactly its declared transitive closure;
- two concurrent selections of the same exact key perform one materialization;
- an unrelated standard addition does not change an existing closure digest;
- a changed artifact digest creates a new generation and invalidates no
  already-bound immutable receipt by mutation;
- cyclic dependencies and strict lazy re-entry fail before stack exhaustion;
- count, depth, byte and computation budgets each have negative tests;
- eviction removes artifact/validation-closure cache entries without changing catalog or
  receipt identities;
- importing the Standard module performs no network, terminology or validation
  effect;
- positive and negative FHIR fixtures are cross-checked against an explicitly
  identified reference validator before any interoperability claim;
- full-suite and integration evidence remain separate from focused unit gates.

A performance receipt SHALL record catalog count, selected closure count,
loaded byte count, parse/materialization/validation-closure counts, cache observations, peak
resident memory, elapsed time, generation and exact source revisions.  A pass
count without these scale facts is not evidence for the 10,000-standard goal.

The 2026-09-17 working-tree qualification found that the original resolver
deep-validated every catalog-admitted Edition once while constructing the
Bundle and again while wrapping the ResolutionReceipt.  A controlled ablation
reduced p95 from =515.630007ms= to approximately =56.818008ms= when both
redundant passes were removed.  The accepted implementation keeps the strict
public constructors and instead proves each selected object is the identical
value stored in the admitted catalog's native hash index before constructing
the internal immutable result.  Its isolated 20-sample receipt reports p95
=73.426962ms=, maximum =99.410057ms=, 10,000 resolver operations, zero loaded
artifacts and zero measured benchmark-interval GC allocation.  A combined run
after the complete Standards core suite reports p95 =211.360931ms= and maximum
=341.505051ms=, still below the 800ms target and 999ms hard maximum.  The
performance test emits =fixture-start=, =fixture-ready= and
=measurement-start= phases so setup and measured stalls remain distinguishable.

** 10.06.163.160 Rejected alternatives

*** Central eager standards registry

Rejected because startup, heap and rebuild cost scale with the total catalog;
catalog inspection would also become accidental materialization.

*** One Gerbil module per external standard

Rejected as the default storage model because dynamically loaded modules are
not an artifact cache, cannot provide the required eviction boundary and turn
untrusted inert standard data into executable namespace growth.

*** Put every industry standard in POO Flow core

Rejected because it reverses contributor ownership, expands the trusted core
and forces unrelated applications to absorb domain vocabulary.

*** Let =gerbil-parser= own FHIR

Rejected because FHIR JSON/XML syntax is not FHIR conformance.  Parser
ownership is appropriate only for actual language grammars and lossless syntax
artifacts; it does not own Healthcare meaning or national implementation
guides.

*** Hide loading behind ordinary lazy slot reads

Rejected because a value lookup would become an invisible I/O and authority
boundary.  Lazy pure computation and explicit effectful materialization remain
separate.

*** Resolve =latest= during Case execution

Rejected because the same Case declaration could acquire different semantics
without a source change and no stable receipt could bind the result.

#+title: Higher-Order Capability Materialization POO Lifecycle Object and Runtime Policy-Prototype Algebra
#+author: POO Flow
#+language: en

* Status

This RFC is an accepted runtime-coordination semantic contract.

It defines one immutable, event-oriented =CapabilityMaterialization= POO
lifecycle object.  It does not admit an implementation, expose a runtime handle
as a semantic slot, create a mutable lifecycle object, or add public syntax.

* Scope

This RFC owns:

- the required slots of =CapabilityMaterialization=;
- its derived lifecycle responsibilities;
- runtime policy-prototype composition;
- immutable lifecycle generations and event lineage;
- legal authorization, claim, materialization, lease, handoff, revocation,
  cleanup, reconciliation, outcome, and receipt transitions;
- the adapter-owned handle-store boundary;
- crash ambiguity and conditional lifecycle-head commit;
- the closure point for the RFC 45-119 through RFC 45-127 architecture chain.

It does not own:

- semantic capability closure;
- upstream POO mechanics;
- concrete provider SDK behavior;
- runtime handle representation;
- secret values;
- package, build, or deployment configuration;
- a public lifecycle or materialization DSL.

* Central decision

=CapabilityMaterialization= is one higher-order POO value with three required
slots:

- =intent=;
- =adapter=;
- =runtime-context=.

All lifecycle behavior is derived through native POO policy prototypes,
structured effect intents, runtime receipts, immutable successor values, and
conditional lifecycle-head transitions.

The actual runtime handle remains in the adapter-owned handle store.  It is
never a slot of =CapabilityMaterialization=.

* Required slot: intent

=intent= is one stabilized capability-materialization EffectIntent.

It identifies:

- semantic capability evidence;
- requester and runtime consumer;
- requested scope and lifetime policy;
- adapter-dispatch responsibility;
- authorization and redaction context references;
- materialization fence;
- idempotency, recovery, cancellation, and cleanup policy.

The intent is immutable and contains no runtime handle, resolved secret,
callback, or raw continuation.

An intent that changes produces a distinct =CapabilityMaterialization=
identity.

* Required slot: adapter

=adapter= is one admitted POO-native runtime adapter value.

It provides runtime-boundary responsibilities for:

- authorization support;
- external acquisition or construction;
- provider query and reconciliation;
- lease binding;
- consumer delivery;
- revocation;
- cleanup;
- receipt projection.

The adapter may encapsulate provider SDKs and runtime resources.  Its handle
store and secret resolver remain behind its runtime boundary.

Adapter selection is completed before the lifecycle object executes an
external-effect handoff.  The object does not use a hidden global registry,
string switch, package name, or host =case=.

* Required slot: runtime-context

=runtime-context= is an explicit runtime-boundary POO value.

It may reference:

- runtime authorization;
- execution lineage;
- claim and fence storage;
- adapter services;
- handle-store authority;
- secret resolver authority;
- lease clock and lifetime policy;
- cancellation and cleanup context;
- redaction and observation budgets.

It does not expose those authorities to Module, Profile, ProfileBundle,
=DispatchEvaluation=, or semantic capability closure.

Changing runtime authority, lineage, adapter generation, or redaction produces
a distinct lifecycle identity.

* Derived lifecycle responsibilities

The lifecycle responsibilities are:

| Responsibility | Inputs | Result |
|----------------+--------+--------|
| =authorization= | intent, adapter, runtime-context | Current authorized or denied decision |
| =claim= | authorized decision, fence, lineage | One logical materialization claim |
| =materialization= | claim and adapter policy | EffectIntent handoff plus external evidence |
| =lease= | materialization evidence and lifetime policy | Scoped adapter-owned lease identity |
| =handoff= | valid lease, consumer, authorization | Delivery evidence without handle serialization |
| =revocation= | lease, authority change, expiration, or request | Immutable revocation transition |
| =cleanup= | revoked or orphaned resource evidence | Cleanup outcome and obligations |
| =reconciliation= | ambiguous event lineage and provider query | Completed, revoked, suspended, or unresolved result |
| =outcome= | all admitted lifecycle evidence | Current immutable lifecycle outcome |
| =receipt= | outcome and redaction policy | Redacted runtime receipt |

These responsibilities are not ten mutable fields and are not separate ordinary
record APIs.

* Immutable lifecycle generations

Each accepted transition produces a new immutable lifecycle value.

A lifecycle generation identifies:

- materialization intent;
- predecessor lifecycle generation;
- triggering event or receipt;
- adapter and runtime-context generations;
- execution lineage;
- transition identity;
- resulting outcome identity.

The predecessor remains historical evidence.  No transition mutates or erases
an earlier authorization, denial, claim, ambiguity, lease, revocation, or
cleanup result.

* Event lineage

Every external observation or effect result is an event with:

- event identity;
- stabilized intent identity;
- predecessor generation;
- adapter identity;
- execution and materialization lineage;
- fence and attempt identity;
- event kind;
- redacted payload identity;
- observation authority;
- source receipt identity.

Duplicate delivery reuses the same event identity.  Retry, replay, renewal,
recovery, revocation, and cleanup create explicit distinct lineage edges.

Events do not contain runtime handles or secret values.

* Policy-prototype algebra

Runtime policy prototypes may refine:

- authorization;
- idempotency and fence behavior;
- provider acquisition;
- lease and lifetime;
- consumer handoff;
- secret resolution;
- cancellation;
- revocation;
- cleanup;
- ambiguity recovery;
- receipt and redaction.

Each policy:

- is a native POO value;
- depends on explicit intent, adapter, runtime-context, and event evidence;
- may project an EffectIntent;
- may narrow authority;
- may call inherited computation;
- cannot expose a runtime handle as a semantic value;
- cannot widen authorization through =super=.

Contribution admission finalizes the policy graph before lifecycle dispatch.
C3 then orders behavior inside the finalized graph.

* Pure control and effect handoff

Lifecycle responsibility evaluation is functional.

An effectful step returns an EffectIntent or RecoveryExecutionIntent.  The
runtime adapter executes it and returns a receipt event.  The receipt event
produces the next immutable lifecycle value.

The control object does not call provider SDKs, secret stores, handle stores, or
cleanup APIs from a pure derived slot.

This preserves the functional Scheme control plane while keeping runtime effects
behind explicit handoff boundaries.

* Authorization transition

Authorization derives either:

- authorized decision with bounded scope and lifetime; or
- denied decision with structured redacted evidence.

Authorization is evaluated against current runtime context.  Historical
semantic capability satisfaction is an input, not an authorization result.

A denied successor contains no claim or external effect.

* Claim transition

An authorized lifecycle may derive one materialization claim.

The claim:

- binds the intent, adapter, consumer, scope, lineage, and generation;
- is stable before adapter invocation;
- rejects concurrent duplicate execution;
- records cancellation and recovery ownership;
- does not claim that the external effect completed.

Claim conflict is a structured lifecycle outcome.

* Materialization transition

The materialization responsibility projects an adapter EffectIntent.

The adapter returns evidence for:

- acquired;
- constructed;
- reused under an existing valid lease;
- unavailable;
- denied by provider;
- suspended;
- completion unknown.

The returned evidence refers to adapter-owned handle identity or fingerprint.
It does not contain the handle.

* Lease transition

A successful materialization may derive a lease.

The lease binds:

- capability, adapter, consumer, and scope;
- materialization generation;
- current authorization;
- lifetime and renewal policy;
- revocation and cleanup policy;
- adapter-owned handle-store reference.

The lifecycle object stores lease evidence, not the handle.

Renewal produces a new lifecycle generation and receipt.

* Handoff transition

Handoff delivers adapter-mediated access to the authorized runtime consumer.

It requires:

- valid non-revoked lease;
- matching consumer and scope;
- current authorization;
- stable materialization and lease evidence;
- admitted atomic or reconciled delivery protocol.

The handoff receipt proves delivery state without serializing the handle.

* Revocation transition

Revocation creates a new lifecycle generation.

It:

- prevents new authorized use;
- invalidates adapter-owned handle-cache entries;
- requests provider revocation when required;
- establishes cleanup obligations;
- preserves the original lease and delivery evidence.

Revocation is not rollback by mutation.

* Cleanup transition

Cleanup follows revocation, cancellation after materialization, lease
expiration, orphan discovery, or failed handoff.

Cleanup may be:

- complete;
- pending;
- retry-admitted;
- suspended;
- denied;
- ambiguous;
- failed.

The lifecycle cannot become terminal-clean while an owned external resource
remains unaccounted for.

* Crash ambiguity

An ambiguous event produces an immutable ambiguous lifecycle generation.

The object records:

- last stable predecessor;
- claimed effect;
- external operation identity when known;
- missing receipt boundary;
- provider-query responsibility;
- cleanup ownership;
- allowed recovery decisions.

It does not overwrite ambiguity with an assumed failure or success.

* Reconciliation transition

Reconciliation projects a RecoveryExecutionIntent when external observation is
required.

Provider query or recovery may derive:

- action did not occur;
- resource exists and can be leased;
- orphan exists and must be revoked;
- revocation completed;
- cleanup completed;
- external evidence unavailable;
- unresolved ambiguity.

The result creates a new lifecycle generation.  It never rewrites the ambiguous
predecessor.

* Outcome algebra

The lifecycle outcome may be:

- authorized;
- denied;
- claimed;
- materialized;
- leased;
- delivered;
- unavailable;
- suspended;
- ambiguous;
- revoking;
- revoked;
- cleanup pending;
- cleaned;
- cancelled.

Outcome is derived from stable event evidence.  It is not an independently
mutable phase field.

* Receipt algebra

Each lifecycle generation may project one redacted receipt.

The receipt identifies:

- lifecycle and predecessor generations;
- intent, adapter, consumer, and capability identities;
- event and execution lineage;
- authorization decision;
- claim and fence;
- materialization evidence;
- lease identity and state;
- handoff state;
- revocation and cleanup obligations;
- ambiguity and reconciliation evidence;
- outcome;
- redaction policy.

It contains no handle or secret.

Materialization, handoff, revocation, cleanup, and reconciliation receipts remain
distinguishable event kinds.

* Conditional lifecycle-head commit

The coordinator owns one externally visible lifecycle head per materialization
identity and scope.

A new generation advances the head only when:

- its predecessor matches the current head;
- event identity has not already been applied;
- authorization and lineage remain valid;
- all required receipts are stable;
- the transition is legal.

Concurrent or stale transitions return structured conflicts.  They do not use
last-writer-wins.

Rollback is represented by a new revocation, recovery, or replacement
generation.

* Adapter-owned handle store

The handle store belongs to the runtime adapter.

It maps admitted lease identity and runtime authorization to provider-owned
handle state.  It is not:

- a semantic cache;
- a Module or Profile slot;
- a global POO registry;
- a composition receipt;
- an Org artifact.

Only the adapter and authorized consumer boundary may dereference the handle.

Handle-store loss or inconsistency produces runtime unavailability or ambiguity,
not semantic capability unsatisfaction.

* Secret and redaction boundary

Secret resolution occurs only through runtime-context authority inside the
adapter boundary.

Policy prototypes and receipts operate on redacted references and generations.
They do not inspect or emit secret values.

Secret rotation may:

- invalidate authorization;
- invalidate a handle-store entry;
- require renewal or replacement;
- trigger revocation and cleanup.

It does not mutate semantic capability closure.

* Cancellation boundary

Cancellation produces a successor lifecycle value.

- Before claim: cancel without external cleanup.
- After claim but before known effect: reconcile.
- After materialization: revoke and clean up.
- After delivery: revoke consumer access, then clean up.
- During cleanup: preserve cleanup ownership until terminal evidence exists.

Cancellation does not erase obligations.

* Observability

Lifecycle explanation may project:

- required slot identities;
- policy prototype graph;
- current and predecessor generations;
- event lineage;
- authorization and claim decisions;
- effect-intent and receipt boundaries;
- lease, handoff, revocation, and cleanup states;
- ambiguity and reconciliation;
- redaction decisions;
- conditional-head conflicts;
- final outcome.

Observation remains capability-scoped, budgeted, and redacted.

* Public-interface boundary

This RFC adds no public materialization or lifecycle syntax.

The ordinary composition surface remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

Runtime materialization is reachable only through admitted EffectIntent and
runtime adapter boundaries.

* Ownership

- =poo-flow-core= owns semantic capability evidence and EffectIntent
  projection.
- The coordinator owns immutable lifecycle generations, event lineage, claims,
  conditional-head commit, recovery admission, and reconciliation.
- Runtime/deployment adapters own runtime-context services, provider effects,
  handle stores, leases, revocation, cleanup, and runtime receipts.
- The final application owns deployment authorization policy.
- =wendao-episteme= may own domain adapters only outside its semantic Module and
  Profile values.
- GSLPH remains a development policy harness and building/testing dependency.
- Gerbil-Bazel, Nix, and =gerbil.pkg= remain outside runtime capability
  semantics.

* Admission checklist

** Object algebra

- [X] Freeze one higher-order =CapabilityMaterialization= POO lifecycle object.
- [X] Freeze =intent=, =adapter=, and =runtime-context= as its three required
  slots.
- [X] Keep authorization, claim, materialization, lease, handoff, revocation,
  cleanup, reconciliation, outcome, and receipt derived.
- [X] Reject runtime handles as lifecycle slots.
- [X] Require immutable successor generations.
- [X] Reject public lifecycle syntax.

** Policy prototypes

- [X] Freeze authorization, idempotency/fence, acquisition, lease, handoff,
  secret, cancellation, revocation, cleanup, recovery, and receipt policies.
- [X] Require explicit EffectIntent handoff for external operations.
- [X] Prevent policy prototypes from widening runtime authority.
- [X] Separate contribution admission from C3 lifecycle dispatch.
- [ ] Define exact internal policy prototype identities after adapter admission.

** Lifecycle and events

- [X] Freeze event and generation lineage.
- [X] Preserve predecessor evidence.
- [X] Derive outcome rather than mutating a phase field.
- [X] Require conditional lifecycle-head commit.
- [X] Reject last-writer-wins transitions.
- [ ] Prove all legal and illegal transitions.

** Handle, lease, and secret boundaries

- [X] Keep the handle in the adapter-owned handle store.
- [X] Store only lease and redacted handle evidence in lifecycle values.
- [X] Resolve secrets only through runtime-context authority.
- [X] Keep semantic cache, lifecycle evidence, and handle store distinct.
- [ ] Prove lease renewal, expiration, revocation, and replacement behavior.
- [ ] Prove secret rotation and handle-store invalidation.

** Ambiguity and cleanup

- [X] Preserve crash ambiguity as an immutable generation.
- [X] Use RecoveryExecutionIntent for effectful reconciliation.
- [X] Reject blind retry.
- [X] Preserve cleanup ownership through cancellation.
- [ ] Prove provider query, orphan discovery, revocation, and cleanup.
- [ ] Prove duplicate event and stale-head conflict handling.

** Implementation admission

- [ ] Admit every consumed upstream POO operation path in RFC 45-120.
- [ ] Implement the lifecycle object as a native POO value.
- [ ] Implement runtime policy prototypes.
- [ ] Implement event storage and conditional-head commit.
- [ ] Implement one concrete runtime adapter.
- [ ] Run focused GSLPH development checks without adding a product dependency.

* Rejected alternatives

- Separate mutable records for authorization, lease, cleanup, and receipt.
- A mutable phase field.
- Runtime handle stored in the lifecycle object.
- Direct provider SDK calls from pure derived slots.
- A global handle or adapter registry.
- Host =case= lifecycle dispatch.
- Last-writer-wins lifecycle head.
- Rewriting ambiguous predecessors after recovery.
- Treating cancellation as removal of cleanup obligations.
- Exposing secrets, handles, or raw continuations in events or receipts.
- Contribution priority replacing C3 policy dispatch.
- A public materialization lifecycle DSL.

* Successor contract

This RFC closes the abstract Module, dispatch, fixed-point, capability, and
runtime-materialization chain from RFC 45-119 through RFC 45-127.

The next step is a closure audit, not an automatic RFC 45-128.

The audit must:

- verify ownership and terminology across RFC 45-119 through RFC 45-127;
- verify every Mermaid edge has an explicit semantic label;
- verify every unfinished item is implementation work, not unknown ownership;
- enumerate exact upstream operation paths still below =ADMITTED=;
- identify the first minimal implementation entry;
- identify its owner, POO objects, functional inputs/outputs, conditions,
  focused evidence, and runtime boundary;
- keep GSLPH, Gerbil-Bazel, Nix, and =gerbil.pkg= in their existing tool and
  package roles.

No implementation begins from this RFC alone.

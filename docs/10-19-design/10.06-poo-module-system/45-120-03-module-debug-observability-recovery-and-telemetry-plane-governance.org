#+title: Module Debug, Observability, Recovery, and Telemetry Plane Governance
#+language: en

* Status

This RFC freezes the accepted Module debug and observability contract.  It
separates immutable semantic observation, debug and recovery control, and
effectful runtime telemetry.  It does not admit an implementation, a mutable
trace store, a public observability DSL, or a fifth required Module slot.

* Scope

This RFC owns:

- the three-plane Module observation and debugging model;
- immutable observation events and their generation lineage;
- dispatch, fixed-point, capability, and lifecycle observation responsibilities;
- continuable conditions and bounded recovery continuations;
- semantic and runtime performance-observation boundaries;
- redaction before telemetry publication; and
- core and Module-local file ownership.

It does not own:

- upstream POO dispatch, slot, prototype, or C3 implementation;
- the four-slot Module semantic contract;
- Type and Contract prototype construction;
- Module-local pure domain transformations;
- runtime handles, external telemetry sinks, or deployment policy; or
- a macro language for probes, events, handlers, or recovery clauses.

* Central decision

Module remains a higher-order POO value with exactly four required
responsibilities:

- =identity=;
- =imports=;
- =capabilities=; and
- =profiles=.

Debug and observability are derived from immutable evaluation generations.  They
are not a fifth Module slot, mutable Module state, or a side-effecting logger
embedded in semantic evaluation.

The architecture has three explicit planes:

#+begin_src mermaid
flowchart LR
  E["immutable Module evaluation generation"] -->|"projects source-owned semantic evidence"| O["semantic observation plane"]
  O -->|"signals an explainable condition when policy requires intervention"| D["debug and recovery control plane"]
  D -->|"returns an authorized recovery decision to the coordinator"| E
  O -->|"applies authority and redaction before publication"| T["runtime telemetry plane"]
  T -->|"publishes logs, metrics, traces, and runtime measurements through adapters"| S["external telemetry sinks"]
#+end_src

No runtime telemetry effect may flow back into semantic evaluation as hidden
state.

* Semantic observation plane

The semantic observation plane is pure and immutable.  It derives observation
from existing POO evaluation values, including:

- =DispatchEvaluation=;
- recursive Module import reachability evaluation;
- capability closure evaluation;
- EffectIntent projection; and
- =CapabilityMaterialization= lifecycle generations.

It does not duplicate those values in a second mutable trace model.

** ObservationEvent prototype

An ObservationEvent is a native POO value or prototype-derived value with three
required responsibilities:

| Responsibility | Meaning |
|----------------+---------|
| =source= | Stable identity of the source evaluation value. |
| =generation= | Immutable evaluation generation identity. |
| =evidence= | Source-owned semantic evidence referenced by the observation. |

The following responsibilities are derived:

- =lineage=;
- =phase=;
- =outcome=;
- =explanation=; and
- =redacted-projection=.

=evidence= is an admitted POO evidence value.  It is not a copied alist snapshot,
runtime handle, raw continuation, secret, or mutable log entry.

Observation kinds are expressed through prototype specialization.  They are not
maintained in a central string or symbol enumeration.

* Evaluation observation responsibilities

** Dispatch observation

Dispatch observation may derive:

- receiver and responsibility identities;
- instance, type, and prototype candidate sources;
- candidate enumeration and C3 precedence;
- the selected candidate and inherited =next= relation;
- dispatch budget consumption;
- cycle and cache identity;
- outcome, provenance, and explanation.

The inherited =next= or =super= relation is dispatch ancestry.  It is not a
recovery continuation.

** Fixed-point observation

Recursive Module import observation may derive:

- demand path and reachable import edges;
- node, edge, depth, and refinement counts;
- SCC membership;
- productive, suspended, unproductive, divergent, or denied cycle
  classification;
- bottom, refinement delta, join, convergence, and invalidation evidence;
- observation and evaluation budget consumption;
- semantic cache hit, miss, publication, and invalidation evidence; and
- the first generation at which progress stopped or divergence became
  observable.

These facts are semantic counters.  They do not read a clock or process metric.

** Capability observation

Capability closure observation may derive:

- requirement and provision identities;
- attenuation paths;
- withdrawal, denial, incompatibility, conflict, or absence evidence;
- contribution-admission priority distinct from C3 dispatch precedence;
- reachable closure provenance; and
- closure outcome and explanation.

Semantic capability satisfaction must not be presented as proof of runtime
authorization or resource availability.

** Lifecycle observation

Capability materialization observation may derive:

- immutable lifecycle generation and event lineage;
- authorization, claim, materialization, lease, handoff, revocation, cleanup,
  and reconciliation transitions;
- conditional lifecycle-head commit evidence;
- cancellation and crash-ambiguity evidence;
- logical exactly-once reconciliation outcome; and
- redacted runtime receipts.

Runtime handles remain in the adapter-owned handle store and never enter an
ObservationEvent.

* Debug and recovery control plane

The debug and recovery plane consumes semantic observations and decides whether
evaluation may continue, suspend, refine, invalidate, reconcile, or abort.

It is expressed with POO-native condition and policy prototypes.  It does not
add host-language clause syntax.

#+begin_src mermaid
flowchart LR
  A["cycle, budget, cache, condition, or performance anomaly"] -->|"constructs an immutable ObservationEvent"| O["semantic observation"]
  O -->|"signals a continuable condition with explanation"| H["debug coordinator handler"]
  H -->|"selects continue, suspend, refine-budget, invalidate-cache, reconcile, or abort"| R["RecoveryDecision"]
  R -->|"authorizes one bounded resumption"| C["evaluation coordinator"]
  C -->|"creates the next immutable generation"| N["resumed evaluation"]
#+end_src

** Condition boundary

A condition contains immutable semantic evidence and available recovery
choices.  It does not contain:

- a raw continuation;
- a runtime handle;
- a secret;
- a mutable trace buffer; or
- an effectful callback.

Conditions must be observable before a recovery choice is executed.

** RecoveryDecision boundary

RecoveryDecision is a POO value or prototype-derived value.  Decision variants
are prototype specializations rather than a mutable command tag.

A RecoveryDecision may authorize:

- continue with unchanged policy;
- suspend and retain the immutable evaluation generation;
- refine an explicit budget;
- invalidate an identified semantic cache entry;
- reconcile an ambiguous runtime transition;
- deny further evaluation; or
- abort the evaluation.

The decision is pure.  The evaluation or runtime coordinator owns execution.

* Continuation and resumption separation

Three continuation concepts remain distinct:

| Concept | Owner | Meaning |
|---------+-------+---------|
| POO inherited continuation | Upstream POO dispatch | Continue through C3 ancestry with =next= or =super=. |
| Fixed-point resumption | Evaluation coordinator | Continue refinement from an immutable generation. |
| Recovery continuation | Debug coordinator | Resume control suspended by a continuable condition. |

First-class continuations and =call/cc= may be used only inside the admitted
debug coordinator.  A raw continuation is ephemeral and coordinator-owned.  It
must not be serialized, cached, logged, returned through the public interface,
stored in Module, or included in a receipt.

A stable resumption identity may appear in redacted evidence, but the authority
and raw continuation remain inside the coordinator.

* Performance observation boundary

Semantic performance observation is deterministic for equal admitted inputs and
evaluation policy.  It may include:

- candidate, dispatch, node, edge, and depth counts;
- SCC and refinement counts;
- cache hit, miss, invalidation, and recomputation counts;
- budget consumption; and
- generation-to-generation progress deltas.

Runtime performance telemetry may include:

- monotonic duration;
- CPU time;
- process RSS or platform footprint;
- I/O latency;
- adapter queue delay; and
- external sink publication latency.

Wall-clock, CPU, memory, and I/O measurements are effects.  They belong to the
runtime telemetry adapter and must not be read by =func.ss= or semantic
observation functions.

An abnormal runtime threshold is a diagnostic signal.  It must lead to
process-and-phase attribution rather than merely raising the threshold.

* Runtime telemetry plane

The runtime telemetry plane consumes redacted ObservationEvent projections and
runtime-owned measurements.  It may publish logs, metrics, or traces through an
adapter.

Before publication, the adapter must:

- apply observer authority;
- remove secrets and raw handles;
- remove raw continuations and recovery authority;
- preserve stable semantic identity and generation lineage;
- distinguish semantic evidence from runtime measurement; and
- emit a publication receipt or actionable denial.

Telemetry failure must not silently mutate or invalidate semantic evaluation.

* File and dependency ownership

The core owners are:

| Owner | Responsibility |
|-------+----------------|
| =src/module-system/observability.ss= | Pure ObservationEvent construction, projection, lineage, and explanation. |
| =src/module-system/debug.ss= | Condition, RecoveryDecision, coordinator, and bounded resumption policy. |
| Runtime observability adapter | Redaction, runtime measurement, publication, and receipt effects. |

The existing =src/module-system/observability.ss= is implementation evidence
for presentation-trace projections.  It does not by itself admit the POO-native
ObservationEvent and three-plane contract defined here.  This new architecture
makes no compatibility or migration commitment to presentation alists.

The target =src/module-system/debug.ss= is not implementation-admitted.

** Module-local owners

Every Module receives the core generic observation of its four responsibilities
and evaluation generations.

A Module adds local =observability.ss= only when it introduces domain-specific
observation prototypes or projections.  It adds local =debug.ss= only when it
introduces domain-specific conditions or recovery policy.  Empty placeholder
files are rejected.

#+begin_src mermaid
flowchart TB
  T["Module-local types.ss"] -->|"contracts events, conditions, and decisions"| F["Module-local func.ss"]
  F -->|"supplies pure domain projections"| O["Module-local objects.ss"]
  O -->|"supplies evaluation identities and responsibilities"| V["optional Module-local observability.ss"]
  V -->|"signals typed conditions without effects"| D["optional Module-local debug.ss"]
  V -->|"projects only redaction-safe explanations"| I["Module-local interface.ss"]
  V -->|"hands redacted events across the effect boundary"| R["runtime telemetry adapter"]
#+end_src

=observability.ss= and =debug.ss= must not be imported by =types.ss=,
=func.ss=, or Module-local =objects.ss=.  Runtime telemetry owners may consume
semantic projections; semantic owners never import runtime telemetry code.

* Public interface

This RFC adds no public macro, probe clause, handler clause, event registry, or
trace DSL.

The ordinary user interface may request a redaction-safe explanation through an
already admitted POO responsibility.  It cannot receive:

- raw candidates hidden by authority;
- secrets or runtime handles;
- raw continuations;
- coordinator recovery authority; or
- mutable trace storage.

* Ownership

- Upstream =gerbil-poo= owns prototype, dispatch, C3, and inherited continuation
  mechanics.
- =poo-flow-core= owns ObservationEvent, condition, RecoveryDecision, semantic
  budgets, and coordinator contracts.
- Each domain Module owns only its domain-specific observation and debug
  specializations.
- Runtime adapters own clocks, process metrics, external sinks, handles,
  redaction execution, and publication receipts.
- =wendao-episteme= may extend observation and debug prototypes for its domain
  without owning the generic core.
- GSLPH, Gerbil-Bazel, Nix, and =gerbil.pkg= own no Module observability
  semantics.

* Admission checklist

** Semantic governance

- [X] Keep Module at exactly four required responsibilities.
- [X] Derive observation from immutable evaluation generations.
- [X] Define ObservationEvent as a native POO value with source, generation, and
  evidence responsibilities.
- [X] Keep dispatch, fixed-point, capability, and lifecycle evidence
  distinguishable.
- [X] Keep semantic observation, debug control, and runtime telemetry separate.
- [X] Keep =super=, fixed-point resumption, and recovery continuation distinct.
- [X] Confine raw =call/cc= continuations to the debug coordinator.
- [X] Separate deterministic semantic counters from runtime measurements.
- [X] Redact before effectful telemetry publication.
- [X] Add no mutable trace store, public DSL, or empty Module-local files.

** Implementation admission

- [ ] Admit the shared =types.ss= foundation.
- [ ] Admit POO-native ObservationEvent construction and projection.
- [ ] Admit typed conditions and RecoveryDecision prototypes.
- [ ] Admit bounded coordinator continuation and resumption tests.
- [ ] Admit fixed-point cycle, budget, cache, and progress observations.
- [ ] Admit runtime metric attribution and redacted telemetry receipts.
- [ ] Select one Module with a real domain-specific observation or condition as
  the first local exemplar.

* Rejected alternatives

- A fifth =observability= slot on Module.
- A mutable global trace store.
- Copying evaluation state into alist event snapshots.
- One empty =observability.ss= or =debug.ss= in every Module.
- Boolean-only failure reports with no evidence or explanation.
- Treating =super= as a recovery continuation.
- Serializing or logging raw =call/cc= continuations.
- Reading clocks, RSS, or I/O state in semantic functions.
- Raising a runtime threshold without process-and-phase attribution.
- Publishing secrets, handles, or recovery authority through telemetry.
- A public probe, handler, trace, or recovery clause DSL.

* Successor contract

The first implementation slice remains the shared POO-native =types.ss=
foundation.  ObservationEvent and RecoveryDecision require that foundation
before any coordinator or telemetry work can be implementation-admitted.

The first Module-local exemplar must introduce a real domain-specific
observation or continuable condition.  A synthetic example or empty owner does
not satisfy admission.

* Accepted upstream ownership correction

POO slot and inheritance trace projection belongs to the pinned
=gerbil-poo= dependency.  Project observability MUST reuse
=gerbil-poo/debug.ss= for native POO trace projection rather than
implementing a parallel object tracer.

POO Flow owns the domain semantics above that projection:

- immutable semantic observation events derived from evaluation
  generations;
- explicit debug and recovery decisions, including bounded
  continuation ownership;
- redacted runtime telemetry publication behind an effect boundary.

These responsibilities do not add an observability slot to Module.
Module remains exactly =identity=, =imports=, =capabilities=, and
=profiles=.  Upstream trace projection, semantic observation, recovery
control, and runtime telemetry are distinct ownership planes.

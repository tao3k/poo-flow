* Scope

POO Flow uses Cedar as a dual-engine policy boundary:

- the Cedar Lean definitional engine owns policy semantics and formal
  theorems;
- the Cedar production engine supplies executable authorization behind the
  Cedar adapter;
- Cedar differential randomized testing checks the production engine against
  the definitional engine over generated policies, schemas, entities, and
  requests.

* Upstream evidence boundary

The Cedar Lean definitional engine exposes =evaluate=, =satisfied=, and
=isAuthorized=.  The upstream theorem surface includes:

- a satisfied forbid policy forces denial;
- authorization requires an explicit satisfied permit;
- the absence of an explicit permit forces denial;
- policy evaluation order and duplicate policies do not change authorization;
- sound policy slicing preserves authorization;
- well-typed expressions restrict the possible evaluation-error family;
- symbolic compilation is sound and complete;
- verification based on the symbolic compiler is sound and complete.

The Cedar DRT framework separately compares the Rust production
implementation with the Lean definition.  Its published target families
include ABAC and RBAC authorization, type-directed authorization, validation,
request and entity validation, partial authorization, policy/entity
round-trips, and entity slicing.

These evidence classes must not be collapsed:

1. a Cedar Lean theorem proves a property of the definitional semantics;
2. DRT supplies finite executable conformance evidence for Rust versus Lean;
3. a POO Flow refinement theorem proves that both engines received the same
   canonical input and that their outputs were projected without loss.

DRT is not a universal proof that arbitrary Rust execution equals the Lean
definition.  Conversely, a Cedar Lean theorem alone says nothing about the
correctness of the POO Flow adapter.

* Canonical policy decision input

Both engines must consume the same logical input artifact.  The input receipt
links:

- Cedar language and semantic version;
- canonical policy-set identity;
- canonical schema revision identity;
- canonical request identity;
- canonical entity-store revision identity;
- admitted extension-set identity;
- =ProfileBundle= semantic identity from RFC 45-113;
- effective capability-contract identity;
- admitted authority-risk and arbitration-policy identity.

The Cedar source text is not the policy identity.  Policy identity belongs to
the parsed and validated policy representation.  Policy order and exact
duplicates are non-semantic because the upstream authorization theorem already
proves their invariance.  Conflicting reuse of one policy identifier is an
admission error and is not normalized.

#let policy-input(

The Cedar policy-input encoding uses the same restricted deterministic-CBOR
and immutable-version rules as RFC 45-113, but it has an independent domain
tag and identity family.

* Outcome is not a Boolean

Dual-engine agreement cannot compare only =Allow= and =Deny=.  The comparison
surface is:

- exact Cedar decision: =Allow= or =Deny=;
- exact Cedar determining policy identities;
- exact Cedar erroring policy identities;
- POO Flow runtime state: completed, timeout, unavailable, crash, or malformed
  projection;
- engine semantic version and exact canonical input identity.

Runtime indeterminacy is not a Cedar decision and is never an authorization
grant.  External authority fails closed while the receipt preserves the exact
runtime cause.  Cedar =erroringPolicies= remain inside the Cedar response and
must not be replaced by an invented generic error class.

#+begin_src typst
$ O_L = "LeanEngine"(I_p) $
$ O_R = "RustEngine"(I_p) $

$ agree(I_p) := O_L = O_R $

$ not agree(I_p) => authority = "Deny"
  and admission = "Suspended"
  and receipt = "EngineDisagreement" $
#+end_src

* Confirmed risk-tier arbitration

The arbitration policy is a semantic policy object, not a caller-selected
flag.  An admitted projection from the effective capability contract supplies
the authority risk:

- governance mutation, authority elevation, capability mutation, policy
  publication, and equivalent high-authority actions are =elevated=;
- an explicitly admitted lower-authority action may be =ordinary=;
- absent or ambiguous classification is =elevated=.

#+begin_src typst
$ mode("elevated") = "strict-lockstep" $
$ mode("ordinary") = "rust-with-lean-shadow" $
$ mode("unknown") = "strict-lockstep" $

$ "strict-lockstep" and (missing or timeout or disagreement)
  => authority = "Deny" and activation = "Suspended" $

$ "conformance-backed" => per_request_dual_witness = false $

$ "shadow-completed" and O_L != O_R
  => authority = "Deny" and activation = "Suspended" $
#+end_src

For ordinary authority, a shadow that was not selected, timed out, or was
unavailable does not become a fictitious disagreement or agreement.  The
decision may use the Rust outcome only when pinned DRT conformance was
admitted, and its receipt remains =conformanceBacked= with
=perRequestDualWitness = false=.  If a shadow completes and disagrees, the
decision fails closed and the activation is suspended.

For elevated authority, a DRT receipt is necessary release evidence but is
never a replacement for the second per-request engine result.  Missing Lean,
missing Rust, either timeout, either unavailable state, malformed projection,
or full-outcome disagreement denies authority and suspends activation.  There
is no silent single-engine fallback.

* Cedar adapter admission contract

POO Flow owns one Cedar adapter boundary.  Cedar's Lean definitional engine,
production engine, DRT, and =cedar-spec= checkout are upstream evidence
providers behind that adapter; none is a separate POO Flow owner.

The Lean owner =PooFlowProof.PooC3.CedarAdapterContract= defines the evidence
required to admit the Cedar adapter.  The contract is not evidence that the
executable adapter has already been implemented.

An admitted projection must satisfy:

#+begin_src typst
$ project(raw_production_response) = expected_cedar_outcome $

$ receipt_comparable(receipt) = expected_cedar_outcome $

$ receipt.executable_digest != none $

$ expected_cedar_outcome =
  (semantic_version, canonical_input_identity, exact_cedar_response) $

Missing executable digest, response mismatch, canonical input-identity
mismatch, or semantic-version mismatch blocks adapter admission.  An admitted
projection may enter strict arbitration with the Lean outcome and produces a
dual witness only because both complete comparable outcomes are then equal.

* POO-native Cedar adapter refinement

The single POO Flow owner is a native =gerbil-poo= adapter object.  Its
physical representation has exactly three object slots:

#+begin_src typst
$ "PhysicalCedarAdapter" =
  (
    "definitionalEngine",
    "productionEngine",
    "arbitrationPolicy",
  ) $

$ adapter_identity =
  H_a(
    definitional_engine.identity,
    production_engine.identity,
    shared_semantic_version,
    arbitration_policy.identity,
  ) $
#+end_src

Canonical policy input, request, entities, policy set, =ProfileBundle=
identity, effective capability, authorization outcome, and receipts are not
physical adapter slots.  They are invocation values or derived observations.
Storing them on the adapter object would conflate a stable POO object with
per-request state.

Admission requires:

- definitional and production engines expose the same Cedar semantic version;
- their executable identities are different;
- the arbitration policy is a POO object whose identity contributes to the
  derived adapter identity.

Using one engine object in both roles is not dual-engine evidence and blocks
admission.  A semantic-version disagreement also blocks admission.

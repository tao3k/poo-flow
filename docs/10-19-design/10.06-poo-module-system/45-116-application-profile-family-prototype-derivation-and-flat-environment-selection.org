#+title: Application Profile Family, Prototype Derivation, and Flat Environment Selection
#+startup: overview

* Status

Accepted architecture decision.

This RFC continues the pure application-profile boundary defined by
[[file:45-115-application-environment-profile-purity-and-capability-scoped-deployment-runtime-input-boundary.org][45-115]].

* Evidence state

A parser-owned ASP owner search used 45-113 as the exact owner anchor.  It
succeeded.

The receipt confirmed:

- the ordinary surface remains =use-composition=, =compose=, =profiles=, and
  =use-module=;
- =compose= with =profiles= is pure;
- profile resolution cannot implicitly observe environment, filesystem, time,
  entropy, network, secrets, or mutable deployment state;
- no environment DSL, Nix-to-POO language, or public input macro is admitted;
- implementation ownership remains =MISSING=.

The receipt did not identify exact upstream =gerbil-poo= authoring operators.
This RFC therefore defines the POO algebra without inventing concrete operator
names.

* Scope

This RFC defines:

- an application-owned profile family;
- immutable base-profile prototypes;
- production, research, sandbox, and replay variants;
- typed contribution and withdrawal;
- explicit deployment-mode selection;
- higher-order POO dispatch;
- flat ordinary composition;
- variant identity, conflict, and explanation behavior.

This RFC does not define:

- global built-in environment profiles;
- an environment enum DSL;
- a host conditional inside composition;
- a =profile-family= macro;
- a new precedence algebra;
- mutable prototype inheritance;
- runtime profile switching without recomposition.

* Central decision

An application profile family is expressed through POO prototypes, derived
profile objects, and typed lineage relations.

Ordinary composition receives one already selected profile value:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

It does not select the environment with =if=, =cond=, keyword clauses, or an
environment macro.

* Profile family

=ApplicationProfileFamily= is a higher-order POO value that may own:

- one immutable application base-profile prototype;
- derived application profile values;
- explicit supported-mode identities;
- mode-to-profile POO dispatch;
- family-wide invariants;
- derivation and provenance relations.

It is not:

- a raw map from symbols to records;
- a global registry;
- a mutable configuration object;
- the ordinary user composition surface.

The ordinary user sees exported derived profile values.

* Base-profile prototype

The application base-profile prototype contains only application-wide
semantics shared by every derived variant.

It may contribute:

- common responsibilities;
- common capability attenuation;
- common redaction and retention;
- common runtime adapter requirements;
- common recovery invariants;
- common observability bounds;
- common package-independent application identity.

It does not contain:

- environment-specific secret values;
- mutable environment observations;
- production-only budgets disguised as universal defaults;
- domain profiles owned by =wendao-episteme=;
- runtime capabilities.

* Immutable derivation

Every variant is derived through native POO prototype extension.

Derivation:

- leaves the base prototype unchanged;
- creates a new application-owned profile identity;
- creates a new immutable profile revision;
- preserves explicit =derived-from= provenance;
- adds typed contributions;
- performs authorized typed withdrawals;
- reuses existing precedence and conflict semantics;
- produces a pure profile value.

No derived profile mutates or overwrites the base.

* Typed variant delta

A variant delta is expressed through native POO relations such as:

- contribution;
- requirement;
- attenuation;
- withdrawal;
- precedence;
- conflict;
- responsibility attachment.

This RFC does not define a patch DSL.

Source order is not a delta or override mechanism.

* Illustrative variant roles

The following names are illustrative application-owned profiles.  They are not
global core profiles.

| Variant | Illustrative semantic emphasis |
|---------+--------------------------------|
| =application-production= | strict publication, bounded recovery, production runtime requirements, narrow diagnostic retention |
| =application-research= | broader authorized explanation, isolated experiments, larger bounded diagnostic budget, restricted publication |
| =application-sandbox= | strong capability attenuation, filesystem/network restriction, low budgets, explicit disposable state |
| =application-replay= | recorded observations, no live commit authority, no live continuation access, isolated caches |

An application may export different variants or different names.

* Domain and application separation

A composed system may select:

- a domain profile from =wendao-episteme=;
- an infrastructure or agent profile from another POO module;
- one application-owned operational profile.

The application profile does not absorb or rename the upstream domain profile.

Each contribution retains its canonical owner and revision.

* Production case

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    (use-module agent session-hardened)
    application-production))
#+end_src

* Research case

#+begin_src scheme
(use-composition research-system
  (compose profiles
    (use-module wendao-episteme research)
    (use-module agent sandbox-restricted)
    application-research))
#+end_src

* Sandbox case

#+begin_src scheme
(use-composition sandbox-system
  (compose profiles
    (use-module wendao-episteme research)
    (use-module agent sandbox-restricted)
    application-sandbox))
#+end_src

* Replay case

#+begin_src scheme
(use-composition replay-system
  (compose profiles
    (use-module wendao-episteme replay)
    application-replay))
#+end_src

Module and profile names in these cases are illustrative.  The normative
contract is the flat composition shape and ownership separation.

* No host conditional

The following conceptual shape is rejected:

#+begin_example
(compose profiles
  (if production?
      application-production
      application-research))
#+end_example

It hides selection provenance inside host control flow and makes the
composition graph depend on an untyped boolean.

Selection occurs before ordinary composition through one of two explicit
mechanisms:

- a statically selected application entry point;
- higher-order POO dispatch over an explicit =DeploymentMode= value.

* Static entry-point selection

Static entry-point selection is the ordinary and preferred path.

Different deployment entry points bind different composition values:

- production entry point selects =production-system=;
- research entry point selects =research-system=;
- sandbox entry point selects =sandbox-system=;
- replay entry point selects =replay-system=.

The deployment system selects an entry point.  It does not inject conditionals
into the profile composition.

Nix or another deployment tool may select which already-declared entry point is
launched.  It does not become a POO profile owner.

* DeploymentMode

=DeploymentMode= is an explicit immutable non-secret POO semantic input.

It has:

- typed mode identity;
- application owner;
- immutable revision;
- allowed profile-family scope;
- provenance.

It is not:

- an environment-variable lookup;
- a raw string;
- a keyword clause;
- a runtime observation;
- a capability.

When a mode affects the semantic composition, its identity appears in the
derived profile and composition receipt.

* Higher-order POO dispatch

When one application entry point must resolve a mode, the advanced layer uses a
higher-order POO dispatch object:

#+begin_example
ApplicationProfileFamily
  × DeploymentMode
  -> DerivedApplicationProfile
     | TypedModeSelectionConflict
#+end_example

Dispatch:

- is pure;
- is total over the declared supported modes or returns typed conflict;
- returns a native POO profile value;
- retains family, mode, and derived-profile identities;
- performs no environment or runtime observation;
- grants no capability.

Exact dispatch syntax must use verified native =gerbil-poo= operations.

* Selection flow

#+begin_src mermaid
flowchart LR
  D["Explicit DeploymentMode or selected entry point"] -->|"application-owned selection identity is fixed"| F["ApplicationProfileFamily"]
  F -->|"native POO dispatch finds supported mode"| V["Derived application profile"]
  F -->|"mode is missing, ambiguous, or unsupported"| X["Typed mode-selection conflict"]
  V -->|"flat compose receives one immutable profile value"| C["compose with profiles strategy"]
  U["Module-owned domain profiles"] -->|"canonical owners and revisions remain distinct"| C
  C -->|"pure resolution validates contributions and precedence"| R["Resolved composition"]
  R -->|"mode and derivation provenance are recorded"| E["ResolvedCompositionReceipt"]
  X -->|"no runtime action is admitted"| Q["Explanation evidence"]
#+end_src

There is no environment observation edge inside profile resolution.

* Prototype family graph

#+begin_src mermaid
flowchart TD
  B["Immutable application base-profile prototype"] -->|"adds strict publication and bounded recovery contributions"| P["application-production"]
  B -->|"adds isolated research observation and non-publication constraints"| R["application-research"]
  B -->|"adds strong capability attenuation and disposable-state constraints"| S["application-sandbox"]
  B -->|"withdraws live effects and requires recorded observations"| Y["application-replay"]
  P -->|"retains derived-from provenance and new immutable revision"| PI["Production profile identity"]
  R -->|"retains derived-from provenance and new immutable revision"| RI["Research profile identity"]
  S -->|"retains derived-from provenance and new immutable revision"| SI["Sandbox profile identity"]
  Y -->|"retains derived-from provenance and new immutable revision"| YI["Replay profile identity"]
#+end_src

The edge labels describe semantic delta.  They are not source-order overrides.

* Precedence and conflict

Variant derivation reuses existing native POO precedence and typed relation
conflict semantics.

It does not introduce:

- environment-specific merge order;
- last-profile-wins behavior;
- source-order priority;
- hidden fallback;
- automatic conflict weakening.

Explicit priority and authority are evaluated by their existing contracts.
Independent constraints survive composition.

* Withdrawal behavior

A derived variant may withdraw a contribution only when:

- the contribution relation is typed as withdrawable;
- the withdrawing profile has the required ownership or authority;
- the withdrawal identifies its target precisely;
- surviving requirements remain satisfiable;
- the resolved receipt records the withdrawal and provenance.

A variant cannot withdraw an upstream module's responsibility merely because it
has a stronger numerical priority.

* Family-wide invariants

An application profile family may require every exported variant to preserve:

- application identity;
- required domain responsibilities;
- mandatory redaction;
- mandatory cleanup and reconciliation;
- capability non-escalation;
- semantic and runtime cache isolation;
- explicit input purity;
- profile export provenance.

A variant failing a family-wide invariant is not exported as a valid profile.

* Variant validation

Every exported variant is composed and validated independently.

Validation checks:

- base-prototype revision;
- derivation lineage;
- contribution and withdrawal legality;
- precedence conflicts;
- capability attenuation;
- module responsibility reachability;
- static semantic input identity;
- absence of ambient observations;
- cache and publication isolation;
- recovery and replay boundaries.

Successful validation of one variant does not imply validation of another.

* Runtime switching

A running composition cannot mutate from production to research, sandbox, or
replay in place.

Changing mode requires:

1. select or dispatch a new derived profile value;
2. create a new resolved composition;
3. validate the new composition;
4. create a new composition receipt;
5. use explicit publication and live-upgrade contracts;
6. request fresh runtime admission.

Prior composition and runtime receipts remain immutable.

* Explanation surface

The POO-native explanation interface can answer:

- which application profile variant was selected;
- which entry point or =DeploymentMode= selected it;
- which base prototype revision it extends;
- which contributions and withdrawals distinguish it;
- which conflict prevented mode selection;
- why a constraint survived precedence;
- which domain and application owners contributed independently.

Explanation does not expose ambient environment state because selection did not
depend on it.

* Ownership

=poo-flow-core= owns the generic profile, prototype, contribution, and conflict
contracts.

=wendao-episteme= owns its domain profiles.

The final application repository owns:

- its profile-family value;
- its base application-profile prototype;
- its derived variants;
- its =DeploymentMode= identities;
- its deployment entry points;
- its final composition bindings.

Deployment tools select entry points or provide explicit safe inputs.  They do
not own profile semantics.

* Public interface boundary

Ordinary users use flat composition forms shown in this RFC.

Profile authors use verified native =gerbil-poo= object and prototype
operations.

Framework authors may extend typed family and dispatch protocols through native
POO prototypes.

No public profile-family, environment-selection, switch, or mode macro is
introduced.

* Failure behavior

The system fails closed on:

- host =if= or =cond= inside profile composition;
- ambient environment lookup used to choose a variant;
- a raw string used as =DeploymentMode=;
- an unsupported or ambiguous mode silently falling back;
- derived profile mutating its base;
- source order used as precedence;
- unauthorized withdrawal;
- application variant impersonating an upstream domain profile;
- runtime mode mutation without recomposition;
- deployment tool treated as semantic owner;
- one variant's validation result reused for another variant.

- [X] Base prototypes remain unchanged by derivation.
- [X] Ordinary composition receives one selected profile value.
- [X] Selection uses a static entry point or explicit POO =DeploymentMode=.
- [X] No host conditional appears inside =compose profiles=.
- [X] Higher-order dispatch is pure and returns typed conflict.
- [X] Existing precedence and conflict semantics are reused.
- [X] Source order never becomes implicit override.

This section is normative and supersedes earlier audit statements that
implementation ownership was =MISSING=. Unchecked items below concern
implementation completion, not owner selection.

  used by that family.

  implementation work.

#+title: Core Module System ownership and migration audit

* Decision and migration baseline

The generic POO Module System is a Core mechanism.  =src/module-system/= is
not its permanent owner.  Core owns module identity, contracts, descriptors,
source references, lazy selection, pure resolution, option projection, Profile
composition, and generic module diagnostics.  POO Flow owns named product
modules, policies, source locations, ASP/runtime handoffs, and presentation.
The POO Flow implementation no longer has a =src/module-system/= directory or
compatibility import aliases: consumers import the single owner directly.

This audit records parent commit =deca0fb= and Core gitlink =3c42394=.
At that commit, =src/module-system/= had 49 Scheme files (9,925 lines). Core already
owns =module-system/schema/=, =object-family/=, =extension-graph/=, =contribution/=,
=composition/lineage.ss=, generic =observability/=, and =poo-clos/=.
No current Core Scheme source imports =:poo-flow/=.  Twelve checked-out
Lambda-episteme Scheme files directly import the current module-system path;
that is a consumer migration, not a reason to retain two authorities.

Deleting thin =interface.ss= files alone did not move the mechanism. Core now
owns the generic catalog and option validation; product descriptor projection
lives in =src/authoring/module-option-projection.ss=. Product runtime receipts
and scalar presentation now live in =src/user-interface/module-runtime-presentation.ss=;
the closure and phase-order mechanism they use remains in Core.

* Final product adapters

Core owns the reusable descriptor, LoadPath, Catalog, lazy-load, and import
closure mechanisms. POO Flow keeps only its branded values and policy adapters:

| Product owner | Source | Boundary |
|-
| Authoring | =src/authoring/module-descriptor.ss= | POO Flow Task/Flow descriptor slots and import admission over Core closure. |
| Authoring | =src/authoring/module-source-collection.ss= | Maintained/contributor filesystem discovery and role/style policy over Core LoadPath. |
| User Interface | =src/user-interface/module-activation.ss= | Typed source failure, Doctor handoff, Task/Flow activation, and RunConfig lowering over Core Catalog. |
| User Interface | =src/user-interface/module-source-tree.ss= | Maintained/user roots and catalog assembly over Core lazy plans and extension graph. |

* Dependency blockers and required order

The current cuts remove the old =profile-composition/=, =observability/=,
and =semantic-module/= subdirectories from =src/module-system/=. They also
move user-selection flags/syntax and the product value catalog to
=src/user-interface/=. Product SemanticModule authoring defaults now live in
=src/authoring/semantic-module.ss=. Core owns Profile selection,
ProfileBundle algebra, and generic observation output. Scenario owns its root
syntax/projection. Product observation inputs and presentation are placed with
Authoring, Testing, Building, and User Interface rather than recreating a
second =src/observability/= owner. The =src/module-system/= directory is
removed after its consumers import Core or these product owners directly.
POO Flow selection values and the
public =use-module= category/flag contract now live in
=src/user-interface/module-selection.ss= and =module-selection-contract.ss=;
Core owns the generic Profile selection algebra. Product source admission lives in
=src/authoring/module-source-admission.ss= and imports generic Core POO
contracts directly; its role and repair vocabulary are POO Flow policy.
Product module config authoring now
lives in =src/authoring/module-config-syntax.ss=; user-facing module and catalog
syntax lives in =src/user-interface/module-authoring-syntax.ss=. Neither is a
separate Core mechanism: the generated forms are POO values, while their public
vocabulary and contract lowering remain POO Flow-owned. Shared final projection and runtime
receipt syntax now live in =src/utilities/=, while POO Flow identity and default
Interface policy live in =src/authoring/module-interface.ss=.

The first Core owner cut is tracked in =poo-flow-core#16= at =ceb5fe5=:
host-trusted verification and semantic Module Contracts/construction moved
to =core/contribution/verification.ss= and =core/module-system/=.
The same Core branch now also owns generic =core/module-system/config.ss= schema indexing,
option policy, and construction; POO Flow retains its brand, receipt kinds,
and default authoring Profile.  Generic ordered inline closure and missing
import findings now live in =core/module-system/graph/funs.ss=; POO Flow supplies
descriptor accessors.  Inert SourceRef identity and inspection now live in
=core/module-system/source/objects.ss=; product import forms remain in POO Flow.
=src/module-system/loader/context.ss= has been removed: its pure queries live
in =core/module-system/funs.ss=, while product =active?= admission lives
with the POO Flow descriptor.
The full Backend mechanism now lives in =core/module-system/loader/objects.ss=; the
product Loader imports it directly and the old Backend file is removed.
Immutable Catalog objects, first-match SourceRef lookup, and inspection now
live in =core/module-system/catalog/objects.ss=.  POO Flow's resolver retains typed
missing-source failure, Doctor, and Task/Flow activation.  Product internals
import Core Catalog directly; the product resolver no longer reexports its
generic bindings.
The POO Flow source, test, and build roots no longer import the old tree.
Downstream repositories remain independent consumers and need their own
exact-head validation before their dependency pins change.

The resulting dependency direction is =Core -> gerbil-parser -> POO Flow=;
Core may depend on Gerbil/gerbil-poo standard facilities but not on
=:poo-flow/=, ASP, Lambda-episteme, or parser-owned syntax.  POO Flow adapters
consume Core through direct imports.  Candidate composition stays pure;
filesystem/process effects remain behind explicit host/runtime handoffs.

The =src/core/= directory is POO Flow's historical product code, not the
independent =core/= package. Its =plan.ss= imports POO Flow Flow, Task, and
projection syntax; the Scenario projection therefore stays under
=src/scenario/= rather than claiming Core package ownership.

* Native configuration composition

Ordinary inherited configuration is a native POO object relation, not a second
Nix-style evaluator. Core =SemanticModule= now composes its =imports= object
through the POO prototype chain. The =contributions= slot rule prepends local
values to the inherited value; C4, not a hand-written graph merge, determines
ancestor precedence and de-duplicates diamonds. A leaf retains the identity of
the imports object passed to its constructor. Core tests cover that identity
and a diamond with one shared base.

Sandbox Profile resolution now builds native POO prototypes from backend field
defaults and applies validated rows with prototype extension. Explicit
append/prepend/remove semantics reuse Core's pure slot-value policy; Sandbox no
longer constructs field-contribution lists or invokes =mk-merge=. In the local
1000-Profile case the old path measured 235 ms and the new path measured
213-263 ms on the same machine. These single runs do not establish a speedup;
the new path remains inside the focused 3000 ms scale gate.

The ambiguous schema =support/merge.ss= and =mk-merge= entry are removed.
Core now separates pure =slot-policy.ss= from targeted
=field-resolution.ss=. Core's object-catalog fallback still invokes the latter
for extension-graph operations; it is not ordinary inherited configuration.
The result object is now named =field-resolution-result=, while loader graph
contributions use the explicit =auto-imports-resolve= entrypoint; neither is a
second ordinary-configuration evaluator.
Child topology and other non-inheritance operations remain explicit and
require separate evidence before further simplification.

The object-catalog fast path is restricted to direct-child contributions. A
contribution addressed to the =objects= root must use the extension resolver:
root slot changes and child topology operations cannot be silently discarded
by child-only grouping. Core now tests a root update together with a child
update; the child-only List merge retains its measured performance gate.

The parent package pins parser =fb2485d= and Orgize =f80ee4d= together.
The former is the exact Core-namespace parser revision required by the
latter. Orgize =8f615eb= instead required parser =2adf0e3=, which still
imports =:poo-flow-foundation/= and fails the Core-only external Bazel build;
the older Orgize =79f8471= pin does not resolve in the current repository.
The Bazel =orgize_package= now declares its parser package dependency, so
isolated external-module builds follow the same graph as =gxpkg=.
Dependency installation must use a clean isolated =GERBIL_PATH= for this pin
change; never remove an installed package to work around a tag conflict.

* Admission and publication gates

- The migration must not introduce a second Module descriptor, schema,
  option-merge algorithm, loader registry, or compatibility alias.
- Core: =just test= before =just build=; native owner tests must cover deep
  prototypes, wide option schemas, lazy 100/1,000-module catalog selection,
  missing/conflicting imports, and non-mutating diagnostics.
- POO Flow: focused consumer tests, then heap-fenced =just test= before
  =just build=.  Require =MODULE-OK=, =HARNESS-OK=, final =OK=, and no
  =ERROR CASE= / =ERROR HARNESS= / heap or stack overflow markers.
  After a module-path migration in a persistent =GERBIL_PATH=, clean and
  rebuild before the full-suite rerun so old compiled imports cannot create
  duplicate POO type identities.
- Lambda-episteme: rewire its direct declaration, Profile, loader, and
  testing-adapter imports; validate its owned tests before updating the
  gitlink.  Do not silently leave the old path as an alias.
- Verify Core has no =:poo-flow/=, ASP, Lambda, or parser imports; verify no
  remaining =:poo-flow/src/module-system/= import after cutover.  The
  exact post-push Ubuntu jobs, not an earlier green head, are the PR gate.

Core is a separate Git repository and source-owned submodule. Core PR #16
owns these migrations. Parent PR #57 cannot itself publish a new Core
commit: the Core change must be published and admitted in its own repository
before #57 pins its commit.  Do not push unreviewed Core changes directly to
=main= or silently open another PR against the user's one-PR instruction.

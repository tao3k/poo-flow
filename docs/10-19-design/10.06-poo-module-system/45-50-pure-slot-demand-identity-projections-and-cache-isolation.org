#+title: Pure Slot Demand Identity Projections and Cache Isolation
#+subtitle: Semantic targets, causal paths, evidence requests, execution policy, and capability-safe reuse
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative demand and cache protocol
- Semantic core :: Native POO demand values and POO Flow evaluation
- Related modules :: =45-44-semantic-generation-transition-and-execution-identity.org= and =45-49-profiles-strategy-facets-and-pure-demand-boundary.org=

This module defines one pure POO slot-demand object with multiple identity projections. It prevents causal roots, evidence requests, budgets, deadlines, and live authorization resources from contaminating business-result cache identity.

* Core decision

#+begin_quote
A PureSlotDemand is a multi-projection POO object. Semantic target, causal path, evidence request, and execution policy have separate identities. Only the semantic target addresses the business result.
#+end_quote

The required projections are:

#+begin_src text
SemanticSlotTargetIdentity
DemandCausalIdentity
DemandEvidenceRequestIdentity
DemandExecutionPolicyIdentity
#+end_src

They remain facets of one POO value rather than separate registries or object systems.

* Typst formalization: business-result cache projection

The identity separation is represented by a product whose components have
different types.  The business-result cache projection is permitted to observe
only the semantic target.

#+begin_src typst
$
  "PureSlotDemand" &= T times C times E times X \
  T &= "SemanticSlotTargetIdentity" \
  C &= "DemandCausalIdentity" \
  E &= "DemandEvidenceRequestIdentity" \
  X &= "DemandExecutionPolicyIdentity" \
  k_"business" &: "PureSlotDemand" -> T \
  k_"business"(t, c, e, x) &= t \
  forall c_1, c_2 in C, quad
    k_"business"(t, c_1, e, x) &=
      k_"business"(t, c_2, e, x) \
  forall e_1, e_2 in E, quad
    k_"business"(t, c, e_1, x) &=
      k_"business"(t, c, e_2, x) \
  forall x_1, x_2 in X, quad
    k_"business"(t, c, e, x_1) &=
      k_"business"(t, c, e, x_2) \
  forall l_1, l_2 in "LiveEvaluationContext", quad
    k_"business"^"live"((d, l_1)) &=
      k_"business"^"live"((d, l_2))
$
#+end_src

Therefore different causal roots, evidence projections, execution policies, or
live resources may produce different receipts and evaluation behavior, but
they cannot split the cache entry for the same semantic target.

* Semantic slot target identity

=SemanticSlotTargetIdentity= answers:

#+begin_quote
Which pure semantic value is requested?
#+end_quote

It is conceptually derived from:

#+begin_src text
H(
  SemanticGenerationIdentity,
  semantic slot reference,
  canonical semantic-view or admission projection,
  semantic evaluator protocol identity
)
#+end_src

It does not contain:

- root caller identity;
- parent demand identity;
- evidence verbosity or redaction request;
- timeout, deadline, or remaining budget;
- worker or scheduler;
- live capability token or lease;
- cancellation handle;
- continuation or recovery portal.

Different callers requesting the same semantic slot in the same canonical semantic view share one business-result identity.

* Demand causal identity

=DemandCausalIdentity= answers:

#+begin_quote
Why did this execution request the semantic target?
#+end_quote

It is conceptually derived from:

#+begin_src text
H(
  root demand identity,
  parent demand identity,
  dependency-edge role,
  SemanticSlotTargetIdentity
)
#+end_src

It supports:

- demand graph construction;
- cycle and current-generation SCC explanation;
- root-to-slot causal traces;
- root-demand recovery-budget ownership;
- cancellation and subscriber tracking.

It does not enter the business-result cache key.

Two roots may share the same semantic result while retaining different causal receipts.

* Demand evidence-request identity

=DemandEvidenceRequestIdentity= answers:

#+begin_quote
Which proof and disclosure projection does this caller require?
#+end_quote

It may include:

- evidence projection identity;
- proof protocol identity;
- retention and redaction projection;
- disclosure-scope identity;
- requested explanation depth.

It addresses evidence materialization and evidence caches, not the business-result cache.

When a business result is already reusable but existing evidence cannot satisfy a new request, the runtime may reevaluate the same semantic target to produce evidence. The reevaluation has a new execution identity and does not manufacture a new business semantic identity.

* Demand execution-policy identity

=DemandExecutionPolicyIdentity= answers:

#+begin_quote
Which operational policy constrains this evaluation attempt?
#+end_quote

It may contain pure descriptors for:

- budget policy;
- retry policy;
- cancellation policy;
- deadline class;
- scheduler class;
- cache-use policy.

Actual live state remains in =LiveEvaluationContext=:

- remaining counters;
- absolute deadline;
- cancellation handle;
- worker and scheduler instances;
- cache client;
- live capability token or lease;
- continuation and recovery portal.

Execution policy does not enter business-result identity.

* Budget exhaustion is operational

Budget exhaustion, deadline expiry, cancellation, and worker failure are operational outcomes. They are not semantic slot conflicts and must not be cached as the business value of the semantic target.

A later execution with a different live context may still compute the same semantic target.

#+begin_src mermaid
flowchart LR
    D["One SemanticSlotTargetIdentity"] -->|"attempt under execution policy P1"| E1["Evaluation execution E1"]
    E1 -->|"budget is exhausted"| O1["Operational failure receipt"]
    D -->|"attempt under execution policy P2"| E2["Evaluation execution E2"]
    E2 -->|"evaluation completes"| V["Reusable semantic result"]
    O1 -->|"must not populate business-result cache"| X["Semantic cache remains unresolved"]
    V -->|"populate business-result cache"| K["Semantic result namespace"]
#+end_src

* Capability-safe semantic views

Capability handling has two distinct forms.

** Access-only capability

When capability controls only access or disclosure:

- the business semantic result is unchanged;
- authorization is validated at delivery;
- the live token does not enter the semantic result key;
- evidence projection uses its disclosure-scope identity;
- cached material is not released without current authorization.

** Semantics-affecting capability

When capability changes which contributions participate:

- the canonical authority-scope or admission projection participates in =SemanticSlotTargetIdentity= or the semantic generation projection;
- the live token, secret, and lease handle remain excluded;
- different valid tokens proving the same canonical scope share one semantic target.

The system must not use a token digest as a shortcut for canonical admission scope.

* Concurrent demand coalescing

Multiple callers may coalesce onto one semantic target while retaining:

- independent causal identities;
- independent evidence requests;
- independent authorization checks;
- independent cancellation subscriptions;
- independent operational receipts.

One caller's cancellation does not cancel work still required by another valid subscriber. The runtime may cancel underlying work only when no valid subscriber remains or when an explicit execution policy permits shared cancellation.

#+begin_src mermaid
flowchart LR
    R1["Root demand A"] -->|"create causal edge A to X"| C1["DemandCausalIdentity A-X"]
    R2["Root demand B"] -->|"create causal edge B to X"| C2["DemandCausalIdentity B-X"]
    C1 -->|"reference the same semantic target"| S["SemanticSlotTargetIdentity X"]
    C2 -->|"reference the same semantic target"| S
    S -->|"address one reusable business value"| V["Semantic result cache"]

    Q2["Audit evidence request"] -->|"select a different projection"| P2["Evidence materialization 2"]
    X1["Live execution context 1"] -->|"may cancel without cancelling other subscribers"| O1["Execution receipt 1"]
    X2["Live execution context 2"] -->|"may complete the shared target"| O2["Execution receipt 2"]
    O2 -->|"commit the reusable result"| V
#+end_src

* Pure and live boundary

The pure demand object contains the four pure projections. Evaluation receives live resources separately:

#+begin_src text
evaluate(
  PureSlotDemand,
  LiveEvaluationContext
)
#+end_src

The pure object does not capture the live context in a closure, strategy slot, registry entry, or hidden dynamic variable.

One pure demand may be evaluated by multiple live contexts. Each execution has a distinct =EvaluationExecutionIdentity= while successful executions converge on the same semantic result identity.

* Cache namespaces

The business-result cache is conceptually keyed by:

#+begin_src text
SemanticSlotTargetIdentity
#+end_src

The evidence cache is conceptually keyed by:

#+begin_src text
SemanticSlotTargetIdentity
+ DemandEvidenceRequestIdentity
+ proof materialization protocol identity
#+end_src

Operational receipts are keyed by evaluation execution identity and may reference:

- causal identity;
- execution-policy identity;
- semantic target identity;
- evidence-request identity.

Neither an operational failure nor an authorization event becomes a business-result cache entry.

* Identity and cache laws

- Semantic-target isolation :: Caller, evidence, and execution policy do not alter business-result identity.
- Causal preservation :: Shared results retain distinct demand paths and roots.
- Evidence isolation :: Evidence projection changes do not manufacture a new business value.
- Operational isolation :: Budget, deadline, cancellation, worker, and retry outcomes do not become semantic conflicts.
- Capability safety :: Live tokens do not enter cache keys and cached values are not disclosed without current authorization.
- Canonical-scope reuse :: Different tokens proving the same semantics-affecting scope share one target.
- Coalescing safety :: Shared work preserves independent cancellation, authorization, evidence, and receipts.
- Pure/live separation :: The pure demand object does not capture runtime handles.

* Evidence requirements

Demand evidence records:

- all four demand projection identities;
- semantic generation and slot reference;
- root and parent causal identities;
- evidence projection and disclosure scope;
- execution-policy identity;
- live execution identity;
- coalesced subscriber identities permitted for disclosure;
- cancellation and budget outcomes;
- semantic cache, evidence cache, and operational namespace decisions;
- canonical capability-scope projection without live token material.

* Implementation checklist

- [ ] Define one pure POO =SlotDemand= object with four identity projections.
- [ ] Define canonical =SemanticSlotTargetIdentity=.
- [ ] Keep root and parent demand identity outside the semantic cache key.
- [ ] Define causal identities for demand graph and SCC evidence.
- [ ] Define evidence-request identity and evidence-cache namespace.
- [ ] Define pure execution-policy identity separately from live counters and handles.
- [ ] Treat budget exhaustion, deadline, cancellation, and worker failure as operational outcomes.
- [ ] Prevent operational failure from populating the business-result cache.
- [ ] Distinguish access-only from semantics-affecting capability.
- [ ] Canonicalize authority scope without hashing live tokens or secrets.
- [ ] Revalidate authorization when serving cached results or evidence.
- [ ] Coalesce equal semantic targets while preserving per-caller causal and operational state.
- [ ] Prevent one subscriber cancellation from invalidating other valid subscribers.
- [ ] Generate separate semantic, evidence, causal, and execution receipts.
- [ ] Verify that the pure demand object captures no live runtime resource.
- [ ] Validate the final POO projection against real =gerbil-poo= primitives.

* Non-goals

- Do not use one undifferentiated demand identity.
- Do not include evidence verbosity, deadline, worker, or root caller in the business cache key.
- Do not cache budget exhaustion as a semantic slot result.
- Do not hash live capability tokens, leases, or secrets into semantic identity.
- Do not let one caller's cancellation silently cancel other subscribers.
- Do not hide live evaluation context inside the pure demand object.
- Do not introduce demand registries, callback tables, or a demand DSL.

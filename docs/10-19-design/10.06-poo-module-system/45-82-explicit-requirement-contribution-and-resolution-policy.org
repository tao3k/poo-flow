#+title: Explicit Requirement, Contribution, and Resolution Policy
#+startup: overview

* Status

This RFC records the accepted semantic-requirement resolution model inside one
explicit POO composition-root closure.

It extends the separation between Gerbil module imports and POO semantic
requirements. It rejects runtime provider search, nearest-match lookup, hidden
registries, and operand-order winners.

* Typst formalization: explicit deterministic requirement resolution

Resolution is a pure relation inside one explicit operand closure.  Candidate
construction never searches loaded modules, the filesystem, or a global
registry.  Complete semantic identities, not lexical names, determine matching.

#+begin_src typst
#let candidate-closure(requirement, composition-root) = (
  contribution |
  contribution in explicit-operands(composition-root)
  and visible-by-scope(requirement, contribution)
)

#let resolution-id(requirement, candidates, policy) = (
  requirement.identity,
  candidates.identity,
  policy.identity,
)

$ resolve(requirement, root, policy)
  ==> pure(policy)
  and candidates = candidate-closure(requirement, root)
  and not reads-loaded-module-state(policy)
  and not reads-filesystem-state(policy)
  and not reads-global-registry(policy) $

$ lexical-name(a) = lexical-name(b)
  ==> not proves(
    lexical-name(a) = lexical-name(b),
    semantic-identity(a) = semantic-identity(b),
  ) $
#+end_src

Compatibility is directional from contribution to requirement.  Capability
contracts do not grant live tokens; priority is local to an exact slot;
operand order and global profile priority cannot resolve ambiguity.

#+begin_src typst
#let compatible(contribution, requirement) = (
  contribution.contract satisfies requirement.contract
  and accepts-revision(requirement, contribution.revision)
  and not capability-scope-escalation(contribution, requirement)
  and confidentiality-sufficient(contribution, requirement)
  and lifecycle-constraints-hold(contribution, requirement)
)

$ capability-contract(contribution)
  ==> not live-capability-token(contribution) $

$ priority(contribution)
  ==> scoped-to(priority(contribution), contribution.slot) $

$ ambiguous(candidates)
  ==> not operand-order-winner(candidates)
  and not global-profile-priority-winner(candidates)
  and fail-closed(resolution) $

$ outcome in ("missing", "incomplete", "admitted-absence")
  ==> pairwise-distinct(outcome) $

$ cyclic(requirements)
  ==> semantic-scc(requirements) $
#+end_src

* Central decision

Requirement resolution is not runtime discovery.

It proves a deterministic semantic relationship between one POO requirement
and explicit POO contributions already contained in the canonical composition
root.

The model uses three ordinary higher-order POO objects:

- =SemanticRequirement=;
- =SemanticContribution=;
- =RequirementResolutionPolicy=.

* POO semantic ownership

Requirement, contribution, visibility, compatibility, selection, aggregation,
and failure policy are native POO objects and prototype relations.

The public extension interface remains POO-native. Resolution must not become a
registry-record format, raw alist DSL, keyword-clause language, or runtime
search callback.

The exact object and slot operations remain deferred until verified against the
real =gerbil-poo= API.

* Semantic requirement

A =SemanticRequirement= projects:

- requirement identity;
- requester profile and anchor identities;
- requester scope path;
- required contract projection;
- required semantic subject or anchor;
- visibility relation;
- multiplicity or aggregation policy;
- capability contract requirement;
- selection policy;
- failure policy.

The requirement is an immutable semantic object.

It does not perform filesystem, module, package, registry, or network lookup.

* Semantic contribution

A =SemanticContribution= projects:

- contribution identity;
- contributor profile and anchor identities;
- contributor scope path;
- offered contract projection;
- semantic subject identity;
- visibility and export relation;
- slot contribution and priority evidence;
- capability contract projection;
- construction provenance.

A contribution is not a live capability token and is not a dynamically
registered service endpoint.

* Requirement resolution policy

A pure =RequirementResolutionPolicy= determines:

- candidate scope construction;
- visibility admission;
- directional contract compatibility;
- selection or aggregation;
- ambiguity handling;
- explicit absence behavior;
- resolution receipt production.

The policy has no authority to load modules, start services, probe workers, or
acquire capabilities.

* Explicit candidate universe

The candidate universe contains only:

- profiles explicitly supplied to =compose profiles=;
- POO objects explicitly contained by those profiles;
- nested profile and submodule projections explicitly exported by those
  objects;
- ordinary objects constructed by admitted higher-order profile composition.

It excludes:

- all loaded Gerbil modules;
- all installed Gerbil packages;
- filesystem entries;
- Git submodules;
- network endpoints;
- global registries;
- runtime health probes;
- whichever worker is currently available.

Candidate construction is a projection of one known graph closure. It is not
provider discovery.

* Scope relations

Contribution visibility is determined by explicit POO scope relations, which
may represent:

- same-scope visibility;
- parent-to-child export;
- child-to-parent projection;
- sibling exposure through an explicit parent;
- federation-agreement projection;
- private or non-exported scope.

The evaluator must not use nearest lexical, filesystem, graph-distance, or
ancestor match as an implicit selection rule.

Scope path and scope-relation identities remain part of resolution evidence.

* Identity matching

Canonical matching uses:

- anchor and revision identities;
- semantic subject identity;
- contract projection identity;
- scope relation identity;
- construction and provenance identities.

Friendly names are diagnostics only.

A lexical name such as =wendao-episteme= does not substitute for complete
semantic identity.

String equality does not prove contract or revision compatibility.

* Directional contract compatibility

For every candidate, resolution proves:

- the offered contract satisfies the required contract;
- the requester accepts the offered revision and schema;
- capability scope does not escalate;
- confidentiality projection is sufficient;
- lifecycle, migration, reversion, and other declared constraints hold.

The compatibility direction is contribution-to-requirement.

Matching contract names do not imply compatibility.

Rejected candidates retain exact incompatibility evidence.

* Capability declaration and live proof

The semantic graph may contain:

- capability contract;
- issuer or resource-owner requirement;
- allowed action and resource scope;
- attenuation relation.

It does not contain a current live capability token merely because a profile
was imported or composed.

Live capability issuance occurs only at the later authority-admission boundary.

Profile composition must not grant runtime authority.

* Multiplicity and aggregation

Multiplicity and aggregation are POO policy objects rather than public tokens
such as =#:one= or =#:many=.

A policy may require:

- one exact contribution identity;
- multiple contributions composed by an explicit aggregation strategy;
- an explicit default object;
- all compatible contributions as an immutable set;
- at least one closed contract proof.

The policy declares its identity, composition semantics, and failure evidence.

* Priority boundary

Numeric priority belongs to an exact slot contribution.

It is not a global rank for a profile, module, resource, capability, or
requirement candidate.

A profile with stronger priority for slot A does not become globally stronger
for slot B or another requirement.

Multiple candidates resolve only through:

- exact contribution identity;
- an admitted aggregation strategy;
- slot-local contribution priority;
- a proof of semantic equivalence and permutation invariance;
- or ambiguity failure.

Operand order must not choose a winner.

* Explicit absence

When absence is legal, the policy provides an explicit POO representation such
as:

- an identity or default contribution;
- explicit absence evidence;
- an absence contract;
- downstream absence-handling policy.

Missing contribution, incomplete evidence, and admitted absence remain
different results.

The evaluator must not use an ambiguous =#f= value for all three roles.

* Structural resolution and value evaluation

Structural resolution uses:

- anchor;
- scope;
- contract;
- contribution identity;
- resolution-policy identity.

It constructs =ProfileSemanticRequirementEdge= before value-level demand
evaluation.

Graph topology must not depend on a hidden runtime value, live health result, or
host-language conditional.

An admitted higher-order POO object may construct new requirements and
contributions purely. Its construction identity and dependency manifest enter
the semantic graph.

Live observations enter later as explicit evaluation evidence.

* Cyclic requirements

Requirements may form cycles.

Structural closure establishes identity-stable semantic edges before
value-level evaluation.

The resulting cycle becomes a POO SCC and is evaluated jointly by POO Flow.

The evaluator must not:

- choose the first currently available contribution;
- break the cycle by module import order;
- search for an external fallback;
- mutate placeholders.

Cycle evidence identifies every requirement and contribution edge.

* Resolution receipts

Every resolution emits a =RequirementResolutionReceipt= containing:

- composition-root identity;
- requester and requirement identities;
- candidate-closure identity;
- all candidate identities;
- accepted and rejected reasons;
- scope relation;
- contract compatibility evidence;
- selection or aggregation policy;
- slot-priority evidence;
- resulting semantic edge or failure identity.

Diagnostics project from this receipt.

The user-facing summary should identify concrete profiles, contracts, scopes,
and ambiguity causes rather than reporting generic multiple-provider text.

* Cache identity

Resolution caching includes:

- composition-root revision;
- requirement identity;
- explicit candidate-closure identity;
- scope-relation identity;
- contract-policy identity;
- selection or aggregation policy identity;
- contribution revision identities.

A newly composed operand or changed nested export creates a new candidate
closure and invalidates affected resolutions.

Loaded-module or registry state never enters the resolution cache key.

* Failure taxonomy

The implementation must distinguish at least:

- explicit candidate closure incomplete;
- requirement identity incomplete;
- contribution identity incomplete;
- scope relation rejected;
- private contribution leaked;
- contract incompatibility;
- capability scope escalation;
- confidentiality projection insufficient;
- no compatible contribution;
- ambiguous compatible contributions;
- aggregation policy unavailable;
- operand-order winner attempted;
- global priority attempted;
- admitted absence unresolved;
- runtime value affected topology;
- cyclic resolution edge unresolved;
- resolution receipt incomplete.

* Required invariants

1. Resolution occurs only inside one explicit operand closure.
2. Requirement, contribution, and resolution policy are POO objects.
3. Candidate construction performs no runtime discovery.
4. Visibility uses explicit scope relations, not nearest match.
5. Canonical matching uses identities rather than names.
6. Contract compatibility is directional.
7. Semantic capability declarations do not grant live capability.
8. Multiplicity and aggregation remain POO policies.
9. Numeric priority remains slot-local.
10. Operand order never resolves ambiguity.
11. Missing, incomplete, and admitted absence remain distinct.
12. Structural topology does not depend on hidden live values.
13. Cyclic requirements become semantic SCCs.
14. Every resolution emits canonical evidence.
15. Public resolution extension remains POO-native.

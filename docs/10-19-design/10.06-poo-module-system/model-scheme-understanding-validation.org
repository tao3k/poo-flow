#+title: 模型对 Scheme 的理解、推理与真实计算验证
#+date: 2026-10-03
#+status: 用户明确的验证目标；新模型实验尚未执行；MRR 后置

* 为什么此前输出了 Prompt

此前实现将实验目标选成了“给定规则和原生答案后的 JSON 复述”。
=runtime_accuracy= 曾拼接自然语言 RULES、任务数据，并给 Native 组追加
Scheme 已计算的完整结果；模型以 non-thinking 模式运行。
这样做是为了规定输出格式和规则、减少对实验协议的误解，但同时替模型
提供了语义解释及解答，改变了要验证的问题。这是实验设计错误。

因此，25% -> 91.67% 只能描述这批历史输入上的复述结果，不能证明模型
理解 Scheme、掌握逻辑语法、具备对应的推理能力或获得了实时学习收益。
non-thinking 配置尤其不能验收用户要求的 Reasoning 能力。
这批记录已退出设计验收；主动 Prompt 构造及付费调用路径已移除。
原始请求计划和响应保留为可审计的历史记录，不能改写成新实验结果。

* 必须验证什么

主线是模型对仓库中实际 Scheme 程序的理解，以及模型自身完成推理和
生成可执行 Scheme 的能力。原生 Runtime 提供真实执行和事后核验。
仅证明原生求解器正确、模型能复制答案、或 Guard 能拦住错误，均不足以
完成这个目标。独立真值用于核对计算，不能进入模型输入。

| 能力 | 实际代码接口 | 可观察的验证结果 |
| Scheme 语言理解 | ASCENT program/scheme-language.ss 的 relational-program / relational-fragment | 正确理解词法捕获、变量、作用域、新鲜名称和宏展开后的行为 |
| 逻辑与关系推理 | relation / rule / limits，以及 relational-op-join / relational-op-fix | 对未提供答案的输入正确推导 join、递归闭包、边界和资源限制 |
| 语法和语义准入 | ASCENT program/scheme-admission.ss | 生成的程序真实通过准入；失败代码和源位置可核对 |
| 证据和当前性理解 | ASCENT candidate/reasoning.ss 与 temporal/lens.ss | 区分 complete / valid；识别 generation、cut、窗口或源撤回造成的变化 |
| POO 组合能力 | POO src/scenario/composition-syntax.ss、src/graph/types-core.ss、src/graph/algorithms.ss | 正确组合实际对象、拓扑与执行路径，并产生可复核结果 |
| Python Runtime 协作 | POO semantic ABI 和 Python 图执行器 | 模型产物经过 Scheme 检查后进入真实调度、IO 和持久化；效果与计算结果一致 |

上述是现有代码中的验证入口。“Pro”暂不另行解释成新语言或引入替代 DSL；
具体任务必须绑定用户指向的现有逻辑语法与模块版本。

* 禁止预设 Prompt 和答案供给

新主线不得包含人工编写的 system/developer 语义教程、RULES 模板、
few-shot 解答、逐步推导、正确答案或原生求解器预先算出的解答。
不得把同样的内容改名为 context、tool description、Guard 文本或协议说明
后再次发送。历史的源代码问答、预设 seed repair 和答案复述实验不能直接
充当这个新协议的验收结果。

实际源代码、用户原始任务和当前执行输入必须分别记录来源及原始字节。
实验器不追加自然语言解题指令。模型接入的最小任务承载方式仍需按真实
供应商接口验证；不能把任意文本输入自动宣称为“无 Prompt”。
源代码可以是理解任务的材料，其来源和范围必须明确；评分键、原生答案
以及事后推导证据始终只交给评估器。

模型产物必须使用现有 Scheme 语言接口；不能新增 Python 所有的解释器，
也不能把第二套 JSON 语义 DSL 当成模型理解 Scheme 的证明。
ABI 内部的字节投影属于跨语言传输实现，不是新的模型语言。

* 真实计算与独立核验

1. 固定确切的 POO / ASCENT 源提交及原生产物；从现有语法和操作接口
   构造未向模型展示解答的任务，覆盖不同规模、拓扑和边界。
2. 保存模型最初的 Scheme 产物或可观察预测；先记录首次表现，再运行
   Scheme 编译、准入和求解。不得由评估器替模型填写缺失逻辑。
3. 用独立的有限真值、原生资格测试或不同算法交叉检查执行结果。
   “模型答案等于提供给它的答案”不构成独立验证。
4. 检查名称重命名、输入排列、未参与事实添加等应保持语义的变化；
   同时检查撤回、generation、窗口与可达边变化应引发的结果变化。
   模型必须对这些未预填结果的任务作出新的判断。
5. 将通过准入的产物接到真实 Python Runtime，核对执行轨迹、动作、
   文件 IO、取消和持久化。没有实际效果证据时不宣称端到端完成。

任务生成规则可以预先固定以避免挑选结果；对应正确答案由隔离评估器
计算。预先固定评价方法不等于提前向模型提供解题过程。

* Guard 的实时教学要求

Guard 必须基于当次 Scheme 产物、当前源和真实执行状态计算反馈。
可返回源位置、实际准入诊断、绑定变化、执行观察或由实际计算得出的
反例。每条反馈必须能追溯到本次计算；不得使用预设自然语言教程。

当前实验评分器已实现当次任务的原生复算、差异路径与反例生成；
准备情况和每一阶段证据见 [[file:model-scheme-validation-record.org][执行记录]]。
这尚未证明模型接收反馈后的迁移效果，也未闭合生产 Runtime 教学接口。

现有 =temporal.verify= 和 =render_temporal_answer= 只有重算、比较和拒绝，
尚未实现向模型传递实时反馈及其学习效果的验证。这部分继续开放。
运行中的结构化反馈和在线权重更新是不同的交付；当前均无已完成的
模型学习证据，不能从一次答对或一次被拒绝推断模型已经学会。

实时教学的收益要在新的、未提供解答的任务上验证。首次表现、反馈后的
表现、跨任务迁移和错误传播分别记录；不以不断重试直至通过制造成功率。
源或 generation 变化后，旧反馈不得作为当前事实直接复用。

* Reasoning、收益与闭合条件

Reasoning 配置及供应商返回的实际使用情况必须记录；不能把禁用思考的
历史实验当成 Reasoning 验证。推理能力用可执行产物、结果预测、边界
判断和新任务迁移评估，不从模型自称理解或不可观察的内部过程作结论。

| 指标 | 必须分别报告 |
| 理解与推理 | 首次语法通过率、语义准确率、结果精确率/召回率、边界判断 |
| 实时教学 | 首次成绩、收到计算反馈后的成绩、留出任务迁移、反馈时效 |
| 真实执行 | 原生计算、准入、轨迹及 IO 的一致性，错误与拒绝覆盖 |
| 成本与性能 | 模型 token/费用、思考使用情况、Native 与 IO 时间、总延迟、资源使用 |
| 验证门 | 接受正确率、覆盖率、误接受、误拒绝；拒绝不能算任务成功 |

新协议没有已执行的真实模型实验，也没有新收益数字。
已用完的 48 次预算不能用于新批次；本次文档修正没有新增模型调用。
RFC 63/120/150 的 ABI 工程证据保留，模型理解、无 Prompt 接入、实时
教学及其效果尚未闭合。达到这些目标并通过对应提交的 CI 后，才推进
MRR Rust Runtime 接入。

#+title: gerbil-poo Native Boundary and POO Flow Adapter Minimization

* Status

Accepted architecture RFC.

This document fixes the boundary between the native =gerbil-poo= operation
surface and POO Flow domain adapters. It does not authorize implementation
work.

* Scope

This RFC defines:

- which object operations remain owned by upstream =gerbil-poo=;
- which POO Flow constructs may remain public domain abstractions;
- which convenience and diagnostic adapters must remain internal;
- which generic aliases are rejected from the future public API;
- the evidence required for any new adapter;
- the relationship between adapter minimization and POO-native extension.

This RFC does not define:

- a second object API;
- a compatibility facade;
- an alist-based public interface;
- a wrapper for every upstream primitive;
- a new prototype or precedence algorithm;
- a hidden object registry;
- migration or deprecation behavior for the new architecture;
- implementation edits.

* Durable dependency identity

The native POO implementation is:

#+begin_example
github.com/mighty-gerbils/gerbil-poo@1c3225637525400341a09e958296962c10184ead
#+end_example

This is the durable upstream pin.

The local =.data/gerbil-poo= checkout is an evidence location only.

POO Flow does not own =object-ref=, =object-extend=, =object-compose=,
=object-mix=, slot mutation, delegation, super, or precedence. Those operations
belong to the pinned upstream implementation.

* Evidence state

** Upstream operation identities

Parser-owned discovery identifies the native =gerbil-poo= families:

- object representation and lifecycle;
- slot presence, projection, update, and deletion;
- prototype extension;
- composition and mix;
- super and delegation;
- precedence inspection and computation;
- diagnostic object-to-alist projection.

The exact public identifiers are recorded in
[[file:45-97-poo-module-object-construction-export-projection-and-responsibility-attachment-algebra.org][45-97]].

** Current project exports

The current POO Flow interface exports:

- =poo-flow-module-interface-prototype=;
- =poo-flow-module-object-has-slot?=;
- =poo-flow-module-object-ref/default=;
- =poo-flow-module-object->alist=.

These names are project-owned adapters. Their export status does not prove that
they belong in the future public architecture.

** Exact owner evidence

The exact owner for =poo-flow-module-object-has-slot?= shows a generic
combination of native object recognition, slot enumeration, and membership
testing. No Module-specific invariant is present.

The exact owner for =poo-flow-module-object-ref/default= shows a generic
slot-presence check followed by native projection or a caller-supplied default.
No Module-specific invariant is present.

The exact owner bytes for =poo-flow-module-interface-prototype= and
=poo-flow-module-object->alist= are missing from the current snapshot. Their
complete implementation semantics are therefore not claimed as verified.

The architecture can still classify their roles:

- the Module interface prototype is a domain-semantic candidate;
- object-to-alist conversion is diagnostic projection, never semantic truth.

* Central decision

POO Flow exposes domain meaning, not renamed generic object mechanics.

The target public boundary is:

#+begin_example
gerbil-poo native operations
  + POO Flow domain prototypes and invariant-bearing helpers
  - generic aliases
  - representation-conversion APIs
  - legacy clause and registry adapters
#+end_example

An adapter is public only when it adds an independently testable POO Flow
domain contract while preserving the native object representation.

A helper that merely renames, partially applies, or supplies a default to an
upstream object operation is not a public domain abstraction.

* Four adapter classes

** KEEP-NATIVE

An upstream =gerbil-poo= operation remains native and is used through its
upstream identity.

Examples include:

- =object-ref=;
- =object-slot-has?=;
- =object-extend=;
- =object-compose=;
- =object-mix=;
- =object-super=;
- =object-delegate=;
- =object-precedence-list=.

POO Flow documentation may explain how a native operation participates in
Module semantics. It must not clone the operation under a project-prefixed
name merely to hide the dependency.

** KEEP-DOMAIN

A POO Flow abstraction may be public when it introduces domain meaning such as:

- the semantic Module prototype;
- the Profile or ProfileBundle contract;
- a capability requirement prototype;
- a responsibility prototype;
- an invariant-bearing pure constructor;
- a validator that proves a POO Flow contract and emits actionable evidence;
- a semantic projection whose result remains a POO object.

The current =poo-flow-module-interface-prototype= is a KEEP-DOMAIN candidate
because the concept of a POO Flow Module prototype is domain-owned.

Its existing implementation is admitted only after exact owner evidence proves
that it carries the approved Module contract. The concept is retained; the
current body is not accepted by name alone.

** INTERNAL

A helper remains internal when it serves:

- bounded diagnostics;
- receipt serialization;
- legacy implementation isolation;
- temporary normalization around an upstream operation;
- test-only observation;
- source compatibility inside one implementation owner before replacement.

=poo-flow-module-object-ref/default= is INTERNAL. It is a generic convenience
helper and adds no Module invariant.

=poo-flow-module-object->alist= is INTERNAL diagnostic projection if it remains
at all. An alist may appear in a receipt encoder or bounded debugger, but it
cannot become a Module value, extension operand, or composition input.

Internal status does not grant semantic ownership.

** REJECT-PUBLIC

A project adapter is rejected from the public API when it:

- only renames an upstream operation;
- supplies convenience defaults without a domain invariant;
- exposes alists or records as the ordinary extension interface;
- hides native prototype ancestry;
- introduces a second conflict or precedence rule;
- maintains a registry beside the POO object graph;
- converts a POO object into another authoritative representation;
- exists only to support a rejected clause parser.

=poo-flow-module-object-has-slot?= is REJECT-PUBLIC because its exact owner
shows generic slot mechanics rather than Module semantics.

The current public export does not create a compatibility obligation. This is a
new architecture.

* Domain prototype boundary

A semantic prototype is not a wrapper around an upstream operation.

It is a native POO object that names and enforces a domain contract.

The Module prototype may own or require:

- stable Module identity;
- export projection;
- direct imports projection;
- capability requirements;
- responsibility roots;
- evidence projection behavior;
- admitted prototype ancestry.

The prototype remains a =gerbil-poo= object. POO Flow owns the Module meaning;
=gerbil-poo= owns the object mechanics.

#+begin_src mermaid
flowchart LR
  Upstream["gerbil-poo native operations"] -->|"construct and inspect native objects"| Prototype["POO Flow Module prototype"]
  Prototype -->|"adds domain invariants"| Module["semantic Module object"]
  Module -->|"projects stable identity"| Export["ProfileBundle export"]
  Module -->|"projects direct relation"| Imports["imports object"]
  Module -->|"projects qualified semantics"| Responsibility["responsibility roots"]
  Upstream -->|"used directly by advanced authors"| Advanced["advanced POO extension"]
  Module -->|"observed through bounded diagnostics"| Receipt["receipt projection"]
  Receipt -->|"may serialize internally"| Alist["internal alist encoder"]
  Alist -.->|"never returns as semantic owner"| Module
#+end_src

The diagnostic edge is one-way. Serialized data cannot redefine the object.

* Generic operation boundary

** Projection

Native slot and object projection remains upstream-owned.

POO Flow may define a domain projection only when the projection:

- names a semantic concept;
- validates the owning prototype or object kind;
- preserves object identity;
- emits domain-specific failure evidence;
- cannot be reproduced by simple renaming or default supply alone.

** Extension and composition

Advanced extension uses verified upstream prototype operations directly.

POO Flow may provide named functional combinators when they enforce a Module,
Profile, capability, proof, or handoff law. Such a combinator must return a
native POO object and expose the invariant it proves.

It must not become a generic substitute for =object-extend=,
=object-compose=, or =object-mix=.

** Diagnostics

Diagnostic projections have no semantic reentry path.

Diagnostic projection may convert a bounded object view to an alist, JSON-like
shape, receipt, trace, or display form.

Diagnostic values:

- are read-only projections;
- carry source object identity;
- are not accepted as composition operands;
- are not cached as semantic Module truth;
- do not participate in native precedence;
- cannot grant authority.

* Public extension surface

The advanced public interface uses upstream native operations directly.

The public advanced surface contains:

- native =gerbil-poo= objects;
- native prototype operations;
- POO Flow domain prototypes;
- POO Flow invariant-bearing pure combinators;
- POO Flow domain validators and evidence projections.

The public surface does not contain:

- project-prefixed aliases for generic object mechanics;
- raw alist access as an extension path;
- record conversion followed by rehydration;
- host-language patch operations;
- open keyword parsers;
- hidden registries;
- generic defaulting wrappers presented as Module semantics.

* Adapter admission test

Every proposed public adapter must answer all of these questions:

1. What POO Flow domain invariant does it add?
2. Why is the upstream operation insufficient as the public advanced surface?
3. Does its input remain a native POO object?
4. Does its output remain a native POO object or bounded evidence projection?
5. Does it preserve prototype ancestry and object identity?
6. Does it preserve capability attenuation?
7. Does it preserve native conflict and precedence semantics?
8. Can its domain failure produce an actionable receipt?
9. Would removing the project prefix lose semantic information?
10. Does it avoid creating a second representation?

If the adapter cannot answer the first and ninth questions with concrete domain
meaning, it is not public.

| Identifier | Current owner | Target class | Reason |
|------------+---------------+--------------+--------|
| =object-ref= and native object operations | =gerbil-poo= | KEEP-NATIVE | Upstream owns generic object mechanics. |
| =poo-flow-module-interface-prototype= | POO Flow | KEEP-DOMAIN candidate | Module semantics are domain-owned; current body still requires exact proof. |

* Ownership and representation laws

** Native ownership law

Generic POO object mechanics retain their upstream =gerbil-poo= identities.

** Domain delta law

A public POO Flow adapter adds an explicit, testable domain invariant.

** Native representation law

A domain adapter preserves the native POO object representation.

** No alias law

A generic upstream operation is not re-exported under a project-prefixed name
without additional domain meaning.

** Diagnostic one-way law

An alist, receipt, trace, or display projection cannot re-enter Module
composition as semantic truth.

** Prototype transparency law

An adapter cannot hide or replace native prototype ancestry and precedence.

** Authority neutrality law

Adapter invocation grants no capability and cannot widen authority.

** Evidence law

Public adapter admission requires exact owner evidence, semantic delta, and
focused conformance tests.

* Failure behavior

Adapter admission fails closed when:

- exact owner evidence is unavailable;
- the proposed invariant is unnamed or untestable;
- the adapter merely renames an upstream operation;
- a diagnostic projection is accepted as a semantic input;
- native object identity or ancestry is lost;
- a second precedence rule is introduced;
- capability authority is widened;
- a representation conversion becomes co-authoritative;
- the adapter exists only for a rejected clause or registry architecture.

Failure identifies:

- adapter identity;
- upstream operation identity;
- expected domain invariant;
- observed input and output kinds;
- prototype ancestry;
- representation boundary;
- missing owner or test evidence.

* Rejected alternatives

The following alternatives are rejected:

- wrapping every =gerbil-poo= operation with a =poo-flow-= prefix;
- keeping generic wrappers public because they are already exported;
- treating =object->alist= as a stable Module schema;
- rebuilding an object after editing its alist projection;
- hiding upstream composition behind a second generic merge API;
- accepting legacy stage and clause helpers as domain adapters;
- calling a convenience default a Module invariant;
- retaining compatibility aliases for the new architecture;
- removing useful domain prototypes merely to minimize line count.

* Conformance checklist

** Ownership

- [ ] The pinned =gerbil-poo= identity is recorded.
- [ ] Native operations retain upstream ownership.
- [ ] POO Flow adapters declare their semantic delta.
- [ ] Current export status is not treated as architectural approval.
- [ ] Legacy helpers remain distinct from domain prototypes.
- [ ] No second object API is introduced.

** KEEP-NATIVE

- [ ] Native projection uses upstream identities.
- [ ] Native extension uses upstream identities.
- [ ] Native composition uses upstream identities.
- [ ] Native mix uses upstream identities.
- [ ] Native delegation and super remain upstream-owned.
- [ ] Native precedence remains upstream-owned.
- [ ] POO Flow does not clone generic names.

** KEEP-DOMAIN

- [ ] A public adapter names a POO Flow invariant.
- [ ] The invariant has a focused test.
- [ ] Inputs remain native POO values.
- [ ] Outputs remain native POO values or bounded evidence.
- [ ] Object identity is preserved.
- [ ] Prototype ancestry is preserved.
- [ ] Capability attenuation is preserved.
- [ ] Domain failures emit actionable evidence.
- [ ] The Module prototype body is verified before admission.

** INTERNAL

- [ ] Defaulting convenience remains internal.
- [ ] Alist conversion remains diagnostic only.
- [ ] Diagnostic values are read-only.
- [ ] Diagnostic values retain source object identity.
- [ ] Diagnostic values cannot enter composition.
- [ ] Temporary normalization has one owner.
- [ ] Legacy clause helpers remain internal.

** REJECT-PUBLIC

- [ ] Generic aliases are absent from the target public API.
- [ ] Raw alists are absent from the extension API.
- [ ] Hidden registries are absent.
- [ ] Second precedence algorithms are absent.
- [ ] Project prefixes do not manufacture domain meaning.
- [ ] Existing exports create no compatibility obligation.

** Evidence

- [ ] Every public adapter has exact owner evidence.
- [ ] Every public adapter names its upstream dependencies.
- [ ] Every public adapter documents its semantic delta.
- [ ] Every public adapter has identity tests.
- [ ] Every public adapter has ancestry tests.
- [ ] Every public adapter has authority-neutrality tests.
- [ ] Every diagnostic adapter has a no-reentry test.
- [ ] Rejected aliases have direct upstream replacements.

* Implementation admission gates

Implementation work is not admitted until:

- [ ] exact owner bytes are available for the Module prototype;
- [ ] exact owner bytes are available for object-to-alist projection;
- [ ] reference frontiers for all four current exports are complete;
- [ ] the Module prototype's domain invariants are enumerated;
- [ ] the future public export list is reviewed;
- [ ] upstream replacements for rejected generic aliases are cited;
- [ ] diagnostic-only ownership is enforced by module boundaries;
- [ ] no diagnostic value can enter =compose profiles=;
- [ ] legacy clause helpers are proven unreachable from the new surface;
- [ ] focused adapter-class tests are specified;
- [ ] the RFC set is reviewed before implementation begins.

* Consequences

POO Flow remains visibly built on =gerbil-poo= instead of gradually obscuring
it behind a cloned adapter vocabulary.

Domain prototypes remain valuable because they add Module, Profile,
capability, proof, and handoff meaning.

Convenience and diagnostic helpers remain available internally where useful,
but they cannot become a second public object interface or semantic
representation.

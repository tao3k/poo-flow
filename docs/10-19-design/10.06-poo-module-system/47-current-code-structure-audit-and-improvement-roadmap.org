* 10.06.47 Current decision

This is the executable advancement plan for the current POO Flow, Lambda Aitia
and Lambda Episteme checkouts.  It replaces the former phase sequence that
treated Session policy syntax, runtime projection syntax and SDLC ownership as
future work.

The plan is evidence ordered:

1. establish reviewable repository baselines;
2. close domain-neutral public capabilities;
3. finish the User Interface expression layer;
4. reduce large Runtime and Session owners;
5. close contribution-owned verticals;
6. measure remaining algorithmic candidates;
7. qualify build currentness and release closure.

Completion in an uncommitted working tree is implementation evidence, not a
landed or released baseline.

* 10.06.47.10 Invariants

1. Public extension surfaces are POO-native. Objects, prototypes, slots,
   native CLOS dispatch and named functional composition are the ordinary API.
2. Pure algorithms live in the nearest reusable =funcs.ss= owner and use
   Gerbil std or SRFI implementations before project-local substitutes.
3. A generic function is introduced only for an open dispatch axis. Direct
   slot behavior, pure functions and small hygienic rules remain valid when
   they express the domain more directly.
4. Public macros only project syntax or phase semantics onto ordinary POO and
   functional code. They do not create a parallel runtime or object model.
5. =build.ss= is the unique package build entry. ASP PackageSpec owns native
   import closure projection and =std/make= owns compilation.
6. =poo-flow-load-modules= owns runtime module-source discovery. It does not
   execute inside =build.ss=.
7. POO Flow owns domain-neutral infrastructure. Lambda Aitia owns
   Software/SDLC, NASA, GitOps, ADR and causal assurance. Lambda Episteme owns
   non-SDLC vertical knowledge such as Healthcare and ontology modules.
8. Generated =source.lock.ss= files are products. The reusable implementation
   is the Sources Lock Feature.
9. Performance claims require an exact Scenario, input scale, measurement
   boundary and retained receipt.
10. Tests move from direct source compilation to atomic owner tests, real
    Scenarios and public consumers. A stale installed artifact cannot make a
    slice green.

* 10.06.47.40 P0 -- reviewable baselines

Goal: stop unrelated owners from accumulating in one unverifiable change.

Deliverables:

- classify every dirty path by POO Flow, Aitia or Episteme ownership;
- keep Standards, Sources Lock, User Interface, Observability and Governance as
  bounded parent slices;
- validate and commit each child repository before changing its parent gitlink;
- record source compile, atomic tests, Scenarios and scale receipts per slice.

Exit criteria:

- no parent commit absorbs child source changes;
- no child commit mixes the other contribution's domain;
- =git diff --check= passes in every affected repository;
- each slice has a named verification receipt.

* 10.06.47.50 P1 -- core public capability closure

** 10.06.47.51 Standards

- retain exact indexed resolution and internal catalog-identity admission;

  lazy re-entry diagnostics;

** 10.06.47.52 Sources Lock

- canonicalize entries independently from filesystem discovery order;
- produce byte-identical generated modules for equivalent declarations;
- verify digest and byte count for text and bytevector sources;
- reject duplicate identities and missing sources;
- qualify 10,000 declarations through freeze, SHA-256, one index construction
  and complete lookup;
- let contributions own the generated lock and source inventory.

Current mechanism receipt (2026-09-18):

- the Feature canonicalizes discovery order, materializes one constructor-owned
  native hash index and emits byte-identical generated source for equivalent
  declarations;
- the atomic Feature suite passes 15 checks covering text, bytevector,
  duplicate identity, digest, byte count and generated source identity;
- =just test-sources-lock-performance= constructs 10,000 reversed admitted
  entries in 187 ms and completes 20 full 10,000-lookup samples with a 5.000114
  ms p95 under the 50 ms hard gate;
- the reader-native POO authoring gate now covers =t/performance/**/*.ss=, so a
  self-referential fixture slot is rejected before benchmark realization.

Contribution-owned generated locks and Provider-specific source inventories
remain P4 deliverables; they do not belong in the core Feature.

** 10.06.47.53 Module admission

- require =types.ss=, =objects.ss=, =funs.ss=, =config.ss= and =interface.ss=;

- diagnose aggregate owner imports and package bootstrap self-imports;
- reject a parallel build projection in =build.ss=.

* 10.06.47.60 P2 -- Doom/Nix-like User Interface

The stable user tree is:

#+begin_src text
user-interface/
  init.ss
  config.ss
  profiles/
  scenarios/
  custom/<module-name>/{types,objects,funs,config,interface}.ss
#+end_src

=init.ss= enables module sources and switches. =config.ss= directly declares
=use-composition=. Profiles are reusable POO values. Scenarios combine modules
and Profiles without redefining them. Directory discovery belongs to the
internal loader.

Deliverables:

- finish Profile and Scenario discovery with stable deterministic ordering;
- make multiple Profiles reusable across multiple Scenarios;
- keep custom user modules separate from maintained and contributor modules;
- remove stale wrapper forms and redundant public =def= bindings;
- retain source locations and actionable syntax failures;
- extend Observability to report discovery, admission and plan construction.

Scale gates:

- 1,000 and 5,000 Profile expansion;
- one cached ExecutionPlan per Case;
- fresh Session state per Case instance;
- no repeated append or repeated full-index construction;
- realistic GitHub Workflow-style composition owned by Aitia.

Current root-interface receipt (2026-09-18):

- Loader projection now exposes only =init.ss= and =config.ss=; obsolete root
  =objects.ss= and =modules/config.ss= APIs were removed;
- =config.ss= directly declares =default-agent-control-plane= with reusable
  Profile selections and Development, Staging and Production stages;
- deterministic discovery imports ordinary Profile modules and only
  =scenarios/<name>/scenario.ss= plus nested Scenario Profile modules;
- the four former =cases/*.ss= examples are ordinary reusable Scenario modules,
  with no =load!= or =eval= bridge;
- =custom/my-module= passes the five-role admission contract and exposes one
  =interface.ss=;
- removing its aggregate config facade reduced a source-first public-interface
  import from approximately 11.2 seconds to 0.48 seconds on the same checkout;
- the focused Doom-style config suite passes 9 checks, and the migrated
  LangChain/LangGraph and CrewAI Scenario suites pass 63 and 12 checks.
- the existing Profile composition scale gate passes all 9 checks for 1,000
  and 5,000 Profiles and for a 1,000-module index without executing GSC.

* 10.06.47.70 P3 -- Runtime and Session owner reduction

Split behavior by dependency direction rather than file size alone.

The Loop Runtime target owners are:

- runtime receipt projections;
- runtime request construction;
- runtime envelope projection;
- command manifest;
- proof manifest;
- runtime snapshot;
- a small orchestration facade.

Session follows the same rule for validation receipts, handoff objects,
selection, materialization and communication.

Acceptance:

- value-in/value-out helpers remain pure;
- final alists exist only at ABI, report or test boundaries;
- heavy scheduling and execution stay outside Scheme;
- no compatibility forwarding layer is added;
- runtime manifest, memory/compression and Session policy Scenarios pass;
- before/after owner import closure and runtime receipts are retained.

Current closure:

- Loop Runtime is a directed owner graph: receipt projection feeds snapshot,
  request, manifest and handoff owners; =runtime-intent.ss= is the public
  aggregation owner and contains no forwarding implementation;
- =runtime.ss= is a 74-line public orchestration owner.  The former duplicate
  packet and receipt constructors were removed, so direct public calls and
  runtime-request materialization now resolve to the same implementation;
- internal runtime projection imports the exact request, manifest and handoff
  owners instead of reopening the aggregate Runtime Intent owner;
- Session policy validation separates the record/admission constructor from
  the final ABI projection while retaining the existing public receipt owner;
- source-first runtime manifest, capability, Profile, memory/compression,
  workflow, sandbox and human-audit suites pass.  The runtime manifest/Profile
  gate covers 202 checks and the capability negative Scenario reports a
  1.644 ms P95 over 20 samples;
- source-first Session policy tests cover 110 checks.  Its 240-agent-attempt +
  240-hook-attempt Scenario reports a 3.536 ms P95 over 20 samples;
- existing Session scale gates pass for 300 selector candidates (3.098 ms
  P95), 300 materialization receipts (2.632 ms), 320 communication receipts
  (1.722 ms), 240 registry entries (7.126 ms), and a 1,200-session graph;
- the repository-wide module Observability scan accepts all maintained Scheme
  sources after the owner split.

* 10.06.47.90 P5 -- measured algorithm work

Candidates are admitted only after a scale fixture shows material cost:

1. long-form CLOS effective-method membership;
2. high-arity lexical method binding;
3. repeated external plan frontier queries;
4. repeated Session selector/registry lookup;
5. repeated Loop intent and UI metadata lookup;
6. Sources Lock discovery and generated-module emission.

For every candidate:

1. state the expected complexity;
2. retain the original implementation for same-source A/B when practical;
3. measure setup separately from the hot operation;
4. prefer Gerbil std/SRFI;
5. place the algorithm in the nearest =funcs.ss=;
6. retain public POO values and canonical ordering;
7. remove the experiment if it does not improve the real Scenario.

* 10.06.47.100 P6 -- build currentness

The qualification matrix uses a clean isolated =GERBIL_PATH=:

| Run | Required evidence |
|-----+-------------------|
| cold | target count, compile count, projection time, executor time, peak memory |
| warm 1 | changed/current target count and numbered bundle count |
| warm 2 | zero compile jobs and unchanged artifacts |
| source-first atomic | current source behavior independent of installed bundles |
| installed public consumer | package artifact behavior after the canonical build |

The repair surface excludes:

- a second scheduler;
- downstream topology sorting;
- retry-until-current loops;
- timestamp touching;
- persistent path-only projection receipts;
- environment-variable product configuration;
- upstream source modification.

Observability must identify the first phase that exceeds its declared budget.

* 10.06.47.130 Slice protocol

Every implementation slice follows this order:

1. identify the source owner and public consumer;
2. define or update the real Scenario;
3. add the smallest meaningful negative contract;
4. implement the owner-bound change;
5. compile changed Scheme modules directly;
6. run the atomic owner test;
7. run the affected Scenario or public consumer;
8. run a scale gate when complexity is part of the claim;
9. inspect old names, wrong owners, positional records, repeated indexes and
   O(n²) accumulation;
10. commit only that slice.

* 10.06.47.140 Definition of done

A slice is complete only when:

- ownership is correct;
- public values are POO-native or functional;
- generated syntax lowers to ordinary code;
- negative behavior is executable;
- source and installed-artifact behavior are distinguished;
- performance evidence names its scale and boundary;
- no second build, test, runtime or registry system was introduced;
- documentation describes the final implementation rather than migration
  history.

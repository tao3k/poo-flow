#+title: Semantic Evidence and Observability Projection Owner Boundary
#+author: POO Flow
#+language: en

* Status

Accepted.

* Context

The module system needs first-class diagnostic evidence for recursive
evaluation, recovery selection, capability checks, and replay.  It also needs
small strict values that doctor, CLI, and user-facing presentation surfaces can
inspect safely while a lazy POO projection is failing.

These are different responsibilities.

The existing =src/module-system/observability.ss= owner provides strict
observation structs, presentation traces, and terminal alist projections.  Its
values are deliberately outside lazy POO evaluation and do not execute runtime
behavior.  That makes the owner suitable for safe presentation, but not for
authoritative semantic evidence.

* Decision

Authoritative semantic evidence and observability projections have separate
owners.

- =ObservationEvent= is a POO-native immutable semantic evidence value.
- =RecoveryDecision= is a pure POO-native decision derived from visible
  evidence and bounded authority.
- =src/module-system/observability.ss= remains the strict read-only projection
  owner for doctor, CLI, serialization, and presentation consumers.
- Runtime telemetry consumes redacted projections.  It does not own semantic
  evidence and cannot reconstruct authority.
- No strict observation struct or alist projection becomes an input to ordinary
  Module composition.

This separation specializes the three-plane governance established by
=45-120-03-module-debug-observability-recovery-and-telemetry-plane-governance.org=
and the structured evidence contract established by
=45-120-08-structured-diagnostic-evidence-and-exception-bridge.org=.

* Normative boundaries

** Authoritative semantic evidence

=ObservationEvent= MUST:

- be an ordinary native =gerbil-poo= object or prototype refinement;
- carry stable semantic identity;
- carry evaluation generation and causal predecessor evidence;
- distinguish observed facts from policy interpretation;
- remain immutable after publication;
- support canonical evidence projection without whole-object serialization;
- expose only capability-visible fields to a recovery policy;
- never contain a raw continuation or an executable runtime handle.

The semantic evidence owner MUST NOT:

- use presentation alists as its canonical representation;
- depend on doctor, CLI, telemetry, or rendering concerns;
- execute retry, substitution, resumption, or abort effects;
- duplicate upstream =gerbil-poo= object, type, debug, or fixed-point
  foundations.

** Pure recovery decision

=RecoveryDecision= MUST:

- be derived purely from visible =ObservationEvent= facts, profile policy, and
  bounded capabilities;
- name a permitted successor action without performing it;
- preserve the evidence identity and generation on which the decision depends;
- fail closed when evidence, authority, or budget is insufficient;
- remain serializable through a Contract-declared canonical evidence
  projection.

=RecoveryDecision= MUST NOT carry or expose the runtime continuation used by a
coordinator.

** Strict observability projection

=src/module-system/observability.ss= owns:

- strict observation structs that remain inspectable during lazy projection
  failure;
- recursive presentation-path detection;
- POO slot-authoring diagnostics;
- report-only presentation traces;
- terminal alist projections for bounded doctor, CLI, serialization, and
  user-facing rendering edges.

These values are projection data transfer objects.  They are not
=ObservationEvent=, =RecoveryDecision=, Module configuration, profile policy,
capability evidence, cache identity, or telemetry storage.

The projection owner MUST:

- remain free of runtime execution;
- avoid dereferencing or realizing the POO object under diagnosis;
- derive every projection from already-visible evidence;
- mark or omit fields that are not visible to the projection audience;
- preserve enough source identity to correlate a projection with its
  authoritative evidence without making the projection authoritative.

The projection owner MUST NOT:

- become a second semantic evidence store;
- grant recovery or visibility capabilities;
- feed alists back into ordinary =compose profiles= or =use-module= paths;
- retain raw continuations, runtime handles, or secret-bearing evidence;
- define a competing POO object, type, contract, or fixed-point system.

** Telemetry boundary

Telemetry receives an audience-safe projection after capability-scoped
redaction.  Telemetry is lossy and disposable.  It cannot serve as replay
evidence, recovery authority, canonical cache identity, or a substitute for the
authoritative evidence store.

* Ownership consequences

The current strict observability owner is reused and specialized only as a
projection consumer.  It is not replaced and is not promoted into the semantic
evidence owner.

The authoritative POO-native semantic evidence owner remains a distinct source
responsibility.  Its concrete source path MUST be resolved through parser-owned
owner discovery before implementation.  This RFC does not invent that source
path and does not authorize a parallel generic type, object, debug, or
fixed-point foundation.

* Conformance checklist

- [X] Semantic evidence and presentation projection are distinct owners.
- [X] =ObservationEvent= is POO-native, immutable, and authoritative.
- [X] =RecoveryDecision= is pure and carries no raw continuation.
- [X] Existing strict observations remain non-authoritative projection values.
- [X] Alists are confined to terminal presentation or serialization edges.
- [X] Runtime telemetry consumes redacted projections only.
- [X] Mermaid edges state the semantic transition or prohibition directly.
- [ ] The concrete semantic evidence source owner has been resolved by
  parser-owned discovery.
- [ ] Implementation has been admitted after the source owner map is complete.

* Non-goals

- Replacing =src/module-system/observability.ss=.
- Treating strict structs or alists as the public composition interface.
- Designing a second generic POO, type, contract, debug, or fixed-point library.
- Storing or replaying raw continuations.
- Moving runtime coordination into evidence or presentation objects.
- Defining an implementation schedule in this RFC.

* Lean-discovered owner gap

The recovery progress algebra already has three owner coordinates:

- runtime crash budget;
- scheduler admission;
- completion storage admission.

45-120-33 supplies owner-native transitions for the crash and storage
coordinates. The scheduling coordinate remains only a projection from
=SourceBoundDeterministicBudgetReceipt.schedulingRemaining=.

That projection cannot by itself establish:

- which recovery owns the scheduling decision;
- which scheduler owner authorized it;
- which runtime epoch and active fence are current;
- whether one deferred transition consumed exactly one authorized unit.

The missing evidence is a type-level owner boundary, not another convergence
theorem.

* Decision

Define a proof-only recovery-scoped scheduler deferral contract and receipt.

The contract binds:

- contract and recovery identities;
- exact replay step;
- scheduler owner identity through an explicit scheduler-authority predicate;
- the existing deterministic budget plan;
- runtime epoch and active fence;
- the authorized scheduling deferral limit;
- provenance.

The receipt binds one concrete, fully closed deterministic budget receipt to
that contract and projects its scheduling consumed and remaining coordinates
without reinterpreting semantic budget, crash budget, or storage admission.
It also carries an explicit =admitted=, =deferred=, or =rejected= decision and
a non-empty owner evidence digest.

* Deterministic plan binding

The deterministic budget owner and scheduler owner are not assumed to be the
same principal.  For deterministic plan =P= and scheduler contract =C_Q=,
require:

#+begin_src typst
$ C_Q."plan" = P."planId"
  and C_Q."limit" = P."schedulingLimit" $
#+end_src

The plan validity predicate and a separate scheduler-authority relation must
both hold:

#+begin_src typst
$ op("PlanValid")(P)
  and op("SchedulerAuthorizes")(o_Q, P, C_Q) $
#+end_src

The recovery expectation independently supplies exact scope:

#+begin_src typst
$ C_Q."recovery" = E."recovery"
  and C_Q."step" = E."step"
  and C_Q."epoch" = E."epoch"
  and C_Q."fence" = E."fence" $
#+end_src

Neither source substitutes for the other.

* Receipt closure

For deterministic budget receipt =B= and scheduler receipt =Q=:

#+begin_src typst
$ Q."budgetReceipt" = B."receiptId"
  and Q."consumed" = B."schedulingConsumed"
  and Q."remaining" = B."schedulingRemaining"
  and Q."consumed" + Q."remaining" = C_Q."limit" $
#+end_src

The complete existing =SourceBoundDeterministicBudgetEvidenceClosed= must hold
for =P= and =B=.  This reuses plan validity, receipt validity, fixed-point,
cycle, progress, conservation, classification, and coordinate binding.  The
scheduler closure does not define a weaker parallel budget closure.

The decision evidence is:

#+begin_src typst
$ delta_Q in { "admitted", "deferred", "rejected" } $
$ delta_Q = "deferred" => 0 < Q."remaining" $
#+end_src

The scheduler receipt therefore narrows an already-authorized scheduling
coordinate; it does not manufacture budget or scheduler authority.

* Deferred transition

A closed scheduler deferral transition requires the prior decision to be
=deferred=.  It preserves contract, recovery, owner, epoch, and fence while
advancing the owner receipt, deterministic budget receipt, and progress
receipt identities and consuming exactly one unit:

#+begin_src typst
$ delta_Q = "deferred"
  and "id"_Q' != "id"_Q
  and "id"_B' != "id"_B
  and "id"_P' != "id"_P
  and "consumed"' = "consumed" + 1
  and "remaining" = "remaining"' + 1
  => "remaining"' < "remaining" $
#+end_src

The strict scheduling decrease, together with non-increasing crash and storage
coordinates, constructs the existing
=schedulingDeferralDecreased= progress receipt owned by
=schedulerAdmission=.

* Why deterministic and recovery evidence remain insufficient

For one deterministic plan and one recovery expectation, Lean constructs two
contracts with identical plan and recovery projections but distinct scheduler
owner identities:

#+begin_src typst
$ pi_P(C_Q^a) = pi_P(C_Q^b)
  and pi_E(C_Q^a) = pi_E(C_Q^b)
  and "owner"_Q^a != "owner"_Q^b $
#+end_src

Therefore a deterministic scheduling limit plus a recovery scope still does
not select the accountable scheduler owner or prove its authority.  The
=schedulerAuthority= predicate is an independent, fail-closed premise.

* Decision classification is not cosmetic

Lean proves:

#+begin_src typst
$ delta_Q = "admitted" => not op("DeferralStep")(Q, Q') $
$ delta_Q = "rejected" => not op("DeferralStep")(Q, Q') $
$ Q' = Q => not op("DeferralStep")(Q, Q') $
#+end_src

Thus:

- an admitted decision does not consume a deferral;
- a rejected decision is terminal rather than an implicit retry;
- unchanged evidence cannot be relabeled as progress;
- only an owner-valid =deferred= receipt with strict accounting may construct
  =schedulingDeferralDecreased=.

* Enterprise security interpretation

This closes the scheduler branch of the proof-carrying detection and response
boundary:

- adaptive detection may recommend deferral;
- the scheduler owner must authorize a finite recovery-scoped contract;
- each deferred step must emit a source-bound receipt;
- unchanged or unowned deferrals cannot construct progress evidence;
- convergence continues to use the existing shared recovery rank.

No model judgement, threat score, observation, or elapsed-time threshold is
promoted into scheduling authority.

* Architecture boundary

- no runtime scheduler API is added;
- no JSON transport surface is added;
- no deterministic receipt field is overloaded;
- no recovery identity is inferred from plan identity;
- no epoch or fence is inferred from generation;
- no new convergence theorem is introduced;
- the proof model remains native Lean structures and propositions.

An implementation RFC must identify the runtime scheduler owner before this
proof contract becomes a runtime artifact.

#+title: Profile Expansion, Phase Reflection, and Identity
#+startup: overview

* Status

Normative RFC.

* Scope

This RFC owns the macro-phase contract for =defprofile= and =compose profiles=,
phase-separated reflection, safe modifier pre-expansion, and Profile identity
domains.  The public composition surface remains owned by
[[file:45-07-user-composition-and-mix-module-interface.org][the user composition
RFC]].

* Decision

=defprofile= is a hygienic binding form over ordinary =gerbil-poo=
expressions.  It creates neither a second Profile object model nor a runtime
Profile DSL.

Macro expansion is limited to syntax shape, modifier ownership, duplicate
selection, written order, identifier hygiene, ordinary POO code generation,
and immutable source provenance.  It MUST NOT create or force a POO root,
enumerate providers, resolve imports or capabilities, execute a fixed point,
decide runtime cycle or divergence, or execute policy or effects.

* Hygienic binding expansion model

The public Profile name is an identifier macro, not a runtime procedure.  A
=defprofile= declaration conceptually creates hygienically generated private
phase-0 bindings for its root and declared refinement POO values, plus one
public phase-1 identifier transformer:

#+begin_src scheme
(defprofile wendao-episteme
  base-episteme
  (+research research-extension)
  (+observability observability-extension))
#+end_src

The conceptual expansion shape is:

#+begin_src scheme
(def <private-wendao-root> base-episteme)
(def <private-wendao-research> research-extension)
(def <private-wendao-observability> observability-extension)

(defsyntax wendao-episteme
  <identifier-or-application-transformer>)
#+end_src

The angle-bracketed names above are explanatory notation, not public
identifiers or a required generated spelling.  Their exact Gerbil construction
is determined by pinned API evidence.

Bare identifier use projects the private root binding.  Application use
validates one or more Profile-local modifier selectors and emits ordered native
=gerbil-poo= composition over the stable private root and refinement bindings.
There is no runtime token dispatch.  An empty application remains an expansion
error.

The root and every declared refinement expression are bound once within the
runtime context and therefore have stable POO identities.  Evaluating a
modifier application may create a new derived Profile identity while retaining
the stable root and refinement prototypes.

Private generated bindings are neither exported nor registered globally.

* Profile-local selector literals

A modifier selector such as =+research= is an operator-local syntax literal in
the grammar of the Profile application.  It is not a runtime value, a free
Scheme identifier reference, a global syntax binding, or a registry entry.

The transformer captures its declared selector mapping in phase-1 lexical
state.  The same selector spelling may therefore have different meanings under
different Profile operators:

#+begin_src scheme
(wendao-episteme +research)
(other-profile +research)
#+end_src

Each operator resolves =+research= through its own local grammar and emits a
hygienic reference to its own private refinement binding.

Selector position is syntax rather than value position:

#+begin_src scheme
(let ((+research some-runtime-value))
  (wendao-episteme +research))
#+end_src

The selector above still denotes the =wendao-episteme= refinement; it does not
reference the local variable.  Selector position accepts only declared bare
selector literals.  It rejects variables, computed expressions, quoted
symbols, keyword lists, and runtime data.  Dynamic behavior is expressed by an
ordinary higher-order POO Profile operand.

Macro hygiene protects the generated private bindings and references from
capture.  It does not turn a Profile-local selector literal into a Scheme
variable binding.  RFC terminology MUST preserve this distinction.

* Ordered refinement clauses

A selector clause contains one or more ordinary POO refinement expressions:

#+begin_src scheme
(defprofile wendao-episteme
  base-episteme

  (+research
    research-foundation
    research-index)

  (+observability
    tracing-extension
    metrics-extension))
#+end_src

Each expression receives its own hygienically generated private phase-0
binding.  Selection emits those bindings directly into a flat native POO
composition chain.  It creates no list, alist, =begin= sequence, or intermediate
refinement AST.

Composition order has two levels:

- selectors follow their written order in the Profile application;
- refinement expressions within one selector follow their declaration order
  in =defprofile=.

For example:

#+begin_src scheme
(wendao-episteme +observability +research)
#+end_src

has the conceptual native composition order:

#+begin_src text
base-episteme
then tracing-extension
then metrics-extension
then research-foundation
then research-index
#+end_src

Provenance records both the application selector position and the clause-local
expression position.  A selector clause may not be empty, and selecting the
same selector twice remains an expansion error.

* Binding evaluation and demand laziness

Private root and refinement bindings use ordinary Gerbil phase-0 definition
semantics.  They are established when their module or runtime context is
instantiated.  =defprofile= does not add a promise, memo thunk, parameter, or
private evaluation cell.

The resulting bindings hold stable POO prototype or object values.  Binding
evaluation does not eagerly solve their slots, imports, or capabilities.
Demand-driven semantic resolution remains the responsibility of the sole
=gerbil-poo= lazy fixed point.

If the pinned =gerbil-poo= API requires a particular native prototype
constructor, the expansion uses that constructor directly rather than wrapping
it in a second laziness mechanism.  Root and refinement expressions remain
pure control-plane expressions; effects belong behind explicit runtime or
Marlin handoff boundaries.

* Cross-module export and phase contract

A defining Gerbil module exports one public Profile identifier macro.  It does
not export selector literals or the private root and refinement POO bindings.
Expansion retains the defining module's lexical context, so generated
references resolve safely to those private bindings.

A consumer performs a normal import of the Profile's Gerbil module.  The macro
implementation owns any required internal phase dependencies; the public
interface does not require users to coordinate separate phase-0 and phase-1
imports.

Re-export preserves the original transformer identity, transformer-local
selector map, and references to the defining module's private bindings.  It
does not clone the declaration into a new Profile identity.

Ordinary Gerbil rename or prefix import mechanisms resolve collisions between
public Profile operator names.  Rename or prefix changes only the operator
name; selector literals remain local to that operator's grammar.  No Profile
registry participates in import resolution.

Exact Gerbil export, rename, prefix, and phase spellings remain subject to
pinned toolchain and API evidence.  The semantic constraints above are
normative.

* Structured expansion diagnostics

Profile validation exposes stable diagnostic reason identities:

#+begin_src text
profile-empty-application
profile-unknown-selector
profile-duplicate-selector
profile-invalid-selector-form
profile-empty-refinement-clause
#+end_src

Each diagnostic carries the Profile operator syntax object, application source
location, declaration source location, offending selector syntax object, and
phase or expansion provenance.  A duplicate-selector diagnostic also carries
the first and repeated occurrence locations.  An unknown-selector diagnostic
reports only the selector literals declared by the current Profile operator.

An empty application explicitly suggests the bare Profile identifier.  An
invalid selector form explains that selector position accepts a declared bare
Profile-local literal rather than a variable, expression, quoted symbol, or
runtime value.

Diagnostics MUST NOT expose generated private binding names or a global list of
Profiles.  Diagnostic reason identities are available to conformance tests and
tooling, but this new architecture defines no compatibility or migration layer.

Expansion failure is not a runtime recovery boundary.  These phase-1 syntax
diagnostics stop compilation and are not resumed by runtime continuations.
Continuable conditions remain reserved for runtime POO demand and fixed-point
semantics.

* Phase-separated reflection

Phase-1 reflection may expose declaration shape, modifier syntax, source
location, and expansion provenance to compiler diagnostics, documentation,
completion, and safe local optimization.

Runtime prototype, slot, import, and Capability reflection belongs only to
=gerbil-poo= object or MOP facilities.  Syntax-binding identity and runtime POO
identity are never interchangeable.  The phases may correlate through
immutable provenance, but provenance carries no runtime authority.

There is no global =profile-descriptor= registry that combines the two
reflection surfaces.

#+begin_src mermaid
flowchart LR
    S["Profile syntax binding"]
    CT["phase-1 syntax reflection"]
    T["compiler and tooling"]
    E["emitted gerbil-poo expression"]
    O["runtime POO object"]
    RT["gerbil-poo object or MOP reflection"]
    P["immutable provenance"]

    S -->|"inspect source declaration"| CT
    CT -->|"diagnostic evidence only"| T
    S -->|"hygienic expansion"| E
    E -->|"runtime demand"| O
    O -->|"semantic reflection"| RT
    CT -.->|"correlate without authority"| P
    P -.->|"attach source reference"| O
#+end_src

* Safe modifier pre-expansion

Modifier applications expand directly into ordered native POO extension
expressions.  The expansion produces ordinary functional Scheme and POO code,
not an intermediate runtime interpreter.

Phase-1 code MUST NOT:

- evaluate a root or refinement POO expression;
- constant-fold a runtime POO object;
- globally memoize a constructed Profile;
- reorder refinements;
- fuse distinct refinement identities;
- share an object across call sites when runtime construction is required;
- discard a duplicate modifier under an assumed idempotence.

Every optimization preserves runtime identity, evaluation timing, prototype
composition semantics, and source provenance.

* Identity domains

A bare Profile identifier denotes a stable named POO value within its runtime
context.  A modifier application is an ordinary derived Profile expression.
Repeated derivations may share canonical content or provenance identity without
sharing runtime POO object identity.

Stable reuse is explicit:

#+begin_src scheme
(defprofile research-episteme
  (wendao-episteme +research))
#+end_src

=compose profiles= performs no implicit interning or caching.  The public
surface contains neither =cache-profile= nor =intern-profile=.

* Conformance checklist

- [ ] A public Profile name supports bare identifier and application syntax.
- [ ] Bare use projects a private stable root POO binding.
- [ ] Application use performs expansion-time selection with no runtime token
  dispatch.
- [ ] Root and refinement declarations create private stable runtime bindings.
- [ ] Generated private bindings are hygienic, unexported, and unregistered.
- [ ] Modifier names are Profile-local selector literals, not Scheme variable
  bindings.
- [ ] The same selector spelling may have independent meanings under different
  Profile operators.
- [ ] Selector position rejects runtime values, expressions, quoted symbols,
  and computed data.
- [ ] Generated references remain hygienic even when call-site bindings reuse
  a selector spelling.
- [ ] Every selector clause contains one or more POO refinement expressions.
- [ ] Every refinement expression has a distinct private stable binding.
- [ ] Selector order follows the application; clause-local expression order
  follows the declaration.
- [ ] Expansion emits one flat native POO chain without list, alist, =begin=,
  or refinement AST intermediates.
- [ ] Provenance retains both selector and clause-local positions.
- [ ] Root and refinement bindings follow ordinary Gerbil phase-0 definition
  semantics.
- [ ] Macro expansion adds no promise, =delay=/=force= layer, memo thunk,
  parameter, or private evaluation cell.
- [ ] POO slots, imports, and capabilities remain demand-lazy under
  =gerbil-poo=.
- [ ] Root and refinement expressions remain pure; effects cross an explicit
  runtime or Marlin handoff boundary.
- [ ] A module exports only the public Profile identifier macro.
- [ ] Selector literals and private root or refinement bindings are not public
  exports.
- [ ] Consumer code uses normal Gerbil module import without manual phase-pair
  management.
- [ ] Re-export preserves transformer identity and defining-module private
  references.
- [ ] Rename or prefix affects the Profile operator name but not its local
  selector grammar.
- [ ] Expansion diagnostics expose stable reason identities and syntax-object
  provenance.
- [ ] Empty application suggests the bare Profile identifier.
- [ ] Unknown selector reports only the current Profile's declared selectors.
- [ ] Duplicate selector identifies both occurrences.
- [ ] Diagnostics expose no private generated binding names or global Profile
  registry.
- [ ] Phase-1 syntax failures are non-continuable and remain separate from
  runtime POO conditions.
- [ ] Empty Profile application fails during expansion.
- [ ] Unknown and duplicate modifiers fail during expansion.
- [ ] Modifier order and source provenance survive expansion.
- [ ] No POO value is evaluated during phase 1.
- [ ] Syntax reflection and runtime MOP reflection remain separate.
- [ ] Runtime, canonical, and syntax-provenance identities remain distinct.
- [ ] Repeated derivations are not implicitly interned.

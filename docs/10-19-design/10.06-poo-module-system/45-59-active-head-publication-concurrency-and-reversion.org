This module separates immutable semantic generation identity from the mutable external selection of an active generation for one publication or deployment scope.

* Core decision

#+begin_quote
Semantic generations are immutable. An active head is a versioned external selection updated through a pure GenerationSelectionProposal, an authorized HeadUpdateIntent, and a conditional runtime commit. Concurrent publication cannot silently overwrite. Reversion is a new head transition and does not erase generation or effect history.
#+end_quote

The distinct artifacts are:

#+begin_src text
SemanticGenerationIdentity
ActiveHeadScopeIdentity
ActiveHeadObservation
GenerationSelectionProposal
HeadUpdateIntent
HeadTransitionReceipt
#+end_src

* Typst formalization: conditional active-head publication

A semantic generation is immutable.  Publication and reversion update a
versioned external selection pointer; they do not rewrite the generation being
selected.  A pure proposal and an authorized intent remain declarative values
until the runtime conditionally commits them against current authoritative
head evidence.

#+begin_src typst
#let head-observation(scope, generation, version, fence, adapter, receipt) = (
  scope: scope,
  generation: generation,
  version: version,
  fence: fence,
  adapter: adapter,
  receipt: receipt,
)

#let selection-proposal(id, kind, scope, target, policy) = (
  id: id,
  kind: kind,
  scope: scope,
  target: target,
  policy: policy,
)

$ H = (scope, generation, version, fence, adapter, receipt) $
$ P = (proposal-id, kind, scope, target-generation, policy-id) $
$ I = (P, H, authorization-id) $

$ CachedHead(generation) not=> CurrentHeadEvidence(H) $
$ Proposal(P) not=> Commit(P) $
$ AuthorizedIntent(I) not=> Commit(I) $
#+end_src

The runtime commit is a compare-and-swap style relation over the complete head
precondition.  The version and fence prevent concurrent writers from silently
overwriting one another.  A reversion chooses an earlier known generation but
preserves the generation and effect histories.

#+begin_src typst
$ ConditionalCommit(I, H_before, H_after) := $
$ quad H_before.scope = I.expected-scope $
$ and H_before.generation = I.expected-generation $
$ and H_before.version = I.expected-version $
$ and H_before.fence = I.expected-fence $
$ and H_after.generation = I.target-generation $
$ and H_after.version != H_before.version $
$ and H_after.fence > H_before.fence $

$ Commit(I) => exists c: ConditionalHeadCommit(c, I) $
$ H_before.version != I.expected-version => not Commit(I) $
$ H_before.fence != I.expected-fence => not Commit(I) $
$ H_before.scope != I.expected-scope => not Commit(I) $

$ Revert(I) and Commit(I)
  => History_generations(H_after) = History_generations(H_before) $
$ Revert(I) not=> Erase(GenerationHistory) $
$ Revert(I) not=> Erase(EffectHistory) $
#+end_src

The dashed edges are exclusions.  They prevent cached state or authorization
from becoming implicit publication authority.  Publication and reversion share
the same conditional commit boundary.

** Proof obligations

- [X] =cachedHeadDoesNotAuthorizePublication= and
  =cachedHeadDoesNotAuthorizeReversion=: remembered state is not current
  publication evidence.
- [X] =observationAloneDoesNotAuthorizeMutation=: observation establishes the
  precondition, not mutation authority.
- [X] =authorizedIntentAloneDoesNotAuthorizeMutation=: authorization cannot
  bypass the runtime conditional commit.
- [X] =conditionalCommitAuthorizesMutation=: only the conditional commit
  evidence kind authorizes the head mutation in this proof slice.
- [X] =preconditionCarriesCurrentVersionEvidence=: every publication
  precondition binds the authoritative observed head version.
- [X] =publicationRequiresConditionalRuntimeCommit=: every admitted
  publication or reversion carries its conditional commit witness.
- [X] =staleHeadVersionCannotCommit= and =staleHeadFenceCannotCommit=: a
  concurrent writer invalidates stale publication attempts.
- [X] =wrongHeadScopeCannotCommit=: a precondition from another scope cannot
  update this active head.
- [X] =reversionDoesNotEraseGenerationHistory=: reversion changes selection
  without deleting the known immutable generations.
- [X] =reversionDoesNotEraseEffectHistory=: the conditional commit carries an
  authoritative receipt whose before/after effect histories are equal.
- [ ] Refine proposals, intents, and active-head scopes through native
  =gerbil-poo= prototypes and runtime conditional-write adapters.
- [ ] Replay the synchronized Lean and Typst claims through external AXLE.

* Immutable semantic generation

A semantic generation:

- is content-addressed;
- may be referenced by multiple environments;
- remains available after leaving active status;
- does not change identity when selected again;
- contains no mutable =current=, =production=, or =latest= label.

Therefore:

#+begin_src text
SemanticGenerationIdentity is not ActiveDeploymentIdentity
#+end_src

* Active head scope

=ActiveHeadScopeIdentity= is conceptually derived from:

#+begin_src text
user-composition root anchor
+ deployment or publication target identity
+ channel or environment semantic role
+ head-adapter protocol identity
#+end_src

One generation may simultaneously be:

- active in staging;
- a production candidate;
- audit-pinned;
- referenced by another explicit head scope.

=user-composition= establishes the root binding. It does not create, register, publish, or update an active head.

* Active head observation

Before any update, the publisher obtains:

- current head generation identity;
- authoritative head version;
- fencing or version metadata;
- head scope identity;
- adapter protocol identity;
- observation receipt.

These form =ActiveHeadObservationIdentity=.

A remembered or locally cached head without current version evidence is not a valid publication precondition.

* Generation selection proposal

A pure =GenerationSelectionProposal= may depend on:

- root anchor;
- target head scope;
- current head observation;
- candidate generation identities;
- required contract proofs;
- evidence requirements;
- compatibility policy;
- promotion or reversion policy;
- unresolved effect outcomes.

The proposal does not update the head and contains no publication authority.

Selection policy must not use an undefined =latest=. A selection relation is explicit, such as:

- promotion edge;
- approved revision;
- semantic version relation;
- evidence rank;
- operator decision;
- another canonical POO policy.

Creation time alone does not prove deployment preference.

* Head update intent

After governance and runtime authorization, a proposal becomes a stable =HeadUpdateIntent= containing:

- target head scope;
- expected current generation;
- expected head version or fencing precondition;
- proposed generation;
- selection-policy identity;
- required publication-barrier identity;
- runtime-capability requirement;
- idempotency and unknown-outcome policy.

It is a commit =EffectIntent= and follows effect stabilization, authorization, idempotency, and reconciliation protocols.

* Publication barrier

An active head does not point to an unavailable or inadmissible generation.

Before head update, =PublicationBarrierIdentity= proves:

- generation content is retrievable;
- required artifacts are materialized;
- result and interface contracts are validated;
- required correctness evidence is available;
- runtime-adapter compatibility is validated;
- required observation freshness remains valid;
- no blocking effect outcome remains unknown;
- target-environment prerequisites are satisfied.

The head update depends on the barrier.

When publication spans multiple external systems, it is an effect DAG and may produce partial commit. Head switch is normally a downstream node, but the actual order is defined by explicit edges and adapter protocol.

* Concurrent publication

Suppose two publishers observe:

#+begin_src text
head version 10 -> generation G0
#+end_src

and propose:

#+begin_src text
G0 -> G1
G0 -> G2
#+end_src

Only one conditional update may succeed.

The losing publisher:

1. observes the new authoritative head;
2. produces a new selection proposal;
3. revalidates policy and compatibility;
4. creates a new update intent;
5. attempts a new conditional update.

It does not silently overwrite the winner.

#+begin_src mermaid
flowchart LR
    O["Observed head G0 at version 10"] -->|"proposal A selects G1"| A["HeadUpdateIntent A"]
    O -->|"proposal B selects G2"| B["HeadUpdateIntent B"]
    A -->|"CAS version 10 succeeds"| H["Head G1 at version 11"]
    B -->|"CAS version 10 fails"| C["ConcurrentHeadUpdate evidence"]
    C -->|"reobserve version 11 and reevaluate policy"| N["New selection proposal"]
    N -->|"must not silently overwrite G1"| V["New conditional transition"]
#+end_src

* Reversion transition

Selecting an older generation is a new reversion transition:

#+begin_src text
head G2
-> authorized reversion transition
-> head G1
#+end_src

Reversion:

- creates a new head version;
- retains the history from G1 to G2;
- records why G1 is selected again;
- revalidates the current publication barrier;
- does not automatically undo effects executed under G2;
- uses separate compensation or reconciliation for external effects.

An older generation may no longer satisfy current external state, schema, adapter, freshness, or capability policy. Historical success does not prove current admissibility.

* Head transition history

Generations form an immutable content-addressed graph. Head selections form an append-only transition-evidence graph:

#+begin_src text
HeadTransitionIdentity =
H(
  head scope identity,
  previous head observation,
  selection decision identity,
  selected generation identity,
  authoritative update receipt
)
#+end_src

The mutable object is the external head pointer. Immutable records include:

- semantic generations;
- selection proposals;
- update intents;
- transition receipts;
- reversion receipts;
- publication failures.

* Unknown head outcome

If a head-update request may have committed but its response is lost, the result is =HeadUpdateUnknownOutcome=.

The publisher:

1. observes the authoritative head or queries an idempotency identity;
2. determines updated, not updated, or still unknown;
3. seals a reconciliation receipt;
4. retries only after authoritative non-update evidence;
5. fails closed when the outcome remains unknown.

Blind retry is prohibited.

* Compare-and-swap, lease, and fencing

The preferred update uses a version or compare-and-swap precondition.

When a lease is used:

- the lease is a live operational resource;
- lease expiry cannot be reversed by a receipt;
- a stale publisher is rejected by adapter-enforced fencing;
- live lease identity does not enter semantic generation identity.

Without compare-and-swap, a covering transaction, or adapter-enforced fencing, the system does not claim lost-update protection.

* Subscriber head observation

A consumer reads:

#+begin_src text
ActiveHeadObservation
-> referenced SemanticGenerationIdentity
#+end_src

It does not read an unversioned mutable name.

When the consumer requires consistency between head and generation artifact:

- the adapter provides an atomic head read or versioned receipt;
- artifact retrieval validates the generation identity;
- a later head transition does not mutate the already read generation;
- follow-new-head behavior is an explicit subscriber policy.

* Cache boundaries

- Semantic-generation cache :: Immutable and content-addressed.
- Active-head observation cache :: Versioned and freshness-bounded.
- Publication-barrier cache :: Bound to candidate generation, target scope, and policy.
- Head-transition receipt :: Immutable evidence.
- Live head handle, lease, and transaction :: Non-cacheable.

A cached =current= observation always requires version and freshness validation.

* Failure taxonomy

The normative failures include:

#+begin_src text
GenerationNotAdmissible
RequiredPublicationEvidenceUnavailable
PublicationBarrierIncomplete
HeadPreconditionFailed
ConcurrentHeadUpdate
HeadUpdateUnknownOutcome
StaleHeadFencingToken
ReversionPolicyRejected
ActiveHeadObservationExpired
#+end_src

They belong to selection, publication, or runtime commit boundaries. They are not semantic slot conflicts.

* Evidence requirements

Head-selection evidence records:

- head-scope identity;
- authoritative previous-head observation;
- candidate and selected generation identities;
- selection-policy and proposal identities;
- publication-barrier identity;
- governance and runtime authorization;
- conditional-update precondition;
- authoritative update or reconciliation receipt;
- concurrent-update conflict;
- reversion reason and current admissibility;
- resulting head version.

Live token, lease, transaction handle, and secret adapter material are never serialized.

* Implementation checklist

- [ ] Define pure ActiveHeadScope and versioned observation objects.
- [ ] Keep current, production, and latest labels outside semantic generation identity.
- [ ] Define pure POO GenerationSelectionProposal.
- [ ] Require explicit selection relation instead of undefined latest ordering.
- [ ] Seal authorized proposals as HeadUpdateIntent values.
- [ ] Define PublicationBarrierIdentity and required proofs.
- [ ] Prevent head switch before artifacts and evidence are ready.
- [ ] Use conditional update, transaction, or fenced lease.
- [ ] Reject silent overwrite after concurrent publication.
- [ ] Reobserve and reselect after head precondition failure.
- [ ] Define reversion as a new transition with a new head version.
- [ ] Keep external-effect compensation separate from head reversion.
- [ ] Define unknown-outcome reconciliation.
- [ ] Preserve append-only head-transition evidence.
- [ ] Version and freshness-bound active-head caches.
- [ ] Validate final head adapter operations against real runtime and =gerbil-poo= primitives.

* Non-goals

- Do not make an active label part of immutable generation identity.
- Do not let =user-composition= auto-publish or create a head registry.
- Do not select latest by wall-clock creation time alone.
- Do not switch a head before publication prerequisites are ready.
- Do not silently overwrite a concurrent publisher.
- Do not describe reversion as erasing history or undoing external effects.
- Do not retry an unknown head update blindly.
- Do not create a global active-generation registry or deployment DSL.

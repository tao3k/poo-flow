#+title: Aggregate Profile Responsibility Projection and Bounded Macro Boundary

* Status

Accepted architecture RFC.

This document records the approved semantic boundary. It does not authorize
implementation work. Exact Gerbil forms remain subject to verification against
the pinned =gerbil-poo= implementation before code is written.

* Scope

This RFC defines:

- the value selected by =(use-module module-name production)=;
- the relationship between =Module=, =ProfileBundle=, and an exported
  =production= identity;
- the POO ownership of graph, loop, proof, handoff, stage responsibility, and
  recursive imports;
- the boundary between canonical POO semantics and bounded hygienic macros;
- the projection and evidence laws required before a compressed user interface
  is admitted.

This RFC does not define:

- a new fixed-point evaluator;
- a replacement for =gerbil-poo=;
- a second provider registry;
- a raw alist, record, patch, or clause DSL;
- runtime authority issuance;
- Gerbil package management;
- build-system integration;
- compatibility, migration, or deprecation behavior.

* Central decision

A =Module= exports stable names whose values are =ProfileBundle= POO objects.
The exported name =production= denotes one such aggregate value.

=production= is not a stage token and is not a request for an imperative phase
transition. It is a stable module-scoped identity for a higher-order Profile
operand accepted by =compose= with the =profiles= strategy.

The selected =ProfileBundle= owns a reachable responsibility closure. That
closure preserves:

- every selected low-level =Profile= identity and value;
- recursive =imports=;
- graph responsibility;
- loop and progress responsibility;
- proof obligations and their evidence projections;
- handoff requirements and handoff evidence;
- capability requirements and their attenuation;
- any stage responsibility previously carried by a case declaration.

The graph, loop, proof, handoff, and stage responsibilities are POO objects or
POO facts reachable from the selected aggregate. They are not sibling clauses
interpreted by =use-composition=.

* Public composition surface

The ordinary user surface remains flat:

#+begin_src scheme
(use-composition crewai-system
  (compose profiles
    (use-module crewai production)))
#+end_src

The responsibilities hidden by this concise selection remain observable
through the selected value and its admitted evidence receipt. Concision must
not erase semantics.

The corresponding conceptual projection is:

#+begin_example
select(crewai, production)
  -> ProfileBundle
  -> low-level Profiles
  -> responsibility objects
  -> recursive imports closure
  -> capability and evidence projection
#+end_example

No =stage=, =graph=, =loop=, =prove=, or =handoff= clause is accepted inside
=use-composition=. No second composition wrapper is introduced.

* Aggregate Profile type

** Module export

A =Module= provides a stable mapping:

#+begin_example
export identity -> ProfileBundle value
#+end_example

The mapping is part of the module's POO identity. It is not a global registry
entry and is not discovered through runtime token dispatch.

** ProfileBundle

A =ProfileBundle= is a higher-order Profile operand. It may contain or project
multiple low-level Profiles, but it participates in =compose profiles= as one
ordinary value.

The bundle must preserve member identity. Flattening for evaluation or runtime
projection must not make two distinct low-level Profiles observationally
indistinguishable.

** Production identity

=production= is an exported identity, not a universal built-in keyword.
Different Modules may export distinct =production= bundles.

An unqualified =production= value cannot escape its Module identity. Selection
therefore retains both:

#+begin_example
module identity + export identity
#+end_example

An explicit module instance alias additionally participates in identity as
defined by [[file:45-93-module-profile-selection-bundle-and-imports-closure-algebra.org][45-93]].

* Responsibility object model

** Stage responsibility

The former notion of a production stage is represented by responsibility
facts owned by the aggregate Profile. It may describe admission expectations,
environment constraints, or evidence requirements.

Stage responsibility does not execute a phase transition and does not grant
authority. The name =production= and the responsibility facts are related but
not identical:

- =production= is the export identity;
- stage responsibility is reachable semantic data;
- runtime admission decides whether the responsibility is satisfied.

** Graph responsibility

Graph responsibility points to a =FlowGraph= POO object or an equivalent
POO-native graph value.

The graph object owns stable node and edge identities, entry and exit
responsibilities, and graph-local capability requirements. Heavy execution is
projected to the runtime boundary; the graph value remains Scheme-owned
semantic truth.

** Loop responsibility

Loop responsibility is a POO value associated with graph progress. It owns
bounded progress requirements such as fuel, retry authority, termination
evidence, and fixed-point observability expectations.

It does not introduce a local fixed-point engine. Evaluation and observation
reuse =gerbil-poo= and POO Flow mechanisms.

Host =if=, =cond=, or =case= forms are not the ordinary extension interface for
loop policy. Higher-order POO values and prototype extension remain the
advanced interface.

** Proof responsibility

Proof obligations are POO objects with stable identities. An obligation may
project a result or receipt, but a declaration is not itself proof evidence.

Proof composition preserves the distinction between:

- obligation identity;
- verifier identity;
- admitted evidence;
- unresolved or rejected evidence;
- runtime projection.

Macros may generate repeated obligation objects, but they may not mark an
obligation proved or manufacture authority.

** Handoff responsibility

A handoff responsibility points to a =HandoffContract= POO object or an
equivalent POO-native value. It declares the destination boundary, required
capabilities, required evidence, and receipt shape.

The object does not issue a capability and does not perform the handoff.
Runtime handoff remains conditional on admitted authority and evidence.

** Imports responsibility

Recursive =imports= remain POO-owned object structure. The active closure is
selection-sensitive: only dependencies reachable from selected Profiles and
their responsibility objects enter the active closure.

Gerbil =import= or =load= operations are backend projections of this semantic
closure, not its owner.

* Macro governance boundary

** Canonical semantic layer

The canonical semantic layer consists of:

- =gerbil-poo= objects and prototype operations;
- =Module= and =ProfileBundle= values;
- low-level Profiles;
- responsibility objects;
- pure functional composition;
- =compose= as a pure function;
- =profiles= as a first-class composition strategy.

Advanced extension uses this layer directly. A macro expansion is never the
only representation of a semantic fact.

** Admitted bounded macros

A bounded macro may:

- introduce a hygienic lexical or module-level binding;
- select a stable Module export;
- generate a repeated family of ordinary POO objects;
- attach source identity for precise diagnostics;
- validate closed declaration shape at expansion time;
- expand to ordinary POO-native and functional code.

The ordinary interface may therefore retain:

- =use-composition= as a thin binding macro;
- =use-module= as a thin Module-selection macro;
- narrowly owned declaration macros for repeated internal object families.

The exact declaration macro names and call forms are not fixed by this RFC.
They must be derived from verified =gerbil-poo= primitives rather than
invented here.

** Rejected macro authority

A macro may not:

- own graph evaluation;
- decide loop progress or recovery;
- discharge proof obligations;
- issue or widen capabilities;
- authorize a handoff;
- maintain a hidden registry;
- interpret an open keyword language;
- turn host conditionals into the ordinary Profile extension mechanism;
- conceal a second semantic representation beside POO objects.

The names =stage=, =graph=, =loop=, =prove=, and =handoff= therefore do not
become a parallel public clause language.

* Expansion transparency

Any admitted declaration macro must have a transparent correspondence:

#+begin_example
bounded surface form
  -> hygienic expansion
  -> ordinary POO objects and pure functions
  -> the same projection and evidence laws
#+end_example

The expanded result must be explainable without executing runtime effects.
Diagnostics must retain both the surface source identity and the resulting POO
object identity.

Macro expansion cannot change authority. If two surface forms expand to
equivalent POO values, their admission behavior must be equivalent.

* Projection laws

** Export stability

For a fixed Module identity, an export identity denotes one declared
=ProfileBundle= value in the current module version.

** Member identity preservation

Selecting an aggregate preserves the stable identities of all reachable
low-level Profiles.

** Responsibility completeness

For every responsibility reachable from a selected low-level Profile, the
aggregate projection includes that responsibility or rejects the aggregate as
incomplete.

** Reachability conservation

Compression of the user surface does not remove reachable imports, capability
requirements, proof obligations, graph edges, loop constraints, or handoff
requirements.

** Selection sensitivity

Responsibilities and imports unreachable from the selected export do not enter
the active closure merely because the Module declares them elsewhere.

** Capability attenuation

Composition may preserve or narrow capability requirements and grants. It may
not widen authority.

** Declaration non-authority

Declaring a proof, handoff, stage, graph, or loop responsibility never satisfies
that responsibility and never grants its required capability.

** Macro semantic transparency

Replacing an admitted bounded macro with its POO-native expansion preserves
selection, composition, closure, evidence, and admission results.

** Runtime non-ownership

Runtime projections may execute graph or handoff effects, but they do not
redefine the Module, ProfileBundle, responsibility, or imports semantics.

* Evidence projection

An admitted selection receipt must identify at least:

- Module identity;
- optional Module instance identity;
- selected export identity;
- aggregate =ProfileBundle= identity;
- reachable low-level Profile identities;
- responsibility object identities;
- active imports closure identity;
- capability requirements after attenuation;
- proof obligation status;
- graph and loop responsibility status;
- handoff eligibility and destination identity;
- source identities for any macro-generated objects;
- rejection reason when completeness or admission fails.

The receipt is a projection of semantic facts. It is not a substitute for those
facts and cannot create authority.

* Failure behavior

Selection fails closed when:

- the Module identity is unresolved;
- the export identity is absent;
- the export does not denote a Profile operand;
- member identity is lost;
- a reachable responsibility is omitted;
- the recursive imports closure is incomplete;
- capability attenuation cannot be established;
- a macro expansion introduces hidden semantic state;
- required proof or handoff evidence is absent.

Failure must identify the owning Module, selected export, responsibility object,
and missing evidence or dependency. A short user form must not produce an
opaque error.

* Rejected alternatives

The following alternatives are rejected:

- treating =production= as a universal stage keyword;
- keeping =stage=, =graph=, =loop=, =prove=, and =handoff= as peer clauses in
  =use-composition=;
- making =use-composition= interpret case semantics;
- making =compose= a macro-owned language;
- flattening a ProfileBundle until low-level identity disappears;
- storing responsibilities only in generated runtime data;
- giving declaration macros proof or capability authority;
- duplicating graph, loop, proof, or handoff semantics outside POO objects;
- implementing a local fixed-point subsystem for this interface.

* Conformance checklist

** Type and identity

- [ ] A Module export maps a stable identity to a POO value.
- [ ] =production= denotes a module-scoped =ProfileBundle=.
- [ ] The bundle is accepted as a normal Profile operand.
- [ ] Module and export identities remain distinct.
- [ ] Explicit instance identity remains distinct.
- [ ] Every low-level Profile retains stable identity.

** Responsibility closure

- [ ] Stage responsibility is reachable data, not an executing phase token.
- [ ] Graph responsibility is a POO object.
- [ ] Loop responsibility is a POO object.
- [ ] Proof obligations are POO objects.
- [ ] Handoff responsibility is a POO object.
- [ ] Recursive imports remain POO-owned.
- [ ] Every reachable responsibility appears in the aggregate projection.
- [ ] Unreachable responsibilities remain outside the active closure.

** Macro governance

- [ ] =use-composition= performs only thin hygienic binding.
- [ ] =use-module= performs only hygienic Module selection.
- [ ] =compose= remains a pure function.
- [ ] =profiles= remains a first-class strategy.
- [ ] Declaration macros expand to ordinary POO-native or functional code.
- [ ] Macro expansion retains source identity.
- [ ] Macros do not own runtime effects.
- [ ] Macros do not issue capabilities.
- [ ] Macros do not discharge proof obligations.
- [ ] Macros do not maintain hidden registries.
- [ ] No open clause DSL is introduced.

** Projection and evidence

- [ ] Selection receipts identify Module and export identities.
- [ ] Receipts identify aggregate and low-level Profile identities.
- [ ] Receipts identify responsibility objects.
- [ ] Receipts identify the active imports closure.
- [ ] Receipts expose capability attenuation.
- [ ] Receipts expose unresolved proof obligations.
- [ ] Receipts expose graph and loop status.
- [ ] Receipts expose handoff eligibility.
- [ ] Incomplete projections fail closed.
- [ ] Rejections name the owning object and missing evidence.

** Case preservation

- [ ] CrewAI preserves all declared Profiles and responsibilities.
- [ ] LangChain preserves all declared Profiles and responsibilities.
- [ ] LangGraph preserves all declared Profiles and responsibilities.
- [ ] Tool-calling preserves all declared Profiles and responsibilities.
- [ ] LangGraph does not gain an implicit observability Profile.
- [ ] Each ordinary case uses one aggregate Module selection.
- [ ] Cross-case composition preserves instance and responsibility identity.

* Implementation admission gates

Implementation work is not admitted until:

- [ ] the exact pinned =gerbil-poo= object and prototype primitives are cited;
- [ ] the target =ProfileBundle= representation is mapped to those primitives;
- [ ] the current =compose= and =use-composition= owners are verified;
- [ ] macro expansion examples are shown as ordinary POO-native code;
- [ ] responsibility completeness tests are specified;
- [ ] selection-sensitive imports tests are specified;
- [ ] capability attenuation tests are specified;
- [ ] evidence receipt tests are specified;
- [ ] all four current user-interface cases have lossless expected projections;
- [ ] the RFC set is reviewed before implementation begins.

* Consequences

The ordinary interface becomes smaller because a user selects one meaningful
aggregate Profile instead of restating its internals.

The semantic model becomes stronger because every hidden detail remains a
reachable POO object with stable identity, explicit responsibility, and
evidence projection.

Macro use remains disciplined: macros improve binding, repetition, and
diagnostics, while POO objects and pure functions remain the only semantic
truth.

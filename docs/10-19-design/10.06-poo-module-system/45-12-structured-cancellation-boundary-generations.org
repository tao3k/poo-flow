#+title: Structured Cancellation And Boundary Generations

* Normative responsibility

This module owns POO Flow structured cancellation across recursive structural
boundaries, coalesced demands, effect attempts, runtime resource leases, and
first-class continuation re-entry.

It defines:

- a POO-native cancellation scope per realization boundary;
- containment-based cancellation propagation;
- demand-authority withdrawal from coalesced operations;
- ordinary and restricted cleanup continuation generations;
- proof requirements for clean cancellation;
- indeterminate cancellation barriers and reconciliation.

Cancellation is not a global mutable flag and is not synonymous with throwing
an exception.

* Ownership boundary: gerbil-poo mechanism and POO Flow governance

=gerbil-poo= owns generic POO identity, demand realization, memoization,
lineage, suspension, fixed-point mechanics, and continuation-aware control.

POO Flow owns:

- cancellation-scope identity and containment;
- cancellation policy and propagation authority;
- demand-authority withdrawal;
- continuation-generation validation;
- cancellation, cleanup, and reconciliation receipts;
- the proof required to declare a boundary cleanly cancelled.

[[file:45-03-runtime-context-and-recovery.org][Runtime Context And Recovery]] owns recovery decisions and receipt validation.
[[file:45-05-lineage-and-cycle-detection.org][Lineage And Cycle Detection]] owns containment/import paths and wait-graph evidence.
[[file:45-08-effect-boundary-commit-reconciliation.org][Effect Boundary Commit And Reconciliation]] owns provider cancellation evidence.
[[file:45-09-effect-intent-suspension-handoff-reinjection.org][Effect Intent, Suspension, Runtime Handoff, And Receipt Reinjection]] owns
coalesced demand and effect handoff.  [[file:45-11-resource-lease-continuation-dynamic-wind.org][Resource Lease, Continuation, And Dynamic-Wind]]
owns physical resource release and dynamic access detachment.

* POO-native cancellation scope

Every realized structural boundary has a POO cancellation-scope object whose
semantic evidence includes:

- realization-context identity;
- structural-boundary lineage;
- parent containment scope;
- current boundary generation;
- contained child scopes;
- joined demand authorities;
- governed effect and lease receipts;
- cancellation and reconciliation policy.

The scope is not a public configuration record, global token registry, or
boolean flag.  Exact constructors and slots remain evidence-gated until the
real =gerbil-poo= API is behavior-proven.

* Cancellation-scope state machine

#+begin_src mermaid
stateDiagram-v2
  [*] --> Active: boundary generation established
  Active --> CancelRequested: authorized cancellation request
  CancelRequested --> Quiescing: reject new ordinary effects and propagate to contained children
  Quiescing --> CancelledClean: child, effect, and lease terminal receipts verified
  Quiescing --> Indeterminate: an external or child outcome cannot be proved
  Indeterminate --> Reconciling: restricted reconciliation authority
  Reconciling --> Quiescing: new terminal evidence obtained
  Reconciling --> Indeterminate: proof remains unavailable
#+end_src

Once a scope leaves =active=, it never returns to =active=.  Reconciliation may
produce new terminal evidence, but it does not revive the cancelled ordinary
generation.

=cancelled-clean= is a proved terminal state.  It requires:

- all contained child scopes to be terminal;
- all governed effect attempts to have terminal evidence;
- every owned resource lease to be released or explicitly transferred by
  verified policy;
- all ordinary dynamic access authority to be detached;
- an immutable cancellation receipt chain.

If any required outcome remains unknown, the scope is =indeterminate= rather
than =cancelled-clean=.

* Containment propagation

Cancellation ownership follows structural containment:

#+begin_src mermaid
flowchart TD
  P["State: parent cancellation scope"] -->|"containment authority propagates request"| C1["State: contained child scope"]
  P -->|"containment authority propagates request"| C2["State: contained child scope"]
  C1 -.->|"child evidence may escalate; request does not automatically propagate upward"| P
  C1 -.->|"siblings remain isolated unless parent policy acts"| C2
  I["State: imported Mix dependency"] -.->|"dependency edge is not cancellation ownership"| P
#+end_src

A parent cancellation request propagates to every contained child scope.  Child
completion or indeterminacy returns evidence to the parent.

A child request does not automatically cancel its parent or siblings.  It may
emit an escalation condition that parent policy can inspect.

Mix =imports= do not transfer containment or cancellation ownership.  Shared
cancellation across an import requires an explicit POO capability and authority
receipt; it is never inferred from the dependency edge.

* Boundary generations and continuation authority

An active boundary has an ordinary continuation generation.  An authorized
cancellation request invalidates that generation for new ordinary work and
creates a restricted cleanup generation.

The cleanup generation may authorize only:

- child cancellation propagation;
- provider cancellation requests;
- resource access detachment and release;
- bounded evidence inspection;
- reconciliation;
- terminal receipt construction.

It cannot initiate unrelated ordinary effects or resume the cancelled
application path.

#+begin_src mermaid
flowchart LR
  O["State: ordinary continuation generation"] -->|"authorized cancellation invalidates ordinary authority"| C["State: cancellation boundary"]
  C -->|"mint restricted authority"| K["State: cleanup continuation generation"]
  O -->|"captured continuation attempts late re-entry"| S["State: stale or cancelled-boundary condition"]
  K -->|"release, cancel, reconcile, or inspect only"| Q["State: quiescing work"]
  Q -->|"terminal evidence complete"| T["State: cancelled-clean receipt"]
  Q -->|"terminal evidence incomplete"| I["State: indeterminate barrier"]
  T -->|"invalidates cleanup generation"| X["State: no remaining continuation authority"]
#+end_src

A captured ordinary continuation validates both realization-context identity
and boundary generation on every re-entry.  Re-entry under an invalidated
generation raises a continuable stale/cancelled-boundary condition.  It MUST NOT
resurrect the boundary, effect, or resource lease.

* Coalesced demand authority

A coalesced provider attempt may serve multiple joined demands.  Each joined
demand contributes its own boundary-scoped authority.

#+begin_src mermaid
flowchart TD
  D1["State: demand authority A"] -->|"joins operation"| O["State: coalesced provider attempt"]
  D2["State: demand authority B"] -->|"joins operation"| O
  D1 -->|"scope A cancels; withdraw only A"| W["State: remaining authority set"]
  O -->|"preserve attempt evidence"| W
  D2 -->|"B remains authorized"| W
  W -->|"one or more authorized waiters remain"| O
  W -->|"no authorized waiter remains and policy permits"| K["State: provider cancellation requested"]
  K -->|"request is not terminal proof"| R["State: await cancellation, commit, failure, or indeterminate receipt"]
#+end_src

Cancelling one joined demand MUST NOT cancel the physical attempt while another
authorized waiter remains.

The authority set is realization-context evidence, not a mutable global
reference count.  Withdrawal and provider-cancellation decisions emit ordered
receipts.

If the provider commits after one or all demand authorities were withdrawn, the
commit receipt remains authoritative evidence.  It does not resume an
invalidated ordinary continuation.  Policy governs cleanup, artifact retention,
or later evidence admission.

* Cancellation request is not cancellation proof

The following are requests or observations, not proof of cancellation:

- a deadline firing;
- budget exhaustion;
- a cancellation exception;
- provider interruption;
- worker or process loss;
- socket closure;
- submitting a provider cancellation request;
- leaving a =dynamic-wind= extent.

Provider cancellation proof belongs to 45-08.  Resource release proof belongs
to 45-11.  A boundary reaches =cancelled-clean= only after consuming both forms
of terminal evidence together with child-scope receipts.

* Deadlines and budgets

Deadline expiry and budget exhaustion produce an authorized cancellation
request with causal evidence.  They do not skip =cancel-requested= or
=quiescing=.

Budget policy distinguishes ordinary work from restricted cleanup work.
Exhausting an ordinary-work budget MUST NOT remove the bounded authority needed
to cancel providers, release resources, reconcile indeterminate outcomes, and
emit terminal receipts.

Cleanup authority remains bounded by explicit time, resource, and escalation
policy.  Exhaustion of cleanup authority with unresolved outcomes produces an
=indeterminate= boundary receipt.

Admission classes, hierarchical budgets, backpressure, and reserved cleanup
capacity are specified by
[[file:45-13-demand-admission-backpressure-cleanup-capacity.org][Demand Admission, Backpressure, And Cleanup Capacity]].  This module owns the
cleanup-generation authority that consumes that capacity.

* Recovery conditions

** Stale or cancelled ordinary continuation

Policy-visible recovery may:

- inspect generation and cancellation evidence;
- use a qualified portable value or artifact that does not revive the boundary;
- defer;
- abort the enclosing declared boundary.

There is no restart that revalidates the old ordinary generation.

** Indeterminate cancellation

Policy-visible recovery may:

- inspect bounded child, effect, and lease evidence;
- reconcile through qualified provider capabilities;
- defer while preserving the barrier;
- escalate to the containing boundary;
- terminate with an explicit indeterminate receipt.

There is no unconditional retry, force-cancelled, or assume-released restart.

* Wait-graph and fixed-point projection

Cancellation adds typed authority and wait edges to the existing graph:

#+begin_src mermaid
flowchart LR
  P["State: parent quiescing node"] -->|"waits for contained child terminal evidence"| C["State: child cancellation node"]
  P -->|"waits for provider terminal evidence"| E["State: effect cancellation node"]
  P -->|"waits for release proof"| L["State: resource lease node"]
  C -->|"child receipt"| P
  E -->|"effect receipt"| P
  L -->|"lease receipt"| P
  I["State: imported dependency"] -.->|"not a containment cancellation edge"| P
  P -->|"closed waits with no progress authority"| X["State: structured cancellation deadlock or indeterminacy evidence"]
#+end_src

Graph traversal does not issue cancellation, resume cleanup continuations, or
force terminal states.  =gerbil-poo= owns generic demand and cycle mechanics;
POO Flow owns the interpretation of cancellation authority and receipts.

* Observability and receipt contract

The ordered cancellation receipt chain records:

- scope, context, boundary, and generation identities;
- parent/child containment paths;
- ordinary-generation invalidation;
- cleanup-generation authority;
- joined-demand authority withdrawal;
- provider cancellation requests and terminal evidence;
- resource release evidence;
- reconciliation and escalation decisions;
- clean or indeterminate terminal outcome.

Observability distinguishes:

- cancellation requested;
- quiescing in progress;
- provider cancellation proved;
- resource release proved;
- child scope terminal;
- boundary cancelled cleanly;
- boundary indeterminate.

No sink may propagate cancellation, withdraw demand authority, resume a
continuation, release a resource, or mark a scope terminal.

Replay verifies historical cancellation generations and receipts according to
[[file:45-14-deterministic-realization-replay.org][Deterministic Realization Replay]].  It cannot revalidate an invalidated ordinary
generation or recreate cleanup authority.

Cancellation receipts use the identity, projection, predecessor, correction,
and contradiction semantics defined by
[[file:45-15-receipt-object-canonical-evidence-projection.org][Receipt Object And Canonical Evidence Projection]].

* API evidence gate

The semantics in this module are normative.  Exact cancellation-scope,
generation, condition, restart, and receipt identifiers remain
=semantic-required= until the relevant =gerbil-poo= and Gerbil behavior is
symbol-located, behavior-proven, and flow-qualified.

Any generally reusable POO cancellation or continuation-generation mechanism
belongs upstream in =gerbil-poo=.  POO Flow MUST NOT introduce a shadow
scheduler, cancellation runtime, or fixed-point evaluator.

* Explicit exclusions

This RFC does not authorize:

- a global cancellation flag or registry;
- cancellation propagation through Mix imports by default;
- sibling or parent cancellation without explicit authority;
- cancelling a coalesced provider attempt while authorized waiters remain;
- treating deadline, exception, worker loss, or cancellation request as proof;
- ordinary effect execution under cleanup authority;
- continuation re-entry under an invalidated generation;
- automatic retry or forced success from an indeterminate state;
- claiming =cancelled-clean= without child, effect, and lease terminal receipts;
- a new public cancellation DSL before the real API is behavior-proven.

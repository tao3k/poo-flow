#+title: Recovery and Observability Profile Projection with a Minimal Use-Composition Surface
#+startup: overview

* Scope

This RFC defines:

- the minimal ordinary user surface;
- projection of POO-native profiles into recovery and observability policies;
- the boundary between profile selection and capability admission;
- ordinary, advanced, and framework extension layers;
- macro-governance constraints;
- conflict, explanation, and validation behavior.

This RFC does not define:

- new recovery clauses;
- new observability clauses;
- a =recovery!= or =observability!= macro;
- a raw profile record;
- a keyword configuration DSL;
- a second profile composition strategy;
- new names for upstream =gerbil-poo= operators.

* Central decision

The ordinary user composes profiles.  The user does not construct recovery
intents, continuation fences, receipt chains, or effect DAG nodes.

The stable ordinary surface is:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)))
#+end_src

When an additional reusable profile object is needed:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    resilient-observability))
#+end_src

In these examples:

- =use-composition= is the thin hygienic top-level binding macro;
- =compose= is a pure function;
- =profiles= is the first-class POO composition strategy;
- =use-module= is the thin module/profile-selection macro;
- =production= and =resilient-observability= denote POO-native profile values.

The example fixes interface shape.  It does not require
=resilient-observability= to become a globally built-in profile name.

* Non-redundancy rules

The ordinary surface does not permit redundant structural wrappers.

The following conceptual shapes are rejected:

#+begin_example
(use-composition ...
  (use-composition ...))

(compose profiles
  (compose profiles ...))

(use-composition ...
  (fixed-point-observability ...))

(compose profiles
  (if condition
      one-profile
      another-profile))
#+end_example

Composition is flat at the call site.  Optional and higher-order variation is
represented by POO-native profile objects and prototype extension, not by host
conditionals inside the composition form.

* Profile projection

A selected profile is a native POO object that may contribute typed facets for:

- recovery policy;
- continuation policy;
- retry and replay policy;
- observability policy;
- budget policy;
- cache and publication policy;
- redaction and retention policy;
- runtime handoff policy.

These facets are internal semantic projections.  They are not user-facing
keyword clauses.

The =profiles= strategy composes the selected objects into one
=ProfileBundle=.  Reachable imports, identities, capabilities, requirements,
and conflicts are derived from that POO value.

* Recovery projection

A recovery profile may constrain:

- which typed conditions are eligible for resume;
- which failures are eligible for retry;
- whether isolated replay is permitted;
- continuation lifetime and one-shot requirements;
- resumption budget limits;
- required cleanup and reconciliation evidence;
- permitted runtime and evaluator versions.

The profile does not itself invoke continuation, retry, or replay.

It projects policy inputs consumed by coordinator admission.

* Observability projection

An observability profile may constrain:

- permitted query and explanation facets;
- evaluation and lineage depth;
- observation budgets;
- redaction and retention;
- cache isolation;
- condition and continuation visibility;
- counterfactual simulation permissions;
- publication of diagnostic evidence.

The profile does not grant unrestricted access to runtime state.

Observability remains capability-attenuated and cannot become commit,
continuation-invocation, resume, retry, or replay authority.

* Profiles do not grant authority

A profile contributes policy, requirements, and requested capability shape.

Actual authority is the intersection of:

#+begin_example
principal authority
  ∩ session authority
  ∩ current governance policy
  ∩ module capability boundary
  ∩ profile constraints
  ∩ demand-specific admission
#+end_example

A profile can attenuate or require authority.  It cannot manufacture it.

Selecting a profile named =recoverable= therefore does not guarantee that a
specific continuation can be resumed.

* Three extension layers

** Ordinary composition

Ordinary users:

- select module-exported profiles;
- compose already-authored profile values;
- inspect validation and explanation;
- do not construct POO slots, receipts, or effect nodes.

The ordinary surface stays at =use-composition=, =compose profiles=, and
=use-module=.

** Profile authoring

Profile authors:

- compose existing POO-native profile values;
- extend prototypes with upstream =gerbil-poo= operations;
- attach typed policy facets;
- publish profile identity and responsibility;
- preserve pure functional composition.

This RFC introduces no generic =profile= macro.  Exact object authoring syntax
must come from verified native =gerbil-poo= operations rather than an invented
local DSL.

** Framework extension

Framework authors may:

- define new typed profile facets;
- extend policy and responsibility prototypes;
- implement POO Flow adapters around upstream POO objects;
- connect admitted POO values to explicit runtime boundaries.

Framework extension remains POO-native.  Raw alists, records, patch DSLs, and
ordinary =(lambda (self super) ...)= hooks are not the normal interface.

* Projection flow

#+begin_src mermaid
flowchart LR
  U["Ordinary user composition"] -->|"thin hygienic binding only"| B["use-composition"]
  B -->|"pure value expression is evaluated"| C["compose with profiles strategy"]
  M["use-module selections"] -->|"module profiles become reachable POO values"| C
  C -->|"profile identities and responsibilities resolve"| P["ProfileBundle"]
  P -->|"typed recovery and observability facets project"| Q["Policy projection"]
  P -->|"unresolved requirement or conflict is preserved"| X["Typed composition conflict"]
  Q -->|"current authority intersection succeeds"| A["Coordinator admission"]
  Q -->|"authority, budget, or policy rejects demand"| D["Typed denial or suspension"]
  A -->|"accepted recovery projects into existing effect intent"| E["Recovery effect graph"]
  E -->|"runtime receipts close cleanup and reconciliation"| O["EvaluationOutcome"]
#+end_src

The user-facing expression remains small even though its resolved POO graph is
rich.

* Flat syntax and semantic depth

Flat syntax does not mean shallow semantics.

One selected profile may project a deep POO graph containing:

- submodule responsibilities;
- transitive requirements;
- capability attenuation;
- recovery policies;
- observation budgets;
- continuation constraints;
- runtime handoff contracts.

The complexity belongs in reusable POO objects and profile prototypes, not in
the user's composition form.

* Higher-order variation

Conditional behavior is expressed by constructing or selecting higher-order
POO profile values before ordinary composition.

A derived research profile may extend a production profile with:

- broader authorized explanation;
- isolated replay;
- larger diagnostic budgets;
- stricter non-publication;
- additional fixed-point observations.

The ordinary composition still selects one profile value.  It does not embed
=if=, =cond=, or a new configuration clause language.

* Conflict behavior

Profile conflicts reuse the existing POO-native composition, precedence, and
control-policy conflict semantics.

Source order is not an implicit override mechanism.

A conflict must expose:

- contributing profile identities;
- conflicting typed facets;
- precedence and authority evidence;
- surviving independent constraints;
- available explanation and simulation demand;
- the absence of an admitted runtime action.

The composition cannot silently choose a recovery policy because it appeared
later in the form.

* Validation before runtime

Composition validation occurs before recovery execution.

Validation checks:

- reachable module and profile identities;
- missing requirements;
- capability-shape compatibility;
- policy-facet conflicts;
- precedence evidence;
- budget and observability bounds;
- runtime adapter availability;
- cache and publication isolation.

Validation produces POO-native evidence.  It does not claim that a future live
continuation, runtime epoch, or principal will be admitted.

* Explanation surface

An ordinary user may ask:

- which profile contributed a recovery policy;
- why resume or retry is permitted or denied;
- which observability facet narrowed a query;
- why a budget or retention bound survived;
- which module responsibility made an import reachable;
- what conflict prevented admission.

Explanation is evaluated through the existing debug-demand interface.  It is
not exposed as extra syntax inside =use-composition=.

* Macro governance

The public macro surface remains:

- =use-composition= for necessary top-level binding;
- =use-module= for necessary module/profile selection.

=compose= remains a pure function and =profiles= remains a first-class POO
strategy.

A new macro is admissible only when:

- hygiene or phase behavior cannot be expressed clearly as a function or
  POO-native object;
- its expansion is small and inspectable;
- it expands to ordinary POO-native and functional code;
- it has an independently reviewed RFC contract;
- it does not hide authority, effects, control flow, or conflict resolution.

Recovery and observability configuration do not currently justify another
public macro.

* Module responsibility

Modules export profile values under explicit identities and responsibilities.

A module-exported profile may aggregate many internal facets.  The importing
composition observes one coherent profile value and its reachable responsibility
closure.

The parent project does not take ownership of a child module's build, test, or
publication path merely because its profile is selected.

* User-interface examples

** Module profile only

#+begin_src scheme
(use-composition research-system
  (compose profiles
    (use-module wendao-episteme research)))
#+end_src

** Module profile plus reusable operational profile

#+begin_src scheme
(use-composition research-system
  (compose profiles
    (use-module wendao-episteme research)
    recoverable-debugging))
#+end_src

** Multiple module selections

#+begin_src scheme
(use-composition governed-system
  (compose profiles
    (use-module wendao-episteme production)
    (use-module agent sandbox-restricted)
    production-observability))
#+end_src

The profile names are illustrative domain values.  This RFC standardizes the
composition shape, not a universal catalogue of built-in profile names.

* User-to-runtime boundary

#+begin_src mermaid
flowchart TD

  U -->|"pure profile composition succeeds"| P["Resolved ProfileBundle"]
  P -->|"inspection remains effect-free"| I["Explanation and validation"]
  P -->|"live demand requests fresh authority"| C["Coordinator admission"]
  A["Advanced profile author"] -->|"uses verified native POO prototype operations"| P
  F["Framework author"] -->|"defines typed facets and bounded adapters"| P

  C -->|"rejected demand produces typed evidence"| I
  R -->|"receipts reconcile into immutable successor context"| T["Terminal outcome"]
#+end_src

No edge allows ordinary syntax to invoke the runtime directly.

* Failure behavior

The composition fails closed on:

- unknown module or profile identity;
- missing reachable responsibility;
- incompatible typed profile facets;
- implicit source-order override;
- a profile attempting to manufacture capability;
- raw recovery or observability clause DSLs;
- host conditional control inside the composition form;
- nested redundant composition wrappers;
- user-visible receipt or effect-node construction;
- runtime invocation during profile resolution;
- unverified invented =gerbil-poo= operator syntax.

- [X] Ordinary users compose profile values, not runtime mechanisms.
- [X] =use-composition= and =use-module= remain thin hygienic macros.
- [X] =compose= remains a pure function.
- [X] =profiles= remains the POO-native composition strategy.
- [X] The ordinary composition shape is flat.
- [X] Recovery and observability are typed profile projections.
- [X] Profiles attenuate or request authority; they do not grant it.
- [X] Optionality is expressed by higher-order POO values, not host conditionals.
- [X] Existing precedence and conflict semantics are reused.
- [X] Advanced extension uses native =gerbil-poo= prototypes and operations.
- [X] Runtime effects remain behind explicit handoff boundaries.
- [X] No new public macro is introduced.

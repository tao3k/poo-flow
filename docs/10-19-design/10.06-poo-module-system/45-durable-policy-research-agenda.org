* 10.06.45 Durable Policy Research Agenda
** 10.06.45.10 Status
Draft for discussion.

This document strengthens the durable-policy thread started in [[file:43-session-memory-recovery-rfc.org][43 Session Memory Durable Policy RFC]].
The goal is not to copy Codex, Claude Code, OpenRath, Temporal, Azure Durable Functions, or any agent-memory paper.
The goal is to extract the durable invariants that fit =poo-flow=: functional flow values, POO-native policy objects, explicit session identity, and Rust/Marlin-owned durable runtime machinery.

** 10.06.45.20 Main Conclusion
Durable should be a first-class capability, not a helper called "recovery".

The correct shape is:

#+begin_src text
POO durable policy
  -> bounded Scheme receipt
  -> runtime fact log
  -> derived indexes
  -> replay/backfill/repair jobs
  -> resumable session, memory, workflow, sandbox, and artifact state
#+end_src

In user-facing Scheme, durable remains a POO object that can be inherited, specialized, and validated.
In the runtime boundary, durable becomes a set of explicit receipts and manifests.
In Rust/Marlin, durable becomes append-only facts, checkpoint materialization, leases, watermarks, indexes, and repair behavior.

This means =durable-policy= is shared by =session= and =memory= instead of being owned by one module.
Recovery is a runtime procedure derived from durable policy plus stored facts.

This agenda uses =memory= only as a derived temporal role.  The canonical object
is the Organization fact/evidence/policy graph with identity, version, lineage,
authority, and time.  "Memory" is the projection selected for one actor, task,
model, repository, toolchain, policy epoch, and point in time.  Durable storage
keeps the history; it does not make every historical item active, applicable, or
authorized.

- Backfill persists progress through watermarks; =checkpoint_backfill= records a running status and last watermark.

- Make durable policy explicit at authoring time, not hidden in runtime conventions.
- Attach durable behavior to session, memory, workflow, sandbox, and artifact policies through POO inheritance/composition.
- Validate resume/replay constraints before projection.
- Keep Scheme objects high-level and POO-native, but project hot receipts into fixed =defstruct= values before ABI alists.

*** 10.06.45.30.30 Claude / Anthropic Evidence
Official Claude Code documentation gives three useful durable signals:

1. Checkpointing is a user-visible safety feature.
   Claude Code creates prompt/edit checkpoints, persists them across resumed conversations, supports restore of code, conversation, or both, and supports targeted summarization.
   It also documents the limits: shell-command file changes and unrelated external changes are not fully tracked.
   Source: [[https://code.claude.com/docs/en/checkpointing][Claude Code Checkpointing]].

2. Subagents are identity-bearing contexts.
   Claude Code subagents run in separate context windows with separate tool access and permissions.
   A resumed subagent keeps its prior conversation, tool calls, results, and reasoning; the parent can address it by agent id through =SendMessage=.
   Subagent transcripts are stored separately under the project/session subagent directory.
   Source: [[https://code.claude.com/docs/en/sub-agents][Claude Code Subagents]].

3. Memory is context, not enforcement.
   Claude Code distinguishes user/project/org instructions from auto memory, and says these are loaded as context rather than hard enforcement.
   Enforcement belongs in hooks such as =PreToolUse=.
   The Claude API memory tool is explicitly client-side: Claude requests file operations, while the application owns storage, path policy, and returned tool results.
   Sources: [[https://code.claude.com/docs/en/memory][Claude Code Memory]] and [[https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool][Claude Platform Memory Tool]].

Anthropic's "Building effective agents" gives the control-plane principle:
- workflows are predefined code paths;
- agents dynamically direct tool use;
- successful production systems prefer simple composable patterns;
- agents need environment feedback, checkpoints, sandbox testing, and guardrails.
Source: [[https://www.anthropic.com/engineering/building-effective-agents][Building effective agents]].

Design lesson:
Claude's surface is strong at user ergonomics, but its documented checkpointing is explicitly not a full durable runtime.
=poo-flow= should learn the user affordance, not stop at it.
Our durable policy must cover tool-side effects, shell/runtime work, sandbox placement, memory writes, and sub-agent communication, because those are exactly the places a simple local checkpoint cannot fully recover.

*** 10.06.45.30.40 Durable Execution Systems
Temporal and Azure Durable Functions provide the durable execution baseline.

Temporal:
- a workflow execution is durable and recoverable;
- each execution has local state and communicates through signals/activities;
- replay checks generated commands against event history;
- after failure, execution resumes from the latest recorded event.
Sources: [[https://docs.temporal.io/workflow-execution][Temporal Workflow Execution]] and [[https://docs.temporal.io/encyclopedia/event-history][Temporal Event History]].

Azure Durable Functions / Durable Task:
- orchestration instances have stable instance ids;
- progress is checkpointed at =await= / =yield= boundaries;
- event sourcing records actions instead of dumping full runtime state;
- orchestrators must be deterministic because they replay.
Sources: [[https://learn.microsoft.com/en-us/azure/durable-task/common/durable-task-orchestrations][Durable Orchestrations]] and [[https://learn.microsoft.com/en-us/azure/durable-task/common/durable-task-code-constraints][Orchestrator Code Constraints]].

Design lesson:
The strong durable pattern is not heap snapshotting.
It is event history plus deterministic replay plus explicit side-effect boundaries.

For =poo-flow=:
- Scheme flow composition should be replay-safe by construction where possible.
- Runtime effects should sit behind named activities/actions/handoffs.
- Session ids, loop-run ids, checkpoint ids, artifact ids, and sandbox handles must be durable addresses.
- Durable policy must decide when a flow can replay, resume, compensate, or require human intervention.

*** 10.06.45.30.50 Recovery And Long-Lived Transaction Papers
ARIES provides the database-recovery baseline.
It uses write-ahead logging, log sequence numbers, restart recovery, redo/undo, and partial rollback.
Source: [[https://dl.acm.org/doi/10.1145/128765.128770][ARIES ACM record]], with accessible PDF mirrors such as [[https://web.stanford.edu/class/cs345d-01/rl/aries.pdf][Stanford ARIES PDF]].

Sagas provide the long-lived-transaction baseline.
A saga decomposes a long transaction into smaller transactions with compensating actions.
Source: [[https://dl.acm.org/doi/10.1145/38713.38742][Sagas ACM record]], with accessible PDF mirrors such as [[https://www.cs.cornell.edu/andru/cs711/2002fa/reading/sagas.pdf][Cornell Sagas PDF]].

Design lesson:
Agent workflows are long-lived, side-effect-heavy computations.
They need compensation and repair semantics, not only "retry".

For =poo-flow=:
- Each durable action should declare whether it is replayable, idempotent, compensatable, or terminal.
- A workflow task should be able to project a compensation receipt.
- A failed child session should produce structured repair facts for the parent instead of mutating parent context directly.

It is useful because =poo-flow= is not only an agent-loop system; it is also a workflow, CI/CD, deploy, sandbox, and policy system.

Sources:
- [[https://www.workflowpatterns.com/documentation/][Workflow Patterns documentation]]

Durable cannot be only "save session state".

- data flow state;

- exception and compensation state;

For =poo-flow=, this argues for a durable policy that can be inherited by workflow, session, memory, sandbox, and CI/CD modules.

*** 10.06.45.30.70 Agent Memory Papers
Generative Agents uses observation, memory stream, reflection, and planning to sustain believable long-horizon behavior.

Memory durability is not one blob of transcript.

- recall selection;
- reflection/consolidation;
- usage accounting;
- skill/artifact promotion;
- retention and deletion.

This matches Codex's local memory job pipeline and should become explicit in =poo-flow= as =memory-policy= inheriting or referencing =durable-policy=.

*** 10.06.45.30.80 Self-Improving Harness And Temporal Validity Evidence

"Self-improving harness" already includes self-evolution.  The useful question is
not whether this is a new name, nor whether the system remains model- and
harness-centred.  The unresolved question is who may promote a model-produced
candidate into future steering authority, under which evaluator and world state,
and how that authority is invalidated.

[[https://lilianweng.github.io/posts/2026-07-04-harness/][Harness Engineering for Self-Improvement]] correctly places permission control,
evaluation, persistent state, and workflow around the model.  It also names weak
evaluators, context and memory lifecycle, negative-result preservation, diversity
collapse, reward hacking, long-term repository health, and the role of humans as
open challenges.  Its strongest boundary is that the evaluator and permission
control should sit outside the harness-evolution loop.  This agenda sharpens that
boundary into a typed promotion transaction instead of treating it as a general
recommendation for "human review".

The April--June 2026 literature is a rapid and important research wave, but its
best results remain bounded:

| Work | What it demonstrates | Boundary that remains open |
|-
| [[https://arxiv.org/abs/2604.25850][Agentic Harness Engineering (AHE)]] | File-level, reversible harness edits, layered trajectory evidence, and falsifiable next-round predictions improve a fixed coding benchmark. | The verifier, model configuration, editable surface, and benchmark remain externally fixed; the paper does not define temporal applicability or promotion authority for evaluator changes. |
| [[https://arxiv.org/abs/2603.28052][Meta-Harness]] | A coding agent can search executable harness code while preserving scores, traces, and candidate history in files. | Complete history is queryable, but history items do not carry a validity domain, invalidation rule, or active/history role transition. |
| [[https://arxiv.org/abs/2605.09998][Continual Harness]] | Reset-free adaptation can create, update, and delete prompts, subagents, skills, and memory artifacts in a fixed game world. | The same model remains the refiner; there is no independent authorization or proof owner for promotion. |
| [[https://arxiv.org/abs/2605.24539][DemoEvolve]] | Human demonstrations stabilize credit assignment when long-horizon reward is sparse and high-variance. | The result shows why self-rollout selection is not a sufficient audit mechanism; it does not solve open-world validity. |
| [[https://arxiv.org/abs/2605.30621][Harness Updating Is Not Harness Benefit]] | Producing a plausible harness update and actually using it correctly are different capabilities. | An append-only memory artifact can be correct yet unused, misloaded, or ignored; no expiry/invalidation protocol is evaluated. |
| [[https://arxiv.org/abs/2606.09498][Self-Harness]] | A propose/evaluate/accept loop with held-in and held-out regression gates can improve a bounded harness. | The held-out split is repeatedly used as a promotion gate inside a fixed task distribution; it is not a permanent external constitutional authority. |
| [[https://arxiv.org/abs/2605.06527][STALE]] | Later evidence can implicitly invalidate earlier memory; retrieval of the update does not guarantee downstream policy adaptation. | TTL and explicit overwrite are insufficient because invalidation may propagate across related attributes and actions. |
| [[https://arxiv.org/abs/2606.27472][Supersede]] | Frontier-model performance falls when bounded self-maintained memory must preserve the current value; more memory capacity does not repair the gap. | The bottleneck is the maintenance and supersession policy, not only storage size or model strength. |
| [[https://arxiv.org/abs/2605.06125][TEBench]] | Passing tests can be stale, and reactive execute-fail-fix agents structurally miss stale and missing tests. | A green evaluator result can itself be expired evidence; evaluator identity and applicability must therefore be versioned and promoted. |
| [[https://arxiv.org/abs/2606.26511][Temporal Validity / MemStrata]] | A bi-temporal ledger and explicit supersession can prevent stale answers in structured fact replacement. | Structured single-fact replacement does not settle implicit conflicts, evaluator drift, organizational authority, or policy promotion. |

The defensible conclusion is narrower than open-world self-evolution:

#+begin_src text
bounded mutation
+ fixed evaluator
+ replayable environment
+ reversible acceptance
=> useful autonomous search inside one validity envelope

It does not imply that the system may rewrite the validity envelope and approve
that rewrite with the new envelope.
#+end_src

Human audit therefore is not a percentage of turns.  Operational work can be
autonomous; adaptation can propose and sandbox candidates; constitutional changes
to objectives, evaluators, authority, or promotion rules require a separate
authority path.  Human judgment supplies organizational legitimacy and value
choice, not infallible factual truth.

** 10.06.45.40 Design Approaches
*** 10.06.45.40.10 Approach A: Git/Checkpoint Wrapper Only
This copies the visible Claude Code checkpoint affordance.

Pros:
- simple user mental model;
- useful for code-edit rollback;
- easy to explain.

Cons:
- does not cover shell side effects, sandbox state, sub-agent transcripts, memory writes, external tools, or runtime jobs;
- cannot express replay/compensation semantics;
- not enough for project/root/child session graphs.

Verdict: useful as one backend capability, but too weak as the durable architecture.

*** 10.06.45.40.20 Approach B: Session Transcript Only
This copies the simplest OpenRath-style append-only session persistence.

Pros:
- matches functional =Session -> Flow -> Session= composition;
- easy to inspect;
- supports lineage and replay input.

Cons:
- derived indexes and repair jobs are missing;
- memory consolidation is bolted on;
- workflow/resource state must be reconstructed ad hoc;
- partial failures need stronger semantics.

Verdict: necessary, but incomplete.

*** 10.06.45.40.30 Approach C: Event Log + Checkpoint + Derived Index
This combines:
- OpenRath's session-as-value model;
- Codex's fact-log/index/job split;
- Temporal/Azure durable replay discipline;
- ARIES/Saga repair and compensation lessons;
- agent-memory paper pipelines.

Pros:
- strong enough for long-lived agent projects;
- supports parent/child/session graph recovery;
- handles memory as a durable pipeline;
- lets Scheme stay POO-native and high level;
- lets Rust/Marlin own IO, concurrency, storage, and repair.

Cons:
- requires careful receipt contracts;
- must define deterministic/replay-safe boundaries;
- needs performance gates for projection and validation.

Verdict: recommended.

** 10.06.45.50 POO Flow Capability Model
Durable should appear in Scheme as a composable capability object family.

Conceptual object families:
- =durable-policy=: fact log, checkpoint cadence, replay mode, repair mode, retention, backend owner.
- =checkpoint-policy=: what to capture at turn/task/session boundaries.
- =journal-policy=: append-only fact categories and redaction rules.
- =index-policy=: which derived indexes are required and rebuildable.
- =resume-policy=: when to auto-resume, ask user, fork, or fail closed.
- =repair-policy=: backup, rebuild, retry, compensate, quarantine, or stop.
- =memory-policy=: recall, extraction, consolidation, ranking, retention, usage accounting.
- =session-policy=: root/child identity, lineage, context grants, communication grants, sandbox grants.
- =workflow-policy=: task state, retry, compensation, parallel branches, join semantics.
- =artifact-policy=: stable handles, content-addressed storage, provenance, retention.
- =sandbox-policy=: inherit, clone, share, isolate, or replace placement.

These should be POO objects, not option trees.
C3/C4-style composition decides inherited slot precedence.
Validation decides whether the resulting policy is legal.
Projection produces bounded runtime receipts.

** 10.06.45.60 Runtime Receipt Shape
The runtime should receive fixed, bounded shapes.
The Scheme side can use native POO while authoring and validating, but hot receipts should use =defstruct= internally before ABI projection.

Representative receipt fields:

#+begin_src scheme
(defstruct durable-policy-receipt
  (policy-id
   project-id
   root-session-id
   session-id
   parent-session-id
   loop-run-id
   checkpoint-policy
   journal-policy
   index-policy
   resume-policy
   repair-policy
   memory-policy-ref
   sandbox-policy-ref
   artifact-policy-ref
   diagnostics)
  transparent: #t)
#+end_src

Bounded projection:

#+begin_src scheme
(def (durable-policy-receipt->alist r)
  ...)
#+end_src

This follows the project direction:
1. user authoring uses POO;
2. generated runtime receipt uses =defstruct=;
3. manifest / JSON / Marlin handoff uses bounded alist serialization.

** 10.06.45.70 Durable State Categories
The durable runtime should separate these categories.

1. Fact log:
   append-only events, session turns, tool requests/results, memory facts, spawn edges, sandbox events, artifact events.

2. Checkpoint:
   bounded materialized state for resume, not a whole heap dump.

3. Derived index:
   queryable views over sessions, children, artifacts, memory summaries, jobs, and latest status.

4. Job state:
   leases, watermarks, retry counters, ownership token, last error, last success watermark.

5. Memory store:
   durable notes, summaries, reflections, skill artifacts, usage counters, retention metadata.

6. Repair journal:
   corruption backup, rebuild attempt, compensation execution, quarantine reason, human-decision receipt.

7. Communication ledger:
   parent/child messages, sibling channels, request/response ids, permission decisions.

8. Sandbox ledger:
   placement, handle id, shared/clone/isolate mode, active resources, close/reopen facts.

** 10.06.45.75 Semantic Role Promotion And Temporal Applicability

The primary operation is not a memory write.  It is a semantic privilege
transition:

#+begin_src text
Trace/Event
  -> Evidence
  -> Claim
  -> Candidate Policy/Skill/Evaluator
  -> Active Harness Projection
#+end_src

Each arrow grants additional influence over future action.  Model output begins
as an observation or candidate.  It must not acquire policy authority merely
because it was written to Markdown, JSON, a vector index, or an Org document.
Org structure and contracts give the transition a canonical representation;
Authority and proof determine whether the transition is allowed.

Expiry is role-specific:

| Role | Temporal rule |
|-
| Event or trace | Remains a historical fact; its occurrence does not expire. |
| Evidence | Its weight, scope, verifier, or applicability can expire. |
| Claim | May be superseded or become inapplicable without deleting its history. |
| Policy or skill | May be revoked, attenuated, or excluded from the active projection. |
| Evaluator or test | May still execute and pass while no longer validating current semantics. |
| Authority | Delegation, lease, quorum, or policy epoch can expire independently of content. |

Applicability needs at least four coordinates:

1. valid time: when the claim is true in the represented world;
2. record/admission time: when the Organization accepted the item;
3. authority epoch: which delegation and policy constitution authorized it;
4. world fingerprint: the relevant organization, model, harness, repository,
   tool/API, evaluator, and runtime versions.

The active harness is therefore a projection, not a memory directory:

#+begin_src text
H(t) = project(
  CanonicalOrganizationBundle,
  actor, task, model, harness, repository, toolchain,
  evaluator epoch, authority epoch, world fingerprint, t)
#+end_src

Content identity and version, provenance, active/history roles, exactly-once
materialization, semantic/causal deduplication, invalidation propagation, and
injection receipts are consequences of making this role transition transactional.
They are not the definition of memory.

Three critical limits remain:

- exactly-once can install the wrong policy exactly once;
- a receipt proves that a named transition occurred, not that its semantic claim
  or evaluator was correct;
- deduplication by object identity does not prevent equivalent content under new
  identities from being counted repeatedly and overweighting future steering.

The canonical Bundle must therefore preserve counter-evidence, dissent, rejected
candidates, and invalidation causes.  Canonicalization must not collapse history
into one self-reinforcing active story.

** 10.06.45.77 POO Flow + Cedar + Lean Dual-Engine Promotion Approval

The normative implementation boundary is specified in
[[file:149-protocol-person-promotion-rfc.org][149 Protocol Person Promotion And Constitutional Boundary RFC]].

The privilege-promotion core is driven by =poo-flow= plus the Cedar and Lean dual
engine.  It is not "POO Flow decides, while Cedar and Lean provide optional
support".  =poo-flow= owns the canonical semantic transaction; Cedar decides
whether the actor is authorized to request that transition; Lean verifies the
declared invariants required by that transition.  Neither engine can substitute
for the other.

This split reduces error classes; it does not create truth.  Cedar can correctly
evaluate a stale or badly governed policy, and Lean can correctly prove a theorem
about an obsolete or inadequate specification.  Current policy/spec epochs,
external evidence, amendment governance, and post-deployment observation remain
part of the acceptance argument.

The existing owners establish a real substrate:

- [[file:107-agentic-control-plane-ac03-five-facets-design.org][107 AC-03 Five Facets]] binds Organization, Authority, Context, Protocol, and
  Evidence to one identity universe, schema, epoch, lineage, digest, and
  validation result.
- [[file:123-agentic-control-plane-ac08-cedar-token-evidence-roots-design.org][123 AC-08 Cedar Token And Evidence Roots]] defines Cedar decision projection,
  one-shot =AuthorizedEffectToken= values, semantic/execution roots, atomic
  mediation, replay protection, and fail-closed indeterminate outcomes.
- [[file:127-agentic-control-plane-ac09-lean-evidence-proof-bridge-design.org][127 AC-09 Lean/Evidence Proof Bridge]] defines the typed proof case and the Lean
  obligations for the authorization/effect chain.
- [[file:129-agentic-control-plane-ac09-qualification-receipt.org][129 AC-09 Qualification Receipt]] records the implemented cross-language
  qualification of that effect-authorization proof chain.

That substrate is necessary but not sufficient.  AC-08/09 qualify authorization
and proof of an effect token; they do not, by themselves, prove that an evaluator,
skill, memory-derived claim, Cedar policy, Lean specification, or complete harness
may be promoted into the next active Organization epoch.  The promotion protocol
below remains a separate research and implementation boundary.

| Owner | Promotion responsibility | Must not do |
|-
| POO Flow Scheme/POO control plane | Canonicalize the =PromotionIntent= and Bundle delta; resolve identity, role, scope, epochs, evidence, invalidators, rollback, and required obligations; join the two engine decisions. | It must not manufacture Cedar permission or Lean proof success. |
| Cedar authorization engine | Evaluate =principal/action/resource/context= against the current Authority facet and policy epoch: who may promote this candidate to this role and scope? | It cannot prove semantic correctness, non-regression, or scientific truth. |
| Lean proof engine | Verify the required proof object against the current specification/kernel epoch: does the transition satisfy the declared invariants? | It cannot grant organizational authority or choose human values. |
| Human Audit / organizational quorum | Supply legitimacy for constitutional changes through a named principal, quorum, signature, or approval evidence referenced by Cedar. | It is not an ad hoc prompt and not an infallible factual oracle. |
| Marlin/runtime kernel | Atomically materialize an already-approved transition, emit execution and injection receipts, and preserve rollback/indeterminate state. | It must not reinterpret Organization semantics or promote a failed/unknown decision. |

#+begin_src mermaid
flowchart TD
  Candidate["Candidate plus evidence"] --> POO["POO Flow compiles PromotionIntent and Bundle delta"]
  POO --> Cedar["Cedar: authorized under current Authority epoch?"]
  POO --> Lean["Lean: proof obligations verified under current spec epoch?"]
  Cedar --> Join["Fail-closed promotion join"]
  Lean --> Join
  Join -->|"both current and complete"| Marlin["Marlin atomically materializes once"]
  Join -->|"deny, refuted, unknown, stale, or incomplete"| History["Retain candidate/history; do not activate"]
  Marlin --> Receipt["Promotion, materialization, and injection receipts"]
  Receipt --> Active["Next active Organization projection"]
#+end_src

The acceptance rule is conjunctive:

#+begin_src text
Promote(candidate) =
  Cedar.PERMIT
  AND Lean.VERIFIED
  AND BundleEpochMatches
  AND AuthorityEpochMatches
  AND ProofSpecEpochMatches
  AND EvaluatorApplicabilityMatches
  AND EvidenceComplete
  AND MaterializationReceiptReady
#+end_src

=Deny=, =Refuted=, =Unknown=, missing evidence, stale epochs, incomplete
receipts, or an indeterminate runtime effect all mean "not promoted".  A proof
generator may be automated, but the small Lean kernel verifies its result.  A
Cedar adapter may be automated, but only the canonical Organization Bundle may
define its principal, resource, action, context, policy identity, and epoch.

The =PromotionIntent= and final receipt must bind at least:

- promotion identity, candidate content digest, schema, and version;
- provenance and causal evidence references;
- source role, target role, scope, and active/history projection;
- Bundle, Cedar policy/entity/decision, Lean theorem/spec/kernel, evaluator, model,
  repository, toolchain, and runtime identities and epochs;
- semantic and causal deduplication keys;
- invalidation triggers, expiry/lease, rollback target, and postconditions;
- exactly-once claim/materialization identity;
- injection target, projection digest, source list, and injection receipt.

Constitutional self-amendment requires a cross-epoch rule:

- a new Cedar policy cannot authorize its own installation; the old/current
  policy epoch plus its required human/quorum path authorizes the transition;
- a new Lean specification cannot establish its own admissibility only under the
  new specification; the old trusted kernel/specification verifies the declared
  translation, compatibility, or amendment obligations;
- POO Flow binds the old and new Bundle, policy, proof, and evaluator identities
  into one transition receipt before Marlin can materialize the new epoch.

This places Human Audit at semantic privilege transitions, especially changes to
objectives, evaluators, authority, proof obligations, and promotion rules.  It
does not require human approval for every operational step or every candidate
experiment.  [[file:52-three-loop-human-audit-runtime-plan.org][52 Three Loop Human Audit Runtime Plan]] owns the broader loop boundary;
this section supplies its dual-engine promotion semantics.

** 10.06.45.78 Falsifiable Self-Evolution Research Program

The architecture should be compared against simpler alternatives rather than
assumed correct.  Run the same evolving-agent workload under four policies:

1. append-only Markdown memory;
2. TTL-based memory;
3. bi-temporal fact supersession;
4. Org-contract semantic role promotion with the POO Flow + Cedar + Lean gate.

Inject controlled faults:

- explicit fact replacement and implicit cross-attribute invalidation;
- a passing but stale evaluator/test;
- model, repository, tool/API, runtime, Cedar policy, Lean specification, and
  authority-epoch changes;
- duplicate semantic content under the same and different identities;
- duplicate or missing injection/materialization receipts;
- an indeterminate external effect;
- a quiet child that tempts duplicate dispatch;
- an attempted self-approval of a new evaluator, Cedar policy, or Lean spec.

Measure:

- stale-action rate and stale-evaluator detection rate;
- false-promotion and false-rejection rates;
- invalidation-propagation completeness;
- duplicate steering weight and exactly-once materialization violations;
- rollback recovery latency and indeterminate-outcome containment;
- human audit minutes per accepted semantic privilege transition;
- long-term regret after the environment or evaluator changes.

The decisive claim is not that the fourth policy stores better memories.  It is
that it reduces unauthorized or stale promotion without making legitimate
adaptation prohibitively expensive.  If it cannot beat the simpler baselines on
that trade-off, the additional Organization, Cedar, Lean, and receipt machinery
has not justified itself.

** 10.06.45.100 Proposed Direction
Use Approach C.

Treat durable as a shared POO capability with runtime-backed fact logs, checkpoints, derived indexes, repair jobs, and memory pipelines.

The user should see concise POO-native policy and module forms.
The Scheme implementation should validate object composition and project bounded receipts.
The runtime should own storage, replay, backfill, leases, corruption repair, and cross-session delivery.

This makes durable a real differentiator for =poo-flow=:
not just "resume a chat", but a policy-governed substrate for long-running agent projects, multi-agent session graphs, workflow execution, memory consolidation, sandbox isolation, CI/CD, deploy, and recovery.

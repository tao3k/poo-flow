* Normative responsibility

This module exclusively owns lineage propagation, context-local wait analysis,
productive-recursion distinction, and cycle-breaker behavior.

* Evaluation lineage

=EvaluationLineage= is immutable and path-local.  Mix, Profile, capability, and
arbitrary submodule descent derive frames without mutating the parent:

#+begin_src text
EvaluationLineageFrame
  frameId
  parentFrameId
  branchId
  compositionPath
  moduleIdentity
  targetIdentity
  operationKind
  enteredAtEventSequence
#+end_src

Concurrent branches receive explicit fork identities.  They do not depend on
ambient thread-parameter inheritance.

One root runtime request creates one lineage root:

#+begin_src text
EvaluationLineage
  runtimeContextId
  rootRequestId
  currentFrame
#+end_src

Nested synchronous composition derives a child frame from =currentFrame=.
Spawning concurrent work requires an explicit fork operation that preserves the
root identity and allocates a new =branchId=.  User syntax cannot provide or
override lineage, frame, branch, or request identities.

POO Flow dynamically binds the current lineage around its own composition and
capability-resolution combinators.  A missing lineage or a lineage from another
runtime context is an =IllegalRuntimeTransitionCondition= owned by 45-03.

A captured continuation retains its originating lineage value.  Resumption
must pass the 45-03 =RuntimeContinuationGuard= before the lineage is rebound.
Resumption never restores an earlier wait graph.

* Productive recursion

Structural POO recursion through =self=, =super=, Mix, Profile, or a descendant
is allowed.  A cycle condition is raised only when POO Flow-owned
module-capability demands form a strict cycle in which no participant can
publish a value.

POO Flow does not inspect or replace arbitrary POO slot recursion.

The following are not cycles:

- a structural =self=/=super= reference that is not currently forced;
- repeated reference to a =ready= target;
- observation of an already =failed= target;
- two branches sharing an evaluating target when the wait graph stays acyclic;
- equal module/capability identity in two different runtime contexts;
- arbitrary nested =.ref= activity that never crosses the POO Flow capability
  boundary.

The following are cycles:

- the current lineage strictly demands a target already evaluating in its
  ancestor path;
- a proposed cross-lineage wait edge closes an alternating ownership/wait path.

* Ownership boundary: gerbil-poo lineage evidence

Prototype lineage, demand ancestry, recursive-object progress, fixed-point
cycle detection, and generic convergence evidence belong to =gerbil-poo=.
This module specifies the evidence that POO Flow requires from that sole POO
library and the POO Flow conditions, traces, receipts, limits, and governance
decisions projected from it.

POO Flow MUST NOT construct a second wait graph by independently evaluating
prototype slots, infer cycles from a parallel memoization table, or implement a
local fixed-point evaluator.  When the pinned library does not expose required
lineage or progress evidence, the missing facility is recorded as a
=gerbil-poo= extension requirement.

* Demand-boundary cycle semantics

The runtime distinguishes structural cycles, productive recursion, and
nonproductive forced cycles.

#+begin_export mermaid
flowchart TD
    A["Repeated prototype reference"] --> B{"Forced at the same demand boundary?"}
    B -->|no| C["Structural cycle: remain lazy"]
    B -->|yes| D{"Outer value produced first?"}
    D -->|yes| E["Productive recursion"]
    D -->|no| F["Nonproductive forced-cycle condition"]
#+end_export

- A structural cycle links prototypes or Submodules without forcing their
  values and may be valid.
- Productive recursion realizes an outer constructor before retaining a lazy
  reference to itself and may be valid.
- A nonproductive forced cycle occurs when realizing a slot requires the same
  slot at the same demand boundary before any value can be produced.

Cycle detection MUST therefore be demand-aware.  An evaluation key includes
at least the lineage-root identity, slot path, and demand boundary.  Merely
encountering the same object again is insufficient evidence of failure.

Each demanded slot has the observable lifecycle:

#+begin_example
unforced -> evaluating -> realized
                     \-> suspended(condition + continuation)
                         -> resumed | replaced | aborted
#+end_example

When an =evaluating= key is forced again at the same demand boundary, the
runtime raises a structured cycle condition immediately rather than waiting
for host stack overflow, timeout, or unexplained performance collapse.  The
condition records the slot cycle, prototype lineage, declaration source for
each dependency edge, evaluation depth, repetition count, adjacent unforced
dependencies, and the continuation authority captured at the boundary.

* Progress evidence and convergence claims

The runtime MUST NOT use deep equality over arbitrary POO objects to decide
whether a fixed point is converging.  Lazy slots and cyclic prototypes make
that comparison potentially nonterminating and semantically unreliable.

A fixed-point domain may instead expose an optional POO progress capability
with the abstract contract:

#+begin_example
previous progress witness
  x current evaluation event
  -> advanced | stable | regressed | unknown
#+end_example

The witness may encode a domain-owned monotonic order, lattice height, or
another bounded progress proof.  It remains a POO semantic object and its
origin is included in evaluation receipts.

Without a progress capability, the runtime may report structural budget
exhaustion or a nonproductive demand cycle.  It MUST NOT claim that convergence
or nonconvergence has been proved merely from elapsed time, object identity,
or an attempted deep comparison.

Effect-boundary wait nodes, external provider edges, and receipt-return edges
follow
[[file:45-09-effect-intent-suspension-handoff-reinjection.org][Effect Intent, Suspension, Runtime Handoff, And Receipt Reinjection]].  This
module retains authority over lineage, progress evidence, and cycle diagnosis;
it does not execute the effect while traversing the wait graph.

* Containment and import dependency paths

Provider candidate traversal through containment and explicit Mix imports is
specified by [[file:45-10-provider-runtime-search-closure.org][Provider Runtime Search Closure]].  This module remains authoritative for
the distinct containment/import paths, lineage evidence, productive recursion,
and cycle diagnosis consumed by that closure.

Cancellation ownership, parent/child propagation, and cleanup wait edges follow
[[file:45-12-structured-cancellation-boundary-generations.org][Structured Cancellation And Boundary Generations]].  This module remains
authoritative for the lineage and wait-graph evidence consumed by cancellation
policy.

Admission, capacity, backpressure, and starvation wait nodes follow
[[file:45-13-demand-admission-backpressure-cleanup-capacity.org][Demand Admission, Backpressure, And Cleanup Capacity]].  This module remains
authoritative for the dependency, progress, and cycle evidence consumed by
admission policy.

Cycle and debugging evidence MUST preserve two separate paths:

- the containment path that identifies the enclosing Profile, Mix, Capability,
  and Submodule scopes;
- the import dependency path that records lazy demand edges between POO
  objects.

An import edge does not reparent the imported object.  A dependency cycle is
reported over import and demand edges while each participant retains its
containment-derived structural address.  Debugging output MUST NOT collapse
the dependency graph into the containment tree or treat a readable path string
as the underlying object identity.

* Runtime wait graph

#+begin_src text
evaluation --owns--> module-capability-cell
evaluation --waits-for--> module-capability-cell
#+end_src

Before installing a wait edge, POO Flow atomically verifies that the graph
remains acyclic.

The graph is a private POO runtime object.  Its mutation and synchronization are
isolated behind named atomic operations.  It does not expose a public graph
DSL.

A capability target address is operational:

#+begin_src text
ModuleCapabilityTargetAddress
  runtimeContextId
  moduleIdentity
  capabilityIdentity
#+end_src

It is not a QualificationKey, package identity, canonical digest, or
DecisionReceipt field.

Graph nodes and directed edges are:

#+begin_src text
evaluation(evaluationId)
capability-cell(ModuleCapabilityTargetAddress)

capability-cell --owned-by--> evaluation
evaluation --waits-for--> capability-cell
#+end_src

#+begin_mermaid
flowchart LR
    A["Evaluation A"] -->|"owns"| CA["Capability cell A"]
    B["Evaluation B"] -->|"owns"| CB["Capability cell B"]
    A -->|"waits"| CB
    B -. "proposes wait" .-> CA
    CA -. "would close cycle" .-> Break["Reject edge and choose B as cycle breaker"]
#+end_mermaid

Different lineage is not proof of independence.  It may wait only when the
proposed graph remains acyclic.

The evaluator proposing the closing edge is the deterministic cycle breaker.
The edge is not installed; unrelated cells are not rewritten.  Normal unwind
publishes operational failure and wakes dependents.

* Atomic wait-edge algorithm

Before waiting on an =evaluating= capability cell, POO Flow performs one atomic
registry operation:

#+begin_src text
propose-wait(currentEvaluation, targetCell):
  1. confirm runtime context and lineage identity
  2. observe targetCell lifecycle and owner
  3. if target is ready or failed, return its outcome
  4. if target occurs in current lineage ancestry, report direct cycle
  5. search from target owner through existing waits/owners
     for currentEvaluation
  6. if reachable, return the discovered cycle path without installing edge
  7. otherwise install currentEvaluation --waits-for--> targetCell
#+end_src

Steps 2 through 7 are serialized with cell ownership publication.  Two
simultaneous proposed edges therefore cannot both pass against an obsolete
graph snapshot.

When more than one path could close the cycle, POO Flow chooses:

1. the path with the fewest alternating edges;
2. then the path with the earliest edge event sequence;
3. then the lowest runtime =evaluationId=.

These are operational tie-breakers only.  They do not enter semantic receipts.

The proposing evaluator is always the breaker.  It records =cycle-detected=
with the chosen path and receives the phase-appropriate structured condition.
No proposed closing edge is ever temporarily installed.

* Continuation-safe cleanup

An installed wait edge is scoped with Scheme =dynamic-wind= or an equivalent
guaranteed unwind boundary:

#+begin_src text
before: install the already-approved wait edge
during: suspend until the target publishes or context closes
after:  remove the wait edge exactly once
#+end_src

The =after= path runs on normal wake, structured exception, continuation escape,
and context close.  A later continuation resumption rechecks context, target,
and token state; it cannot restore the removed edge.

Edge removal is idempotent for cleanup but does not make edge installation
repeatable.  A stale or foreign cleanup token produces a runtime-control
condition rather than removing another evaluation's edge.

Waiter wake order is not semantic and no FIFO guarantee is required.  All
waiters observe the same immutable target outcome.

* Bounded analysis

Wait-graph traversal is bounded by the 45-04
=maxActiveEvaluationCells= limit and by the lineage-depth limit.  If analysis
cannot complete within a configured hard limit, POO Flow raises
=EvaluationResourceLimitCondition= for the affected operation.  It MUST NOT
guess that a cycle exists.

The cycle diagnostic contains:

#+begin_src text
breakerEvaluationId
ModuleCapabilityTargetAddress
lineagePath
waitGraphPath
truncated
observedDepth
#+end_src

45-04 owns the detached snapshot projection, truncation presentation, and event
retention.  This module owns only discovery of the bounded causal paths.

* Failure scope

| Phase | Condition | Recovery |
|-
| internal G0 | =QualificationCycleCondition= | abort initialization or replace context |
| active composition | =CompositionDemandCycleCondition= | abort current composition |

An active composition cycle does not revoke the already-qualified core
capability.

Direct G0 re-entry and a G0 cross-branch wait cycle both produce
=QualificationCycleCondition=.  Active Profile/Mix/submodule capability cycles
produce =CompositionDemandCycleCondition=.

The cycle breaker unwinds only its owning phase.  Dependent waiters wake from
the published operational failure.  POO Flow does not force unrelated cells to
failed and does not reset the runtime context.

* Recursive submodule propagation

A-to-B-to-C nesting derives one frame per POO Flow-owned capability boundary:

#+begin_mermaid
flowchart LR
    A["A capability frame"] --> B["A imports B"]
    B --> C["B capability frame"]
    C --> D["B imports C"]
    D --> E["C capability frame"]
#+end_mermaid

There is no architecture-level maximum submodule depth.  Runtime diagnostic
capture remains bounded by the configured safety limit.  Descendants share the
active runtime context and never create another parent G0 cell.

* Fixed-point and dependency boundary

Pinned =gerbil-poo= owns structural POO fixed-point, self/super, lazy slot
cache, and prototype composition.  This module neither wraps arbitrary =.ref=
nor implements a second fixed-point evaluator.

The only instrumented demand is =resolve-module-capability= from 45-06.  A
future upstream generic slot-demand hook would be a separate optional
observability enhancement, not a requirement of this cycle contract.

GSLPH may run direct, nested, concurrent, continuation, cleanup, and
resource-limit fixtures.  It does not propagate lineages, own the graph, choose
the breaker, or issue conditions.

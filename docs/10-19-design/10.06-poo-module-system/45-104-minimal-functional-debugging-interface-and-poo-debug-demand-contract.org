#+title: Minimal Functional Debugging Interface and POO DebugDemand Contract

* Status

Accepted architecture RFC.

This document fixes the minimal user-facing debugging interface. It does not
authorize implementation work and does not claim that current selectors already
implement this contract.

* Scope

This RFC defines:

- ordinary Scheme function forms for =inspect=, =explain=, =diff=, and
  =simulate=;
- pure POO DebugDemand construction;
- explicit admitted DebugEvaluationContext evaluation;
- canonical query objects and advanced POO query extension;
- result and rendering separation;
- REPL and tooling adapter boundaries;
- macro governance and failure behavior.

This RFC does not define:

- a debugging clause DSL;
- keyword-based query syntax;
- a public debugging macro;
- an ambient global snapshot;
- an ambient global authority context;
- a direct commit or resume function;
- raw alist or record query values;
- compatibility, migration, or deprecation behavior;
- implementation edits.

* Evidence state

Parser-owned searches of current Module and composition owners emit no verified
public selectors for:

- inspect;
- explain;
- diff;
- simulate;
- debug session;
- DebugDemand;
- DebugEvaluationContext;
- result rendering;
- condition proposals.

The current owner route fails with:

#+begin_example
provider owner-search-stdin failed: status=exit status: 2 stderr=
#+end_example

Broader Gerbil Scheme discovery is also blocked by an unpublished provider
source envelope.

Therefore the current call forms, ambient context behavior, result shape, and
render coupling remain =MISSING=.

This RFC defines the target functional interface without preserving an
unverified current surface.

* Central decision

The ordinary user interface is:

#+begin_src scheme
(inspect snapshot)
(explain judgment)
(diff before after)
(simulate snapshot proposal)
#+end_src

Advanced queries remain ordinary function calls with POO values:

#+begin_src scheme
(inspect snapshot query)
(explain judgment question)
(diff before after query)
(simulate snapshot proposal)
#+end_src

There is no additional wrapper, public macro, keyword clause, or generic query
language.

The functions construct pure POO DebugDemand values. An admitted evaluator
applies an explicit DebugEvaluationContext and returns a POO evidence result.

* Why functions construct demands

A user call identifies a semantic debugging request but does not itself possess:

- read authority;
- simulation authority;
- continuation authority;
- commit authority;
- redaction policy;
- runtime budgets;
- session retention policy.

Constructing a demand keeps the user interface short while keeping authority
explicit at evaluation.

#+begin_example
ordinary function call
  -> immutable POO DebugDemand
  -> admitted DebugEvaluationContext
  -> pure evaluation
  -> POO evidence result
#+end_example

The demand is a first-class value and composes through the normal POO Flow
functional route.

* DebugDemand

A DebugDemand is a native POO object that projects:

- demand identity;
- operation identity;
- input snapshot identities;
- query, question, or proposal identity;
- requested evidence profile;
- requested budget;
- source and session correlation identity;
- observation dependencies;
- optional continuation condition identity.

A demand contains no capability grant.

It may contain a capability request or required-scope declaration, but actual
authority belongs to DebugEvaluationContext admission.

* DebugEvaluationContext

DebugEvaluationContext is an explicit POO value supplied by the admitted
evaluator.

It projects:

- principal and session identity;
- read capability;
- simulation capability;
- continuation capability when present;
- commit authority status, which debugging never consumes;
- redaction policy;
- maximum budgets;
- retention policy;
- observation boundary;
- evaluator and policy versions;
- isolated simulation cache namespace.

The context is not a global parameter hidden behind the user functions.

An admitted outer POO Flow evaluation may close over the context
functionally. The semantic evaluator still receives it as an explicit value.

* Inspect forms

** Ordinary inspect

#+begin_src scheme
(inspect snapshot)
#+end_src

This form uses a canonical typed summary query object.

The canonical query object is inherited from the inspection-query prototype. It
is not a missing argument interpreted by a macro.

** Advanced inspect

#+begin_src scheme
(inspect snapshot query)
#+end_src

=query= is a POO inspection-query object.

Advanced authors extend the query prototype with native POO operations and pure
functional combinators.

A list of fields, keyword clauses, strings, or raw predicate lambda is not the
ordinary extension interface.

* Explain forms

** Ordinary explain

#+begin_src scheme
(explain judgment)
#+end_src

This form uses a canonical question object for the current judgment.

** Advanced explain

#+begin_src scheme
(explain judgment question)
#+end_src

=question= is a POO explanation-question object.

It may target selection, shadowing, conflicts, constraints, capabilities,
cycles, budgets, cache invalidation, or recovery alternatives.

The question object names semantic identities. It does not contain an
unstructured natural-language query as semantic truth.

* Diff forms

** Ordinary diff

#+begin_src scheme
(diff before after)
#+end_src

This form compares the complete visible semantic projections of two compatible
snapshots.

** Advanced diff

#+begin_src scheme
(diff before after query)
#+end_src

=query= is a POO diff-query object that narrows the comparison without changing
the input snapshots.

An advanced query cannot hide a change required by the result's completeness
contract. Omitted categories remain explicit in result metadata.

* Simulate form

#+begin_src scheme
(simulate snapshot proposal)
#+end_src

Simulation has no proposal-free form.

=proposal= is a POO counterfactual proposal object. Its prototype identifies the
proposal family and required simulation capability.

No third argument supplies commit, apply, resume, or authorization behavior.

* Canonical query objects

Canonical ordinary queries are typed POO objects:

- inspection summary query;
- current-judgment explanation question;
- complete visible diff query.

They are:

- immutable after publication;
- identity-bearing;
- capability-neutral;
- inherited through query prototypes;
- replaceable by explicit advanced query objects;
- visible in demand and result receipts.

There is no canonical default simulation proposal.

* Query and proposal extension

Advanced extension uses:

- native POO prototypes;
- object extension and composition;
- named pure functional combinators;
- typed capability requirement objects;
- bounded evidence projections.

An extension may add:

- a new inspection projection;
- a new explanation question family;
- a new diff comparison dimension;
- a new counterfactual proposal family.

It may not add:

- hidden authority;
- unbounded traversal;
- runtime effects;
- commit behavior;
- raw host callbacks;
- an open keyword parser.

* Demand evaluation

Conceptually:

#+begin_example
evaluate-debug-demand(context, demand) -> evidence result or typed condition
#+end_example

The exact Scheme identifier is not frozen by this RFC.

The evaluator is a pure function over:

- immutable context;
- immutable demand;
- immutable semantic snapshots;
- explicit observation inputs.

Runtime acquisition of the input snapshots and capabilities occurs before this
pure evaluation boundary.

* Function and result correspondence

| Function | Demand operation | Result prototype |
|----------+------------------+------------------|
| =inspect= | inspection | inspection evidence |
| =explain= | explanation | explanation graph |
| =diff= | semantic comparison | semantic diff |
| =simulate= | counterfactual evaluation | simulation result |

The function name does not select rendering or output transport.

* Rendering boundary

Rendering is a separate adapter:

#+begin_example
POO evidence result + renderer -> presentation
#+end_example

A renderer may produce:

- REPL display;
- Org report;
- Mermaid graph;
- terminal text;
- structured protocol projection;
- bounded machine-readable receipt.

Rendering:

- receives no commit authority;
- cannot alter evidence;
- preserves result identity;
- makes redaction visible;
- does not become a semantic cache input.

* REPL behavior

A REPL or tooling adapter may submit a DebugDemand immediately and render the
returned evidence.

The semantic sequence remains visible:

#+begin_example
construct demand -> admit context -> evaluate -> render
#+end_example

The REPL does not:

- obtain an implicit current snapshot;
- infer an unrestricted principal;
- reuse an expired capability;
- auto-commit a simulation;
- auto-resume a continuation;
- hide demand or result receipts.

* No ambient current snapshot

Every user call includes its snapshot or judgment input explicitly.

This avoids:

- session drift;
- confusion between current and simulated revision;
- accidental cross-thread inspection;
- stale cache lookup;
- hidden authority escalation;
- unreplayable debugging commands.

A tooling adapter may offer a visible selected snapshot binding. That binding
is still an ordinary explicit POO value passed to the function.

* No ambient authority

The ordinary functions do not read a global current capability.

Authority enters only through DebugEvaluationContext admission.

Lexical closure over an admitted context is allowed inside an owning functional
evaluation, but:

- the closed context identity is visible;
- scope cannot widen;
- demand receipts identify the context;
- serialization does not capture live authority;
- replay requires fresh admission.

* Conditions and continuations

Evaluation may return or raise a typed continuable condition.

The condition may carry:

- demand identity;
- partial evidence;
- missing capability or evidence;
- consumed budget;
- recovery proposal prototypes;
- live continuation identity;
- portable suspension descriptor.

The ordinary user functions do not resume the condition.

An authorized recovery evaluator accepts a POO proposal and continuation
capability through the condition plane defined by the owning RFCs.

* Debug interface graph

#+begin_src mermaid
flowchart LR
  User["ordinary Scheme call"] -->|"constructs pure value"| Demand["POO DebugDemand"]
  Snapshot["explicit immutable snapshot"] -->|"is referenced by identity"| Demand
  Query["canonical or advanced POO query"] -->|"defines bounded request"| Demand
  Context["admitted DebugEvaluationContext"] -->|"supplies scope, budget, and redaction"| Evaluate["pure demand evaluator"]
  Demand -->|"contains no authority"| Evaluate
  Evaluate -->|"returns identity-bearing semantics"| Evidence["POO evidence result"]
  Evaluate -->|"returns typed failure when incomplete"| Condition["POO condition"]
  Evidence -->|"projects through separate adapter"| Render["REPL / Org / Mermaid renderer"]
  Condition -->|"accepts authorized proposal only"| Recovery["recovery evaluator"]
  Recovery -->|"creates new demand or revision receipt"| Evaluate
#+end_src

No edge from Render returns to semantic state.

* Evaluation sequence

#+begin_src mermaid
sequenceDiagram
  participant User as "user"
  participant Function as "inspect / explain / diff / simulate"
  participant Demand as "DebugDemand"
  participant Admit as "context admission"
  participant Eval as "pure evaluator"
  participant Result as "POO evidence"
  participant Render as "presentation adapter"

  User->>Function: "passes explicit POO inputs"
  Function-->>Demand: "returns immutable demand"
  Demand->>Admit: "requests scoped evaluation"
  Admit->>Eval: "supplies explicit context and snapshots"
  Eval-->>Result: "returns evidence or typed condition"
  Result->>Render: "supplies identity-bearing result"
  Render-->>User: "shows bounded presentation"
#+end_src

User-interface simplicity does not erase the authority boundary.

* Macro governance

The four public operations are functions, not macros.

Functions and native POO objects remain the default abstractions.

A tooling-only macro may be admitted later only when it:

- captures source location hygienically;
- expands directly to one of the four functions;
- supplies no hidden snapshot or context;
- owns no query semantics;
- performs no evaluation, commit, render, or resumption;
- has an independently reviewed RFC.

This RFC introduces no such macro.

* Semantic laws

** Functional-construction law

Each public operation constructs one immutable POO DebugDemand.

** Explicit-input law

Snapshots, judgments, queries, and proposals are explicit values.

** Explicit-context law

Evaluation authority and budgets arrive through DebugEvaluationContext.

** No-global-state law

No semantic operation depends on a global current snapshot, principal, or
capability.

** Typed-default law

Ordinary optional queries use canonical typed POO objects.

** No-default-proposal law

Simulation always receives an explicit proposal.

** Pure-evaluation law

Demand evaluation is pure over immutable admitted inputs.

** Rendering separation law

Presentation is not evidence and cannot alter semantic results.

** Authority separation law

Demand construction, read admission, simulation, continuation, and commit
remain distinct.

** Macro-minimality law

The public debugging interface requires no macro.

** Fail-closed law

Invalid input kinds, missing scope, insufficient budgets, or unavailable
evidence return typed conditions or rejections.

* Evidence projection

A DebugDemand receipt identifies:

- function and demand identities;
- explicit input snapshot identities;
- canonical or advanced query identity;
- proposal identity when present;
- requested evidence profile and budget;
- source location;
- absence of embedded authority.

An evaluation receipt identifies:

- DebugEvaluationContext identity;
- admitted capability scopes;
- redaction and retention policy;
- evaluator and policy versions;
- demand and snapshot identities;
- result or condition identity;
- consumed budget;
- cache namespace;
- non-mutation and non-publication evidence.

A rendering receipt may identify presentation format and renderer version, but
it does not replace the evaluation receipt.

* Failure behavior

Demand construction fails closed when:

- snapshot or judgment input is not a POO value;
- query or proposal has the wrong prototype;
- diff inputs are structurally unidentifiable;
- a simulation proposal is missing;
- a raw list, alist, keyword clause, or lambda is used as the ordinary query
  interface.

Evaluation fails closed when:

- DebugEvaluationContext is absent;
- capability scope is insufficient;
- redaction cannot preserve honesty;
- budgets are missing or exceeded;
- snapshot revisions are stale or incompatible;
- simulation attempts runtime or publication effects;
- result identity or provenance is incomplete.

Every failure identifies the function, demand, input object, expected
prototype, missing context, and permitted next actions.

* Rejected alternatives

The following alternatives are rejected:

- =(debug (inspect ...) (format ...))= wrapper syntax;
- a public =debug!= macro;
- keyword query clauses;
- raw field-name lists;
- generic alist query records;
- hidden current-snapshot parameters;
- hidden global capability context;
- automatic simulation commit;
- automatic condition resumption;
- renderers that mutate evidence;
- one polymorphic =debug= operation replacing the four clear functions;
- compatibility wrappers around unsafe current debug commands.

* Conformance checklist

** Ordinary interface

- [ ] =inspect= is an ordinary function.
- [ ] =explain= is an ordinary function.
- [ ] =diff= is an ordinary function.
- [ ] =simulate= is an ordinary function.
- [ ] Ordinary forms are short and flat.
- [ ] No wrapper form is required.
- [ ] No public debugging macro is introduced.
- [ ] No keyword query DSL is introduced.

** DebugDemand

- [ ] Every call returns a POO DebugDemand.
- [ ] Demand identity is explicit.
- [ ] Operation identity is explicit.
- [ ] Snapshot identities are explicit.
- [ ] Query or proposal identity is explicit.
- [ ] Requested budget is explicit.
- [ ] Demands contain no capability grant.
- [ ] Demands are immutable.

** Query and proposal objects

- [ ] Ordinary inspect uses a typed summary query.
- [ ] Ordinary explain uses a typed current question.
- [ ] Ordinary diff uses a typed complete-visible query.
- [ ] Simulation requires an explicit proposal.
- [ ] Advanced queries extend POO prototypes.
- [ ] Raw lists and alists are rejected.
- [ ] Raw predicate lambdas are not the ordinary interface.
- [ ] Query extension grants no authority.

** Evaluation context

- [ ] DebugEvaluationContext is explicit to the evaluator.
- [ ] Principal and session identity are explicit.
- [ ] Read capability is explicit.
- [ ] Simulation capability is explicit.
- [ ] Continuation capability remains distinct.
- [ ] Commit authority is not consumed.
- [ ] Redaction and retention policies are explicit.
- [ ] Budgets and cache namespace are explicit.

** Purity and rendering

- [ ] Evaluation uses immutable inputs.
- [ ] Evaluation is pure.
- [ ] Simulation publishes no state.
- [ ] Results are POO evidence objects.
- [ ] Rendering is a separate adapter.
- [ ] Renderings preserve result identity.
- [ ] Renderers receive no commit authority.
- [ ] Renderings cannot re-enter as semantic truth.

** Sessions and recovery

- [ ] No global current snapshot is semantic.
- [ ] No global current capability is semantic.
- [ ] Tool-selected snapshots remain explicit POO bindings.
- [ ] REPL adapters expose demand and result receipts.
- [ ] User functions do not resume conditions.
- [ ] Recovery proposals use the condition plane.
- [ ] Replay requires fresh context admission.

** Macro governance

- [ ] Functions and POO objects remain default abstractions.
- [ ] This RFC introduces no macro.
- [ ] Any future tooling macro requires a separate RFC.
- [ ] A tooling macro supplies no hidden context.
- [ ] A tooling macro owns no query or evaluation semantics.
- [ ] Macro expansion targets ordinary functions.

** Evidence

- [ ] Demand receipts identify functions and inputs.
- [ ] Demand receipts prove absence of authority.
- [ ] Evaluation receipts identify context and capabilities.
- [ ] Evaluation receipts identify result or condition.
- [ ] Receipts identify budgets and cache namespace.
- [ ] Rendering receipts remain subordinate.
- [ ] Failures identify expected POO prototypes.
- [ ] Failures expose permitted next actions.

* Implementation admission gates

Implementation work is not admitted until:

- [ ] the Gerbil Scheme source envelope is published;
- [ ] current debug/session/context selectors are identified;
- [ ] current ambient-state behavior is audited;
- [ ] current result/render coupling is audited;
- [ ] DebugDemand prototype is specified;
- [ ] DebugEvaluationContext prototype is specified;
- [ ] canonical query prototypes are specified;
- [ ] pure evaluator signature is specified;
- [ ] ordinary and advanced arity tests are specified;
- [ ] no-global-state tests are specified;
- [ ] capability separation tests are specified;
- [ ] simulation non-publication tests are specified;
- [ ] rendering separation tests are specified;
- [ ] condition and recovery integration tests are specified;
- [ ] the RFC set is reviewed before implementation begins.

* Consequences

The user interface remains as simple as four ordinary Scheme function calls.

POO values carry every advanced query, proposal, capability requirement, and
evidence extension.

Authority and budgets remain explicit at evaluation without burdening the
ordinary call syntax or introducing macro and clause proliferation.

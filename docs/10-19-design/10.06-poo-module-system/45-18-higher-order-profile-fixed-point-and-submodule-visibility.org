#+title: Higher-Order Profile Fixed Point and Submodule Visibility
#+startup: overview

* Status

Normative RFC.

* Scope

This RFC owns higher-order Profile participation, textual composition order,
lazy global Capability resolution, and visibility across arbitrarily nested
submodules.

* Uniform higher-order Profile

A contextual extension is an ordinary Profile operand:

#+begin_src scheme
(compose profiles
  wendao-episteme
  research-policy
  production)
#+end_src

=research-policy= is a first-class higher-order POO object whose prototype owns
its imports, identity, capabilities, and extension behavior.  It is authored
with =defprofile=, not =defpolicy=, =defconditional-profile=, a kind tag, or a
conditional Profile DSL.

Raw =if=, =cond=, and =case= forms are not direct operands of the public
=compose profiles= surface.  Contextual behavior is expressed by ordinary
higher-order POO Profile operands.

* Capability-directed higher-order refinement

A higher-order Profile targets a POO Capability contract and prototype lineage,
not a Profile macro name, module name, string, or registry entry.

=research-policy= receives the target's ordered predecessor Capability view and
imports every context or policy Capability required by its semantics.  It
provides a refinement Capability in the target's prototype lineage.  The
global fixed point connects ordinary imports and the contribution through
Capability identity and lineage.

Consequently, the policy can refine any implementation satisfying the same
Capability contract; it is not coupled to the spelling
=wendao-episteme=.  A missing target produces a missing-Capability condition.
Unrelated singleton providers follow
[[file:45-19-capability-ambiguity-resolution-overlay-and-replay.org][the
Capability ambiguity contract]].

* Predecessor view and global imports

The target predecessor view and an ordinary Capability import have different
resolution semantics:

- the predecessor view is determined by textual composition order and the
  target prototype lineage;
- an ordinary import is resolved by the lazy global fixed point and may be
  provided by a later-written Profile.

A higher-order refinement receives only the target state preceding its own
contribution.  It does not import or demand the final target Capability that
already contains its output.  It then derives a same-lineage refinement as a
pure POO extension.

The public interface exposes no raw =(lambda (self super) ...)= hook.
Predecessor or super behavior belongs to the native POO prototype mechanism,
not a patch DSL or another evaluator.  A missing predecessor produces a
missing-target condition.  Cycles through ordinary context imports follow the
normal fixed-point and cycle contract.

* Lineage and contribution identity

Same-lineage refinement does not collapse all contributions into one identity.
The composition distinguishes:

- target prototype-lineage identity inherited from the predecessor;
- refinement contribution identity owned by the concrete policy or refinement
  declaration;
- runtime POO identity of a concrete realization;
- canonical causal or content identity derived from lineage, contribution, and
  relevant context-input provenance.

Context inputs affect canonical causality and content but do not replace or
fork the target prototype lineage.  A repeated contribution identity in the
same composition lineage raises a duplicate-contribution condition rather than
executing silently twice.  Different contribution identities remain distinct,
ordered refinements even when they happen to produce similar values.

Textual order determines the order of distinct contributions.  Evidence
correlates lineage, contribution, context inputs, and runtime realization
without treating any of them as interchangeable.

Identity representation uses native =gerbil-poo= object capabilities and
[[file:45-15-receipt-object-canonical-evidence-projection.org][the canonical
evidence contract]].  POO Flow introduces no string-based identity system.

* Instance-scoped duplicate contributions

Duplicate contribution detection is scoped by root identity, submodule instance
identity, target prototype-lineage identity, contribution identity, and demand
generation.

Applying the same policy once in each of two distinct submodule instances is
legal.  Applying the same contribution twice to the same lineage in the same
instance and generation raises a duplicate-contribution condition.

Graph reachability is not application.  One contribution visible through two
import or export paths is a shared alias and remains one contribution node.
Re-export preserves that node and does not create a new contribution identity.
This rule prevents diamond-shaped module graphs from being misclassified as
duplicate refinement.

A successor generation may realize the contribution again without becoming a
duplicate in the previous generation; evidence records the causal relation.
A child that explicitly authors a new refinement contribution requires a new
contribution identity rather than masquerading as an inherited alias.

Detection uses POO graph identity and contribution-application events, never
module-name or path strings.

* Submodule instance identity

Submodule identity distinguishes:

- child prototype identity;
- embedding-edge identity owned by the parent Capability or contribution;
- canonical causal instance identity combining parent causality, embedding
  edge, child prototype, and an explicit multiplicity key when required;
- runtime instance identity of the concrete object in the current root or
  context.

Instantiating one child prototype twice produces distinct runtime instance
identities.  Alias and re-export preserve the existing instance rather than
instantiating again.  A fresh replay root may realize the same canonical causal
instance identity as a new runtime object.

Moving a child under a different parent changes canonical causal instance
identity because its causal parent changed.  Identity does not depend on
mutable display paths, module names, or collection ordinals.

A multi-instance Capability contract supplies an explicit POO-native element
identity or key.  List position is not an identity mechanism.  Canonical
identity supports provenance, replay, and graph correlation; it never replaces
live runtime POO identity and requires no submodule registry.

* Demand-lazy submodule realization

Parent composition declares a child prototype, embedding edge, and canonical
causal instance identity.  Declaration does not eagerly realize every child
runtime instance.

The first demand for an exported child Capability asks native =gerbil-poo= to
realize that child in the current root and generation.  Repeated demands for
the same instance identity in that root and generation observe the same POO
realization.  Alias and re-export reach that realization rather than creating a
copy.  A child that is never demanded remains unrealized.

Submodule realization is pure POO evaluation.  External effects cross explicit
runtime or Marlin boundaries.  Re-entrant demand follows the existing
cycle/progress condition contract.

POO Flow records demand, identity, generation, and lineage evidence around the
sole =gerbil-poo= evaluator.  It MUST NOT add a second lazy cache, realization
registry, or evaluator.  Exact sharing mechanics remain subject to pinned
=gerbil-poo= API evidence.

* Order and fixed point

Textual order determines deterministic POO refinement and override precedence.
It is not initialization order and does not constrain Capability availability.
All operands enter one logical lazy global POO fixed point.  A later-written
Profile may satisfy an import demanded by an earlier-written Profile; users do
not topologically sort operands.

* Nested submodule visibility

Parent, child, and nested-child modules participate in the same logical fixed
point.  Visibility is constrained by explicit POO imports, exports, and
Capability projection.

A parent Capability reaches a child only through export.  A nested child sees
it only after re-export.  Child-local state does not leak upward or laterally
to siblings.

#+end_src

* Conformance checklist

- [ ] Higher-order contextual extensions are ordinary Profile operands.
- [ ] No conditional Profile DSL or macro-level kind classification exists.
- [ ] Higher-order Profiles target Capability contracts and prototype lineage,
  never Profile names, module names, strings, or registry entries.
- [ ] Policy target input is an ordered predecessor Capability view.
- [ ] Policy context inputs are ordinary global fixed-point imports.
- [ ] A policy never demands a final target Capability containing its own
  contribution.
- [ ] Policy output is a same-lineage POO refinement Capability.
- [ ] The public surface exposes no raw self/super lambda hook or patch DSL.
- [ ] Prototype lineage, contribution, runtime, and canonical causal identities
  remain distinct.
- [ ] Context inputs affect canonical causality without replacing target
  lineage.
- [ ] Repeating one contribution identity in the same lineage raises a
  duplicate-contribution condition.
- [ ] Duplicate detection is scoped by root, submodule instance, target
  lineage, contribution, and generation.
- [ ] The same policy may be applied independently in distinct submodule
  instances.
- [ ] Diamond import or export reachability remains one alias node rather than
  a duplicate application.
- [ ] Re-export preserves contribution identity, while a newly authored child
  refinement requires a new contribution identity.
- [ ] Successor-generation realization is causally linked rather than treated
  as a prior-generation duplicate.
- [ ] Child prototype, embedding edge, canonical causal instance, and runtime
  instance identities remain distinct.
- [ ] Alias and re-export preserve an existing instance; repeated
  instantiation creates a new runtime identity.
- [ ] Fresh replay realizes canonical causality in a new runtime object.
- [ ] Moving a child to a different parent changes canonical causal instance
  identity.
- [ ] Multi-instance contracts provide explicit POO-native keys rather than
  list positions.
- [ ] Submodule identity uses neither display paths, module names, ordinals,
  nor a registry.
- [ ] Parent composition declares child prototypes and embedding identity
  without eager child realization.
- [ ] First Capability demand realizes a child through native =gerbil-poo=.
- [ ] Same-instance repeated demand, alias, and re-export observe one runtime
  realization in the same root and generation.
- [ ] Unused submodules remain unrealized.
- [ ] Submodule realization remains pure and crosses explicit boundaries for
  effects.
- [ ] POO Flow adds no lazy cache, realization registry, or replacement
  evaluator.
- [ ] Distinct contribution identities remain ordered refinements even when
  their produced values appear similar.
- [ ] Identity uses native POO objects and canonical evidence rather than
  strings.
- [ ] Missing targets and unrelated singleton providers produce structured
  Capability conditions.
- [ ] Textual order affects precedence, not Capability availability.
- [ ] Later providers may satisfy earlier imports.
- [ ] Nested submodules require explicit export and re-export.
- [ ] Child-local state does not leak to parents or siblings.
- [ ] POO Flow does not implement a replacement fixed-point evaluator.

#+title: Canonical POO Resolver, Resolution Proposal, and Recovery Authority
#+subtitle: Pure policy evaluation, live authorization, and deterministic conflict recovery
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative design module
- Semantic core :: =gerbil-poo= objects and POO Flow evaluation
- Related modules :: =45-41-poo-profile-slot-contribution-priority.org= and =45-42-poo-conflict-recovery-generation-resumption.org=

This module separates pure conflict-resolution policy from live recovery authority. A resolver may propose a semantic change, but it cannot authorize or apply that change.

* Core decision

#+begin_quote
A canonical resolver is a pure, deterministic, identity-addressed higher-order POO object that produces a =ResolutionProposal=. A live recovery portal independently validates the proposal and seals an admitted =RecoveryDecision=. Resolver policy and recovery authority are never the same object.
#+end_quote

The canonical flow is:

#+begin_src text
ConflictEvidence
-> ResolutionProposal
-> live authorization
-> RecoveryDecision
-> new composition generation
#+end_src

* Pure resolver input

A resolver may receive:

- pure conflict evidence;
- canonical candidate projections;
- its own POO semantic identity;
- immutable policy parameters;
- a pure composition-context identity;
- the semantic slot and conflict class declared by its scope.

A resolver must not receive:

- a live recovery portal;
- a continuation or resumption;
- a capability token or lease;
- mutable evaluator state;
- an unprojected runtime resource;
- a global resolver registry;
- ambient authority inferred from the handler process.

The resolver evaluates policy only. It does not mutate a generation, resume a continuation, or consume recovery authority.

* Resolution proposal

A resolver returns a pure POO =ResolutionProposal= or a pure decline result.

A proposal may describe:

- a priority adjustment for an identified contribution;
- replacement or removal of an identified contribution;
- an explicitly constructed Profile operand identity;
- a canonical native POO operation admitted for the projected values;
- explicit termination of the composition.

A proposal is not a raw callback and does not contain authority to apply itself. Every semantic reference inside a proposal must be identity-addressed and carry enough provenance to explain its origin.

When a resolver is not applicable, it returns an explicit pure decline result. It must not use an exception, implicit fallback, or presentation-order selection to mean "decline."

* Proposal and decision separation

The live recovery portal validates a proposal against the current generation:

- the resolver is admitted for the semantic slot and conflict class;
- the proposal remains inside its capability and authority scope;
- the proposal changes the conflicting semantic identity;
- the proposal does not enlarge authority;
- the root-demand recovery budget permits another transition;
- the resolver and policy identities remain admitted;
- the referenced operands and operations still belong to the current composition context.

Only a proposal that passes validation becomes a sealed =RecoveryDecision=.

* Canonical resolver laws

A canonical resolver satisfies:

- Determinism :: The same resolver identity, conflict identity, and policy-context identity produce the same proposal or decline.
- Permutation invariance :: Candidate presentation order does not change the result.
- Explicit decline :: An unsupported conflict produces a pure decline value.
- No authority fabrication :: A proposal cannot create or enlarge capability or authority.
- Bounded demand :: Resolver evaluation does not force dormant business values.
- Identity completeness :: Algorithm version, policy parameters, declared scope, and relevant semantic dependencies participate in resolver identity.
- No hidden mutation :: Resolver output is a new pure POO value.
- Loop visibility :: An equivalent proposal for the same conflict has the same semantic identity and can be detected as a recovery loop.
- Evidence completeness :: The resolver can explain which pure inputs caused each proposed semantic change.

"Canonical" does not mean universally correct or globally privileged. It means that the resolver produces one identity-addressed, explainable, presentation-order-independent result for the same pure input.

* Resolver authority bootstrap

A conflicting contribution must not grant authority to the resolver that decides its conflict. Otherwise a candidate could install a resolver that selects itself.

Resolver authority therefore:

- comes from an independently admitted control Profile or composition strategy;
- is established before evaluation of the business slot conflict;
- is scoped to declared semantic slots and conflict classes;
- is not dynamically elected from the conflicting contributions;
- cannot be enlarged by the resolver's own proposal.

* Multiple resolver conflicts

Overlapping resolver scopes are resolved in the control-plane composition before business-slot evaluation.

- Explicit prototype construction may construct one control Profile before it enters composition.
- A resolver must not recursively invoke another resolver to decide resolver selection.
- Operand order must not choose between overlapping resolvers.
- If the control plane cannot establish one canonical resolver policy, it fails closed with resolver-conflict evidence.
- Resolver-conflict recovery requires a new externally admitted control composition, not recursive use of the conflicted resolver set.

This boundary prevents an infinite meta-resolution tower.

* Cache boundary

A pure resolver result may be cached under:

#+begin_src text
resolver semantic identity
+ conflict evidence identity
+ pure policy-context identity
#+end_src

Cacheable values include:

- a =ResolutionProposal=;
- a decline result;
- pure resolver-evaluation evidence.

Non-cacheable values include:

- a live recovery portal;
- a capability or lease;
- an authorization result reused as authority;
- a continuation or resumption;
- consumed recovery authority;
- mutable evaluator state.

Retrieving a cached proposal never authorizes it. The current live recovery portal must repeat capability, scope, identity, and budget validation.

* Resolver evidence

Pure resolver-evaluation evidence records:

- resolver semantic identity;
- declared slot and conflict scope;
- conflict evidence identity;
- canonical candidate-projection identities;
- policy-context identity;
- proposal or decline identity;
- the causal policy rule that produced the result;
- evaluation budget consumption;
- whether the result came from a validated cache projection.

Recovery authorization evidence separately records admission or rejection. It references the proposal identity without serializing the live portal or authority token.

* Public-interface constraint

The ordinary user interface remains:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    base
    wendao-episteme
    production))
#+end_src

A resolver is an advanced POO object introduced through an independently admitted Profile or composition-strategy extension. It does not add a =:resolver= clause, a recovery DSL, a public domain macro, or a raw =(lambda (self super) ...)= hook.

Concrete prototype operations and resolver construction helpers must be based on verified native =gerbil-poo= interfaces. This RFC does not invent a parallel resolver object system.

* Implementation checklist

- [ ] Define pure POO =ResolutionProposal= and explicit decline objects.
- [ ] Define canonical identities for resolver algorithm, version, parameters, and scope.
- [ ] Restrict resolver inputs to pure canonical projections.
- [ ] Verify deterministic and permutation-invariant resolver output.
- [ ] Verify that dormant business values are not forced.
- [ ] Prevent proposal objects from containing capability, authority, continuation, or mutable state.
- [ ] Establish resolver authority independently of business conflict candidates.
- [ ] Reject resolver self-authorization.
- [ ] Resolve overlapping resolver scopes in control-plane composition.
- [ ] Fail closed when no canonical resolver policy can be established.
- [ ] Prevent recursive resolver selection and meta-resolution towers.
- [ ] Cache only pure proposals, declines, and resolver evidence.
- [ ] Revalidate every cached proposal through the current live recovery portal.
- [ ] Seal an admitted proposal as a =RecoveryDecision= before deriving a new generation.
- [ ] Generate separate resolver-evaluation and recovery-authorization evidence.
- [ ] Validate final object operations against real =gerbil-poo= primitives.

* Non-goals

- Do not give a resolver live recovery authority.
- Do not let a proposal apply itself.
- Do not select resolvers from the conflict candidates they decide.
- Do not create a resolver registry or closed resolver enumeration.
- Do not recursively invoke resolvers to resolve resolver conflicts.
- Do not expose raw callbacks as the ordinary resolver interface.
- Do not cache capability, authorization, continuation, or portal state.
- Do not add a resolver macro or recovery DSL.

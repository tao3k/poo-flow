#+title: Continuable Exception, Resumption Option, and Handle Lifecycle
#+author: POO Flow
#+language: en

* Status

Accepted.

* Context

Scheme continuable exceptions and first-class continuations can expose recovery
at the point where evaluation still has useful semantic context.  Unconstrained
continuations can also retain large object graphs, escape dynamic resource
scopes, repeat effects, re-enter stale generations, or bypass capability and
budget checks.

POO Flow therefore separates the pure semantic resumption option from the raw
runtime continuation handle.

* Decision

A continuation may be captured only at a named runtime recovery boundary.

The boundary publishes a POO-native =ResumptionOption= while the raw
continuation remains in a coordinator-owned ephemeral handle registry.

=ResumptionOption= is an independent =ObjectType= prototype family whose base
responsibilities are:

- originating evidence;
- evaluation generation;
- input Contract;
- result Contract;
- authority requirement;
- typed budget request;
- expiry Contract.

The initial refinements are:

- =OneShotResumptionOption=;
- =MultiShotResumptionOption=.

The prototype lineage defines invocation multiplicity.  A mutable mode tag is
not the ordinary mechanism.

* Named recovery boundary

Continuation capture MUST be explicit in the runtime coordinator or an
authorized exception bridge.

Ordinary Module composition, profile selection, macro expansion, pure
fixed-point algebra, and terminal projection MUST NOT capture a continuation
implicitly.

The boundary MUST record:

- the originating authoritative observation identity;
- the active evaluation generation;
- source and phase provenance;
- the declared input and result Contracts;
- the applicable authority and budget requirements;
- the selected resumption prototype;
- the handle registration outcome.

* Resumption option

=ResumptionOption= is authoritative semantic evidence that a bounded recovery
path existed at capture time.

It MUST NOT contain:

- a raw continuation;
- a process-local address;
- an executable closure or handle;
- a serialized dynamic environment;
- an unbounded authority token;
- a presentation alist as its canonical representation.

The option identity is the only semantic key connecting evidence to the
ephemeral registry entry.

* Ephemeral handle registry

The registry is coordinator-owned runtime state.  It is distinct from:

- the authoritative evidence store;
- semantic caches;
- runtime telemetry;
- package or build state.

A registry entry binds an option identity to a raw continuation and the minimum
runtime metadata required to enforce its Contract.

The raw handle MUST NOT appear in canonical evidence, receipt projections,
cache keys, telemetry, logs, serialization, or user-facing diagnostics.

The registry MUST fail closed when:

- the handle is unavailable;
- the active generation differs from the option generation;
- authority has been revoked or cannot be revalidated;
- the required budget is unavailable;
- the option has expired;
- a one-shot option has already been claimed;
- a prior invocation has an indeterminate outcome.

* One-shot resumption

=OneShotResumptionOption= is the default refinement.

Invocation requires an atomic claim after accepted coordinator admission.  The
claim prevents concurrent or repeated use of the same handle.

After a successful, failed, or indeterminate invocation attempt, the handle
MUST NOT become available automatically.  The outcome produces immutable
receipt and successor evidence.

* Multi-shot resumption

=MultiShotResumptionOption= is an explicit advanced refinement.  It requires:

- a dedicated multi-shot capability;
- a replay or idempotency Contract for the continuation segment;
- a declared maximum invocation count;
- independent admission and typed budget accounting for every invocation;
- explicit safety obligations for external resources, dynamic scopes, and
  non-reentrant objects;
- an independent successor generation for every invocation;
- termination of further invocation after an indeterminate outcome.

Underlying Scheme support for repeated continuation invocation does not imply
POO Flow authority to expose it.

* Expiry and retirement

An option becomes unavailable when its Contract requires retirement, including:

- successful one-shot claim;
- active generation invalidation;
- capability revocation;
- budget exhaustion;
- enclosing resource-scope invalidation;
- coordinator shutdown or registry loss;
- explicit expiry evidence;
- indeterminate invocation outcome.

Expiry or unavailable-handle discovery MUST produce structured evidence.  It
MUST NOT expose the continuation or silently fall back to a different recovery
path.

* Observability

The registry may produce capability-redacted observation evidence for:

- active handle count;
- handle age and generation;
- capture, claim, invocation, retirement, and expiry counts;
- rejected duplicate invocation;
- cleanup caused by budget or generation invalidation;
- conservative retention-size information when the runtime can provide it.

These observations diagnose continuation leaks and re-entry without exposing
raw handles.  Telemetry receives only audience-safe projections.

* Conformance checklist

- [X] Continuations are captured only at named runtime recovery boundaries.
- [X] =ResumptionOption= is POO-native authoritative evidence.
- [X] Raw continuations remain in a coordinator-owned ephemeral registry.
- [X] Option identity is the only semantic handle correlation key.
- [X] One-shot resumption is the default.
- [X] One-shot invocation requires an atomic claim.
- [X] Multi-shot resumption requires explicit capability, replay Contract,
  invocation bound, and per-invocation budget.
- [X] Stale, expired, unavailable, or indeterminate handles fail closed.
- [X] Handle diagnostics never expose continuation content.
- [X] Module composition and macro expansion do not capture continuations.
- [ ] Concrete exception-bridge and handle-registry source owners have been
  resolved through parser-owned owner discovery.
- [ ] Implementation has been admitted after owner resolution.

* Non-goals

- Exposing raw =call/cc= continuations as user configuration values.
- Assuming that every Scheme continuation is safe for repeated invocation.
- Serializing a continuation or dynamic environment.
- Treating the ephemeral registry as an evidence store or cache.
- Bypassing coordinator admission for local-looking resumptions.
- Defining an implementation schedule.

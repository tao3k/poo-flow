#+title: RFC 149-03 — Promotion Transaction Snapshot And Atomic Materialization Refinement
#+language: en

* Status

This is a Lean-proven refinement of RFC 149, RFC 149-01, and RFC
149-02.

RFC 149 currently joins Cedar, Lean, and Human Audit evidence before
Marlin materialization.  That establishes admission for one subject and
epoch.  It does not establish that the policy, entity, authority, and
runtime snapshots observed during admission are still current when the
effect is committed.

This refinement specifies the proof obligation.  It does not claim that
the Marlin runtime transaction has already been implemented.

* Discovered logical defects

** Admission evidence is vulnerable to time-of-check/time-of-use replay

An accepted admission receipt is a historical fact.  If materialization
checks only its =accepted= field, the same receipt remains eligible after
policy replacement, entity replacement, authority revocation, or a
concurrent runtime update.

Lean proves this counterexample as:

#+begin_src text
admissionReceiptReplaysAfterGovernanceChange
#+end_src

The admission snapshot and the current snapshot are different, while the
old receipt remains accepted.

** AuthorizationSubject does not identify the Human Audit snapshot

RFC 149-01 correctly binds the Cedar request, policy set, entity store,
Bundle, and epoch.  Human authority was refined later by RFC 149-02.
Consequently, two commit subjects can contain the same
=AuthorizationSubject= while referring to different authority snapshots.

Lean proves:

#+begin_src text
authorizationSubjectDoesNotIdentifyAuthoritySnapshot
#+end_src

The transaction subject must therefore extend, rather than weaken, the
dual-engine authorization subject.

** Matching receipt fields do not prove an authorized atomic commit

A receipt can copy the expected transaction identifier, admission
identifier, subject, snapshot, and state digests.  Those equalities do
not prove that the Marlin transaction owner performed an atomic
compare-and-swap or emitted the receipt.

Lean proves:

#+begin_src text
matchingCommitFieldsDoNotProveCommitAuthority
#+end_src

The closure must retain an owner-supplied =CommitReceiptValid= relation.

** Rejection and rollback require state preservation semantics

An outcome label alone is insufficient.  A rejected or rolled-back
transaction must end at its observed pre-state; a committed or duplicate
transaction must end at the exact requested target state.

* Lean countermodels and positive theorems

- =admissionReceiptReplaysAfterGovernanceChange= proves historical
  acceptance does not imply current snapshot equality.
- =authorizationSubjectDoesNotIdentifyAuthoritySnapshot= proves the
  Cedar/Lean subject is not by itself a complete materialization subject.
- =staleAdmissionDoesNotMatchCurrentSnapshot= rejects an admission after
  the authority snapshot and epoch change.
- =atomicCommitRejectsStaleAdmission= rejects the same stale admission at
  the complete transaction closure.
- =matchingCommitFieldsDoNotProveCommitAuthority= keeps Marlin receipt
  validity as an independent owner relation.
- =closedRejectedCommitPreservesPreState= proves fail-closed rejection.
- =closedCommittedCommitReachesExactTarget= proves exact post-state
  binding for a successful commit.

* Mathematical model

The durable mathematical surface is Typst:

#+begin_src typst
$ A = (d_q, d_p, d_e, d_b, n) $

$ C = (A, d_h, d_m) $

$ G = (n_G, d_p^G, d_e^G, d_h^G, d_r^G) $

$ M(C, G) =
  (n = n_G)
  and (d_p = d_p^G)
  and (d_e = d_e^G)
  and (d_h = d_h^G) $

$ O(Q, R) = cases(
  R_"post" = Q_"target" & "if committed or duplicate",
  R_"post" = R_"pre" & "if rejected or rolled back",
) $

$ "Closed"(G, A, Q, R) =
  "accepted"(A)
  and "AdmissionValid"(A)
  and (Q_"admission" = A_"id")
  and (Q_"subject" = A_"subject")
  and M(Q_"subject", G)
  and (Q_"expected-pre" = G_"runtime")
  and "Bind"(R, Q, A, G)
  and O(Q, R)
  and "CommitReceiptValid"(R) $

$ exists A, G_"current":
  "accepted"(A) and not M(A_"subject", G_"current") $
#+end_src

Here =admission-valid= is not a boolean convenience field.  Its owner
must establish the RFC 149-01 dual-decision closure together with the RFC
149-02 Human Audit closure for the exact commit subject.

=commit-receipt-valid= is likewise not derived from field equality.  It
is the Marlin transaction owner's proof that the observed pre-state was
atomically compared and the recorded outcome was produced by that
transaction.

* Refined transaction subject

=PromotionCommitSubject= contains:

- the complete RFC 149-01 =AuthorizationSubject=;
- =authoritySnapshotDigest= for the RFC 149-02 delegation, revocation,
  responsibility, and authentication state;
- =materializationPlanDigest= for the exact Marlin effect plan.

The authorization subject remains the Cedar/Lean decision subject.  The
commit subject is the higher-order transaction subject that binds
authorization, accountable human authority, and the effect plan.

* Snapshot and compare-and-swap contract

At commit time, the Marlin owner must atomically observe a
=GovernanceSnapshot= containing:

- governance epoch;
- policy-set digest;
- entity-store digest;
- authority-snapshot digest;
- runtime pre-state digest.

The commit precondition is:

#+begin_src text
request.subject matches currentSnapshot
request.expectedPreStateDigest = currentSnapshot.runtimeStateDigest
#+end_src

Any mismatch fails closed.  The system must not silently refresh one
digest, substitute a newer subject, or reuse the earlier decision while
changing the effect plan.  A caller may request a new admission
transaction against the new snapshot.

* Transaction state machine

#+begin_src mermaid
stateDiagram-v2
  [*] --> Proposed: "state=proposed / subject assembled"
  Proposed --> Admitted: "state=admitted / Cedar + Lean + Human Audit valid"
  Admitted --> CommitCheck: "state=checking / atomically read governance + runtime snapshot"
  CommitCheck --> Rejected: "state=rejected / subject or pre-state mismatch"
  CommitCheck --> Applying: "state=applying / compare-and-swap succeeded"
  Applying --> Committed: "state=committed / post-state = exact target"
  Applying --> RolledBack: "state=rolled-back / post-state = observed pre-state"
  Committed --> Duplicate: "state=duplicate / same transaction id and exact target"
  Rejected --> [*]: "terminal / no state change"
  RolledBack --> [*]: "terminal / pre-state restored"
  Duplicate --> [*]: "terminal / no second effect"
  Committed --> [*]: "terminal / one committed effect"
#+end_src

The state labels are semantic receipt states.  They are not logging
strings.  Every transition must be represented by a receipt owned by the
component that performs that transition.

* Recovery and idempotency rules

- A transaction identifier names one admission, one commit subject, one
  expected pre-state, and one target post-state.
- Reusing a transaction identifier with any different field is rejected;
  it is not a duplicate.
- A valid duplicate receipt proves that the exact target state was
  already committed and that no second effect was applied.
- A rejected receipt preserves the observed pre-state.
- A rolled-back receipt proves restoration of the observed pre-state.
- An interrupted =applying= state is not assumed safe.  Recovery must
  query the transaction owner and produce a valid =committed=,
  =rolled-back=, or =rejected= receipt before retry admission.
- Recovery authority is separate from approval authority and must follow
  the existing recovery-decision and coordinator boundaries.

* Owner boundaries

- Cedar owns policy evaluation against the bound request, policy, and
  entity snapshots.
- Lean owns the abstract model, counterexamples, and proof obligations.
- Human Audit or the organization authority contract owns delegation,
  authentication, revocation, and responsibility evidence.
- Marlin owns effect-plan execution, atomic compare-and-swap, rollback,
  idempotency, and commit receipts.
- POO Flow composes these first-class evidence objects.  It does not
  reproduce Cedar, Human Audit, or Marlin internals.

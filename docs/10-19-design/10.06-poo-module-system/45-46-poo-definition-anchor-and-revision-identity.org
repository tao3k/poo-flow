#+title: POO Definition Anchor and Revision Identity
#+subtitle: Stable semantic roles, content revisions, generated objects, and cyclic identity closure
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative design module
- Semantic core :: Native =gerbil-poo= definitions and POO Flow identity projection
- Related modules :: =45-35-macro-expanded-poo-prototype-definition-identity.org= and =45-45-canonical-poo-composition-root-and-definition-graph-identity.org=

This module separates the stable logical identity of a POO definition from the identity of its current semantic content.

* Core decision

#+begin_quote
A DefinitionAnchorIdentity identifies a stable POO semantic role. A DefinitionRevisionIdentity identifies the current canonical semantic content of that role. Named, generated, anonymous, and cyclic definitions must use both layers to remain explainable, incrementally comparable, and independent of source location.
#+end_quote

The semantic identity of a definition is:

#+begin_src text
DefinitionSemanticIdentity =
(
  DefinitionAnchorIdentity,
  DefinitionRevisionIdentity
)
#+end_src

* Definition anchor identity

A definition anchor is derived from:

#+begin_src text
package semantic namespace
+ module semantic namespace
+ declared or hygienically derived binding role
+ definition kind
#+end_src

An anchor excludes:

- the current definition body;
- a Git commit or build artifact digest;
- source path and line number;
- sibling ordinal;
- runtime address;
- a printed compiler gensym;
- process-local expansion order.

Changing semantic content does not make the definition appear removed and re-created. It changes the revision associated with the same anchor.

* Definition revision identity

A definition revision is conceptually derived from:

#+begin_src text
H(
  definition-revision schema identity,
  DefinitionAnchorIdentity,
  normalized expanded POO definition,
  native operation identities and operand roles,
  captured pure dependency revisions,
  priority, contract, and capability-requirement projections
)
#+end_src

The normalized expanded POO projection, not raw Scheme source text, determines the revision.

Consequently:

- comments and source relocation do not change the revision;
- hygiene-preserving local alpha-renaming does not change the revision;
- changing slot computation, prototype operands, priority, contracts, or semantic dependencies changes the revision;
- different macro surface forms may share a revision when they expand to the same POO semantic projection;
- distinct anchors remain distinct even when their revision payloads are structurally similar.

#+begin_src mermaid
flowchart LR
    N["Package, module, binding role, and definition kind"] -->|"derive stable logical identity"| A["DefinitionAnchorIdentity"]
    B["Normalized expanded POO body"] -->|"combine with operation roles and pure dependencies"| R["DefinitionRevisionIdentity"]
    A -->|"anchor the current revision"| R
    A -->|"remain stable across semantic edits"| S["DefinitionSemanticIdentity"]
    R -->|"identify current semantic content"| S
    P["Source path, line, and call site"] -->|"record separately"| E["Provenance evidence"]
    E -->|"explain origin without changing semantic identity"| S
#+end_src

* Named public definitions

An ordinary named definition may obtain an anchor from its hygienic binding and public semantic namespace:

#+begin_src scheme
(def production ...)
#+end_src

By default, a public binding name is part of its public semantic role. A public rename therefore appears as:

#+begin_src text
old public anchor removed
new public anchor added
#+end_src

The system must not infer a rename from structural similarity.

An explicitly stable POO object identity may preserve the object anchor across source refactoring. A changed export binding still has its own interface-identity change and evidence. Object identity and public binding identity are related but not interchangeable.

* Local anonymous definitions

An anonymous object must not use its sibling position as a stable anchor. Inserting an unrelated sibling would otherwise shift every later identity.

Anonymous definitions are divided into:

- Revision-local anonymous object :: Used only inside one enclosing definition and not referenced by imports, capability, recovery, evidence, or cyclic edges. It may use a content-addressed identity local to the enclosing revision.
- Semantically addressable object :: Referenced across slots, modules, revisions, recovery, or cycles. It must have an explicit semantic role key.

If an anonymous object must be recognized across revisions, it is no longer semantically anonymous.

An explicit role is expressed through POO identity values and native object construction, not a new public identity macro or configuration DSL.

* Macro-generated definitions

Hygienic gensym prevents binding capture but does not provide a stable cross-build semantic identity.

A macro that generates addressable POO definitions derives each anchor from:

#+begin_src text
enclosing DefinitionAnchorIdentity
+ macro semantic identity
+ generated family role key
+ domain item semantic key
#+end_src

It must not derive identity from:

- a printed gensym value;
- expansion order;
- list ordinal;
- source line;
- a compiler-process counter.

Generated collections use the semantic identity of each domain item. They do not use "first," "second," or "third" as longitudinal identity.

#+begin_quote
A macro that generates semantic nodes cannot enter a canonical composition path unless it proves deterministic semantic role-key derivation.
#+end_quote

This requirement is part of macro admission governance.

* Public rename and explicit identity

Public binding identity and POO object identity have different purposes:

- Public binding identity identifies the exported interface role.
- POO object anchor identifies the semantic object role.

An explicit object anchor may survive a source-level rename when the object role remains the same. The export rename still produces interface evidence and must not be hidden.

There is no automatic compatibility migration or deprecation protocol in this new architecture. Any retained identity is explicit semantic identity, not heuristic compatibility.

* Cyclic definition revision

Cyclic members must not recursively contain one another's complete revision digests. Internal references use stable anchors, and the SCC envelope closes the revision:

#+begin_src text
DefinitionSCCRevisionIdentity =
H(
  definition-SCC-revision schema identity,
  sorted member DefinitionAnchorIdentities,
  normalized member-local payloads,
  labeled internal edges expressed by member anchors,
  external dependency revision identities
)
#+end_src

Each member revision is then derived conceptually from:

#+begin_src text
H(
  DefinitionSCCRevisionIdentity,
  member DefinitionAnchorIdentity,
  member-local semantic projection
)
#+end_src

#+begin_src mermaid
flowchart LR
    A["Stable member anchors"] -->|"identify cyclic nodes without recursive revision hashing"| S["Definition SCC envelope"]
    L["Normalized member-local payloads"] -->|"preserve slot and operation semantics"| S
    I["Internal labeled edges by anchor"] -->|"close the cycle structurally"| S
    X["External dependency revisions"] -->|"bind outside semantic content"| S
    S -->|"content-address the cyclic definition region"| V["DefinitionSCCRevisionIdentity"]
    V -->|"combine with each member anchor"| M["Member DefinitionRevisionIdentity"]
#+end_src

This is identity projection over a cyclic definition graph. It is not fixed-point value evaluation and does not reimplement =gerbil-poo=.

* Incremental comparison

Two semantic generations compare definitions as:

#+begin_src text
same anchor + same revision    -> reusable
same anchor + changed revision -> modified
new anchor                     -> added
missing anchor                 -> removed
#+end_src

This permits precise invalidation for:

- one slot-definition revision;
- one prototype edge;
- one priority, contract, or capability-requirement projection;
- one SCC member addition or removal;
- one external dependency revision.

The evaluator does not treat an entire Profile as new merely because one anchored definition changes revision.

#+begin_src mermaid
flowchart LR
    O["Previous generation anchor-revision map"] -->|"compare by stable anchor"| D["Definition delta"]
    N["Current generation anchor-revision map"] -->|"compare by stable anchor"| D
    D -->|"same revision"| R["Reuse eligible"]
    D -->|"changed revision"| M["Modified definition"]
    D -->|"new anchor"| A["Added definition"]
    D -->|"missing anchor"| X["Removed definition"]
    M -->|"trace dependency edges"| I["Affected slot and downstream SCC invalidation"]
    A -->|"update definition topology"| I
    X -->|"update definition topology"| I
#+end_src

* Identity laws

- Anchor stability :: Semantic body changes do not alter the logical anchor.
- Revision sensitivity :: Semantic content changes alter the revision.
- Hygienic alpha invariance :: Hygiene-preserving local renaming does not alter identity.
- Sibling insertion invariance :: Inserting an unrelated sibling does not alter existing anchors.
- Explicit addressability :: An anonymous node addressable across revisions has an explicit semantic role.
- Direction preservation :: Operand roles remain part of revision identity.
- Cycle closure :: Internal cycle references use anchors and an SCC revision envelope.
- No authority implication :: A stable anchor does not grant capability or authority.
- No automatic rename inference :: Structural similarity does not imply identity continuity.
- Namespace separation :: Package, module, binding, object, and schema identities use explicit domains.

* Evidence requirements

Definition identity evidence records:

- anchor schema and namespace projection;
- definition kind and binding role;
- revision schema and normalized semantic dependencies;
- native operation identities and operand roles;
- macro semantic identity and generated role key where applicable;
- explicit identity declarations;
- public binding and object-anchor relationships;
- SCC envelope and member identities;
- added, removed, modified, and reusable classifications.

Source provenance may explain where an anchor was declared without entering the anchor or revision digest.

* Implementation checklist

- [ ] Define domain-separated schemas for anchor, revision, and semantic definition identity.
- [ ] Derive named anchors from package, module, hygienic binding role, and definition kind.
- [ ] Exclude body content, path, line, ordinal, runtime address, and printed gensym from anchors.
- [ ] Derive revisions from normalized expanded POO projections and pure dependency revisions.
- [ ] Preserve distinct explicit anchors for structurally similar definitions.
- [ ] Define revision-local anonymous identity.
- [ ] Require explicit semantic roles for cross-revision addressable anonymous objects.
- [ ] Require deterministic generated-family and domain-item role keys from macros.
- [ ] Reject ordinal- and expansion-counter-based generated identities.
- [ ] Separate public binding identity from POO object anchor identity.
- [ ] Project cyclic revisions through an anchor-based SCC envelope.
- [ ] Compare generation definitions by anchor and revision.
- [ ] Drive slot-local and SCC invalidation from definition deltas.
- [ ] Generate identity and delta evidence without using source coordinates as semantic input.
- [ ] Validate anchor construction against real Gerbil hygiene and =gerbil-poo= object interfaces.

* Non-goals

- Do not use one undifferentiated hash for logical role and current content.
- Do not infer stable identity from source position or sibling ordinal.
- Do not use printed gensyms as cross-build identity.
- Do not infer public renames from structural similarity.
- Do not add a public identity macro or raw identity DSL.
- Do not treat stable identity as authority.
- Do not recursively hash cyclic member revisions without an SCC envelope.
- Do not introduce compatibility migration or deprecation machinery.

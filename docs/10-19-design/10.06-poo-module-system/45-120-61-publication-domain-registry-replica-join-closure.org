#+title: Publication-Domain Registry Replica Join Closure
#+startup: overview

* Status

- State :: Proposed
- Scope :: multi-verifier checkpoint knowledge, monotonic join, and split-view safety
- Depends on :: RFC 58, RFC 60

* Problem

RFC 60 closes durable registry-checkpoint recovery for one verifier.  Multiple
verifiers can still recover different, individually authority-issued checkpoint
positions on the same lineage.

If one verifier knows minimum position =5= and another knows minimum position
=8=, candidate position =6= is accepted by the first and rejected by the
second.  Both local checks are internally valid.

Replica checkpoint knowledge therefore needs a monotonic merge operation that
never forgets rollback knowledge held by either replica.

* Independent checkpoints permit split view

For one actual lineage =L=:

#+begin_src typst
#align(center)[
  $
    "Accepted"(K_5, 6)
      and
    not "Accepted"(K_8, 6)
  $
]
#+end_src

where =K_p= denotes knowledge whose minimum accepted lineage position is =p=.
Local durable recovery alone does not make the replicas agree.

* Lineage-indexed replica knowledge

Replica knowledge is indexed by the actual lineage object:

#+begin_src typst
#align(center)[
  $
    K_L = p_"min"
  $
]
#+end_src

Knowledge from different lineage objects cannot be joined by the typed
interface.  A caller-provided lineage identifier is not a substitute for this
index.

* Monotonic join

Two knowledge values on the same lineage join by maximum:

#+begin_src typst
#align(center)[
  $
    K_l "join" K_r = max(K_l, K_r)
  $
]
#+end_src

The join is commutative, associative, and idempotent:

#+begin_src typst
#align(center)[
  $
    K_l "join" K_r = K_r "join" K_l
    \
    (K_l "join" K_m) "join" K_r =
      K_l "join" (K_m "join" K_r)
    \
    K "join" K = K
  $
]
#+end_src

It never lowers either input:

#+begin_src typst
#align(center)[
  $
    K_l <= K_l "join" K_r
      and
    K_r <= K_l "join" K_r
  $
]
#+end_src

* Rollback-rejection preservation

If either replica rejects a candidate position as older than its known minimum,
the joined knowledge also rejects it:

#+begin_src typst
#align(center)[
  $
    (p < K_l or p < K_r)
      "implies"
    not "Accepted"(K_l "join" K_r, p)
  $
]
#+end_src

The property is safety-monotonic: a merge may reject more historical positions,
but it cannot re-accept one already rejected by either input.

* Authority-issued recovery provenance

Replica knowledge is projected from RFC 60 authority-issued recovery evidence.
Its minimum position is the recovered position:

#+begin_src typst
#align(center)[
  $
    "IssuedRecovery"(A_L, E_L)
      "implies"
    p_"durable"(A_L) <= K(E_L)
  $
]
#+end_src

The pure join operates on already admitted knowledge.  It does not make
unissued checkpoint claims authoritative.

* This is not a consensus theorem

The join proves convergence and rollback-safety properties for checkpoint
knowledge already bound to one lineage.  It does not prove:

- linearizable registry publication;
- leader election;
- quorum availability;
- atomic network delivery;
- Byzantine agreement;
- authority-issued provenance for arbitrary peer messages.

Those properties require separate protocols and evidence.  They are not
inferred from semilattice laws.

* Ownership boundary

- RFC 60 owns authority-issued local recovery.
- The replica-knowledge object owns only the admitted minimum position.
- The pure join owns monotonic knowledge convergence on one actual lineage.
- Transport owns delivery and deduplication, not semantic authority.
- Consensus or quorum protocols remain separate from this safety closure.

* State machine

#+begin_src mermaid
stateDiagram-v2
  [*] --> LocalRecoveryChecked: verify RFC60 authority-issued recovery
  LocalRecoveryChecked --> ReplicaKnowledgeReady: project recovered position
  LocalRecoveryChecked --> AdmissionRejected: recovery unissued or indeterminate
  ReplicaKnowledgeReady --> PeerKnowledgeChecked: require the same lineage object
  PeerKnowledgeChecked --> KnowledgeJoined: take maximum minimum-position
  PeerKnowledgeChecked --> AdmissionRejected: lineage differs or provenance missing
  KnowledgeJoined --> RollbackRejected: either replica already rejected candidate
  KnowledgeJoined --> CandidateAccepted: joined minimum does not exceed candidate
  RollbackRejected --> [*]: preserve known safety
  AdmissionRejected --> [*]: fail closed
  CandidateAccepted --> [*]: continue registry-head validation
#+end_src

* Architectural consequence

Distributed registry safety begins with monotonic knowledge, not with an
implicit claim that all replicas are already synchronized.  The maximum join
provides a pure, deterministic safety kernel; authority provenance and
coordination remain explicit surrounding planes.

#+title: Programming Style 06 - Import Build And Performance

* Import ownership

Normal consumers import =modules/<name>/interface.ss=.  Module roles use
relative imports for their own owners.  Cross-domain implementations import a
precise public owner and use =only-in= for a bounded symbol set.  Global
facades deliberately export a stable surface and never wildcard-reexport
concrete Profiles, Scenarios or test owners.

* Build roots and laziness

A production ASP PackageSpec root is a separately required bootstrap artifact,
not a source inventory.  Native Gerbil imports close dependencies.  Do not list
both facade and internals, or production and test owners, as independent roots.
Profiles, Scenarios, contribution modules and advanced authoring owners remain
lazy until an explicit consumer demands them.

Use the ASP Build API and upstream =std/make=.  Do not add a scheduler,
currentness cache, source expander or duplicate graph.  Diagnose root count,
compile count, first-event latency, wall time, peak process-tree memory and
saturation separately.

* Performance law

Avoid repeated list scans and repeated closure/index construction.  Reuse
stable prototypes and derived indexes.  Do not lower concurrency to hide a
regression.  Performance changes require an A/B scenario with the same source
and semantic result; an optimization without a receipt is not project style.

#+title: POO Merge Priority and Recursive Override
#+startup: overview

* Status

Accepted design.

The POO Module System defines native merge-priority and recursive-override
semantics using POO objects and slot contracts.

The design absorbs several strong ideas documented by
[[https://nickel-lang.org/user-manual/merging/#merge-priorities][Nickel]]:

- priority metadata is distinct from operand order;
- unequal priorities select the stronger value;
- equal priorities continue through semantic merge;
- contracts remain applicable when a weaker value is suppressed;
- recursive dependencies observe the selected value.

These ideas are reconstructed in Gerbil Scheme through native =gerbil-poo=
prototype, slot, open-recursion, Capability, authority, and receipt semantics.
This is not a Nickel language mode, compatibility layer, record model, or
annotation syntax.

The design integrates with:

- [[file:45-19-capability-ambiguity-resolution-overlay-and-replay.org][45-19]]
  singleton ambiguity and explicit resolution;
- [[file:45-28-poo-native-slot-contracts-and-algebraic-laws.org][45-28]]
  POO-native slot contracts and algebraic laws.

It does not adopt Nix's lower-number-wins direction or its independent order
priority.

* Priority domain

The ordered merge-priority domain is:

#+begin_example
default < every numeric priority < force
#+end_example

Rules:

- an ordinary contribution has numeric priority =0=;
- numeric priorities compare by ordinary numeric order;
- a larger numeric priority is stronger;
- negative and fractional numeric priorities are permitted when their
  representation has canonical identity;
- =default= is weaker than every numeric priority;
- =force= is stronger than every numeric priority.

Durable semantic identity requires a canonical number representation.
Inexact values whose equality or serialization is unstable are not valid
merge-priority identities.

* Priority is a POO object

Priority metadata is represented by a POO object carried by the contribution.
It is not:

- an integer field in a definition record interpreted by a central evaluator;
- a wrapper around an otherwise unrelated runtime value;
- a module-name or provider-order convention;
- an enum switch;
- a string token.

The priority object carries:

- priority-domain prototype lineage;
- =default=, numeric, or =force= rank;
- canonical numeric identity when applicable;
- contribution and module-instance identity;
- authority scope;
- generation;
- provenance.

The ordinary priority object is the lawful base for a priority-enabled
contribution slot and represents numeric =0=.

Alias and re-export reachability of the same priority-bearing contribution do
not duplicate it.

* Merge algorithm

Priority evaluation occurs only after the canonical contribution set for the
current generation has closed.

For one priority-enabled slot:

1. close the complete canonical contribution set;
2. validate every contribution and priority object's identity and authority;
3. determine the maximum priority rank;
4. retain the complete maximum-priority class as active values;
5. preserve lower-priority contributions as suppressed evidence;
6. pass the active equal-priority class to the slot's POO algebra contract;
7. commit a successor only when that contract validates the result.

Input order, provider discovery order, thread completion, and module path do not
affect the result.

* Equal-priority behavior

Priority never breaks a tie by textual or runtime order.

When active values have equal priority, the governing 45-28 contract decides:

- canonical sets perform identity-based union;
- equal primitive or singleton values may coalesce when their semantic
  identities agree;
- nested objects refine through native ==>.+= or the declared recursive object
  contract;
- ordered same-lineage behavior follows native prototype inheritance;
- singleton unrelated values remain ambiguous;
- incompatible values produce a structured non-mergeable condition.

There is no last-writer-wins fallback.

* Suppressed evidence

A stronger priority suppresses the value semantics of weaker contributions.
It does not erase their existence.

Suppressed evidence retains:

- contribution and provider identities;
- priority object and rank;
- root, module-instance, and generation identities;
- source and causal provenance;
- the reason the contribution was inactive;
- applicable contracts and authority requirements.

Observability may show both active and suppressed contributions.

Replay must reconstruct the same maximum-priority class and suppression
explanation.

* Contract propagation

The POO merge contract preserves an important property learned from Nickel:
suppressing a lower-priority value does not automatically suppress semantic
contracts attached to that contribution.

Applicable contracts accumulate independently from value selection.  The
winning or merged value must satisfy every applicable contract whose authority
and scope cover the slot.

This includes:

- type and shape requirements;
- Capability and identity requirements;
- authority restrictions;
- budget and conservation constraints;
- provenance and receipt requirements.

A high-priority value cannot use priority to discard a lower-priority security,
authority, or correctness contract.

Conflicting applicable contracts produce a contract condition.  Priority does
not choose one contract over another unless the contract family itself
explicitly defines priority semantics for contract contributions.

* Default

=default= is the bottom of the priority domain.

It provides an overridable contribution while preserving recursive dependency.
When a stronger contribution wins, slots depending on the selected value are
recomputed through the native demand-lazy fixed point.

=default= is distinct from native =gerbil-poo= =?=:

- =?= supplies the base of one inherited slot computation;
- merge-priority =default= marks one contribution as weaker than all numeric
  and =force= contributions.

They may be used together only when both the slot algebra and priority contract
permit it.

=default= is not provider fallback.  It participates in the closed candidate
set and is suppressed only by an explicitly stronger contribution.

* Force

=force= is the top of the priority domain.

Because POO Flow carries authority and recovery semantics, creating or applying
a =force= priority requires explicit force authority scoped to:

- the root and module instance;
- the target slot and Capability;
- the contribution and generation;
- the contracts that remain applicable;
- the allowed successor scope.

=force= cannot bypass:

- authority attenuation;
- budget conservation;
- receipt predecessor continuity;
- contract propagation;
- generation validation;
- replay evidence.

Two distinct =force= contributions have equal priority and therefore continue
to the ordinary slot algebra.  A singleton tie remains ambiguity.

* Recursive override

Priority selection occurs within the same open-recursive POO object.

When a stronger contribution replaces a weaker value:

- the selected slot's canonical identity changes;
- dependent lazy slots observe the new value through =self=;
- only demanded dependents are recomputed;
- the fixed point derives a new canonical successor generation;
- unrelated slots remain lazy.

No external tree-rewrite pass is required.

This is the POO equivalent of Nickel's recursive overriding, implemented by
native =gerbil-poo= open recursion rather than a second record evaluator.

* Singleton Capability

A singleton Capability may explicitly adopt the POO merge-priority contract.

Its demand algorithm is:

- no candidates: unavailable condition;
- one maximum-priority candidate: selected candidate;
- several aliases of one maximum-priority contribution: one candidate;
- several unrelated maximum-priority candidates: ambiguity;
- weaker candidates: suppressed evidence.

The resulting selection proof binds:

- the complete closed candidate-set identity;
- every candidate's priority identity;
- the maximum-priority class;
- the suppressed candidate set;
- the selected contribution when unique;
- the slot-contract and priority-contract identities;
- root, module-instance, generation, authority, and provenance.

This is explicit POO resolution policy, not implicit provider-order fallback.

A singleton contract that does not import the priority contract continues to
ignore priority metadata and treats unrelated candidates according to the
ordinary ambiguity rules.

* Same-lineage refinement

Native =gerbil-poo= inheritance precedence remains the mechanism for ordered
same-lineage slot computations.

Merge priority does not reorder the =.mix= prototype chain and does not change
which inherited computation =next= invokes.

Priority is used when the slot contract closes and merges contribution values.
Prototype precedence governs open-computation inheritance.

These layers may coexist, but their evidence and identities remain separate.

* No independent order priority

This design does not introduce Nix-style =order-priority=.

Ordering is expressed by:

- native =.mix= precedence for same-lineage prototype refinement;
- canonical unordered identity for set-valued contracts;
- an explicit ordered-value contract when an application genuinely requires
  an ordered collection.

Merge priority controls value precedence only.

* Contracts that may reject priority

Priority metadata does not make an invalid semantic transition valid.

A slot contract may reject or ignore priority when selection by value
precedence would violate its laws.

In particular:

- authority remains governed by attenuation and grant construction;
- observation budgets remain governed by partition and conservation;
- receipt chains remain governed by predecessor continuity;
- historical evidence cannot be suppressed out of replay;
- cancellation and recovery authority cannot be fabricated by =force=.

Priority may select among valid candidate values only after the relevant
authority, identity, and generation checks.

* Conditions

Priority processing may produce structured continuable conditions:

- =merge-priority-invalid= for noncanonical or out-of-domain priority values;
- =merge-priority-authority-denied= for unauthorized priority metadata;
- =merge-force-authority-required= for unauthorized =force=;
- =merge-priority-tie-ambiguous= for unresolved strongest singleton ties;
- =merge-equal-priority-nonmergeable= for incompatible strongest values;
- =merge-priority-contract-violation= when the selected value violates an
  applicable retained contract;
- =merge-priority-stale= when candidate or generation evidence changed before
  commit.

Conditions carry the full candidate closure, active and suppressed classes,
priority identities, contracts, authority, generation, and provenance.

* Observability

Diagnostic projection includes:

- the complete candidate closure;
- each contribution's priority;
- why the maximum class won;
- which values were suppressed;
- which contracts propagated from suppressed contributions;
- equal-priority merge or ambiguity evidence;
- force authority when applicable;
- the final successor identity.

Presentation sorting does not become semantic priority.

* Replay

Replay:

1. reconstructs the closed canonical contribution set;
2. validates priority objects and authority;
3. derives the same maximum-priority class;
4. retains the same suppressed evidence;
5. accumulates the same applicable contracts;
6. runs the same equal-priority slot algebra;
7. validates the same successor and receipt.

Replay does not infer priority from source order, module path, timestamps, or
provider order.

Historical =force= authority is evidence only and cannot authorize a live
forced merge.

* Runtime and ownership boundary

=gerbil-poo= owns native prototype, slot, inheritance, and fixed-point
evaluation.

POO Flow owns the POO priority domain, contribution metadata, selection proof,
authority, conditions, observability, and receipts.

The runtime does not sort providers or implement a hidden merge evaluator.  It
preserves the POO evidence required by the priority-enabled slot computation.

The harness validates priority ordering, equal-priority algebra, recursive
override, contract propagation, authority, and replay.  It is not a priority
provider.

- [ ] Define the domain =default < numeric < force=.

- [ ] Make larger numeric priorities stronger.
- [ ] Require canonical numeric identity.
- [ ] Close the full contribution set before priority selection.
- [ ] Retain the complete maximum-priority class.
- [ ] Preserve weaker contributions as suppressed evidence.
- [ ] Delegate equal-priority values to the 45-28 slot algebra.
- [ ] Propagate applicable contracts independently from value suppression.
- [ ] Require explicit authority for =force=.
- [ ] Keep =force= subject to authority, conservation, continuity, and replay.
- [ ] Support recursive override through native POO open recursion.
- [ ] Produce singleton selection proof from the full priority closure.
- [ ] Preserve ambiguity for tied unrelated strongest candidates.
- [ ] Keep native =.mix= precedence separate from merge priority.
- [ ] Do not add an independent order-priority axis.
- [ ] Allow slot contracts to reject priority where it violates their laws.
- [ ] Expose active, suppressed, contract, and authority evidence to

#+title: POO Definition Invalidation Explanation and Causal Diff
#+status: Accepted
#+language: en

* Decision

Every semantic invalidation MUST produce a structured POO explanation that
identifies:

1. the smallest changed semantic identity;
2. the invalidation seed;
3. the actual demand edges that propagated the change;
4. the resulting slot or SCC recomputation closure;
5. the final reuse, recomputation or fail-closed decision.

An operational cache miss, eviction, timeout or worker event MUST be reported
separately and MUST NOT be presented as a semantic definition change.

The explanation is a family of POO evidence objects.  It is not a reason
string, enum registry, raw log format or user-authored diagnostic DSL.

* Three distinct outcomes

| Outcome | Meaning |
|---------+---------|
| Semantic invalidation | A definition, binding, contract, priority, dependency, capability or authority identity changed |
| Proof unavailable | Equality may hold, but current evidence cannot authorize reuse; evaluation recomputes conservatively |
| Operational miss | Physical cache, worker, host or timing behavior prevented an optimization without changing semantics |

Only the first outcome proves that semantic identity changed.

flowchart LR
  D["Definition identity delta"] -->|"identifies the smallest changed Merkle leaf"| S["Invalidation seed"]
  S -->|"propagates through actual reverse-demand edges"| A["Affected slot demands"]
  A -->|"crosses a mutual dependency boundary"| C["Current sealed SCC closure"]
  A -->|"remains acyclic and local"| L["Local slot closure"]
  C -->|"current evidence authorizes equivalence"| R["Validated reuse"]
  C -->|"semantic identity changed"| X["Targeted recomputation"]
  C -->|"equivalence proof is incomplete"| F["Conservative recomputation"]
  L -->|"records the same decision classes"| E["POO invalidation explanation"]
  R -->|"records why reuse remained valid"| E
  X -->|"records the causal semantic delta"| E
  F -->|"records proof unavailability without claiming a change"| E
#+end_src

* Explanation layers

An invalidation explanation contains five causally linked layers.

| Layer | Required question |
|-------+-------------------|
| Definition delta | Which phase, binding, prototype, slot, contract or substrate identity changed? |
| Invalidation seed | Which smallest semantic object first became ineligible for reuse? |
| Demand propagation | Which current or predecessor demand edges carried the invalidation? |
| Closure decision | Why did the affected unit remain one slot or expand to a submodule or SCC? |
| Evaluation outcome | Why was the result reused, recomputed, conservatively recomputed or rejected? |

The layers form a graph because one changed definition may affect several
demands and one demand may have several independent causes.

* Minimal semantic diff

The explanation begins at the smallest changed identity for which evidence is
available.

Examples include:

- one macro transformer in a specific phase;
- one resolved hygienic binding;
- one expanded slot-definition leaf;
- one prototype-shape key;
- one ordered supers or precedence edge;
- one slot-contract object;
- one contribution, priority or force-authority identity;
- one runtime dependency result;
- one native =gerbil-poo= operation identity.

A whole module, source file or prototype root is used only when evidence cannot
prove a narrower diff.

* Macro-expansion explanations

** Transformer changed, semantic definition stable

#+begin_src mermaid
flowchart LR
  T["Phase transformer identity changed"] -->|"invalidates expansion execution reuse"| E["Fresh hygienic expansion"]
  E -->|"canonical POO definition remains equal"| S["Semantic slot identity preserved"]
  S -->|"prevents unnecessary reverse-demand propagation"| R["Slot result remains eligible"]
  R -->|"records re-expansion and equality proof"| X["Explanation receipt"]
#+end_src

The explanation distinguishes required re-expansion from semantic
invalidation.

Its human projection should communicate:

#+begin_example
re-expanded because a phi+1 transformer changed
canonical POO definition remained equal
slot result remained eligible for reuse
#+end_example

** Transformer changed, slot definition changed

The explanation links:

#+begin_example
phase transformer delta
-> fresh expansion
-> expanded slot-definition delta
-> invalidation seed
-> reverse-demand closure
#+end_example

** Hygienic binding changed

Equal printed names do not hide a binding change.  The explanation identifies
the predecessor and successor binding origins, phases and defining module
identities.

It MUST NOT reduce the diff to textual symbol equality.

** Alpha-normalized generated binding

A generated local name change that disappears under hygienic
alpha-normalization produces no semantic invalidation.  It may appear in
diagnostic evidence when useful.

** Opaque procedural macro

When compile-time dependencies are incomplete, the explanation states that
reuse proof is unavailable and identifies the unproven dependency class.

The macro remains valid.  POO Flow performs fresh expansion and conservative
recomputation without falsely claiming that the semantic definition changed.

* Causal propagation

Invalidation propagates through the actual demand graph, not through file or
package proximity.

#+begin_src mermaid
flowchart TD
  P["Phase or binding delta"] -->|"changes one canonical expanded slot leaf"| S["Slot definition"]
  S -->|"invalidates the corresponding demand identity"| D["Demanded slot"]
  D -->|"was consumed by"| A["Dependent slot A"]
  D -->|"was consumed by"| B["Dependent slot B"]
  A -->|"belongs to the current mutual dependency closure"| C["Sealed SCC"]
  B -->|"belongs to the current mutual dependency closure"| C
  C -->|"recomputes under the successor generation"| R["Successor semantic receipt"]
  R -->|"retains definition delta and every causal edge"| E["Complete explanation closure"]
#+end_src

Every propagation edge commits to:

- source and target demand identity;
- predecessor and successor generations;
- nested submodule and prototype lineage;
- the consumed slot or structural observation;
- capability and authority scope;
- predecessor dependency receipt.

* Reflection-aware explanation

The reason for propagation reflects the native POO observation:

| Observation | Explanation relation |
|-------------+----------------------|
| Known slot demand | The slot lookup lineage or definition changed |
| =.has?= or =.key?= | The observed key-existence identity changed |
| =.all-slots= | Prototype shape changed |
| =.mix= or inherited lookup | Ordered supers or precedence changed |
| Nested access | A traversed nested object or final slot identity changed |
| Contract demand | A retained contract object or its obligation changed |

The explanation therefore shows why a structural observer was invalidated
without pretending that every reflection operation depends on the whole
prototype.

* Complete cause closure

POO Flow MUST preserve every causally relevant cause in the explanation
closure.

A user interface may project one primary cause for concise presentation.  The
primary cause is selected canonically from semantic identity and causal path.
It is not selected by:

- wall-clock arrival order;
- worker completion order;
- cache response order;
- arbitrary hash-map iteration;
- first exception observed by a thread.

Secondary causes remain queryable from the same POO evidence object.

* Semantic and operational separation

#+begin_src mermaid
flowchart LR
  I["Semantic identity comparison"] -->|"changed definition or dependency"| S["Semantic invalidation evidence"]
  I -->|"equivalence cannot be proved"| P["Proof-unavailable evidence"]
  O["Cache and execution runtime"] -->|"miss, eviction, timeout or worker event"| M["Operational evidence"]
  S -->|"may require targeted recomputation"| R["Evaluation decision"]
  P -->|"requires conservative recomputation"| R
  M -->|"may remove an optimization but not change POO meaning"| R
  R -->|"links distinct evidence without conflation"| E["Explanation projection"]
#+end_src

Examples:

- A missing cache artifact is an operational miss.
- A malformed artifact may be an operational rejection and a trust-boundary
  failure, but it does not prove the source definition changed.
- A changed slot-definition identity is semantic invalidation.
- An opaque macro is proof unavailable until fresh expansion supplies current
  evidence.

* User-facing projection

The ordinary projection should lead with:

- what changed;
- why the current slot depends on it;
- how far invalidation propagated;
- what the evaluator did;
- whether the result or only the execution path changed.

Raw digests MAY be available as secondary evidence.  They MUST NOT be the only
explanation.

A concise projection may read:

#+begin_example
slot production.summary recomputed
because wendao.index changed after phi+1 macro expansion
the change propagated through demand edge production.summary -> wendao.index
both slots belong to fixed-point component <identity>
the successor component converged in generation <identity>
#+end_example

* Authority and redaction

Explanation must not disclose live authority or sensitive inputs.

- Authority tokens, capability handles and resource leases never enter the
  explanation.
- Secret compile-time or runtime input values are represented by authorized
  identity commitments.
- Source and binding provenance are projected only within the current
  observability authority.
- Operational host paths and cache locations remain in the operational plane.
- Redaction must preserve causal structure so that a hidden value does not
  become an unexplained missing edge.

The explanation object may carry a restricted identity commitment while its
human projection states that the underlying value is redacted.

* Continuable conditions

Proof unavailability normally causes conservative recomputation, not an error.

A continuable condition is appropriate when:

- the required recomputation exceeds a logical budget;
- a phase dependency cannot be captured under current policy;
- authority is required to inspect or use a dependency;
- topology oscillation prevents the explanation closure from sealing;
- the current generation cannot establish a required identity.

The condition carries the partial explanation graph and offers only authorized
recovery choices.  Resumption enters a successor contribution generation.

* Explanation receipt

The canonical explanation receipt SHOULD commit to:

- predecessor and successor semantic identities;
- changed Merkle leaves;
- definition-delta evidence;
- invalidation seeds;
- demand-propagation edges;
- slot and SCC closure decisions;
- semantic, proof-unavailable and operational evidence separation;
- reuse or recomputation outcome;
- canonical primary-cause projection;
- complete secondary-cause closure;
- redaction commitments;
- predecessor receipts and successor generation.

The receipt is a POO evidence object.  It is not a compiler log, cache manifest
or free-form diagnostic string.

* Required failure conditions

Explanation construction MUST fail closed or raise an authorized continuable
condition when:

- a semantic invalidation has no identified changed identity;
- propagation omits a demand edge required by the recomputation closure;
- a whole-file hash hides a known smaller definition delta;
- proof unavailability is falsely reported as semantic change;
- an operational cache miss is reported as definition invalidation;
- a primary cause is selected by runtime arrival order;
- a secondary cause is discarded;
- hygiene is explained only through printed identifier names;
- redaction removes causal structure;
- an explanation leaks authority, capability or secret values.

* Acceptance checklist

- [X] Every semantic invalidation identifies a smallest known semantic delta.
- [X] Root cause and demand propagation are separate evidence layers.
- [X] Macro re-expansion and expanded semantic change are distinguished.
- [X] Hygienic binding changes and alpha-normalized renames are distinguished.
- [X] Opaque macros produce proof-unavailable evidence rather than a false
  semantic-change claim.
- [X] Reflection operations explain their actual dependency width.
- [X] Complete cause closure is retained.
- [X] Primary-cause projection is canonical and non-racy.
- [X] Semantic, proof-unavailable and operational outcomes remain distinct.
- [X] User-facing projection leads with causal meaning rather than raw hashes.
- [X] Redaction preserves the causal graph without leaking authority.
- [X] Continuable conditions carry partial explanation evidence.
- [ ] Validate the model with executable transformer-stable,
  transformer-changing, hygienic-binding, alpha-rename, opaque-macro,
  reflection, multi-cause, cache-miss, redaction and budget scenarios before
  implementation begins.

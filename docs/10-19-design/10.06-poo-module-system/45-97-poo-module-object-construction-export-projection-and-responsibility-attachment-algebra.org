#+title: POO Module Object Construction, Export Projection, and Responsibility Attachment Algebra

* Status

Accepted architecture RFC.

This document fixes the POO-native Module construction algebra. It does not
authorize implementation work and does not invent unverified =gerbil-poo= call
forms.

* Scope

This RFC defines:

- the POO object graph that constitutes a semantic =Module=;
- the role of prototype composition, extension, delegation, and precedence;
- the object-level representation of exports and recursive imports;
- the attachment of ProfileBundles and responsibility objects;
- the pure functional public authoring route;
- the boundary between upstream =gerbil-poo= primitives and POO Flow adapters;
- conflict, reachability, evidence, and admission laws.

This RFC does not define:

- a replacement object system;
- a local fixed-point evaluator;
- a map, record, patch, or slot-clause DSL;
- a hidden Module or export registry;
- a second prototype precedence algorithm;
- an imperative public authoring interface;
- a new package manager or build system;
- compatibility, migration, or deprecation behavior.

#+end_example

POO Flow adopts and extends this implementation and theory. It does not create

* Ownership classification

** Upstream gerbil-poo

The identifiers listed in the evidence state are owned by the pinned
=gerbil-poo= implementation.

They provide the native object, slot, prototype, delegation, extension,
composition, mix, and precedence vocabulary from which the POO Flow Module
model must be built.

** POO Flow adapters

The following are current project adapters, not upstream primitives:

- =poo-flow-module-interface-prototype=;
- =poo-flow-module-object-has-slot?=;
- =poo-flow-module-object-ref/default=;
- =poo-flow-module-object->alist=.

They may help bridge current code, but they do not define a second object model.

** Legacy composition helpers

Current profile-composition accessors, syntax planners, alist projections,
stage clauses, and binding builders are legacy implementation surfaces.

They do not constrain the new public algebra and are not automatically admitted
as future public APIs.

* Central decision

A semantic =Module= is one POO object whose prototype ancestry and reachable
object graph own:

- stable Module identity;
- exported identity projections;
- exported ProfileBundle values;
- direct imports;
- capability requirements;
- responsibility reachability;
- evidence projection hooks;
- version and source identity where required by owning RFCs.

The Module is constructed by native POO object and prototype operations.

No parallel map representation, raw alist representation, clause tree, or
registry is semantically authoritative.

Raw alists, registries, and clause DSLs are excluded from semantic ownership.

The construction relation is:

#+begin_example
Module prototype
  + identity-bearing extension
  + export object
  + direct imports object
  + capability requirements
  -> complete Module object
#+end_example

The exact Scheme call spelling remains subject to verified =gerbil-poo=
selectors and procedure contracts.

* Native operation families

** Object identity and lifecycle

=object=, =instantiate-object!=, and related lifecycle procedures establish the
upstream object representation.

POO Flow must not expose manual lifecycle mutation as the ordinary Module
authoring surface. The public route constructs a complete value through named
POO-native or pure functional helpers.

** Slot projection

=object-ref=, =object-slot-has?=, and related slot operations provide native
projection.

Module identity, exports, imports, capabilities, and responsibility references
must be object-owned projections. Raw alists are not the canonical interface,
even though upstream and project adapter surfaces can project an object to an
alist for bounded diagnostics.

** Prototype extension

=object-extend= and =extend-object!= belong to the native extension family.

Public advanced authoring uses a named POO-native extension helper whose result
is a Module value. Destructive variants may be used internally only when their
identity, isolation, and purity boundary is explicit.

** Composition and mix

=object-compose= and =object-mix= are distinct upstream identifiers.

This RFC does not collapse them into one generic operation and does not infer
their exact argument order or conflict semantics from their names.

POO Flow must verify each upstream contract before selecting which operation
implements a particular Module composition law.

** Delegation, super, and precedence

=object-delegate=, =object-super=, =object-precedence-list=, and the upstream
precedence computation family provide the native ancestry and resolution
surface.

POO Flow does not introduce a second super chain or precedence list.

Any project-level conflict policy must project through the native object
ancestry and must produce evidence identifying the selected and shadowed
origins.

* Pure functional authoring route

Public Module authoring is pure.

The ordinary Module authoring route is pure:

#+begin_example
Module value -> Module value
#+end_example

Authoring helpers accept POO values and return POO values. Side effects remain
behind explicit runtime, build, persistence, or handoff boundaries.

Upstream procedures whose names end in =!= are not automatically rejected.
They may be used internally to implement isolated construction, but they are
not the ordinary public interface.

Mutation-marked upstream operations are confined to isolated internal
construction.

An admitted functional wrapper must prove:

- no shared input object is mutated observably;
- the result has stable identity and prototype ancestry;
- repeated construction from equivalent inputs is deterministic;
- capability authority is not widened;
- the resulting value remains a native =gerbil-poo= object.

* Module object structure

The POO object graph preserves Module, export, ProfileBundle, Profile, and
responsibility identity.

** Identity projection

Module identity is an object-owned semantic projection.

It is not derived solely from:

- a Gerbil source binding;
- a repository directory;
- a package name;
- a =use-module= alias;
- a runtime registry key.

Those identities may be recorded in evidence, but they remain distinct.

** Export object

Exports are represented by a POO object or a POO-native projection owned by the
Module.

Each exported identity resolves to a Profile operand. Under the current
architecture, =production= resolves to one module-scoped =ProfileBundle=.

The export object is not:

- a raw alist public API;
- a string-keyed runtime registry;
- a keyword clause parsed by a macro;
- a copy of the exported ProfileBundle.

** Direct imports object

A Module owns direct import relationships as native POO object structure.

The recursive active imports closure is derived from:

- the selected export;
- its reachable low-level Profiles;
- reachable responsibility objects;
- their direct imports;
- capability-qualified projection.

Users do not enumerate the complete transitive closure.

** Capability requirements

Capability requirements are POO values reachable from the Module, exported
ProfileBundles, or responsibility objects.

Composition preserves or attenuates requirements and grants. Object
construction, extension, composition, or mix cannot manufacture authority.

* ProfileBundle attachment

A ProfileBundle is attached by an object-level export relationship:

#+begin_example
Module --export identity--> ProfileBundle
#+end_example

Attachment does not copy or flatten the bundle.

The relationship preserves:

- Module identity;
- export identity;
- ProfileBundle identity;
- low-level Profile identities;
- prototype ancestry;
- responsibility reachability;
- direct and recursive imports evidence.

=production= is one export identity. It is not an instruction to enter an
imperative stage.

* Responsibility attachment

Graph, loop, proof, handoff, stage responsibility, and observability facts are
ordinary POO objects or POO facts.

They are attached through object-level reachability from a Profile or
ProfileBundle. They are not placed in a parallel Module clause table.

#+begin_src mermaid
flowchart LR
  Prototype["Module prototype"] -->|"extends through native POO ancestry"| Module["Module object"]
  Module -->|"projects stable export identity"| Export["export object"]
  Export -->|"references without flattening"| Bundle["production ProfileBundle"]
  Bundle -->|"preserves member identity"| Profiles["low-level Profiles"]
  Profiles -->|"reach semantic responsibility"| Graph["graph object"]
  Profiles -->|"reach progress responsibility"| Loop["loop object"]
  Profiles -->|"reach evidence obligation"| Proof["proof object"]
  Profiles -->|"reach runtime boundary contract"| Handoff["handoff object"]
  Profiles -->|"reach qualification facts"| Stage["stage responsibility"]
  Module -->|"owns direct dependency relation"| Imports["direct imports object"]
  Graph -->|"contributes reachable dependency"| Imports
  Loop -->|"contributes reachable dependency"| Imports
  Proof -->|"contributes reachable dependency"| Imports
  Handoff -->|"contributes reachable dependency"| Imports
#+end_src

The relationship may be expressed with verified slot, extension, composition,
mix, delegation, or prototype operations. This RFC does not invent a new
attachment primitive.

* Composition and precedence

** Native precedence first

Native =gerbil-poo= precedence is the first and authoritative object-resolution
layer.

When Module objects or their prototypes are composed, native =gerbil-poo=
ancestry and precedence remain the base resolution mechanism.

POO Flow may constrain admissible compositions, but it does not replace the
upstream precedence model with a macro-owned merge algorithm.

** No silent export overwrite

If multiple operands contribute the same export identity, composition must:

- resolve it through an explicitly admitted native POO rule and emit the
  selected ancestry path; or
- reject the composition as an unresolved export conflict.

An alist overwrite, iteration order, source order accident, or hidden registry
update is never a valid resolution.

** Responsibility accumulation

Selecting one export accumulates every responsibility reachable from the
selected ProfileBundle after native precedence resolution.

A stronger prototype value cannot erase an independent lower-precedence
requirement merely by replacing a neighboring slot. Constraint preservation
and capability attenuation remain mandatory.

** Control-policy priority separation

Numeric control-policy priority is governed by
[[file:45-90-poo-control-policy-composition-priority-conflict-and-veto-resolution.org][45-90]].

Control-policy priority remains distinct from prototype precedence.

This RFC does not create a second numeric priority system for Module exports.
Prototype precedence and policy priority are related through evidence, but they
remain distinct semantic dimensions.

* Construction pipeline

#+begin_src mermaid
sequenceDiagram
  participant Author as "Module author"
  participant Upstream as "gerbil-poo operations"
  participant Adapter as "POO Flow semantic adapter"
  participant Module as "complete Module object"
  participant Bind as "thin binding macro"
  participant Select as "use-module"

  Author->>Upstream: "constructs or extends native POO values"
  Upstream-->>Adapter: "returns identity-bearing object"
  Adapter->>Adapter: "validates Module interface and purity boundary"
  Adapter-->>Module: "projects exports, imports, and requirements"
  Module->>Bind: "enters binding as one completed expression"
  Bind-->>Select: "exposes one hygienic Module reference"
  Select->>Module: "selects stable ProfileBundle export"
  Module-->>Select: "returns value and reachability evidence"
#+end_src

The adapter validates a native object. It does not convert that object into a
second semantic representation.

* Construction laws

** Native object law

Every admitted Module value is a native object of the pinned =gerbil-poo=
implementation.

** Prototype ancestry law

Extension and composition preserve an inspectable native precedence list.

** Identity preservation law

Construction preserves the identities of Module, export, ProfileBundle,
low-level Profile, and responsibility objects.

** Export projection law

An export relationship references a Profile operand without copying,
flattening, or re-identifying it.

** Reachability law

The active responsibility and imports closure contains exactly the qualified
objects reachable from the selected export.

** Pure authoring law

Ordinary public authoring is observationally equivalent to a pure transformation
from POO inputs to one POO Module output.

** Authority neutrality law

Object construction and composition grant no capability.

** Constraint preservation law

Prototype precedence cannot silently erase an independent requirement,
obligation, or veto.

** Conflict evidence law

Every resolved duplicate export identifies the native ancestry and rule that
selected its value. Unresolved conflicts fail closed.

** Representation uniqueness law

No alist, record, syntax plan, runtime registry, or generated manifest becomes
co-authoritative with the Module object.

* Evidence projection

A Module construction receipt must identify:

- durable =gerbil-poo= dependency identity;
- verified upstream primitive identities used;
- POO Flow adapter identity;
- Module object identity and prototype ancestry;
- direct super and delegation relations where applicable;
- export object identity;
- exported ProfileBundle identities;
- direct imports object identity;
- capability requirement identities;
- responsibility reachability roots;
- any destructive primitive used internally;
- isolation evidence for destructive construction;
- duplicate export resolution evidence;
- source owner and construction origin;
- absence of authority widening.

An exact primitive selector without owner bytes is discovery evidence, not
implementation proof.

* Failure behavior

Construction fails closed when:

- a value is not a native =gerbil-poo= object;
- the expected Module interface is absent;
- stable Module identity is missing;
- an export identity is malformed or duplicated without an admitted rule;
- an exported value is not a Profile operand;
- a ProfileBundle is flattened or re-identified;
- direct imports are stored only in a parallel representation;
- responsibility reachability is incomplete;
- a destructive operation leaks mutation to shared inputs;
- native precedence cannot be inspected;
- capability authority is widened;
- the upstream primitive contract required by an adapter is unverified.

Failure identifies the upstream operation, adapter, Module identity, export or
slot identity, ancestry path, and missing evidence.

* Rejected alternatives

The following alternatives are rejected:

- treating =object-mix= as the whole POO API;
- creating local substitutes for native object extension or precedence;
- inventing exact upstream call syntax from identifier names;
- exposing =object->alist= or =poo-flow-module-object->alist= as the canonical
  Module interface;
- making mutation-marked upstream procedures the ordinary public authoring
  surface;
- representing exports as a hidden mutable registry;
- copying ProfileBundles into a flattened Module record;
- attaching responsibilities through a separate clause tree;
- silently overwriting duplicate exports;
- using macro source order as prototype precedence;
- merging control-policy priority with prototype precedence;
- publishing local =.data/gerbil-poo= paths as dependency identities.

Implementation work is not admitted until:

- [ ] =object-compose= has a verified operational contract;
- [ ] =object-mix= has a verified operational contract;
- [ ] delegation, super, and precedence contracts are verified;
- [ ] slot projection and update contracts are verified;
- [ ] mutating and non-mutating operation families are distinguished;
- [ ] the Module prototype maps directly to pinned upstream primitives;
- [ ] export projection has a POO-native representation test;
- [ ] ProfileBundle identity preservation has a focused test;
- [ ] responsibility reachability has a focused test;
- [ ] imports closure has a focused test;
- [ ] duplicate export conflict behavior has a focused test;
- [ ] authority neutrality has a focused test;
- [ ] no alist or registry representation is co-authoritative;
- [ ] the RFC set is reviewed before implementation begins.

* Consequences

POO Flow uses the full native POO vocabulary rather than reducing the design to
=mix=.

Module construction remains POO-native and extensible, while the ordinary
authoring route remains pure and comprehensible.

Exports, ProfileBundles, responsibilities, and imports stay inside one
identity-bearing object graph. Macros and adapters can project that graph, but
they cannot become its semantic owner.

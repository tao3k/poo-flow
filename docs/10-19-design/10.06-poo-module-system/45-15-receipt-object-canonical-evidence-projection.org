#+title: Receipt Object And Canonical Evidence Projection

* Normative responsibility

This module owns the common POO Flow semantics for:

- an in-process POO-native receipt object;
- canonical causal projection across runtime boundaries;
- stable causal receipt identity;
- external provider outcome identity and verifier evidence;
- immutable correction, contradiction, and predecessor relationships;
- bounded diagnostic annotations and redaction.

It does not define global receipt storage, retention, indexing, an active
evidence closure, or a new package/dependency declaration language.

* Ownership boundary

=gerbil-poo= remains the sole Scheme POO implementation.  It owns runtime POO
object identity, prototype composition, slots, refinement, and generic
continuation-aware realization.

POO Flow owns receipt semantics, causal identity, projection gates, verifier
relationships, and condition behavior.

The runtime or Marlin boundary owns the concrete transport of a canonical
projection.  External storage policy owns persistence, retention, access
control, and indexing.  Neither transport nor storage becomes semantic receipt
authority merely by carrying the projection.

* Three receipt identities

Every portable receipt relationship distinguishes three identities:

| Identity | Scope | Authority |
|---+---+---|
| runtime receipt object identity | one Scheme runtime context | ordinary =gerbil-poo= object identity |
| canonical causal identity | canonical identity-bearing projection | causal comparison across contexts |
| external outcome identity | provider/verifier domain | proof of an operation, artifact, resource, or external result |

The identities MUST NOT be collapsed:

- runtime object identity is process-local and is never serialized;
- canonical causal identity does not impersonate provider outcome identity;
- provider outcome identity does not establish POO runtime identity.

  R -->|"explicit runtime or Marlin projection"| C["State: canonical receipt projection"]

* POO-native receipt object

Inside Gerbil, a receipt is an ordinary POO object.  Receipt families use POO
prototype identity, composition, and refinement.  The ordinary Scheme
interface MUST NOT be a raw alist DSL, record DSL, JSON constructor, or
string-keyed patch language.

A receipt object may expose:

- semantic transition evidence;
- boundary, context, operation, attempt, policy, and verifier relationships;
- typed predecessor relationships;
- outcome and portability evidence;
- a projection capability.

Exact prototypes, slots, helpers, and macros remain API-evidence-gated.  A
generally reusable receipt-object mechanism belongs upstream in =gerbil-poo=.

Constructing a receipt object does not automatically persist, publish, or
project it.

* Canonical projection boundary

Canonical projection is explicit.  It occurs only when a receipt must cross a
runtime/process boundary, enter an external verifier, or participate in
cross-context replay/admission.

The projection separates:

1. an identity-bearing causal core;
2. bounded diagnostic annotations.

#+begin_src mermaid
flowchart TD
  R["State: runtime receipt POO object"] -->|"project semantic fields"| C["State: identity-bearing causal core"]
  R -->|"project bounded non-authoritative metadata"| A["State: diagnostic annotations"]
  C -->|"canonical normalization + digest contract"| I["State: causal identity"]
  C -->|"transport envelope"| T["State: portable receipt projection"]
  A -->|"attached without changing causal identity"| T
  V["State: verifier capability"] -->|"declares evidence and annotation coverage"| T
#+end_src

Wall-clock timestamps, host names, process ids, queue timing, display labels,
and truncation metadata are diagnostic annotations.  They MUST NOT alter
canonical causal identity.

If a provider signature or verifier covers diagnostic annotations, its coverage
is recorded explicitly.  That coverage does not make the annotations semantic
precedence or causal authority.

* Identity-bearing causal core

The causal core carries semantic evidence sufficient for its receipt family,
including:

- receipt semantic-contract identity and version;
- transition kind and semantic outcome;
- portable source/content provenance;
- boundary and operation evidence appropriate to the receipt;
- typed causal predecessor identities;
- governing policy and verifier identities;
- external outcome evidence when present;
- portability, redaction, and qualification evidence;
- successor/correction relationship when present.

The canonical causal identity is derived from the normalized causal core.  The
identity field itself is not recursively included in its own derivation.

Exact encoding, field representation, normalization rules, digest algorithm,
and C ABI remain evidence-gated.  Any chosen encoding MUST preserve the
semantic distinctions in this RFC and produce identical causal identity for
equivalent cores.

* Typed causal predecessor edges

Receipt predecessors form a causal partial order.  Each edge has a semantic
role, such as:

- transition predecessor;
- policy authorization;
- provider verification;
- containment parent;
- demand dependency;
- cancellation propagation;
- resource acquisition or release;
- correction or contradiction.

#+begin_src mermaid
flowchart LR
  R["State: current receipt causal core"] -->|"transition predecessor"| T["State: prior transition receipt"]
  R -->|"policy authorization"| P["State: immutable policy receipt"]
  R -->|"provider verification"| V["State: verifier evidence"]
  R -->|"containment parent"| C["State: parent-boundary receipt"]
  R -->|"correction or contradiction"| X["State: earlier disputed receipt"]
  T -.->|"edge role is semantic; array position is not execution precedence"| P
#+end_src

Serialization order of predecessor fields does not create runtime execution
order.  The canonical representation normalizes unordered collections while
preserving ordered relationships whose owning semantic contract explicitly
requires order.

The DAG need contain only predecessors selected for the current artifact or
verification frontier.  A receipt identity can reference evidence stored
elsewhere.  POO Flow does not require a globally materialized closure.

* Immutability, correction, and contradiction

A receipt is immutable after construction.  It MUST NOT be:

- edited in place;
- replaced by last-write-wins storage;
- retroactively relabeled as another terminal outcome;
- mutated to hide a failed verification.

A correction is a new successor receipt that identifies the earlier receipt,
the correcting authority, new evidence, and causal reason.

Contradictory receipts may coexist as evidence.  A verifier reports a structured
contradiction condition containing both causal identities and their incompatible
claims.  Storage order does not resolve the contradiction.

  O["State: original immutable receipt"] -->|"new evidence + correcting authority"| C["State: correction successor receipt"]
  O -->|"incompatible terminal claim"| X["State: contradictory receipt"]
  C -->|"verifier evaluates causal relationship"| V["State: qualification result"]
  X -->|"verifier raises structured contradiction"| V
  O -.->|"never overwritten"| S["State: external storage"]
#+end_src

* Trust and verifier evidence

A local receipt object may be authoritative only inside its realization context
and authority domain.

Cross-context use requires:

- canonical projection;
- causal identity verification;
- the verifier capability required by the receipt family;
- policy authorization for the consuming context;
- qualification of referenced external outcome evidence.

Cryptographic signatures are one possible verifier mechanism, not the only
one.  The semantic contract names verifier identity and proof coverage without
hard-coding a signature scheme.

Transport success, database presence, or possession of a receipt is not proof
that its claims are trusted.

* Sensitive evidence and redaction

Canonical projections MUST NOT contain raw:

- credentials or secret material;
- provider session tokens;
- runtime handles;
- closure environments;
- continuations;
- capacity permits;
- mutable authority objects.

Sensitive external evidence is represented through a verifier reference,
content digest, controlled artifact identity, or policy-approved redaction
proof.

Redaction cannot remove a semantic field required to verify the receipt.  If a
required field cannot be disclosed or proved through an approved reference, the
receipt is not qualified for that consumer.

Diagnostic annotations follow bounded snapshot and truncation policy.

* Cross-context admission and replay

Cross-context admission and deterministic replay consume canonical causal
identity.  They never import runtime receipt object identity.

A replay evidence artifact explicitly selects a bounded receipt set and
frontier.  It does not:

- activate a global receipt closure;
- require production retention of every receipt;
- equate source and replay roots;
- authorize an external effect merely because a historical receipt exists.

Missing predecessors may be resolved by external policy or produce structured
missing-evidence conditions.  They are not silently assumed.

* Dependency evidence boundary

A build/runtime receipt may include the resolved =gerbil-poo= dependency
revision as source qualification evidence.

This does not:

- project a new dependency declaration;
- replace or extend =gerbil.pkg=;
- make package resolution a POO Flow receipt service;
- turn Bazel, Nix, GSLPH, or a build tool into runtime semantic authority.

The package manager remains Gerbil's package manager.  The receipt only records
already resolved evidence needed by its owning qualification contract.

* Storage and retention boundary

POO Flow defines no mandatory global receipt database, registry, or retention
period.

External policy decides:

- which receipts are persisted;
- how long they are retained;
- access control and encryption;
- indexing and retrieval;
- compaction and archival;
- whether a replay artifact is assembled.

Removing a stored receipt does not mutate another receipt's causal identity.
It may make a later verification frontier incomplete, which produces
missing-evidence rather than fabricated closure.

* Observability contract

Observability projects bounded receipt identity, transition, verifier,
predecessor-role, contradiction, correction, and redaction evidence.

No sink may:

- mutate a receipt;
- establish trust merely by displaying it;
- resolve a contradiction by ordering;
- retrieve secrets through redaction references;
- materialize a global active closure;
- project diagnostic timing into causal identity.

Receipt immutability, contradiction, redaction, and causal-identity conformance
follow
[[file:45-16-semantic-conformance-adversarial-fault-injection.org][Semantic Conformance And Adversarial Fault Injection]].

* API evidence gate

The semantic contract is normative.  Exact receipt prototypes, projection
helpers, canonical encoding, digest algorithm, verifier ABI, and C runtime
representation remain =semantic-required= until they are symbol-located,
behavior-proven, and flow-qualified.

POO Flow MUST extend =gerbil-poo= when a generally reusable POO receipt
mechanism is missing.  It MUST NOT ship a shadow POO runtime or make a raw
serialized record the ordinary Scheme interface.

* Explicit exclusions

This RFC does not authorize:

- serializing runtime POO object identity;
- collapsing causal receipt identity with provider outcome identity;
- diagnostic timestamps or host metadata in causal identity;
- mutable or last-write-wins receipts;
- storage order as causal precedence;
- raw secrets, handles, continuations, or authority in projections;
- a global receipt registry, retention mandate, or active evidence closure;
- redefining =gerbil.pkg= dependency declarations;
- exact encoding or ABI claims before evidence qualification;
- a public raw record/alist receipt DSL.

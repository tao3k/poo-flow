#+title: Resolved Composition Receipt and Package, Source, Build, and Runtime Evidence Separation
#+startup: overview

* Status

Accepted architecture decision.

This RFC continues the ownership and identity separation fixed by
[[file:45-111-profile-ownership-naming-export-identity-and-composition-repository-boundaries.org][45-111]].

* Evidence state

A parser-owned ASP owner search used 45-111 as the exact owner anchor.  It
succeeded.

The receipt confirmed:

- =use-composition= is a thin hygienic binding macro;
- =compose= is a pure function;
- =profiles= is the first-class POO composition strategy;
- =use-module= is a thin module/profile-selection macro;
- repository, submodule, package, Gerbil module, POO module, profile revision,
  and composition identities are distinct;
- =RepositoryIdentity= is reserved for source repository pinning and does not
  identify packages, POO modules, or profiles.

Implementation ownership for =ResolvedCompositionReceipt= remains =MISSING=.
This RFC makes no implementation-completion claim.

* Scope

This RFC defines:

- the minimal semantic composition receipt;
- its relation to the pure composition result;
- separation from =gerbil.pkg=;
- separation from Git repository and submodule pins;
- separation from build and test evidence;
- separation from coordinator and runtime receipts;
- cache-key and invalidation boundaries;
- optional persistence and publication behavior.

This RFC does not define:

- a package lock file;
- dependency installation;
- a new =gerbil.pkg= projection;
- an active evidence closure;
- a mandatory global evidence store;
- a new build receipt format;
- a runtime capability token;
- a composition macro.

* Central decision

=ResolvedCompositionReceipt= is immutable evidence produced by one pure
POO-profile resolution.

It records what semantic values were resolved and why.

It does not:

- fetch source;
- install packages;
- declare dependencies;
- lock transitive packages;
- run builds or tests;
- grant runtime authority;
- activate a composition globally;
- maintain an active evidence closure.

The authoritative package dependency declaration remains =gerbil.pkg=.

* Why a semantic receipt exists

The receipt exists only to support:

- deterministic composition identity;
- cache qualification;
- conflict provenance;
- explanation;
- debugging;
- comparison between composition results;
- admission input identity.

The pure resolved POO value remains the semantic result.

The receipt does not replace the value and does not become a second
configuration language.

* Minimal receipt algebra

=ResolvedCompositionReceipt= is a native POO object.  Its minimal projections
are:

- composition identity;
- composition-strategy identity and revision;
- selected POO module identities;
- selected profile export and immutable revision identities;
- typed contribution and precedence evidence;
- reachable responsibility and semantic-import relation identities;
- resolved capability-shape requirements;
- unresolved requirement and conflict evidence;
- validation outcome;
- content identity of the resolved POO value;
- provenance for the final composition binding.

These are semantic identities.  They are not package dependency declarations.

* Explicit exclusions

The receipt does not contain:

- a transitive package dependency lock;
- Git checkout paths;
- =.data/= evidence paths;
- package installation commands;
- submodule update instructions;
- build-system target graphs;
- GSLPH harness configuration;
- Nix derivations;
- Gerbil-Bazel build definitions;
- live continuation handles;
- runtime capability tokens;
- mutable cache handles;
- mutable active-head state.

Optional diagnostic references may point to separately owned evidence.  They do
not copy that evidence into the semantic identity model.

* Four independent evidence planes

** Source evidence

Source evidence answers:

- which repository revision is pinned;
- which submodule revision is recorded;
- where source provenance originated.

Its owners are Git repositories and parent integration repositories.

** Package and build evidence

Package evidence answers:

- which packages were declared;
- which packages were resolved and installed;
- which Gerbil modules became importable.

Build and test evidence answers:

- which targets were built;
- which test and policy gates ran;
- which artifacts were produced.

=gerbil.pkg=, Gerbil package tooling, Gerbil-Bazel, Nix, and GSLPH retain their
own distinct responsibilities.

** Semantic composition evidence

Semantic composition evidence answers:

- which POO modules and profile revisions were selected;
- how their typed relations composed;
- which requirements became reachable;
- which conflicts or validations survived;
- which pure POO value resulted.

=ResolvedCompositionReceipt= belongs only to this plane.

** Runtime evidence

Runtime evidence answers:

- which principal and capability were admitted;
- which evaluation context and budget were used;
- which effect intent was handed off;
- which continuation or evaluator ran;
- which cleanup, reconciliation, and outcome receipts closed.

Runtime receipts do not become package declarations or semantic profile
exports.

* Evidence ownership matrix

| Evidence | Authoritative owner | Consumed by | Must not become |
|----------+---------------------+-------------+-----------------|
| repository revision | Git repository | source integration | package or profile identity |
| submodule pin | parent Git repository | source checkout | child build/profile ownership |
| package dependency declaration | child package =gerbil.pkg= | Gerbil package tooling | semantic composition receipt |
| build artifact receipt | build system | testing and deployment | POO profile export |
| GSLPH test/policy receipt | development harness | development validation | runtime capability provision |
| resolved composition receipt | pure =profiles= composition | explanation, cache, admission | package lock or active evidence closure |
| coordinator admission receipt | coordinator | runtime handoff | dependency declaration |
| runtime outcome receipt | runtime/control plane | observation and recovery | profile export identity |

Each receipt remains authoritative only for its own question.

* Package dependency boundary

=gerbil.pkg= remains the sole Gerbil package dependency declaration.

POO Flow does not generate an exact =gerbil.pkg= projection from:

- selected profiles;
- reachable POO semantic imports;
- a composition receipt;
- runtime observations;
- active outcomes.

A semantic import relation and a Gerbil package dependency are not the same
relation.

The package manager makes code importable.  POO composition operates on the
POO-native values provided by already available code.

* Submodule boundary

A submodule pin may make child source available in the parent source tree.

It does not:

- declare a Gerbil package dependency;
- make the child package installed;
- resolve a POO module;
- select a profile;
- become part of a semantic composition receipt.

If parent integration needs both a submodule and a package declaration, each is
maintained by its own owner and contract.

* Build and test boundary

Gerbil-Bazel, Nix, and other build systems may produce build evidence.

GSLPH may produce development policy, harness, build, and test evidence.

Those receipts may validate that expected code and tests exist.  They do not
contribute runtime POO capabilities or profile facets.

The semantic receipt may reference a validation receipt for diagnostics when
policy requires it.  The reference does not transfer ownership or merge the
two receipt schemas.

* Composition lifecycle

The ordered lifecycle is:

1. source is made available by repository and optional submodule mechanisms;
2. =gerbil.pkg= and package tooling make required Gerbil code importable;
3. build systems produce required artifacts;
4. imported code constructs native POO module and profile values;
5. =compose= with =profiles= resolves those values purely;
6. a =ResolvedCompositionReceipt= describes that pure result;
7. a live demand independently requests coordinator admission;
8. runtime handoff and terminal receipts describe execution.

Later stages do not retroactively redefine earlier identities.

* Lifecycle graph

#+begin_src mermaid
flowchart LR
  G["Git repository or submodule pin"] -->|"source revision becomes available without semantic ownership"| S["Available source"]
  P["gerbil.pkg"] -->|"package tooling resolves declared dependencies"| L["Importable Gerbil modules"]
  S -->|"build system consumes pinned source"| B["Build artifacts"]
  L -->|"Gerbil imports expose constructors and values"| M["Native POO modules and profiles"]
  B -->|"artifact availability satisfies load boundary"| M
  M -->|"pure compose with profiles strategy resolves semantic graph"| C["Resolved POO composition"]
  C -->|"immutable semantic provenance is projected"| R["ResolvedCompositionReceipt"]
  R -->|"receipt identity qualifies explanation and semantic cache"| E["Semantic inspection"]
  R -->|"fresh principal and policy request admission"| A["Coordinator admission"]
  A -->|"accepted demand projects into existing effect intent"| H["Runtime handoff"]
  H -->|"cleanup and reconciliation close execution"| O["Runtime outcome receipts"]
#+end_src

No edge projects the semantic receipt back into =gerbil.pkg=.

* No active evidence closure

There is no =active evidence closure= object in this architecture.

A composition receipt is:

- immutable;
- specific to one pure resolution;
- optionally retained;
- optionally published;
- never mutated into a global dependency or runtime state container.

Re-evaluating composition produces either:

- the same content identity and an idempotently equivalent receipt; or
- a new resolved value and a new receipt.

If an application publishes a currently selected composition, that is a
separate active-head publication decision.  It does not mutate the receipt or
turn the receipt set into an active closure.

* Persistence boundary

Persistence is optional.

A local composition may keep the receipt only as an in-memory POO value.

A system that needs replay, cross-process explanation, audit, or cache reuse may
persist the immutable receipt through an explicitly selected evidence adapter.

Persistence policy does not alter composition semantics.

No global database is required by the user interface.

* Cache separation

The architecture has separate cache identities:

| Cache | Key material | Invalidated by |
|-------+--------------+----------------|
| source/package cache | repository revision, package declaration, toolchain | source or dependency change |
| build artifact cache | source, build graph, compiler/toolchain | build-input change |
| semantic composition cache | POO module/profile revisions, composition strategy, typed relations | semantic input change |
| admitted runtime cache | demand, evaluation context, policy, evaluator, qualified outcome | runtime admission/version change |
| replay/simulation cache | isolated replay or simulation lineage | lineage or replay-input change |

No cache entry is promoted across these boundaries merely because identifiers
appear related.

* Semantic cache key

The semantic composition cache key is derived from:

- POO module identities and revisions;
- profile export identities and revisions;
- composition-strategy identity and revision;
- typed contribution and precedence relations;
- relevant resolution-policy identity.

It is not derived from:

- local checkout path;
- submodule directory name;
- build target label;
- test harness name;
- live runtime capability;
- mutable active-head status.

* Invalidation behavior

A package or source update may load a different POO module or profile revision.
That changed semantic identity causes a composition cache miss or new receipt.

The semantic layer does not:

- run package update;
- rewrite =gerbil.pkg=;
- move a submodule pin;
- rebuild an artifact;
- infer package changes from a runtime outcome.

Invalidation flows forward through changed identities.  It does not flow
backward as a package-management side effect.

* Failure classification

Failures remain typed by their owner:

| Failure | Owning plane |
|---------+--------------|
| missing repository or submodule revision | source integration |
| package dependency or import unavailable | Gerbil package/import system |
| build target or artifact failure | build system |
| GSLPH policy or test failure | development harness |
| POO module/profile export absent | semantic composition |
| typed profile relation conflict | semantic composition |
| authority, budget, or policy denial | coordinator admission |
| continuation, evaluator, cleanup, or reconciliation failure | runtime/control plane |

A package import failure is not reported as a profile conflict.

A runtime denial is not reported as a package dependency failure.

* Receipt reference rules

Cross-plane references are allowed only as typed evidence references.

A reference:

- preserves the owner receipt identity;
- does not copy ownership;
- does not reinterpret fields;
- does not make the referenced receipt part of the referencing schema;
- cannot grant authority;
- can be absent when not required by policy.

The semantic receipt therefore may explain which separately verified artifact
was loaded without becoming that artifact's lock or build receipt.

* Public interface boundary

The ordinary user interface remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

The user does not pass:

- package locks;
- submodule paths;
- build receipts;
- evidence databases;
- runtime receipt constructors;
- active-closure options.

Advanced inspection consumes the POO-native resolved composition and its
receipt through the existing debug-demand interface.

* Evidence-flow separation

#+begin_src mermaid
flowchart TD
  SRC["Source evidence"] -->|"proves source revision only"| PKG["Package and load evidence"]
  PKG -->|"makes Gerbil definitions available without selecting profiles"| SEM["Semantic composition evidence"]
  BUILD["Build and test evidence"] -.->|"validates artifacts without contributing profile semantics"| SEM
  SEM -->|"provides immutable composition identity, not authority"| ADM["Admission evidence"]
  ADM -->|"authorizes one bounded execution"| RUN["Runtime evidence"]
  RUN -.->|"may trigger a new explicit composition demand but never rewrites prior receipt"| SEM2["New semantic composition evaluation"]
  SEM -.->|"optional typed reference preserves separate owner"| BUILD
#+end_src

The dotted references are evidence links, not ownership transfer.

* Failure behavior

The system fails closed on:

- a composition receipt used as a package lock;
- semantic imports projected into =gerbil.pkg=;
- a submodule path embedded as durable semantic identity;
- build or GSLPH receipts treated as runtime capability;
- runtime outcomes rewriting package declarations;
- a mutable active evidence closure;
- cross-plane cache promotion;
- missing owner identity on a cross-plane evidence reference;
- package/load failure mislabeled as semantic conflict;
- runtime admission failure mislabeled as package failure.

- [X] There is no active evidence closure.

- [ ] The resolved composition value and receipt are native POO objects.
- [ ] Receipt projections contain semantic identities only.
- [ ] No package lock or dependency projection is generated.
- [ ] Source paths and submodule directories are absent from durable semantic

- [ ] Admission and runtime receipts grant no package or profile ownership.

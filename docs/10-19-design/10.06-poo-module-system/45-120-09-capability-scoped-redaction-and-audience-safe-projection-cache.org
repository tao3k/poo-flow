#+title: Capability-Scoped Redaction and Audience-Safe Projection Cache
#+startup: overview

* Status

The architecture in this RFC is accepted.

This acceptance freezes diagnostic visibility, redaction, delegation,
and projection-cache semantics.  It does not admit implementation
files, disclosure categories, storage backends, renderer schemas, or a
public macro surface.

* Scope

This RFC defines how immutable internal diagnostic evidence becomes a
safe projection for a particular consumer and purpose.

It covers:

- visibility capability and presentation policy;
- structured field-level redaction;
- purpose and consumer binding;
- safe exception normalization;
- cross-Module visibility delegation;
- audience-safe projection caching;
- redaction receipts;
- renderer and telemetry boundaries.

* Central decision

Redaction occurs over structured evidence before text rendering,
serialization, persistence, API delivery, or telemetry publication.

A renderer receives only an admitted safe projection.  It never
receives complete internal evidence and then removes fields itself.

Visibility capability defines the maximum evidence that may be
disclosed.  Profile presentation policy may select a less detailed
projection, but it cannot widen visibility.

Recovery execution capability and diagnostic visibility capability are
independent authorities.  Possessing one does not imply the other.

* Internal evidence minimization

Internal diagnostic evidence contains the semantic facts required for
explanation, authorization, recovery, and lineage.  It does not embed
raw continuation handles, credentials, secret material, or unrestricted
runtime objects.

When a protected value is relevant to diagnosis, evidence refers to an
admitted opaque identity, classification, provenance, or secure owner.
It does not copy the protected value into a diagnostic field.

This minimization applies before redaction.  Redaction is not a license
to accumulate arbitrary secrets in an internal event.

* Visibility capability

A diagnostic visibility capability is a native POO value that bounds:

- the consumer identity or consumer class;
- the source Module and responsibility scope;
- the evidence categories that may be disclosed;
- the permitted projection purpose;
- the eligible generations;
- expiration and revocation conditions;
- required provenance or Contract evidence;
- cross-Module delegation lineage.

The RFC term =VisibilityCapability= is a semantic role.  It does not
automatically freeze a public constructor, record, or macro name.

Visibility authority does not arise from import reachability, recovery
authority, profile priority, renderer availability, deployment role,
or possession of a diagnostic identifier.

* Presentation policy

A presentation policy is a profile-composed native POO value.  Within
the admitted visibility capability it may choose:

- verbosity;
- ordering and grouping;
- localization;
- pagination;
- explanatory emphasis;
- a more restrictive evidence subset.

It cannot disclose a category absent from the visibility capability,
change semantic cause or lineage, reveal an opaque protected value, or
convert a hidden field into a free-form explanation.

Higher profile priority affects presentation preference only.  It does
not override visibility authority.

* Projection authorization and redaction

Every projection request binds:

- source diagnostic evidence identity;
- consumer identity;
- active visibility capability identity;
- presentation-policy identity;
- projection schema identity;
- declared purpose;
- source and capability generation evidence.

Projection authorization validates all of those identities before field
selection or rendering.

Missing, ambiguous, incomplete, expired, revoked, or purpose-mismatched
visibility evidence fails closed.  The result is a minimal safe
diagnostic rather than a best-effort disclosure.

The minimal diagnostic may identify a safe diagnostic identity,
non-sensitive failure class, evidence-owner contact boundary, and the
visibility evidence needed for a fuller projection.  It cannot reveal
the hidden value through field names, counts, lengths, formatting,
timing, or error details.

* Safe exception normalization

Raw exception messages and printed runtime objects may contain paths,
credentials, user data, source fragments, addresses, or capability
material.

The exception bridge therefore derives an admitted stable
classification and structured safe fields before diagnostic
projection.  It MUST NOT copy a raw exception string into a public or
telemetry projection.

When the raw exception is required for privileged investigation, the
semantic diagnostic contains only an opaque secure reference and
ownership evidence.  Access to the protected artifact follows a
separate explicitly authorized boundary.

Raw continuation handles remain unavailable even to the most detailed
serializable diagnostic projection.

* Cross-Module visibility delegation

Importing a Module makes evidence reachable to semantic closure.  It
does not grant permission to disclose that evidence.

Cross-Module visibility requires an explicit native POO delegation that
binds:

- delegating visibility capability;
- consumer;
- target Module and responsibility;
- evidence categories;
- purpose;
- eligible generations;
- expiration and revocation;
- non-widening proof and parent delegation lineage.

Every delegation may preserve or reduce visibility.  It cannot widen
the parent capability.  An unrooted visibility-delegation cycle grants
no visibility.

Recovery delegation and visibility delegation remain distinct.  A
recovery coordinator may execute an authorized action while receiving
only the minimum diagnostic projection required for that action.

* Audience-safe projection cache

A safe projection may be cached only under an immutable key containing:

- source diagnostic evidence identity;
- consumer identity or admitted equivalence class;
- visibility capability identity;
- presentation-policy identity;
- projection schema identity;
- declared purpose;
- all relevant generation identities.

A projection cached for one audience, purpose, capability, policy, or
schema cannot answer another key without an explicit equivalence proof.

Cache storage, eviction, encryption, and physical placement are runtime
concerns.  A cache failure cannot broaden disclosure or fall back to an
unredacted diagnostic.

* Redaction receipt

Every projection produces an immutable receipt identifying:

- source evidence identity;
- consumer, capability, schema, policy, and purpose identities;
- the categories admitted, withheld, or unavailable;
- the authorization and delegation evidence;
- projection generation and cache disposition;
- the reason for minimal or denied disclosure.

The receipt describes categories and decisions without copying hidden
values, secret-derived lengths, raw exception text, or continuation
handles.

* Renderer and telemetry boundary

Renderers consume only safe projections.  They may format, localize,
paginate, filter within the admitted projection, or suppress additional
fields.

They cannot request hidden values through free-form templates,
reconstruct redacted evidence, combine audiences to widen disclosure,
or treat renderer-specific data as semantic truth.

Telemetry uses an explicitly purpose-bound visibility capability and
the minimum admitted projection.  Telemetry availability, delivery,
retention, and correlation cannot feed back into semantic authority or
diagnostic visibility.

* Implementation admission checklist

- [ ] Minimize protected values before redaction.
- [ ] Exclude raw continuations, credentials, secret material, and
  unrestricted runtime objects from diagnostic evidence.
- [ ] Perform structured field-level redaction before rendering,
  serialization, persistence, API delivery, or telemetry.
- [ ] Give renderers only admitted safe projections.
- [ ] Keep recovery and visibility capabilities independent.
- [ ] Bind projection to source evidence, consumer, visibility
  capability, policy, schema, purpose, and generations.
- [ ] Prevent profile priority from widening visibility.
- [ ] Normalize raw exception data before public projection.
- [ ] Fail closed to a minimal safe diagnostic when visibility evidence
  is missing or invalid.
- [ ] Prevent hidden values from leaking through metadata, formatting,
  timing, or error details.
- [ ] Require explicit non-widening visibility delegation across Module
  boundaries.
- [ ] Derive no visibility from imports or unrooted delegation cycles.
- [ ] Include audience, capability, policy, schema, purpose, and
  generation identities in projection cache keys.
- [ ] Prevent cache fallback from broadening disclosure.
- [ ] Emit a non-leaking immutable redaction receipt.
- [ ] Keep telemetry one-way and purpose-bound.
- [ ] Add no public redaction, secret-handling, or visibility macro.
- [ ] Apply authoritative evidence, disposable cache, telemetry, handle
  registry, and pure replay boundaries in
  [[file:45-120-10-authoritative-evidence-cache-telemetry-handle-registry-and-pure-replay.org][45-120-10]].

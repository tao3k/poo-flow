#+title: Structured Diagnostic Evidence and Exception Bridge
#+startup: overview

* Status

The architecture in this RFC is accepted.

This acceptance freezes diagnostic facts, projections, recovery-option
semantics, and the exception bridge.  It does not admit implementation
files, command names, renderer schemas, or a public macro surface.

* Scope

This RFC defines the first structured diagnostic emitted for closure,
cycle, cache, budget, Contract, capability, delegation, recovery, and
runtime materialization failures.

It also defines:

- pure human and machine explanation projections;
- shared recovery-option values;
- interactive and automated selection semantics;
- the Gerbil exception and continuation bridge;
- renderer and telemetry ownership boundaries.

* Central decision

The source of diagnostic truth is immutable native POO evidence, not a
text log.

Human explanation, automated recovery policy, Org or CLI rendering,
user interfaces, and telemetry consume projections of the same
diagnostic evidence.  None of those consumers may establish an
independent semantic account of the failure.

Selecting a displayed recovery option proposes a =RecoveryDecision=.
It does not grant authority.  Capability, Contract, current-generation,
and budget validation still determine whether the proposal may execute.

* Structured diagnostic evidence

The first diagnostic for a semantic failure MUST identify:

- the diagnostic and source evidence identities;
- the owning Module and responsibility;
- the evaluation generation and phase;
- the exact failure class and cause;
- the dependency frontier;
- SCC or cycle evidence when present;
- typed closure-evaluation or recovery-action budget evidence;
- semantic cache hit, miss, conflict, or reuse disposition;
- relevant Contract, capability, delegation, and profile-policy
  evidence;
- the last admitted semantic result or refinement;
- the available pure inspections and candidate recovery options.

Runtime resource observations MAY accompany the diagnostic as a
separate projection.  They MUST NOT replace the semantic cause or
semantic budget evidence.

The RFC term =DiagnosticEvidence= is a semantic role.  It does not
automatically freeze an exported constructor, record, or macro name.

* First-response timing

The evaluator and coordinator emit structured evidence when the
condition is first known to violate an admitted semantic or runtime
boundary.

Cycle recognition MUST precede unbounded Scheme recursion.  Typed
budget exhaustion MUST be reported at the exhausting semantic step.
Cache conflicts MUST be reported before selecting a result.  Stale
generation or authorization evidence MUST be rejected before executing
a recovery action.

If an infrastructure failure prevents complete semantic evidence from
being produced, the receipt explicitly identifies that loss of
evidence.  It MUST NOT fabricate a semantic diagnosis from partial logs.

* Pure diagnostic projections

A diagnostic projection is a pure function of immutable evidence and
an admitted projection schema.

Supported semantic views include:

- why this result or denial occurred;
- the evidence and generation lineage;
- the active dependency frontier;
- SCC membership and incoming root evidence;
- cache disposition and dependency identities;
- typed budget allocation and consumption;
- candidate recovery alternatives and their required authority.

Inspecting or rendering a projection does not create a new evaluation
generation, consume a recovery budget, invoke a continuation, or mutate
the diagnostic.

A projection cannot read current mutable runtime state and present it as
historical semantic evidence.  Live runtime data remains a separately
identified observation.

* Shared recovery-option values

A recovery option is a native POO value derived from diagnostic
evidence.  It identifies:

- the source diagnostic and generation;
- the candidate action kind;
- the target Module and responsibility;
- the required capability and Contract evidence;
- the required typed budget;
- the expected successor-evidence shape;
- a pure explanation of its consequences.

An option is a candidate, not authorization.  Human selection and
automated policy selection produce the same kind of pure
=RecoveryDecision= proposal.

An adapter MUST return the selected option identity.  It MUST NOT
construct an unlisted action, widen the option, embed a raw continuation
handle, or bypass authorization.

* Exception and continuation bridge

Gerbil exceptions, continuable exceptions, and first-class
continuations are runtime mechanisms.  The bridge normalizes an
admitted runtime interruption into structured diagnostic evidence.

The bridge records:

- the semantic evaluation or coordinator boundary;
- the owning Module and generation;
- a stable exception classification and admitted explanation;
- the recovery-point identity when continuation is possible;
- the evidence loss when normalization is incomplete.

The raw exception object is not the governance protocol.  A raw
continuation handle is never a diagnostic field, renderer value,
telemetry value, recovery option, or persistent receipt.

When a continuable exception retains a recovery point, only the runtime
coordinator holds the continuation handle.  Semantic evidence refers to
the recovery-point identity and invocation bounds.  Authorization
precedes every invocation.

* Renderer and adapter boundary

CLI, Org, graphical UI, API, and telemetry renderers are projection
adapters.  They may choose layout, localization, filtering, pagination,
and redaction appropriate to their consumer.

They may not:

- reinterpret semantic cause or lineage;
- infer authority from display priority;
- introduce renderer-specific recovery actions;
- parse free-form log text as authoritative evidence;
- expose raw capabilities, continuations, secrets, or unredacted
  provenance;
- write runtime observations back into semantic evaluation.

Renderer output is replaceable.  Structured diagnostic evidence remains
the source of truth.

* Public and advanced extension boundary

Ordinary users inspect explanations and select admitted option
identities through an adapter.  They do not write continuation handlers,
exception clauses, trace mutations, or recovery macros in the Module
composition interface.

Advanced diagnostic projections, recovery options, and policies are
native =gerbil-poo= values composed through existing POO and functional
boundaries.

A later RFC may admit a hygienic projection macro only when necessary
syntax or phase semantics cannot be represented by ordinary functions
and native POO values.

* Implementation admission checklist

- [ ] Emit immutable structured evidence rather than requiring log
  parsing.
- [ ] Identify owner, responsibility, generation, frontier, exact
  cause, SCC, typed budget, and cache disposition when applicable.
- [ ] Distinguish incomplete infrastructure evidence from a semantic
  diagnosis.
- [ ] Use one diagnostic fact source for human, policy, UI, Org, CLI,
  API, and telemetry projections.
- [ ] Keep all semantic inspection projections pure.
- [ ] Ensure inspection does not create a generation or consume a
  recovery budget.
- [ ] Represent candidate recovery options as native POO values.
- [ ] Treat human and automated selection as the same kind of pure
  decision proposal.
- [ ] Require authorization after every option selection.
- [ ] Keep raw exceptions and continuations outside semantic evidence.
- [ ] Keep continuation handles private, ephemeral, coordinator-owned,
  and invocation-bounded.
- [ ] Require adapters to return option identity rather than construct
  arbitrary actions.
- [ ] Keep renderer-specific layout and localization outside semantic
  interpretation.
- [ ] Redact secrets, capabilities, continuations, and provenance before
  external projection.
- [ ] Add no public debug, exception, continuation, or recovery macro.
- [ ] Apply capability-scoped redaction and audience-safe projection
  caching in
  [[file:45-120-09-capability-scoped-redaction-and-audience-safe-projection-cache.org][45-120-09]].

#+title: Native gerbil-poo Operation Surface
#+startup: overview

* Status

Accepted design.

The POO Module System adopts the native operation surface of =gerbil-poo= as
its core object language.  It does not reduce POO to =.mix=, wrap the library
behind a record DSL, or replace native operations with Profile feature
selectors.

This document is based on the upstream documentation:

- [[https://github.com/mighty-gerbils/gerbil-poo/blob/master/doc/poo.md][Prototype
  Object Orientation in Gerbil Scheme]];
- [[https://github.com/mighty-gerbils/gerbil-poo/blob/master/doc/prototypes.md][Prototype
  Object Programming in Gerbil Scheme]].

The canonical package dependency is:

#+begin_example
github.com/mighty-gerbils/gerbil-poo@1c3225637525400341a09e958296962c10184ead
#+end_example

The module-semantic role of each operation family is defined separately by
[[file:45-27-native-poo-operations-as-module-semantics.org][45-27]].

* Decision

The core syntax is the complete family of native operations needed to define,
refine, compose, demand, invoke, inspect, and explicitly manipulate POO
objects.

The families are:

1. prototype and object definition;
2. open-recursive slot computation;
3. inheritance and object composition;
4. lazy slot demand and method invocation;
5. nested-object traversal;
6. object reflection;
7. explicit effectful instance and prototype manipulation;
8. instantiation lifecycle.

These are not separate configuration languages.  They are aspects of one POO
object model in which an object carries both a composable prototype and its
demand-lazy fixed-point instance.

* Prototype definition

The native definition forms are =.o= and =.def=.

=.o= defines an object prototype directly:

#+begin_example
(.o [([:: [self [super [extra-slots ...]]]])]
  slot-definitions ...)
#+end_example

=.def= binds a name to the corresponding native object:

#+begin_example
(.def (name self super extra-slots ...)
  slot-definitions ...)
#+end_example

The parameters have semantic meaning:

- =self= refers to the final instance being computed;
- =super= declares one or more direct super-prototypes;
- =extra-slots= introduces hygienic lazy access to slots supplied by other
  prototypes in the final object.

These constructs directly express imports, open recursion, and cross-slot
dependency.  The POO Module System must use them rather than translating
module definitions into an alist or record description.

The brace syntax from =gerbil-poo= is an alternative surface for =.o=.  It is
part of the native language family, not a JSON-like configuration format.

* Slot-computation forms

Native slot definitions provide several distinct refinement operations.

** Override

#+begin_example
(slot-name form)
slot-name: form
#+end_example

The computation ignores the inherited computation and supplies a more-specific
value.

** Inherited combination

#+begin_example
(slot-name => combining-function extra-arguments ...)
slot-name: => combining-function extra-arguments ...
#+end_example

The inherited result is always demanded and passed through the combining
function.  This is the ordinary native form for accumulating evidence,
Capabilities, imports, diagnostics, and receipts.

** Nested prototype refinement

#+begin_example
(slot-name =>.+ overriding-prototype)
slot-name: =>.+ overriding-prototype
#+end_example

The slot contains a POO object and is refined with another prototype.  This is
central to recursive submodules and nested fixed-point objects.

** General inherited computation

#+begin_example
(slot-name (next)
  form)
#+end_example

The slot computation explicitly decides when to demand the inherited
computation.  =next= is native inherited-computation syntax, not the public raw
=(lambda (self super) ...)= interface rejected by this project.

** Lexical slot binding

#+begin_example
(slot-name)
slot-name
#+end_example

The slot takes the value of the same-named lexical binding.

** Default

#+begin_example
(slot-name ? default-value)
slot-name: ? default-value
#+end_example

Defaults provide the base of inherited recursion and remain distinct from
ordinary overriding values.

* Composition and inheritance

=.mix= composes any number of objects or recursively nested object lists:

#+begin_example
(.mix object1 [object2 [object3 object4] object5] object6)
#+end_example

Earlier, leftmost, more-specific prototypes take precedence over later,
rightmost super-prototypes.  Inherited slot computations delegate along that
native precedence chain.

=.mix= is therefore one operation within the language, not the complete POO
abstraction.

The higher-order fixed-point operand from
[[file:45-25-native-poo-fixed-point-operand-composition.org][45-25]] uses the
definition, slot-refinement, composition, demand, and reflection operations
together.

* Lazy slot demand

The native access operations are:

- =.ref= for a dynamically named slot;
- =.get= and =.@= for statically named and nested slot access;
- =.call= for invoking a function-valued method slot.

Slot demand implicitly instantiates the object and closes the open-recursive
slot computations through the native fixed point.

Access is demand-lazy:

- unused slots remain unevaluated;
- missing base definitions fail only when demanded;
- nested objects instantiate only at their point of use;
- a method is an ordinary function-valued slot;
- POO Flow must not add a second force, cache, or evaluator layer.

* Nested objects and submodules

A slot value may itself be a POO object.  Native nested access can traverse:

#+begin_example
(.get object parent child capability)
#+end_example

Nested objects retain both prototype and instance behavior.  They may refer
back to surrounding objects and may be refined through ==>.+= without deciding
eagerly where instantiation occurs.

This native recursive-object property is the basis for:

- submodules under submodules;
- parent, child, and sibling Capability visibility;
- To-B and To-C nested module structures;
- recursive fixed-point configuration;
- demand-lazy child realization.

The POO Module System must not flatten nested objects into paths or registries.

* Reflection

The documented native reflection family includes:

- =object?= to recognize a POO object;
- =.key?= to test whether an object defines a slot;
- =.has?= for statically named nested slot checks;
- =.all-slots= to inspect the available slot set.

Reflection operates on the object itself.  It does not require a parallel
Profile registry, string-keyed manifest, or provider index.

POO Flow may build stronger identity, provenance, Capability, and diagnostic
views from these native operations and the =gerbil-poo= MOP, but it must not
replace native object reflection.

* Explicit effectful operations

=gerbil-poo= also documents native effectful operations:

- =.put!= and =.set!= mutate an instance slot;
- =.putslot!= and =.setslot!= modify prototype slot definitions;
- =.def!= adds a prototype slot definition after object creation;
- =.putdefault!= changes a slot default;
- =uninstantiate-object!= invalidates a previously materialized instance.

Their supporting slot-spec constructors include constant, thunk, self, and
computed slot specifications.

These operations are part of the core native vocabulary.  They are not
reimplemented behind a POO Flow patch language.

They are effectful and therefore cross an explicit lifecycle boundary.  They
must not silently mutate canonical semantic evidence already used by a
fixed-point generation.

An effectful operation that changes relevant instance or prototype state must:

1. identify the target object and affected generation;
2. possess the required control authority;
3. emit immutable mutation-intent evidence;
4. perform the native operation;
5. invalidate or close affected instantiated state;
6. create a successor generation;
7. emit an outcome receipt.

This preserves the project invariant that ordinary composition is pure while
still treating the complete native =gerbil-poo= surface as first-class.

* Pure and effectful native families

Core vocabulary does not mean that every operation is valid in every plane.

The ordinary semantic path uses:

- =.o= and =.def=;
- native slot-computation forms;
- =.mix=;
- =.ref=, =.get=, =.@=, and =.call=;
- nested objects;
- native reflection.

Effectful mutation and uninstantiation belong behind explicit recovery,
debugging, runtime, or lifecycle authority.

Both families remain native =gerbil-poo=.  The distinction is about causal and
authority boundaries, not about replacing one family with a new DSL.

* Macro and phase boundary

Gerbil hygienic macros may:

- generate repeated =.o= or =.def= families;
- validate statically known slot vocabularies;
- expand declarative module declarations to ordinary native slot forms;
- preserve syntax provenance for diagnostics.

Macros must emit ordinary native POO expressions.  They must not serialize an
alternate AST for runtime interpretation.

Runtime does not reparse =.o=, =.mix=, slot specs, or access operations from
symbols.

* Replay

Replay reconstructs the native operation family that contributed to each
generation:

- prototype definitions and inheritance identities;
- slot-computation and default identities;
- nested prototype refinements;
- demanded access paths;
- reflection evidence when semantically retained;
- authorized effectful operation intents;
- instance invalidation and successor-generation receipts.

Replay does not rerun an unrecorded mutation, rebuild objects from an alist
facade, or reinterpret printed syntax.

* Runtime and ownership boundary

=gerbil-poo= owns the native object representation, syntax, inheritance, lazy
instantiation, reflection primitives, and effectful operations.

POO Flow uses and extends those objects with module, Capability, identity,
provenance, condition, authority, observability, and receipt semantics.

POO Flow does not fork or reimplement the fixed-point object system.

The harness validates the operation contracts and lifecycle receipts.  It is a
development dependency and not a provider of POO semantics.

* Implementation checklist

- [ ] Treat the complete native =gerbil-poo= operation family as the core
      object language.
- [ ] Use =.o= and =.def= for prototype definitions.
- [ ] Preserve =self=, =super=, and extra-slot open recursion.
- [ ] Use native override, inherited combination, ==>.+=, general inherited
      computation, lexical binding, and default slot forms.
- [ ] Use =.mix= as native inheritance composition rather than as the entire
      abstraction.
- [ ] Use =.ref=, =.get=, =.@=, and =.call= for lazy demand.
- [ ] Preserve nested POO objects for recursive submodules.
- [ ] Build stronger views without replacing native reflection.
- [ ] Keep native effectful operations available behind explicit authority and
      lifecycle boundaries.
- [ ] Create successor generations for semantically relevant native mutation.
- [ ] Expand hygienic macros directly to native POO expressions.
- [ ] Avoid alist, record, patch-language, registry, and evaluator facades.
- [ ] Replay canonical operation and generation evidence.
- [ ] Test every adopted native operation family against the pinned
      =gerbil-poo= package.
- [ ] Verify that Mermaid edges explain the relevant state or transition
      without mechanical label prefixes.

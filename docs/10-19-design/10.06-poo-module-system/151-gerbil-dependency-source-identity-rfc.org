* Current decision (corrected 2026-07-27)

The root =gerbil.pkg= is the only POO Flow declaration of Gerbil package
dependencies. POO Flow MUST NOT copy those dependencies into a Scheme object,
POO prototype, JSON contract projection, test fixture, or generated module
fragment and then treat that copy as canonical package identity.

Gerbil-Bazel may carry the additional immutable revision, archive URL,
SHA-256, and strip-prefix data required for hermetic Bzlmod materialization.
Those values are build-adapter inputs and lock data, not a POO Flow domain
contract. Gerbil-Bazel emits the observed source-resolution receipt after
materialization. A machine-local source path is not canonical identity.

The POO Flow Bazel target calls the Gerbil-Bazel
=gerbil_project_compile= library API. Gerbil-Bazel owns receipt construction,
schema validation, and dependency-source-resolution validation. POO Flow does
not wrap that contract in a local Starlark test rule or Scheme validator.

* Historical decision (superseded 2026-07-27)

The POO contract is the only canonical owner of dependency-source identity.
=gerbil.pkg=, =gerbil deps= output, Bzlmod tags, archive URLs, lockfile state,
and source-resolution receipts are projections or observations of that
contract; none may silently become a competing owner.

The canonical identity contains the logical package, canonical repository URI,
immutable revision, archive content digest, and projection schema/version. A
machine-local source path is not part of that identity.

=GERBIL_PATH= owns the Gerbil workspace/build environment. Its =pkg=
subdirectory may be consulted by an explicitly local developer provider, but
it is mutable runtime state. =GERBIL_LOADPATH= is a compiled-module lookup
path derived after materialization. It cannot prove source provenance, and it
must not be used to resolve dependency-source identity. Gerbil does not define
a separate canonical =GERBIL_LIB_PATH= owner for this purpose.

The ordinary Bazel lane is hermetic: the POO contract deterministically emits
=gerbil-dependencies.MODULE.bazel=; =gerbil-bazel= downloads the declared
revision, verifies SHA-256 before exposure, and emits
=gerbil-bazel.dependency-source-resolution-receipt.v1= with
=resolutionMode=hermetic-archive=. Local checkout resolution remains a named
fallback and must fail closed on missing source, compiled-only state,
ambiguity, revision mismatch, or URI mismatch.

* Historical decision (superseded 2026-07-23)

The canonical dependency declaration is the identified and versioned entry in
=gerbil.pkg=. A logical package name such as =gerbil-poo= is not a source
identity.

=gerbil-bazel= owns dependency-source resolution and the resolution receipt
because =project_dependency_sources_repository= and the module-extension
projection live there. GSLPH is a downstream build-framework consumer; it does
not own the declared dependency identity or the resolver, and it may not weaken
either to a logical package name.

Bazel consumes only a successful, provenance-bearing source resolution. A
compiled package directory such as =.gerbil/lib= is not evidence of a source
snapshot.

* Qualification root cause receipt (historical)

=bazel mod show_repo= exposes the generated repository contracts:

#+begin_example
project_dependency_sources_repository(
  package = "gerbil-poo",
  project_library_relative_path = ".gerbil/lib",
)
#+end_example

The generated identity omits:

- canonical namespace and repository URI;
- pinned revision;
- manifest digest;
- source snapshot digest;
- resolver identity and version;
- selection cardinality;
- provenance from declaration to selected checkout.

The local package registry simultaneously exposes =git.cons.io/...@master= and
=github.com/...@master= identities, while =gerbil.pkg= declares commit-pinned
=github.com= dependencies. Name-only resolution cannot distinguish them.

* Historical path-qualified identity (superseded 2026-07-23)

A declared dependency identity MUST carry:

| Field | Meaning |
|-
| =logical-name= | Human-readable package name |
| =canonical-namespace= | Registry or repository namespace |
| =canonical-uri= | Normalized repository identity |
| =revision= | Immutable commit or content revision |
| =manifest-digest= | Digest of the declaring =gerbil.pkg= projection |

Local absolute paths and mutable branch names are runtime observations, not
canonical identity fields.

The declared canonical package path is interpreted relative to the directory owned by =project_root_marker=.
The resolver MUST NOT silently reinterpret it as relative to =.gerbil/pkg=; that directory is selected only when the declaration itself names it.
When the package path selects a subdirectory of a Git checkout, =sourceSnapshotDigest= is the Git tree identity of that package subtree and immutable materialization archives only that subtree, not the containing monorepo.

* Source resolution receipt

Schema identity:

#+begin_example
poo-flow.gerbil.dependency-source-resolution-receipt.1
#+end_example

The receipt MUST carry:

- declared dependency identity and manifest digest;
- resolver id and version;
- candidate count;
- selected canonical namespace, URI, and revision;
- source snapshot digest;
- source-owner count and source-kind summary;
- resolution outcome;
- causal receipt digest when replaying a prior resolution.

Allowed outcomes are =resolved=, =replayed=, =missing=, =ambiguous=,
=revision-mismatch=, =digest-mismatch=, =identity-mismatch=, and
=compiled-artifact-only=.

=resolved= is valid only when exactly one candidate matches every canonical
identity field and yields a non-empty source snapshot digest.

* Fail-closed resolution

Let \(D\) be the declared dependency identity, \(C(D)\) the matching source
candidates, and \(R(D)\) the resolution operation.

#+begin_src typst
#let resolves(D, C) = $ abs(C(D)) = 1 $
#let receipt(D, C) = $ R(D) = cases(
  "resolved", if abs(C(D)) = 1,
  "missing", if abs(C(D)) = 0,
  "ambiguous", if abs(C(D)) > 1,
) $

$ resolves(D, C) iff abs(C(D)) = 1 $

$ abs(C(D)) != 1 => not exists r:
  r.outcome = "resolved" and r.dependency = D $
#+end_src

Zero candidates and multiple candidates are both terminal non-resolution
states. Search order, registry order, filesystem order, or a previously
compiled artifact MUST NOT break the tie.

* Exactly-once source materialization

The materialization key is derived from canonical dependency identity,
manifest digest, resolver version, and source snapshot digest. It excludes the
local checkout path.

#+begin_src typst
$ K_s = H(
  D.namespace,
  D.uri,
  D.revision,
  D.manifest_digest,
  resolver.version,
  source.digest,
) $
#+end_src

For one \(K_s\), at most one active materialization receipt may claim the
selected snapshot. A replay refers to the original causal receipt. A changed
revision, manifest digest, resolver version, or source digest invalidates the
active materialization and requires a new key.

* Owner boundary

| Concern | Canonical owner |
|-
| Dependency declaration identity | =gerbil.pkg= |
| Gerbil package lifecycle | =gxpkg= |
| Hermetic archive declaration and materialization | Bzlmod / Gerbil-Bazel |
| Source resolution receipt | Gerbil-Bazel |
| Source snapshot bytes and digest | Selected source repository |
| Receipt construction and validation | Gerbil-Bazel |
| Policy harness and build/test framework | GSLPH development dependency |
| ABI semantic contracts | POO Contract |
| ABI Scheme/C qualification result | POO Flow Bazel tests |

POO Contract remains the sole canonical semantic owner for the Runtime
Language ABI. This RFC governs build-input identity and provenance; it does not
make GSLPH, Bazel, or =gerbil.pkg= a semantic co-owner of the ABI.

* Required =gerbil-bazel= owner change

This section is owned by =gerbil-bazel=. GSLPH consumes the resolved snapshot
through the generated repository but does not implement
=project_dependency_sources_repository=, emit its resolution receipt, or own
its qualification fixtures.

=project_dependency_sources_repository= MUST accept a complete declared
dependency identity or an immutable manifest projection rather than only:

#+begin_example
package = "gerbil-poo"
project_library_relative_path = ".gerbil/lib"
#+end_example

It MUST:

1. enumerate candidates without silently selecting by search order;
2. compare namespace, canonical URI, and revision;
3. reject zero or multiple exact candidates;
4. reject compiled-artifact-only directories as source snapshots;
5. digest the selected source snapshot;
6. emit the resolution receipt;
7. expose the receipt and snapshot digest to Bazel analysis.

* Qualification gates

The downstream repair is complete only when all of these gates pass:

1. duplicate namespace fixtures return =ambiguous=;
2. missing source fixtures return =missing=;
3. compiled-only fixtures return =compiled-artifact-only=;
4. revision mismatch fixtures return =revision-mismatch=;
5. one exact commit-pinned checkout returns =resolved=;
6. replay produces the same materialization key and causal receipt;

Current executable receipt: the local =gerbil-bazel= owner branch passes the non-cached source-resolution suite =3/3=, including byte-identical replay receipts for two materializations of =.gerbil/pkg/clan= at deterministic fixture revision =eaf43dc92bfeeb9abeb348137a7cca449843936f=.
The fixture creates its own Git repository with fixed content, author, timestamp, and origin, so the proof does not depend on owner checkout history depth.
The isolated nested-Bazel harness executes the production failure path and passes =4/4=: =missing=, =compiled-artifact-only=, =ambiguous=, and =revision-mismatch=.
Each rejection emits =SOURCE_RESOLUTION_RECEIPT= followed by the same v1 JSON schema through Bazel's diagnostic stream; the harness asserts both the typed =outcome= and the exact human diagnostic.
This closes the executable negative-path matrix without registering intentionally failing repositories in the root module graph.
7. the three ABI 0.3 focused Bazel labels execute and pass;
8. a clean checkout reproduces the same source snapshot digest.

No =gxpkg uninstall=, hidden registry-order preference, local checkout reset,
or user-change overwrite is an acceptable qualification step.

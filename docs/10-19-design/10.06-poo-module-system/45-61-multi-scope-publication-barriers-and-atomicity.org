#+title: Multi-Scope Publication Barriers and Proven Atomicity
#+startup: overview

* Status

This RFC records the accepted semantics for publication across multiple cohort
and environment scopes.

It extends the governed-rollout model without changing the immutability of
generations or the versioned active-head contract.

* Central distinction

A publication barrier proves that a proposed publication is ready to begin.

A publication barrier does not, by itself, prove that multiple active heads can
be committed atomically.

Multi-head atomicity is a capability proven and supplied by a runtime adapter.
It cannot be created by a pure POO policy declaration.

* Typst formalization: readiness barriers and atomic head-set transitions

A publication barrier is pure readiness evidence.  It proves that every scope
named by the barrier satisfies its declared readiness predicate, but it does
not grant a shared commit boundary.  Atomicity is a separate live capability
owned by the runtime adapter.

#+begin_src typst
#let barrier(id, scopes, ready) = (
  id: id,
  scopes: scopes,
  ready: ready,
)

#let head-set(entries) = (
  entries: entries,
)

$ B = (barrier-id, {scope_1, ..., scope_n}, ready) $
$ Ready(B) := forall scope in B.scopes: B.ready(scope) $

$ Ready(B) not=> Atomic(B.scopes) $
$ IndependentCommits(scopes) not=> Atomic(scopes) $
$ Ordered(scopes) not=> Atomic(scopes) $
$ SequentialWriteThenCompensate(scopes) not=> Atomic(scopes) $
#+end_src

Coupled scopes require an adapter witness for one transactional comparison and
transition of the complete head set.  If that witness is unavailable, an
atomicity-requiring policy has no admitted fallback.

#+begin_src typst
$ W = (witness-id, adapter-protocol-id, H_before, H_after, atomic-relation) $
$ RuntimeAtomicityWitness(W)
  := W.atomic-relation(H_before, H_after) $

$ CoupledAdmission(B, W)
  => Ready(B) and RuntimeAtomicityWitness(W) $

$ forall entry in H_after:
    exists commit: ConditionalHeadCommit(commit)
    and ProjectAfter(commit) = entry $

$ RequiresAtomicity(policy) and not exists W: RuntimeAtomicityWitness(W)
  => FailClosed(policy) $

$ Authority(PublicationBarrier) = false $
$ Authority(RuntimeAtomicityWitness) = true $
#+end_src

** Proof obligations

- [X] =barrierEstablishesReadiness=: the barrier carries readiness witnesses
  for every declared scope.
- [X] =barrierDoesNotEstablishAtomicity=: readiness evidence does not create a
  shared commit boundary.
- [X] =independentCommitsDoNotEstablishAtomicity=: independent scope progress
  is not a multi-head transaction.
- [X] =orderingDoesNotEstablishAtomicity=: causal ordering does not imply
  atomic visibility.
- [X] =compensationDoesNotEstablishAtomicity=: sequential writes followed by
  reverse writes are not atomic rollback.
- [X] =runtimeWitnessEstablishesAtomicity=: only the runtime adapter witness
  establishes multi-head atomicity in this proof slice.
- [X] =barrierAloneFailsClosedForCoupledPolicy=: an atomicity-requiring policy
  rejects barrier-only evidence.
- [X] =coupledAdmissionRequiresRuntimeAtomicityWitness=: every admitted coupled
  transition carries its runtime atomicity witness.
- [X] =atomicHeadSetProjectionComesFromConditionalCommits=: every after-entry
  in the atomic head set is projected from an RFC 45-59 conditional
  active-head commit witness.

* POO-native relation model

Relationships among publication scopes are ordinary higher-order POO objects.
They are extended through native prototype composition and object operations
provided by the canonical =gerbil-poo= dependency.

The model must not expose an enum-like =#:atomic= or =#:ordered= token DSL as
the public extension interface.

A relation object may project:

- scope independence relations;
- transition dependency relations;
- required commit capabilities;
- partial-state admissibility predicates;
- convergence policy;
- evidence requirements;
- receipt disclosure policy.

Ordinary users consume already composed policies through the constrained user
interface. Advanced extension uses POO objects as the only semantic interface.

* Independent scopes

Independent scopes may progress without a shared commit boundary.

Each scope:

- observes its own active-head version;
- receives its own proposal and authorization;
- commits through its own head transition;
- emits its own success, failure, or unknown-outcome receipt.

A failure in one independent scope does not erase or reverse a successful
transition in another scope.

The =research= scope is independent from production rollout by default. A
dependency must be stated explicitly by a POO relation object before research
evidence or publication can block production.

* Ordered scopes

Ordered scopes express causal dependencies rather than atomicity.

The default canary-to-stable relation is:

1. publish the candidate generation to the canary scope;
2. observe the resulting canary execution;
3. admit the required canary evidence closure;
4. produce a stable-scope promotion proposal;
5. authorize and publish the stable transition.

The stable proposal must reference the completed canary head transition and
its admitted evidence closure.

Publishing canary and stable simultaneously would remove the evidence boundary
that gives canary rollout its meaning. Therefore =canary -> stable= is ordered
by default and is not an atomic head-set transition.

* Coupled scopes

Scopes are coupled only when the domain invariant rejects every intermediate
combination of their active heads.

A coupled relation declares the required transactional capability. It does not
claim that the capability exists.

Before publication, the live runtime must prove that its adapter supports a
transactional multi-head compare-and-swap over the complete coupled scope set.

If the proof is admitted, the runtime may produce one atomic head-set
transition and one atomic publication receipt.

If the proof is unavailable:

- a policy that requires atomicity fails closed before the first head update;
- a policy that admits partial completion may use ordered commits and explicit
  convergence.

Sequential writes followed by reverse writes are not an atomic transaction.

* Partial completion

Partial completion is a first-class result when admitted by policy.

A =PartialPublicationReceipt= records, for every intended scope:

- target generation identity;
- observed head version;
- intended transition identity;
- commit attempt identity;
- =success=, =failure=, or =unknown= outcome;
- resulting head version when known;
- adapter and capability proof identities;
- reconciliation requirement.

An unknown scope outcome is not equivalent to failure. The runtime must
reconcile that scope against its authoritative external head before proposing
further transitions.

Partial completion must never be hidden behind a single generic rollout
failure.

* Convergence

Convergence is a new governed operation after an admitted partial result.

It requires:

- a fresh observation of every affected active head;
- the immutable partial publication receipt;
- a pure convergence proposal;
- newly admitted authority;
- version-checked head-update intents.

Convergence may complete the intended publication or select a different
generation. It is not hidden automatic rollback and it must not reuse stale
head-update intents.

* Cohort assignment expansion

Expanding cohort assignment can route new subjects to a target scope.
Therefore assignment expansion must depend explicitly on publication of the
corresponding target head.

The safe default order is:

1. materialize and admit the target generation;
2. publish the target cohort head;
3. observe the successful head-transition receipt;
4. authorize the assignment expansion.

If head publication and assignment expansion must be indistinguishable to
observers, the runtime must provide a transactional capability covering both
resources. Otherwise the policy must use the safe ordered relation.

* Atomicity proof boundary

The adapter capability proof must identify:

- the complete resource and scope set;
- the transactional store or authority;
- the observed version vector;
- the compare-and-swap semantics;
- the commit boundary;
- the fencing and lease assumptions;
- the receipt returned after commit;
- the reconciliation interface for unknown outcomes.

An adapter name or configuration flag is not an atomicity proof.

* Failure taxonomy

The implementation must distinguish at least:

- incomplete barrier evidence;
- unsatisfied transition dependency;
- missing multi-head transaction capability;
- incompatible resource scopes;
- stale version vector;
- compare-and-swap conflict;
- partial ordered commit;
- unknown per-scope outcome;
- reconciliation disagreement;
- unauthorized convergence;
- atomic receipt publication failure.

* Required invariants

1. Barrier admission and commit atomicity remain separate proofs.
2. Independent scopes do not acquire hidden coupling.
3. Ordered scopes preserve their evidence-producing causal boundary.
4. Canary-to-stable promotion is ordered by default.
5. Research is independent from production by default.
6. Coupled scopes require an adapter-proven transactional capability.
7. Missing required atomicity fails before the first head update.
8. Partial completion records every scope outcome independently.
9. Unknown outcomes require reconciliation.
10. Convergence requires fresh evidence and new authority.
11. Assignment expansion cannot precede publication of its target head.
12. Public semantic extension remains POO-native.

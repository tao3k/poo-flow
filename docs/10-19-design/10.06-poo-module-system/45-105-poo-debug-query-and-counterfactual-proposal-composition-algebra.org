#+title: POO Debug Query and Counterfactual Proposal Composition Algebra

* Status

Accepted architecture RFC.

This document fixes the POO algebra for debugging queries and counterfactual
proposals. It does not authorize implementation work.

* Scope

This RFC defines:

- typed inspection, explanation, and diff query objects;
- counterfactual simulation proposal objects;
- query and proposal composition;
- bounded traversal and pure predicate contracts;
- completeness, redaction, capability, and budget semantics;
- proposal preconditions and conflict behavior;
- macro governance and evidence requirements.

This RFC does not define:

- raw field-name lists;
- alist or record query schemas;
- raw predicate lambdas as the ordinary interface;
- keyword query clauses;
- a generic patch language;
- a commit or apply operation;
- authority embedded in a proposal;
- unlimited traversal;
- compatibility, migration, or deprecation behavior;
- implementation edits.

* Evidence state

Parser-owned discovery of the current Module interface is blocked by:

#+begin_example
provider owner-search-stdin failed: status=exit status: 2 stderr=
#+end_example

The route emits no verified current owner for:

- query objects;
- proposal objects;
- filters or predicates;
- traversal policy;
- completeness;
- budgets;
- redaction;
- simulation preconditions.

Current use of raw lists, alists, lambdas, keywords, or hidden authority remains
=MISSING= rather than inferred.

This RFC defines the target POO-native surface without preserving unverified
current representations.

* Central decision

Queries and proposals are separate POO object algebras.

#+begin_example
Query
  = bounded read projection

Proposal
  = counterfactual semantic change with explicit preconditions
#+end_example

A Query cannot propose state change.

A Proposal cannot grant authority, publish state, or apply itself.

Both remain immutable, identity-bearing, composable native POO values.

* Query families

The public query families are:

- InspectionQuery;
- ExplanationQuestion;
- DiffQuery.

Each family has:

- a domain prototype;
- canonical ordinary query values;
- an identity query value for compatible composition;
- POO projection facets;
- traversal policy;
- requested budget;
- completeness requirement;
- requested evidence classes;
- redaction-visible result contract;
- declared observation dependencies.

The names identify semantic families. Exact Scheme type and constructor names
remain subject to verified owner design.

* InspectionQuery

An InspectionQuery identifies:

- target snapshot prototype;
- requested inspection facets;
- object and relation domains;
- traversal boundary;
- completeness requirement;
- requested evidence classes;
- result evidence prototype.

The ordinary =(inspect snapshot)= function uses the canonical summary
InspectionQuery.

An advanced query is passed explicitly:

#+begin_src scheme
(inspect snapshot query)
#+end_src

* ExplanationQuestion

An ExplanationQuestion identifies:

- target judgment or condition prototype;
- causal subject identity;
- requested explanation dimensions;
- maximum causal traversal;
- required evidence classes;
- completeness expectation;
- explanation graph prototype.

The ordinary =(explain judgment)= function uses the canonical current-judgment
question.

An advanced question is passed explicitly:

#+begin_src scheme
(explain judgment question)
#+end_src

* DiffQuery

A DiffQuery identifies:

- compatible input snapshot prototypes;
- semantic comparison dimensions;
- identity matching policy;
- visibility and completeness requirements;
- ignored presentation-only dimensions;
- result diff prototype.

The ordinary =(diff before after)= function uses the canonical complete-visible
DiffQuery.

An advanced diff query is passed explicitly:

#+begin_src scheme
(diff before after query)
#+end_src

* Query facets

A query facet is a POO object that names one semantic projection.

A facet identifies:

- facet identity;
- owning query domain;
- input prototype requirements;
- result projection prototype;
- observation dependencies;
- traversal contribution;
- budget contribution;
- evidence and redaction requirements.

Field strings and keywords are not facet identities.

The same facet identity is idempotent under query composition.

* Query predicates

A QueryPredicate is a named POO object with:

- predicate identity;
- admitted input prototypes;
- a pure evaluation function;
- declared observation dependencies;
- maximum resource demand;
- failure evidence contract;
- authority neutrality.

A raw =(lambda (value) ...)= is not the ordinary query interface.

Advanced authors may place a named pure function behind a QueryPredicate
prototype after its dependencies and resource bounds are explicit.

The predicate cannot:

- read mutable global state;
- perform runtime effects;
- inspect hidden authority;
- mutate the queried snapshot;
- return an untyped truth value without evidence when the contract requires an
  explanation.

* TraversalPolicy

TraversalPolicy is a POO object that bounds:

- maximum nodes;
- maximum edges;
- maximum depth;
- allowed edge and responsibility kinds;
- ancestry and delegation traversal;
- cycle revisits;
- evaluation steps;
- wall-clock observation budget when admitted;
- result volume.

There is no unlimited numeric or symbolic sentinel.

A requested traversal policy is intersected with DebugEvaluationContext limits.
It cannot widen the admitted context.

* Completeness

CompletenessRequirement is a POO object.

It may request:

- complete within the admitted semantic domain;
- bounded complete for named facets;
- partial with explicit omitted dimensions;
- first conflict or first causal path;
- summary with declared aggregation.

A result always records:

- satisfied completeness level;
- omitted dimensions;
- budget or redaction causes;
- unresolved dependencies;
- whether retry may improve completeness.

Partial evidence never presents itself as complete.

* Redaction semantics

A Query may request visibility but cannot set the effective redaction policy.

Effective visibility is derived from:

#+begin_example
query request
  intersect
DebugEvaluationContext capability and redaction policy
  -> effective visible projection
#+end_example

Query composition cannot weaken redaction.

A facet whose evidence is redacted remains represented by a redaction evidence
object when policy permits disclosure of its existence.

* Query budget semantics

Each query contributes a requested budget object.

Compatible composition accumulates resource demand. Admission clamps or rejects
the demand against DebugEvaluationContext.

No query can:

- reset consumed budget;
- borrow commit authority;
- hide traversal cost;
- make a recursive traversal unbounded;
- split itself to evade aggregate accounting.

Budget receipts count descendants, retries, predicates, explanation edges,
redaction projections, and result aggregation.

* Query composition

Compatible query composition is a pure operation:

#+begin_example
query + query -> query or typed query conflict
#+end_example

It obeys:

- domain closure;
- semantic associativity for compatible facets;
- permutation independence for independent facets;
- idempotence by facet identity;
- provenance preservation;
- budget accumulation;
- redaction non-weakening;
- completeness honesty.

Composition returns a new query identity when semantic content changes.

* Query conflict

A typed QueryConflict arises when:

- query families differ;
- target snapshot prototypes are incompatible;
- result prototypes are incompatible;
- completeness requirements contradict;
- traversal policies cannot be reconciled;
- predicates require unavailable evidence;
- one facet attempts to weaken redaction;
- aggregate budget cannot be represented honestly.

A conflict is a POO evidence object. It is not resolved by source order or a
generic override token.

* Counterfactual proposal families

Simulation proposal families include:

- DomainAdmissibilityProposal;
- ControlPolicyProposal;
- ContributionProposal;
- WithdrawalProposal;
- ModuleRevisionProposal;
- EvidenceSupplementProposal;
- CapabilityRequestProposal;
- BudgetObservationProposal.

Every proposal remains counterfactual until ordinary admission publishes a
separate revision or demand.

* Proposal contract

A proposal identifies:

- proposal identity and family;
- base snapshot and revision identities;
- semantic target identities;
- proposed POO values;
- explicit preconditions;
- required capability kinds;
- requested simulation budget;
- predicted affected relations and closures;
- expected evidence;
- source and provenance;
- expiration or freshness boundary.

A proposal contains no capability grant and no commit token.

* Proposal preconditions

Preconditions are typed POO objects.

They may require:

- exact base Module or relation revision;
- contribution presence or absence;
- native ancestry snapshot identity;
- conflict identity;
- policy and authority context identity;
- evidence identity and freshness;
- cache or observation boundary;
- resource budget.

Simulation evaluates preconditions against the supplied immutable snapshot.

Failed preconditions return a typed proposal condition. They do not trigger
best-effort mutation.

* Proposal composition

Compatible proposals may form a ProposalBundle POO object.

Composition is allowed when:

- base snapshots and revisions are compatible;
- targets are independent or governed by an explicit domain composition law;
- preconditions can hold together;
- capability requests remain requests;
- aggregate budget is representable;
- effect and publication prohibitions remain intact.

Independent compatible proposals are permutation-independent.

Repeated proposal identity is idempotent.

* Proposal conflict

A ProposalConflict arises when:

- base revisions differ incompatibly;
- two proposals assign incompatible values to one semantic target;
- a withdrawal and contribution conflict on one identity;
- preconditions cannot hold together;
- aggregate authority requirements conflict;
- a proposal attempts runtime or publication effects;
- one proposal assumes the result of another without explicit dependency.

The conflict retains every proposal, precondition, target, and provenance
identity.

* Explicit proposal dependencies

One proposal may depend on another only through a typed dependency edge.

The edge identifies:

- predecessor and successor proposal identities;
- required result evidence;
- failure propagation rule;
- aggregate budget contribution;
- cycle policy.

Proposal dependency cycles produce a typed condition and use bounded
fixed-point observability. They are not executed as an implicit sequence.

* Query and proposal separation

A Proposal may reference a Query identity to state required evidence.

A Query may inspect a Proposal as an immutable POO value.

Neither relation permits:

- Query to apply Proposal;
- Proposal to redefine Query redaction;
- Query result to become authority;
- Proposal to capture evaluator context;
- circular hidden execution.

#+begin_src mermaid
flowchart LR
  QueryProto["typed Query prototype"] -->|"extends through POO facets"| Query["bounded Query object"]
  Query -->|"constructs read-only demand"| DebugDemand["DebugDemand"]
  ProposalProto["typed Proposal prototype"] -->|"extends through preconditions"| Proposal["counterfactual Proposal object"]
  Proposal -->|"constructs simulation demand"| DebugDemand
  Context["DebugEvaluationContext"] -->|"intersects scope, budget, and redaction"| Evaluate["pure evaluator"]
  DebugDemand -->|"contains no authority"| Evaluate
  Evaluate -->|"returns read evidence"| QueryResult["POO query result"]
  Evaluate -->|"returns counterfactual evidence"| Simulation["POO simulation result"]
  Simulation -.->|"cannot publish or apply"| Proposal
  QueryResult -.->|"cannot grant authority"| Context
#+end_src

The dotted edges express prohibited semantic feedback.

* Canonical query values

Canonical ordinary queries are immutable published POO values.

They use the sharing rules for proven immutable typed values:

- stable prototype and value identity;
- no session-specific state;
- no capability;
- no mutable cache;
- explicit result prototype;
- bounded traversal and result volume.

If immutability cannot be proven, only the canonical prototype is shared and a
fresh query instance is constructed.

* Advanced extension

Advanced users extend Query and Proposal objects through:

- native POO prototype composition;
- object extension;
- named pure functional combinators;
- typed predicates;
- typed traversal and completeness policies;
- typed preconditions and dependency edges.

No public macro or alternate language is required.

* Evaluation sequence

#+begin_src mermaid
sequenceDiagram
  participant User as "user"
  participant QP as "Query or Proposal object"
  participant Demand as "DebugDemand"
  participant Context as "DebugEvaluationContext"
  participant Eval as "pure evaluator"
  participant Result as "POO evidence result"

  User->>QP: "constructs or extends native POO value"
  QP->>Demand: "contributes identity, bounds, and preconditions"
  Demand->>Context: "requests scoped evaluation"
  Context->>Eval: "supplies effective visibility and budgets"
  Eval->>Eval: "checks query compatibility or proposal preconditions"
  Eval-->>Result: "returns evidence, conflict, or typed condition"
#+end_src

No evaluation step publishes semantic state.

* Macro governance

Functions and native POO objects remain the default abstractions.

A bounded internal macro may generate repeated Query facet or Proposal
precondition families only when it:

- expands to ordinary POO-native objects and pure functions;
- assigns stable family and source identity;
- owns no evaluation, redaction, authority, or commit semantics;
- introduces no keyword or field-list DSL;
- preserves inspectable expansion evidence.

No public query, filter, proposal, patch, or simulation macro is introduced.

* Semantic laws

** Algebra separation law

Queries project read evidence; Proposals describe counterfactual change.

** Native-value law

Every Query, Predicate, TraversalPolicy, CompletenessRequirement, Proposal, and
Precondition is a native POO object.

** Query boundedness law

Every query declares traversal, result, and evaluation bounds.

** Predicate purity law

Query predicates are pure, named, dependency-declared, and bounded.

** Redaction non-weakening law

Query construction and composition cannot weaken admitted redaction.

** Completeness honesty law

Every result declares achieved and omitted completeness.

** Proposal non-authority law

A Proposal contains no capability grant or commit authority.

** Precondition law

Simulation checks every proposal precondition against the explicit base
snapshot.

** Composition determinism law

Equivalent compatible inputs produce equivalent Query or ProposalBundle
objects.

** Non-publication law

Query and Proposal evaluation publishes no semantic revision or runtime effect.

** Macro-minimality law

The public algebra requires no macro.

** Fail-closed law

Incompatible queries, proposals, bounds, preconditions, or scopes produce typed
conflicts or conditions.

* Evidence projection

A Query receipt identifies:

- query family and identity;
- facet and predicate identities;
- traversal and completeness policies;
- requested budget;
- requested evidence classes;
- observation dependencies;
- result prototype;
- source provenance.

A Proposal receipt identifies:

- proposal family and identity;
- base snapshot and revision;
- targets and proposed values;
- every precondition;
- required capability kinds;
- dependency edges;
- requested budget;
- non-authority and non-publication evidence.

An evaluation receipt additionally identifies:

- effective context scope;
- effective redaction;
- admitted budget;
- achieved completeness;
- failed predicates or preconditions;
- conflicts and omitted dimensions;
- result identity.

* Failure behavior

Query construction or composition fails closed when:

- family or domain identity is absent;
- a raw field list, alist, keyword clause, or lambda is supplied;
- target or result prototypes are incompatible;
- traversal is unbounded;
- predicate dependencies are undeclared;
- redaction would be weakened;
- completeness would be misstated;
- budget accounting is incomplete.

Proposal construction or composition fails closed when:

- base snapshot or revision is absent;
- target identity is absent;
- preconditions are incomplete or incompatible;
- a capability grant or commit token is embedded;
- runtime effects are requested;
- dependency cycles lack bounded observation;
- proposal provenance is incomplete.

Every failure identifies the family, object, conflicting inputs, missing
evidence, and permitted repair.

* Rejected alternatives

The following alternatives are rejected:

- field-name lists as queries;
- alist query records;
- keyword clauses for traversal or completeness;
- raw predicate lambdas as public filters;
- an unlimited traversal marker;
- query-controlled redaction;
- implicit partial results presented as complete;
- proposals as generic patches;
- proposals carrying granted capabilities;
- automatic proposal application after simulation;
- source order as proposal conflict resolution;
- hidden proposal dependencies;
- public query or proposal macros;
- compatibility wrappers for an unverified current query surface.

* Consequences

Advanced debugging remains fully POO-native without turning queries into a
second language.

Traversal, completeness, redaction, budgets, preconditions, and proposal
dependencies become inspectable semantic objects.

Queries remain read-only and Proposals remain counterfactual, so debugging and
simulation cannot silently become mutation or authority interfaces.

#+title: Profile Objects and Prototype Extensions: Native gerbil-poo Correspondence
#+author: POO Flow
#+language: en

* Status

This RFC records an approved semantic boundary.

- [X] A normal Profile is an immutable POO object.
- [X] A higher-order Profile extension is a native prototype.
- [X] A composition root performs one explicit prototype instantiation.
- [X] Native =gerbil-poo= operations remain the semantic foundation.
- [X] Operand admission uses native value domains rather than tags, wrappers,
  or registries.
- [X] Admission separates shape recognition from semantic validation.
- [X] Object operands are lifted in place without changing declared order.
- [X] Object-to-prototype correspondence adopts the upstream POOF construction
  through the pinned =gerbil-poo= implementation, as governed by
  [[file:45-85-poof-proof-adoption-and-poo-flow-correspondence-obligations.org][45-85]].
- [ ] Verify the exact operand-admission predicates against executable
  =gerbil-poo= examples before freezing a public helper name.
- [ ] Add implementation conformance tests only after the public contract is
  approved.

This document specifies architecture.  It does not authorize implementation.

* Formal correspondence surface

The local proof does not reconstruct the POOF theorem or define another
object-to-prototype formula.  It proves only the POO Flow correspondence
obligations that surround the construction adopted from POOF through the pinned
=gerbil-poo= dependency.

Here =A_s= is shape admission.  Full admission =A= additionally requires

* Central decision

POO Flow SHALL preserve both native representation layers provided by
=gerbil-poo=:

1. an ordinary Profile is a POO object whose slots carry identity, imports,
   capabilities, requirements, contributions, and policies; and
2. a higher-order Profile extension is a prototype that transforms a base
   object through native fixed-point composition.

The two representations are complementary.  POO Flow MUST NOT reduce all
Profile composition to =.mix=, and it MUST NOT replace native prototype
instantiation with a local fixed-point evaluator.

The composition root is the only boundary that instantiates the composed
prototype into the immutable root object admitted by one generation.

* Composition roles

** Profile object

A normal Profile operand is already a first-class POO value.  Its domain
meaning is carried by slots rather than by a raw alist, record DSL, package
manifest, runtime token, or hidden registry entry.

An object operand does not need another wrapper merely to participate in
=compose profiles=.

** Profile extension

A higher-order Profile extension is a native prototype.  It may express
recursive references and =self=/=super= computation without embedding host
=if=, =cond=, or =case= dispatch in the user composition.

The ordinary public path MUST use named POO-native or functional helpers.
Raw =(lambda (self super) ...)= remains an advanced implementation escape
hatch, not the normal user interface.

** Composition strategy

=profiles= is a first-class POO composition-strategy object.  It owns:

- operand admission;
- preservation of declared operand order;
- projection of object operands into native object composition;
- projection of prototype operands into native prototype composition;
- root instantiation; and
- production of the immutable composition result.

It does not own package discovery, filesystem search, module loading, provider
registration, or a second object runtime.

*** Native value-domain admission

=profiles= admits operands through the native Gerbil/POO value boundary:

- a POO object is admitted as an ordinary Profile value; and
- a native prototype procedure is admitted as a higher-order Profile
  extension.

This distinction MUST NOT be represented by a =kind= slot, symbolic token,
wrapper form, package identity, global table, or hidden registry.  Admission
observes the value already supplied to =compose=.

The exact Gerbil predicates and procedure-arity checks remain an executable
verification question.  This RFC fixes the semantic distinction but does not
invent names for unverified helpers.

*** Two-stage admission

Operand admission has two stages.

The shape stage accepts only a native POO object or a value satisfying the
verified native prototype calling shape.  Any other value fails closed with an
=InvalidProfileOperand= receipt before root instantiation.

The semantic stage occurs at the single root-instantiation boundary.  The
result MUST be a POO object satisfying the admitted Profile contract.  A
callable value is not considered a valid Profile extension merely because it
passes a procedure predicate.

The failure receipt MUST identify:

- the operand position;
- the operand identity when the value exposes one;
- the observed native value category;
- the admission stage;
- the expected object or prototype contract; and
- the contract violation.

Receipt construction MUST NOT search the filesystem, package graph, module
loader, or a registry.

*** Ordered object lifting

Before native prototype composition, the strategy uses the object-to-prototype
construction established by POOF and realized by the pinned =gerbil-poo=
implementation.  The ordinary Profile object remains at its original operand
position.  A native prototype operand remains a prototype contribution at its
original position.

The resulting ordered contribution sequence may be passed to
=compose-proto*= and instantiated once at the root.  The implementation MUST
NOT batch all objects into one =.mix= before composing all extensions.

POO Flow MUST NOT invent a second lifting formula or conduct a local
=.mix=-versus-=.+= algebra.  Its remaining responsibility is to verify the
correspondence between the pinned =gerbil-poo= path and the adopted POOF
construction before freezing any POO Flow helper name.

The proof-adoption boundary and the remaining POO Flow correspondence
obligations are owned by
[[file:45-85-poof-proof-adoption-and-poo-flow-correspondence-obligations.org][45-85]].

** Composition root

The composition root is an immutable POO object produced by one explicit
instantiation boundary.  A running generation keeps that root revision.  It
does not re-resolve a lexical name, reload a module, or select a newer Profile
revision in place.

This preserves the revision and reload boundary specified by
[[file:45-83-profile-revisions-live-upgrade-and-module-reload-boundaries.org][45-83]].

* Ordered composition

=compose profiles= MUST preserve the declared operand order.

An implementation MUST NOT first group every object operand and every
prototype operand if that regrouping changes observable =self=, =super=, slot
precedence, requirement resolution, or contribution order.

Any normalization is valid only when it carries a proof or executable
conformance result that it is observationally equivalent to the declared
order.

Each operand is therefore normalized in place:

| Supplied value | In-place contribution |
| POO Profile object | Pure object-to-prototype lifting |
| Native Profile extension prototype | The same prototype value |

This normalization creates one ordered prototype sequence.  It does not create
an object batch followed by an extension batch.

The following remains the admitted minimal user surface:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    base-profile
    wendao-episteme
    production-profile))
#+end_src

=user-composition= is the thin hygienic module-definition macro.  =compose= is
an ordinary pure function.  =profiles= is the strategy object.  None of these
forms duplicates the role of another.

The exact surface syntax for inserting a higher-order extension remains
unfrozen until its operand admission is verified against the native
=gerbil-poo= API.

* Two different kinds of cycles

** Prototype recursion

Prototype recursion belongs to fixed-point semantics.  It can be valid, but a
particular evaluation may diverge, exceed a budget, or repeatedly demand an
unproductive slot.

POO Flow observability may attach evaluation paths, budgets, suspension
receipts, resumptions, and causal evidence to this execution.  These facilities
observe and govern native prototype evaluation; they do not replace
=instantiate-proto=.

** Inheritance cycles

The object supers relation is a precedence graph.  A cycle in that graph is
structurally invalid and native =gerbil-poo= rejects it while computing C3
precedence.

POO Flow MUST NOT convert this structural error into a resumable fixed-point
request.  The error must retain the offending object path and fail before the
root is admitted.

* Priority is not inheritance precedence

=gerbil-poo= does not provide a global numeric Profile rank.

Numeric priority remains a slot-local input to a
=RequirementResolutionPolicy=.  It MUST NOT:

- reorder the native C3 precedence graph;
- become a global Profile strength;
- select packages or modules;
- override declared operand order outside the owning slot policy; or
- hide an unresolved contribution conflict.

* Macro governance

The public macro layer remains deliberately small.

- =user-composition= may define the composition root and preserve lexical
  context.
- Native =.o= and =.def= remain the advanced object construction surface.
- Repeated internal object families may use bounded hygienic metaprogramming
  only when expansion produces ordinary POO-native or functional code.
- A macro MUST NOT implement a second evaluator, object model, registry,
  resolution engine, or runtime dispatch language.

The detailed macro constraints remain owned by
[[file:44-current-project-programming-style.org][44-current-project-programming-style]].

* Prohibited designs

The following designs are outside the approved architecture:

- reimplementing =instantiate-proto= or =compose-proto*= inside POO Flow;
- treating =.mix= as the complete meaning of =compose profiles=;
- introducing a local fixed-point object, evaluator, or registry;
- tagging operands with a =kind= slot or symbolic runtime token;
- wrapping every operand only to distinguish object from prototype;
- accepting a callable value as semantically valid without root-contract
  validation;
- batching all object operands before all prototype operands;
- representing Profiles as raw alists, records, or patch programs;
- using host conditionals as the ordinary Profile extension mechanism;
- conflating recursive prototype evaluation with an inheritance cycle;
- applying requirement priority to native inheritance precedence;
- instantiating a new root implicitly during module reload; or
- exposing a redundant macro layer over native POO operations.

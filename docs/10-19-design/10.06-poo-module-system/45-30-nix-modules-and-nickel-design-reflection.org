#+title: Nix Modules and Nickel Design Reflection
#+status: Accepted design reference
#+language: en

* Decision

Nix Modules and Nickel are important design references for the POO module
system, but neither one defines its public language or its implementation
model.

The reference path is:

1. learn from the power and the failure modes of Nix Modules;
2. identify which of those failure modes Nickel has materially improved;
3. retain the unresolved problems as explicit design pressure;
4. reconstruct the useful ideas with Gerbil Scheme and native
   =gerbil-poo= prototypes.

Terms such as =Nickel-style=, =Nix-style=, Nickel records, Nix option
declarations, and Nix priority numbers MUST NOT become POO public API names.
The references explain design choices; they do not create compatibility
layers.

* Design lineage

  F -->|"simplifies merge through symmetry, metadata, contracts, recursive override"| K["Nickel"]
  K -->|"still leaves custom merge, incremental evaluation, caching and performance open"| O["Unresolved configuration-language problems"]
  P -->|"reconstructed as native prototypes and open recursion"| G["Gerbil Scheme plus gerbil-poo"]
  K -->|"contributes design principles without syntax or namespace inheritance"| G
  O -->|"drives observability, recovery and bounded evaluation requirements"| G
  G -->|"adds identity, capability, authority, receipts and continuable recovery"| M["POO module semantics"]

The arrows intentionally describe the status of each transfer.  This is not a
language genealogy in which POO becomes a Nickel or Nix dialect.

* What Nix Modules demonstrates

Nix Modules establishes several important capabilities:

- a configuration may be computed as a lazy global fixed point;
- modules may depend on values contributed by other modules;
- submodules may be nested recursively and behave as module systems of their
  own;
- option types may own validation and merge behavior;
- definitions may carry override and ordering information.

These capabilities show that a module is more than a package declaration or a
static configuration record.  A module participates in a recursively composed
semantic object.

* Problems exposed by Nix Modules

The NixOS manual also makes several costs visible:

- a direct conditional over the value being constructed may cause infinite
  recursion, requiring =mkIf= to push the condition into definitions;
- values needed before the module fixed point, especially imports, require a
  separate =specialArgs= path;
- override priority and merge ordering are separate numeric systems with
  different meanings;
- option declaration, option definition, type-owned merge, internal definition
  normalization, and free-form attributes create several semantic layers;
- free-form attributes cannot freely depend on sibling attributes without
  encountering recursion;
- powerful submodule behavior inherits the surrounding option machinery and
  its evaluation difficulties.

These are not reasons to discard fixed points or submodules.  They are reasons
to make dependency, demand, recursion, observation, failure and recovery
first-class semantic objects.

* What Nickel materially improves

Nickel should be treated as a serious reflection on the Nix lineage rather
than as a source of isolated syntax ideas.

** Symmetric merge

Nickel merge is symmetric and commutative.  Operand position does not silently
mean stronger or weaker.  When contributions differ, explicit metadata carries
the distinction.

This is a stronger basis for independent module contribution than an implicit
left-wins or right-wins convention.

** One explicit merge-priority order

Nickel gives ordinary values priority =0=, orders numeric priorities by their
numeric value, places =default= below every numeric priority, and places
=force= above them.  Higher priority wins.  Equal priorities recursively merge
or produce a conflict.

The POO priority contract in
[[file:45-29-poo-merge-priority-and-recursive-override.org][POO Merge Priority and Recursive Override]]
adopts this clarity while rebuilding priority as native POO metadata with
authority and evidence requirements.

** Recursive override

Nickel combines recursive records and priorities so that an outer contribution
can override a nested value while the rest of the recursively computed
structure remains available.

For POO this is not record patching.  It is evidence that recursive override
belongs inside prototype open recursion and slot computation.

** Contracts survive selection

Contracts attached as field metadata accumulate through merge and continue to
constrain the final selected value, including a value that wins by priority.
Contract checking is delayed until the value is demanded, allowing an
incomplete intermediate contribution to be completed by later merges.

This directly informs
[[file:45-28-poo-native-slot-contracts-and-algebraic-laws.org][POO-Native Slot Contracts and Algebraic Laws]]:
discarded values do not imply discarded semantic obligations.

** Modular configuration without operand-order patch semantics

Nickel shows how reusable configuration fragments, metadata, contracts and
recursive merge can form a modular configuration without making operand order
the ordinary conflict-resolution mechanism.

* What Nickel does not settle

Nickel improves important parts of the Nix design space, but the RFC MUST NOT
claim that it solves every Nix Modules problem.

- Nickel describes itself as a generic configuration language whose result is
  normally exported as static data for another system.
- Custom merge functions remain future work in the current manual.
- Incremental evaluation, caching and further performance improvements remain
  roadmap items.
- Recursive computation may still fail to terminate; symmetric merge and
  contracts do not themselves provide convergence budgets or cycle witnesses.
- Runtime contracts improve error attribution but do not by themselves provide
  first-class continuations, continuable exceptions or authorized resumptions.
- Nickel records do not supply the POO module identities, prototype lineage,
  capability ownership, authority attenuation, generation tracking and causal
  receipts required by this architecture.

Nickel is therefore an important completed design reference for some merge and
contract questions, and an explicit source of open questions for evaluation
and tooling.

* Ownership of the remaining gap

The distinction above is intentional and complete only when the unresolved
items have an explicit owner.  They are not merely limitations recorded
against Nickel:

| Unresolved reference problem | Native substrate | POO Flow responsibility |
|------------------------------+------------------+-------------------------|
| Infinite recursion and fixed-point debugging | =gerbil-poo= prototypes, slots and open recursion | Observable demand graph, cycle witness, convergence budget, continuable exception and authorized resumption |
| Incremental evaluation | POO identity, lineage and slot demand | Contribution generations, dependency footprints, invalidation and bounded re-evaluation |
| Caching | Stable POO identity and pure slot computation | Evidence-bearing reuse decisions, cache invalidation receipts and replay equivalence |
| Performance | Native POO composition without a parallel evaluator | Demand budgets, incremental work accounting, hot-path evidence and explicit realization boundaries |

=gerbil-poo= remains the sole POO implementation and the native semantic
substrate.  POO Flow MUST NOT reimplement its object model, prototype
composition, slot evaluation or open recursion.  POO Flow owns the higher
module-system semantics that make those native operations observable,
recoverable, incremental and evidence-bearing.

#+begin_src mermaid
flowchart LR
  GP["gerbil-poo"] -->|"provides native objects, prototypes, slots and open recursion"| PF["POO Flow module semantics"]
  NX["Nix Modules experience"] -->|"identifies fixed-point recursion and module-evaluation failure modes"| PF
  NK["Nickel improvements"] -->|"supplies merge, priority, recursive override and contract lessons"| PF
  NK -->|"leaves incremental evaluation, caching and performance as open roadmap work"| PG["Explicit POO Flow gap"]
  NX -->|"leaves recursion diagnosis dependent on evaluation structure"| PG
  GP -->|"makes the gap solvable without inventing a second evaluator"| PG
  PG -->|"implemented as demand observation, generations, budgets, receipts and resumptions"| PF
#+end_src

Thus POO Flow does not wait for Nickel to provide these capabilities and does
not copy a future Nickel implementation.  It closes the gap in the Gerbil POO
semantic domain, where first-class continuations, continuable exceptions and
native prototype identities can participate directly.

* POO reconstruction

The POO module system carries the useful design pressure forward through its
own semantic core:

| Reference insight | POO reconstruction |
|-------------------+--------------------|
| Lazy global fixed point | Native POO open recursion with demand-scoped observation |
| Nested submodule | Higher-order POO object with imports, identity and capability |
| Symmetric independent contribution | Full contribution closure before contract-specific selection |
| Merge priority metadata | POO priority object with scoped authority and retained evidence |
| Equal-priority recursive merge | Slot-contract algebra over native prototype values |
| Accumulated lazy contracts | POO contract objects retained across selection and checked at demand |
| Infinite-recursion failure | Cycle witness, convergence budget and causally identified demand path |
| Evaluation failure | Continuable exception with an authorized, generation-bound resumption |
| Static configuration result | Inspectable module object plus explicit realization boundary |

The reconstruction MUST use native =gerbil-poo= operations and Gerbil macro
expansion.  It MUST NOT introduce a parallel evaluator, record DSL, patch
language, priority registry or public raw compute-hook convention.

* Fixed-point debugging is the main step beyond both references

#+begin_src mermaid
flowchart TD
  C["POO contribution closure"] -->|"discovers every candidate before selection"| S["Slot-contract merge"]
  S -->|"applies priority while retaining suppressed evidence and contracts"| V["Provisional fixed-point value"]
  V -->|"demand records slot, prototype lineage, generation and budget"| D["Observable demand"]
  D -->|"returns a value and advances the fixed point"| V
  D -->|"detects repeated causal demand"| W["Cycle witness"]
  D -->|"exhausts bounded observation"| B["Budget exception"]
  W -->|"offers only authorized generation-bound choices"| R["Continuable recovery"]
  B -->|"offers retry, refine, suspend or abort according to policy"| R
  R -->|"re-enters with a new contribution generation and receipt"| C
#+end_src

This is not merely improved error text.  The goal is to make a problematic
fixed point observable at first demand, explain its causal path, and allow a
controlled continuation without hiding the original contribution closure.

* Adoption checklist

- [X] Treat Nix Modules as a reference for global fixed points and recursive
  submodules.
- [X] Treat Nix Modules recursion and priority complexity as design evidence,
  not behavior to reproduce.
- [X] Treat Nickel as an important design evolution of the Nix lineage.
- [X] Adopt explicit priority metadata, stronger numeric priority, equal-class
  recursive merge and retained contracts as principles.
- [X] Keep Nickel and Nix names out of the public POO namespace.
- [X] Reconstruct the adopted principles through native =gerbil-poo= objects,
  slots and open recursion.
- [X] Require POO identity, capability, authority, evidence and generation
  semantics beyond configuration-record merge.
- [X] Keep fixed-point observability and continuable recovery as first-class
  requirements.
- [ ] Validate the final native POO surface against executable algebraic,
  recursion, ambiguity and resumption scenarios before implementation begins.

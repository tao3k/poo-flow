#+title: Minimal Higher-Order Module POO Value and Responsibility-Slot Algebra
#+author: POO Flow
#+language: en

* Status

This RFC is an accepted semantic contract.

It defines the minimum higher-order Module POO value.  It does not admit an
implementation, freeze dispatch behavior, or add public syntax.  Implementation
remains blocked until RFC 45-120 admits the exact thin-adapter paths used by the
Module value.

* Scope

This RFC owns:

- the minimum required semantic slots of a Module POO value;
- the distinction between required slots and derived responsibilities;
- the purity and identity rules of recursive Module imports;
- the relation among Module capabilities, exported Profiles, ProfileBundle
  projection, conflicts, provenance, and composition receipts;
- the upstream POO authoring and projection operations intended for later
  adapter admission.

It does not own:

- upstream =gerbil-poo= object, prototype, dispatch, or precedence semantics;
- exact dispatch resolution or tracing;
- runtime capability handles;
- package dependencies;
- application deployment policy;
- fixed-point runtime implementation;
- a new Module macro or clause DSL.

* Central decision

A Module is one higher-order native POO value with four required semantic
slots:

- =identity=;
- =imports=;
- =capabilities=;
- =profiles=.

The required slots contain first-class semantic values.  They are not raw
lists, alists, hashes, strings, package declarations, runtime handles, or
imperative callbacks.

All remaining Module behavior is derived through native POO prototype
extension, composition, slot projection, and dispatch.

* Required slot: identity

=identity= is a stable semantic Module identity.

It is distinct from:

- a Git repository or revision;
- a Gerbil package identity;
- a filesystem path;
- a deployment generation;
- a runtime execution identity;
- a final composition identity.

Prototype extension may derive a new Module value without changing its semantic
identity only when the extension preserves the same Module responsibility.
Changes that define a distinct Module responsibility require a distinct
identity.

Identity equality, revision evidence, and composition provenance must remain
separate relations.

* Required slot: imports

=imports= is a first-class POO responsibility relation.

It expresses Modules reachable from this Module, including transitive
to-B-to-C structures.  It does not mean:

- =gerbil.pkg= dependencies;
- Git submodules;
- source checkout paths;
- build graph edges;
- runtime process dependencies.

Import reachability is evaluated lazily and purely.  Construction of a Module
value does not eagerly traverse or instantiate the global graph.

Recursive imports are admitted only through explicit evaluation context,
lineage, cycle detection, budgets, structured outcomes, and observable
provenance.  A cycle is not automatically an error; an unproductive or
unbounded evaluation is a structured condition.

* Required slot: capabilities

=capabilities= is a first-class POO capability contract with two semantic
responsibilities:

- requirements;
- provisions.

It describes what a Module responsibility needs and can provide.  It does not
contain ambient authority, open file descriptors, secret values, runtime
clients, environment lookups, or effectful callbacks.

Capability satisfaction, attenuation, conflict, and explanation are pure
semantic operations.  Runtime realization occurs later through admitted
runtime/deployment adapters.

* Required slot: profiles

=profiles= exports first-class Profile values owned by the Module.

It does not export:

- unqualified global names;
- raw configuration sections;
- imperative activation hooks;
- package build targets;
- deployment variants owned by the final application.

A selected Profile projects one ProfileBundle responsibility.  The recursive
imports closure and capability admission of that bundle are derived from the
Module graph; they are not embedded as duplicate Profile data.

* Derived responsibilities

The following are derived semantic responsibilities, not additional required
storage fields:

- recursive reachable responsibilities;
- admitted capability closure;
- selected ProfileBundle;
- conflicts and explanations;
- identity and export provenance;
- semantic composition receipt.

Their exact dispatch names are not frozen here.  RFC 45-122 must define
dispatch ownership, candidate selection, precedence, inherited computation,
structured failure, tracing, and cache behavior before any derived
responsibility becomes public.

* Upstream operation correspondence

The intended upstream operation families are already semantics-proven at the
pinned revision:

| Module concern | Upstream operation family | Admission use |
|----------------+---------------------------+---------------|
| Base POO value authoring | =.def= and =.o= | Author one Module POO value without a project object representation |
| Prototype derivation | =.extend= | Derive one responsibility-preserving variant |
| Higher-order composition | =.mix= and =.+= | Compose native prototypes without a project merge engine |
| Slot projection | =.get= and =.@= | Project required and derived semantic responsibilities |
| Generic prototype composition | =compose-proto= and =compose-proto*= | Evidence for higher-order prototype composition, not an alias for =compose profiles= |
| Precedence and inherited computation | upstream object slot and precedence semantics | Preserve upstream behavior; do not reimplement it |

Those operation families remain unadmitted as project adapters.  RFC 45-120
must move each consumed path to =ADMITTED= before implementation entry.

* Purity boundary

The Module value is pure:

- required slots depend only on explicit semantic inputs;
- derived responsibilities are deterministic for the same evaluation context;
- no host =if= selects a Profile variant inside composition;
- no environment, filesystem, clock, entropy, or secret observation occurs;
- no mutation operator enters ordinary Module composition;
- no runtime publication changes the Module value.

Lazy evaluation, memoization, and fixed-point behavior do not weaken purity.
They require explicit cache identity, cycle observability, budgets, and
structured terminal or continuable outcomes.

* Authoring and public interface

Native =gerbil-poo= object and prototype operations are the advanced extension
interface.

The ordinary interface remains a thin selection and composition surface:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

=use-module= selects an exported Profile from one Module and projects one
ProfileBundle responsibility.  It does not construct a Module, traverse package
dependencies, execute runtime effects, or interpret clauses.

* Admission checklist

** Required semantic slots

- [X] Freeze =identity= as semantic identity rather than repository, package,
  revision, deployment, or execution identity.
- [X] Freeze =imports= as a first-class recursive responsibility relation.
- [X] Freeze =capabilities= as pure requirements and provisions.
- [X] Freeze =profiles= as first-class Module-owned Profile exports.
- [X] Reject raw list, alist, hash, string, runtime-handle, and callback values
  as the ordinary representation of required slots.

** Derived responsibilities

- [X] Keep reachability, ProfileBundle, conflict, provenance, and receipt values
  derived rather than duplicated required storage.
- [ ] Define dispatch semantics for every derived responsibility in RFC 45-122.
- [ ] Define evaluation-context, cycle, budget, cache, and explanation behavior
  for recursive imports.
- [ ] Prove that capability closure is monotonic under attenuation and explicit
  withdrawal.

** Upstream adapter admission

- [ ] Admit the =.def= and =.o= authoring path required by the Module value.
- [ ] Admit =.extend= for responsibility-preserving derivation.
- [ ] Admit =.mix= and =.+= only where the Module semantic contract requires
  native prototype composition.
- [ ] Admit =.get= and =.@= for typed semantic projection.
- [ ] Prove that no adapter reproduces upstream precedence, inherited
  computation, slot, or object semantics.

** Integration boundary

- [ ] Prove one-root instantiation and recursive import closure.
- [ ] Prove structured cycle and budget outcomes.
- [ ] Prove semantic receipt separation from package, build, and runtime
  evidence.
- [ ] Run focused GSLPH development checks without introducing a product
  dependency.

* Rejected alternatives

- A Module represented by an alist, record DSL, or package manifest.
- Separate imperative objects for identity, imports, capabilities, and Profiles.
- Imports interpreted as package or build dependencies.
- Capabilities represented by runtime handles or ambient authority.
- Profiles represented by unqualified names or configuration sections.
- Eager global graph traversal during Module construction.
- Host conditionals selecting Profile variants inside =compose=.
- Duplicating upstream prototype composition, inherited computation, or
  precedence logic.
- Freezing dispatch names before dispatch semantics are reviewed.

* Successor contract

RFC 45-122 must treat dispatch as a first-class POO semantic plane.

It must define:

- dispatch request and candidate identity;
- instance, type, and prototype dispatch sources;
- precedence and inherited-computation behavior;
- =super= and next-method continuation;
- missing-method and ambiguity conditions;
- purity and capability boundaries;
- dispatch tracing, explanation, cycle detection, budgets, and cache identity;
- the relation between dispatch and Module derived responsibilities.

It must not introduce a new public dispatch DSL or hide runtime effects behind
a dispatched slot.

* Native object and type foundation

The four-slot Module value is the first domain object in this RFC chain, but it
is not the project's primitive object foundation.  Its implementation depends
on the following already ordered layers:

#+begin_src mermaid
flowchart LR
  O["project objects.ss"] -->|"constructs native project POO objects through upstream mechanics"| T["project types.ss"]
  T -->|"assigns POO-native type and contract responsibilities"| M["Module: identity, imports, capabilities, profiles"]
  M -->|"supplies a complete semantic receiver"| D["DispatchEvaluation"]
#+end_src

=objects.ss= owns project object construction on top of upstream =gerbil-poo=.
The intended =types.ss= owns POO-native Type and Contract prototypes.  A Module
is then an ordinary typed POO value whose four required responsibilities are
described and checked by that shared foundation.

This ordering has several consequences:

- Module must not wrap another object or convert a record, alist, package
  manifest, or registry entry into a second object representation.
- Module must not carry a private validator that duplicates the shared Type and
  Contract prototype algebra.
- Type and Contract checks are pure semantic responsibilities that produce
  inspectable success or diagnostic evidence; they do not acquire runtime
  handles or perform adapter effects.
- Downstream domain packages such as =wendao-episteme= extend or compose the
  admitted Module prototype rather than defining a competing Module base.
- =use-module= remains a later thin hygienic projection.  It is not required to
  construct the foundational objects.
- =DispatchEvaluation= starts only after a Module value satisfies the shared
  object and type/contract foundation.

The exact project owner =src/module-system/types.ss= is not implementation-
admitted yet.  This RFC therefore freezes the dependency and semantic boundary,
not a completed implementation.

** Foundation admission checklist

- [X] Keep exactly four required Module responsibilities.
- [X] Place Module above the project object and type/contract foundation.
- [X] Require Type and Contract to remain POO-native semantic values.
- [X] Keep downstream extension and dispatch evaluation outside construction.
- [ ] Admit the shared Type and Contract prototype algebra.
- [ ] Admit Module construction against that shared algebra.

* Normative responsibility

This module exclusively owns the public composition shape and the internal
higher-order Mix module POO shape.

* Approved public composition surface

The canonical user surface is:

#+begin_src scheme
(use-composition my-system
  (use-module wendao-episteme as episteme
    (profiles research observability)
    (profile production))
  (compose
    (profiles episteme research observability production)))
#+end_src

=use-composition= is the sole public macro head and names the final user
composition.  /User Composition/ is the conceptual domain, not a second macro
identifier.  =use-module MODULE as ALIAS= is the canonical module clause,
=compose= is the composition declaration, and =profiles= is a hygienic syntax
marker selecting the profile composition algebra.  No nested composition
wrapper, =user-composition= compatibility alias, =initial= form, public =mix=
tag, or explicit =base-profile= belongs to this surface.

Every admitted operand is a hygienic identifier whose runtime value is a POO
Profile object.  The parser does not accept an arbitrary Scheme expression as
a direct =compose= operand.  A higher-order Mix may participate because it is
profile-compatible, but it is first declared through =(profile MIX-NAME)=; its
=identity=, =imports=, and =capabilities= slots remain internal POO slots and
MUST NOT leak into ordinary author grammar.

Imported profile cases are declared and selected through the canonical alias:

#+begin_src scheme
(use-module wendao-episteme as episteme
  (profiles research observability))

(compose
  (profiles episteme research observability))
#+end_src

This does not call another composition operation.  The imported slots
contribute their profile prototypes to the enclosing composition boundary, and
the expander flattens those contributions with the remaining declared profiles
into one ordered lineage.

The public form requires at least one profile operand.  The internal law that
a receiver with no refinements is observationally equivalent to the receiver
does not justify a public empty composition or a visible base profile.

** Gerbil expander responsibilities

Gerbil metaprogramming is used as a staged compiler for the POO author surface,
not merely as a hygienic textual rewrite:

#+begin_export mermaid
flowchart LR
    A["Profile declaration"] --> B["Compile-time semantic projection"]
    A --> C["Runtime POO prototype"]
    B --> D["Lexical binding and case validation"]
    D --> E["Flat ordered lineage plan"]
    E --> F["One POO prototype composition"]
    C --> F
#+end_export

- =defrules= handles direct constructor families and simple syntax-to-POO
  lowering.
- =defsyntax= with =syntax-case= performs shape validation, case selection,
  source-aware errors, and alternate expansion paths.
- =with-syntax= creates hygienic temporaries so each runtime operand is
  evaluated at most once.
- =begin-syntax= holds bounded, declaration-owned static facts.
- =syntax-local-value= resolves profile and refinement declarations by lexical
  binding rather than strings or a global symbol registry.
- =for-syntax= makes phase dependencies explicit.
- macro objects are reserved for declarations that genuinely require explicit
  expander state.

The compile-time projection owns syntax, lexical binding, static shape, source
locations, and flat-lineage planning.  The runtime projection owns POO slots,
prototype resolution, laziness, fixed points, and recoverable control.  Macro
expansion MUST produce ordinary POO-native and functional code and MUST NOT
execute the runtime model during expansion.

* Use-composition result and binding contract

The public contract requires =use-composition= to establish the named
=clan/poo= prototype binding directly.  It does not bind a configuration AST,
composition builder, realization handle, module-registry entry, or intermediate
value that requires a later initialization step.

The current implementation is still an expression macro and therefore forces
authors to repeat the name as =(def my-system (use-composition my-system
...))=.  That shape contradicts the direct-binding contract and is not accepted
as the final public syntax.  The binding transition remains an explicit open
implementation item below; no second =user-composition= wrapper may repair it.

#+begin_src scheme
(use-composition my-system
  (use-module wendao-episteme as episteme
    (profiles research)
    (profile production))
  (compose
    (profiles episteme research production)))
#+end_src

#+begin_export mermaid
flowchart LR
    A["use-composition declaration"] -->|"intended: binds once"| B["Compile-time profile descriptor"]
    X["current expression macro"] -.->|"counterexample: repeats binding name"| R["Redundant outer def"]
    A --> C["Runtime clan/poo prototype binding"]
    B --> D["Case validation and flat contribution plan"]
    D --> C
    C --> E["Normal Gerbil import and export"]
    C --> F["POO extension and composition"]
    C --> G["Lazy slot demand"]
#+end_export

** One name with two phase projections

The declaration has a compile-time projection containing the profile role,
case declarations, source locations, and flat-contribution plan, and a runtime
projection containing the resulting =clan/poo= prototype.  Hygienic expansion
keeps generated bindings private; the author manages only the declared name.

The concrete Gerbil transformer technique remains subject to exact
=symbol-located= evidence.  The public contract does not depend on a generated
identifier or private expander representation.

** Normal Gerbil module integration

Downstream modules obtain the declared prototype through normal Gerbil lexical
import and export.  They may read its POO slots, extend it through public
=gerbil-poo= operations, use it as another profile-composition operand, place
it in a higher-order Mix or Submodule, or demand a lazy slot.

=user-composition= does not replace the Gerbil module system and does not
introduce a package loader, registry, or initialization protocol.  There is no
public:

#+begin_src scheme
(initial my-system)
(realize-composition my-system)
#+end_src

The declaration establishes the prototype lineage.  Realization occurs through
the =gerbil-poo= slot-demand lifecycle rather than a second authoring phase.

** Composition closure

The declared result remains profile-compatible and may participate in another
composition:

#+begin_src scheme
(use-composition production-research
  (use-module local-profiles as local
    (profile my-system)
    (profile hardened-production))
  (compose
    (profiles local my-system hardened-production)))
#+end_src

This operation extends a POO prototype lineage; it does not compose a serialized
configuration result.  The expander validates the compile-time profile
projection and lowers runtime behavior to the pinned =clan/poo= API.

* Static declarations and first-class POO operands

Profile is a contextual role, not a macro-created nominal type or runtime
marker.  Any valid =clan/poo= prototype may act as an operand in a
=compose profiles= context.  A compile-time descriptor provides earlier case
validation when a declaration is lexically known, but it does not grant a
runtime Profile identity.

#+begin_export mermaid
flowchart TD
    A["compose profiles operand"] --> B{"Lexically known declaration?"}
    B -->|yes| C["Read compile-time descriptor"]
    C --> D["Validate cases and contribute a flat prototype plan"]
    B -->|no| E["Evaluate expression once"]
    E --> F{"Valid clan/poo prototype?"}
    D --> G["One ordered clan/poo composition"]
    F -->|yes| G
    F -->|no| H["Structured operand condition"]
#+end_export

** Static profile operands

A lexically known POO Profile is declared by identifier inside the canonical
=use-module= clause.  Imported module slots use =(profiles NAME ...)=; existing
lexical POO values use =(profile NAME)=.  The =compose= clause then refers to
those declarations through the hygienic module alias plus profile identifiers.
Raw case-selection calls and arbitrary expressions are not direct =compose=
operands.

#+begin_src scheme
(use-module wendao-episteme as episteme
  (profiles research observability)
  (profile production))
#+end_src

Case flags belong to the declaration syntax.  They are not runtime keyword
arguments.

** Dynamic profile values

A first-class Scheme expression may produce a profile-compatible POO object,
but the expression is evaluated and bound before composition.  The canonical
parser consumes the resulting identifier through =(profile NAME)=; it does not
execute or embed the arbitrary expression as a =compose= operand.

#+begin_src scheme
(def selected-profile (select-profile environment))

(use-composition selected-system
  (use-module local-profiles as local
    (profile selected-profile)
    (profile production))
  (compose
    (profiles local selected-profile production)))
#+end_src

The dynamic expression is evaluated exactly once and is not executed by the
expander.  Its only base operand check is that the result is a valid
=clan/poo= prototype; this check does not force lazy slots.  The resulting
prototype joins the same single ordered =clan/poo= composition.

The macro MUST NOT guess a case owner for:

#+begin_src scheme
((select-profile environment) +research)
#+end_src

A dynamic selector that needs a case returns the already refined POO prototype
as its ordinary value.

** Descriptor boundary

The compile-time descriptor may contain case grammar, source provenance,
static contribution shape, and the identity of the corresponding runtime
binding.  It MUST NOT contain a Profile type tag or copy slot values, imports,
capability realizations, fixed-point state, or a realized runtime lineage.

Static unknown profiles or cases fail during expansion at the declaration
site.  A dynamic value that is not a valid =clan/poo= prototype raises a
structured operand condition.  The condition may participate in the approved
recovery model.

** Contextual Profile role and optional Mix structure

=profiles= selects the authoring and diagnostic context.  It does not add a
=profile?= predicate, =profile-role-tag=, hidden class, or compatibility marker
to the runtime object.

#+begin_export mermaid
flowchart LR
    A["clan/poo prototype"] --> B["Contextually used as Profile"]
    A --> C{"Exposes Mix structural capability?"}
    C -->|yes| D["Also acts as higher-order Mix"]
    C -->|no| E["Ordinary Profile prototype"]
#+end_export

An ordinary Profile does not require Mix slots.  Only an object that also
assumes the higher-order Mix role is checked for the internal =identity=,
=imports=, and =capabilities= structure and invariants.  Capability and
Submodule roles are likewise checked only when those structural roles are
actually used.

The =profiles= marker may validate static case syntax, collect prototype
contributions, preserve order, and produce profile-specific diagnostics.  It
MUST NOT redefine prototype linearization, slot resolution, =super=,
fixed-point behavior, or runtime object identity; those remain =gerbil-poo=
semantics.

* Profile case semantics

A Profile case is a statically named POO refinement, not a function keyword,
boolean feature flag, configuration option, or runtime registry entry.

#+begin_src scheme
(wendao-episteme +research +observability)
#+end_src

The declaration contributes the base prototype followed by the selected case
refinement prototypes in source order.

#+begin_export mermaid
flowchart LR
    A["wendao-episteme declaration"] --> B["+research case"]
    A --> C["+observability case"]
    B --> D["Ordered POO refinement contributions"]
    C --> D
    D --> E["Flat lineage plan"]
#+end_export

** Lexical case ownership

A case identifier is owned by its Profile declaration descriptor.  The
expander first resolves the head declaration and then interprets its following
case identifiers.  The same spelling, such as =+observability=, may denote
different refinements for different Profile declarations without a global
feature registry or qualified string namespace.

** Order and duplication

Case order is semantically significant and MUST be preserved.  The expander
does not sort, canonicalize, or treat cases as a set.  Slot interaction follows
the resulting =gerbil-poo= lineage and =super= semantics.

A case repeated in the same static application is an expansion-time error:

#+begin_src scheme
(wendao-episteme +research +research)
#+end_src

The expander MUST NOT silently deduplicate it, apply it twice, or choose the
last occurrence.  A repeatable operation requires a separately declared
semantic case rather than an implicit token count.

** Contributions to multiple boundaries

One case may contribute ordered refinements to several structural boundaries
while preserving the identity scope of each boundary.

#+begin_export mermaid
flowchart TD
    A["+observability case"] --> B["Current Mix refinement"]
    A --> C["Nested observability Submodule refinement"]
    A --> D["Capability refinement"]
    A --> E["Policy refinement"]
    B --> F["Mix boundary"]
    C --> G["Submodule boundary"]
    D --> H["Capability boundary"]
    E --> I["Policy boundary"]
#+end_export

The descriptor records the case identifier, allowed occurrence count, ordered
contribution description, target structural boundaries, source provenance, and
static shape constraints.  It MUST NOT contain realized objects, forced
imports, runtime lineage results, or fixed-point state.

** Dynamic parameters remain Scheme values

Ordinary cases are parameterless.  A requirement with dynamic parameters is
expressed as a Scheme function that returns a POO prototype and is then used as
a dynamic operand:

#+begin_src scheme
(research-profile-for dataset)
#+end_src

The case surface MUST NOT expand into an arbitrary nested configuration DSL
with timeout, retry, dataset, or other runtime arguments.

** POO-native case bodies

The root and every case contribution are ordinary POO expressions.  Existing
POO-native operators may be used directly:

#+begin_src scheme
(defprofile wendao-episteme
  (.o
    <root-slot-definition> ...)

  (+research
    (==> <research-prototype>
         <slot-transform> ...))

  (+observability
    (==>.+= <observability-prototype>
            <slot-transform> ...)))
#+end_src

=defprofile= does not redefine the POO-native operators shown above and does
not introduce a row, record, patch, or configuration DSL around them.

** Hygienic dual projection

#+begin_export mermaid
flowchart LR
    A["defprofile declaration"] --> B["Hidden runtime root prototype"]
    A --> C["Hidden runtime refinement prototypes"]
    A --> D["Compile-time case descriptor"]
    D --> E["Public lexical binding: wendao-episteme"]
    B --> E
    C --> D
    E --> F["wendao-episteme with selected cases"]
#+end_export

The macro creates hygienic hidden runtime bindings for the root and refinement
prototypes, plus a compile-time descriptor that maps case identifiers to
ordered structural contributions.  Expansion preserves source provenance and
does not evaluate POO expressions at compile time or copy runtime slot and
fixed-point state.

** Multiple structural contributions

One case clause may contribute several already constructed POO refinements:

#+begin_src scheme
(+observability
  observability-mix-refinement
  telemetry-capability-refinement
  recovery-policy-refinement)
#+end_src

Each contribution carries its own structural boundary.  The author does not
declare string targets or write a public path-refinement DSL.

Case declaration order provides deterministic descriptor output but does not
define application precedence.  The order written at the use site determines
the ordered refinement lineage.

** One exported identifier

A downstream module imports only the declared name, such as
=wendao-episteme=.  Hidden prototype bindings, case tables, descriptors, and
syntax support remain implementation details.  =defprofile= is a structural
macro that declares a POO prototype and its static case projection; it does not
create a Profile class or another object system.

* Profile identifier expansion contract

One exported Profile identifier has three context-sensitive uses while
preserving one runtime prototype identity.

#+begin_export mermaid
flowchart TD
    A["wendao-episteme occurrence"] --> B{"Syntax position"}
    B -->|"bare expression"| C["Expand to hidden root prototype binding"]
    B -->|"case application"| D{"Inside compose profiles?"}
    D -->|yes| E["Contribute root and cases to enclosing flat plan"]
    D -->|no| F["Perform one local gerbil-poo composition"]
    B -->|"other application"| G["Expansion-time syntax error"]
#+end_export

** Bare identifier expression

A bare Profile identifier expands to the hygienic hidden root
=clan/poo= prototype binding and therefore remains a first-class Scheme value:

#+begin_src scheme
(define selected wendao-episteme)
(list wendao-episteme production)
#+end_src

There is no public value or prototype accessor and no explicit unwrap step.

** Standalone case expression

A case application outside an enclosing =compose profiles= form performs one
local =gerbil-poo= composition and returns the refined prototype:

#+begin_src scheme
(define research-system
  (wendao-episteme +research))
#+end_src

** Case expression inside composition

When the same case application is an operand of =compose profiles=, the outer
expander reads its descriptor directly and contributes the root and selected
case refinements to the enclosing flat plan.  It MUST NOT first construct an
intermediate refined prototype and then compose that value again.

Thus a standalone case expression has one local composition boundary, while
an enclosed case expression joins the one enclosing boundary.  Neither path
emits nested prototype-composition calls.

** Invalid application and dynamic parameters

A Profile identifier in operator position accepts only its declared static
case identifiers.  Another argument shape, such as:

#+begin_src scheme
(wendao-episteme dataset)
#+end_src

is an expansion-time syntax error rather than a guessed function call.  A
dynamic parameter is handled by an ordinary Scheme function that returns a POO
prototype.

** Lexical transformer export

=defprofile= exports one lexical transformer.  In identifier position it
projects the hidden runtime root; in application position it resolves static
cases; and when inspected by =compose profiles= it provides the compile-time
descriptor.

Generated runtime references retain the defining module's lexical context.
Downstream modules import only the declared Profile name and do not import root,
case-table, descriptor, or syntax-support identifiers separately.  The exact
Gerbil transformer mechanism remains =symbol-located= work; this contract fixes
only its public observable behavior.

* Boundary-local ordering and contribution projection

A user composition does not create one global lineage spanning the Profile
root, every Mix root, and every nested Capability or Submodule.  Source
operands and cases are projected into the ordered contribution sequence of
each structural boundary.

#+begin_export mermaid
flowchart TD
    A["State 1: lexical operand stream"]
    A -->|"project ordinary Profile contributions"| B["State 2P: Profile-boundary plan"]
    A -->|"detect Mix role and scoped identity"| C["State 2M: wendao Mix-boundary plan"]
    A -->|"route case contribution to capability scope"| D["State 2C: observability capability plan"]
    B -->|"append source item 1"| B1["base"]
    B1 -->|"same boundary: precedes"| B2["wendao Profile projection"]
    B2 -->|"same boundary: precedes"| B3["production"]
    B3 -->|"normalize once"| BP["State 3P: ordered Profile lineage"]
    C -->|"append root"| C1["wendao root"]
    C1 -->|"case order: research first"| C2["+research Mix refinement"]
    C2 -->|"case order: observability second"| C3["+observability Mix refinement"]
    C3 -->|"normalize once"| CP["State 3M: ordered wendao Mix lineage"]
    D -->|"append scoped refinement"| D1["+observability capability refinement"]
    D1 -->|"normalize once"| DP["State 3C: ordered capability lineage"]
#+end_export

** Boundary-local order preservation

For any two contributions that enter the same structural boundary, their
relative order follows the source operand order and then the case and case-body
order.  The expander MUST NOT sort, group by spelling, or treat contributions
as an unordered set.

If a later Profile operand contributes another refinement to an existing Mix
or Capability root, that contribution follows earlier contributions in that
same boundary.

** No cross-boundary precedence

Different boundaries do not override one another.  Source order may be
retained as provenance for conditions and receipts, but it creates no
cross-boundary slot precedence or =super= relationship.

=super= resolves only within one lineage root.  Sibling Mix roots do not inherit
from one another.  Capability, Mix, and Submodule relationships use
containment or explicit POO references, while =imports= establishes dependency
edges rather than inheritance.

** Bounded compile-time contribution forest

#+begin_export mermaid
flowchart LR
    A["State 1: lexical operands and cases"]
    A -->|"resolve descriptors without runtime evaluation"| B["State 2: bounded contribution forest"]
    B -->|"select Profile boundary identity"| C["State 3P: ordered Profile sequence"]
    B -->|"select each Mix boundary identity"| D["State 3M: ordered Mix sequences"]
    B -->|"select each Capability or Submodule identity"| E["State 3S: ordered nested sequences"]
    C -->|"after symbol-located and behavior-proven: invoke once"| CP["State 4P: gerbil-poo Profile prototype"]
    D -->|"for each Mix boundary: invoke once"| DP["State 4M: sibling gerbil-poo Mix prototypes"]
    E -->|"for each nested boundary: invoke once"| EP["State 4S: sibling nested prototypes"]
    CP -. "no cross-boundary precedence" .-> DP
    DP -. "containment or explicit references only" .-> EP
#+end_export

The contribution forest maps structural boundary identities to ordered
contribution syntax.  It is a bounded compile-time lowering plan, not a runtime
configuration AST, object system, registry, or merge engine.

Every boundary is lowered to one =gerbil-poo= composition operation whose exact
public symbol and behavior must reach =behavior-proven=.  The POO Flow expander
does not resolve slots or implement prototype linearization.

If one case contributes several refinements to the same boundary, their case
body order is preserved.  Contributions to different boundaries enter their
respective local sequences without acquiring a false global evaluation order.

** Lazy and concurrent realization

Source order constrains prototype semantics only within one lineage.  Sibling
boundaries without dependency edges may be demanded lazily or evaluated
concurrently by the =gerbil-poo= lifecycle.  A single user composition MUST NOT
force unrelated Submodules into source-order serial execution.

* Use-composition identity separation

=use-composition= MUST keep three identities distinct:

1. the lexical Gerbil binding name;
2. the runtime lineage-root identity owned by =gerbil-poo=;
3. the provenance/content identity carried by qualification evidence.

These identities answer different questions and MUST NOT be collapsed into one
user-supplied string.

#+begin_src mermaid
flowchart LR
  D["State: user-composition declaration"] -->|"Gerbil binding projection"| L["State: lexical binding name"]
  D -->|"gerbil-poo prototype construction"| R["State: fresh runtime lineage root"]
  D -->|"source + descriptor + dependency revision + lowering evidence"| P["State: provenance receipt"]
  P -->|"canonical evidence projection"| C["State: content identity"]
  L -->|"import rename changes spelling only"| L2["State: renamed lexical binding"]
  R -->|"same object is imported or re-exported"| R2["State: preserved runtime lineage root"]
  P -.->|"diagnostic attribution; no precedence or runtime identity authority"| L2
  R -->|"derived composition constructs a new root"| DR["State: derived runtime lineage root"]
  P -->|"records parent root, refinements, source, dependency revision, and lowering evidence"| DP["State: derived provenance receipt"]
  DR -->|"qualified by"| DP
#+end_src

** Lexical binding identity

In

#+begin_src scheme
(use-composition my-system
  (use-module wendao-episteme as episteme
    (profiles research observability)
    (profile production))
  (compose
    (profiles episteme research observability production)))
#+end_src

=my-system= is a Gerbil binding name.  It participates in lexical scope,
import, rename, and re-export.  It is useful for diagnostics, but it MUST NOT
be a runtime lineage identity, memoization key, or cross-context cache key.

The public form MUST NOT add a =#:identity= string parameter.  The hygienic
macro already has the lexical binding identity, while =gerbil-poo= owns the
runtime object identity.

** Runtime lineage-root identity

Each independently evaluated =use-composition= declaration constructs a
fresh =gerbil-poo= lineage root.  Two declarations with identical source text
therefore do not denote the same runtime root.

Import rename and re-export preserve the imported POO object and its runtime
lineage-root identity.  Changing the lexical spelling MUST NOT reconstruct the
object or mint a replacement root.

A derived composition constructs a new lineage root.  It MUST NOT overwrite,
borrow, or impersonate a parent root merely because it contains the same
refinements.

** Provenance and content identity

Qualification receipts describe how a composition was produced.  A derived
composition receipt MUST link at least:

- the parent lineage-root evidence;
- the ordered refinements and boundary-local order;
- the source/descriptor evidence;
- the exact dependency revision evidence;
- the macro-lowering evidence state.

Provenance/content identity supports evidence comparison across contexts and
processes.  A successful comparison may authorize evidence-linked reuse, but
it MUST NOT claim that two independently constructed runtime roots are the
same POO object.

** Identity behavior under module operations

| Operation | Lexical binding | Runtime lineage root | Provenance/content |
|---+---+---+---|
| local declaration | creates the declared name | creates a fresh root | creates declaration evidence |
| import rename | changes local spelling | preserves the imported root | preserves and may extend import attribution |
| re-export | exposes another binding path | preserves the exported root | preserves and may extend export attribution |
| independent identical declaration | may reuse the same spelling in another scope | creates a distinct root | may have equal content evidence |
| derived composition | creates the derived binding | creates a new derived root | links parents, refinements, dependencies, and lowering |

* Provider-resolution reference

Boundary-scoped provider capability resolution is specified by
[[file:45-10-provider-runtime-search-closure.org][Provider Runtime Search Closure]].  This module owns Profile, Mix, and capability
composition; it does not define runtime search order or execute a provider.

* Retired public spelling (non-normative)

Earlier notes used a =user-composition= macro head and the unparenthesized
=compose profiles= shorthand.  Neither form is a compatibility syntax,
deprecation path, or alternate public parser entry.  The sole normative macro
head is =use-composition=; its =use-module MODULE as ALIAS= clause is part of
the canonical grammar rather than historical loader syntax.

The canonical module clause remains:

#+begin_src gerbil
(use-module MODULE as ALIAS)
#+end_src

It appears directly inside the enclosing =compose profiles= declaration and
is followed by ordinary Profile operands.

#+begin_src gerbil
(use-composition governance-workspace
  (use-module wendao-episteme as episteme
    (profiles episteme-profile)
    (profile local-governance-profile))
  (compose
    (profiles episteme episteme-profile local-governance-profile)))
#+end_src

The Profile names are illustrative.  The public grammar is not extended with
=identity=, =imports=, =capabilities=, =initial=, or =resolve= clauses.

The existing parser owner remains
=profile-composition-syntax-plan.ss=.  This RFC owns the semantic expansion
contract, not another parser.

* Mix identity scope and Profile projection

A Mix is an independent higher-order POO composition boundary.  Its internal
=identity=, =imports=, and =capabilities= slots MUST NOT be flattened into the
ordinary slot namespace of the final Profile root, where unrelated Mix
identities would overwrite one another.

#+begin_export mermaid
flowchart TD
    A["Final Profile prototype"] --> B["Ordinary Profile lineage"]
    A --> C["Internal Mix-space POO prototype"]
    C --> D["Mix identity A"]
    C --> E["Mix identity B"]
    D --> F["A imports and capabilities"]
    E --> G["B imports and capabilities"]
#+end_export

=Mix space= is a conceptual name for this internal POO composition boundary.
It is not public grammar, a raw map, a registry, or a second object system.
Its implementation consists only of =gerbil-poo= objects and public prototype
operations.

** Mix operand projection

The public composition remains:

#+begin_src scheme
(use-composition my-system
  (use-module local-profiles as local
    (profile wendao-episteme)
    (profile another-mix)
    (profile production))
  (compose
    (profiles local wendao-episteme another-mix production)))
#+end_src

The POO Flow role combinator distinguishes an ordinary Profile contribution
from a higher-order Mix contribution without adding a Profile runtime tag.
Ordinary contributions join the Profile lineage.  A Mix contribution enters
the internal Mix space under its identity boundary.

#+begin_export mermaid
flowchart LR
    A["Profile operand"] --> B{"Exposes Mix structure?"}
    B -->|no| C["Ordinary Profile lineage contribution"]
    B -->|yes| D["Contribute Mix root by identity"]
    D --> E["Internal Mix-space prototype"]
    C --> F["Final Profile prototype"]
    E --> F
#+end_export

Within one Mix space, different identities establish sibling Mix roots.
Contributions with the same identity refine one another only when they share
the same lineage root.  Independent roots that claim the same identity raise
an identity-collision condition.  A Profile refinement cannot change an
existing Mix root identity.

** Imports boundary

A Mix =imports= slot denotes lazy POO dependencies in the Mix semantic model.
It is not a Gerbil module =import=, a =gerbil.pkg= dependency, or a Bazel or Nix
build dependency.  Shape validation MUST NOT force it.  Demand, recursion,
cycle behavior, and fixed-point evaluation remain =gerbil-poo= semantics.

** Capability space

The =capabilities= slot is itself an internal POO prototype space.  Each
capability is a POO prototype whose identity establishes its refinement
boundary.  Different capability identities form sibling roots; contributions
to the same identity use the normal =gerbil-poo= lineage when they share a
root.  Capability removal or narrowing requires an explicit refinement rather
than an absent key or =#f= overwrite.

The same scoped structure may recur inside a Mix Submodule, allowing arbitrary
to-B and to-C nesting without introducing another module language.

* Recursive scoped identity and dependency topology

A Mix identity is unique only among sibling roots in its enclosing Mix space.
It is not a global system name.  The same local identity may legally occur
under different parent Mix roots.

#+begin_export mermaid
flowchart TD

    B --> C["wendao-episteme"]
    B --> D["production-services"]
    C --> E["observability"]
    C --> F["research"]
    D --> G["observability"]
#+end_export

The two =observability= roots above do not collide because their enclosing Mix
spaces differ.  Their readable structural addresses are derived from POO
containment lineage; they are not global string registry keys.

** Recursive local flatness

Each POO composition boundary owns one flat, ordered refinement lineage.  A
recursive Submodule hierarchy is therefore a hierarchy of locally flat
lineages, not one global flattened list and not a runtime tree of nested
=compose= calls.

The root Profile, its Mix space, every Mix root, and every nested Capability or
Submodule boundary each normalize their own contributions once.  Composition
does not cross or erase these identity scopes.

** Containment and import edges

#+begin_export mermaid

Containment establishes ownership and identity scope.  A Mix =imports= edge
establishes a lazy demand dependency and does not change the imported object's
parent.  Import cycles use =gerbil-poo= recursive-object, fixed-point, and cycle
semantics.

An internal import should hold a lexically resolved POO prototype reference or
a structural reference carrying the parent-scope identity.  It MUST NOT depend
on a mutable global registry or a global string path.  Human-readable paths in
conditions and receipts are observation projections derived from containment
lineage rather than the source of object identity.

** Cross-boundary case refinements

A statically declared Profile case may contribute a refinement to a nested
boundary.  The declaration descriptor records the target structural boundary
and hygienically contributes the nested prototype while the public form
remains:

#+begin_src scheme

#+end_src

The author does not write a public path-refinement DSL.  A dynamic operand that
needs the same behavior returns an already constructed nested POO prototype.

** Scoped collision condition

An identity collision requires all three facts:

#+begin_example
same enclosing Mix space
  + same local identity
  + distinct lineage roots
#+end_example

Equal local identities under different parents are valid siblings in different
scopes.  Contributions sharing the same root form an ordinary refinement
lineage.

* Higher-order Mix module

#+begin_src text
MixModuleObject
  identity
  imports
  capabilities
#+end_src

All three are POO slots:

- =identity= is immutable semantic module identity.
- =imports= is a POO object of lazy capability computations.
- =capabilities= is a POO object of composable values.

The local alias is presentation identity only.  It does not enter module
identity, G0 canonical values, package identity, or receipts.

Profiles remain separate POO composition objects.  There is no required fourth
=profiles= semantic slot on =MixModuleObject=.

The slots have distinct extension rules:

| Slot | Rule |
|-
| =identity= | established by the module object and preserved unchanged by Profile composition |
| =imports= | POO object that Profiles may extend with lazy module-capability demands |
| =capabilities= | POO object that Profiles may extend/override through normal self/super composition |

A Profile cannot change module identity by overriding a slot.  The expansion
validates that final identity equals the base module identity before publishing
the object.

** Proof-discovered binding, identity, and demand constraints

=UseCompositionBindingIdentityDemandGapModel= separates constraints that the
previous prose had conflated.  The public macro head, lexical binding, runtime
lineage identity, profile coordinate, provenance identity, demand generation,
and mutable demand state are different semantic dimensions.

The current expression macro requires
=(def my-system (use-composition my-system ...))=.  The Lean countermodel proves

parser head is canonical.  Reintroducing =user-composition= would repair the
binding only by violating the single-head contract, so it is not an admissible
solution.

Alias spelling cannot own profile identity: renaming an alias would change an
alias-derived identity for the same module profile.  Slot name alone is also
insufficient because two modules may export the same slot.  The candidate
identity for an exported profile must therefore contain module semantic
identity and slot identity, while the fresh =gerbil-poo= lineage root remains
explicit and alias independent.

That coordinate is not valid for every profile origin.  A local POO Profile,
Mix, or prior composition has no intrinsic module-export coordinate.  The
current mandatory =use-module= syntax can wrap such a value in a presentation
module, but the wrapper identity MUST NOT become the local value's semantic
identity: renaming =local-profiles= would otherwise rename the same POO object.
The proof model therefore uses an origin sum: =moduleExport(module, slot)= or
=localLineage(lineage-root)=.  Both alternatives retain the explicit fresh
lineage root.  This is a proof constraint, not yet the selected concrete Gerbil
prototype or a decision to keep/remove the mandatory module clause.

The current lowerer already supplies the necessary distinction.  An imported
=(profiles NAME ...)= object retains its source module identity.  An existing
or locally declared =(profile NAME)= value does not receive the enclosing
wrapper module or alias as object fields; those values survive only in the
composition-level module-binding and profile-binding metadata.  The future
identity prototype MUST derive local identity from the local POO value and
lineage, never from that lookup metadata.

Consequently wrapped and direct local syntax form one semantic equivalence
class.  Two wrapper spellings may be syntactically different yet elaborate to
the same local identity; a direct local reference is the normal form of that
class.  This quotient does not apply to imported profiles: changing a real
source module changes =moduleExport(module, slot)= and therefore changes
identity.  The proof makes the two interface options comparable without
prematurely selecting one.

Demand state cannot participate in profile identity because a normal
=pending -> realizing -> realized= transition would mutate identity.  Demand
lookup also cannot use profile identity alone: the same profile in two runtime
generations would alias a stale realization.  The candidate demand key must
bind profile identity and runtime generation while keeping mutable demand state
outside semantic identity.

* Lean proof closure for the public syntax boundary

** Requirement

The conceptual domain may be called /User Composition/, but the only public
macro head is =use-composition=.  A successful expansion MUST prove all of the
following properties together:

- the outer form is exactly one =use-composition= form;
- the module header is exactly =use-module MODULE as ALIAS=;
- every body clause is either =compose= or =stage=, and stage identifiers are
  unique;
- the admitted plan contains at least one profile operand; an empty body or a
  stage-only body fails with =composition-missing-profile-operand=;
- the generated alias is a hygienic lexical identifier and cannot capture an
  outer binding with the same spelling;
- the alias is presentation identity only and does not enter module semantic
  identity, profile identity, or the resulting POO lineage.

No theorem about the final list of composed profiles is sufficient by itself.
Such a theorem cannot distinguish the canonical macro from a second
=user-composition= wrapper, a name-only alias resolver, or another rejected
surface that happens to produce the same profile list.

** Observation and counterexamples

The earlier generic composition proofs establish fixed-point and effect
closure after a composition object already exists.  They do not own parser
admission or hygienic binding.  Two minimal counterexamples therefore remain
possible under that weaker model:

1. a noncanonical =user-composition= form and the canonical
   =use-composition= form have the same generic module/profile projection;
2. an outer identifier and a generated alias have the same spelling, so a
   string-only resolver reports a match even though their lexical scopes are
   distinct;
3. the former parser accepted an empty body or a stage-only body even though
   the RFC requires at least one profile operand.

The dedicated Lean owner
=PooFlowProof.Enterprise.UseCompositionSyntaxClosure= constructs both
counterexamples.  It then models the fail-closed parser and proves that parser
acceptance implies a single canonical =use-composition= outer form.

** Cedar capability grant closure

*** Cedar grant requirement

A profile contributes capability *requests*.  It never manufactures policy
grants.  A grant consumed by =use-composition= MUST be an =allow= decision from
the Cedar dual-engine boundary and MUST be bound to all of the following:

- the exact profile origin identity;
- the active runtime generation;
- one shared Cedar authorization subject for both engines and the grant;
- the current authority, policy, authorization, and revocation validation
  context;
- a valid, versioned subject-context bridge receipt whose registry identity and
  generation are bound to both request and grant, and whose mapping from Cedar
  policy-set digest to policy snapshot identity is functional;
- an authority-owned validation result whose authority identity equals the
  current receipt-validation context and whose registry semantic identity is
  bound to both request and grant;
- an authorized capability set that is a subset of the profile request, and a
  granted set that is a subset of that authorized set.

The grant is therefore evidence owned by the policy/admission plane.  Neither a
Mix object nor the composition macro may copy requested capabilities into a
granted slot.

*** Observation and counterexample

The existing dual-engine theorem proves that two distinct engines decide the
same Cedar subject consistently.  The existing capability-envelope theorem
proves confinement of granted capabilities to an authorized set.  Their plain
conjunction is nevertheless insufficient for composition: it does not state
that the grant belongs to the profile identity and runtime generation currently
being composed.

=legacyAdmissionAcceptsCrossProfileGrantReuse= constructs two valid, distinct
Cedar =allow= receipts and a capability-confined grant issued for the
origin-aware identity =(module 42, slot 7, lineage 100)=.  The legacy
conjunction still admits it for =(module 42, slot 8, lineage 101)=.
=legacyAdmissionAcceptsCrossGenerationGrantReuse= constructs the analogous
replay from generation =11= into generation =12=.  These are architectural
counterexamples, not Cedar engine failures.

The first bridge draft still used the higher-order predicate
=AuthorizationSubject -> ReceiptValidationContext -> Prop=.  The predicate
=fun _ _ => True= inhabits that type while providing no registry owner,
generation, lookup receipt, or uniqueness evidence.  Worse, an accept-all
validator can admit two receipts mapping the same registry generation and
policy digest to different snapshots.  The theorem
=acceptAllBridgeReceiptsAreNotFunctional= is the executable counterexample.

Functionality is still not authority.  A validator that accepts exactly one
forged receipt is trivially single-valued.  The theorem
=forgedSingletonIsFunctionalButUnauthorized= constructs such a validator: its
claimed authority is =999= while the current validation-context authority is
=17=.  Consequently, bridge closure now consumes the existing generic
=AcceptanceAuthority= and =AuthorityBoundNode= contract instead of trusting a
self-reported =valid= predicate.

** Cedar input content-identity refinement

*** Input-identity requirement

An authority-bound node containing an exact grant and an exact admitted Cedar
evidence value does not, by containment alone, prove that the grant's four
subject digests identify the evidence's request, entities, and policies.

Final admission MUST use a versioned content-identity authority that projects:

- =Cedar.Spec.Request -> requestDigest=;
- =Cedar.Spec.Entities -> entityStoreDigest=;
- =Cedar.Spec.Policies -> policySetDigest=;
- the complete request/entities/policies tuple to =bundleDigest=.

The projection is bound to the selected lifecycle evidence's authority identity
and to semantic identity/generation fields carried by the authority-validated
grant binding.

*** Digest mismatch and collision boundary

=weakAcceptedBindingAllowsCrossSubjectCedarInputs= constructs one accepted pair
whose request, entity-store, and policy identities all differ from the grant
subject.  Merely placing both values in one binding therefore proves nothing
about their content identity.

The contract deliberately does *not* claim that a finite cryptographic digest
is globally injective.  Instead, each authority proves uniqueness only over the
request/entity/policy/snapshot values admitted by its exact generation.  This is
the mathematical boundary needed for replay-safe equality without asserting an
impossible collision-free universe.

** Content-identity generation transition

*** Generation-transition requirement

The input-identity refinement proves that one admitted grant is bound to the
current authority generation.  It does not by itself constrain how two
successive generations relate.  The architecture therefore needs two distinct
transitions:

- a compatible generation advance keeps the authority identity and semantic
  identity stable, admits every previously admitted input, and preserves every
  digest projection on those old admitted inputs;
- a semantic-identity rotation advances the generation but changes the
  semantic identity, so a receipt issued for the old semantic identity cannot
  be accepted by the current refinement.

This is a v1 identity-transition invariant for the new architecture.  It is
not a compatibility-migration or deprecation policy.

*** Generation-transition observation and counterexample

Authority identity, semantic identity, and a strictly increasing generation
are insufficient on their own.  Two authorities may satisfy all three facts
while mapping the same previously admitted Cedar input to different digests.
The executable counterexample
=legacySameSemanticTransitionAllowsDigestDrift= witnesses exactly that hole.

** Authority-issued content-identity transition

*** Transition-evidence authority requirement

The generation-transition predicate establishes what a compatible advance or
semantic rotation means.  A proof of those equations is not evidence that the
real content-identity authority issued the transition, and an issuer identity
alone does not prove that the claimed generation is the authority's current
head.  Admission therefore MUST bind the transition artifact to all three
owners:

- the exact Cedar content-identity transition authority;
- an authority-issued validation context;
- the trusted current checkpoint and watermark.

The checkpoint context must also commit the exact validated transition
artifact.  Authority identity plus generation is not sufficient: two distinct
semantic rotations can share both coordinates and otherwise reuse the same
checkpoint.

The existing checkpoint contract represents authority identities as =Nat=,
while =CedarInputContentIdentityAuthority= uses =String=.  An implicit or
collision-prone conversion would create another authority-confusion hole.
Their bridge therefore requires an explicitly injective identity encoding.
Likewise, =authorizationSnapshotIdentity= and transition artifact identity
belong to different identity domains.  They MUST be related by an
authority-validated snapshot projection, not collapsed into numerical
equality.

*** Transition-evidence counterexamples

The executable model exposes two independent failures:

1. =selfReportedAcceptanceAllowsCounterfeitIssuer= constructs a transition
   claim whose issuer is =999= while the actual authority is =17=; the legacy
   structural predicate still accepts it because issuer identity is absent.
2. =issuerOnlyAcceptanceAllowsNonCurrentHead= uses the correct issuer but
   claims generation =4= while the authority has already reached generation
   =5=; issuer equality alone still accepts the stale transition.
3. =contextOnlyCheckpointAllowsSameGenerationSemanticFork= constructs two
   valid rotations from semantic identity =31= to =41= and =42=.  Both use
   authority =17= and generation =4=, so the same context-only checkpoint
   admits both even though their semantic identities and artifact identities
   differ.
4. =registryProjectionAcceptsSeparatedIdentityDomains= and
   =collapsedIdentityRejectsValidSeparatedProjection= exhibit a valid snapshot
   =900= that resolves to artifact =701=.  Registry projection accepts the
   relation, while the collapsed equality contract incorrectly rejects it.

** Published predecessor lineage

*** Predecessor-lineage requirement

Binding the transition successor to the current checkpoint is necessary but
not sufficient.  The artifact's =oldAuthority= MUST be the directly preceding
published authority context.  Otherwise a caller can invent an old authority
with an empty admitted set: admission monotonicity and projection stability
then hold vacuously even when the real predecessor's admitted content changes
digest.

The predecessor requirement spans three existing owners and therefore cannot
be inferred from any one name:

- the transition artifact owns its prior and current contexts;
- =SuccessorAdmissionClosure= owns fresh coordinator admission, distinct
  execution identities, before/after context binding, and no authority
  widening;
- =AuthorityContextLineage= owns published positions and strictly increasing
  generations;
- the already closed current-checkpoint layer proves the successor context is
  the authority-issued current head.

A total =contextAt : Nat -> ReceiptValidationContext= is a mathematical
lineage, not an assertion that every future position has already been
published.  The checkpoint publication domain therefore MUST equal the lineage
prefix ending at the current position.  Merely passing a lineage and a domain
with the same authority identity leaves them logically independent.

*** Vacuous-predecessor counterexample

=fabricatedEmptyOldMakesCompatibilityVacuous= constructs generation =2= with
the right authority and semantic identity but with =admitted = False=.  It is
formally compatible with the drifting generation =4= because both monotonicity
obligations have empty premises.  The actual published generation =3= admits
content =7=, and its digest differs from generation =4=; therefore the
fabricated old state bypasses the real compatibility obligation.

=independentLineageAllowsUnpublishedFabricatedPredecessor= exposes the second
hole: an arbitrary adjacent lineage can contain generations =2 -> 4= and share
the real current head =4= even though the actual publication domain contains
only generations =3= and =4=.  Adjacency inside an unbound lineage is not
publication evidence.

*** Registry content-transition requirement

A registry trust-root generation advance MUST NOT treat stable authority,
stable registry semantics, and an increasing generation number as evidence that
registry content was preserved.  For every descriptor registered by the
predecessor root, the successor MUST either retain that exact descriptor or
carry an acceptance-authority-validated retirement bound to the predecessor
root claim and the exact successor generation.

The registry is not append-only.  Explicit retirement is required for enterprise
revocation and compromised-domain response; the forbidden operation is silent

and a descriptor with the same domain identity but different semantics takes

position monotonicity nor stable metadata proves a disposition for the removed
descriptor.

** Successor descriptor admission and same-domain rotation

*** Successor-side admission requirement

A content-governed registry transition MUST govern both sides of the transition.
The predecessor side requires exact preservation or authority-issued retirement.
The successor side requires exact pre-existence or authority-issued admission.

Admission evidence MUST bind the descriptor to the canonical successor registry
claim and the successor generation.  When a successor descriptor reuses a
predecessor descriptor's =domainIdentity= with different authority or semantic
identity, admission alone is insufficient: every predecessor descriptor with
that domain identity MUST also carry authority-issued retirement evidence.
Thus a genuinely new domain can be admitted without inventing a predecessor,
while a same-domain semantic rotation has an explicit two-sided disposition.

*** Vacuous-predecessor injection counterexample

=retirementOnlyTransitionPermitsUnissuedSuccessorInjection= constructs an empty
predecessor registry and a singleton successor registry.  Identity and
generation transition rules hold, while every predecessor disposition
obligation is vacuous.  The retirement-only contract therefore accepts a
successor descriptor that was neither previously registered nor authority
issued.

This counterexample proves that predecessor preservation-or-retirement cannot
own successor admission.  A separate successor-indexed obligation is required.

Recovery MUST distinguish a descriptor already registered at the committed
position from a descriptor that first appears before the recovered position.

recovered position, the governed lineage MUST expose a concrete adjacent
position inside that interval carrying authority-issued descriptor admission.

do not by themselves expose this provenance.  The witness is derived from every
adjacent transition's =successorDisposition= obligation, not invented by the

position-only recovery predicate accepts the event while requiring no
descriptor-admission witness.

that position-only recovery is the weak counterexample owner and cannot support
the enterprise admission claim.

disposition do not imply recovered-head coverage.

** Authority-issued descriptor retirement

*** Retirement issuance requirement

A claim-bound retirement record MUST NOT by itself authorize descriptor
deletion.  Safe registry transitions require the exact retirement authority,
the exact claim-bound descriptor evidence, and proof that this authority issued
that descriptor/evidence pair.

The executable registry acceptance authority remains responsible for signature
and commitment validation.  The Lean contract owns the semantic result of that
validation as an =issued= predicate and an issuance proof; it does not fabricate
cryptographic evidence.

*** Claim-valid but unissued retirement counterexample

=AuthorityValidatedDescriptorRetirementEvidence= binds predecessor
registration, the canonical predecessor registry claim, and successor
generation.  Those values are all publicly constructible proof inputs.
=claimValidDescriptorRetirementPermitsUnissuedRetirement= constructs that exact
claim-valid evidence together with a retirement authority whose =issued=
predicate rejects every evidence value.

Therefore =Nonempty AuthorityValidatedDescriptorRetirementEvidence= cannot
distinguish an authorized enterprise revocation from locally assembled metadata.

** Full Cedar lifecycle registry join

*** Full-registry requirement

The local =AuthorizationLifecycleEvidence.Closed= model establishes lifecycle
semantics once its authority-path and separation-of-duty predicates are given.
It does not prove that those predicates, the evidence, or the commitment came
from the installed registry/signature lifecycle owner.

Final composition admission therefore MUST additionally consume the existing
=SourceBoundEffectCompletionRecoveryCedarAuthorizationLifecycleEvidence= and
its selected, registered Cedar evidence.  The selected evidence must be the
same evidence carried by an authority-validated binding of the exact capability
grant.

*** Carrier mismatch and unregistered-evidence counterexample

The local lifecycle model and the full registry model are intentionally not the
same type:

- the local model uses =Nat= identities and a reduced authorization response;
- the full model uses =String= identities, =Cedar.Spec.Response=, and the real
  Cedar request, entity, and policy values.

No implicit conversion between them is permitted.  A validator owns any
cross-carrier refinement and produces one exact authority-bound binding.

=localClosedAuthorityEpochJoinAcceptsUnregisteredEvidence= constructs locally
closed evidence with the expected authority and epoch, while the evidence is
not the value selected by the active registry at its claimed commitment.  This
proves that local closure is not registry authenticity.

** Cedar lifecycle join closure

*** Lifecycle join requirement

An authority-bound capability grant is not yet a lifecycle-bound grant.  Before
=use-composition= may consume it, one authority-validated lifecycle binding MUST
join the exact grant to the existing Cedar authorization lifecycle evidence.
The join binds:

- decision identity and commitment;
- accountability identity and responsibility-scope digest;
- active fence token;
- policy snapshot identity and evidence root;
- credential identity and credential generation;
- current authority identity and runtime epoch.

These fields are internal evidence coordinates.  They do not add syntax to the
public =use-composition= macro or permit profiles to mint grants.

*** Parallel-model observation and counterexample

The proof audit found three related but distinct type owners:

- =CedarDualEngineAuthorization.AuthorizationSubject=, used by the real grant
  closure;
- =CedarAuthorizationSubjectBridgeModel.AuthorizationSubject=, an independent
  numeric proof model;
- =AuthorizationLifecycleEvidence=, which owns policy epoch, fence, credential,
  authority-path, and separation-of-duty semantics.

Their theorems cannot be conjoined by structural similarity.  No prior theorem
proved that one admitted composition grant denoted the same lifecycle decision.
The counterexample =legacyJoinAcceptsLifecycleUnboundGrant= keeps authority
=17= and epoch =11= equal while replaying different decision, commitment,
fence, policy-evidence, and credential identities.

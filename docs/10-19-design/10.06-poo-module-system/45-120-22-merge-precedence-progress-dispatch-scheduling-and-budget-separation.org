#+title: Merge Precedence, Progress, Dispatch, Scheduling, and Budget Separation
#+author: POO Flow
#+language: en

* Status

Accepted.

* Context

Module composition and recursive evaluation use several ordering or selection
relations.  Calling all of them priority would incorrectly couple semantic
conflict resolution, fixed-point convergence, POO behavior selection,
operational scheduling, and resource limits.

The accepted numeric precedence convention governs contribution conflicts only.
It does not define semantic progress, prototype specificity, evaluation order,
or budget.

* Decision

The following relations are distinct:

#+begin_example
merge precedence
  != fixed-point progress order
  != POO dispatch specificity
  != evaluation scheduling
  != resource budget
#+end_example

Each relation has its own Contract, evidence, and owner.

* Responsibility table

| Relation | Question answered | Governing evidence |
|----------+-------------------+--------------------|
| Merge precedence | Which declared contribution wins an actual conflict? | Contribution identities, precedence declarations, and merge receipt |
| Progress order | Is the current generation semantically closer to the domain fixed point? | Domain ProgressContract and progress witnesses |
| Dispatch specificity | Which prototype behavior applies to the current POO object? | Prototype lineage and dispatch derivation |
| Evaluation scheduling | Which ready node is evaluated next? | Scheduler decision and causal execution evidence |
| Resource budget | How much typed work may this evaluation or recovery consume? | Budget authority, consumption, and settlement evidence |

* Merge precedence

Merge precedence applies only when multiple contributions govern the same
semantic responsibility and the merge Contract requires a winner.

It MUST NOT:

- define fixed-point progress;
- determine prototype dispatch;
- force evaluation order;
- increase resource authority;
- suppress an unresolved conflict without a merge receipt.

The accepted numeric convention remains governed by the merge-precedence
design.  This RFC neither reverses nor duplicates that convention.

* Progress order

Fixed-point progress is a domain semantic partial order supplied through a
pure POO-native =ProgressContract=.

Numeric merge precedence MUST NOT be interpreted as distance to a fixed point.

=ProgressContract= produces POO-native witness values:

- =EquivalentProgress=;
- =AdvancingProgress=;
- =IncomparableProgress=;
- =RegressingProgress=.

The base =ProgressEvidence= responsibilities are:

- previous semantic identity;
- current semantic identity;
- domain Contract identity;
- remaining obligations;
- derivation evidence.

* SCC aggregation

An SCC is classified as:

- converged when every governed node has =EquivalentProgress= and all governed
  obligations are complete;
- advancing when at least one node has =AdvancingProgress= and every other node
  is equivalent or advancing;
- stalled when every node is equivalent but governed obligations remain;
- incomparable when any required relation cannot be proven;
- regressing when any node violates its monotone progress Contract;
- oscillating when canonical non-equivalent fingerprints repeat;
- budget exhausted when no terminal classification is proven before an
  authorized structural limit.

No numeric merge precedence participates in this aggregation.

* POO dispatch specificity

Dispatch specificity follows prototype lineage and the native =gerbil-poo=
dispatch model.

It MUST NOT be converted into:

- a numeric merge precedence;
- a central tag-to-handler registry;
- scheduler rank;
- budget weight.

Dispatch evidence identifies the applicable prototype derivation.

* Evaluation scheduling

Scheduling is operational.  It chooses which ready evaluation node runs next.

For values satisfying their Contracts, a scheduling change MUST NOT change the
valid semantic result.  If it does, the evaluator emits schedule-sensitive
diagnostic evidence rather than silently assigning semantic meaning to the
schedule.

Scheduling heuristics may use cache locality, dependency readiness, or bounded
runtime information.  They MUST NOT rewrite merge precedence or progress
evidence.

* Resource budget

A budget bounds typed work.  It does not choose a contribution, prove progress,
select a prototype handler, or assign scheduler semantics.

Closure-evaluation budgets and recovery-action budgets remain distinct.
Runtime watchdog measurements remain separate from deterministic structural
budgets.

* Contract placement

=ProgressContract= belongs to the governed value-domain =ObjectType= or
Contract refinement.  It is not a fifth =ModuleType= responsibility slot.

Profiles may select a stricter progress policy.  They MUST NOT weaken the value
domain Contract or reinterpret merge precedence as progress.

The Module invariant remains:

#+begin_example
ModuleType
  = ObjectType(identity, imports, capabilities, profiles)
#+end_example

* Conformance checklist

- [X] Merge precedence governs contribution conflicts only.
- [X] Progress is a semantic partial order with POO-native witnesses.
- [X] Dispatch follows prototype lineage.
- [X] Scheduling remains operational.
- [X] Budgets bound typed work without choosing semantic winners.
- [X] SCC aggregation uses progress evidence rather than numeric precedence.
- [X] Scheduling changes cannot silently change valid semantics.
- [X] =ProgressContract= does not enlarge =ModuleType=.
- [X] Profiles may strengthen but not weaken progress policy.
- [ ] Concrete progress-evidence and scheduler source owners have been resolved
  through parser-owned owner discovery.
- [ ] Implementation has been admitted after owner resolution.

* Non-goals

- Changing the accepted numeric merge-precedence convention.
- Assigning one universal priority number to unrelated semantic relations.
- Using scheduler rank as semantic evidence.
- Treating budget exhaustion as proof of semantic impossibility.
- Replacing native =gerbil-poo= prototype dispatch.
- Defining an implementation schedule.

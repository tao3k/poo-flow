** =semantic-required=

The =poof= model or this RFC requires a general POO semantic capability, but
the pinned library implementation has not yet been located and proved.  This
state MUST NOT be described as an available API.

** =symbol-located=

Evidence identifies the exact public module owner, exported symbol, argument
and result shape, and pinned source identity.  An RFC heading, local checkout
path, private binding, or symbol name inferred from prose is insufficient.

** =behavior-proven=

A minimal executable proof consumes the exact =gerbil.pkg= dependency revision
and demonstrates the required behavior.  Proofs may cover prototype
composition, lineage order, slot and =super= resolution, recursive-object or
fixed-point behavior, and public condition, debug, or evaluation extension
points.

The proof MUST NOT substitute a different checkout or bypass package
resolution.

** =flow-qualified=

The POO Flow authoring macro lowers to the proved =clan/poo= API, and
qualification demonstrates that no local linearizer, shadow evaluator,
duplicated fixed-point implementation, private-layout dependency, or fallback
POO implementation participates.

** Flat-lineage responsibility split

For:

#+begin_src scheme
(compose profiles
  (wendao-episteme +research)
  production)
#+end_src

the POO Flow expander resolves the =profiles= role, validates cases, preserves
source order, and emits a flat contribution sequence.  =gerbil-poo= performs
the actual prototype composition, linearization, slot resolution, and =super=
semantics.

If the pinned revision already exposes the required ordered composition
operation, POO Flow uses it directly.  If a missing operation is general to
POO, it is implemented in =gerbil-poo=.  POO Flow MUST NOT introduce its own
linearizer.

* Flat prototype composition contract

Prototype composition is a pure, one-shot operation with the abstract
contract:

#+begin_example
receiver prototype
  x ordered refinement prototypes
  -> new prototype
#+end_example

The operation receives the complete ordered contribution sequence.  It MUST
NOT expose a mutable add/finalize lifecycle, repeatedly construct nested
binary composition calls, or mutate any participating prototype.

The following laws are normative:

- closure: the result is a POO prototype;
- order preservation: composition is not commutative;
- flat normalization: one boundary has one ordered lineage, not a binary
  composition tree;
- receiver identity: an empty refinement sequence leaves the receiver
  observationally equivalent;
- ordinary POO resolution: slots and =super= follow the prototype lineage
  without a macro-defined shadow merge policy;
- laziness preservation: establishing a lineage does not force lazy slots;
- source preservation: the lineage retains declaration provenance for
  conditions and observability.

An ordinary slot is not an error when several prototypes define it.  Later
refinement and =super= access use the standard POO rules.  The system MUST NOT
infer recursive deep merge merely because a slot value happens to be a POO
object.

Recursive composition is instead a capability of the prototype stored in the
slot.  A receiver that implements the prototype-composition capability may
accept an ordered refinement sequence and establish a new flat Submodule
boundary.  No public =composable-slot= DSL or second slot type system is
required.

** Mix identity and capability refinement

=identity= is scoped to a Mix root in an internal POO Mix space.  It is not
flattened as an ordinary slot shared by every Mix operand in the final Profile
root.  Different identities therefore form sibling Mix roots rather than
competing slot overrides.

Identity equality is evaluated within one enclosing Mix space.  The exact
collision condition is the conjunction of the same parent scope, the same
local identity, and distinct lineage roots.  Equal local identities beneath
different parent Mix roots do not collide.

=identity= is the semantic anchor of a Mix lineage rather than an ordinary
replaceable configuration value.  Different identities denote distinct Mix
roots.  Contributions with the same identity may refine one another only when
they share the same lineage root.  Two independent roots claiming the same
identity raise an identity-collision condition.

#+begin_export mermaid
flowchart TD
    A["Same local Mix identity"] --> B{"Same enclosing Mix space?"}
    B -->|no| C["Distinct scoped roots"]
    B -->|yes| D{"Shared lineage root?"}
    D -->|yes| E["Continue as ordered refinement"]
    D -->|no| F["Raise identity-collision condition"]
#+end_export

The implementation MUST NOT decide this by deep equality: lazy slots, cyclic
objects, and fixed points make deep comparison both unsound and potentially
nonterminating.  A refinement inherits its root identity; changing identity
creates a new Mix root rather than refining the old root.

A capability is itself a POO prototype object.  Its identity establishes its
composition boundary, and contributions to that capability form an ordered
refinement lineage.  Capability removal or narrowing requires an explicit POO
refinement and MUST NOT be encoded as an absent key or a =#f= overwrite.

Static violations are reported at the declaration site.  Violations that
depend on lazy runtime values raise structured, continuable POO conditions.

[[https://github.com/metareflection/poof][metareflection/poof]], “Prototypes: Object Orientation, Functionally”.
It owns the POO concept lineage and the prototype-oriented functional model
against which general semantic extensions are reasoned.

The Gerbil Scheme implementation is =gerbil-poo=.  The root =gerbil.pkg=

* Sole Scheme POO library invariant

=gerbil-poo= is the core Scheme implementation of POO and the only POO
library.  Its normative source identity is the repository and revision declared
by =gerbil.pkg=.  API alignment, implementation evidence, and proposals for
general POO extensions MUST be grounded in that pinned source identity rather
than a machine-local checkout path.  POO Flow MUST NOT define, embed, emulate,
or fall back to another POO object model.

#+begin_export mermaid
flowchart LR
    A["gerbil-poo"] --> B["Prototype, slot, super, and recursive-object semantics"]
    A --> C["POO Flow higher-order roles and policy objects"]
    C --> D["Profile, Mix, Capability, and Submodule composition"]
    D --> E["wendao-episteme"]
#+end_export

The following consequences are normative:

- all public POO Flow extension and module objects are =gerbil-poo= objects;
- all generated composition code calls public =gerbil-poo= operations;
- realization contexts, demand cells, conditions, policies, decisions, and
  receipts are expressed as =gerbil-poo= objects rather than a local object
  runtime;
- POO Flow does not own a prototype engine, fixed-point engine, alternate slot
  resolver, compatibility facade, or shadow evaluator;
- there is no local =poo-fixed-point= package or fallback implementation;
- a generally useful POO primitive or evaluation extension is implemented in
  =gerbil-poo= itself, then consumed through the pinned library dependency;
- POO Flow owns only its domain roles, staged authoring macros, governance
  policies, runtime handoff boundaries, and qualification evidence.

The realization and recovery model in this RFC suite describes how POO Flow
uses and instruments the public =gerbil-poo= lifecycle.  It does not authorize
replacement of that lifecycle.  If the library lacks a required general
extension point, the extension belongs in =gerbil-poo= rather than a parallel
implementation in POO Flow.

* Per-boundary composition invocation

POO Flow may build a bounded compile-time projection of Profile, Mix,
Capability, and Submodule contributions, but each structural boundary is
implemented by one public =gerbil-poo= composition operation.  No POO Flow
layer may fold slots, perform linearization, or emulate =super= across
boundaries.

The exact composition symbol remains =semantic-required= until it is
=symbol-located= and =behavior-proven= at the pinned dependency revision.
Independent boundary invocations do not create inheritance or evaluation
precedence between sibling roots.

* Existing object layer

The pinned =object.ss= layer already owns:

- delayed object instantiation;
- lazy cached =.ref=;
- =.ref/cached= for an existing cached slot;
- =force-object= for explicit full forcing;
- constant, thunk, self, and computed slot specifications;
- self/super computation;
- object instance caching;
- precedence-list construction and circular precedence-graph rejection.

These facts constrain POO Flow; they do not enlarge the 45-02 G0 binding list.
POO Flow MUST NOT copy this cache, mutate private object instance state, or
reimplement precedence calculation.

Circular inheritance precedence and circular lazy slot demand are different.
The pinned implementation detects the former.  Its own TODO identifies generic
circular slot-definition detection through a suitable =hash-ensure-ref= variant
as future work.  POO Flow therefore cannot claim that arbitrary nested =.ref=
cycles are already diagnosed.

* Existing debug layer

The pinned =debug.ss= provides =trace-inherited-slot= and =trace-poo=.  Their
scope is opt-in tracing of inherited procedure-valued methods by wrapping
slots.

They are:

- useful development utilities;
- not a callback around every =.ref= cache miss;
- not required by G0;
- not runtime cycle authority;
- not an observability sink or receipt source;
- not provided by GSLPH.

* Instrumentation limit

The pinned API does not expose a general callback around every nested =.ref=
cache miss.  Its tracing utilities wrap inherited procedure-valued slots, not
all slot demand.

Therefore POO Flow guarantees cycle diagnosis only at its own
module-capability boundary:

#+begin_src text

  runtimeContext
  evaluationLineage
  moduleIdentity
  capabilityIdentity
  computation
    -> capabilityValue
#+end_src

#+begin_src text
resolve-module-capability
  runtimeContext
  evaluationLineage
  moduleIdentity
  capabilityIdentity
  computation
    -> capabilityValue
#+end_src

This is a POO Flow internal combinator.  It is not a =gerbil-poo= adapter
contract and does not alter the dependency API.

Its responsibilities are limited to:

1. derive the next 45-05 evaluation-lineage frame;
2. perform the context-local wait-graph check;
3. record bounded 45-04 diagnostics;
4. invoke the existing capability-producing POO computation;
5. publish or propagate the result through the 45-03 runtime cell.

It does not inspect arbitrary slot computations or own POO object
instantiation.

* Forbidden work

- No replacement of =.ref= or =hash-ensure-ref=.
- No access to private object instance cache.
- No copied fixed-point or memoization engine.
- No required =gerbil-poo= fork or source patch.
- No adapter contract.
- No claim to detect arbitrary user slot recursion.

* Dependency and build boundaries

=gerbil.pkg=/=gxpkg= may install the dependency.  They do not project its API,
select runtime bindings, or attest the reviewed pin.

Gerbil-Bazel may fetch/build the pinned dependency and POO Flow.  It does not
define =MixModuleObject= semantics, provide a semantic adapter, or become an
input to G0 Decision.

GSLPH may execute focused API-shape and no-patch qualification.  It does not
provide =gerbil-poo=, wrap its functions, select the pin, or issue runtime
capabilities.

#+title: Recursive Capability Delegation and Budget Closure
#+startup: overview

* Status

The architecture in this RFC is accepted.

This acceptance freezes recursive authority and budget semantics.  It
does not admit implementation files, exported constructor names,
runtime persistence, or a new public macro surface.

* Scope

This RFC defines capability delegation through recursive Module and
import graphs, including parent-to-child, business-to-business, and
business-to-customer compositions.

It covers:

- the difference between evidence reachability and authority;
- explicit scoped delegation;
- non-widening authority proofs;
- multi-level delegation lineage;
- conserved recovery budgets;
- cyclic import and delegation behavior;
- target-bound coordinator execution.

* Central decision

An import makes Module evidence reachable.  It does not implicitly
delegate recovery authority.

Capability authority does not propagate through an import edge unless
an explicit native POO delegation value authorizes that exact edge and
scope.

Every delegation is a refinement of already admitted parent authority.
It may preserve or narrow authority.  It may never widen authority.

Every delegated budget is allocated from current parent budget
evidence.  The same budget evidence cannot be spent, copied, or
reintroduced through another branch or cycle.

* Evidence reachability is not authority

The Module =imports= responsibility provides declared recursive
reachability for identity, Contract, profile, capability, and evaluation
evidence.  Reachability permits semantic inspection and dependency
closure.  It does not grant permission to:

- retry an imported Module;
- substitute an imported responsibility or result;
- resume an imported recovery point;
- abort an imported evaluation;
- consume an imported recovery budget;
- invoke an imported continuation handle.

An imported Module may expose capability evidence without delegating
that capability to its importer.  Authority requires a separate,
explicit delegation proof.

* Delegation responsibility

A delegation is a native POO value with semantic evidence for:

- the delegating Module identity;
- the parent capability or parent delegation identity;
- the delegated target Module identity;
- the target responsibility scope;
- the admitted recovery action kinds;
- the eligible generation or generation range;
- the allocated budget dimensions;
- expiration, revocation, and continuation bounds;
- the non-widening relation to parent authority;
- the parent evidence required to reconstruct the delegation chain.

These responsibilities do not automatically freeze a public
=Delegation= constructor, record, macro, or DSL.

A target Module cannot infer delegation from naming, import position,
profile priority, merge order, deployment topology, or coordinator
availability.

* Non-widening authority closure

Effective authority at a target is the repeated refinement of explicit
root capability evidence through every delegation edge.

For each edge, the child authority MUST be no broader than the parent
authority in all relevant dimensions:

- action kinds;
- target Module and responsibility scope;
- eligible generations;
- retry and total recovery budgets;
- substitution scope;
- continuation invocation bounds;
- expiration and revocation conditions;
- required Contract and provenance evidence.

Adding a delegation may make an already admitted subset reachable at a
new target.  It does not create a new kind or quantity of authority.

* Budget allocation and conservation

Budget dimensions are typed semantic evidence.  A retry count,
continuation invocation bound, substitution scope, and total recovery
limit are not interchangeable numeric values.

Allocating a child budget produces new immutable budget evidence:

- the previous parent budget remains historical evidence;
- the successor parent budget identifies its retained balance;
- the child allocation identifies its delegated share;
- both identify the allocation action and parent budget generation.

For every budget dimension, the retained parent amount plus all live
child allocations MUST NOT exceed the admitted parent amount.

A raw copy of a budget object is not a new allocation.  A child budget
is usable only when its allocation lineage and current-generation
receipt are valid.

Concurrent materialization requires an effectful coordinator receipt so
that two branches cannot consume the same current budget generation.
The mutable runtime mechanism used to serialize materialization remains
behind the coordinator boundary; semantic budget evidence remains
immutable.

* Recursive and cyclic graphs

Import cycles may participate in the Module evidence fixed point.  They
do not create an authority root.

Delegated authority closure starts only from explicit admitted root
capabilities and follows explicit non-widening delegation edges.
Therefore:

- a delegation cycle with no reachable root capability has no effective
  authority;
- returning to an already visited delegation identity cannot increase
  authority or restore spent budget;
- each traversal preserves the complete parent delegation lineage;
- cycle detection produces semantic observation evidence rather than an
  unbounded evaluator recursion;
- a budget allocation cannot re-enter its own ancestry as a new live
  allocation.

The closure evaluator MUST memoize or otherwise identify visited
delegation and budget generations.  Detection, explanation, and
recovery remain governed by the fixed-point observability RFCs; this
document only freezes the authority result.

* Profile and policy boundary

Profiles may select different recovery behavior for a delegated target,
but only within the effective delegated capability.

A profile cannot:

- manufacture a delegation edge;
- broaden a target or responsibility scope;
- restore exhausted or revoked budget;
- make an authority cycle productive;
- bypass parent delegation lineage;
- authorize a different generation.

Profile priority affects policy preference.  It never affects the
non-widening authority proof.

* Target-bound coordinator execution

The coordinator validates the complete delegation and budget lineage
against the current target generation before execution.

It MUST reject:

- a decision for another Module or responsibility;
- a stale or ineligible target generation;
- an incomplete, cyclically amplified, expired, or revoked delegation;
- an exhausted, duplicated, or mismatched budget allocation;
- an action outside the delegated capability;
- a continuation handle outside the delegated invocation bound.

Successful execution emits:

- the exact admitted target and action;
- the complete authorization and delegation evidence identity;
- the consumed budget generation;
- the successor target generation;
- a redacted coordinator receipt for observation and telemetry.

* Public and advanced extension boundary

Ordinary users continue to select Module profiles through
=use-composition=, =compose profiles=, and =use-module=.  Recursive
delegation does not add a user-facing clause language.

Advanced delegation is represented by native =gerbil-poo= objects,
prototypes, slots, composition, and dispatch in the =capabilities=
responsibility.  A macro may be considered only by a later RFC that
proves necessary hygienic syntax or phase semantics over this native
POO representation.

* Implementation admission checklist

- [ ] Keep import reachability separate from capability authority.
- [ ] Require an explicit delegation value for every authority edge.
- [ ] Bind every delegation to delegator, target Module,
  responsibility, actions, generation eligibility, and budget.
- [ ] Prove every delegation is no wider than its parent authority.
- [ ] Preserve the complete multi-level delegation lineage.
- [ ] Allocate child budgets from current parent budget evidence.
- [ ] Prevent copied, stale, duplicated, exhausted, or cyclically
  reintroduced budget evidence from being consumed.
- [ ] Keep semantic budget evidence immutable.
- [ ] Keep concurrent spend materialization behind the coordinator
  effect boundary.
- [ ] Derive cyclic authority only from explicit reachable root
  capabilities.
- [ ] Ensure an unrooted delegation cycle has no effective authority.
- [ ] Prevent profiles and profile priority from widening delegation.
- [ ] Bind coordinator execution to the exact target generation.
- [ ] Emit actionable denial and successor evidence.
- [ ] Keep Module at exactly four responsibility slots.
- [ ] Add no public delegation DSL, raw record language, or effect hook.
- [ ] Apply incremental closure evaluation, semantic cache, and SCC
  convergence rules in
  [[file:45-120-07-semantic-cache-scc-evidence-generation-invalidation-and-fail-closed-convergence.org][45-120-07]].

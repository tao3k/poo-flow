#+title: use-composition Current Gap and Thin Macro Contract
#+startup: overview

* Status

Accepted target architecture.

This RFC records the current ~use-composition~ implementation evidence and
freezes the direct replacement contract for ~user-composition~.

The architecture is new.  The current clause grammar receives no compatibility
surface, migration period, or deprecation protocol.

* Scope

This document owns:

- the exact public shape of the target ~use-composition~ macro;
- its binding, identity, hygiene, phase, and root-instantiation obligations;
- the boundary between the macro and value-level Profile composition;
- the boundary between semantic POO ~imports~ and physical Gerbil module
  loading;
- the disposition of the current clause parser on the new public path;
- the syntax-error boundary; and
- the conformance criteria for User Interface cases.

It does not own:

- Profile object or prototype semantics;
- the implementation of ~compose~;
- the implementation of the ~profiles~ strategy object;
- a Profile-definition macro;
- control-policy resolution;
- runtime continuation behavior;
- Gerbil package installation; or
- a compatibility layer for the old grammar.

* Current implementation evidence

** Public macro owner

The current public macro is implemented in
[[file:../../../src/module-system/profile-composition-use-syntax.ss][profile-composition-use-syntax.ss]].

Its current syntax pattern is:

#+begin_src scheme
(_ composition-name module-form form ...)
#+end_src

The current implementation pattern ~(_ composition-name module-form form ...)~
is evidence of the current gap; it is not an accepted target pattern.

The current source owner is
[[file:../../../src/module-system/profile-composition-use-syntax.ss][profile-composition-use-syntax.ss]].

The macro passes the module form and remaining forms to a compile-time syntax
plan parser, lowers imported/local profiles, stages, and clauses, then returns
a composition object expression.

It does not create the lexical binding named by ~composition-name~.

** Current parser grammar

[[file:../../../src/module-system/profile-composition-syntax-plan.ss][profile-composition-syntax-plan.ss]]
currently requires:

- one canonical ~(use-module module-name as alias ...)~ form;
- profile or profiles declarations inside that form;
- one or more compose or stage forms after it;
- profile references tied to the declared alias; and
- a closed set of stage clauses.

The parser constructs mutable-implementation-specific syntax-plan classes for
profiles, references, stages, and clauses.

** Current clause macros

[[file:../../../src/module-system/profile-composition-clause-syntax.ss][profile-composition-clause-syntax.ss]]
currently exports ~profile~, ~profiles~, and ~compose~ as syntax transformers.

The current ~compose~ transformer constructs a composition clause.  It is not
the accepted pure ~compose~ function.

The current ~profiles~ transformer constructs a list of profile references.  It
is not the accepted first-class POO composition-strategy object.

** Current inline lowering

[[file:../../../src/module-system/profile-composition-inline-runtime.ss][profile-composition-inline-runtime.ss]]
currently lowers local profile sections through alists, ~object<-alist~,
special section names, hooks, and host conditional dispatch.

That lowering is outside the accepted POO-native public contract.

* Central decision

The target public form has exactly two operands after the macro name:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    (use-module wendao-episteme
      production-governance)
    (use-module runtime
      distributed-runtime
      sandboxed)
    (use-module observability
      full-receipts)))
#+end_src

The syntax contract is:

#+begin_src scheme
(_ composition-name composition-expression)
#+end_src

#+begin_src typst
$ "current-use-composition-shape" =
  ("name", "module-form", "clause"_1, dots, "clause"_n) $

$ "target-user-composition-shape" = ("name", "expression") $
$ "target-binding-count" = 1 $
$ "target-root-instantiation-count" = 1 $
$ "outer-def-required" = false $
#+end_src

~user-composition~ is a thin hygienic module-level binding macro.

It:

1. validates that ~composition-name~ is an identifier;
2. preserves ~composition-expression~ as one ordinary Scheme expression;
3. binds ~composition-name~ exactly once;
4. projects the declared name into the POO composition identity;
5. evaluates the ordinary composition expression at the value phase; and
6. performs exactly one explicit composition-root instantiation.

The user does not write an enclosing ~def~.

* Direct replacement

The old and new public forms are intentionally not accepted at the same time.

The target macro rejects:

- a dedicated ~use-module~ module-form followed by separate compose or stage
  clauses;
- more than one composition expression;
- ~profile~ or ~profiles~ declaration clauses;
- ~compose~ clauses;
- ~stage~ clauses;
- keyword profile sections;
- inline hooks;
- an enclosing duplicate ~def~ pattern presented as canonical usage; and
- any attempt to select the old parser through a mode or compatibility flag.

There is:

- no legacy parser fallback;
- no syntax-version token;
- no warning-only period;
- no deprecation annotation;
- no automatic source rewrite; and
- no runtime compatibility adapter.

This is a replacement boundary for a new architecture, not a migration
protocol.

* Target ownership

| Surface | Target owner | Required character |
|---------+--------------+--------------------|
| ~user-composition~ | thin hygienic macro | one identifier and one expression |
| ~compose~ | ordinary pure function | consumes one strategy and Profile values |
| ~profiles~ | first-class POO strategy object | owns Profile composition semantics |
| Profile operands | immutable POO values or admitted higher-order Profile values | no clause wrappers |
| ~imports~ | first-class POO recursive module graph | carried by higher-order Profile/Module values |
| physical module loading | phase-owned backend projection | derived from an admitted ~imports~ closure |
| stages and handoffs | Profile/POO objects | value-level composition |
| root instantiation | composition-root boundary | exactly once |

The macro does not recognize ~compose~ or ~profiles~ as grammar literals.
They resolve lexically like ordinary Gerbil identifiers.

The macro likewise does not recognize or lower ~use-module~.  A
~use-module~ expression is an independent hygienic value projection owned by
[[file:45-93-module-profile-selection-bundle-and-imports-closure-algebra.org][45-93]].
It produces a ProfileBundle before ordinary Profile composition.

* Target expansion boundary

The observable target expansion is equivalent to:

1. define the requested module-level identifier;
2. evaluate the supplied expression without rewriting its internal syntax;
3. attach the declared composition identity through an ordinary POO-native
   identity projection; and
4. instantiate the resulting composition root exactly once.

This equivalence does not name an unverified helper procedure.  The exact
helper call must be selected from the verified Profile and ~gerbil-poo~
implementation boundary.

The macro must not:

- parse the body of ~(compose profiles ...)~;
- enumerate operands;
- expand Profile-specific clauses;
- resolve module aliases;
- construct alists;
- call ~object<-alist~;
- manufacture hooks;
- inspect control policies;
- issue capabilities;
- install runtime handlers; or
- evaluate Profiles at macro-expansion time.

#+begin_src typst
$ "expand"("user-composition"("name", e)) =
  "hygienic-bind"("name", "identity-project"("name", e)) $

$ "parse-expression-body"(e) = false $
$ "enumerate-operands"(e) = false $
$ "issue-capability"(e) = false $
$ "install-runtime-handler"(e) = false $
$ "legacy-parser-fallback" = false $
#+end_src

* Composition identity

~composition-name~ has two related but distinct roles:

- it is the lexical module-level binding introduced by the macro; and
- it is the declared stable identity projected into the composition root.

The identity projection is explicit in macro expansion and inspectable after
expansion.

It is not derived from:

- a runtime registry;
- module source position;
- object allocation identity;
- operand ordering;
- an implicit string conversion at runtime; or
- package discovery.

Import renaming of the lexical binding does not silently rewrite the declared
composition identity.

* Hygiene

The macro preserves:

- lexical references inside ~composition-expression~;
- source locations for errors in the expression;
- the binding identity of imported ~compose~ and ~profiles~ values;
- local higher-order Profile bindings;
- phase separation; and
- the declared composition identifier.

The macro introduces private temporary bindings hygienically.

It must not use ~syntax->datum~ on the composition expression or dispatch on
the textual names of identifiers inside it.

* Phase ownership

| Phase | Allowed responsibility | Prohibited responsibility |
|-------+------------------------+----------------------------|
| expansion | arity, identifier, hygienic binding, identity projection | Profile evaluation or clause parsing |
| module value initialization | evaluate the ordinary composition expression | package discovery |
| root boundary | one POO-native instantiation | a second prototype evaluator |
| runtime | evaluate admitted Profile and control semantics | macro re-entry |

The composition expression may contain ordinary Scheme abstraction created
outside the macro.  The macro does not become aware of that abstraction.

* Imports

The public architecture uses ~imports~, not one user-authored Gerbil ~import~
surface.

~imports~ is a first-class immutable POO object carried by every higher-order
Profile or Module.  It owns:

- direct module dependencies;
- recursive submodule dependencies;
- stable dependency identity;
- capability requirements on dependency edges;
- cycle and fixed-point evidence;
- revision and generation constraints; and
- the phase projection required to materialize physical module boundaries.

One dependency may contribute submodules whose own ~imports~ objects contribute
further dependencies.  The composition root therefore evaluates an imports
graph, not a flat source list.

The ~imports~ closure:

- deduplicates nodes by stable identity;
- intersects capability requirements;
- preserves cycles for POO Flow fixed-point evaluation;
- emits cycle, budget, and projection receipts;
- supports incremental and cached reevaluation under the owning RFCs; and
- projects the minimal required Gerbil import or load boundaries only after
  semantic admission.

Gerbil ~import~ remains a backend mechanism.  It is not the public module-system
object and is not enumerated by ordinary users.

The target form has no ~use-module~ clause, alias declaration, inline imported
profile declaration, user-authored recursive import list, or macro-owned
dependency resolver.

This prohibition applies to the old dedicated module-form position in
~use-composition~.  The target ~user-composition~ does not prohibit an
independent ~use-module~
expression inside the single composition expression.

The old dedicated use-module module-form is rejected.

An independent use-module expression inside the single composition expression
is admitted.

~user-composition~ remains thin.  It does not inspect its composition expression
to discover dependencies.  It consumes higher-order Profile values whose
~imports~, identity, and capability projections are already owned by the
module-system phase boundary.

Package ownership remains with ~gerbil.pkg~.  ~user-composition~ neither installs
nor projects Gerbil package dependencies.

* Profile, stage, and policy values

Profile selection, stage structure, handoff behavior, observability, and
control policies are expressed through Profile and POO values before they enter
~user-composition~.

The macro does not provide special syntax for:

- local Profile definitions;
- Profile extension;
- stage declarations;
- graph clauses;
- loop clauses;
- proof clauses;
- handoff clauses;
- policy clauses;
- priority; or
- capability requirements.

Advanced extension remains the native POO object and prototype interface.

* Error contract

The macro owns only structural errors for:

- invalid arity;
- a non-identifier composition name; and
- failure of the explicit identity/root projection boundary.

Errors originating inside ~composition-expression~ retain their original
source location and semantic owner.

The macro must not replace a Profile, POO, import, capability, or root failure
with a generic clause-parser error.

Old clause forms fail as invalid target macro arity or expression structure.
They do not trigger legacy parsing.

#+title: POO-Native Type and Contract Prototype Foundation
#+language: en

* Status

This RFC freezes an accepted semantic foundation.  It defines Type and Contract
as native =gerbil-poo= prototypes or prototype-derived values owned by
=poo-flow-core=.  It does not admit an implementation, a compatibility layer, a
public type-declaration macro, or a registry.

* Scope

This RFC owns:

- the relationship between the project object foundation and type construction;
- the minimal Type and Contract prototype responsibilities;
- contract refinement through native prototype composition;
- inspectable classification and validation evidence;
- the ObjectType specialization required before Module construction; and
- the ownership and effect boundaries of =types.ss=.

It does not own:

- the four-slot Module value itself;
- dispatch evaluation or recursive fixed-point evaluation;
- runtime authorization, materialization, handles, or adapters;
- a package, build, or development-harness contract; or
- downstream domain types owned by =wendao-episteme=.

* Central decision

Type and Contract are POO semantic objects.  They are not static tags, records,
alists, predicate registries, schemas, or wrappers around another object model.

The project foundation is ordered as follows:

#+begin_src mermaid
flowchart LR
  U["upstream gerbil-poo"] -->|"provides object, prototype, slot, dispatch, and C3 mechanics"| O["poo-flow-core objects.ss"]
  O -->|"provides native project object construction"| T["poo-flow-core types.ss"]
  T -->|"specializes Type with responsibility contracts"| OT["ObjectType"]
  OT -->|"requires identity, imports, capabilities, and profiles"| M["Module"]
  M -->|"supplies an admitted semantic receiver"| D["DispatchEvaluation"]
#+end_src

The exact project owner =src/module-system/types.ss= is currently missing.
This RFC admits the semantic contract for that owner, not its implementation.

* Type prototype

A Type prototype has exactly two required responsibilities:

| Responsibility | Meaning |
|----------------+---------|
| =identity= | Stable semantic identity of the type. |
| =classify= | Pure classification of a candidate value into inspectable evidence. |

=classify= must return immutable semantic evidence.  It must not return only an
unexplained Boolean.  The following responsibilities are derived views:

- =accepts?= is the Boolean projection of classification evidence;
- =diagnostics= projects structured rejection or refinement facts; and
- =explanation= projects a redaction-safe account of the decision.

Prototype composition, extension, and precedence remain upstream
=gerbil-poo= operations.  Type does not add a second inheritance algorithm.

* Contract prototype

A Contract is a refinement and composition of Type.  It is not a wrapper around
a Type value and not a parallel lookup registry.

Contract inherits =identity= and =classify= and adds one required
responsibility:

| Responsibility | Meaning |
|----------------+---------|
| =obligations= | First-class, pure semantic obligations applied after classification. |

The following responsibilities are derived:

- =validate= combines classification evidence with obligation evidence;
- =accepts?= remains the Boolean projection of the combined evidence;
- =diagnostics= explains failed classification or obligations; and
- =explanation= records which prototype and obligation supplied each decision.

Contract obligations may depend on an explicit semantic context.  They must not
read ambient process state, resolve secrets, acquire handles, perform I/O, or
invoke runtime adapters.

* ObjectType specialization

ObjectType is a Type refinement for native POO values.  It adds a required
=responsibilities= value that associates responsibility identities with Contract
prototypes.

=responsibilities= is itself a POO value or prototype-derived value.  It is not
an alist field schema or a record descriptor.

ObjectType derives:

- responsibility presence evidence;
- responsibility contract evidence;
- prototype and C3 provenance;
- missing-responsibility diagnostics; and
- an explanation of the selected contract implementation.

ObjectType never duplicates upstream object identity, prototype ancestry,
dispatch, or C3 linearization.

* ModuleType specialization

ModuleType is the first domain specialization of ObjectType in this RFC chain.
It requires Contract prototypes for exactly these responsibilities:

- =identity=;
- =imports=;
- =capabilities=; and
- =profiles=.

ModuleType does not construct a second object representation.  A conforming
Module is an ordinary native POO value classified and validated through the
shared Type and Contract foundation.

* Evidence flow

#+begin_src mermaid
flowchart LR
  V["candidate POO value"] -->|"is classified without effects"| C["Type classify responsibility"]
  C -->|"emits immutable classification evidence"| E["classification evidence"]
  E -->|"satisfies the base type before refinement"| O["Contract obligations"]
  O -->|"emits obligation evidence and provenance"| R["validation outcome"]
  R -->|"projects a compact Boolean view"| B["accepts?"]
  R -->|"projects structured failure facts"| G["diagnostics"]
  R -->|"projects selected prototypes and obligations"| X["explanation"]
#+end_src

Boolean acceptance, diagnostics, and explanation are projections of one
evidence-bearing decision.  They must not be recomputed by unrelated validators.

* Functional and macro boundary

Type and Contract responsibilities are implemented with named pure functions and
native POO objects.  Raw =(lambda (self super) ...)= hooks are not the ordinary
project interface.

A bounded internal Gerbil macro may declare repeated Type or Contract object
families only when it:

- expands to ordinary native POO construction and named pure functions;
- adds no parallel runtime or registry;
- preserves inspectable identities and provenance; and
- is separately admitted under the project macro-governance rules.

This RFC adds no public macro.

* Existing implementation evidence

The repository already contains:

- =src/module-system/objects.ss=;
- =src/module-system/object-core.ss=; and
- =src/module-system/object-core-support/contracts.ss=.

Those owners prove that project object and contract concerns already exist below
Module.  They do not prove the Type and Contract prototype algebra defined here.
Existing alist predicates, merge helpers, or diagnostics are implementation
evidence only.  This new architecture makes no compatibility or migration
commitment to those representations.

* Ownership

- Upstream =gerbil-poo= owns object, prototype, slot, dispatch, and C3 mechanics.
- =poo-flow-core= owns Type, Contract, ObjectType, and ModuleType semantic
  contracts.
- =wendao-episteme= owns downstream domain Type, Contract, and Module
  specializations.
- Runtime adapters own effects and runtime handles.
- GSLPH, Gerbil-Bazel, Nix, and =gerbil.pkg= own no public Type or Contract
  semantics in this RFC.

* Admission checklist

** Semantic contract

- [X] Type and Contract are native POO prototypes or prototype-derived values.
- [X] Type requires only =identity= and =classify=.
- [X] Contract refines Type and adds =obligations=.
- [X] Acceptance, diagnostics, and explanation derive from inspectable evidence.
- [X] ObjectType describes POO responsibilities rather than record fields.
- [X] ModuleType requires exactly four Module responsibilities.
- [X] Runtime effects and handles remain outside the type foundation.
- [X] No compatibility, registry, schema, or public macro surface is admitted.

** Implementation admission

- [ ] Admit the exact =src/module-system/types.ss= owner.
- [ ] Admit Type and Contract prototype constructors.
- [ ] Admit evidence-bearing classification and validation.
- [ ] Admit ObjectType responsibility-contract validation.
- [ ] Admit ModuleType only after the shared foundation passes its own tests.

* Rejected alternatives

- A static type-tag enumeration.
- A global mutable type or contract registry.
- Raw alist or record schemas as the ordinary type surface.
- Boolean-only predicates with no evidence or explanation.
- A Contract wrapper that contains a separate Type object model.
- Module-specific validators that bypass the shared foundation.
- Reimplementation of upstream prototype composition or C3 precedence.
- Runtime authorization or handle checks inside semantic contracts.

* Successor contract

The accepted module-local functional kernel that supplies named pure functions
to Type, Contract, and object responsibilities is defined separately in
=45-120-02=.  Keeping that contract separate from this prototype algebra
prevents either RFC from becoming a combined architecture and style document.

* Accepted upstream ownership correction

The generic POO type foundation belongs to the pinned =gerbil-poo=
dependency.  In particular, primitive validation and typed value-pair
machinery remain upstream responsibilities of =gerbil-poo/type.ss=.
POO Flow MUST NOT implement a parallel generic type system.

=Type=, =Contract=, =ObjectType=, and =ModuleType= are frozen here as
semantic relations and higher-order POO design values.  Their names do
not automatically become exported constructors, macros, registries, or
new generic type APIs.  A concrete exported name requires separate
source-owner evidence and RFC admission.

A project or Module-local =types.ss= MAY specialize the upstream
foundation for domain responsibilities, classifications, contextual
obligations, and Module admission.  It MUST compose native
=gerbil-poo= prototypes or prototype-derived values.  It MUST NOT
duplicate upstream validation, prototype composition, object
construction, or value-pair mechanics.

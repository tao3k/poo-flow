#+title: Source-bound effect completion crash-recovery closure
#+startup: overview

* Status

This RFC closes the next v1 proof boundary after
[[file:45-120-28-source-bound-effect-completion-publication-closure.org][45-120-28]].

It addresses the crash interval in which an effect provider has already
executed an effect and acknowledged its completion, while the atomic completion
publication has not yet become visible to the recovering engine.

This remains a v1 stabilization:

- no v2 schema is introduced;
- no second replay ledger or completion-ledger owner is introduced;
- the existing completion publication and commit receipt remain the only
  storage-commit authority;
- the core Lean model remains pure Lean data and propositions;
- JSON is permitted only as an audit or Python/AXLE transport projection through
  the existing FFI boundary.

* Context

The v1 completion publication proof distinguishes provider acknowledgement from
the later atomic ledger/frontier commit.  That separation is necessary, but it
creates an unavoidable crash interval:

1. the replay ledger still contains a pending entry;
2. the provider may already have performed the physical effect;
3. the process crashes before the atomic publication is committed or observed;
4. recovery sees the same engine-owned ledger state as it would have seen if
   the effect had never executed.

The engine projection therefore cannot distinguish two physical worlds.

#+begin_src typst
#let W_0 = ("ledger", "entry", "not-executed")
#let W_1 = ("ledger", "entry", "executed-uncommitted")

$ pi_"engine"(W_0) = pi_"engine"(W_1) = ("ledger", "entry") $
#+end_src

A ledger-only recovery function must make the same decision in both worlds.
Executing is unsafe in the second world; suppressing is unsafe in the first.

#+begin_src typst
#let safe(state, decision) = {
  if state == "not-executed" and decision == "execute" { true }
  else if state == "executed" and decision == "suppress" { true }
  else { false }
}

$ forall d in {"execute", "suppress"},
  not (op("Safe")("not-executed", d)
    and op("Safe")("executed-uncommitted", d)) $
#+end_src

This is not an implementation accident.  It is an information boundary.  A
correct recovery design needs independent provider-owned observation evidence.

* Decision

Keep the existing v1 owners and introduce only a proof-level recovery
classification over their evidence.

The recovery classification has four states:

| State | Required evidence | Only permitted disposition |
|-
| =not-executed= | pending ledger entry, no commit receipt, authoritative provider negative observation | =execute= |
| =executed-uncommitted= | pending ledger entry, no commit receipt, authoritative provider acknowledgement, closed completion receipt | =resume-publication= |
| =committed= | existing closed completion publication and commit receipt | =suppress-committed= |
| =indeterminate= | provider conflict/unknown, or a completed ledger flag without closed commit evidence | =fail-closed= |

The provider observation is bound to:

- recovery identity;
- provider identity;
- exact replay step and idempotency key;
- runtime epoch;
- active fence token;
- provider-state digest;
- idempotency-contract digest;
- evidence and provenance digests.

An acknowledgement also carries the existing
=SourceBoundEffectCompletionReceipt=.  Its closure remains owned by
=SourceBoundEffectCompletionReceiptClosed=.

#+begin_src typst
#let authoritative(status, physical) = {
  if status == "definitely-not-executed" {
    physical == "not-executed"
  } else if status == "acknowledged" {
    physical == "executed"
  } else {
    true
  }
}

$ op("Authoritative")(o, s) =
  cases(
    s = "not-executed" & "if" o = "definitely-not-executed",
    s = "executed" & "if" o = "acknowledged",
    "true" & "if" o in {"indeterminate", "conflict"},
  ) $
#+end_src

An absent provider receipt is not automatically a negative observation.
=definitely-not-executed= is accepted only under the independent provider
observation-authority predicate.  Eventual absence, timeout, transport failure,
or an unreadable provider state is =indeterminate= and must fail closed.

* Recovery state function

The proof-level state function is:

#+begin_src typst
$ op("Recover")(e, o, c) =
  cases(
    "committed" & "if" op("ClosedCommit")(c),
    "executed-uncommitted" &
      "if" not e."completed"
      and o."status" = "acknowledged"
      and op("ClosedReceipt")(o."receipt"),
    "not-executed" &
      "if" not e."completed"
      and o."status" = "definitely-not-executed"
      and op("AuthoritativeNegative")(o),
    "indeterminate" & "otherwise",
  ) $
#+end_src

The action projection is total and fail closed:

#+begin_src typst
$ op("Action")(s) =
  cases(
    "execute" & "if" s = "not-executed",
    "resume-publication" & "if" s = "executed-uncommitted",
    "suppress-committed" & "if" s = "committed",
    "fail-closed" & "if" s = "indeterminate",
  ) $
#+end_src

The two essential safety consequences are:

#+begin_src typst
$ s = "executed-uncommitted"
  => op("Action")(s) != "execute" $

$ s = "committed"
  => exists c,
    op("ClosedCompletionPublication")(c)
    and op("Action")(s) = "suppress-committed" $
#+end_src

The diagram makes the crash boundary explicit:

- provider success advances to =executed-uncommitted=, not directly to
  =committed=;
- =executed-uncommitted= resumes the existing publication and never executes
  the physical effect again;
- a completed boolean without closed commit evidence cannot justify
  suppression;
- conflict, stale fence, transport absence, and unknown state all converge on
  =fail-closed=.

* Authority separation

The proof keeps three authorities independent.

| Plane | Owner | What it may establish | What it may not establish |
|-
| Provider observation | effect provider | authoritative negative state or durable completion acknowledgement | storage commit |
| Completion publication | existing v1 storage commit owner | atomic ledger/frontier publication and commit receipt | provider physical execution by itself |
| Core proof | Lean | implication, impossibility, closure, and authority separation | external provider or storage facts |

The existing FFI is a transport boundary, not a fourth authority:

| Projection | Allowed representation | Authority |
|-
| Core recovery model | pure Lean inductives, structures, and =Prop= | mathematical only |
| Audit receipt | existing declaration-closure/audit projection; JSON may be used | no provider or commit authority |
| Python/AXLE integration | existing FFI and Python-owned transport representation | no new semantic owner |

#+begin_src typst
$ op("AuditProjection")(p)
  not=> op("ProviderAuthority")
    or op("StorageCommitAuthority") $
#+end_src

This RFC does not add =ToJson= or =FromJson= derivations to the core
crash-recovery types.  If a Python consumer needs a JSON value, the existing FFI
or audit owner projects the already-proved declaration; the transport shape does
not leak back into the mathematical model.

* Proof findings

The Lean model exposes the following v1 design defects and closes them:

1. A pending ledger entry is observationally identical before execution and
   after execution-but-before-publication.
2. No deterministic ledger-only =execute/suppress= decision can be safe in both
   worlds.
3. A provider acknowledgement does not create storage commit evidence.
4. Receipt absence is not authoritative negative evidence.
5. A completed ledger boolean without a closed existing commit receipt must
   fail closed.
6. An acknowledgement from a stale fence token cannot close the recovery
   observation.
7. An executed-uncommitted effect must resume publication and must never execute
   again.
8. Exactly-once physical effect behavior still requires the provider's
   idempotency and durable-observation contract; Lean proves the consequences of
   that authority, not the external fact itself.

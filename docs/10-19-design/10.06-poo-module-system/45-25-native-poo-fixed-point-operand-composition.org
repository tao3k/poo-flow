#+title: Native POO Fixed-Point Operand Composition
#+startup: overview

* Status

Accepted design.

This document defines how fixed-point observability and recovery enter the
public user composition.  It connects:

- [[file:45-18-higher-order-profile-fixed-point-and-submodule-visibility.org][45-18]]
  higher-order POO operands inside Profile composition;
- [[file:45-24-fixed-point-observability-and-recoverable-debugging.org][45-24]]
  semantic, recovery-control, and observability plane separation;
- [[file:45-26-native-gerbil-poo-operation-surface.org][45-26]] for the complete
  native object-definition, slot, demand, reflection, and lifecycle operation
  surface;
- the native =.o=, =.def=, and =.mix= semantics of
  [[https://github.com/mighty-gerbils/gerbil-poo][gerbil-poo]].

The canonical package dependency remains:

#+begin_example
github.com/mighty-gerbils/gerbil-poo@1c3225637525400341a09e958296962c10184ead
#+end_example

No checkout-local path is part of this contract.

* Decision

The public composition contains two distinct semantic layers:

1. =compose profiles= combines system-level Profile operands;
2. native =gerbil-poo= =.mix= constructs one higher-order fixed-point POO
   object from prototype refinements.

The inner =.mix= expression is one operand of the outer
=compose profiles=.  It is not another Profile composition and is not a
duplicate spelling of the outer operation.

* Public user composition

The accepted public shape is:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    wendao-episteme
    (.mix
      recoverable-debugging
      fixed-point-observability
      fixed-point-core)
    production))
#+end_src

There is one =user-composition= and one =compose profiles=.  The nested
abstraction is the native POO inheritance expression that constructs the
fixed-point operand.

There is no =initial=, nested =user-composition=, =use-composition=,
=fixed-point-observability= selector application, public =poo-compose=,
runtime token dispatch, or raw conditional.

* Native POO meaning

=fixed-point-core=, =fixed-point-observability=, and
=recoverable-debugging= are prototype objects, not configuration records,
feature bundles, or selector namespaces.

Library authors define them with native =.o= or =.def= forms.  Their slots and
inherited slot computations express:

- fixed-point demand and convergence behavior;
- immutable semantic condition evidence;
- diagnostic-view projection;
- continuation and recovery-control boundaries;
- breakpoint and authority behavior.

=.mix= combines these prototypes using native =gerbil-poo= inheritance.  The
leftmost, more-specific prototype takes precedence over prototypes to its
right, while inherited slot computations may delegate to the corresponding
super-prototype computations.

The accepted chain therefore means:

#+begin_example
recoverable-debugging
  refines fixed-point-observability
  refines fixed-point-core
#+end_example

The resulting object simultaneously preserves its composite prototype and its
demand-lazy fixed-point instance, as defined by =gerbil-poo=.

* Why selectors are incorrect here

The rejected shape was:

#+begin_example
(fixed-point-observability
  +cycles
  +budgets
  +resumptions)
#+end_example

That shape incorrectly modeled semantic parts of the fixed-point object as
Profile feature switches.

Cycles, budgets, resumptions, conditions, and evidence are mutually recursive
slots and Capabilities of the fixed-point object.  They are refined through
native prototype inheritance.  They are not optional package labels selected
at Profile expansion time.

This decision does not reject hygienic Profile-local selectors in general.
It states that selectors are the wrong abstraction for constructing the
fixed-point semantic object.

* Fixed-point core

=fixed-point-core= is the base prototype.  It owns the object-level contracts
for:

- demand identity and predecessor state;
- imports and Capability visibility;
- semantic observation transitions;
- cycle and progress-budget conditions;
- generation and causal evidence;
- fixed-point result slots.

It does not own presentation, telemetry transport, debugger sessions, or
deployment authority.

* Observability refinement

=fixed-point-observability= is a native POO refinement of
=fixed-point-core=.  It may:

- inherit semantic condition evidence;
- add pure diagnostic-projection slots;
- refine condition publication with immutable observability evidence;
- add semantic breakpoint matching;
- export attenuated observation Capabilities.

It cannot turn cycle, budget, or resumption categories on and off through
Profile selectors.  All semantic evidence remains part of the coherent
fixed-point object; demand laziness determines which slots are evaluated.

It cannot acquire recovery authority or resume a continuation.

* Recoverable-debugging refinement

=recoverable-debugging= is the most-specific native POO refinement in the
accepted chain.

It inherits semantic conditions and observability projections, and refines the
live recovery boundary.  It may use explicitly imported recovery authority to
produce:

- resume evidence;
- rebase proofs;
- ambiguity resolution;
- decline propagation;
- cancellation receipts;
- authorized debugger suspension.

It cannot mint authority, infer authority from observation access, or obtain
authority from =production=.

Recovery operations remain condition-specific POO behavior.  They are not
public selectors or runtime strings.

* Demand laziness instead of feature switches

The native fixed-point object contains the semantic relationships required for
cycle, budget, resumption, observability, and recovery behavior.

Unused slots are not evaluated merely because the prototypes were mixed.
Native =gerbil-poo= demand laziness ensures that:

- unused diagnostics do not force telemetry;
- unused recovery paths do not demand authority;
- an unused child module remains unrealized;
- mutually recursive slots are resolved through the native fixed point;
- no local promise, cache, registry, or evaluator is required.

Thus composition expresses semantic availability, while demand expresses
actual evaluation.  Static selectors are unnecessary.

* Reusable Scheme binding

When the same fixed-point object is reused, ordinary Scheme naming is
sufficient:

#+begin_src scheme
(def observable-fixed-point
  (.mix
    recoverable-debugging
    fixed-point-observability
    fixed-point-core))

(user-composition my-system
  (compose profiles
    wendao-episteme
    observable-fixed-point
    production))
#+end_src

This binding does not create a registry, Profile kind, cache, or new language
form.  It names an ordinary =gerbil-poo= object expression.

If identity or reusable refinements require a public Profile binding, the
hygienic =defprofile= rules of 45-17 apply to the outer reusable operand.  They
do not replace the inner native =.mix= semantics.

* Capability-directed participation

The fixed-point POO object enters =compose profiles= as one higher-order
operand with imports, identity, and Capabilities.

Its behavior is resolved through the global demand-lazy fixed point.  It does
not search neighboring Profile names or depend on provider order.

The outer composition may place domain and deployment operands before or after
the fixed-point operand according to intended refinement precedence.  Imports
may still resolve from later-written operands through fixed-point Capability
visibility.

* Submodules

A submodule may contain or refine its own fixed-point POO object using the same
native =.mix= semantics.

Parent projection and child attenuation operate on object Capabilities and
causal submodule identities.  They do not expand a hidden selector list for
each child.

Distinct child instances may inherit from the same prototype chain while
retaining distinct canonical causal instance identities and budget
generations.

* Replay

Replay reconstructs:

- the canonical =.mix= prototype chain;
- prototype and contribution identities;
- fixed-point object identity;
- demanded semantic and diagnostic slots;
- imported authority evidence;
- transition and recovery receipts;
- root and submodule generations.

Replay does not reconstruct the object from selector tokens, Profile-name
search, source order heuristics, or a checkout-local library path.

The same canonical prototypes and inheritance order must reproduce the same
fixed-point object identity.

* Runtime and ownership boundary

Native =gerbil-poo= owns the complete operation surface catalogued by 45-26,
including object definition, slot refinement, inheritance, lazy demand,
reflection, explicit mutation, and instantiation lifecycle.

Gerbil macros own =user-composition= and =compose profiles= expansion.

POO Flow owns the fixed-point core, observability, recovery, Capability,
condition, authority, and receipt contracts expressed through those native
objects.

The runtime does not interpret selectors, build prototype registries, or
reimplement =.mix=.  The harness validates the composed behavior but is not a
semantic provider.

- [ ] Remove fixed-point category selectors and runtime dispatch tokens.
- [ ] Use inherited slot computations for semantic refinement.
- [ ] Preserve native demand laziness for unused diagnostic and recovery slots.

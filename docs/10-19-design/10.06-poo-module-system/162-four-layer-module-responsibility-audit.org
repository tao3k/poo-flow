* 10.06.162 Four-Layer Module Responsibility Audit

** 10.06.162.10 Decision

CLOS coverage is not a project metric.  The metric is whether every module
closes its =types -> objects -> funs/contracts -> config/provider=
responsibilities.  Multi-dispatch is required only when that audit exposes two
independently extensible axes.

This audit is source-owned and self-applying.  A module cannot be marked
=closed= because four facade files exist; each claimed layer needs a runtime
contract or focused test receipt.

** 10.06.162.30 Receipts In This Change

1. =model-core/types.ss= now owns four native =define-type= contracts.
2. =model-core/objects.ss= owns POO constructors and an entirely POO-native
   selection receipt.
3. =model-core/funs.ss= owns lookup, capability matching and selection.
4. =model-core/config.ss= owns only concrete catalog and policy composition.
5. =authorization/contracts.ss= owns the open capability-contract generic and
   fail-closed base method.

7. Sandbox backend modules contribute capability registries as selection data;
   =sandbox-core= no longer imports or branches on concrete backend names.

** 10.06.162.40 Admission Rule

A future module change is admitted only when its review names:

- the boundary types and invalid counterexample;
- the POO object/prototype owner;
- the pure algorithm or relational contract owner;
- the concrete configuration/Provider owner;
- zero, one, or multiple dispatch axes, with evidence for that cardinality;
- a focused test showing an extension can be added without modifying the
  generic caller when CLOS is claimed.

Introducing a CLOS class without this receipt is decorative abstraction.
Introducing a Provider-name =case= after two axes exist is a closed extension
point.  Both are policy failures.

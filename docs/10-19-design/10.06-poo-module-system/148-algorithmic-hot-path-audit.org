#+title: Algorithmic hot-path audit and shared funcs ownership
#+date: 2026-09-13

* Rule

Algorithmic mechanics belong in the nearest reusable =funcs.ss= factor. Domain
files call those functions and retain policy ownership. Gerbil std remains the
first choice when it already owns the algorithm: this pass uses
=std/misc/plist#plist?= and =std/sort#stable-sort= instead of local substitutes.

* Native product and type expression

The core and Module System previously owned separate, identical field-row
macros.  Both have been replaced by one internal
=utilities/product-syntax.ss= owner.  Its public shape follows the upstream
=gerbil-poo/io.ss= pattern: a small =defrule= lowers a declared product directly
to ordinary Scheme pairs.  It creates no runtime schema, adapter object, or
parallel construction protocol.  Core and Module System projection facades
re-export that single syntax binding, and all call sites use the same name.

Semantic responsibility contracts remain direct upstream =define-type=
declarations.  Wrapping =define-type= in another local declaration macro was
tested and rejected: it added a fragile expansion phase without adding a
domain operation or reusable method bundle.

Single-pattern syntax uses =defrule=.  =defrules= remains reserved for genuine
alternative grammars such as guarded versus unguarded final projections.

This batch also replaced map-plus-=apply append= construction in effective-slot
and method-key projection with SRFI-1 =append-map=.  The change removes the
intermediate list of lists while leaving order, duplicate resolution, and the
POO-owned public values unchanged.

The POO CLOS runtime remains outside =src/module-system/api.ss= and is loaded
only through its explicit module owner.  Its metadata-only =config.ss= is the
kernel profile entrypoint; selecting the module does not pull dispatch,
lifecycle, or declaration syntax into ASP's mandatory build closure.

The 250/500/1000-item five-sample median check, with a collection before each
sample, observed these milliseconds:

| Path | 250 | 500 | 1000 |
|------+-----+-----+------|
| CLOS make-instance | 14.18 | 35.69 | 52.58 |
| Organization validation | 4.13 | 8.26 | 16.78 |
| Verification admission and lookup | 0.76 | 1.50 | 2.96 |

These measurements establish the intended scaling on this fixture. They are
not a whole-program complexity proof and CLOS timings retain allocator noise.

The second batch passed the native CLOS lifecycle, control-plane, tutorial
feature batch, profile-composition, profile expansion performance, and public
Module System facade suites. The incremental-frontier unit fixture also counts
node accessor calls: four nodes require twelve calls during index construction
and remain at twelve across all completion updates, demonstrating that the
execution loop no longer rescans source nodes.

* Next measured candidates

1. =poo-clos/dispatch.ss=: effective-method membership scans all method groups
   and each group's methods. Index only after a fixture shows large long-form
   combinations; ordinary qualifier counts are bounded and should stay simple.
2. =core/plan.ss=: public ad hoc frontier queries intentionally remain pure and
   list-shaped. If scheduler callers invoke them repeatedly outside =runner=,
   add a reusable immutable indexed plan view rather than hiding a process cache.
3. Repeated local alist readers in UI, loader, loop, and session modules need
   call-site cardinality measurements. Small fixed metadata remains a legitimate
   projection alist; only repeated hot-loop lookup should become an index.
4. =poo-clos/syntax.ss= lowers required and optional lexical bindings to
   repeated list-position reads.  High-arity methods can make binding quadratic
   in argument count, but ordinary CLOS arities are small; require a high-arity
   invocation fixture before paying a vector allocation on every method body.

* Current CR and CI evidence

The post-change focused native batch passed class lifecycle, class evolution,
dispatch, method-combination, recursive GitHub workflow validation, JSON Schema
bridge validation, and the JSON Schema performance gate.  The evolution fixture
now includes a native-POO diamond and proves that redefining the root increments
the shared leaf generation exactly once.

One local post-change p95 receipt reported =63.19 ms= for 80 alist workflow
validations and =92.64 ms= for the equivalent POO-root validations.  The
single-job micro paths reported =14.88 us= fast-validation average and =16.06
us= receipt average.  These are host-local regression evidence, not a portable
hardware claim; the existing budgets were not relaxed.

Run =34847512726= separates the CI bottleneck from Testing: Ubuntu spent =6m17s=
in native package build, =23s= in the single native unit entrypoint, and =1m14s=
in isolated performance scenarios.  The macOS lane remained in =gerbil build=
before either test step began.  ASP's pinned Build API already initializes
=GERBIL_BUILD_CORES= from =##cpu-count= and assigns Gerbil compiler
=__available-cores= before =std/make=.  Therefore no downstream scheduler,
test batching override, or guessed fixed worker count is added here; macOS build
receipts must establish whether the remaining gap is compiler throughput or
host contention.

* Build boundary

The root and contributor scripts declare public entry modules. The root now
uses =src/module-system/api.ss=, which composes the subsystem-owned public
=interface.ss= files. ASP's native Gerbil import closure therefore discovers
CLOS, profile composition, contribution, loader, and the other public Module
System sources without =all-gerbil-modules= or implementation-file enumeration.

This correction invalidates the former 1.95-second root comparison: that build
only reached the metadata-only =src/module-system/interface.ss= and omitted the
public subsystem closure. The first corrected isolated build compiled the full
closure successfully; two warm runs emitted zero compile jobs but took 21.71
and 34.90 seconds. Dependency admission also found that =gerbil.pkg= requests
=asp-gerbil-scheme@a3d132a= while the installed package remains =7fb8e8b=.
After fetching the requested object, both implicit and exact project-level
=gxpkg deps --update= left the shared link/tag state unchanged, while
=gxpkg deps --install= rejects the incompatible installed tag. The linked
checkout is =db904ad= and the local library contains artifacts produced across
multiple prior revisions, so the exact dependency was also compiled in an
isolated =GERBIL_PATH=. Its zero-job warm runs took 28.56 and 23.46 seconds.
The verbose boundary projected 137 targets before handing control to
=std/make=. The persistent projection experiment and its complete-build
rejection are recorded in =149-persistent-native-public-closure-projection.org=.

The experiment did prove that a receipt can reduce isolated 112-module closure
projection from a 24.682-second p50 to 0.984 seconds. It did not remove that
work from the complete build. Fresh native projection constructs module
contexts that the following =std/make= invocation can reuse; receipt admission
returns only paths, so =std/make= reconstructs those contexts after the verbose
handoff.

Three zero-job native-projection builds measured 51.68, 38.24, and 28.63
seconds. Three zero-job receipt-hit builds measured 31.73, 47.97, and 39.80
seconds. The medians were 38.24 and 39.80 seconds respectively, making the
receipt path about 4.1 percent slower. The receipt implementation, policy slot,
CI timing lane, and downstream opt-ins were removed. POO Flow retains the
standard native closure and =std/make= even though the remaining warm latency
is unresolved.

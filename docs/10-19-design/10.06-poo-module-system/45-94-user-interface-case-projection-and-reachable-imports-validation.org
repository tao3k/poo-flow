#+title: User Interface Case Projection and Reachable imports Validation
#+startup: overview

* Status

Accepted architecture.

This RFC applies the Module, ProfileBundle, and imports-closure algebra in
[[file:45-93-module-profile-selection-bundle-and-imports-closure-algebra.org][45-93]]
to the current CrewAI, LangChain, LangGraph, and tool-calling User Interface
cases.

It validates whether the target surface reduces repetition without hiding
Profile identity, dependency reachability, capability requirements, proofs, or
runtime handoffs.

* Scope

This document owns:

- the target Module responsibility of each current case;
- the aggregate ~production~ Profile projection for each Module;
- preservation of current low-level Profile identities;
- preservation of graph, loop, proof, and handoff semantics;
- reachable imports closure expectations;
- capability-responsibility expectations;
- concise ordinary user examples; and
- case conformance receipts.

It does not own:

- implementation of the framework runtime;
- package ownership transfer;
- compatibility with the old clause grammar;
- definition of new fixed-point semantics;
- control-policy priority;
- physical Gerbil import generation; or
- a framework-specific user DSL.

Scale-parametric safety for arbitrary finite Module counts and the separate
100, 1,000, and 10,000 Module executable admission receipts are owned by
[[file:45-112-scale-parametric-module-graph-safety-and-executable-admission.org][45-112]].

* Central decision

Each case becomes one higher-order POO Module.

Each Module exports one ordinary aggregate Profile named ~production~.  That
Profile owns the graph, loop, proof, handoff, low-level Profile selection, and
imports reachability required by the current case.

The ordinary examples become:

#+begin_src scheme
(user-composition crewai-system
  (compose profiles
    (use-module crewai
      production)))

(user-composition langchain-system
  (compose profiles
    (use-module langchain
      production)))

(user-composition langgraph-system
  (compose profiles
    (use-module langgraph
      production)))

(user-composition tool-calling-system
  (compose profiles
    (use-module tool-calling
      production)))
#+end_src

The four ordinary examples contain four Profile selections rather than 74
declaration-and-reference occurrences.

This compression is admitted only when the imports closure and evidence receipt
still expose every reachable low-level Profile and stage responsibility.

* Framework names are provenance, not new semantics

CrewAI, LangChain, and LangGraph are case-provenance names.

They do not create:

- new POO object kinds;
- new composition strategies;
- new control decisions;
- new capability types merely because a framework uses different vocabulary;
- new fixed-point evaluators;
- new package managers; or
- framework-specific clause languages.

Every case is expressed through the same Module, Profile, ProfileBundle,
imports, capability, graph, proof, and handoff objects.

* Reachability validation

For each case ~K~:

#+begin_src typst
$ "imports"("use-module"(K, "production")) =
  "closure"("dependencies-reachable-from"(K / "production")) $
#+end_src

The closure receipt identifies:

- the aggregate Profile;
- every reachable low-level Profile;
- every recursive Module dependency;
- every excluded Module/Profile subgraph;
- effective capability requirements;
- graph and loop identities;
- proof obligations;
- handoff identity or explicit absence;
- revision and generation; and
- deterministic closure digest.

Absence is evidence.  For example:

- LangChain records no tool branch and no runtime handoff;
- LangGraph records no implicit observability Profile;
- a case without human input records no human-input authority; and
- an unselected framework Module contributes no dependencies.

* Cross-case composition

The same algebra permits cases to compose without creating a framework bridge
DSL:

#+begin_src scheme
(user-composition governed-tool-agent
  (compose profiles
    (use-module langgraph
      production)
    (use-module tool-calling
      production)
    (use-module wendao-episteme
      production-governance)))
#+end_src

Module-scoped Profile identity keeps the two ~production~ selections distinct.

The composition must reconcile:

- LangGraph tool-node requirements;
- tool-calling permission and sandbox requirements;
- governance proof and decision requirements;
- runtime handoff compatibility;
- loop budgets;
- shared identity; and
- evidence closure.

No framework name determines precedence.

* Aggregate Profile completeness

An aggregate case Profile is admitted only when:

- every current low-level Profile responsibility is either reachable or
  explicitly removed with an architectural decision;
- graph identity is preserved;
- loop budget and exit identity are preserved;
- every proof obligation has a POO-native evidence owner;
- handoff identity or explicit absence is preserved;
- capability requirements are explicit;
- no additional framework subgraph becomes reachable accidentally; and
- closure receipts expose the full mapping.

The shorter user syntax is not evidence of completeness by itself.

* User Interface ownership

The target User Interface case file should contain only:

- the ordinary ~user-composition~ example;
- selection of one or more aggregate Module Profiles;
- optional explicit Module instance aliases; and
- comments that identify the scenario purpose.

The owning Module definition contains:

- low-level Profiles;
- aggregate Profiles;
- imports projections;
- capability requirements;
- graph and loop objects;
- proof objects;
- handoff objects; and
- revision/provenance metadata.

This separation prevents an example file from becoming a second Module
definition language.

* Current implementation gap

The current files combine:

- Module declaration;
- Profile declaration;
- Profile selection;
- Profile composition;
- stage construction;
- proof declaration;
- and runtime handoff.

They also repeat every low-level Profile identity.

The target files select already-published aggregate Profiles.  The owning
Modules remain POO-native and may be reused by tests, downstream packages, and
other compositions.

No compatibility case is required.

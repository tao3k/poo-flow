#+title: Capability Requirement, Provision, Attenuation, Withdrawal, and Reachable-Closure Contract
#+author: POO Flow
#+language: en

* Status

This RFC is an accepted semantic contract.

It defines capability satisfaction and closure over the reachable Module graph.
It does not define runtime capability handles, an authorization service, a
mutable permission registry, or an implementation.

Implementation remains blocked until every consumed upstream POO operation path
is =ADMITTED= by RFC 45-120.

* Scope

This RFC owns:

- the higher-order POO value held by the Module =capabilities= slot;
- capability identity, requirements, provisions, attenuation, withdrawal, and
  denial evidence;
- positive monotonic capability closure;
- stratified negative contributions;
- contribution-admission priority versus C3 dispatch precedence;
- capability cycles, conflicts, outcomes, cache identity, provenance, and
  explanation;
- separation of semantic capability evidence from runtime handles.

It does not own:

- upstream POO object, prototype, dispatch, or precedence mechanics;
- runtime credential or handle materialization;
- secret retrieval;
- package, source, build, or deployment dependencies;
- application contribution-priority definitions;
- a public capability DSL.

* Central decision

The Module =capabilities= slot contains one higher-order native POO contract
with two required semantic responsibilities:

- =requirements=;
- =provisions=.

Capability identity and all contributions are first-class POO semantic values.
They are not names in a registry, strings, booleans, runtime handles, callbacks,
or environment probes.

Capability closure is evaluated as a derived responsibility of
=DispatchEvaluation= over the reachable graph produced by RFC 45-124.

* Capability contract

The =capabilities= value is a native POO contract.

=requirements= declares semantic capability obligations.

=provisions= declares semantic capability evidence that a Module or Profile may
offer when its own requirements and contribution policies are satisfied.

The contract may derive:

- admitted positive provisions;
- unsatisfied requirements;
- withdrawn provisions;
- denied provisions;
- conflicts;
- attenuation paths;
- closure outcome;
- provenance and explanation.

Those derived responsibilities are not duplicate required storage.

* Capability identity

A capability is identified by:

- semantic capability identity;
- contract or schema identity;
- owner Module or Profile identity;
- immutable prototype or contribution generation;
- constraint identity;
- provenance.

It is distinct from:

- a runtime token, file descriptor, client, or credential;
- a secret value;
- a package feature;
- a build option;
- a deployment handle;
- an unqualified global name.

Capability matching is semantic and typed.  It does not compare only strings.

* Requirement semantics

A requirement states:

- required capability identity;
- admitted constraint;
- requesting Module or Profile identity;
- import path and attenuation context;
- whether multiple compatible providers may compose;
- failure and explanation requirements.

A requirement cannot directly execute discovery, environment access, or handle
acquisition.

Requirement satisfaction is derived only from admitted semantic provisions.

* Provision semantics

A provision states:

- provided capability identity;
- provider Module or Profile identity;
- semantic constraints and guarantees;
- dependencies on other admitted requirements;
- attenuation and visibility limits;
- contribution provenance.

A provision proves semantic availability.  It does not grant runtime authority
and does not contain a runtime handle.

Conditional provisions may participate in positive fixed-point refinement only
when their dependencies and refinement rules are monotonic.

* Reachable-graph closure

Capability closure consumes the reachable Module graph and its import-edge
evidence.

For each reachable node, it:

1. projects the Module =capabilities= contract;
2. attaches Module, Profile, and import-edge provenance;
3. narrows authority along the incoming edge;
4. submits contributions to admission;
5. evaluates positive closure;
6. applies stratified negative constraints;
7. validates requirements;
8. returns one closure outcome and explanation.

Unreachable Modules do not contribute requirements, provisions, withdrawals,
or conflicts.

* Capability attenuation

Authority may only narrow along an import edge.

The outgoing authority context must be less than or equal to the incoming
authority context under the admitted attenuation relation.

Combining semantic provision evidence from multiple paths does not union
runtime authority.

The same Module reached under a distinct attenuated capability context has a
distinct evaluation identity unless the cached result is proven safe under the
narrower projection.

Every attenuation step records:

- incoming authority identity;
- edge requirements;
- admitted visible provisions;
- outgoing authority identity;
- denied or redacted evidence.

* Positive monotonic closure

Positive closure begins from an explicit bottom value.

It may add:

- admitted unconditional provisions;
- provisions whose positive requirements become satisfied;
- positive compatibility and composition evidence;
- derived positive capability facts.

Each refinement step must:

- be deterministic;
- be monotonic;
- preserve capability attenuation;
- carry a semantic delta;
- consume an explicit refinement budget;
- converge under a declared relation.

A positive cycle is productive only when it has a seed or refinement path that
produces monotonic progress and converges.

Two capabilities that merely require each other without a seed form an
unproductive dependency, not evidence of mutual satisfaction.

* Negative contributions and stratification

Negative contributions include:

- withdrawal of an admitted provision;
- explicit denial;
- incompatibility;
- requirements that depend on completed absence evidence.

Negative contributions do not participate in the same unrestricted monotonic
fixed point as positive provisions.

They must be stratified:

- a negative stratum may depend positively or negatively only on completed
  lower strata according to the admitted stratification relation;
- a negative dependency cannot point back into the same unresolved stratum;
- an unstratified negative cycle is a structured condition.

Absence is proven only after the relevant positive and lower negative strata
are complete.  Failure to discover a value within an unfinished or
budget-exhausted evaluation is not proof of absence.

* Withdrawal

Withdrawal is an immutable contribution that masks or removes a provision
according to contribution-admission policy.

It:

- names the targeted capability and contribution identity;
- carries owner and provenance;
- participates in contribution priority before the dispatch graph is
  finalized;
- produces a new capability-contract generation;
- never mutates the original Module or Profile.

A withdrawal cannot erase evidence that the withdrawn contribution existed.
The explanation preserves both the contribution and withdrawal paths.

* Contribution priority and C3

Contribution priority and C3 precedence remain separate:

- contribution priority admits, rejects, or withdraws capability contributions
  before the prototype graph is finalized;
- C3 precedence dispatches behavior inside the finalized graph.

This RFC does not redefine the numeric priority scale.

After dispatch begins, a priority value cannot:

- skip a C3 provider;
- rewrite =super=;
- revive a withdrawn contribution;
- override attenuation;
- grant runtime authority.

If contributions cannot form one valid graph, capability closure returns a
composition condition before dispatch.

* Provider composition and conflict

Multiple providers may satisfy one requirement only when the capability
contract declares a compatible composition algebra.

Otherwise:

- one admitted provider is selected through the finalized POO policy graph; or
- incompatible providers produce a structured conflict.

Provider composition must define:

- identity of the composite provision;
- monotonic refinement or deterministic selection;
- constraint intersection or compatibility;
- provenance of every provider;
- attenuation behavior;
- explanation.

Last-writer-wins is not a capability composition algebra.

* Cycle classifications

Capability cycles reuse the fixed-point classifications from RFC 45-124:

- productive positive cycle;
- suspended dependency;
- unproductive positive cycle;
- divergent refinement;
- denied or invalid cycle.

This RFC adds:

- unstratified negative cycle;
- withdrawal conflict;
- incompatible-provider cycle;
- attenuation violation.

Cycle evidence remains attached to the same capability-closure outcome.

* Outcomes

Capability closure may return:

- satisfied semantic closure;
- unsatisfied requirements;
- denied capability;
- incompatible providers;
- unstratified negative dependency;
- suspended dependency;
- budget or convergence condition;
- cancelled outcome.

A partially evaluated closure is not silently treated as satisfied.

Unsatisfied, denied, and unavailable are distinct:

- unsatisfied means no admitted semantic provision meets the requirement;
- denied means policy or attenuation rejects an otherwise relevant provision;
- unavailable means evaluation is incomplete, suspended, or failed.

* Exactly-once reconciliation

The same capability contribution may be reachable through multiple import
paths.

The closure evaluator:

- evaluates one semantic contribution identity once per closure context;
- retains every provenance witness;
- reconciles contribution and refinement budgets once;
- evaluates every distinct attenuation edge;
- does not materialize a runtime handle for each witness.

Duplicate provenance, retry, replay, and coordinator resumption remain distinct
relations.

* Cache identity and invalidation

A stable capability-closure cache key includes:

- reachable-graph identity;
- Module and selected Profile identities;
- capability-contract and contribution generations;
- contribution-admission policy identity;
- positive refinement and negative stratification identities;
- attenuation context;
- evaluation-context projection;
- redaction boundary.

Changes to requirements, provisions, withdrawals, contribution priority,
attenuation, prototype generation, or reachable imports invalidate affected
entries.

Partial positive or negative strata remain local to one evaluation context and
are not published as complete closure.

* Provenance and explanation

The explanation may project:

- requirement and provision identities;
- Module, Profile, and import-edge ownership;
- admitted and rejected contributions;
- contribution-priority decisions;
- attenuation paths;
- positive refinement deltas;
- negative strata;
- withdrawals and denied provisions;
- selected or composed providers;
- unsatisfied and conflict reasons;
- cache and budget decisions;
- final closure outcome.

Observation is demand-driven, budgeted, capability-scoped, and redacted.

* Runtime-handle boundary

Semantic capability closure produces evidence and authority requirements.  It
does not produce a runtime handle.

When a selected responsibility needs runtime materialization:

- pure dispatch projects an admitted EffectIntent;
- a runtime/deployment adapter checks runtime authorization;
- the adapter acquires or constructs the handle;
- runtime receipt, lease, revocation, and cleanup remain outside semantic
  closure.

Semantic satisfaction does not guarantee runtime availability.  Runtime denial
does not rewrite the semantic closure.

* Module and ProfileBundle integration

The Module =capabilities= contract remains one of the four required Module
slots.

Capability closure is attached to the reachable ProfileBundle as semantic
evidence:

- requirements remain attributable to their owners;
- provisions remain attributable to their providers;
- attenuation remains attributable to import edges;
- withdrawals and conflicts retain contribution provenance;
- no runtime handle enters the ProfileBundle.

The final application selects Profiles and contribution policy.  It does not
mutate domain capability contracts.

* Public-interface boundary

This RFC adds no public capability syntax.

The ordinary interface remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

Advanced capability extension uses native POO objects, prototypes, and admitted
generic operations.

* Ownership

- Upstream =gerbil-poo= owns object, prototype, dispatch, inherited
  computation, and C3 mechanics.
- =poo-flow-core= owns capability semantic identity, requirements, provisions,
  closure, attenuation, stratification, conditions, cache identity, provenance,
  and explanation.
- =wendao-episteme= owns domain capability contracts supplied by its Modules and
  Profiles.
- The final application owns contribution-admission policy and selected
  Profiles.
- Runtime/deployment adapters own runtime authorization, materialization,
  leases, revocation, cleanup, and receipts.
- GSLPH remains a development policy harness and building/testing dependency.

* Admission checklist

** Capability object

- [X] Freeze =requirements= and =provisions= as the two required semantic
  responsibilities of the higher-order capability contract.
- [X] Require semantic and typed capability identities.
- [X] Reject strings, booleans, runtime handles, callbacks, and registries as
  the ordinary representation.
- [X] Keep closure, conflicts, withdrawals, and explanations derived.
- [ ] Define exact internal POO prototype identities after adapter admission.

** Closure semantics

- [X] Evaluate only capabilities from the reachable Module graph.
- [X] Require attenuation on every import edge.
- [X] Separate positive monotonic closure from negative stratification.
- [X] Require explicit bottom, refinement, convergence, and explanation deltas.
- [X] Reject seedless mutual requirements as automatic satisfaction.
- [ ] Prove at least one productive cyclic capability closure.

** Negative contributions

- [X] Freeze withdrawal as an immutable contribution.
- [X] Preserve withdrawn contribution evidence.
- [X] Reject unstratified negative cycles.
- [X] Prove absence only after lower strata complete.
- [X] Separate contribution priority from C3.
- [ ] Prove withdrawal, denial, incompatibility, and absence conditions.

** Cache and observability

- [X] Freeze closure cache identity and invalidation inputs.
- [X] Require exactly-once logical contribution reconciliation.
- [X] Preserve multi-path provenance.
- [X] Reject publication of partial strata as complete closure.
- [ ] Prove cache invalidation for imports, contributions, priority, and
  attenuation changes.
- [ ] Prove budget reconciliation across duplicate paths.

** Runtime boundary

- [X] Separate semantic capability evidence from runtime handles.
- [X] Require EffectIntent projection before runtime materialization.
- [X] Keep runtime denial distinct from semantic unsatisfaction.
- [ ] Define runtime materialization, lease, revocation, cleanup, and receipt
  contracts.
- [ ] Run focused GSLPH development checks without adding a product dependency.

** Implementation admission

- [ ] Admit every consumed upstream POO operation path in RFC 45-120.
- [ ] Implement capability contracts as native POO values.
- [ ] Implement closure as a =DispatchEvaluation= derived responsibility.
- [ ] Integrate closure with recursive reachability and ProfileBundle evidence.

* Rejected alternatives

- A mutable permission or capability registry.
- Capability identity represented only by strings.
- Runtime handles stored in Module or Profile values.
- Unioning runtime authority across import paths.
- Mixing withdrawal and absence into an unrestricted positive fixed point.
- Treating unfinished evaluation as proof of absence.
- Numeric contribution priority replacing C3 dispatch.
- Last-writer-wins provider selection.
- Mutating the original capability contract during withdrawal.
- Re-evaluating one contribution for every provenance witness.
- Treating semantic satisfaction as guaranteed runtime availability.
- A public capability clause DSL.

* Successor contract

The next RFC should define the boundary from semantic capability evidence to
runtime capability materialization.

It must specify:

- EffectIntent projection;
- runtime authorization;
- handle construction or acquisition;
- lease identity and lifetime;
- revocation;
- cleanup and cancellation;
- runtime denial;
- receipt identity and redaction;
- the separation between semantic closure cache and runtime handle cache.

It must not put runtime handles into Module, Profile, ProfileBundle, or
=DispatchEvaluation= semantic values.

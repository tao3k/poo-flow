#+subtitle: Multi-source semantic inputs, version vectors, watermarks, partial collection, and honest consistency claims

* RFC status

- Status :: Accepted design
- Kind :: Normative multi-observation consistency protocol
- Semantic core :: Content-addressed POO observation artifacts and explicit consistency contracts
- Related modules :: =45-55-effect-intent-stabilization-runtime-handoff-and-reconciliation.org= and =45-57-resource-scope-version-precondition-and-concurrency-control.org=

This module defines when multiple external observations may be sealed as one semantic input. Individually content-addressed values do not prove that the values belong to one atomic, causal, or otherwise consistent view.

* Core decision

#+begin_quote
Multiple external observations become one semantic ObservationSet only after an explicit ObservationConsistencyContract is validated by snapshot, version-vector, watermark, or explicitly bounded best-effort evidence. Similar timestamps, concurrent requests, and individual content identities do not prove cross-resource snapshot consistency.
#+end_quote

The distinct artifacts are:

#+begin_src text
ObservationArtifact
ObservationSet
ObservationConsistencyContract
SnapshotProof
#+end_src

* Typst formalization: validated observation sets

Content-addressed observations remain independent evidence until an explicit
consistency contract is validated.  Coincident timestamps, equal content
identities, or numerically similar versions do not synthesize a cross-resource
snapshot.

#+begin_src typst
#let observation(resource-id, version, digest, observation-id, generation, observed-at) = (
  resource-id: resource-id,
  version: version,
  digest: digest,
  observation-id: observation-id,
  generation: generation,
  observed-at: observed-at,
)

#let consistency-contract(role, relation, version-domain, freshness-bound, skew-bound) = (
  role: role,
  relation: relation,
  version-domain: version-domain,
  freshness-bound: freshness-bound,
  skew-bound: skew-bound,
)

$ O = {o_1, ..., o_n} $
$ C = (role, related, version-domain, freshness-bound, skew-bound) $
$ Candidate(O) != ValidatedObservationSet(O, C) $

$ SameTimestamp(o_i, o_j) not=> Consistent(o_i, o_j) $
$ SameContentIdentity(o_i, o_j) not=> Consistent(o_i, o_j) $
$ SimilarVersionNumber(o_i, o_j) not=> Comparable(o_i, o_j) $
#+end_src

A sealed set carries both the declared relation and the witnesses that the
actual observations satisfy it.  Freshness is evaluated against the semantic
generation reference time; declaring a bound without validating observations
against that bound does not establish freshness.

#+begin_src typst
$ ValidatedObservationSet(O, C, t_ref) := $
$ quad O != emptyset $
$ and forall o_i, o_j in O: C.related(o_i, o_j) $
$ and forall o in O: t_ref <= o.observed-at + C.freshness-bound $
$ and forall o_i, o_j in O:
    o_i.observed-at <= o_j.observed-at + C.skew-bound $

$ SemanticGenerationInput(x) => exists S: ValidatedObservationSet(S) $
$ Authority(C) = false $
$ Fresh(C) = false $
$ Fresh(ValidatedObservationSet(O, C, t_ref)) = true $

$ Comparable(v_i, v_j) => exists D, R:
    D(resource_i, resource_j) and R(v_i, v_j) $
#+end_src

The solid path constructs a sealed semantic input.  The dashed edges are
exclusions: raw observations and an unvalidated contract remain evidence about
the world, but they do not yet describe one consistent and sufficiently fresh
view of the world.

** Proof obligations

- [X] =contentAddressedObservationsDoNotEstablishConsistency=: content
  addressing proves observation identity, not cross-resource consistency.
- [X] =identicalTimestampsDoNotEstablishConsistency=: timestamp coincidence
  does not construct a snapshot relation.
- [X] =contractAloneDoesNotEstablishConsistency=: a declared relation without
  witnesses for the actual observations does not establish consistency.
- [X] =contractAloneDoesNotEstablishFreshness=: a declared freshness bound is
  not evidence that observations satisfy it.
- [X] =validatedSetEstablishesConsistency= and
  =validatedSetEstablishesFreshness=: only the validated-set evidence kind
  establishes both properties in this proof slice.
- [X] =validatedSetCarriesExplicitContract=: every admitted observation set
  carries its explicit consistency contract.
- [X] =validatedSetCarriesConsistencyWitness=: every admitted set carries the
  pairwise relation witness for its actual observations.
- [X] =validatedSetCarriesFreshnessWitness=: every admitted set carries the
  reference-time freshness witness.
- [X] =semanticGenerationRequiresValidatedSet=: semantic generation accepts a
  validated set rather than a raw observation list.
- [X] =versionComparabilityCarriesDeclaredDomain=: cross-resource version
  comparison carries a declared resource domain and version relation.

* Observation set identity

A pure =ObservationSetIdentity= is conceptually derived from:

#+begin_src text
H(
  member ObservationArtifact identities,
  member ResourceScope identities,
  source version projections,
  ObservationConsistencyContract identity,
  SnapshotProof identity when available
)
#+end_src

Only a validated and sealed ObservationSet may enter a semantic generation as one multi-source input.

* Consistency roles

Every ObservationSet declares a consistency role through a POO contract object.

** Independent observations

This role proves only:

#+begin_src text
artifact A is content-addressed
artifact B is content-addressed
no cross-resource snapshot claim
#+end_src

It is valid when the semantic consumer does not require cross-resource consistency.

** Single-adapter snapshot

One adapter may provide:

- transaction snapshot identity;
- common revision;
- database snapshot token;
- authoritative read timestamp;
- snapshot receipt.

The set may claim one snapshot only when the adapter protocol explicitly guarantees the relation.

** Version-vector or causal-cut consistency

Distributed sources may use:

- version vector;
- causal dependency vector;
- source sequence;
- dominance relation;
- consistent-cut proof.

Version numbers from unrelated domains are not directly comparable without a declared vector domain and relation.

** Watermark-bounded consistency

Stream and event sources may use:

- per-source watermark;
- event-time domain;
- late-event policy;
- completeness boundary;
- watermark proof.

** Freshness or skew-bounded best effort

This role declares:

- maximum observation age;
- maximum collection skew;
- authoritative clock domain;
- validation time;
- best-effort status.

It is not labeled atomic snapshot.

flowchart LR
    A["Observation artifact A"] -->|"contribute version and resource scope"| S["ObservationSet"]
    B["Observation artifact B"] -->|"contribute version and resource scope"| S
    C["ObservationConsistencyContract"] -->|"declare the required relation"| V["Consistency validation"]

#+end_src

* Timestamp limitation

The following do not independently prove one snapshot:

- similar wall-clock timestamps;
- responses returned within the same second;
- similar filesystem modification times;
- concurrently started requests;
- metadata labeled "latest";
- local collection start and end time.

Clock skew, network delay, write races, and independent commit histories make those observations insufficient.

Timestamps may support freshness evidence. They do not replace an adapter snapshot or causal protocol.

* Cross-system consistency

Across independent databases, APIs, or services:

- no global transaction is assumed;
- no atomic snapshot is claimed without a covering protocol;
- independent or best-effort consistency is explicit;
- a strong consistency requirement fails closed when proof is unavailable;
- consistency is not silently weakened to continue evaluation.

Weakening an observation consistency contract requires explicit control policy and authority. It derives a different semantic identity and produces a weakening receipt.

* Collection pipeline

The normative pipeline is:

#+begin_src text
pure ObservationSetPlan
-> execute member observation intents
-> materialize member artifacts
-> collect version, snapshot, or watermark evidence
-> validate ObservationConsistencyContract
-> seal ObservationSet
-> derive a new semantic generation
#+end_src

Downstream semantic results cannot treat an unsealed set as a complete consistent input.

* Partial observation

Every member declares required or optional semantics.

- Missing required member :: Produces =ObservationSetIncomplete= and prevents sealing.
- Missing optional member :: Allowed only when the contract explicitly admits absence and canonical absence evidence is produced.
- Operational failure :: Does not automatically become optional absence.
- Unauthorized observation :: Does not mean the resource is absent.
- Redacted observation :: Does not count as complete semantic content when the value is required.

Absence has identity and provenance. It is not represented by silent omission.

* Optimistic multi-read validation

When no true snapshot exists, an adapter may support optimistic validation:

1. Observe required members and their versions.
2. Revalidate the declared versions.
3. Discard the set if any version changed.
4. Observe again under a bounded retry policy.

This proves only the stability interval supported by the adapter protocol.

If revalidation leaves an unclosed race between check and use, the system reports =SnapshotValidationRace=. It does not relabel the result as atomic snapshot.

* Version-vector validation

A version-vector projection identifies:

- source identity;
- per-source version;
- causal dependency;
- vector domain;
- dominance or incomparability;
- missing-source policy.

Incomparable vectors may:

- be admitted as concurrent only under an explicit consistency policy;
- require collection of a new consistent cut;
- fail closed with =VersionVectorIncomparable=.

The system does not select a newer vector by string, hash, or display ordering.

* Watermarks and late data

A watermark contract declares:

- event-time or processing-time domain;
- watermark source;
- per-source progress;
- allowed lateness;
- correction or retraction policy;
- seal condition.

A late event does not mutate an already sealed set:

- the old set remains historical evidence;
- the event becomes a new observation artifact;
- policy derives a new ObservationSet;
- a new semantic generation follows when the set is admitted.

When the required watermark has not been reached, the set remains unsealed or fails with =WatermarkNotReached= according to bounded policy.

* Freshness expiry

Artifact content identity does not change as time passes. Its admission under a freshness policy may expire.

- Content identity remains stable.
- Freshness validation produces current admission or execution evidence.
- An expired artifact remains historical cache content.
- A current demand cannot use it when freshness is required.
- A new observation is requested.
- A previous receipt does not prove freshness forever.

Absolute current time does not continuously mutate the semantic hash. The active freshness policy identity is pure; current-time validation remains operational or admission evidence.

* Nested submodule observations

A submodule may provide a sealed ObservationSet with its own proof.

The parent:

- preserves the child set and proof identities;
- inherits only the consistency actually proven by the child;
- does not combine a child snapshot with unrelated parent observations and claim one atomic snapshot;
- declares a new cross-set consistency contract;
- fails closed or uses an explicitly authorized weaker policy when the required cross-set proof is unavailable.

Nested composition cannot raise a child consistency label.

    P -->|"validate a new cross-set contract"| V["Parent consistency validation"]
    V -->|"cross-set proof exists"| S["Parent sealed ObservationSet"]

#+end_src

* Cache boundary

Pure cacheable artifacts include:

- member ObservationArtifacts;
- SnapshotProof;
- sealed ObservationSet;
- consistency validation receipt;
- canonical absence evidence;
- watermark and version-vector projections.

Before reuse, the evaluator validates:

- protocol applicability;
- freshness and lease validity where required;
- required-member completeness;
- disclosure authorization;
- semantic-generation reference to the same set identity.

Live snapshot handles, transactions, tokens, and connections are not cached.

* Failure taxonomy

The normative failures include:

#+begin_src text
ObservationSetIncomplete
SnapshotConsistencyUnavailable
SnapshotValidationRace
VersionVectorIncomparable
WatermarkNotReached
LateObservationRequiresRevision
FreshnessExpired
ObservationScopeUnauthorized
#+end_src

They retain distinct ownership and are not collapsed into one network or adapter failure.

* Evidence requirements

Observation-set evidence records:

- set plan and sealed-set identity;
- member artifact and resource-scope identities;
- required, optional, and absent-member classification;
- consistency-contract identity;
- snapshot, vector, watermark, or best-effort proof;
- collection and validation interval;
- freshness policy and current validation;
- late-data correction or revision;
- child and parent consistency scopes;
- successor semantic generation.

Evidence does not serialize live snapshot, transaction, connection, or capability handles.

* Implementation checklist

- [ ] Define identity-addressed POO ObservationSet plans and sealed sets.
- [ ] Define explicit independent, snapshot, vector, watermark, and best-effort consistency roles.
- [ ] Prevent timestamps and concurrent requests from being treated as snapshot proof.
- [ ] Require a covering protocol for cross-system atomic snapshot claims.
- [ ] Define required and optional member semantics.
- [ ] Represent absence with canonical identity and provenance.
- [ ] Prevent operational failure and unauthorized access from becoming absence.
- [ ] Implement bounded optimistic multi-read validation where supported.
- [ ] Report unclosed revalidation races.
- [ ] Define version-vector domains, dominance, and incomparability.
- [ ] Define watermark, lateness, correction, and seal policies.
- [ ] Keep sealed sets immutable when late data arrives.
- [ ] Validate freshness without mutating artifact identity.
- [ ] Preserve and constrain nested submodule consistency proofs.
- [ ] Generate collection, consistency, freshness, and successor-generation evidence.
- [ ] Validate final observation objects against real =gerbil-poo= and adapter primitives.

* Non-goals

- Do not treat individually content-addressed observations as one automatic snapshot.
- Do not use similar timestamps as cross-resource consistency proof.
- Do not claim atomic cross-system snapshot without a covering protocol.
- Do not silently weaken consistency when proof is unavailable.
- Do not turn operational failure or unauthorized access into optional absence.
- Do not mutate sealed sets when late data arrives.
- Do not let a parent raise a child consistency guarantee.
- Do not introduce an observation registry, snapshot DSL, or raw callback protocol.

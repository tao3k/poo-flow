* 10.06.18 Agent Sandbox Profile Interface
** 10.06.18.10 Bass-Derived User Interface Rule
Bass keeps user work visible as small, inspectable recipes before a runtime executes them. The important lesson for =poo-flow= sandbox work is not the Bass language implementation. The lesson is the user-facing shape:

- users write short scenario rows;
- rows are ordinary data before execution;
- runtime images, cache, mounts, and host access remain explicit;
- backends do the heavy execution outside the small user interface.

For =poo-flow=, agent sandbox profiles should follow the same rule. A profile is an inert POO recipe that names the backend, network policy, capabilities, resource policy, and metadata. Projection to backend descriptors is a later step. Runtime execution remains owned by =marlin-agent-core= or the selected backend adapter.

** 10.06.18.20 User Surface
Root =init.ss= keeps module selection separate from sandbox profile recipes. The public user surface is concrete module loading; the facade builds the canonical =users= profile from those rows. Built-in sandbox profile recipes live upstream in =src/modules/agent-sandbox/config.ss=, and downstream user files load those defaults instead of spelling out backend policy rows.

#+begin_src scheme
(use-module nono-sandbox +nono +doctor)
(use-module cubeSandbox +cube +doctor)

poo-flow-default-sandbox-profiles
(poo-flow-default-sandbox-profile-presentation)
#+end_src

The public user row is module-level: =(use-module nono-sandbox ...)=. The full profile construction layer remains upstream so agents or higher profiles can generate one =users= profile without making the user understand descriptor catalogs, C3 slot resolution internals, or Marlin runtime manifests.

** 10.06.18.30 Boundary
The boundary is:

- concrete =(use-module ...)= rows select sandbox modules such as =nono-sandbox= and =cubeSandbox=;
- =poo-flow-default-sandbox-profiles= declares upstream profile recipes consumed by those modules or their runtime bridges;
- downstream user config may select or override profile names, but it should not own built-in backend policy rows;
- =pooFlowSandboxProfilesPresentation= gives tools a shallow receipt with names, backend refs, runtime handoff intent, runtime summaries, and handoff summaries;
- =poo-flow-sandbox-profile->profile= projects one recipe into the existing validated sandbox profile contract;
- =agent-sandbox-profile-runtime-summary= and =agent-sandbox-profile-handoff-summary= live under =src/modules/agent-sandbox/profile.ss= so workflow and loop code consume sandbox-owned projection data instead of reparsing resource policy rows;
- no package installation, descriptor realization, or runtime command execution happens in the user interface layer.

** 10.06.18.32 Recipe Path Portability

The earlier leading-=/= predicate was not the portability contract.  It
accepted a relative =target= even though target ownership belongs to runtime
materialization, accepted =source ../outside= even though it escapes the
declared logical resource root, and did not recognize Windows drive, UNC, or
=file:= absolute forms.  These are concrete countermodels, not platform
compatibility cases.

Recipe validation is now structural.  A =target= field is forbidden regardless
of its spelling.  A logical =source= is either the project root =.= or a
canonical non-empty relative segment list with no empty, =.=, or =..= segment,
backslash, or drive separator.  Absolute POSIX, Windows rooted/drive/UNC, and
=file:= forms fail closed.  A =project-marker= is one canonical filename
segment.  Symlink and mount resolution are deliberately not claimed by this
lexical predicate: the backend materialization policy resolves the declared
logical role and source, and its receipt owns the concrete target and
confinement evidence.

entry identifies the project workspace with its logical =role=,

path.  The concrete mount target belongs exclusively to the backend runtime
materialization boundary.

for the former recipe =target= field.  A recipe containing any absolute path
fails closed before descriptor projection.

*** Formal closure

Subject identity alone does not close authorization freshness.  The countermodel
=subjectBindingAlonePermitsRuntimeEpochSubstitution= keeps the projected subject
equal while choosing distinct authorization and execution epochs.  Therefore
the canonical closure reuses =RecoveryAuthorizationFresh= rather than inventing
sandbox-local freshness semantics.  =SandboxMaterializationCedarLifecycleFreshnessBridge=
projects the Cedar lifecycle commitment, authority, accountability,
responsibility scope, runtime epoch, and active fence token into one admitted
=RecoveryAuthorization=; it projects the sandbox execution receipt epoch and
fence into the corresponding =RecoveryExpectation=.  The theorem
=cedarLifecycleFreshnessBindsExecutionGeneration= then derives exact
lifecycle-to-execution epoch and fence equality.  The already-proved replay
closure carries the execution receipt equality onward to the replay window.

The freshness bridge is an existential proposition rather than a data-carrying
replacement object.  This keeps
=SandboxMaterializationAuthorizationSubjectBridge= proof-irrelevant while
requiring a real canonical recovery authorization witness.  Projection registry
selection, subject identity, provider provenance, lifecycle admission, and
replay generation remain distinct obligations connected by explicit equations.

That first closure was still insufficient: it did not bind the declared
backend, backend policy identity, or exact policy-resolved target.  Therefore

countermodel, adds the declared backend to =PortableRecipe=, and requires the

Exact policy binding is also not policy admission.  A stale authority context
can issue a receipt for the same policy identity and target, and the
backend-policy predicate alone still accepts the materialization.  Final
admissibility therefore also requires an authority-owned
=MaterializationAdmission= accepted at the exact current
=ReceiptValidationContext=, together with equality between the backend policy
identity and that context's =policySnapshotIdentity=.  This reuses the
project's existing freshness model rather than inventing a sandbox-local
notion of current authority.

The previous wording, “publish a receipt before execution”, was still unsafe.
It permitted a time-of-check/time-of-use gap: an admitted request and a later
=committed = true= flag did not prove that execution used the admitted target
or context.  =SandboxProfileMaterializationExecutionBindingClosure= now gives
the admission an explicit identity and requires the execution request and
execution receipt to consume that exact identity atomically with the expected
pre-state, current context, backend, policy, and resolved target.
That exact execution closure is still not an exactly-once consumer protocol. Two
stateless consumers can accept the same valid execution receipt because
acceptance alone does not publish shared completion state.
=SandboxProfileMaterializationReplayClosure= keeps this as a concrete
countermodel, then bridges the sandbox execution into the existing source-bound
replay and completion-publication owners. The bridge reuses the canonical
=PromotionTransactionAtomicity.TransactionId=,
=EffectDomainCoverage.EffectId=, runtime epoch, active fence token, and
completion result digest; it does not introduce sandbox-local numeric identity
types.

The replay bridge intentionally uses two ledger states. The pre-entry has
=completed = false= and =replaySafe = true=, so the selected step is =execute=.
The completion publication advances that exact entry to a post-entry with
=completed = true= and the exact completion receipt identity. Replanning against
the completed post-entry can only yield =suppressCompleted=, so the same effect
cannot legally remain an =execute= step. Treating one ledger value as both
pre-state and post-state would make the model contradictory and is forbidden by
the transition witness.

The replay bridge still exposed a separate authorization flaw: equality of the
transaction and effect identifiers does not constrain
=SourceBoundEffectExecutionEvent.ownerSubject=. Two different POO composition
owners can therefore satisfy an effect-only binding. The parameterized Lean
countermodel =effectOnlyBindingPermitsOwnerSubjectSubstitution= makes this
omission explicit.

The correction does not equate unrelated identities. A POO
=CompositionObjectSubject= is not a Cedar =AuthorizationSubject=, and a
completion =providerIdentity= is neither of them. Instead,
=SandboxMaterializationAuthorizationSubjectProjection= is an explicit contract
that projects the POO owner together with the exact materialization receipt and
current validation context into the Cedar subject. The projection must be
injective in the owner at that materialization and context. The existing Cedar
dual-engine subject bridge then proves that both production and reference
receipts carry that exact projected subject, while provider identity remains
separate completion provenance.

The proof is split at the actual assurance boundary. The dependency-light
=SandboxProfileMaterializationAuthorizationSubjectModel= contains the generic
owner-substitution counterexample, injective projection theorem, and
dual-engine subject equation; both Lean and AXLE verify that algebra. The
=SandboxProfileMaterializationAuthorizationSubjectClosure= then specializes
the model to the canonical POO, sandbox replay, and Cedar lifecycle types and
is checked by the full Lean aggregate. This split does not treat imported
project types as axioms and does not claim that an AXLE model receipt alone
verifies the Cedar implementation specialization.

Injectivity alone was still insufficient. Two different injective projection
functions can map the same owner, materialization, and context to different
Cedar subjects, and each local equality can appear closed. The new
=injectivityAlonePermitsProjectionSubstitution= theorem records that concrete
semantic-drift countermodel.

Projection semantics are therefore resolved through
=AuthorizationSubjectProjectionRegistry= at the exact
=ReceiptValidationContext.authorizationSnapshotIdentity=. One snapshot key can
resolve only one projection function, so two projections registered at that
same snapshot produce the same subject for every owner, materialization, and
context. The execution request and receipt already bind the whole expected and
observed =ReceiptValidationContext=; consequently this closure reuses the
canonical authorization snapshot identity instead of inventing another
projection version field.

That registry theorem is deliberately scoped to one registry instance. Two
unbound registries can reuse the same snapshot key and still resolve different
projection functions; =sameSnapshotAcrossUnboundRegistriesPermitsProjectionSubstitution=
keeps this second-order substitution as a countermodel. The canonical closure
therefore wraps the registry in =ReceiptAuthorityBindingClosure.AuthorityBoundNode=.
Its artifact is the complete current =ReceiptValidationContext=, and its exact
node binding is the registry used by subject projection. The context is not an
arbitrary parameter: =SandboxMaterializationLiveAuthorityContextBinding=
requires an authority-issued checkpoint attestation accepted by the trusted
watermark and binds the sandbox context to the live authority's current
checkpoint head. The projection lookup itself remains keyed by that context's
=authorizationSnapshotIdentity=. Because one deterministic authority
validation of one full-context artifact cannot return two registry bindings,
=deterministicAuthorityValidationRejectsRegistrySubstitution= closes registry
replacement without treating the registry as self-authenticating data.

This chain intentionally terminates at
=LiveCheckpointAttestationAuthority.currentCheckpoint= as the explicit trust
root. Lean proves consequences of its =issuanceSound= contract and the trusted
watermark; it does not recursively manufacture proof that the live authority
service itself is authentic. Runtime qualification must pin that authority and
publish its identity, generation, checkpoint lineage, and watermark evidence.

** 10.06.18.35 Runtime Summary Ownership
Sandbox profile projection is owned by the sandbox modules, not by =loop-engine= or the module-system base presentation layer. The concrete split is:
- =src/modules/sandbox-core/profile.ss= owns generic POO profile row resolution, inheritance, and merge operators;
- =src/modules/agent-sandbox/config.ss= owns user-facing POO profile recipes and projects those recipes into validated agent sandbox profiles;
- =src/modules/agent-sandbox/profile.ss= owns the contract-level runtime summary and handoff summary, including filesystem structure, diagnostics, validation status, and =runtime-executed #f= evidence.

Workflow, CI, and loop-engine features should depend on these summaries as data. They should not infer filesystem mounts, backend refs, or validation state from raw user rows.
=loop-engine= consumes sandbox summaries through a config-level catalog. If a loop declares =(profile . ci/build)= and the same config contributes a matching POO sandbox profile, the runtime manifest request carries =sandbox-runtime-summaries= and =sandbox-handoff-summaries=. If the profile ref is not visible in the config catalog, the manifest keeps =sandbox-unresolved-profile-refs= so an agent or doctor can report the missing profile without inventing a runtime policy.

** 10.06.18.40 POO Rule
The public profile value stays a POO object. Alists are presentation products only. This follows the gerbil-poo policy surface: macros are thin syntax bridges, while object/protocol slots keep semantic state. Future nono and cubeSandbox specialization should therefore extend the profile object family or runtime bridge projection instead of making user init rows parse backend-specific strings.

#+title: Publication-Domain Registry Checkpoint Recovery Closure
#+startup: overview

* Status

- State :: Proposed
- Scope :: durable registry checkpoint recovery, issued evidence, and indeterminate restart handling
- Depends on :: RFC 57, RFC 59

* Problem

RFC 59 rejects an earlier registry trust root after the current-head checkpoint
advances.  An in-memory checkpoint does not survive a verifier restart.

If the durable checkpoint position is =5= but restart reconstructs position
=0=, a registry root at position =3= changes from rejected to accepted.  The
lineage remains valid; the verifier has forgotten how far it already advanced.

Recovery must therefore bind the reconstructed position to the durable
checkpoint owned by the verifier runtime.

* Volatile reset countermodel

Let =p_min= be the minimum accepted lineage position:

#+begin_src typst
#align(center)[
  $
    not "PositionAccepted"(5, 3)
      and
    "PositionAccepted"(0, 3)
  $
]
#+end_src

Resetting only the local minimum changes the admission result without changing
the registry root, lineage, or evidence.

* Lineage-indexed recovery evidence

Recovery evidence is indexed by the actual lineage object =L=:

#+begin_src typst
#align(center)[
  $
    E_L = (p_"committed", p_"recovered")
  $
]
#+end_src

The lineage is a type-level input, not a self-reported identifier.  Evidence for
one lineage cannot be used as evidence for another lineage.

Valid recovery never lowers the checkpoint:

#+begin_src typst
#align(center)[
  $
    "ValidRecovery"(E_L)
      "iff"
    p_"committed" <= p_"recovered"
  $
]
#+end_src

Any position already below the committed checkpoint remains below the recovered
checkpoint.

* Self-reported committed position is insufficient

An evidence value may internally satisfy =0 <= 0= while the actual durable
checkpoint is =5=:

#+begin_src typst
#align(center)[
  $
    "ValidRecovery"((0, 0))
      and
    0 < p_"durable"
  $
]
#+end_src

Internal monotonicity does not establish that the claimed committed position is
the position persisted by the verifier.

* Committed-only issuance permits an unbounded recovered position

Binding only the committed position still permits an issued claim such as
=(committed=5, recovered=100)=:

#+begin_src typst
#align(center)[
  $
    p_"committed" = p_"durable"
      and
    p_"committed" <= p_"recovered"
      and
    p_"recovered" > p_"authority-head"
  $
]
#+end_src

The recovered position must therefore be bound to a checkpoint owned by the
same recovery authority.  Monotonicity supplies a lower bound; authority-owned
current-head evidence supplies the upper interpretation boundary.

* Durable recovery authority

For a fixed lineage =L=, the verifier runtime owns a durable recovery authority
=A_L=.  The authority owns both the durable committed position and the recovered
checkpoint.  Issued evidence must bind both positions:

#+begin_src typst
#align(center)[
  $
    "Issued"_(A_L)(E_L)
      "implies"
    p_"committed"(E_L) = p_"durable"(A_L)
      and
    p_"recovered"(E_L) = p_"head"(A_L)
  $
]
#+end_src

Together with valid recovery:

#+begin_src typst
#align(center)[
  $
    "Issued"_(A_L)(E_L)
      and
    "ValidRecovery"(E_L)
      "implies"
    p_"durable"(A_L) <= p_"recovered"(E_L)
  $
]
#+end_src

Thus every position below the durable checkpoint is rejected after
authority-issued recovery.

* Indeterminate recovery is fail closed

Recovery has two outcomes:

- =Recovered(E_L)= carries authority-issued, valid recovery evidence;
- =Indeterminate= carries no recovered checkpoint.

#+begin_src typst
#align(center)[
  $
    "RecoveryOutcome" = "Indeterminate"
      "implies"
    not "RegistryCheckpointAdmitted"
  $
]
#+end_src

Missing, corrupt, or ambiguous durable state cannot be converted into position
zero.

* Ownership boundary

- The verifier runtime owns the durable committed checkpoint.
- The recovery authority owns the exact recovered current-head checkpoint.
- Recovery evidence is indexed by the actual RFC 59 lineage object.
- The durable recovery authority owns evidence issuance.
- Evidence cannot self-select the durable committed position.
- An indeterminate recovery outcome cannot admit any registry checkpoint.

* State machine

#+begin_src mermaid
stateDiagram-v2
  [*] --> DurableCheckpointLoaded: read persisted registry checkpoint
  DurableCheckpointLoaded --> RecoveryEvidenceChecked: bind evidence to actual lineage
  DurableCheckpointLoaded --> Indeterminate: state missing corrupt or ambiguous
  RecoveryEvidenceChecked --> AuthorityBindingChecked: claimed committed position loaded
  AuthorityBindingChecked --> RecoveryAccepted: committed equals durable and recovered equals authority head
  AuthorityBindingChecked --> RecoveryRejected: either position is self-reported or unbound
  RecoveryAccepted --> KnownRollbackRejected: prior rejected positions remain rejected
  Indeterminate --> AdmissionRejected: no recovered checkpoint exists
  RecoveryRejected --> [*]: require durable-state repair
  AdmissionRejected --> [*]: explicit reconciliation required
  KnownRollbackRejected --> [*]: continue live registry validation
#+end_src

* Architectural consequence

Registry checkpoint recovery is an authority operation over one actual lineage,
not deserialization of two caller-owned numbers.  Durable binding and an
explicit indeterminate state preserve the RFC 59 current-head invariant across
process restart.

#+title: Terminal Projection Macro Governance
#+author: POO Flow
#+language: en

* Status

Accepted.

* Context

POO Flow uses native =gerbil-poo= objects, prototype refinement, slot
operators, and pure functions as its semantic foundation.  Some terminal
receipts and presentation surfaces repeat a small fixed pattern: evaluate
explicit local bindings once, construct ordered rows with fixed keys, and
return an external representation.

Gerbil hygienic macros can remove that mechanical repetition.  They must not
become an alternative object model, configuration DSL, recovery language, or
hidden semantic owner.

The current =defpoo-module-final-projection= declaration delegates to
=defpoo-static-receipt-projection=.  The lower macro validates duplicate
arguments, bindings, and field keys at expansion time and produces an ordinary
Gerbil procedure.  This is an admissible bounded projection use of macros.

* Decision

A macro may project already-defined POO semantics, but it may not own, conceal,
or enlarge those semantics.

Terminal projection macros are constrained internal declarations.  Their only
responsibility is to lower a fixed, explicit external shape into an ordinary
pure projection procedure.

They do not add a public composition abstraction.  Native POO objects,
prototype refinement, slot operators, and pure functions remain the only
semantic extension foundation.

* Projection relationship

* Admission rules

A terminal projection macro is admissible only when all of the following are
true:

- [X] The projected semantics already exist in native POO values or pure
  functions.
- [X] The expansion is bounded by the declaration size.
- [X] The expansion produces an ordinary Gerbil procedure.
- [X] Introduced identifiers and caller bindings remain hygienic.
- [X] Field keys and their output order are explicit at the declaration site.
- [X] Local binding expressions are evaluated once.
- [X] Duplicate arguments, local bindings, and field keys fail during
  expansion.
- [X] The result is confined to an inspection, receipt, presentation, or
  serialization boundary.
- [X] The declaration owns no runtime effect, resolver, fixed point, recovery
  action, capability grant, or policy decision.

If any item is false, the abstraction MUST be expressed as a native POO object,
prototype refinement, slot operator, or pure function instead.

* Required boundaries

Terminal projection macros MUST:

- keep the complete projected field set visible at the declaration site;
- preserve deterministic field order;
- expose guard and fallback behavior explicitly when either is present;
- evaluate already-authorized values without widening their visibility;
- remain removable without changing the semantic object model;
- preserve source mapping for expansion-time diagnostics.

Terminal projection macros MUST NOT:

- accept dynamic field declarations that form an ad hoc record or alist DSL;
- construct or mutate Module, ProfileBundle, capability, or policy semantics;
- select profiles or resolve imports;
- enter lazy global fixed-point evaluation;
- capture or resume continuations;
- execute retry, substitution, resumption, abort, telemetry, or runtime effects;
- turn an external receipt back into ordinary Module composition input;
- hide provider selection, package management, build, or distribution behavior;
- become a general public macro family.

* Relationship to public syntax

The bounded public macros =use-composition= and =use-module= are governed
separately as hygienic projections onto ordinary POO-native and functional
semantics.

Terminal receipt macros are internal implementation tools.  Their existence
does not justify another public macro, another configuration layer, or a
macro-shaped advanced extension interface.  Advanced extensions continue to
enter =compose profiles= as first-class POO values.

* Relationship to observability

An authoritative POO-native =ObservationEvent= may be projected into a strict
doctor, CLI, receipt, or serialization value through a conforming terminal
projection procedure.

The projected struct or alist is non-authoritative.  It cannot become recovery
evidence, capability authority, cache identity, Module configuration, or an
input to =compose profiles=.

* Non-goals

- Replacing native =gerbil-poo= objects or prototype composition.
- Defining a dynamic alist, record, patch, or configuration DSL.
- Moving semantic validation from Contracts into macros.
- Encoding runtime coordination in macro expansion.
- Expanding the public macro surface.
- Defining an implementation schedule.

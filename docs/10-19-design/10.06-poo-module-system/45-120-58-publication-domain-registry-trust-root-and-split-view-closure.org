#+title: Publication-Domain Registry Trust Root and Split-View Closure
#+startup: overview

* Status

- State :: Proposed
- Scope :: publication-domain registry canonicality, verifier trust roots, and split-registry rejection
- Depends on :: RFC 55, RFC 57

* Problem

RFC 57 makes publication-domain identifiers injective inside one registered
descriptor set.  That property is local to the selected registry.

Two registries can each satisfy local injectivity while assigning the same
domain identifier to different descriptors.  A verifier that accepts whichever
registry accompanies the evidence therefore permits a registry split view.

The missing invariant is not another identifier comparison.  The verifier must
pin the registry object through a trust root, and all admitted evidence must be
indexed by that same object.

* Local injectivity does not establish canonicality

Let =R_l= and =R_r= each register exactly one descriptor.  Both registries are
injective, but they can disagree across their boundary:

#+begin_src typst
#align(center)[
  $
    "Injective"(R_l)
      and
    "Injective"(R_r)
      and
    "Registered"(R_l, D_l)
      and
    "Registered"(R_r, D_r)
      and
    "id"(D_l) = "id"(D_r)
      and
    D_l != D_r
  $
]
#+end_src

No theorem quantified over only one registry can reject this countermodel.
Calling both registries canonical does not add a mathematical constraint.

* Verifier-pinned registry trust root

The trust root is a verifier input:

#+begin_src typst
#align(center)[
  $
    T_R = (A_R, S_R, R)
  $
]
#+end_src

where:

- =A_R= identifies the authority responsible for selecting the registry;
- =S_R= identifies the semantic contract of the selected registry;
- =R= is the actual publication-domain registry object.

The numeric labels do not substitute for =R=.  They identify its authority and
contract for receipts and observability; evidence admission is indexed by the
actual pinned object.

* Trust-root-bound evidence

For a fixed trust root =T_R=, checkpoint-watermark evidence must carry
registered evidence from exactly =registry(T_R)=:

#+begin_src typst
#align(center)[
  $
    "TrustRootBound"(T_R, E)
      "implies"
    "RegisteredIn"("registry"(T_R), "descriptor"(E))
  $
]
#+end_src

The RFC 57 authority binding remains mandatory:

#+begin_src typst
#align(center)[
  $
    "TrustRootBound"(T_R, E)
      "implies"
    A("descriptor"(E)) = A("watermark"(E))
  $
]
#+end_src

* Split-view rejection theorem

Two pieces of evidence indexed by the same trust root and carrying the same
publication-domain identifier resolve to the same descriptor:

#+begin_src typst
#align(center)[
  $
    "TrustRootBound"(T_R, E_l)
      and
    "TrustRootBound"(T_R, E_r)
      and
    D("watermark"(E_l)) = D("watermark"(E_r))
      "implies"
    "descriptor"(E_l) = "descriptor"(E_r)
  $
]
#+end_src

This theorem is stronger than local identifier equality because both descriptor
registrations are interpreted by the same injective registry object.

* Ownership boundary

- The verifier configuration owns the pinned registry trust root.
- The registry authority owns publication and replacement of the registry object.
- RFC 57 owns descriptor registration and watermark-to-descriptor authority binding.
- A receipt may name the registry authority and semantic contract, but it cannot select a replacement registry.
- Missing, ambiguous, or unpinned registry state is an admission failure.

* State machine

#+begin_src mermaid
stateDiagram-v2
  [*] --> TrustRootLoaded: load verifier-pinned registry object
  TrustRootLoaded --> RegistryEvidenceChecked: evidence references the pinned registry
  TrustRootLoaded --> AdmissionRejected: trust root missing or ambiguous
  RegistryEvidenceChecked --> AuthorityBindingChecked: descriptor is registered under pinned object
  RegistryEvidenceChecked --> SplitViewRejected: evidence selects another registry
  AuthorityBindingChecked --> AdmissionAccepted: domain and authority bindings match
  AuthorityBindingChecked --> AdmissionRejected: descriptor authority differs from watermark
  SplitViewRejected --> [*]: require registry reconciliation
  AdmissionRejected --> [*]: fail closed
  AdmissionAccepted --> [*]: continue live checkpoint validation
#+end_src

* Architectural consequence

Canonicality is not a property that each registry may assert independently.
It is a relation between admitted evidence and one verifier-pinned registry
object.  Local injectivity becomes globally useful only after that shared
interpretation boundary is explicit.

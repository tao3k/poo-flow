#+title: Effect DAG, Partial Commit, Compensation, and Atomicity
#+subtitle: Stable handoff frontiers, conflict scopes, authoritative outcomes, and non-fictional rollback
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative multi-effect execution protocol
- Semantic core :: Pure POO effect graphs, functional composition, and explicit runtime handoff
- Related module :: =45-55-effect-intent-stabilization-runtime-handoff-and-reconciliation.org=

This module defines how multiple stable effect intents form a pure dependency graph. It prevents source order, hash order, and worker timing from becoming business commit semantics, and it treats partial commit and compensation as first-class outcomes.

* Core decision

#+begin_quote
Multiple EffectIntent values form a pure labeled effect DAG. Only a stable ready frontier may cross the runtime handoff boundary. Parallel execution requires explicit conflict-scope or commutativity evidence. Non-atomic execution admits PartialCommitOutcome. Compensation is a new fallible effect and never erases commit history.
#+end_quote

* Typst formalization: ready frontier, partial commit, and atomicity

Readiness and parallel safety are separate proof obligations.  Every frontier
member must be semantically stable with committed predecessors, while every
distinct pair must additionally have conflict-scope or commutativity evidence.

#+begin_src typst
$
  "Ready"(e, s) & equiv
    "Planned"(e)
    and "SemanticStable"(e)
    and "Materialized"(e) \
  & quad and
    forall p, quad D(e, p) =>
      "Outcome"(s, p) = "Committed" \
  & quad and "RuntimeCapabilityValidated"(e)
    and not "InUnstableSemanticScc"(e) \
  "StableFrontier"(F, s) & equiv
    forall e in F, quad "Ready"(e, s) \
  "ParallelSafe"(F) & equiv
    forall a, b in F, quad a != b =>
      "ConflictScopeDisjoint"(a, b) or "Commutes"(a, b) \
  "BatchHandoff"(F) & =>
    "StableFrontier"(F, s)
    and "ParallelSafe"(F) \
  & quad and
    forall e in F, quad "AuthorizedStableIntentHandoff"(e)
$
#+end_src

A non-atomic execution may preserve both a committed effect and a failed,
uncommitted effect.  This is a direct counterexample to all-or-nothing.

#+begin_src typst
$
  "AllOrNothing"(P, H) & equiv
    (forall e in P, quad "Committed"(H, e))
    or (forall e in P, quad not "Committed"(H, e)) \
  "PartialCommit"(P, H) & equiv
    exists c, f in P, quad
      "Committed"(H, c)
      and not "Committed"(H, f) \
  "PartialCommit"(P, H) & => not "AllOrNothing"(P, H) \
  "Compensate"(c) &= c_"comp" \
  "CompensationIsNew" & equiv c_"comp" != c \
  "CompensationOutcome" &=
    "Committed" + "Failed" \
  "Compensate"(c) & =>
    "CommittedHistoryStillRecords"(c) \
  "AtomicClaim"(P) & =>
    exists g, quad "RuntimeAtomicityGuarantee"(g)
      and "Covers"(g, P)
$
#+end_src

* Pure effect plan

A pure =EffectPlan= is conceptually identified by:

#+begin_src text
EffectPlanIdentity =
H(
  semantic generation identity,
  stable EffectIntent identities,
  labeled dependency edges,
  commit-policy identity,
  conflict-scope projections
)
#+end_src

Edges express semantic relationships such as:

- outcome dependency;
- commit-before dependency;
- materialization dependency;
- authorization barrier;
- external-resource conflict scope;
- compensation relationship.

The plan contains no:

- live capability token;
- adapter instance;
- worker assignment;
- mutable node status;
- continuation or recovery portal;
- retry counter;
- wall-clock schedule.

#+begin_src mermaid
flowchart LR
    A["Stable EffectIntent A"] -->|"its outcome is required by B"| B["EffectIntent B"]
    B -->|"must commit before C"| C["Commit EffectIntent C"]
    D["Independent materialization D"] -->|"has no shared conflict scope"| F["Parallel-ready frontier"]
    E["Independent materialization E"] -->|"has no shared conflict scope"| F
    C -->|"register an explicit compensation relationship"| X["CompensationIntent for C"]
#+end_src

Directional edges are preserved. They are not normalized as an unordered set.

* Observation boundary

An observation outcome terminates the current semantic plan boundary:

#+begin_src text
generation G
-> observation intent
-> execute observation
-> content-address observation artifact
-> derive generation G+1
-> recompute and stabilize downstream intents
#+end_src

A commit intent depending on an unknown observation outcome cannot be considered stable in generation =G=.

The effect plan exposes only the stable handoff frontier for the current generation. Downstream intent identities are recomputed after the observation enters =G+1=.

* Stable ready frontier

An intent enters a ready frontier only when:

- its semantic definition is stable;
- all pure dependency projections are satisfied;
- required materialization artifacts exist;
- predecessor commit outcomes are authoritatively known;
- no dependency has an unresolved unknown outcome;
- effect conflict scopes permit execution;
- runtime capability can be validated at handoff;
- the intent is outside an unstable semantic SCC.

Ready-frontier identity is a pure projection. Worker and schedule assignment remain operational.

* Parallel-execution safety

Two ready intents may execute in parallel only when at least one of the following is proven:

- no dependency edge and no overlapping external conflict scope;
- the adapter protocol declares the operations commutative;
- one explicit transaction protocol supports their concurrent execution.

When potentially conflicting commits have neither an order edge nor a commutativity proof, plan validation produces =EffectOrderingConflict=.

The runtime must not infer business order from:

- source order;
- operand order;
- identity or digest sorting;
- worker availability;
- map iteration order;
- observed scheduling order.

#+begin_src mermaid
flowchart LR
    A["Ready intent A"] -->|"conflict scope resource-X"| V["Parallel-safety validation"]
    B["Ready intent B"] -->|"conflict scope resource-X"| V
    V -->|"explicit order edge exists"| S["Execute in declared order"]
    V -->|"commutativity or transaction proof exists"| P["Execute in parallel"]
    V -->|"no proof and no order edge"| F["EffectOrderingConflict"]
#+end_src

* Effect dependency cycles

Pure materialization dependencies may participate in semantic fixed-point analysis.

Commit-order cycles cannot be solved by executing effects:

#+begin_src text
A commits before B
B commits before A
#+end_src

This produces =CommitDependencyCycle= before any external commit.

Repeated observation-generation transitions are bounded by generation and recovery budgets. An unbounded sequence:

#+begin_src text
observe
-> new generation
-> observe
-> new generation
#+end_src

fails closed with cycle and budget evidence.

* Atomicity boundary

POO Flow reports atomic commit only when:

- one adapter exposes an explicit transaction protocol;
- every included effect belongs to the adapter's transaction scope;
- prepare, commit, abort, and authoritative receipt semantics are declared;
- the adapter protocol identity participates in the plan;
- runtime evidence proves the transaction outcome.

The graph itself does not create atomicity.

Across independent external systems:

- no distributed transaction is assumed;
- a successful call sequence is not called exactly-once;
- two-phase preparation may still produce an in-doubt outcome;
- recovery follows reconciliation evidence rather than a fictional rollback.

* Partial commit outcome

A non-atomic plan may contain:

#+begin_src text
confirmed committed nodes
confirmed not-committed nodes
unknown nodes
failed nodes
blocked or not-attempted nodes
completed materializations
#+end_src

These form pure =PartialCommitOutcome= evidence.

#+begin_src mermaid
flowchart LR
    P["Stable commit frontier"] -->|"A receives authoritative success"| A["A committed"]
    P -->|"B receives authoritative failure"| B["B not committed"]
    P -->|"C loses authoritative response"| C["C unknown"]
    B -->|"block dependent D"| D["D not attempted"]
    A -->|"remain in external history"| R["PartialCommitOutcome"]
    B -->|"record confirmed failure"| R
    C -->|"require reconciliation"| R
    D -->|"record dependency block"| R
#+end_src

The plan is not summarized as one undifferentiated failure after an external subset has committed.

* Compensation intent

Compensation is a new =CompensationIntent= that:

- references the original effect identity and authoritative outcome;
- declares runtime capability requirements;
- declares idempotency policy;
- declares conflict scope;
- declares outcome contract;
- has its own anchor and revision identity;
- may fail or produce unknown outcome;
- produces an independent receipt.

Compensation preserves the original commit receipt.

The final history is:

#+begin_src text
original commit occurred
+ compensation later occurred
#+end_src

It is not:

#+begin_src text
original commit never occurred
#+end_src

* Compensation ordering

Reverse dependency order is a common policy but not an automatic law.

The compensation graph or adapter protocol declares:

- which committed effects have compensation;
- compensation dependencies;
- safe parallel compensation;
- irreversible effects;
- required observation or reconciliation barriers.

The runtime does not reverse the original DAG mechanically when no compensation semantics are declared.

* Compensation authority

Automatic compensation requires:

- an explicit plan policy permitting compensation;
- a stable compensation intent;
- dedicated compensation authority in the live context;
- authoritative original outcome evidence;
- compatible idempotency and reconciliation policy;
- scope contained within delegated authority.

Ordinary runtime-execution authority does not automatically include compensation authority.

An unauthorized or out-of-scope compensation attempt fails closed and does not modify original outcome evidence.

* Partial-commit recovery

Partial-commit handling separates:

1. Reconciliation :: Establish the authoritative state of unknown nodes.
2. Resume remaining plan :: Retry only confirmed not-committed nodes whose policy allows retry.
3. Compensation :: Execute new compensation intents for confirmed committed nodes.

Each action has new operational execution identity and receipts.

When resulting external state becomes semantic input:

#+begin_src text
partial commit or compensation
-> authoritative observation
-> content-addressed artifact
-> new semantic generation
#+end_src

The old semantic generation is not mutated to match external reality.

* Scheduling identity

Effect-plan semantic identity includes:

- intent identities;
- semantic edges;
- conflict scopes;
- transaction and commit policy.

It excludes:

- worker assignment;
- thread count;
- start time;
- retry timing;
- safe parallel schedule selected at runtime.

Different safe operational traces converge to the same canonical outcome classification when they establish the same authoritative external outcomes.

* Cache boundaries

Pure cacheable projections include:

- effect plan;
- stable frontier;
- parallel-safety proof;
- conflict-scope projection;
- authoritative outcome;
- partial-commit projection;
- compensation plan;
- reconciliation receipt.

Live worker state, capability tokens, active transaction handles, and mutable node status remain operational.

A commit receipt is evidence of an external action. It is not a reusable semantic value or future authority.

* Functional and POO composition

The intended route is:

#+begin_src text
EffectIntent POO values
+ functional dependency combinators
-> pure EffectPlan
-> explicit runtime handoff
#+end_src

POO provides identity, prototype extension, capability requirements, contracts, policies, and evidence. Funflow may provide functional graph composition after verification against its real interface.

This RFC does not create a transaction or compensation DSL.

* Evidence requirements

Multi-effect evidence records:

- effect-plan identity;
- intent identities and labeled edges;
- stable-ready frontier;
- conflict scopes and parallel-safety proof;
- transaction protocol and adapter scope;
- node authorization and execution attempts;
- authoritative committed, not-committed, failed, unknown, and blocked outcomes;
- =PartialCommitOutcome=;
- reconciliation actions;
- compensation intent, authorization, and outcome;
- successor observation and generation identities;
- operational schedule without treating it as business semantics.

* Implementation checklist

- [ ] Define identity-addressed pure =EffectPlan= objects.
- [ ] Preserve labeled directional dependency edges.
- [ ] Expose only stable current-generation handoff frontiers.
- [ ] Recompute downstream intents after observation-generated transitions.
- [ ] Define external conflict-scope projection.
- [ ] Require order, commutativity, or transaction proof before parallel commits.
- [ ] Fail closed on ambiguous ordering and commit-dependency cycles.
- [ ] Report atomicity only under an explicit adapter transaction protocol.
- [ ] Define first-class =PartialCommitOutcome=.
- [ ] Reconcile unknown nodes before retry or compensation.
- [ ] Define identity-addressed =CompensationIntent=.
- [ ] Preserve original commit evidence after compensation.
- [ ] Require dedicated compensation authority.
- [ ] Represent compensation order through explicit graph or adapter protocol.
- [ ] Keep worker scheduling out of effect-plan semantic identity.
- [ ] Generate plan, frontier, outcome, reconciliation, and compensation evidence.
- [ ] Validate final functional graph operations against real Funflow and =gerbil-poo= primitives.

* Non-goals

- Do not use a list, source order, digest order, or worker timing as commit semantics.
- Do not execute a commit intent depending on an unknown observation.
- Do not resolve a commit cycle by performing external effects.
- Do not claim atomicity or exactly-once behavior without adapter guarantees.
- Do not summarize a partial commit as one ordinary failure.
- Do not describe compensation as erasing history or as guaranteed rollback.
- Do not infer compensation order by mechanically reversing a DAG.
- Do not create a transaction registry, compensation DSL, or raw callback graph.

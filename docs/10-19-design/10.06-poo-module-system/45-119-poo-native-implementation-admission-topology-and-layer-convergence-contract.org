#+title: POO-Native Implementation Admission Topology and Layer Convergence Contract
#+author: POO Flow
#+language: en

* Status

This RFC is an accepted architecture contract.

It defines semantic admission dependencies.  It is not an implementation plan,
release schedule, compatibility migration, package lock, or build pipeline.
No implementation is admitted by this document alone.

* Scope

This RFC owns:

- the evidence boundary between upstream =gerbil-poo= operations and
  project-owned adapters;
- the admission dependency from upstream correspondence to pure
  =poo-flow-core= semantics;
- the two post-core branches for runtime/deployment adapters and
  application-owned Profile families;
- the convergence gate for operator and deployment integration;
- the exclusion of package management, development harnesses, and build systems
  from the public POO composition semantics.

It does not own:

- upstream =gerbil-poo= object or prototype semantics;
- a second POO implementation;
- domain Profiles owned by =wendao-episteme=;
- application deployment policy;
- runtime effect execution;
- =gerbil.pkg= dependency resolution;
- GSLPH policy-harness or building/testing-framework implementation;
- Gerbil-Bazel or Nix build and environment behavior.

* Central decision

Implementation admission is a dependency graph, not a sequence of calendar
phases.

The upstream correspondence gate must close before a project adapter or core
semantic object is admitted.  Pure =poo-flow-core= semantics must close before
either runtime execution or application composition can claim integration
readiness.

After the pure core gate:

- runtime/deployment adapters and pure application Profile families may be
  investigated independently;
- neither branch may claim end-to-end closure alone;
- operator and deployment integration is admitted only after both branches
  converge through explicit semantic values, capabilities, intents, and
  receipts.

* Gate U: upstream operation correspondence

The admitted upstream operation families are owned by =gerbil-poo=:

- object representation and lifecycle;
- slot projection, update, and deletion;
- prototype extension;
- composition and mix behavior;
- delegation and =super= behavior;
- precedence.

This RFC does not invent concrete operator or macro names.  Exact operator
identity and semantics must be proven from the pinned upstream source before a
project adapter is admitted.

The upstream source identity is:

#+begin_example
github.com/mighty-gerbils/gerbil-poo@1c3225637525400341a09e958296962c10184ead
#+end_example

The POO concept prototype remains:

#+begin_example
github.com/metareflection/poof@a07a6841d3fde46159f990065cde55b811f1f680
#+end_example

* Gate C: pure core semantics

=poo-flow-core= may implement only project-owned semantic contracts on top of
the admitted upstream operations.

This gate includes:

- Module-domain conformance and reachable ProfileBundle responsibilities;
- pure =compose= behavior and the first-class =profiles= strategy;
- immutable debug query, proposal, context, outcome, and lineage values;
- recovery admission and pure recovery-intent projection;
- generic identity, export, conflict, and provenance contracts;
- =ResolvedCompositionReceipt= as semantic evidence, not package or runtime
  evidence.

Core admission requires deterministic evaluation, explicit inputs, structured
conditions, bounded observation, and no hidden runtime authority.

* Gate R: runtime and deployment adapters

Runtime/deployment adapters may consume admitted core values and capabilities.
They own:

- environment, filesystem, time, entropy, and secret observation;
- durable claims and continuation-fence execution;
- effect-intent stabilization and runtime handoff;
- execution, cleanup, reconciliation, and publication receipts;
- generation pinning, active-head transition, rollback, and operator commit.

They do not own the POO object model, pure composition, domain Profiles, or a
public composition macro.

* Gate A: application Profile families

The final application owns:

- its base-profile prototype and derived Profile family;
- typed Profile contributions and withdrawals;
- explicit deployment-mode selection;
- the final composition identity;
- application authorization policy.

Application Profiles remain pure.  Runtime values enter through admitted
capabilities and deployment references, never ambient evaluation or host
conditionals inside =compose=.

=wendao-episteme= owns only its domain Modules, Profiles, identities, and
exports.  It does not own application deployment policy or the generic
composition engine.

* Gate O: convergence

Operator and deployment integration is admitted only when:

- the application branch supplies an immutable candidate and authorization
  policy;
- the runtime branch supplies admitted query, simulation, claim, commit, and
  receipt capabilities;
- both branches consume the same pure core identity and composition semantics;
- failures remain structured and observable;
- no publication syntax enters =use-composition=;
- no runtime state is reinterpreted as Profile semantics.

The ordinary interface remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

Advanced extension remains native POO object and prototype extension.  This
topology does not add a public admission DSL or a new user macro.

* Tooling boundary

=gerbil.pkg= manages Gerbil package dependencies.  It does not project semantic
composition evidence.

GSLPH is a development dependency for policy harnesses and building/testing
framework behavior.  It may execute admission checks, but it does not own or
provide product semantics.

Gerbil-Bazel is a build system.  Nix owns environment, build, and deployment
materialization concerns.  Neither belongs to the POO semantic layer.

* Admission checklist

** Upstream correspondence

- [ ] Pin and verify the upstream =gerbil-poo= revision through =gerbil.pkg=.
- [ ] Produce exact correspondence evidence for every upstream operation used
  by the Module/Profile implementation.
- [ ] Prove that no project adapter introduces a second object API, hidden
  registry, raw alist facade, or ad hoc patch language.
- [ ] Correct the remaining normative =user-composition= term in RFC 45-93 to
  =use-composition= once exact parser-owned source projection is available.

** Pure core

- [ ] Admit the Module-domain prototype body against upstream operations.
- [ ] Admit pure ProfileBundle closure and =compose profiles= behavior.
- [ ] Admit immutable debug, outcome, resumption, recovery-intent, and semantic
  receipt objects.
- [ ] Prove deterministic inputs, budget behavior, cache isolation, structured
  conditions, and macro-governance compliance.

** Runtime and application branches

- [ ] Admit capability-scoped runtime/deployment adapters.
- [ ] Admit application-owned pure Profile families independently of runtime
  observation.
- [ ] Verify that =wendao-episteme= remains a domain package and does not absorb
  final-application or runtime ownership.

** Convergence

- [ ] Admit query, diff, simulation, proposal, authorization, and conditional
  commit through adapter values rather than composition syntax.
- [ ] Verify execution, reconciliation, publication, and rollback receipts.
- [ ] Run GSLPH development checks without introducing a product dependency.
- [ ] Keep Gerbil-Bazel, Nix, and =gerbil.pkg= evidence outside the semantic
  composition receipt.

* Rejected alternatives

- Treating the admission topology as a linear project schedule.
- Reimplementing upstream POO operations in =poo-flow-core=.
- Naming concrete upstream operators before correspondence evidence exists.
- Letting runtime adapters define Profile or composition semantics.
- Letting application Profiles observe ambient environment state.
- Encoding admission, publication, or recovery as new public macros.
- Treating GSLPH, Gerbil-Bazel, Nix, or =gerbil.pkg= as semantic layers.
- Claiming end-to-end closure from only the runtime branch or application
  branch.

* Successor contract

The next RFC may select the first implementation-entry contract only after it
identifies:

- the exact upstream =gerbil-poo= operators involved;
- the project-owned POO object or adapter being admitted;
- the pure semantic inputs and outputs;
- the structured failure and observation boundary;
- the focused development evidence required for admission.

It must not contain implementation code, a release schedule, or compatibility
migration policy.

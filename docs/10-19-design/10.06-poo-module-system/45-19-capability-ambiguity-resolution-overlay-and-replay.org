#+title: Capability Ambiguity, Resolution Overlay, and Replay
#+startup: overview

* Status

Normative RFC.

* Scope

This RFC owns Capability collision classification, continuable ambiguity
conditions, boundary-local resolution overlays, and deterministic evidence
projection.

* Capability collision classes

Textual precedence applies only to refinements in the same POO prototype
lineage.  Unrelated identities providing the same singleton Capability produce
a structured condition.  Multiple providers aggregate only when the Capability
contract explicitly declares POO-native multiplicity semantics.  Implicit
alist merging and list concatenation are forbidden.

* Continuable resolution

Unknown or duplicate modifier syntax fails during macro expansion.  Semantic
provider ambiguity appears when the affected Capability is first demanded by
the lazy fixed point.

The condition carries Capability identity, candidate provider identities,
prototype lineages, and the demand trace.  It never resolves through provider
order, search order, or an implicit first-provider rule.  Continuation requires
an explicit POO resolution Profile and starts a successor demand generation;
the suspended evaluation cell remains immutable evidence.

* Resolution Profile and proof

A resolution Profile is a condition-specific higher-order POO object.  It
operates on already discovered Capability and provider contribution identities;
it does not perform provider search.

The Profile imports the structured ambiguity condition, its immutable candidate
set, and boundary resolution authority.  It provides a POO-native resolution
proof or contribution.  It is not an alist, string mapping, numeric priority,
or raw candidate callback.

The proof binds the original condition identity, Capability identity, candidate
contribution identities, prototype lineage, and parent generation.  A successor
generation rediscovers and revalidates the candidate set before accepting the
proof.  Changed candidate identity or lineage raises a stale-resolution
condition rather than applying an obsolete decision.

A generic permanent policy is an ordinary Profile in canonical composition.
A continuation injects the condition-specific resolution Profile instance
produced by that policy.  Evidence records policy provenance and authority
receipt without serializing the condition continuation.

* Boundary resolution authority

An ambiguity condition carries evidence and no resolution authority.  Authority
is a separate POO Capability provided by the owning demand boundary and
imported explicitly by the resolution Profile.

Authority scope binds boundary identity, Capability identity, the permitted
lineage or candidate domain, and authority generation.  A child may resolve
only ambiguity owned within its boundary.  Ambiguity crossing parent and child
edges is elevated to the smallest common boundary that owns every involved
edge.

Authority may be explicitly attenuated or delegated; a child cannot enlarge
its scope.  A resolution proof records authority identity and generation.  The
successor generation revalidates that the authority remains active and its
scope still matches.

Cancellation, revocation, or generation invalidation makes the old authority
and proof stale.  Failure produces a structured unauthorized or stale
condition and never falls back to provider order.  There is no ambient global
resolution authority or administrator priority.

* Singleton resolution disposition

A condition-specific singleton resolution proof selects exactly one
contribution identity from the immutable candidate set.  Candidate collection
order has no semantics.  Selection uses neither array index, path, display
name, nor numeric priority.

The successor generation validates candidate membership, prototype lineage,
resolution authority, and generation.  Selecting zero candidates, multiple
candidates, a synthetic identity, or a stale candidate produces an invalid
resolution condition.

The proof cannot synthesize a provider value, convert a singleton contract into
a multi-provider contract, or merge candidates.  If no candidate is acceptable,
the policy declines resolution; it cannot return an empty or incomplete value
as successful resolution.

A new provider or aggregation contract enters through an ordinary Profile
contribution in canonical composition and is rediscovered by a new generation.
A permanent policy may produce condition-specific singleton proofs, but each
proof is revalidated independently.

* Resolution disposition and cancellation separation

A condition-specific resolver has two legal dispositions:

#+begin_src text
select(candidate-contribution-identity)
decline
#+end_src

=select= produces a proof subject to successor validation.  =decline= produces
no proof, no empty value, and no successful resolution.  It preserves the
original condition identity, candidate set, and suspended evaluation cell, then
propagates the condition to the outer owning Scheme condition boundary.

If no resolver accepts the condition, it remains unhandled.  Resolution
authority does not imply demand-cancellation authority.  Abort or cancellation
requires a separate boundary-owned Capability and produces its own successor
generation and receipt under
[[file:45-12-structured-cancellation-boundary-generations.org][the structured
cancellation contract]].

Any resolver chain is explicit POO composition.  Candidate order and a global
handler registry do not define resolver precedence.

* Explicit resolver lineage

A resolver chain is an explicit POO prototype lineage rather than an iterated
handler list.  Each resolver contribution receives the predecessor resolution
state.

When the predecessor state is unresolved, a resolver may decline or select.
Decline passes the same unresolved state to the next contribution.  Once a
valid selected state is produced, it becomes stable and later resolvers are not
demanded.

This ordering comes from canonical Profile composition, never candidate
discovery order.  Evidence records the resolver contribution identity that
produced selection.

Independent resolver proofs without one shared predecessor lineage produce a
resolver-ambiguity condition.  Load order cannot choose between them.  A
condition-specific overlay resolver must be inserted explicitly into the
resolver lineage and is never registered in a global handler table.

Resolvers remain pure POO objects.  External consultation or approval crosses
the explicit suspension and handoff contract in
[[file:45-09-effect-intent-suspension-handoff-reinjection.org][the effect-intent
handoff RFC]].

* Suspended resolver evaluation

Suspension is an evaluation state before a resolver produces its final
=select= or =decline= disposition.  It is not a third disposition.

When external consultation is required, the pure resolver produces a POO effect
intent and suspends its demand.  Because resolver ordering is explicit, later
resolver contributions are not demanded while the current contribution is
suspended.

The intent records condition identity, candidate contribution identities,
resolver contribution identity, generation, and requested authority scope.  It
does not perform network, UI, or approval effects and does not serialize the
continuation.

The runtime handoff owns external interaction and returns a verified outcome
receipt.  The receipt does not select a provider directly.  It is reinjected as
ordinary POO input in a successor generation, where the resolver revalidates
receipt, authority, candidate set, lineage, and generation before producing a
final disposition.

A separate cancellation authority may cancel the suspended demand.  Timeout is
an explicit timeout or cancellation condition, never an implicit decline.

* Boundary-local overlay

A reinjected resolution Profile is local to the successor generation's demand
boundary.  Descendant demands inherit it only through authorized Capability
projection.  It does not rewrite canonical =user-composition=, mutate Profile
definitions, or register global state.  It terminates with the boundary.

* Evidence and replay

Evidence records canonical composition identity, reconstructible resolution
Profile provenance or content identity, affected Capability and provider
identities, parent-to-successor generation causality, and outcome.

It never serializes a POO root, closure, continuation, active evaluation cell,
or live reference.  Replay creates a fresh root and context, reconstructs the
declared resolution Profile, and reinjects it under the same boundary contract.
An unreconstructible transient resolution is =context-bound= and cannot claim
deterministic replay.

Live resume and historical replay validate different authority states:

- live resume requires current active authority, current candidates, and a
  valid successor generation;
- historical replay verifies recorded authority evidence and external outcome
  evidence without claiming that the historical authority remains active.

Replay performs no provider, network, UI, approval, or handoff effect.  It
verifies receipt identity, external outcome identity, resolver identity,
condition identity, historical authority evidence, and causal generation, then
reinjects the receipt as immutable POO evidence input.

A historical receipt cannot authorize a new live resolution.  Missing,
corrupt, or unverifiable evidence raises a missing- or
unverifiable-evidence condition; replay never falls back to requesting another
approval.

The replayed disposition aligns with historical canonical causal identity while
runtime object identity may differ in the fresh root.  Continuations, live
authority objects, and suspended cells never enter the replay payload.

* Conformance checklist

- [ ] Same-lineage refinement and unrelated singleton collision remain distinct.
- [ ] Multi-provider behavior requires an explicit POO contract.
- [ ] Ambiguity conditions carry identity, lineage, and demand evidence.
- [ ] Recovery requires an explicit resolution Profile.
- [ ] Resolution operates on discovered candidates and performs no provider
  search.
- [ ] Resolution is a higher-order POO object, not an alist, string map,
  priority number, or callback.
- [ ] Resolution proof binds condition, Capability, candidates, lineage, and
  parent generation.
- [ ] Successor generations rediscover and revalidate candidates.
- [ ] Changed candidates or lineage produce a stale-resolution condition.
- [ ] Permanent policy and condition-specific injected instances remain
  distinct.
- [ ] Ambiguity conditions carry evidence but no resolution authority.
- [ ] Resolution authority is an explicitly imported boundary-owned POO
  Capability.
- [ ] Authority scope binds boundary, Capability, lineage or candidates, and
  generation.
- [ ] Delegation may attenuate but never amplify child authority.
- [ ] Cross-boundary ambiguity resolves only at the smallest common owning
  boundary.
- [ ] Successor generations revalidate authority identity, activity, and
  scope.
- [ ] Revoked, stale, or out-of-scope authority produces a structured
  condition with no provider-order fallback.
- [ ] No ambient global authority or administrator priority exists.
- [ ] Singleton proof selects exactly one contribution identity from the
  immutable candidate set.
- [ ] Candidate order, index, path, name, and priority carry no selection
  semantics.
- [ ] Successor validation checks membership, lineage, authority, and
  generation.
- [ ] Proof cannot synthesize a provider, alter multiplicity, or merge
  candidates.
- [ ] No acceptable candidate declines resolution without producing an empty
  successful value.
- [ ] Decline preserves the condition, candidates, and suspended cell and
  propagates to the outer owning condition boundary.
- [ ] Resolution authority never implies demand-cancellation authority.
- [ ] Cancellation requires a separate Capability, successor generation, and
  receipt.
- [ ] Resolver chains are explicit POO composition rather than candidate order
  or a global handler registry.
- [ ] Resolver contributions form an explicit predecessor lineage.
- [ ] Decline forwards unresolved state; valid selection stabilizes the state
  and prevents later resolver demand.
- [ ] Resolver order comes from canonical Profile composition, not candidate
  discovery.
- [ ] Evidence identifies the resolver contribution that selected.
- [ ] Independent proofs without shared predecessor lineage raise
  resolver-ambiguity.
- [ ] Overlay resolvers enter the lineage explicitly and never use a global
  handler table.
- [ ] External consultation uses suspension and handoff rather than effects
  inside the pure resolver.
- [ ] Suspension is a resolver evaluation state, not a third disposition.
- [ ] Later resolver contributions remain undemanded while the current resolver
  is suspended.
- [ ] Resolver effect intent carries condition, candidates, resolver,
  generation, and requested authority scope.
- [ ] Runtime handoff owns external interaction and serializes no continuation.
- [ ] External receipt becomes POO input and never selects a provider directly.
- [ ] Reinjection revalidates receipt, authority, candidates, lineage, and
  generation before final disposition.
- [ ] Cancellation uses separate authority; timeout never becomes implicit
  decline.
- [ ] New providers and aggregation contracts enter canonical composition as
  ordinary Profile contributions.
- [ ] Recovery overlays remain boundary-local and immutable by generation.
- [ ] Replay uses a fresh root and serializes no live runtime state.
- [ ] Unreconstructible resolution is classified =context-bound=.
- [ ] Live resume validates active authority; historical replay validates only
  recorded authority evidence.
- [ ] Replay invokes no provider, network, UI, approval, or handoff effect.
- [ ] Receipt verification binds outcome, resolver, condition, authority
  evidence, and causal generation.
- [ ] Historical receipts cannot authorize new live resolution.
- [ ] Missing or unverifiable evidence fails replay without re-requesting
  approval.
- [ ] Replay preserves canonical causal identity while allowing fresh runtime
  identity.
- [ ] Continuations, live authority objects, and suspended cells remain outside
  replay payloads.

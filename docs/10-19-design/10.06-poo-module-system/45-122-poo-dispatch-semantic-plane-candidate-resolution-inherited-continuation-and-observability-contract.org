#+title: POO Dispatch Semantic Plane, Candidate Resolution, Inherited Continuation, and Observability Contract
#+author: POO Flow
#+language: en

* Status

This RFC is an accepted semantic contract.

It defines dispatch as a first-class POO semantic plane.  It does not admit a
POO Flow dispatch implementation, replace upstream =gerbil-poo= dispatch, or add
a public dispatch DSL.

Implementation remains blocked until the consumed upstream operation paths in
RFC 45-120 reach =ADMITTED=.

* Scope

This RFC owns:

- the semantic inputs and phases of POO Flow dispatch;
- instance, type, and prototype dispatch sources;
- candidate identity and C3 precedence boundaries;
- inherited computation, =super=, and next-method continuation;
- dispatch outcomes, structured conditions, traces, budgets, cycles, and cache
  identity;
- the boundary between pure semantic dispatch and runtime effects;
- the use of dispatch for Module-derived responsibilities.

It does not own:

- upstream object, slot, prototype, generic, or precedence implementation;
- contribution admission priority;
- a global fixed-point implementation;
- runtime continuation invocation;
- package or build dispatch;
- application deployment policy;
- a new public macro or clause language.

* Upstream evidence boundary

The pinned upstream identity is:

#+end_example

Pinned source evidence establishes:

  =object/slot-spec=, =$computed-slot-spec=, =NoApplicableMethod=,

- =mop.ss=: =.defgeneric=, =.call.method=, =.call=, =.ref=,

These are upstream semantics.  POO Flow may project Module responsibilities,
structured conditions, and observation values around them, but it must not
reimplement their dispatch algorithms.

* Central decision

Dispatch is an explicit semantic evaluation with five phases:

1. normalize one receiver and one requested responsibility;
2. enumerate admitted instance, type, and prototype candidates;
3. order candidates through upstream precedence semantics;
4. evaluate one candidate with an inherited-computation continuation;
5. return one semantic outcome and one observable explanation.

Dispatch is not an opaque function call.  Every phase must remain explainable
under the authority and redaction limits of its evaluation context.

* Dispatch demand

A dispatch demand contains the minimum semantic inputs:

- receiver semantic identity;
- requested responsibility identity;
- explicit =DebugEvaluationContext= or an admitted narrowed projection;
- capability envelope;
- execution lineage and cache namespace;
- remaining observation and evaluation budgets.

This is an internal semantic value, not a new ordinary user form.

The receiver is a native upstream POO value.  The requested responsibility may
name a required Module slot, a derived responsibility, or an admitted generic
operation.

* Dispatch sources

Dispatch sources are distinct:

- instance source: behavior provided directly by the receiver;
- type source: behavior provided by the receiver's admitted type descriptor;
- prototype source: inherited behavior supplied through the prototype graph.

=.defgeneric= may select instance or type as its method source.  Prototype slot
dispatch follows upstream object and slot semantics.

POO Flow must preserve source identity in every explanation.  It must not
flatten the three sources into a hidden registry or unordered map.

* Candidate identity and precedence

Each candidate is identified by:

- receiver identity;
- requested responsibility;
- source kind;
- provider prototype or type identity;
- upstream slot or generic identity;
- prototype generation or immutable graph identity.

Candidate enumeration does not choose a winner.

For a valid prototype graph, upstream C3 precedence determines the dispatch
order.  POO Flow must not add a second priority number, linearization pass, or
last-writer-wins rule.

Invalid or circular precedence is a structured dispatch condition.  It is not a
reason to fall back to source order.

* Contribution priority is not dispatch precedence

Contribution priority and dispatch precedence are separate relations:

- contribution priority participates in admission and conflict resolution
  before a prototype graph is finalized;
- C3 precedence resolves behavior inside the finalized prototype graph.

Numeric contribution priority cannot dynamically skip a C3 provider, rewrite a
=super= chain, or select a method after dispatch begins.

If admitted contributions cannot form one valid prototype graph, composition
fails before dispatch.

* Inherited computation and continuation

Upstream computed slots receive inherited computation through the slot-spec
protocol.  =super= or next-method advances within the current dispatch chain.

This dispatch continuation is:

- local to one receiver and requested responsibility;
- ordered by the already established precedence path;
- bounded by the current evaluation context;
- unable to widen capabilities or redaction authority;
- unable to restart runtime execution.

It is not a =call/cc= recovery continuation.

A recovery continuation belongs to the coordinator resumption contract.  It
creates a new execution identity, crosses a continuation fence, and requires
explicit admission.  Dispatch =super= does none of those things.

* Dispatch outcomes and conditions

Pure dispatch returns one semantic outcome:

- a semantic value;
- a structured condition;
- a suspended result;
- a denied result;
- a cancelled result.

The dispatch plane recognizes at least:

- =NoApplicableMethod=;
- invalid or circular precedence;
- capability denial;
- recursive dispatch cycle;
- evaluation-budget exhaustion;
- observation-budget exhaustion;
- redaction denial;
- effect required in a pure plane;
- candidate evaluation condition.

For a valid C3 graph, dispatch does not invent an ambiguity result after
precedence resolution.  Contribution ambiguity must be rejected before the
graph enters dispatch.

* Module-derived responsibilities

The four required Module slots remain direct semantic projections:

- =identity=;
- =imports=;
- =capabilities=;
- =profiles=.

Dispatch may derive:

- recursive reachable responsibilities;
- capability satisfaction and attenuation;
- selected ProfileBundle projection;
- conflicts and explanations;
- identity and export provenance;
- semantic composition receipts.

Exact public names for those derived responsibilities remain unadmitted.  Their
semantics must be proven before names become part of the project interface.

* Fixed-point and cycle boundary

Dispatch may enter recursively imported Modules or lazily computed
responsibilities.  It does not itself own a global fixed-point engine.

POO Flow supplies the explicit evaluation context around upstream dispatch:

- active receiver/responsibility path;
- execution lineage;
- cycle identity;
- evaluation and observation budgets;
- cache namespace;
- capability attenuation;
- redaction limits.

A repeated dispatch identity may be:

- a valid cache hit;
- a productive fixed-point dependency;
- a suspended dependency awaiting a value;
- an unproductive cycle;
- a budget-exhausted evaluation.

The result must be observable and structured.  Infinite recursion, stack
overflow, silent recomputation, and unexplained performance collapse are not
accepted conditions.

* Cache identity

** Module-demand cache identity

A module demand uses two semantic memoization layers inside one realization
context.  Neither layer is an implicit process-global cache.

The base-prototype resolution key includes:

- stable module identity;
- prototype generation or immutable prototype-graph identity;
- realization-context cache namespace and fixed-point epoch;
- the admitted semantic evaluation-context projection.

The refined-demand key includes:

- the base-prototype resolution key or its semantic receipt;
- the ordered, normalized profile-prototype identities;
- every profile contribution priority participating in normalization;
- the capability, redaction, recovery-policy, and dependency-closure identities
  that can change the semantic result.

*** Canonical profile-refinement key

Profile-key normalization consumes semantic POO values, not the original Scheme
syntax.  Each admitted contribution projects:

- stable profile semantic identity;
- prototype generation or immutable graph identity;
- qualified authority and conflict domain;
- normalized control-priority value;
- capability and redaction projection relevant to the result.

Unannotated priority normalizes to numeric =0=.  Larger numbers are stronger;
the semantic default and forced elements remain below and above all numeric
values respectively.  Authority intersection and domain qualification precede
priority comparison.  Equal-priority values recursively compose through the
POO algebra, and an incompatible equality produces a structured conflict rather
than an arbitrary winner.

The exact-real numeric domain, endpoint values, total order, and
=profile-priority.v1= canonical identity are owned by
[[file:45-120-48-profile-priority-value-and-contract-refinement.org][ProfilePriority
Value and Contract Refinement]].

Source position, alias, parser order, and module loading order are excluded from
the semantic key.  They remain available only as diagnostic attribution.
Higher-order POO profile extension changes the profile or prototype semantic
identity and therefore changes the key.  A raw conditional syntax tree is
never a profile identity.

Normalization does not sort or rewrite native prototype ancestry.  The key
records the resulting immutable prototype-graph identity and precedence
generation separately from numeric control priority.  Two demands share a
refinement key only when both their normalized contribution semantics and
their native prototype-graph identity are equal.

Priority ownership remains with
[[file:45-101-typed-module-relation-contribution-composition-conflict-and-withdrawal-algebra.org][Typed
Module Relation Contribution and Conflict Algebra]].  Native prototype and C3
precedence ownership remains with
[[file:45-102-native-prototype-precedence-and-typed-relation-conflict-resolution-bridge.org][Native
Prototype Precedence and Typed Relation Conflict Resolution Bridge]].

The composition-local alias is excluded from both keys.  It is diagnostic and
lexical attribution, not module identity.  Runtime handles, process identity,
wall-clock time, and other ambient effect state remain excluded from pure
module-demand keys.

The base layer may reuse one resolved =ModuleType= prototype for several
profile projections in the same fixed-point epoch.  The refinement layer may
reuse only a result whose complete normalized refinement key matches.  A cache
entry contains the semantic outcome, explanation, and dependency receipt; a
bare value without equivalent evidence is not a valid hit.

Cross-context or cross-epoch reuse is forbidden by default.  It requires the
explicit snapshot or receipt admission defined by
[[file:45-03-runtime-context-and-recovery.org][Runtime Context and Recovery]],
including matching lineage, cache namespace, recovery policy, capability
projection, and dependency evidence.

*** Active-demand and cycle boundary

Re-entering the same refined-demand key while that key is active produces a
cycle observation immediately.  It must not recursively invoke the evaluator,
block on its own unfinished cache entry, or expose a partially computed value
as a valid hit.

The existing fixed-point recovery plane decides whether the dependency is
productive, suspended, recoverable, denied, or failed.  A continuation or
replacement value becomes reusable only after its recovery decision and
explanation are part of the semantic outcome.  Cycle and recovery ownership
remains with [[file:45-10-provider-runtime-search-closure.org][Provider Runtime
Search Closure]].

*** Module-demand cache checklist

- [ ] Keep base-prototype and refined-demand memoization as separate layers.
- [ ] Exclude composition-local aliases from semantic cache identity.
- [ ] Include normalized profile identities and contribution priorities in the
      refined-demand key.
- [ ] Scope both layers to a realization-context namespace and fixed-point
      epoch by default.
- [ ] Store semantic outcomes together with explanations and dependency
      receipts.
- [ ] Detect active-key re-entry before waiting on or recursively evaluating an
      unfinished entry.
- [ ] Route productive cycles, suspension, denial, and recovery through the
      existing fixed-point observation and recovery plane.
- [ ] Prove that different aliases share results while different profile
      priorities do not collide.
- [ ] Prove that cross-context reuse fails closed without an explicitly
      admitted compatible snapshot or receipt.

A dispatch cache key includes:

- receiver semantic identity;
- requested responsibility identity;
- immutable prototype graph or generation identity;
- source kind;
- inherited-continuation position;
- the semantic projection of the evaluation context;
- capability attenuation and redaction identity.

Runtime handles, secret values, process identities, wall-clock time, and
ambient environment state do not enter a pure dispatch cache key.

A cache hit preserves the same semantic explanation boundary as direct
evaluation.

* Observability contract

Every observable dispatch may project an explanation containing:

- receiver and responsibility identities;
- admitted source kinds;
- candidate provider identities;
- rejected candidates and structured reasons;
- precedence path;
- selected provider;
- inherited-computation or next-method path;
- cache hit, miss, or bypass reason;
- cycle classification;
- budget reservations and consumption;
- redaction decisions;
- terminal or continuable outcome.

The explanation is a semantic value.  It does not expose secret data, hidden
capabilities, raw continuation objects, or mutable runtime handles.

Observation is demand-driven and budgeted.  Dispatch does not emit an unbounded
global trace by default.

* Effect boundary

Pure dispatch cannot perform environment access, secret retrieval, I/O,
publication, durable claims, or continuation invocation.

When a responsibility requires an effect, dispatch returns an admitted
=EffectIntent= or =RecoveryExecutionIntent= value.  A runtime/deployment adapter
may later execute that intent under explicit authority.

The resulting runtime receipt is distinct from the dispatch explanation and
from =ResolvedCompositionReceipt=.

* Macro governance and public interface

=.defgeneric= is an upstream native POO macro.  Its use in the advanced
extension interface does not authorize a project-specific dispatch macro
family.

Project macros may only provide a small hygienic or phase-semantic projection
onto ordinary native POO and functional code.

The ordinary interface remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

Dispatch is not written inside =use-composition=.

* Ownership

- Upstream =gerbil-poo= owns object, slot, prototype, generic, inherited
  computation, and precedence mechanics.
- =poo-flow-core= owns Module responsibility identity, dispatch evaluation
  context, capability boundary, structured condition projection, cache
  identity, and semantic explanation.
- =wendao-episteme= owns its domain Module, Profile, and dispatched domain
  behavior.
- The final application owns selected Profiles and contribution-admission
  policy.
- Runtime/deployment adapters own admitted effect execution and runtime
  receipts.
- GSLPH may test dispatch contracts as a development dependency; it does not
  provide dispatch semantics.

- [X] Prove upstream =.defgeneric= and instance/type source behavior.
- [X] Prove upstream =NoApplicableMethod= identity.

- [ ] Move every consumed dispatch path from semantics proof to project-adapter
  =ADMITTED= in RFC 45-120.

** Semantic dispatch

- [X] Freeze receiver, responsibility, context, capability, lineage, and budget
  as explicit dispatch inputs.
- [X] Separate source enumeration, candidate identity, precedence, evaluation,
  inherited continuation, and outcome.
- [X] Separate contribution priority from C3 dispatch precedence.
- [X] Separate =super= continuation from coordinator recovery continuation.
- [ ] Define concrete POO values for dispatch demand, explanation, and
  structured conditions.

** Fixed point and observability

- [X] Require active-path, cycle, budget, cache, capability, and redaction
  context.
- [X] Require demand-driven and budgeted explanations.
- [ ] Prove productive fixed-point dependency behavior.
- [ ] Prove unproductive-cycle and budget-exhaustion behavior.
- [ ] Prove cache-key sufficiency and invalidation.
- [ ] Prove redaction and capability non-widening across =super=.

** Integration

- [ ] Map each Module-derived responsibility to one dispatch contract.
- [ ] Prove pure dispatch cannot execute runtime effects.
- [ ] Prove EffectIntent handoff and receipt separation.
- [ ] Prove application contribution admission finishes before C3 dispatch.
- [ ] Run focused GSLPH development checks without adding a product dependency.

* Rejected alternatives

- A hidden global dispatch registry.
- A second project-owned method lookup or prototype linearization engine.
- Last-writer-wins dispatch.
- Numeric contribution priority replacing C3 precedence.
- Dispatch ambiguity invented after a valid C3 order exists.
- Host =if= or =case= selecting Module or Profile behavior.
- Treating =super= as a recoverable runtime continuation.
- Performing runtime effects inside a pure dispatched responsibility.
- Unbounded global dispatch tracing.
- Cache keys that omit receiver, responsibility, prototype generation,
  inherited position, authority, or redaction identity.
- A public dispatch DSL layered over native POO operations.

* Successor contract

The next RFC may define the first concrete POO Flow dispatch semantic values:

- dispatch demand;
- candidate identity;
- dispatch explanation;
- structured dispatch condition.

It must keep them native POO values, preserve upstream mechanics, and avoid
exposing a new ordinary user interface.

No implementation may begin until the exact upstream adapter paths it consumes
are =ADMITTED= by RFC 45-120.

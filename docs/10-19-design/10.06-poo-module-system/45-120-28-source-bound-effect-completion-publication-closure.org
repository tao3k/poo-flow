#+title: Source-Bound Effect Completion Publication Closure

* Status

Proof-backed v1 refinement.

This RFC does not define a v2 effect event, ledger, plan, or retry-authority
schema.  It closes the next v1 boundary after
[[file:45-120-27-source-bound-effect-replay-idempotency-closure.org][45-120-27]]:
an authorized =execute= step must become a provider-acknowledged completion and
an atomically committed ledger/frontier transition before it can be treated as
completed.

* Context

The replay ledger currently stores:

- =completed : Bool=;
- =completionReceiptId : String=.

Its closure proves that a completed entry has a nonempty receipt identity.
That is insufficient evidence.  A string does not prove:

- which exact replay step executed;
- whether the effect provider reported success;
- whether the provider acknowledged the same idempotency key;
- whether the result belongs to the active runtime epoch and fence token;
- whether the ledger snapshot and completion frontier committed atomically;
- whether the same key was already committed in an earlier publication.

The replay plan therefore proves what may execute, but not that execution
completed or committed exactly once.

* Decision

Keep the v1 replay owners unchanged and add three later proof values:

1. a completion receipt binds the exact execute step, request, window, plan,
   epoch, fence token, result digest, and provider acknowledgement;
2. a publication binds the complete before/after ledgers, exact plan-step
   projection, and a one-step completion-frontier advance;
3. a publication history chains committed publications and globally separates
   publication identities, commit identities, completion identities, and
   executed idempotency keys.

The storage owner supplies an independent atomic-commit validity predicate.
Lean proves the required binding and composition.  JSON is a deterministic
validation projection, not an authority owner.

* Mathematical model

A provider completion receipt is:

#+begin_src typst
$
C = (r_c, p, q, w, l, s, e, f, b, d_r, d_a, d_p)
$
#+end_src

where $r_c$ is the receipt identity, $p$ the provider, $q$ the restore
request, $w$ the replay window, $l$ the replay plan, $s$ the exact step,
$(e,f)$ the runtime epoch and fence token, $b$ the success bit, and
$d_r,d_a,d_p$ the result, provider-acknowledgement, and provenance digests.

A closed receipt requires:

#+begin_src typst
$
op("Closed")_C(C) :=
  op("Valid")_p(C)
  and b = "true"
  and s in op("Plan")(l)
  and op("action")(s) = "execute"
  and op("key")(s) != emptyset
  and (q,w,l,e,f) = (q_a,w_a,l_a,e_a,f_a)
$
#+end_src

One publication item relates exactly one before entry, after entry, and plan
step:

#+begin_src typst
$
op("Item") = (E_0, E_1, s, delta)
$

$
delta =
cases(
  "executed"(C), & op("completed")(E_0) = "false"
    and op("completed")(E_1) = "true"
    and op("receipt")(E_1) = r_c,
  "suppressed", & op("action")(s) = "suppress-completed"
    and E_1 = E_0
)
$
#+end_src

An atomic publication is:

#+begin_src typst
$
P = (L_0, L_1, F_0, F_1, I, c_p)
$

$
op("Closed")_P(P) :=
  op("map")(op("before"), I) = op("entries")(L_0)
  and op("map")(op("after"), I) = op("entries")(L_1)
  and op("map")(op("step"), I) = op("steps")(op("Plan"))
  and F_1 = F_0 + 1
  and op("AtomicCommit")(c_p, P)
$
#+end_src

The history is a nonempty chain of publications:

#+begin_src typst
$
H = [P_0, P_1, dots, P_n]
$

$
forall i < n:
  op("ledger-after")(P_i) = op("ledger-before")(P_(i+1))
  and op("frontier-after")(P_i) = op("frontier-before")(P_(i+1))
$

$
op("PairwiseDistinct")(op("keys")(H))
and op("PairwiseDistinct")(op("completion-receipts")(H))
and op("PairwiseDistinct")(op("commit-receipts")(H))
$
#+end_src

The proved guarantee is deliberately precise:

#+begin_src typst
$
op("ProviderIdempotent")
and op("Closed")_H(H)
=> "at most one committed completion per idempotency key"
$
#+end_src

Lean alone cannot prove that an arbitrary external provider performs a physical
side effect exactly once.  End-to-end exactly-once behavior additionally
requires the provider acknowledgement to validate the same idempotency key.
Without that provider contract, the v1 guarantee is exactly-once *committed
completion evidence*, not universal exactly-once external execution.

=ToJson=, and =FromJson=.

The projection schema is:

  "schemaId": "poo-flow.effect-completion-validation.v1"

JSON validation checks stable scalar bindings and required evidence fields.
It does not replace either:

- =SourceBoundEffectCompletionReceiptValid=, owned by the effect provider;
- =SourceBoundEffectCompletionCommitReceiptValid=, owned by the atomic storage
  commit boundary.

The theorem =jsonValidationDoesNotEntailProviderAuthority= prevents an
=okay=true= JSON projection from being treated as provider evidence.

* State model

#+begin_src mermaid
flowchart TD
  A["Retry authority closed"] -->|"execute / authorized"| B["Provider execution attempt"]
  A -->|"suppress-completed / already committed"| H["Canonical completion history"]
  B -->|"failure / no completion commit"| R["Pending replay remains retryable"]
  B -->|"success + idempotency acknowledgement"| C["Completion receipt"]
  C -->|"Lean ToJson projection"| D["JSON validation receipt"]
  D -->|"errors nonempty / fail closed"| X["Rejected evidence"]
  D -->|"okay=true / structural binding only"| E["Provider receipt closure"]
  E -->|"provider predicate rejects"| X
  E -->|"provider predicate validates"| F["Publication transition"]
  F -->|"atomic commit predicate rejects"| X
  F -->|"ledger and frontier commit together"| G["Atomic commit receipt"]
  G -->|"append with predecessor match"| H
  H -->|"duplicate key, receipt, or publication"| X
  H -->|"globally unique committed evidence"| I["At-most-one committed completion per key"]
  I -->|"provider idempotency contract also holds"| J["End-to-end exactly-once behavior"]
#+end_src

The edge labels are part of the semantic distinction:

- =okay=true= advances only to provider validation;
- provider success advances only to publication construction;
- only the atomic commit predicate advances ledger and frontier together;
- history uniqueness proves at-most-one committed completion;
- end-to-end exactly-once still depends on the provider idempotency contract.

* Proof findings

The Lean model exposes six v1 defects:

1. a nonempty =completionReceiptId= can close the old ledger entry without any
   receipt object;
2. JSON structural validity cannot entail provider authority;
3. completion evidence cannot entail atomic commit authority;
4. before/after ledger coverage must be exact, otherwise entries can be
   inserted, dropped, or reordered during publication;
5. one locally closed publication cannot establish global exactly-once
   behavior;
6. an external effect cannot be claimed exactly once without a provider-owned
   idempotency acknowledgement.

The executable counterexample
=opaqueReceiptIdentityCanCloseLedgerEntryWithoutReceiptEvidence= proves the
first defect against the existing v1 ledger predicate.

* Crash-recovery continuation

The v1 continuation in
[[file:45-120-29-source-bound-effect-completion-crash-recovery-closure.org][45-120-29]]
proves why the engine ledger cannot distinguish =not-executed= from
=executed-uncommitted= after a pre-publication crash.  It adds a pure Lean
four-state recovery classification, keeps the existing completion publication
as the only storage-commit authority, and limits JSON to the existing
audit/Python FFI boundary.

* Next proof gap

This RFC closes committed completion publication.  The next v1 question is
crash recovery between provider acknowledgement and atomic publication:

- how an uncommitted provider acknowledgement is rediscovered;
- how the same idempotency key is queried rather than re-executed blindly;
- how recovery distinguishes =not executed=, =executed but uncommitted=, and
  =committed= without inventing a second ledger owner.

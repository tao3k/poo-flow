#+title: Submodule, Package, Module, and Profile Ownership Boundaries
#+startup: overview

* Status

This RFC records the accepted ownership and import boundaries among Git
submodules, Gerbil packages, Gerbil modules, and POO profile values.

It applies the boundary concretely to the current =wendao-episteme= source
submodule and the thin projection owned by =poo-flow-core=.

* Typst formalization: four orthogonal ownership layers

Git submodule, Gerbil package, Gerbil module, and POO profile are four distinct
layers.  No layer implicitly creates another, and every cross-layer projection
requires an explicit contract.

#+begin_src typst
#let layers = (
  "git-submodule",
  "gerbil-package",
  "gerbil-module",
  "poo-profile",
)

$ forall S, T in layers:
  (S != T) => not "ImplicitlyCreates"(S, T) $

$ forall S, T in layers:
  "CrossLayerProjection"(S, T)
  => "ExplicitProjectionContract"(S, T) $

$ forall P:
  "GitSubmodule"(P)
  => "Records"(P_"repository", P_"commit", P_"checkout", P_"provenance")
  and not "ImpliesGerbilPackage"(P)
  and not "ImpliesGerbilModule"(P)
  and not "ImpliesPooProfile"(P) $
#+end_src

The =packages/wendao-episteme= path is a pinned child source checkout, not a
Gerbil package declaration.  The child owns its build, tests, and publication.
=gerbil.pkg= manages package metadata and installation relationships; a Gerbil
module provides lexical bindings; only an explicit first-class POO profile
value participates in =compose profiles=.

#+begin_src typst
$ forall C:
  "ParentPins"(C)
  => "ChildOwns"(C_"build")
  and "ChildOwns"(C_"tests")
  and "ChildOwns"(C_"publication")
  and not "ParentOwns"(C_"lifecycle") $

$ forall P:
  "GerbilPackage"(P)
  => not "DeclaresPooProfile"(P)
  and not "RegistersProvider"(P)
  and not "DefinesRuntimeCapability"(P)
  and not "SelectsCompositionRoot"(P) $

$ forall M:
  "Import"(M)
  => "LexicalBindings"(M)
  and not "GrantsRuntimeCapability"(M)
  and not "ActivatesPooProfile"(M) $

$ forall S, P:
  "Update"(S)
  => "NewSourceProvenance"(S)
  and not "AutomaticallyActivate"(P) $
#+end_src

* Central decision

The following are four different layers:

1. Git submodule;
2. Gerbil package;
3. Gerbil module;
4. POO profile.

No layer implicitly creates or owns another layer.

* Git submodule

A Git submodule records:

- child repository URL;
- exact child commit;
- checkout location;
- source provenance.

A submodule does not imply:

- a Gerbil package;
- an importable Gerbil module;
- a POO profile;
- parent ownership of child build, test, or publication;
- runtime evidence closure;
- provider registration.

The =packages/wendao-episteme= checkout is a pinned external source tree. Its
directory name does not turn its repository root into a Gerbil package.

The submodule commit is source identity evidence. It is not the complete
semantic identity of a profile.

* Gerbil package

A Gerbil package is a package-manager and compiled-module-tree unit understood
through Gerbil package metadata and tooling.

=gerbil.pkg= manages:

- Gerbil package metadata;
- Gerbil package dependencies;
- package installation and update relationships;
- compile-time package availability.

=gerbil.pkg= does not:

- declare POO profiles;
- project an active dependency evidence closure;
- register providers;
- define runtime capabilities;
- convert arbitrary Git submodules into Gerbil modules;
- select composition roots.

The current =wendao-episteme= submodule root is not a Gerbil package. RFCs and
examples must not imply otherwise.

* Gerbil module

A Gerbil module provides normal lexical language bindings through:

- module path;
- import and export;
- rename and prefix controls;
- compile and load boundaries;
- hygienic binding identity.

A POO profile used by Scheme code is obtained through an explicitly owned
Gerbil module export.

Profile discovery must not depend on:

- filesystem scanning;
- Git-submodule traversal;
- scanning =gerbil.pkg= files;
- import-time registration;
- a hidden global registry;
- same-name last-write-wins.

Lexical module imports and explicit rename resolve binding names.

* POO profile

A POO profile is a first-class Gerbil value backed by =gerbil-poo= object and
prototype semantics.

It is not:

- a repository;
- a package manifest;
- a module path;
- a registry entry;
- a runtime token.

A Gerbil module may export more than one profile. Multiple modules may export
the same lexical name, and normal import controls resolve that collision.

Profile composition receives values directly. It does not perform name lookup.

* Current wendao-episteme ownership

The current ownership boundary is:

- the =wendao-episteme= repository owner owns its source content;
- the parent repository owns only the Git submodule pin;
- =poo-flow-core= owns only the POO projection contract it consumes;
- the parent does not own child build, test, distribution, or publication;
- the projection does not claim that the child supplies a Gerbil package;
- the semantic subject and public profile name remain
  =wendao-episteme=.

The profile must not be renamed to a broader or ambiguous Wendao identity.

* Thin projection module

When the current architecture needs an importable Scheme profile,
=poo-flow-core= owns a thin projection module.

The projection may represent:

- approved POO contracts;
- the pinned source-provenance identity;
- profile identity and revision;
- imports and capability requirements;
- provided contract projections;
- construction evidence.

The projection must not:

- compile the child repository;
- run child tests;
- publish a child package;
- interpret arbitrary child implementation files;
- claim child-owned capabilities;
- present the child tree as a Gerbil module tree;
- own child integration or distribution tests.

The projection is a =poo-flow-core= contract about how core composes the pinned
semantic subject. It is not a transfer of child repository ownership.

* Possible future child-owned module

If =wendao-episteme= later publishes a real Gerbil package and module, that
creates a new explicit ownership and import contract.

The current RFC must not assume that future interface already exists.

A future transition identifies:

- child package identity;
- exported module identity;
- profile revision;
- source and build provenance;
- compatibility with the current core-owned projection;
- ownership and verification responsibilities.

The future child-owned module does not retroactively turn the current submodule
revision into a Gerbil package.

* Profile export evidence

A profile export projects:

- profile semantic identity;
- profile anchor and revision;
- exporting module identity;
- source provenance;
- construction-strategy identity;
- required imports;
- required capabilities;
- provided contract projections;
- confidentiality and disclosure classification;
- profile-construction receipt.

These are POO object slots or projections, not global registry metadata.

Exact slot and operator spelling remains deferred until verified against the
real =gerbil-poo= API.

* Import, construction, evaluation, and handoff

The lifecycle remains staged.

** Gerbil import

Import resolves lexical bindings and code loading.

It does not execute live resource work.

** Profile construction

Profile construction creates an ordinary pure POO value.

** Composition

=compose profiles= combines only the values explicitly supplied by the user.

** POO Flow evaluation

Evaluation resolves the graph, fixed point, contracts, capabilities, and
evidence.

** Runtime handoff

Live effects occur only after a pure proposal crosses an explicit authority
boundary.

* Import-time prohibition

Importing a profile module must not:

- connect to a database;
- probe a remote provider;
- acquire a capability;
- modify an active head;
- start a worker;
- execute a migration;
- register a global handler;
- mutate a runtime registry.

Import-time work remains bounded to normal module loading and construction of
ordinary pure values.

* Profile revision identity

A profile revision identity includes at least:

#+begin_example
exporting module identity
+ profile anchor and revision
+ POO construction identity
+ source provenance identity
+ contract projection identity
#+end_example

A Git submodule commit contributes source provenance. It does not identify the
complete profile semantics.

A lexical profile name also does not identify the complete profile revision.

* User composition

The user interface remains:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    base
    wendao-episteme
    production))
#+end_src

The operands are lexical Scheme bindings obtained through normal Gerbil module
imports.

=compose= does not query a package manager, filesystem, source tree, or global
registry to resolve these names.

* Ownership summary

The normative summary is:

#+begin_quote
A Git submodule provides a source pin. gerbil.pkg manages Gerbil package
dependencies. A Gerbil module provides lexical bindings. A POO profile provides
composition semantics.
#+end_quote

No layer silently substitutes for another layer.

* Failure taxonomy

The implementation must distinguish at least:

- submodule treated as a Gerbil package;
- =gerbil.pkg= treated as POO profile metadata;
- profile export module owner unresolved;
- filesystem auto-discovery attempted;
- hidden registry lookup attempted;
- import-time effect attempted;
- profile source provenance incomplete;
- profile revision identity incomplete;
- parent attempted child build or test ownership;
- child capability claimed by projection;
- conceptual future child module treated as current;
- lexical profile binding unresolved.

* Required invariants

1. Git submodule, Gerbil package, Gerbil module, and POO profile remain distinct.
2. A submodule pin proves source revision only.
3. =gerbil.pkg= remains package-management metadata.
4. Profiles are explicit first-class module exports.
5. Profile composition performs no hidden discovery or registry lookup.
6. The parent owns no child build, test, distribution, or publication.
7. =poo-flow-core= owns only its thin POO projection contract.
8. The current child is not presented as a Gerbil package.
9. Future child-owned module contracts are not assumed current.
10. Import performs no live effect.
11. Profile revision identity includes construction and contract identity.
12. The public semantic subject remains =wendao-episteme=.
13. Public extension remains POO-native.

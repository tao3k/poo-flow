#+title: Canonical Typed-Empty POO Values, Shared Prototype, Copy-on-Extension, and Cache Safety

* Status

Accepted architecture RFC.

This document fixes the semantics of canonical typed-empty POO values. It does
not authorize implementation work and does not claim unverified upstream
mutation or copying behavior.

* Scope

This RFC defines:

- the typed-empty values required by the minimal Module contract;
- the distinction between a shared prototype and a shared instance;
- the default fresh-instance rule;
- copy-on-extension semantics;
- isolation requirements for mutation-marked upstream procedures;
- identity, equality, evidence, and cache laws;
- macro governance for repeated typed-empty object families.

This RFC does not define:

- a generic untyped empty object;
- raw empty lists as semantic values;
- a mutable shared singleton;
- a new copy, clone, freeze, or immutability primitive;
- exact upstream =gerbil-poo= call forms;
- a compatibility, migration, or deprecation strategy;
- implementation edits.

* Durable POO identity

All typed-empty prototypes and instances remain native objects of:

#+begin_example
github.com/mighty-gerbils/gerbil-poo@1c3225637525400341a09e958296962c10184ead
#+end_example

POO Flow owns the domain meaning of empty exports, direct imports, and
capability requirements. =gerbil-poo= owns object mechanics.

including:

- =object-extend=;
- =extend-object!=;
- =object-compose=;
- =object-mix=;
- =object-set!=;
- =object-update!=;
- =object-slot-delete!=;

- =object-super=;
- =object-precedence-list=.

The current provider cannot decode exact bodies for the key upstream selectors.
The exact blocker is:

#+begin_example

#+end_example

The project owner route also emits no verified selectors for canonical
typed-empty exports, direct imports, or capability requirements.

Therefore the following remain =MISSING= implementation evidence:

- which upstream operations return new objects;
- which upstream operations mutate in place;
- whether composition preserves ancestry by construction;
- whether an immutable or frozen object mode exists;
- whether clone or copy primitives exist;
- whether the current project already constructs typed-empty objects.

This RFC defines the required observable semantics without assigning those
semantics to an unverified procedure.

* Central decision

POO Flow has three distinct typed-empty domains:

1. empty exports;
2. empty direct imports;
3. empty capability requirements.

They are not interchangeable.

The default safe representation is:

#+begin_example
shared typed-empty prototype
  -> fresh typed-empty instance per owning Module relation
  -> copy-on-extension result with new relation identity
#+end_example

Only the prototype is shared by default.

A shared typed-empty instance is admitted only when immutability is enforced
and proven by exact upstream and project evidence.

* Typed-empty domains

** Empty exports

An empty exports value:

- is a native POO object;
- inherits from the typed empty-exports prototype;
- contains no export identity;
- grants no capability;
- does not imply a =production= export;
- causes selection of any export to fail closed.

** Empty direct imports

An empty direct imports value:

- is a native POO object;
- inherits from the typed empty-imports prototype;
- contributes no direct dependency edge;
- is the recursion base for imports closure;
- does not represent an unavailable or unknown import set.

Empty and unknown are different states.

** Empty capability requirements

An empty capability requirements value:

- is a native POO object;
- inherits from the typed empty-capability-requirements prototype;
- contributes no additional requirement;
- grants no capability;
- does not mean unrestricted authority.

No requirement is not equivalent to unlimited grant.

* Why the empty values are typed

A single generic empty object would erase:

- the relation being represented;
- admissible extension operations;
- error ownership;
- evidence vocabulary;
- cache identity;
- capability meaning;
- prototype ancestry.

Typed empties allow validation to reject:

- an imports object used as exports;
- an exports object used as capability requirements;
- a raw list used as any semantic relation;
- an unknown relation mislabeled as empty.

* Shared prototype rule

The typed-empty prototypes may be shared because prototypes define domain
behavior and ancestry.

The prototype itself is read-only after publication.

No procedure may:

- mutate a published typed-empty prototype;
- attach Module-specific identity to the shared prototype;
- store Module-specific cache state on the prototype;
- use the prototype object as a writable relation instance;
- make prototype mutation an extension mechanism.

#+begin_src mermaid
flowchart TD
  ExportsProto["shared empty-exports prototype"] -->|"instantiates isolated relation"| ExportsA["Module A empty exports"]
  ExportsProto -->|"instantiates isolated relation"| ExportsB["Module B empty exports"]
  ImportsProto["shared empty-imports prototype"] -->|"instantiates isolated relation"| ImportsA["Module A empty imports"]
  ImportsProto -->|"instantiates isolated relation"| ImportsB["Module B empty imports"]
  CapProto["shared empty-capability prototype"] -->|"instantiates isolated relation"| CapA["Module A empty requirements"]
  CapProto -->|"instantiates isolated relation"| CapB["Module B empty requirements"]
  ExportsA -->|"copy-on-extension creates new identity"| ExportsA2["Module A extended exports"]
  ExportsB -.->|"remains observationally unchanged"| ExportsA2
  ImportsA -->|"copy-on-extension creates new identity"| ImportsA2["Module A extended imports"]
  ImportsB -.->|"remains observationally unchanged"| ImportsA2
  CapA -->|"attenuating extension creates new identity"| CapA2["Module A extended requirements"]
  CapB -.->|"remains observationally unchanged"| CapA2
#+end_src

The dotted edges express non-interference, not data flow.

* Shared instance admission

A shared typed-empty instance is an optimization, not the semantic default.

It is admitted only when all of these are proven:

- the instance is immutable after construction;
- no native or adapter operation can mutate it;
- no Module-specific identity or cache state is stored on it;
- extension always returns a distinct relation object;
- object ancestry remains inspectable;
- identity-sensitive caches distinguish the shared empty from extension
  results;
- concurrent readers observe one stable value;
- serialization retains the typed domain.

If any proof is missing, implementations share only the prototype and create
fresh instances.

* Copy-on-extension

Public relation extension has this observable contract:

#+begin_example
typed relation input + extension operand
  -> new typed relation output
#+end_example

The input remains observationally unchanged.

The output:

- has a new relation object identity;
- preserves the typed-empty prototype in its ancestry;
- contains the newly contributed relation;
- preserves independent constraints;
- carries evidence linking input, operation, and output;
- does not mutate sibling Module relations.

The phrase copy-on-extension defines observable semantics. It does not require
eager physical copying when a persistent native representation can prove the
same behavior.

* Module revision effect

Extending a direct relation produces a new Module revision or a new Module
value according to the owning revision RFC.

The semantic Module identity may remain stable while the revision identity
changes.

The relation object identity always changes when its semantic content changes.

This distinction prevents:

- stale closure caches;
- silent in-place Module mutation;
- ambiguous receipts;
- cross-session state leakage.

* Mutation-marked upstream procedures

A procedure whose name ends in =!= is treated as potentially destructive until
its exact contract is proven.

It may be used only inside an isolated construction region with:

- fresh, unpublished input objects;
- unique ownership evidence;
- no escaped aliases;
- no concurrent readers;
- a declared mutation boundary;
- final native ancestry validation;
- publication only after construction completes;
- a receipt naming every destructive operation.

It may never mutate:

- a published Module;
- a shared typed-empty prototype;
- a shared typed-empty instance;
- a relation object reachable from another Module revision;
- a value already used as a cache key;
- an admitted evidence object.

The public result must remain observationally equivalent to copy-on-extension.

* Unknown upstream operation semantics

The presence or absence of =!= is useful evidence but is not a complete
operational proof.

Until exact owner bodies are available:

- =object-extend= is not assumed non-destructive;
- =object-compose= is not assumed non-destructive;
- =object-mix= is not assumed non-destructive;
- =extend-object!= is treated as destructive but remains unverified;
- =object-set!= and =object-update!= are treated as destructive but remain
  unverified;
- ancestry preservation remains an admission gate.

No public helper may claim purity merely because its upstream procedure lacks
=!= in its name.

* Identity model

Each typed-empty domain has:

- prototype identity;
- relation domain identity;
- optional instance identity;
- owning Module and revision identity;
- source-construction identity.

Two fresh empty-import instances may be semantically equal while retaining
distinct object identities.

Identity is not reduced to pointer equality, structural empty-list equality, or
a shared singleton address.

* Equality model

Typed-empty semantic equality requires:

- the same relation domain;
- admitted typed-empty prototype ancestry;
- no contributed relation;
- equivalent domain constraints.

Object identity equality remains distinct.

An empty exports value is never semantically equal to an empty imports value,
even if both contain no contributed slots.

* Cache safety

Cache identity for a derived closure includes at least:

- Module semantic identity;
- Module revision identity;
- selected export identity;
- direct relation object identities;
- typed-empty prototype identities;
- capability context identity;
- evaluator and policy version;
- observation dependencies.

A shared typed-empty prototype may safely participate in many cache keys.

A fresh typed-empty instance may be normalized by semantic empty identity only
when the cache also preserves:

- relation domain;
- owning Module revision;
- ancestry qualification;
- authority context.

Mutation of a cache-key object after admission is forbidden.

* Fixed-point base behavior

Typed-empty direct imports provide an explicit recursion base:

#+begin_example
expand(empty direct imports) -> no new dependency demands
#+end_example

Typed-empty capability requirements provide an explicit attenuation base:

#+begin_example
attenuate(empty requirements, authority) -> no added requirement
#+end_example

Neither law bypasses cycle detection, budgets, resumptions, or observability
when non-empty recursive objects are present.

* Evidence projection

A typed-empty construction receipt identifies:

- durable =gerbil-poo= dependency identity;
- typed-empty domain;
- prototype identity;
- instance identity;
- owning Module and revision identity;
- construction operation;
- whether the instance is fresh or shared;
- immutability proof when shared;
- native ancestry;
- source owner;
- authority neutrality.

A copy-on-extension receipt additionally identifies:

- input relation identity;
- extension operand identity;
- output relation identity;
- native operation or adapter identity;
- destructive operations used internally;
- uniqueness and no-alias evidence;
- preserved prototype ancestry;
- cache invalidations;
- non-interference with sibling Modules.

* Macro governance

Functions and native POO objects remain the default abstractions.

A bounded internal macro may generate a repeated typed-empty prototype family
only when it:

- expands to ordinary native POO objects and pure functions;
- preserves a distinct domain identity for each family;
- contains no mutation or sharing policy;
- does not create runtime registries;
- emits inspectable source and object identities.

No public macro is introduced for creating or extending typed-empty values.

Public extension uses POO objects, prototype operations, and functional
combinators.

* Construction and publication sequence

#+begin_src mermaid
sequenceDiagram
  participant Prototype as "shared typed-empty prototype"
  participant Builder as "isolated constructor"
  participant Relation as "fresh relation instance"
  participant Extend as "pure public extension"
  participant Cache as "derived closure cache"
  participant Publish as "Module publication"

  Prototype->>Builder: "provides typed ancestry"
  Builder->>Relation: "constructs unpublished instance"
  Relation->>Extend: "enters as immutable input"
  Extend-->>Relation: "leaves input observationally unchanged"
  Extend->>Publish: "returns new relation and Module revision"
  Publish->>Cache: "invalidates prior revision keys"
  Cache-->>Publish: "admits identity-complete new keys"
#+end_src

Publication is the boundary after which mutation of the relation is forbidden.

* Semantic laws

** Typed distinction law

Empty exports, imports, and capability requirements are different semantic
values.

** Shared prototype law

Typed-empty prototypes are shareable and read-only after publication.

** Fresh instance default law

Without immutability proof, every owning Module relation receives a fresh
typed-empty instance.

** Shared instance proof law

A shared typed-empty instance requires enforceable immutability and
non-interference evidence.

** Copy-on-extension law

Public extension returns a new relation identity and leaves its input
observationally unchanged.

** Ancestry preservation law

Extension preserves the appropriate typed-empty prototype ancestry.

** Mutation fence law

Destructive operations are confined to fresh, uniquely owned, unpublished
objects.

** Publication immutability law

A published relation object is never mutated.

** Authority neutrality law

Typed-empty construction and extension grant no capability.

** Cache identity law

Every cached result includes sufficient Module, revision, relation, prototype,
authority, and observation identity.

** Unknown is not empty law

Unavailable or unresolved relation state cannot be represented by a
typed-empty value.

* Failure behavior

Typed-empty construction or extension fails closed when:

- a raw list, alist, or record is used as the semantic value;
- relation domain identity is absent;
- prototype ancestry is absent or wrong;
- a shared instance lacks immutability proof;
- a destructive operation touches a shared or published object;
- input mutation is observable;
- the output reuses identity after semantic change;
- capability authority is widened;
- a cache key omits relation or revision identity;
- unknown state is mislabeled empty;
- the selected upstream operation contract is unverified.

Failure identifies:

- typed-empty domain;
- prototype and instance identities;
- owning Module and revision;
- operation identity;
- mutation and ownership state;
- cache dependencies;
- missing proof.

* Rejected alternatives

The following alternatives are rejected:

- one generic empty POO object for every relation;
- raw =()= as exports, imports, or capability requirements;
- one mutable singleton instance shared by all Modules;
- mutating a shared prototype to add Module-specific data;
- assuming no-=!= means pure;
- assuming =!= fully specifies destructive semantics;
- copying by converting an object to an alist and rebuilding it;
- pointer identity as semantic empty equality;
- reusing a relation identity after content changes;
- caching closures without Module revision and relation identity;
- adding public macros for typed-empty mutation;
- compatibility aliases for untyped empty values.

- [ ] Empty exports has a distinct domain prototype.
- [ ] Empty direct imports has a distinct domain prototype.
- [ ] Empty capability requirements has a distinct domain prototype.
- [ ] Typed-empty values are native POO objects.
- [ ] Empty and unknown remain distinct.
- [ ] No typed-empty value grants authority.
- [ ] No raw list or alist is semantic truth.

** Sharing

- [ ] Typed-empty prototypes are read-only after publication.
- [ ] Prototypes contain no Module-specific state.
- [ ] Fresh instances are the default.
- [ ] Shared instances require immutability proof.
- [ ] Shared instances contain no Module-specific cache state.
- [ ] Sibling Modules cannot interfere.
- [ ] Published relation objects are immutable.

** Extension

- [ ] Public extension is observationally non-destructive.
- [ ] Extension returns a new relation identity.
- [ ] Extension preserves typed prototype ancestry.
- [ ] Extension preserves independent constraints.
- [ ] Module revision identity changes when content changes.
- [ ] Source relation identity remains valid and unchanged.
- [ ] No public helper claims unverified upstream purity.

** Mutation isolation

- [ ] Mutation-marked procedures remain internal.
- [ ] Mutated inputs are fresh and unpublished.
- [ ] Unique ownership is evidenced.
- [ ] No aliases escape before publication.
- [ ] No concurrent readers observe construction.
- [ ] Every destructive operation appears in a receipt.
- [ ] Shared prototypes and instances are never mutated.
- [ ] Cache-key objects are never mutated.

- [ ] Cache keys include Module semantic identity.
- [ ] Cache keys include Module revision identity.

- [ ] Cache keys include capability context.
- [ ] Cache keys include observation dependencies.

- [ ] Non-empty cycles still use budgets and observability.

** Macro governance

- [ ] Functions and POO objects remain default abstractions.
- [ ] Any family macro is internal and bounded.

** Evidence

- [ ] ancestry preservation is proven;
- [ ] any freeze or immutability primitive is identified or marked absent;
- [ ] typed-empty prototypes are mapped to native POO objects;
- [ ] fresh-instance construction is specified;
- [ ] shared-instance optimization has an immutability proof;
- [ ] copy-on-extension conformance tests are specified;
- [ ] sibling non-interference tests are specified;

- [ ] cache identity and invalidation tests are specified;
- [ ] empty-versus-unknown tests are specified;
- [ ] capability-neutrality tests are specified;
- [ ] macro expansion evidence is specified;
- [ ] the RFC set is reviewed before implementation begins.

* Consequences

Typed-empty POO values provide explicit, identity-bearing base cases without
introducing raw lists or missing-slot conventions.

Sharing remains safe because prototypes are shared by default while relation
instances remain isolated unless immutability is proven.

Copy-on-extension preserves functional composition, cache correctness, native
prototype ancestry, and sibling non-interference even when an implementation
uses isolated destructive construction internally.

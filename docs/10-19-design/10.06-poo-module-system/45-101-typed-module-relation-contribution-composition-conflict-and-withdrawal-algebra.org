#+title: Typed Module Relation Contribution, Composition, Conflict, and Withdrawal Algebra

* Status

Accepted architecture RFC.

This document fixes the algebra of non-empty Module relation objects. It does
not authorize implementation work and does not promote current option-policy
helpers into the new public API.

* Scope

This RFC defines:

- typed export, direct import, and capability requirement relations;
- identity-bearing contributions;
- pure composition and conflict laws;
- explicit, authorized withdrawal;
- revision, provenance, and evidence requirements;
- derived indexes and closure boundaries;
- macro governance for relation declarations.

This RFC does not define:

- a generic map CRUD API;
- raw key/value records as semantic relations;
- silent overwrite;
- mutation-based removal;
- a global relation registry;
- a second prototype precedence algorithm;
- a second control-policy priority system;
- compatibility, migration, or deprecation behavior;
- implementation edits.

* Durable POO identity

Every relation, contribution, conflict, and withdrawal is a native POO object
of:

#+begin_example
github.com/mighty-gerbils/gerbil-poo@1c3225637525400341a09e958296962c10184ead
#+end_example

POO Flow owns the domain algebra. =gerbil-poo= owns object identity, prototype
ancestry, extension, composition, delegation, super, and precedence.

* Central decision

The minimal Module relations are three distinct POO object families:

1. export relations;
2. direct import relations;
3. capability requirement relations.

Each family has:

- a typed-empty identity value;
- identity-bearing contribution objects;
- a pure compatible-composition operation;
- a typed conflict object;
- a typed authorized-withdrawal object;
- a derived lookup or closure projection;
- an evidence receipt.

There is no generic relation map whose CRUD operations define all three
domains.

* Relation object model

#+begin_example
typed-empty relation
  + contribution objects
  + native prototype ancestry
  + domain composition law
  -> typed relation object
#+end_example

A contribution is an object, not a key/value pair.

Every contribution identifies:

- contribution identity;
- relation domain;
- owning Module identity and revision;
- origin prototype or Profile identity;
- semantic subject identity;
- contributed value or constraint identity;
- direct provenance;
- required capability when applicable;
- source evidence.

* Export relation

** Export contribution

An export contribution relates:

#+begin_example
Module identity + export identity -> Profile operand identity
#+end_example

The Profile operand remains a native Profile or ProfileBundle object.

The contribution does not copy, flatten, or re-identify the operand.

** Compatible composition

Export contributions with distinct export identities accumulate.

Repeated contribution of the same contribution identity is idempotent.

Repeated contribution of the same export identity and same Profile operand
identity is idempotent when provenance and constraints are compatible.

** Export conflict

Two contributions to the same export identity with different Profile operand
identities create an export conflict.

The conflict may:

- resolve through an explicitly admitted native prototype precedence rule with
  complete selected and shadowed ancestry evidence; or
- remain unresolved and fail closed.

Iteration order, source order, alist overwrite, and a generic =override= token
are not valid resolution rules.

** Export withdrawal

Export withdrawal identifies one exact contribution identity.

It does not delete a key in place. It contributes an authorized withdrawal to a
new Module revision whose active export projection excludes the target.

Withdrawal of an inherited contribution must occur at its owning authority or
carry an explicit domain capability.

* Direct import relation

** Import contribution

A direct import contribution is an identity-bearing edge between:

- the owning Module revision;
- a source or declaration identity;
- a target Module identity;
- an optional target revision constraint;
- an instance identity;
- an optional selected export or capability requirement;
- provenance.

An alias is not the import edge identity.

Two aliases of the same target may represent distinct Module instances and
therefore remain distinct contributions.

** Compatible composition

Independent import edges accumulate.

The same contribution identity is idempotent.

The same target Module may appear through multiple distinct instance
identities.

** Import conflict

A reused instance identity with incompatible target, revision, or authority
constraints creates an import conflict.

The conflict fails closed unless a domain rule resolves it with complete
evidence.

** Import withdrawal

Import withdrawal targets one direct import contribution.

It cannot directly delete:

- a transitive derived dependency;
- a dependency owned by another Module;
- a responsibility-derived dependency;
- an edge required by an independently selected Profile.

The active recursive closure is recomputed from the new direct relation and
selected roots.

* Capability requirement relation

** Requirement contribution

A capability requirement contribution identifies:

- requirement identity;
- authority domain;
- required capability or constraint object;
- owning Module, Profile, or responsibility identity;
- provenance;
- attenuation evidence.

The relation contains requirements, not grants.

** Compatible composition

Independent requirements accumulate.

Repeated contribution identity is idempotent.

Composition preserves or narrows the admissible authority set.

No contribution may widen authority or convert absence of a requirement into a
grant.

** Requirement conflict

Requirements that cannot be satisfied together create an explicit capability
requirement conflict.

Priority does not silently erase a lower-priority independent requirement.

The conflict is resolved by the owning control-policy algebra or fails closed.

** Requirement withdrawal

Requirement withdrawal is non-monotonic and requires:

- exact target contribution identity;
- authority to alter the owning requirement;
- owning Module or Profile revision transition;
- reason and source evidence;
- proof that independent inherited requirements remain;
- cache invalidation.

A generic =remove= operation cannot weaken capability requirements.

* Typed-empty identity

The typed-empty value is the semantic identity element of compatible
composition:

#+begin_example
empty(domain) compose relation = relation
relation compose empty(domain) = relation
#+end_example

These equalities are semantic. An implementation may return a distinct relation
object with new construction evidence.

Empty values from different domains are never interchangeable.

The sharing, fresh-instance, and copy-on-extension rules are owned by
[[file:45-100-canonical-typed-empty-poo-values-shared-prototype-copy-on-extension-and-cache-safety.org][45-100]].

* Contribution composition laws

** Domain closure

Composition of two values from the same relation domain returns a value in that
domain or a typed conflict.

Cross-domain composition is invalid.

** Associativity

Compatible contribution composition is semantically associative.

Grouping cannot change the active contribution set, conflict set, provenance,
or authority result.

** Permutation independence

Independent compatible contributions are permutation-independent.

Source order is not semantic priority.

** Idempotence

Reapplying the same contribution identity does not duplicate its semantic
effect.

** Provenance conservation

Composition preserves every active contribution's origin and evidence.

** Conflict explicitness

Incompatible contributions produce typed conflict objects rather than implicit
overwrite or exception-only control flow.

** Authority neutrality

Contribution and relation composition grant no capability.

** Copy-on-extension

Composition returns a new relation identity when active semantic content
changes and leaves its inputs observationally unchanged.

* Conflict object

A typed conflict object identifies:

- relation domain;
- semantic subject identity;
- conflicting contribution identities;
- owning Module and revision identities;
- native prototype ancestry;
- constraints that remain independently active;
- admitted resolution policy identity, if any;
- selected and shadowed origins, if resolved;
- unresolved reason and actionable alternatives.

A conflict object is evidence, not authority.

A runtime token, source order, or hidden registry cannot resolve it.

#+begin_src mermaid
flowchart TD
  Empty["typed-empty relation"] -->|"accepts identity-bearing contribution"| Relation["typed relation object"]
  ContributionA["contribution A"] -->|"pure compatible composition"| Relation
  ContributionB["contribution B"] -->|"same subject; compare domain law"| Decision{"compatible?"}
  Relation -->|"supplies active provenance"| Decision
  Decision -->|"yes; preserve both origins"| Next["new relation identity"]
  Decision -->|"no; retain every constraint"| Conflict["typed conflict object"]
  Conflict -->|"native precedence and policy evidence complete"| Resolved["resolved relation and receipt"]
  Conflict -->|"resolution absent or unauthorized"| Rejected["fail-closed rejection"]
  Withdrawal["authorized withdrawal object"] -->|"targets exact contribution in new revision"| Next
#+end_src

Every edge names a domain judgment rather than a map operation.

* Withdrawal algebra

Withdrawal is a typed POO object and an explicit revision event.

It is not ordinary composition because it changes the active contribution set
non-monotonically.

The evidence history remains monotonic:

#+begin_example
prior contribution receipt
  + withdrawal receipt
  -> new active projection with complete history
#+end_example

Withdrawal must:

- target an exact active contribution;
- identify the owning authority;
- identify source and target revisions;
- preserve the withdrawn contribution's historical receipt;
- preserve unrelated contributions;
- invalidate affected indexes and closures;
- fail on stale or absent targets;
- grant no authority.

* Derived indexes

Implementations may derive bounded lookup indexes for:

- export identity;
- import edge and instance identity;
- capability requirement identity;
- conflict subject identity;
- withdrawal target identity.

An index:

- is derived from the typed relation object;
- carries relation and revision identity;
- is invalidated by contribution or withdrawal;
- cannot accept mutation as semantic input;
- cannot become a public generic map;
- does not replace native POO ancestry.

* Recursive and fixed-point boundary

Only direct import contributions belong to the direct import relation.

Recursive imports are derived through selected Profiles and responsibility
reachability.

Cycles are evaluated through POO Flow fixed-point semantics with budgets,
observability, and continuable conditions. They are not rejected merely because
the direct relation graph is cyclic.

Withdrawal triggers a new closure evaluation. It does not mutate a live closure
in place.

* Priority and precedence separation

Native POO prototype precedence resolves object ancestry.

Control-policy priority resolves authorized policy decisions as defined by
[[file:45-90-poo-control-policy-composition-priority-conflict-and-veto-resolution.org][45-90]].

Relation composition does not introduce a third generic priority axis.

An export conflict may consult admitted native precedence. A capability
requirement conflict may consult control policy. Neither may erase independent
constraints without evidence.

* Macro governance

Functions and native POO objects remain the default abstractions.

A bounded macro may generate repeated contribution object declarations only
when it:

- expands to ordinary POO-native objects and pure functions;
- assigns stable source and contribution identities;
- does not parse a generic CRUD language;
- does not own conflict resolution;
- does not authorize withdrawal;
- does not interpret priority;
- does not mutate a relation.

No public macro is introduced for =append=, =override=, =delete=, or
=withdraw=.

Advanced extension uses contribution, conflict, and withdrawal POO objects
directly.

* Relation evaluation sequence

#+begin_src mermaid
sequenceDiagram
  participant Author as "Module author"
  participant Relation as "typed relation object"
  participant Compose as "pure domain composition"
  participant Conflict as "conflict policy"
  participant Revision as "Module revision"
  participant Derive as "closure and index evaluator"

  Author->>Relation: "provides identity-bearing contribution"
  Relation->>Compose: "submits active contributions and provenance"
  Compose-->>Relation: "returns new relation or typed conflict"
  Relation->>Conflict: "submits conflict without losing constraints"
  Conflict-->>Revision: "returns authorized resolution or rejection"
  Author->>Revision: "submits authorized withdrawal when required"
  Revision->>Derive: "publishes new direct relation identities"
  Derive-->>Revision: "returns rebuilt indexes and closure evidence"
#+end_src

No participant mutates an admitted relation object in place.

* Evidence projection

A contribution receipt identifies:

- relation domain;
- contribution identity;
- semantic subject and value identities;
- owning Module and revision;
- origin prototype, Profile, or responsibility;
- direct provenance;
- capability requirements;
- source identity;
- authority neutrality.

A relation composition receipt identifies:

- input relation identities;
- typed-empty identity when used;
- active contribution identities;
- output relation identity;
- compatibility judgments;
- conflict identities;
- native precedence evidence;
- preserved constraints;
- derived index invalidations.

A withdrawal receipt identifies:

- withdrawal identity and domain;
- target contribution identity;
- authorizing capability;
- source and target revisions;
- reason and provenance;
- preserved unrelated contributions;
- cache and closure invalidations;
- historical receipt retention.

* Failure behavior

Relation construction or composition fails closed when:

- relation domains differ;
- contribution identity is missing;
- semantic subject or value identity is missing;
- provenance is incomplete;
- incompatible contributions are silently overwritten;
- a generic option token replaces a domain law;
- an import instance identity points to incompatible targets;
- capability requirements become weaker without authority;
- native precedence or policy evidence is incomplete;
- input mutation is observable.

Withdrawal fails closed when:

- the target contribution is absent or stale;
- the caller lacks domain authority;
- the target belongs to another owner;
- an inherited independent requirement would be erased;
- source or target revision identity is absent;
- affected derived indexes cannot be invalidated;
- history would be discarded.

* Rejected alternatives

The following alternatives are rejected:

- one map type for all Module relations;
- public =get=, =put=, =append=, =override=, and =delete= CRUD operations;
- representing contributions as raw key/value pairs;
- source order as conflict resolution;
- silent last-write-wins exports;
- alias text as import edge identity;
- capability requirement override by priority alone;
- deleting transitive imports directly;
- mutating an admitted relation in place;
- erasing withdrawn history;
- using derived indexes as semantic truth;
- promoting current unverified option-policy helpers by name;
- compatibility wrappers for legacy relation records.

* Consequences

Each Module relation becomes a meaningful POO algebra instead of a generic map.

Composition remains functional and identity-preserving. Conflicts remain
explicit. Withdrawal remains authorized, revisioned, and historically
observable.

Exports, imports, and capability requirements can evolve independently without
creating three incompatible versions of a generic CRUD interface.

#+subtitle: Semantic admission, runtime execution, disclosure, live proof, and canonical scope

* RFC status

- Status :: Accepted design
- Kind :: Normative capability and authorization protocol
- Semantic core :: POO-native capability requirements and explicit pure/live separation
- Related modules :: =45-50-pure-slot-demand-identity-projections-and-cache-isolation.org= and =45-51-live-evaluation-context-narrowing-and-resource-conservation.org=

This module separates capability artifacts from capability roles. It prevents live tokens, runtime execution authority, and disclosure authority from being confused with semantic admission or business-result identity.

* Core decision

#+begin_quote
Capability requirement, canonical scope, live proof, and admission receipt are separate artifacts. Semantic admission, runtime execution, and disclosure are separate authority roles. Only a canonical semantics-affecting scope participates in semantic target identity; live proof never does.
#+end_quote

The normative capability roles are:

#+begin_src text
SemanticAdmissionCapability
RuntimeExecutionCapability
DisclosureCapability
#+end_src

They may share a lower-level POO capability abstraction, but they do not share identity, token use, validation boundary, or cache semantics.

* Typst formalization: artifact and role isolation

The four artifacts inhabit distinct types.  Possessing a requirement, canonical
scope, or receipt is not equivalent to possessing live execution authority.

#+begin_src typst

  "RuntimeAuthority"("scope"(s)) & = bot \

Only an explicitly semantics-affecting canonical scope may occur inside the
semantic target.  Requirements, live proofs, and receipts remain separate
projections of the demand.

* Four capability artifacts

Every role distinguishes:

#+begin_src text
CapabilityRequirement
CapabilityScopeProjection
LiveCapabilityProof
CapabilityAdmissionReceipt
#+end_src

** Capability requirement

A requirement is a pure POO value declared by a Profile, strategy, resolver policy, runtime adapter policy, or evidence projection.

It identifies:

- required semantic role;
- requested scope;
- declaring POO definition identity;
- policy and protocol identity;
- attenuation rules;
- failure behavior.

** Capability scope projection

A scope projection is a canonical pure value describing the authority that was requested or admitted. It contains no token, secret, lease handle, or process session.

It supports:

- stable identity;
- subset and attenuation comparison;
- evidence projection;
- cross-proof equivalence;
- cache and semantic-view classification.

** Live capability proof

A live proof is an execution-scoped token, lease, session, handle, or other authority-bearing resource.

It is:

- non-serializable;
- non-cacheable;
- excluded from semantic identity;
- time- and scope-bounded;
- invalid after expiry or context close;
- unable to be reconstructed from a receipt.

** Capability admission receipt

An admission receipt records that a live proof was validated or rejected for a canonical scope at one boundary.

The receipt is pure evidence. It is not a token, does not extend a lease, and cannot authorize a future operation.

* Semantic admission capability

Semantic admission controls which contributions, resolver policies, submodule providers, or other semantic participants may enter a view.

The canonical relation is:

#+begin_src text
BaseCompositionIdentity
+ CanonicalAdmissionScopeProjection
-> AdmittedSemanticViewIdentity
#+end_src

A semantic slot target is then derived from the admitted view:

#+begin_src text
AdmittedSemanticViewIdentity
+ SemanticSlotReference
+ semantic evaluator protocol identity
-> SemanticSlotTargetIdentity
#+end_src

* Required admission and explicit filtering

Missing semantic capability must not silently select a weaker composition.

The policy declares one of:

- Required admission :: The scope is required. Failure to prove it prevents target construction and fails closed.
- Explicit filtering semantics :: An unadmitted candidate is excluded, and the resulting canonical admitted view has a distinct identity and evidence.

Filtering is semantic policy. It is not an operational fallback inferred from token absence.

Priority, including =force=, cannot admit an unauthorized candidate.

* Runtime execution capability

Runtime execution capability authorizes an effect or adapter, including:

- filesystem or network access;
- external process execution;
- cache materialization;
- runtime or Marlin handoff;
- deployment or publication;
- hardware or resource adapter use.

Runtime execution capability:

- does not alter the business candidate set;
- does not enter the business-result cache key;
- is held by =LiveEvaluationContext=;
- is revalidated immediately before the effect;
- is delegated to a child only through explicit narrowing;
- produces operational authorization and effect receipts.

Missing or expired authority produces operational authorization failure, not a business semantic value.

If an adapter changes pure business meaning, it is not merely a runtime adapter. Its semantic protocol identity must participate in strategy or admitted-view identity.

* Disclosure capability

Disclosure capability controls:

- result delivery;
- visible fields;
- evidence fields;
- redaction level;
- explanation depth;
- secret-bearing provenance.

It does not alter business computation.

- Business results may be shared across disclosure scopes.
- Every subscriber is reauthorized at delivery.
- Evidence projection identity includes canonical disclosure scope.
- A cached value is not disclosed merely because it exists.
- Denied disclosure does not trigger a new semantic computation.
- Redacted evidence cannot be used as authority.

* No cross-role substitution

The roles are not interchangeable:

#+begin_src text
semantic admission capability is not runtime execution capability
runtime execution capability is not disclosure capability
disclosure capability is not semantic admission capability
#+end_src

Consequently:

- authority to view a production result does not authorize deployment;
- authority to execute a network request does not admit a provider into composition;
- semantic admission of a contribution does not disclose its secret evidence;
- priority cannot override any capability role;
- recovery or resolver authority is not inferred from these roles.

Recovery and resolver authority remain separate control-plane authority governed by proposal, live authorization, and bounded portal protocols.

* Canonical scope projection

A canonical scope projection:

- contains no token, secret, or live handle;
- describes allowed semantic slots, operations, adapters, or disclosure fields;
- includes policy and protocol identity;
- supports subset and attenuation;
- gives equivalent scopes the same identity across different live proofs;
- may appear as an opaque digest under evidence redaction.

Two different live proofs for the same canonical scope produce:

#+begin_src text
the same admitted semantic view
the same semantic cache namespace
different authorization event receipts
#+end_src

The system must not use a token digest as a shortcut for canonical scope.

* Lease expiry and reauthorization

An admission receipt does not extend a live lease.

When a semantic result exists but an earlier proof has expired:

- the result identity remains unchanged;
- a new proof may establish the same canonical scope;
- successful reauthorization may reuse the semantic result;
- runtime effects still require a current runtime proof;
- delivery still requires a current disclosure proof;
- historical receipts cannot be presented as live authority.

* Child-context attenuation

When deriving a child context:

- semantic admission scope remains the same or becomes narrower;
- runtime capabilities are explicitly delegated and narrowed;
- disclosure scope becomes narrower or equal;
- lease lifetime does not exceed the parent;
- sibling scopes are not unioned.

If semantic admission scope becomes narrower, a distinct =AdmittedSemanticViewIdentity= and semantic target may result.

Changes limited to runtime or disclosure scope do not create a different business target.

* Shared evaluation

Multiple subscribers may share evaluation only when their semantics-affecting canonical scope produces the same semantic target.

- Subscriber tokens are never unioned.
- The worker uses the minimum authority required by the computation.
- Runtime effects validate execution authority at use time.
- Result delivery validates disclosure authority per subscriber.
- Authorization, denial, and delivery receipts remain distinct.

* Capability role declaration

Capability extension remains POO-native and need not use a closed enumeration. Every capability prototype nevertheless declares:

- its normative authority role;
- whether it changes semantic target identity;
- its validation boundary;
- its canonical scope projection;
- its child attenuation rule;
- its cache and evidence behavior;
- its expiry and revalidation rule.

A capability that cannot classify these properties fails closed. It is not defaulted into the runtime or semantic plane.

Concrete objects and operations must be based on verified native =gerbil-poo= interfaces rather than a new capability DSL.

* Cache isolation

The namespaces are:

- Semantic result namespace :: Includes canonical semantics-affecting admission scope.
- Evidence namespace :: Includes canonical evidence and disclosure projection.
- Operational namespace :: Includes runtime execution attempts and capability checks.
- Authorization namespace :: Includes validation events and receipts.

Live proof, lease, token, handler, or session identity never becomes a business-result cache key.

Serving a cached value always revalidates current disclosure authority. Performing a cached or planned runtime effect always revalidates current execution authority.

* Evidence requirements

Capability evidence records:

- requirement identity and declaring POO definition;
- normative authority role;
- requested and admitted canonical scope identities;
- validation boundary;
- admission, rejection, or filtering result;
- admitted semantic view identity when applicable;
- runtime effect authorization and receipt;
- disclosure projection and delivery result;
- lease expiry and reauthorization;
- parent and child attenuation;
- redacted proof metadata permitted for disclosure.

It never serializes live authority material.

* Implementation checklist

- [ ] Define POO-native requirement, canonical scope, live proof, and receipt artifacts.
- [ ] Define semantic admission, runtime execution, and disclosure authority roles.
- [ ] Require every capability prototype to declare its role and identity effect.
- [ ] Build admitted semantic views from canonical scopes rather than token identities.
- [ ] Implement required admission and explicit filtering as distinct policies.
- [ ] Prevent token absence from causing silent weaker fallback.
- [ ] Revalidate runtime authority immediately before effects.
- [ ] Revalidate disclosure authority immediately before delivery.
- [ ] Keep runtime and disclosure scope outside business-result identity.
- [ ] Keep live tokens, leases, secrets, and handles out of pure projections.
- [ ] Implement canonical scope subset and attenuation.
- [ ] Prevent capability union across children and subscribers.
- [ ] Treat expired receipts as evidence rather than authority.
- [ ] Reuse results across different proofs of the same canonical scope.
- [ ] Generate separate semantic, runtime, disclosure, and authorization receipts.
- [ ] Validate final capability objects against real =gerbil-poo= primitives.

* Non-goals

- Do not use one generic token for semantic admission, runtime execution, and disclosure.
- Do not hash live proof or token identity into business semantic identity.
- Do not let missing authority silently select a weaker composition.
- Do not let priority or =force= bypass capability validation.
- Do not infer recovery or resolver authority from another capability role.
- Do not union subscriber or sibling capabilities.
- Do not treat a receipt as reusable live authority.
- Do not introduce a capability registry, closed enum, or raw capability DSL.

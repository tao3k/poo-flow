#+title: ProfilePriority Value and Contract Refinement

* Status

Approved in conversation on 2026-07-30.  This document freezes the semantic
value domain and contract.  Implementation remains subject to the checklist
below.

* Objective

Define one deterministic POO-native value domain for profile control priority.
The shallow =profile= syntax and advanced POO profile construction must project
the same values, total order, canonical identity, and evidence.

* Ownership

This refinement specializes the Type and Contract foundation in
[[file:45-120-01-poo-native-type-and-contract-prototype-foundation.org][POO-native
Type and Contract Prototype Foundation]].

=poo-flow-core= owns the =ProfilePriority= semantic Type, its Contract,
canonical identity, comparison, and evidence projection.  It does not export a
new priority macro or clause language.

Numeric priority merge semantics remain owned by
[[file:45-101-typed-module-relation-contribution-composition-conflict-and-withdrawal-algebra.org][Typed
Module Relation Contribution and Conflict Algebra]].  Profile syntax remains
owned by
[[file:45-48-compose-function-profiles-strategy-and-lazy-evaluator-boundary.org][Compose,
Profiles Strategy, and Lazy Evaluator Boundary]].  Cache identity remains owned
by
[[file:45-122-poo-dispatch-semantic-plane-candidate-resolution-inherited-continuation-and-observability-contract.org][POO
Dispatch Semantic Plane and Observability Contract]].

* Type and Contract relation

=ProfilePriority= is a Type identity for one closed semantic value family:

#+begin_example
ProfilePriority
  = Default
  | Numeric(exact-real)
  | Force
#+end_example

The =ProfilePriority= Contract is a Type prototype refinement that requires:

- exactly one of the three admitted variants;
- a canonical semantic identity;
- a deterministic total-order position;
- a canonical evidence receipt;
- no runtime handle, ambient environment value, or syntax object.

The domain is closed so every admitted pair is comparable.  Higher-order POO
policy objects may calculate, select, or transform a priority, but their final
projection must be an admitted =ProfilePriority= value.  They cannot extend the
priority domain with an incomparable fourth variant.

* Numeric domain

=Numeric= admits exact real numbers only.  Integers, negative values, zero,
positive values, and exact rational values are valid.  The following are not
valid:

- complex numbers;
- inexact floating-point values;
- NaN or infinity;
- values whose canonical rational identity cannot be produced.

An exact rational is normalized to a reduced numerator and a positive
denominator.  Therefore =2/4= and =1/2= have one semantic identity.  The
denominator of an integer is canonically =1=.

* Total order

The order is:

#+begin_example
Default < every Numeric value < Force
#+end_example

Numeric values use ordinary increasing exact-real order.  An unannotated
profile priority projects =Numeric(0)=.  Equal canonical values compare equal
and enter the equal-priority POO composition law.  The order contains no
source-position or module-loading tie breaker.

The endpoint values =profile-priority/default= and
=profile-priority/force= are ordinary immutable POO values.  They are not
macros.  A numeric priority is an ordinary immutable value of the same Type
family.

* Canonical identity and receipt

The canonical identity schema is =profile-priority.v1=.  Its semantic payload
is exactly one of:

#+begin_example
(profile-priority.v1 default)
(profile-priority.v1 numeric <reduced-numerator> <positive-denominator>)
(profile-priority.v1 force)
#+end_example

The canonical digest is derived from that payload.  Diagnostic attribution,
source location, profile alias, parser order, module loading order, and
fixed-point epoch are excluded from priority identity.  They may appear in the
surrounding explanation or evaluation receipt.

A cache or composition receipt must carry the canonical priority identity, not
the original Scheme literal and not a printed inexact approximation.

* Condition refinement and recovery vocabulary

=ProfilePriorityCondition= is one Contract refinement of the shared
=poo-flow-core= structured-condition ObjectType.  It is not a result wrapper,
not three condition subclasses, and not a local object that forces
=func.ss -> objects.ss= dependency.

The refinement admits exactly three reason values:

- =unsupported-variant=: the input is outside the closed
  =Default | Numeric | Force= family;
- =non-exact-real=: the numeric candidate is complex, inexact, NaN, infinite,
  or otherwise lacks a canonical exact-real identity;
- =canonical-identity-mismatch=: a supplied receipt does not match the
  canonical =profile-priority.v1= projection.

An ordinary exact rational that is not reduced is valid input.
=profile-priority/normalize= reduces it rather than emitting a condition.

Every admitted condition carries:

- its =ProfilePriorityCondition= Contract identity;
- one reason and a reason-specific detail;
- the expected =ProfilePriority= Contract;
- redacted input attribution;
- source and generation attribution;
- the admissible recovery-action set.

The admissible recovery actions are:

- =use-value=: supply a replacement candidate and re-enter normalization;
- =defer=: suspend only for an unresolved pure dependency;
- =abort-realization=: terminate the current realization with evidence.

=use-super= is not meaningful for value normalization.
=exclude-refinement= belongs to the outer composition owner and is not a
restart of this condition.  The priority module never substitutes numeric =0=,
uses source order, or selects an arbitrary profile as implicit recovery.

The restart vocabulary and authority remain owned by
[[file:45-03-runtime-context-and-recovery.org][Runtime Context and Recovery]].
This refinement only narrows the admissible action set for this condition
family.

* Implementation module ownership

The implementation follows
[[file:45-120-02-module-local-functional-kernel-governance.org][Module-local
Functional Kernel Governance]].  The dependency direction is:

#+begin_example
types.ss -> func.ss -> objects.ss -> interface.ss
#+end_example

The family is rooted under one =profile-priority/= module directory.

** =types.ss=

=types.ss= owns:

- the =ProfilePriority= Type identity;
- the closed =Default | Numeric | Force= classification;
- the =ProfilePriorityCondition= refinement, reason classification, and
  Contract projections over the shared core condition ObjectType;
- Type-level inputs and outputs required by the pure kernel.

It does not import the functional kernel, POO objects, the public interface, or
the profile macro owner.

** =func.ss=

=func.ss= imports =types.ss= and owns only named pure functions with explicit
consumers:

- =profile-priority/normalize=;
- =profile-priority/compare=;
- =profile-priority/receipt=.

It does not define POO prototypes, macros, registries, caches, runtime handles,
or anonymous policy hooks.

*** Closed functional kernel

The semantic signatures are:

#+begin_example
profile-priority/normalize
  PriorityInput
  -> CanonicalProfilePriority
   | StructuredCondition

profile-priority/compare
  CanonicalProfilePriority
  x CanonicalProfilePriority
  -> Ordering

profile-priority/receipt
  CanonicalProfilePriority
  -> profile-priority.v1
#+end_example

=profile-priority/normalize= owns exact-real admission, rational reduction,
variant validation, and structured failure projection.  Contract admission
delegates to this function rather than maintaining a parallel predicate or
coercion path.  Success returns the canonical POO value directly.  Failure
returns the existing structured condition value directly.  There is no
=Result= record, =SemanticOutcome= family, or =ProfilePriorityResult= wrapper.
The function consumes the shared condition foundation admitted by =types.ss=;
it does not import local =objects.ss= to construct a failure.

=profile-priority/compare= consumes canonical values only and implements the
complete =Default < Numeric < Force= order.  Semantic equality is derived from
the =equal= comparison result; there is no independent equality algorithm.

=profile-priority/receipt= projects the canonical identity payload.  Digest
construction consumes that payload through the shared content-identity owner;
this module does not implement another hash function.

The functional kernel is closed to additional ordinary functions unless an RFC
demonstrates a new pure responsibility that cannot be derived from these three.
Priority merge, authority admission, syntax lifting, caching, dispatch, and
runtime recovery remain in their existing owners.

*** Functional laws

- normalization is idempotent;
- normalization maps semantically equal exact rationals to one canonical value;
- comparison is total, antisymmetric, and transitive;
- comparison equality agrees with canonical identity equality;
- receipt projection is deterministic and injective over canonical values;
- all three functions are independent of alias, source location, loading
  order, fixed-point epoch, runtime handles, and ambient environment state.

*** Condition and continuation boundary

=func.ss= constructs a structured condition but never invokes, captures, or
stores a continuation.  The Contract admission boundary consumes the
=CanonicalProfilePriority | StructuredCondition= result:

- a canonical value proceeds to comparison, receipt, and composition;
- a condition produces an authoritative =ObservationEvent=;
- the recovery coordinator may raise the admitted continuable condition and
  request a =RecoveryDecision=;
- an authorized replacement value re-enters
  =profile-priority/normalize=;
- denial, deferral, abort, or exhausted budget preserves the condition and
  decision evidence without manufacturing a priority value.

Recovery authority, restart vocabulary, continuation confinement, and decision
receipts are owned by
[[file:45-03-runtime-context-and-recovery.org][Runtime Context and Recovery]].
=ObservationEvent= and semantic-budget ownership are defined by
[[file:45-120-03-module-debug-observability-recovery-and-telemetry-plane-governance.org][Module
Debug, Observability, Recovery, and Telemetry Plane Governance]].
=RecoveryDecision= authority, typed budget requests, and successor-event
contracts are defined by
[[file:45-120-18-recovery-decision-prototype-family-and-coordinator-boundary.org][RecoveryDecision
Prototype Family and Coordinator Boundary]].

The raw continuation remains confined to its suspended cell.  Each resumption
requires an authorized decision, consumes its admitted budget, and produces
successor observation evidence.  A recovery loop therefore cannot silently
retry forever.

An invalid literal detected by the contextual macro remains an expansion-time
syntax error.  It does not enter runtime continuation or recovery.  A
structured normalization failure is not a canonical value and cannot enter a
profile-refinement cache.

** =objects.ss=

=objects.ss= imports =types.ss= and =func.ss=.  It owns:

- the immutable =Default=, =Numeric=, and =Force= POO prototype family;
- the two named endpoint values;
- binding the named pure functions to POO responsibilities and dispatch;
- native POO construction and refinement of admitted priority values.

It does not duplicate normalization, comparison, receipt, or validation logic.

** =interface.ss=

=interface.ss= projects exactly six semantic capabilities:

- =ProfilePriority=
- =ProfilePriority/contract=
- =profile-priority/default=
- =profile-priority/numeric=
- =profile-priority/force=
- =profile-priority/admit=

=ProfilePriority= is the Type projection.
=ProfilePriority/contract= is its Contract projection.
=profile-priority/default= and =profile-priority/force= are the immutable
endpoint POO values.  =profile-priority/numeric= is the native Numeric POO
prototype used by advanced construction.

=profile-priority/admit= is the only named admission boundary.  It accepts a
candidate, delegates pure normalization to =profile-priority/normalize=, and
either returns the canonical priority value or routes the structured condition
into the existing observation and recovery plane.  It does not own priority
merge, cache identity, dispatch policy, or recovery authority.

Normalization internals, representation details, and parser-specific helpers
remain private.  =profile-priority/normalize=,
=profile-priority/compare=, and =profile-priority/receipt= are not re-exported.
=interface.ss= exports no global =priority= macro.

** Macro dependency

=profile-composition-clause-syntax.ss= may depend on the small
=profile-priority/interface.ss= projection at the appropriate expansion phase.
It may only lower contextual syntax to ordinary imports, native POO values, and
direct references to named functions.  The macro must not generate hidden
functions, define priority semantics, import implementation internals, or
create a reverse dependency into the profile-priority family.

The macro checks literal syntax shape during expansion.  Its generated runtime
code passes both literals and dynamic POO expressions through
=profile-priority/admit=.  It does not normalize a value at expansion time and
does not preserve a syntax object in the runtime representation.

* Interface projection

The public module surface is the six-item projection defined by
=profile-priority/interface.ss=.  Neither the shallow syntax nor advanced POO
construction receives a parallel helper API.

* POO dispatch responsibilities

The family exposes exactly three responsibility identities through native
=gerbil-poo= dispatch:

- =admit= on the =ProfilePriority/contract= receiver;
- =compare= on admitted =ProfilePriority= value receivers;
- =receipt= on admitted =ProfilePriority= value receivers.

=profile-priority/admit= is a thin functional projection of the Contract
receiver's =admit= responsibility.  The responsibility binds the private
=profile-priority/normalize= function and owns no second normalization
algorithm.

The =Default=, =Numeric=, and =Force= prototypes bind =compare= to the same
private =profile-priority/compare= function and bind =receipt= to the same
private =profile-priority/receipt= function.  They do not duplicate one method
body per variant.  Variant behavior remains data in the closed Type domain,
not three independently drifting implementations.

Advanced consumers invoke the responsibilities through native POO object
dispatch.  The interface does not export ordinary =compare= or =receipt=
helper functions, raw =kind= or =raw-value= representation accessors, or a
second generic-method layer.  The standard POO identity slot remains the
identity mechanism; this family adds no separate =identity= responsibility.

Dispatch candidate selection follows native prototype precedence.  Numeric
profile priority is an input to control-policy merge only; it never orders
methods, changes C3 precedence, or selects a dispatch provider.  Native
precedence separation remains owned by
[[file:45-102-native-prototype-precedence-and-typed-relation-conflict-resolution-bridge.org][Native
Prototype Precedence and Typed Relation Conflict Resolution Bridge]].

Each responsibility dispatch uses the existing dispatch explanation boundary:
receiver semantic identity, responsibility identity, provider prototype and
generation, semantic outcome or structured condition, and admitted
observation-budget evidence.  This family creates no separate trace stream,
telemetry registry, or debugging API.

The hygienic shallow syntax:

#+begin_src scheme

  (priority 3/2)

Advanced construction uses the native =gerbil-poo= object/prototype interface;
there is no second record representation, wrapper object, or priority DSL.

* Non-goals

* Design reference

The default/numeric/forced ordering and equal-priority merge behavior learn
from [[https://nickel-lang.org/user-manual/merging/#merge-priorities][Nickel
merge priorities]].  The POO object model, Type/Contract ownership, capability
boundary, evidence identity, and fixed-point integration are POO Flow
semantics built on the pinned
[[https://git.cons.io/mighty-gerbils/gerbil-poo][gerbil-poo]] package.

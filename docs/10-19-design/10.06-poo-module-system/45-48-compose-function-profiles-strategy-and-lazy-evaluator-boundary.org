#+title: Compose Function, Profiles Strategy, and Lazy Evaluator Boundary
#+subtitle: Pure orchestration, first-class POO composition policy, and demand-driven fixed-point execution
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative composition protocol
- Semantic core :: Native =gerbil-poo= objects, prototypes, and operations
- Related modules :: =45-41-poo-profile-slot-contribution-priority.org= and =45-47-user-composition-root-binding-and-thin-macro-contract.org=

This module separates the ordinary =compose= function, the first-class =profiles= POO composition strategy, and the POO Flow evaluator.

* Core decision

#+begin_quote
=compose= is a pure ordinary higher-order function. =profiles= is a first-class POO composition-strategy object. =compose= constructs a lazy pure composition value and does not execute fixed-point evaluation.
#+end_quote

The conceptual signature is:

#+begin_src text
compose :
  CompositionStrategy
  x Operand...
  -> PureCompositionValue
#+end_src

This is a semantic contract, not a request to introduce a separate type DSL.

* Responsibilities of =compose=

=compose=:

- receives a strategy POO object and already constructed operand values;
- preserves ordinary Scheme single-evaluation behavior;
- delegates composition semantics to the strategy POO protocol;
- returns a pure, immutable, canonical-projectable composition value;
- preserves strategy identity, operand identities, and provenance references;
- reports structural contract failures through ordinary POO evidence.

=compose= does not:

- identify =profiles= through =case=, name comparison, or a registry;
- parse a macro keyword;
- execute a slot computation;
- compute a fixed point;
- define priority semantics;
- select a resolver;
- validate a live capability token;
- create a semantic generation;
- access a result cache;
- allocate a root anchor;
- establish global registration.

* Responsibilities of the =profiles= strategy

=profiles= is a higher-order POO object that defines the pure Profile-composition protocol:

- strategy semantic identity;
- the POO contract accepted from operands;
- projection of Profile operands into slot contributions;
- preservation of imports, submodules, identities, and capability requirements;
- interpretation of inherited and slot-local priority;
- formation of admitted candidate sets;
- equal-priority canonical combination;
- fail-closed conflict behavior when no canonical combination exists;
- projection of control-plane resolver policy;
- construction of the canonical definition graph;
- pure evidence projections retained by the composition value;
- the demand interface exposed to the evaluator.

These responsibilities are POO strategy semantics. They are not branches embedded in =compose=.

* Responsibilities of the POO Flow evaluator

The evaluator receives an already constructed composition value and performs:

- semantic generation creation or reuse;
- demand-driven slot evaluation;
- fixed-point and cyclic dependency handling;
- current-generation SCC discovery;
- invalidation and cache reuse;
- evaluation and recovery budgets;
- continuable conditions, recovery portals, and resumptions;
- runtime and Marlin handoff;
- semantic, transition, recovery, and operational receipts.

The evaluator does not reinterpret Profile composition rules. It executes the lazy semantic graph projected by the strategy.

* Pure composition value

A pure composition value may conceptually retain:

#+begin_src text
strategy semantic identity
operand semantic identities
lazy definition-graph projection
priority and admission-policy projections
resolver-policy identities
pure provenance references
demand interface
#+end_src

It does not retain:

#+begin_src text
evaluated business-slot cache
live capability token
continuation or recovery portal
worker or scheduler
runtime handle
mutable registry
#+end_src

The lazy definition graph must be represented through real =gerbil-poo= objects and native operations. This RFC does not introduce a raw record, alist, or parallel object DSL.

* Structural validation and semantic evaluation

=compose= and the strategy may reject structural failures without evaluating business slots:

- the strategy does not satisfy the required POO composition protocol;
- an operand cannot provide the required Profile projection;
- a required semantic identity cannot be canonicalized;
- control-plane resolver scopes have no canonical composition;
- a semantic closure captures a live resource forbidden from pure composition.

The following remain demand-driven:

- equal-priority conflict in a business slot;
- a dependency cycle discovered only after demand;
- a slot-computation condition;
- live capability admission;
- fixed-point or evaluation-budget exhaustion.

A structural check must not become an eager whole-system evaluation.

* Strategy extension

An advanced strategy is constructed through native POO prototype extension:

#+begin_src scheme
(def audited-profiles
  (.mix profiles
        audit-policy))

(compose audited-profiles
  base
  wendao-episteme
  production)
#+end_src

The specific operation is illustrative and must be validated against real =gerbil-poo= primitives.

Strategy extension:

- does not modify =compose=;
- does not add a strategy registry;
- does not add a macro;
- contributes its semantic identity to the composition value;
- preserves the observable laws required by =profiles=.

* Empty composition identity

The strategy provides a composition identity element:

#+begin_src scheme
(compose profiles)
#+end_src

This returns the empty =profiles= composition value. It does not return =#f=, allocate a root, or signal an error.

The empty value:

- has a canonical strategy-scoped semantic identity;
- contains no Profile contributions;
- is reusable as the identity element of same-strategy unanchored composition;
- remains a pure composition value rather than a runtime singleton registry entry.

* Single-operand composition

#+begin_src scheme
(compose profiles production)
#+end_src

This produces the canonical single-operand composition value.

It preserves the operand identity and strategy identity. It does not silently turn the operand into a new anchored root or erase the distinction between the Profile and the composition value.

* Same-strategy unanchored nesting

An unanchored composition value using the same strategy may be normalized:

#+begin_src scheme
(compose profiles
  base
  (compose profiles
    wendao-episteme
    production))
#+end_src

It has the same observable semantic result as:

#+begin_src scheme
(compose profiles
  base
  wendao-episteme
  production)
#+end_src

Normalization operates on the pure composition graph. It does not force business slots, depend on operand presentation order, or apply a directional native operation implicitly.

* Anchored roots and different strategies

A composition root created by =user-composition= has an explicit root anchor. When used as an operand, that anchor remains visible and prevents unconditional flattening.

Different strategies also form a boundary:

- a nested value with a different strategy is not automatically flattened;
- it participates only if the outer strategy explicitly admits that operand protocol;
- strategy conversion, if supported, is an explicit POO operation with its own semantic identity and evidence.

* Composition laws

- Purity :: =compose= produces a pure value and performs no runtime handoff.
- Single evaluation :: Each argument expression follows ordinary Scheme single-evaluation behavior.
- Strategy delegation :: Profile semantics come from the strategy POO object.
- Identity element :: Empty same-strategy composition is a canonical identity element.
- Single-operand preservation :: A single operand retains its semantic identity.
- Unanchored same-strategy normalization :: Equivalent nesting does not change observable semantics.
- Anchored-root preservation :: Explicit root identity is not flattened away.
- Strategy-boundary preservation :: Different strategies require explicit admission or conversion.
- Lazy construction :: Composition does not force business slots or evaluate a fixed point.
- No hidden registration :: Construction creates no registry entry, export, or runtime publication.

* Evidence requirements

Composition-construction evidence records:

- strategy semantic identity;
- operand semantic identities;
- empty, single, nested, or anchored composition form;
- same-strategy normalization steps;
- preserved anchored-root boundaries;
- explicit different-strategy admission or conversion identity;
- structural rejection evidence;
- proof that construction did not force business-slot evaluation.

Source argument positions may remain provenance but do not define semantic precedence.

* Implementation checklist

- [ ] Define the minimal POO protocol required from a composition strategy.
- [ ] Implement =compose= as an ordinary pure higher-order function.
- [ ] Verify ordinary Scheme single evaluation of strategy and operands.
- [ ] Delegate Profile semantics without =case=, name comparison, or registry lookup.
- [ ] Construct a pure lazy composition value with canonical projection.
- [ ] Separate structural validation from demand-driven semantic evaluation.
- [ ] Define the =profiles= strategy identity element.
- [ ] Define canonical single-operand composition.
- [ ] Normalize same-strategy unanchored nesting without forcing slots.
- [ ] Preserve anchored user-composition roots.
- [ ] Require explicit admission or conversion for different strategies.
- [ ] Keep live capability, continuation, runtime, cache, and worker state outside the value.
- [ ] Generate construction and normalization evidence.
- [ ] Validate strategy construction and operations against real =gerbil-poo= primitives.
- [ ] Verify that evaluator responsibilities do not leak back into =compose=.

* Non-goals

- Do not turn =compose= into a macro.
- Do not make =profiles= a keyword or closed enumeration.
- Do not evaluate a fixed point during composition construction.
- Do not create a strategy or composition registry.
- Do not flatten an anchored root.
- Do not implicitly convert different strategies.
- Do not add raw alist, record, patch, or callback DSLs.
- Do not reimplement =gerbil-poo= object semantics.

#+title: Native Prototype Precedence and Typed Relation Conflict Resolution Bridge

* Status

Accepted architecture RFC.

This document fixes the semantic bridge from native prototype precedence to
typed relation conflict resolution. It does not authorize implementation work
and does not invent unverified upstream precedence behavior.

* Scope

This RFC defines:

- native precedence as candidate-origin order;
- typed relation admissibility as a separate domain judgment;
- control-policy authority as a third, later judgment;
- selected, shadowed, and independent constraint evidence;
- ambiguity, cycle, resumption, cache, and revision behavior;
- macro governance for precedence-related declarations.

This RFC does not define:

- a replacement precedence algorithm;
- a generic override rule;
- a numeric encoding of prototype order;
- a third priority system;
- source order as precedence;
- silent shadowing;
- a global conflict registry;
- compatibility, migration, or deprecation behavior;
- implementation edits.

* Central decision

Conflict resolution has three ordered judgments:

1. native prototype precedence produces an ordered candidate-origin snapshot;
2. the typed relation law decides whether precedence-based shadowing is
   admissible for this semantic subject;
3. an authorized control policy decides any remaining authority-sensitive
   resolution.

#+begin_example
native candidate order
  -> domain admissibility
  -> authorized policy decision
  -> selected value or fail-closed conflict
#+end_example

No judgment may be skipped.

Native precedence is not automatic override authority.

Native precedence is not numeric control-policy priority.

* Core identities

Every bridge evaluation identifies:

- semantic subject identity;
- typed relation domain;
- relation and Module revision identities;
- contribution identities;
- contribution origin prototype identities;
- native precedence snapshot identity;
- domain admissibility rule identity;
- control policy and capability identities when consulted;
- selected and shadowed origin identities;
- candidate-local and independent constraint identities.

The bridge never resolves anonymous values.

* Native candidate-origin snapshot

The first judgment derives a stable snapshot from verified upstream ancestry
and precedence behavior.

The snapshot contains:

- root object identity;
- direct super relations;
- delegation relations when the verified upstream contract includes them;
- complete candidate origin identities;
- ordered precedence positions;
- upstream algorithm identity and version;
- ancestry cycle or ambiguity status;
- source construction evidence.

A precedence position is an ordered structural fact. It is not a user-facing
number and is not compared with control-policy priority.

Until the upstream delegate contract is verified, delegate edges remain
reported separately from the admitted precedence order.

* Candidate qualification

A relation contribution enters the candidate set only when:

- it belongs to the typed relation domain;
- it targets the same semantic subject;
- it has stable contribution identity;
- its origin prototype is present in the admitted ancestry snapshot;
- its provenance is complete;
- its revision is active;
- its capability requirements are not already rejected.

A contribution outside admitted ancestry cannot gain precedence by source
order, alias, registration time, or numeric annotation.

* Domain admissibility

The typed relation law decides whether two distinct candidate values may be
resolved through native precedence.

The default for distinct values is explicit conflict.

Precedence-based resolution is admitted only when an identity-bearing domain
fact states:

- the relation domain;
- the semantic subject;
- the candidate kinds;
- why shadowing is valid for that subject;
- which constraints remain active;
- which evidence must be retained.

This fact is a POO object. It is not a generic =override= keyword.

If no admissibility fact exists, the candidate order remains diagnostic
evidence and the conflict fails closed.

* Export conflict bridge

For two export contributions to the same export identity:

- identical contribution identity is idempotent;
- identical Profile operand identity with compatible provenance is compatible;
- distinct Profile operand identities create a typed conflict;
- native precedence may select one only when export-domain admissibility is
  explicit;
- the selected Profile operand retains its own candidate-local responsibilities;
- independent relation constraints from other origins remain active;
- every shadowed export origin remains visible in the receipt.

A shadowed Profile operand's local responsibilities do not become active merely
because its origin appears in the precedence list.

This distinction prevents both constraint erasure and accidental activation of
an unselected alternative.

* Import conflict bridge

Native precedence may help identify which prototype contributed an import edge,
but it cannot silently reuse one instance identity for incompatible targets.

An import instance conflict remains subject to direct-import domain laws:

- same edge identity is idempotent;
- distinct instance identities may coexist;
- one instance identity with incompatible target or revision fails closed;
- precedence resolution requires explicit import-domain admissibility;
- recursive imports remain derived after the direct relation is resolved.

* Capability requirement bridge

Capability requirements accumulate independently of value shadowing.

Prototype precedence cannot erase:

- a requirement contributed by an independent active origin;
- an inherited veto;
- an attenuation boundary;
- a proof or handoff capability requirement.

If requirement objects conflict, resolution belongs to the authorized
control-policy algebra.

Control priority is considered only after authority intersection and domain
qualification. It does not reorder the native prototype list.

* Candidate-local and independent constraints

The bridge classifies constraints as:

- candidate-local: reachable only through one candidate value;
- subject-wide: attached to the semantic subject;
- relation-wide: attached to the typed relation;
- Module-wide: attached to the active Module revision;
- authority-wide: attached to the admission context.

When one candidate is selected:

- its candidate-local constraints become active;
- shadowed candidates' candidate-local constraints remain inactive;
- subject-wide, relation-wide, Module-wide, and authority-wide constraints
  remain active;
- no constraint changes class because of precedence position.

The receipt records the classification and result.

* No third priority axis

Prototype precedence and control-policy priority are different:

| Dimension | Owner | Meaning |
|-----------+-------+---------|
| Prototype precedence | =gerbil-poo= | Structural candidate-origin order. |
| Typed relation admissibility | POO Flow relation law | Whether shadowing is semantically legal. |
| Control-policy priority | POO Flow control policy | Strength among authorized policy decisions. |

The bridge introduces no numeric relation priority.

A precedence-list position is never serialized as a reusable priority value.

* Resolution result

A successful bridge returns a POO resolution object containing:

- subject and relation identities;
- native precedence snapshot;
- candidate set;
- admissibility judgment;
- authority judgment when required;
- selected contribution and value;
- shadowed contributions;
- active constraint set;
- inactive candidate-local constraint set;
- conflict and resolution evidence;
- cache dependency identity.

The selected value is not returned without its resolution object.

* Unresolved conflict

An unresolved conflict remains a first-class POO object.

It identifies:

- candidate identities and origins;
- native order when available;
- missing domain admissibility;
- missing authority;
- incompatible constraints;
- ambiguity or cycle state;
- available inspection and recovery actions.

The conflict grants no authority and does not mutate the relation.

* Ambiguity and cycle behavior

The bridge fails closed when:

- the precedence snapshot is incomplete;
- an origin appears more than once without a verified upstream explanation;
- ancestry order is ambiguous;
- a super or delegate cycle prevents a finite admitted snapshot;
- the upstream algorithm exceeds its evaluation budget;
- candidate provenance is missing;
- a domain admissibility object is absent;
- an authority-sensitive resolution lacks capability.

Failure is observable before an uncontrolled recursion consumes the process.

Cycle and budget failures use the POO Flow condition and observation planes.
They preserve diagnostic continuations only under the live continuation
capability rules.

* Continuable recovery

A conflict or precedence condition may expose continuable inspection actions:

- inspect candidates;
- inspect native ancestry;
- explain constraint classification;
- simulate an explicit admissibility object;
- propose a new control-policy object;
- retry against a new Module revision.

Continuation does not:

- mutate the active relation;
- manufacture admissibility;
- grant capability;
- select an arbitrary winner;
- alter the native precedence snapshot in place.

Recovery submits new POO values through normal admission and produces a new
receipt.

* Revision and withdrawal

A contribution withdrawal or prototype revision invalidates the prior
candidate snapshot.

The bridge recomputes:

- active contribution set;
- ancestry snapshot;
- candidate order;
- domain admissibility;
- active constraints;
- policy result;
- derived closure and cache identity.

Withdrawal of the selected contribution may reveal a previously shadowed
candidate. That candidate is not activated until the new revision completes the
entire bridge again.

* Cache safety

A resolution cache key contains:

- Module and relation revision identities;
- semantic subject identity;
- active contribution identities;
- native ancestry and precedence snapshot identity;
- domain admissibility identity;
- control policy and capability context identities;
- constraint classification identity;
- upstream algorithm version;
- observation dependencies.

Changing any input invalidates the cached resolution.

A cached winner without shadowed-origin and constraint evidence is invalid.

* Determinism and replay

With identical:

- Module and relation revisions;
- contribution set;
- native precedence snapshot;
- domain admissibility facts;
- authority context;
- policy objects;
- observation inputs;

the bridge returns an equivalent resolution object.

Source traversal order, hash-map iteration, registration time, and cache
population order cannot affect the result.

* Macro governance

Functions and native POO objects remain the default abstractions.

A bounded internal macro may generate repetitive admissibility object families
only when it:

- expands to native POO objects and pure functions;
- preserves stable subject and rule identity;
- owns no candidate order;
- owns no control priority;
- grants no authority;
- performs no conflict resolution;
- emits inspectable expansion evidence.

No public precedence, override, winner, or priority macro is introduced.

The observer cannot rewrite the active resolution.

* Semantic laws

** Native-order law

Candidate-origin order derives only from admitted native POO precedence.

** Domain-admissibility law

Native order does not authorize shadowing without a typed relation rule.

** Policy-after-domain law

Control-policy priority is considered only after domain and authority
qualification.

** No-third-priority law

The bridge introduces no reusable numeric relation priority.

** Provenance preservation law

Selected and shadowed contribution origins remain visible.

** Independent-constraint law

Independent constraints survive candidate shadowing.

** Candidate-locality law

Shadowed candidates do not activate their candidate-local constraints.

** Revision sensitivity law

Any contribution, ancestry, policy, or authority revision invalidates the
resolution.

** Determinism law

Equivalent complete inputs produce an equivalent resolution.

** Authority neutrality law

Candidate ordering and domain admissibility grant no capability.

** Fail-closed law

Missing precedence, admissibility, constraint, or authority evidence yields a
typed unresolved conflict.

* Evidence projection

A native precedence receipt identifies:

- upstream =gerbil-poo= revision;
- root object identity;
- direct super and delegate evidence;
- precedence snapshot identity;
- candidate origin order;
- algorithm identity and budget;
- cycle and ambiguity status.

A domain admissibility receipt identifies:

- typed relation domain;
- semantic subject;
- candidate kinds and identities;
- admissibility object identity;
- candidate-local and independent constraint classification;
- preserved provenance.

A final resolution receipt identifies:

- selected and shadowed contributions;
- active and inactive constraint sets;
- policy and capability evidence;
- unresolved alternatives when applicable;
- cache dependency identity;
- source and Module revision identities;
- authority neutrality.

* Failure behavior

Bridge evaluation fails closed when:

- an origin is absent from admitted ancestry;
- precedence order is incomplete or ambiguous;
- super or delegate semantics are unverified for the required path;
- a domain conflict lacks explicit admissibility;
- candidate-local and independent constraints cannot be distinguished;
- independent constraints would be erased;
- control policy is consulted before authority qualification;
- a numeric annotation attempts to replace native order;
- candidate provenance is incomplete;
- the evaluation budget is exhausted;
- a cache lacks complete dependency identity.

Every failure identifies the bridge stage, candidates, origin graph, missing
evidence, and permitted recovery actions.

* Rejected alternatives

The following alternatives are rejected:

- using source order as prototype precedence;
- translating precedence positions into public numeric priority;
- treating the first native candidate as automatically authorized;
- using a generic =override= keyword as domain admissibility;
- erasing every constraint from a shadowed origin;
- activating every constraint from an unselected candidate;
- consulting control priority before authority intersection;
- hiding shadowed origins from receipts;
- mutating relation state during continuable recovery;
- accepting an incomplete ancestry snapshot;
- creating a second super or delegation algorithm;
- compatibility wrappers for legacy precedence behavior.

* Consequences

Native prototype precedence remains authoritative for structural origin order
without becoming blanket override authority.

Typed relation laws retain domain meaning and independent constraints.

Control-policy priority remains an authorized decision mechanism rather than a
second ancestry system. Every winner, shadowed origin, constraint, ambiguity,
and recovery proposal remains observable.

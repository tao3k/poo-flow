#+title: POO Control Policy Composition, Priority, Conflict, and Veto Resolution
#+startup: overview

* Status

Accepted architecture.

This RFC freezes how multiple POO-native control policies produce one
ControlDecision for the algebra defined in
[[file:45-89-poo-native-control-condition-decision-and-capability-algebra.org][45-89]].
It does not authorize implementation until the deterministic resolution and
authority tests in this document are complete.

* Formal policy-resolution surface

The formal surface fixes exact integer priority and makes authority
intersection and hard-stop processing strict predecessors of priority
selection.

#+begin_src typst
#let default-priority = 0
#let stronger = (left, right) => left > right

$ "default-priority" = 0 $
$ "stronger"(left, right) := left > right $

$ "resolve-order" = (
  "candidate-admission",
  "constraint-intersection",
  "hard-stop-validation",
  "numeric-priority",
  "equal-priority-merge",
  "final-decision",
) $

$ "unlimited-priority-sentinel" = false $
#+end_src

Numeric priority orders terminal-effect proposals only.  It cannot bypass
candidate admission, remove an admitted constraint, defeat a validated hard
stop, or cross an identity fence.

#+begin_src typst
#let allowed = "allowed"
#let intersect = "intersect"

$ allowed(intersect(a, b), action) =
  (allowed(a, action) and allowed(b, action)) $

$ "order"("authorized-veto") < "order"("numeric-priority") $
$ "order"("authorized-cancellation") < "order"("numeric-priority") $

$ "equal-priority" and "different-effects"
  ==> "fail-closed-conflict" $

$ merge(a, b) = merge(b, a) $
$ merge(merge(a, b), c) = merge(a, merge(b, c)) $
$ merge(a, a) = a $
#+end_src

The equal-priority merge is commutative, associative, and idempotent only for
compatible candidates that refine the same terminal effect.  Different
effects at the greatest priority are a semantic conflict, not an ordering
question.

* Scope

This document owns:

- the POO object families for control policies and decision candidates;
- candidate admission and scope matching;
- authority intersection;
- numeric priority ordering;
- equal-priority merge and conflict behavior;
- explicit veto and cancellation authority;
- deterministic receipt construction; and
- production of exactly one final ControlDecision.

It does not own:

- Profile merge precedence;
- native ~gerbil-poo~ slot precedence;
- Profile composition order;
- raw continuation behavior;
- portable suspension reconstruction;
- package management; or
- a generic configuration merge language.

Priority in this RFC belongs only to control-policy resolution for one
ControlCondition.

* Design references

This design learns from Nickel's merge semantics without importing Nickel
syntax or treating Scheme as a configuration language.

The relevant ideas are:

- merge order is symmetric rather than positional;
- ordinary numeric priority defaults to zero and a larger number has stronger
  selection priority;
- equal-priority values must still merge or report a conflict; and
- constraints attached to a lower-priority contribution remain obligations on
  the selected value.

POO Flow does not adopt Nickel records, field metadata syntax, distinguished
priority sentinels, recursive record merge, or its evaluator.

* Central decision

Multiple policies never return competing ControlDecision objects directly to
the runtime handler.

Instead:

1. each admitted ~ControlPolicy~ POO object evaluates the same
   ControlCondition and produces zero or one ~DecisionCandidate~ POO object;
2. one pure ~ControlPolicyResolver~ composes the finite candidate set;
3. authority and constraints are intersected before priority selection;
4. explicit veto and cancellation authority are applied;
5. priority selects a terminal-effect candidate only among the remaining
   admitted candidates;
6. equal-priority candidates merge or fail closed; and
7. the resolver constructs exactly one final ControlDecision.

Source order, import order, Profile order, and object mix order must not decide
the result.

* POO object families

** ControlPolicy

A ControlPolicy is an immutable higher-order POO object that:

- declares the condition prototype family it can evaluate;
- declares its authority requirements;
- declares its resolution scope;
- contains a pure candidate-producing behavior;
- contributes explicit constraints and bounded evidence; and
- has a stable policy identity.

A policy does not install an exception handler, capture a continuation, mutate
a registry, or return a Profile value.

ControlPolicy is an open prototype family.  Domain-specific policies may extend
it, provided their candidate production remains pure and their authority
requirements can only become stricter.

** DecisionCandidate

A DecisionCandidate is not yet a ControlDecision.  It proposes:

- one terminal effect from Continue, Suspend, Deny, or Cancel;
- the exact condition identity;
- the producing policy identity;
- a resolution scope;
- a DecisionPriority;
- an authority claim;
- capability constraints;
- pure decision evidence; and
- an optional explicit hard-stop claim.

A candidate contains no raw continuation, Profile value, mutable controller, or
portable resumption authority.

** ControlPolicyResolver

The resolver is a pure POO strategy object.  It owns:

- candidate admission;
- constraint intersection;
- hard-stop validation;
- priority comparison;
- equal-priority merge;
- conflict construction; and
- canonical receipt projection.

The resolver does not own the Gambit handler.  The handler receives only the
single final ControlDecision produced after resolution.

* Finite resolution boundary

Resolution is performed over a finite candidate set for one already-observed
ControlCondition.

This layer does not introduce:

- a lazy global fixed point;
- recursive controller discovery;
- an implicit provider registry;
- policy evaluation that waits on its own final decision; or
- re-signaling through the same active exception handler.

A cyclic policy dependency fails closed with a policy-resolution conflict
receipt.  It must not recursively raise another condition through the same
handler.

* Candidate admission

A candidate enters resolution only when:

- its condition identity exactly matches the active condition;
- its policy identity is admitted in the current control scope;
- its issuer witness is valid;
- its terminal effect is one of the four closed effects;
- its priority representation is canonical;
- its authority claim is no broader than the policy capability;
- its constraints are pure and bounded;
- its evidence is pure and bounded; and
- it contains neither a Profile value nor live continuation authority.

An inadmissible candidate cannot influence priority, veto, constraint
intersection, or receipts except through its explicit rejection evidence.

* DecisionPriority

** Numeric ordering

Ordinary priority is an exact signed integer:

- the default priority is ~0~;
- a larger integer has stronger selection priority;
- negative priorities are valid fallback contributions; and
- source position never breaks a tie.

Default numeric priority is 0.

Larger exact integers have stronger selection priority.

Exact integers are used instead of arbitrary Scheme numbers so that NaN,
inexact comparison, fractional serialization, and cross-runtime numeric drift
cannot affect deterministic resolution.

Priority is represented by a POO value owned by the control-policy layer.  A
thin hygienic user projection may accept an integer, but that syntax must
expand to the ordinary POO object and must not become a new merge DSL.

** No unlimited priority sentinel

POO Flow does not encode unlimited authority as an extreme number.

There is no numeric sentinel for unlimited priority.  A candidate with a very
large priority still cannot:

- bypass capability admission;
- erase a propagated constraint;
- defeat an authorized veto;
- acquire cancellation authority;
- cross an identity fence; or
- turn an invalid terminal effect into a valid one.

Hard-stop authority is a distinct capability, not a priority value.

** Fallback

A fallback policy uses a negative numeric priority selected by its owner.
The core does not require a special fallback syntax or a distinguished lowest
number.

If several fallback candidates share the strongest surviving priority, they
must merge or conflict under the ordinary equal-priority rule.

* Constraint propagation

Priority chooses among proposed terminal effects; it does not choose which
security and correctness constraints survive.

All constraints from admitted, in-scope candidates are intersected before
priority resolution.  The final ControlDecision must satisfy the intersection
even when its terminal effect came from the highest-priority candidate.

Authority intersection occurs before priority selection.

No priority value grants unlimited authority.

Examples of propagated constraints include:

- permitted terminal effects;
- maximum additional budget;
- safe-point restrictions;
- expiry;
- revocation;
- root, revision, and generation fences;
- principal requirements;
- evidence requirements; and
- external-effect fences.

If the intersection is empty or inconsistent, resolution fails closed before
numeric priority is considered.

This prevents a high-priority policy from erasing a lower-priority safety
contract.

* Veto and cancellation

** Veto is explicit authority

A DenyDecision candidate is not automatically an absolute veto.

An absolute veto requires a valid ~VetoCapability~ whose scope includes:

- the active condition identity;
- the proposed terminal-effect set;
- the deciding principal;
- the active root and generation; and
- the current policy-resolution scope.

An authorized veto resolves to Deny before numeric priority selection.
An unauthorized veto claim is rejected and contributes no ordering power.

** Cancellation is a hard stop

An admitted Cancel candidate requires a valid ~CancellationCapability~.
Once validated for the current demand, cancellation is a hard stop and is
applied before numeric priority.

Cancellation authority remains subject to revocation, lifetime, principal,
root, revision, generation, and demand fences.

** Conflicting hard stops

If multiple valid hard-stop candidates agree on Cancel, their constraints and
evidence merge.

If valid hard-stop candidates disagree in a way that cannot be merged, the
resolver emits a governance conflict receipt and fails closed at the
noncontinuable boundary.  It does not use source order or numeric priority to
silence a governance conflict.

* Priority resolution

After admission, constraint intersection, and hard-stop processing:

1. determine the greatest numeric priority among remaining candidates;
2. retain every candidate at that priority;
3. merge candidates that refine the same terminal effect;
4. reject distinct terminal effects at the same priority; and
5. construct one final ControlDecision from the merged candidate.

Lower-priority terminal-effect proposals are not selected, but their admitted
constraints remain active.

flowchart TD

  I -->|"intersection is empty or inconsistent"| X["Fail-closed constraint conflict"]
  I -->|"intersection is satisfiable"| V["Validate hard-stop claims"]
  V -->|"authorized Cancel is present"| C["Final Cancel decision"]
  V -->|"authorized veto is present"| N["Final Deny decision"]
  V -->|"no hard stop applies"| M["Find the greatest numeric priority"]
  M -->|"one terminal effect occupies the greatest priority"| G["Merge its evidence and refinements"]
  M -->|"several candidates share one terminal effect"| G
  M -->|"different terminal effects share the greatest priority"| Q["Equal-priority conflict"]
  G -->|"merged candidate satisfies propagated constraints"| D["Construct one ControlDecision"]
  G -->|"merged candidate violates a propagated constraint"| X
  Q -->|"canonical conflict receipt is emitted"| X
  X -->|"abort prevents implicit selection"| B["Noncontinuable denial boundary"]
#+end_src

* Equal-priority merge

Equal-priority candidates may merge only when:

- their condition identities are identical;
- their resolution scopes are identical;
- they refine the same terminal effect;
- their authority claims are compatible;
- their constraints have a nonempty intersection; and
- their evidence can be combined canonically.

The merge:

- intersects authority and constraints;
- unions evidence by stable evidence identity;
- preserves every issuer and policy identity;
- retains the common terminal effect; and
- is commutative, associative, and idempotent for admitted inputs.

Different terminal effects at the same priority are a conflict even if one
would appear later in a source file or composition list.

* Determinism

For the same condition, candidate set, capability state, and evaluator
revision, resolution must produce the same:

- admitted-candidate identities;
- rejected-candidate reasons;
- effective constraint intersection;
- hard-stop outcome;
- greatest priority;
- equal-priority merge result or conflict;
- final ControlDecision identity; and
- canonical evidence receipt.

Candidate evaluation may run in parallel, but receipt ordering is canonical by
stable policy identity rather than completion time.

* Policy composition law

For admitted policies ~A~, ~B~, and ~C~ evaluated against one condition:

- permutation of ~A~, ~B~, and ~C~ does not change the result;
- grouping does not change the result;
- repeating the same policy contribution does not amplify authority;
- adding a stricter constraint cannot expand the result set;
- adding an unauthorized candidate cannot change the selected decision;
- adding a valid hard stop can only preserve or restrict execution; and
- erasing the policy layer from an allowed completed execution preserves the
  native POO result or failure.

These laws apply to the policy resolver, not to arbitrary object slot
precedence.

* POO-native dispatch

Policy and candidate behavior is selected through admitted POO prototypes and
functional combinators.

The ordinary interface must not use:

- ~case~ over terminal-effect symbols;
- nested host-language conditionals in ~compose profiles~;
- a mutable table of policy kinds;
- callback registration;
- source-order override;
- raw ~(lambda (self super) ...)~ policy hooks; or
- a second object evaluator.

Internal bounded macros may generate repetitive policy prototype families only
when their expansion is inspectable ordinary POO and functional code.

* User composition boundary

The complete higher-order Profile projection and flat ordinary user interface
is owned by
[[file:45-91-control-policy-profile-projection-and-user-composition-interface.org][45-91]].
This section owns only the boundary required by policy resolution.

A ControlPolicy is a first-class POO object.

It may enter a user composition only through a higher-order Profile that
provides the policy under an explicit control capability.  It is not
automatically a Profile operand merely because it is a POO object.

The user-facing Profile surface remains:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    wendao-episteme
    production))
#+end_src

A higher-order Profile may contain or extend policy objects without adding a
new ~policy-composition~ clause, nested ~compose~, host conditional, or runtime
registry.

* Evidence receipt

Every resolution receipt records:

- condition and control-context identities;
- resolver identity and revision;
- every candidate policy identity;
- candidate priority;
- requested terminal effect;
- authority admission or rejection;
- constraint contribution;
- hard-stop claim and validation;
- greatest surviving priority;
- equal-priority merge or conflict;
- final effective constraints;
- final decision identity; and
- deterministic receipt digest.

The receipt contains no issuer witness, live continuation, secret capability
material, Profile value, or unresolved external effect.

* Required resolution tests

** Admission tests

- [ ] Reject a candidate for another condition identity.
- [ ] Reject a candidate from an unadmitted policy.
- [ ] Reject an invalid issuer witness.
- [ ] Reject a non-integer priority.
- [ ] Reject an unknown terminal effect.
- [ ] Reject a candidate containing a Profile value.
- [ ] Reject a candidate containing live continuation authority.

** Priority tests

- [ ] Prove that the default numeric priority is zero.
- [ ] Prove that a larger integer wins terminal-effect selection.
- [ ] Prove that negative priorities act as ordinary weaker candidates.
- [ ] Prove that source order does not affect selection.
- [ ] Prove that import and Profile order do not affect selection.
- [ ] Prove that no numeric priority bypasses capability admission.

** Constraint tests

- [ ] Intersect constraints from all admitted in-scope candidates.
- [ ] Preserve lower-priority constraints after terminal-effect selection.
- [ ] Reject an empty authority intersection.
- [ ] Reject incompatible safe-point constraints.
- [ ] Prove that a higher priority cannot erase revocation or expiry.
- [ ] Prove that repeated contributions do not amplify authority.

** Equal-priority tests

- [ ] Merge equal-priority candidates with the same terminal effect.
- [ ] Canonically union their evidence.
- [ ] Reject different terminal effects at equal priority.
- [ ] Prove merge commutativity.
- [ ] Prove merge associativity.
- [ ] Prove merge idempotence.

** Hard-stop tests

- [ ] Reject a veto claim without VetoCapability.
- [ ] Apply an admitted veto before numeric priority.
- [ ] Reject a Cancel candidate without CancellationCapability.
- [ ] Apply admitted cancellation before numeric priority.
- [ ] Merge agreeing hard-stop evidence.
- [ ] Fail closed on incompatible authorized hard stops.

** Determinism tests

- [ ] Randomize candidate enumeration order.
- [ ] Randomize parallel policy completion order.
- [ ] Prove identical final decision identities.
- [ ] Prove identical canonical receipt digests.
- [ ] Prove that a cyclic policy dependency yields one bounded conflict receipt.

** Cross-plane tests

- [ ] Prove that resolution produces no Profile result.
- [ ] Prove that evidence observation does not change selection.
- [ ] Prove that a conflict terminates through the noncontinuable boundary.
- [ ] Prove erasure to native POO semantics for allowed completed execution.

* Admission criteria

Implementation may begin only when:

- [ ] ControlPolicy, DecisionCandidate, and ControlPolicyResolver are ordinary
  POO object families;
- [ ] candidate production is pure and finite;
- [ ] authority intersection precedes priority;
- [ ] valid hard stops precede numeric priority;
- [ ] default priority is zero and larger exact integers are stronger;
- [ ] equal-priority conflicts fail closed;
- [ ] lower-priority constraints survive terminal-effect selection;
- [ ] resolution is commutative, associative, and idempotent where merge is
  admitted;
- [ ] candidate and receipt order is deterministic;
- [ ] no priority value represents unlimited authority;
- [ ] the user interface adds no new composition DSL; and
- [ ] the concrete capability-governance, revocation, and audit owner is
  resolved and linked; and
- [ ] all 45-86 through 45-89 obligations remain satisfied.

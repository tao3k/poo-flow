#+subtitle: Pure POO effect plans, fixed-point safety, observations, commits, idempotency, and unknown outcomes
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative effect and runtime-handoff protocol
- Semantic core :: Pure POO values, functional composition, and explicit POO Flow runtime boundaries
- Related modules :: =45-51-live-evaluation-context-narrowing-and-resource-conservation.org= and =45-53-phased-slot-resolution-contracts-and-failure-taxonomy.org=

This module prevents speculative, incremental, cyclic, or resumed semantic evaluation from directly repeating external effects. Pure evaluation constructs an identity-addressed effect intent; live execution occurs only after stabilization and explicit authorization.

* Core decision

#+begin_quote
Pure evaluation produces an identity-addressed EffectIntent. Fixed-point evaluation stabilizes the intent without executing it. A live executor performs the effect only after runtime authorization at an explicit handoff boundary.
#+end_quote

An external outcome that changes semantic meaning becomes a content-addressed input to a new semantic generation. It is not injected into the old generation.

* Typst formalization: stable intent handoff and reconciliation

Stabilization creates an identity-addressed intent but performs no external
effect.  Crossing the runtime boundary requires both a committed
=RetryCapability= and authorized effect evidence bound to the same intent.

#+begin_src typst
$
  I_"stable" &=
    ("SemanticIdentity", "IntentIdentity", "Role",
      "AuthorizationDigest", "PayloadDigest", "ObservationDigest") \
  "Bind"(i, c) & equiv
    i."authorization" = c."decision-digest"
    and i."payload" = c."selected-payload" \
  & quad and
    i."observation" = c."selected-observation" \
  "Handoff"(i, c, e) & =>
    i in I_"stable"
    and "RetryCapability"(c) \
  & quad and "Bind"(i, c)
    and "AuthorizedEffectL2"(e) \
  "Stabilize"(x) & => not "ExecuteExternalEffect"(x)
$
#+end_src

An execution receipt refines the handoff instead of minting a new semantic or
intent identity.  Reconciliation may add observed outcome evidence, but it
cannot rewrite either committed identity.

#+begin_src typst
$
  "ExecutionReceipt"(r, h) & =>
    r."semantic-id" = h."intent"."semantic-id" \
  & quad and
    r."intent-id" = h."intent"."intent-id" \
  "Reconcile"(q, r) & =>
    q."semantic-id" = r."semantic-id" \
  & quad and q."intent-id" = r."intent-id" \
  "CommittedNoRehandoff" & equiv
    not ("Committed" -> "HandedOff") \
  "ReconciledTerminal" & equiv
    not ("Reconciled" -> "AnyFurtherEffectStep")
$
#+end_src

* Effect intent identity

An =EffectIntent= is a pure POO object with:

- =EffectAnchorIdentity=;
- =EffectRevisionIdentity=;
- operation semantic identity;
- canonical input identities;
- required runtime-capability scope;
- required adapter-protocol identity;
- expected outcome contract;
- idempotency policy;
- retry policy;
- effect role;
- provenance.

It contains no:

- live capability token or lease;
- adapter instance;
- network connection;
- file descriptor;
- process handle;
- continuation or recovery portal;
- mutable retry counter;
- execution result.

The ordinary public extension route uses POO objects and functional combinators. It does not expose an effect DSL, callback table, or raw effectful hook.

* Fixed-point stabilization

Speculative and cyclic evaluation may construct and revise intents:

#+begin_src text
slot computation
-> pure EffectIntent
-> fixed-point stabilization
#+end_src

It must not perform:

#+begin_src text
slot computation
-> immediate external effect
#+end_src

Only a stable intent projection may cross the runtime handoff boundary.

#+begin_src mermaid
flowchart LR
    S["Pure slot computation"] -->|"construct an identity-addressed value"| I["EffectIntent"]
    I -->|"participate without executing the effect"| F["Fixed-point and SCC stabilization"]
    F -->|"intent identity becomes stable"| H["Runtime handoff boundary"]
    F -->|"intent changes during iteration"| S
    H -->|"validate runtime capability and adapter scope"| E["Live effect executor"]
    E -->|"materialize outcome and receipt"| O["Effect outcome projection"]
#+end_src

Reevaluation, invalidation, and continuation resumption do not repeat an external effect merely because the slot computation runs again.

* Effect roles

Each effect intent declares one of the following semantic roles or a POO extension with equivalent explicit identity and cache rules.

** External observation

An observation reads external state that affects semantics, including:

- remote metadata;
- filesystem content;
- environment discovery;
- service query;
- clock-derived semantic input.

The outcome is materialized as a content-addressed pure artifact:

#+begin_src text
ExternalObservationIdentity
#+end_src

The artifact becomes an explicit input to a new generation:

#+begin_src text
generation G stabilizes observation intent
-> execute observation
-> materialize observation artifact
-> derive generation G+1
-> resume semantic demand against G+1
#+end_src

Generation =G= does not silently read an external value and continue under its old semantic identity.

** Deterministic materialization

A compiler, renderer, generator, or external tool may be treated as deterministic materialization only when its adapter contract establishes:

#+begin_src text
canonical inputs
+ toolchain semantic protocol identity
-> content-addressed artifact
#+end_src

Worker, temporary directory, scheduling, and timing remain operational.

An adapter that cannot establish hermetic or deterministic behavior is not classified as pure materialization.

** Commit effect

A commit effect changes external state, including:

- deployment;
- publication;
- external message;
- database mutation;
- remote state change.

Commit execution occurs only after its semantic plan is stable. It produces an operational commit receipt and does not retroactively alter the sealed business result.

If the resulting external state must influence later semantics, a new observation intent reads it and introduces a new content-addressed input.

* Runtime handoff pipeline

The normative handoff is:

#+begin_src text
Pure EffectIntent
-> structural validation
-> fixed-point stabilization
-> runtime-capability validation
-> adapter selection from LiveEvaluationContext
-> effect execution
-> outcome materialization
-> outcome-contract validation
-> receipt
-> optional new semantic generation
#+end_src

The adapter comes from explicitly delegated live-context capability. =EffectIntent= declares the required adapter protocol but holds no adapter instance.

No global adapter registry or ambient process lookup provides authority.

* Observation generation transition

#+begin_src mermaid
flowchart LR
    G["Semantic generation G"] -->|"stabilize an external-observation intent"| I["Pure observation intent"]
    I -->|"runtime authorization succeeds"| E["Execute external observation"]
    E -->|"content-address returned data"| A["ExternalObservation artifact"]
    A -->|"become an explicit semantic input"| N["Semantic generation G+1"]
    N -->|"resume the suspended demand"| R["Demand evaluation against G+1"]
    E -->|"authorization or adapter fails"| F["Operational failure receipt"]
#+end_src

A continuation resumes the suspended caller against =G+1=. It does not inject the observation into =G=.

* Idempotency policy

Equal intent identity does not imply that an effect is safe to repeat.

The declared policy distinguishes:

- Pure materialization :: Safe to recompute from canonical inputs.
- Idempotency-keyed effect :: The adapter contract accepts and enforces a canonical idempotency key.
- At-most-once effect :: Automatic retry is prohibited after an attempt that may have committed.
- Non-repeatable effect :: Every execution requires a new explicit authorization.

Intent identity may contribute to an idempotency key only when the adapter contract explicitly guarantees the key semantics.

POO Flow does not claim exactly-once delivery merely because an intent is content-addressed.

* Unknown commit outcome

The sequence:

#+begin_src text
request sent
-> remote side may have committed
-> connection lost before authoritative receipt
#+end_src

produces =UnknownCommitOutcome=, not an ordinary retryable failure.

Reconciliation:

1. Query the remote system using an authoritative operation or idempotency identity.
2. Obtain canonical committed, not-committed, or still-unknown evidence.
3. Seal a reconciliation receipt.
4. Retry only when non-commit is established and policy allows it.
5. Fail closed when the outcome cannot be established.

#+begin_src mermaid
flowchart LR
    C["Commit attempt"] -->|"authoritative success receipt"| S["Committed outcome"]
    C -->|"authoritative non-commit receipt"| N["Retry may be considered"]
    C -->|"connection lost after possible commit"| U["UnknownCommitOutcome"]
    U -->|"query remote idempotency or operation identity"| R["Reconciliation"]
    R -->|"confirmed committed"| S
    R -->|"confirmed not committed"| N
    R -->|"still unknown"| F["Fail closed for external coordination"]
#+end_src

Blind retry after unknown commit is prohibited.

* Effect intents and SCCs

An intent may be present in a dependency graph, but execution waits for stability:

- an observation intent changing inside an SCC remains pure and unevaluated;
- a stable observation intent may execute once under its policy;
- its outcome enters a new generation and may change the SCC;
- a commit intent depending on an unstable SCC cannot execute;
- an intent that cannot stabilize produces =EffectIntentCycleCondition=.

The evaluator must not execute an effect to discover whether a semantic cycle converges.

* Outcome contract

After execution, the outcome projection validates:

- artifact or external-result identity;
- adapter protocol identity;
- declared outcome contract;
- provenance;
- completeness;
- redaction requirements.

An invalid outcome is not committed as semantic input.

For observation:

- a valid outcome enters a new generation;
- an invalid outcome produces a handoff or outcome-contract condition;
- operational interruption does not become an observation value.

Outcome-contract checks use identity-addressed POO contract objects and explicit coverage.

* Retry and generation boundaries

- Same intent and semantic inputs, with retry allowed :: New operational execution against the same semantic generation.
- Changed intent semantic identity :: New semantic plan or generation.
- Changed observation outcome :: New generation.
- Changed admission or contract policy :: New generation.
- Changed worker, scheduler, or transient transport :: New execution identity only.
- Commit retry :: Requires idempotency and reconciliation policy.

An operational retry cannot change semantic inputs while claiming to be the same intent.

* Cache boundaries

Pure cacheable artifacts include:

- effect intent;
- stabilization evidence;
- deterministic materialization artifact;
- observation artifact;
- outcome-contract proof;
- reconciliation receipt.

Live or operational artifacts include:

- capability proof;
- adapter instance;
- network or process handle;
- retry counter;
- active continuation;
- worker execution.

A materialization cache key includes canonical inputs and toolchain semantic protocol identity. A commit receipt is evidence of an external action, not a reusable semantic value or future authority.

* Functional and POO path

The architectural direction remains:

#+begin_src text
pure POO values
+ functional combinators
-> EffectIntent graph
-> explicit runtime or Marlin handoff
#+end_src

Funflow anchors the functional route. Concrete combinators and handoff operations must be verified against the real Funflow, =gerbil-poo=, and Gerbil runtime interfaces.

This RFC does not introduce a parallel effect language.

* Evidence requirements

The complete effect evidence chain records:

- intent anchor and revision;
- declaring slot and semantic generation;
- effect role;
- stabilization and SCC evidence;
- runtime capability validation;
- adapter protocol and implementation receipt;
- idempotency policy and key projection;
- execution attempts;
- outcome artifact identity;
- outcome contract and coverage;
- committed, unknown, reconciled, or failed status;
- successor generation identity;
- continuation and resumption receipt.

Evidence redaction may hide sensitive adapter or external-system details while retaining the causal chain.

* Implementation checklist

- [ ] Define identity-addressed POO =EffectIntent= objects.
- [ ] Keep live tokens, adapters, handles, continuations, and counters outside intents.
- [ ] Stabilize intents before runtime handoff.
- [ ] Prevent speculative, invalidated, and cyclic evaluation from executing effects.
- [ ] Define observation, deterministic materialization, and commit roles.
- [ ] Materialize semantics-affecting observations as content-addressed inputs.
- [ ] Derive a new generation from an admitted observation artifact.
- [ ] Validate runtime capability at the handoff boundary.
- [ ] Select adapters only from explicitly delegated live context.
- [ ] Define explicit idempotency policies.
- [ ] Prevent blind retry after a possibly committed attempt.
- [ ] Define =UnknownCommitOutcome= and reconciliation receipts.
- [ ] Block commit effects that depend on unstable SCCs.
- [ ] Validate outcome contracts before artifact or semantic-input admission.
- [ ] Separate semantic generation changes from operational retries.
- [ ] Generate intent, execution, outcome, reconciliation, and transition evidence.
- [ ] Validate the final functional and POO interfaces against real Funflow and =gerbil-poo= primitives.

* Non-goals

- Do not execute external effects during speculative fixed-point evaluation.
- Do not inject an external observation into the old semantic generation.
- Do not assume content identity implies effect idempotency.
- Do not claim exactly-once behavior without adapter guarantees.
- Do not retry an unknown commit blindly.
- Do not use a global adapter registry or ambient runtime authority.
- Do not expose raw effect callbacks or create a separate effect DSL.
- Do not reimplement Funflow, =gerbil-poo=, or Gerbil runtime semantics.

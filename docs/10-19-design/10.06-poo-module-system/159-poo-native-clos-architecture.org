#+title: POO-Native CLOS Architecture
#+startup: overview

* Scope and acceptance

This document defines the stable architecture and acceptance boundary for the
POO-native CLOS extension.  It is not a delivery plan.  Implementation order,
temporary slices, and historical test-run identifiers are deliberately absent.

The ANSI profile covers the CLOS class, instance, generic-function, method,
method-combination, class-change, class-redefinition, and load-form semantics
identified by Common Lisp HyperSpec sections 4.3, 7.5, 7.6, and the Objects
Dictionary in section 7.7.  The de facto Metaobject Protocol is admitted only
through the separate =MOP-EXTENDED v1= profile and cannot satisfy or dilute an
ANSI requirement.

Acceptance is executable and fail-closed:

- every required ANSI dictionary operator has a source-owned evidence fixture;
- every semantic clause names an owner plus positive and negative tests;
- interpreted and freshly compiled AOT fixtures have identical nonzero
  assertion counts;
- all inputs and generated artifacts remain unchanged across qualification;
- no accepted receipt is written while a required ANSI row is open.

* Ownership boundary

The compatibility module at =src/module-system/poo-method-combination/= remains
frozen at v1.  The CLOS owner is =src/module-system/poo-clos/=.  Public values
are native Gerbil POO objects, and declarations lower hygienically to those
objects plus functional dispatch operations.

Native POO owns object identity, prototype inheritance, slots, and C3.  The
CLOS extension owns the semantics that coordinate multiple arguments,
specializers, effective methods, ANSI class precedence, class generations, and
invocation frames.  It does not wrap a Common Lisp runtime, expose raw alist
DSLs, or construct a parallel record-based object hierarchy.

* Stable contract areas

| Contract area | Required semantics |
|---------------+--------------------|
| Metaobjects | POO class, slot, instance state, slot cell, specializer, method, generic function, effective method, invocation frame, and condition values |
| Specialization | class, =eql=, universal, multiple dispatch, and argument precedence order |
| Class precedence | ANSI 4.3.5 topological class precedence, independent of native prototype C3 |
| Method management | add, remove, lookup, same-signature replacement, generation tracking, and cache invalidation |
| Standard combination | around, before, primary, after, multiple values, and exact next-method applicability |
| Custom combination | all ANSI built-ins plus declarative short and long forms, method groups, ordering, required groups, arguments, generic-function binding, =call-method=, and =make-method= |
| Lambda lists | required, optional, rest, key, allow-other-keys, supplied-p, auxiliary bindings, and congruence |
| Classes and slots | direct superclasses, direct/effective slots, initforms, initargs, readers/writers, and instance/class allocation |
| Instance lifecycle | allocate, initialize, shared-initialize, reinitialize, slot-boundp, slot-makunbound, slot-missing, and slot-unbound |
| Evolution | change-class, update-instance-for-different-class, class redefinition, dependency propagation, explicit obsolescence, and lazy instance convergence |
| Load forms | two-phase creation/initialization, cycle-safe reference resolution, selected-slot saving, unbound preservation, and class-name association |
| Declaration surface | POO-native =.defclass=, =.defgeneric=, =.defmethod=, and =.define-method-combination= |
| Reflection | defensive class, slot, method, generic, specializer, dependency, and generation projections |
| MOP-EXTENDED | sealed read-only portable profile that remains outside ANSI acceptance |

The executable clause and operator manifests live in
=t/qualification/poo-clos/clause-ledger.ss=.  Ledger rows contain semantic
identity, profile, owner, and positive/negative evidence.  They intentionally
contain no project-management stage or delivery-sequence field.

* Declaration and runtime interfaces

The declaration parser produces immutable, phase-owned declaration IR values.
Runtime construction, method selection, effective-method computation, and
invocation remain ordinary POO-native or functional operations.  Raw
=(lambda (self super) ...)= hooks and private patch languages are not ordinary
authoring interfaces.

The explicit-frame kernel form remains available to low-level implementations:

#+begin_src scheme
(def generic
  (poo-clos-generic-function
   'route 2 argument-precedence-order: '(1 0)))

(poo-clos-add-method
 generic
 (poo-clos-method
  'route-by-class
  (list (poo-clos-class-specializer request-prototype)
        (poo-clos-eql-specializer 'priority))
  (lambda (frame request mode)
    (if (poo-clos-next-method? frame)
      (poo-clos-call-next-method frame request mode)
      request))))
#+end_src

Ordinary authoring uses the hygienic declaration forms, which supply lexical
next-method operations without exposing the frame argument.

* Deliberate Scheme and POO adaptations

- Class and generic-function redefinition reinitialize an existing POO object
  in place.  Identity is stable; generation and layout history carry only the
  information required for cache invalidation and lazy migration.
- CLOS =eql= specializers use Scheme =eqv?= without serialization or numeric
  canonicalization.
- Initargs and generic keywords accept native Gerbil keywords and symbols;
  =allow-other-keys:= keeps the ANSI admission role.
- Multiple values use Scheme's native values protocol.
- =make-load-form-saving-slots= returns a creation thunk and an initialization
  procedure.  The initialization procedure accepts an optional reference
  resolver so cyclic graphs can be restored without embedding a serialization
  DSL.  Initforms are never replayed by this protocol.

* Qualification fixtures

Qualification groups tests only where a stable semantic fixture needs its own
resource observation and interpreted/AOT attribution:

- method-combination compatibility;
- generic dispatch;
- class and instance lifecycle;
- declaration surface;
- method combination;
- evolution, reflection, and load form;
- ANSI clause ledger.

Fixture names describe durable evidence boundaries, not delivery stages.  The
qualifier applies heap ceilings, elapsed-time guards, the shared process-tree
memory anomaly guard, SHA-256 input/artifact snapshots, dependency checking,
and exact interpreted/AOT assertion agreement.  Receipts state
=performance-claim? #f= unless a separately approved workload and SLA exist.

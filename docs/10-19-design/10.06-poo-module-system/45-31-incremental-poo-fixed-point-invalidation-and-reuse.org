#+title: Incremental POO Fixed-Point Invalidation and Reuse
#+status: Accepted
#+language: en

* Decision

Incremental fixed-point evaluation is defined over native POO slot demand.

- An observed POO slot demand is the ordinary minimum invalidation unit.
- A strongly connected component of mutually dependent slot demands is the
  minimum recomputation closure when a cycle exists.
- Semantic reuse is authorized only by current-generation identity and
  dependency evidence.
- A physical cache is an optional projection of authorized semantic reuse.  It
  is never the source of module-system truth.

The module system MUST NOT invalidate whole packages, source files, Profiles or
module trees when a smaller causally complete demand closure is available.  It
also MUST NOT split a cyclic fixed-point component merely to obtain a smaller
cache key.

* Native semantic basis

This RFC does not introduce a second evaluator.

=gerbil-poo= remains responsible for native objects, prototypes, slot demand
and open recursion.  POO Flow observes those native operations and adds:

- stable demand identity;
- contribution generations;
- dependency footprints;
- targeted invalidation;
- cycle-aware recomputation closure;
- reuse receipts;
- replay equivalence;
- bounded incremental-work evidence.

All ordinary user composition remains native POO composition.  Cache commands,
dependency alists, invalidation patches and raw evaluator callbacks MUST NOT
become public configuration syntax.

* Two invalidation units

** Acyclic slot demand

When a demanded slot is outside a dependency cycle, its result may be
invalidated and recomputed independently, followed by propagation through the
reverse demand edges that actually consumed it.

The invalidation unit is identified by the semantic demand, not by the source
location that happened to define it.

** Cyclic fixed-point component

When slot demands form a strongly connected component, the component is a
single recomputation closure.  Every member participates in the same
fixed-point convergence claim.

Reusing one member while independently recomputing another could combine
results from incompatible fixed-point generations.  POO Flow therefore
invalidates, observes, converges, resumes and receipts the complete component.

flowchart LR
  G["New contribution generation"] -->|"changes one or more semantic identities"| I["Invalidation frontier"]
  I -->|"demand has no cyclic dependency"| S["Single slot-demand closure"]
  I -->|"demand belongs to a cycle"| C["Complete fixed-point SCC"]
  S -->|"recomputes the smallest causally complete value"| V["Validated result"]
  C -->|"recomputes every mutually dependent member together"| V
  V -->|"records newly observed dependency edges"| F["Current dependency footprint"]
  F -->|"authorizes reverse-edge propagation only where consumed"| I
  F -->|"all reuse identities remain equivalent"| R["Reuse receipt"]
#+end_src

* Stable slot-demand identity

A reusable slot-demand result MUST be bound to at least:

| Identity dimension | Required meaning |
|--------------------+------------------|
| POO object identity | The higher-order object being observed |
| Prototype lineage | The native supers and refinement lineage participating in lookup |
| Slot identity | The demanded semantic slot, including its nested object path |
| Contribution-closure identity | Every active and suppressed contribution relevant to the slot |
| Slot-contract identity | The POO contract objects and algebra governing combination |
| Priority identity | The full priority class and authorized force metadata |
| Capability identity | The capability ownership visible to the demand |
| Authority identity | The authority scope under which selection and realization are permitted |
| Evaluation generation | The contribution generation in which the demand was observed |

Source timestamps, file paths, process-local addresses and cache locations are
not semantic identities.

* Dependency footprint

A dependency footprint is accumulated from actual native slot demand.  An edge
means that one observed slot computation consumed another semantic value.

#+begin_src mermaid
flowchart TD
  A["Demand A"] -->|"reads slot B in the current branch"| B["Demand B"]
  A -->|"enters nested submodule C"| C["Submodule demand C"]
  B -->|"observes contract and priority metadata"| M["Merge obligations"]
  C -->|"checks capability and authority"| U["Authority obligations"]
  B -->|"records the causal demand edge"| P["Current-generation footprint"]
  C -->|"records the nested identity edge"| P
  M -->|"remains part of reuse validation even when its value loses priority"| P
  U -->|"prevents reuse under a different authority scope"| P
#+end_src

The footprint is demand-sensitive.  It is not a static import graph and it does
not claim that every syntactically reachable slot was consumed.

* Previous footprints are hints, not proofs

A previous-generation footprint MAY schedule likely invalidation and
recomputation work.  It MUST NOT prove the current dependency closure.

A contribution change may alter control flow so that:

#+begin_example
previous generation: A demands B
current generation:  A demands C
#+end_example

The current generation must observe the demand again, confirm its actual
dependencies and issue a new receipt.  Reusing the previous footprint without
this confirmation would hide changed branches and stale capability or contract
requirements.

* Full contribution closure participates in reuse

Priority selection does not reduce reuse identity to the winning value.

The contribution-closure identity includes:

- the winning contribution;
- every lower-priority suppressed contribution;
- every equal-priority contribution;
- contracts attached to any contribution;
- priority and authorized force metadata;
- ambiguity and resolution obligations;
- prototype lineage and nested contribution identities.

A suppressed value may disappear from the realized result while its contract,
authority restriction or evidence obligation remains active.  Consequently, a
change to a suppressed contribution can invalidate reuse even when the winning
value is byte-for-byte unchanged.

* Reuse authorization

A previous result is eligible for semantic reuse only when the current
generation proves:

1. the POO object, prototype lineage and slot identities are equivalent;
2. the complete contribution closure is equivalent;
3. slot contracts and their algebraic identities are equivalent;
4. priority, capability and authority identities are equivalent;
5. every required dependency result is itself current or validly reused;
6. the newly confirmed dependency footprint is compatible with the result;
7. no stale resumption, revoked authority or superseded generation is present.

Eligibility does not require that a physical cache exists.  POO Flow may reuse
an in-memory value, retrieve an encoded value, replay a pure computation, or
recompute it.  These realization choices do not change the semantic result.

* Three distinct concepts

| Concept | Semantic role |
|---------+---------------|
| Semantic reuse | The POO Flow decision that a prior result remains equivalent in the current generation |
| Physical cache | Optional memory, disk or remote storage for an encoded reusable result |
| Replay evidence | The receipt chain proving why retrieval and fresh evaluation are equivalent |

These concepts MUST remain separate.

- A cache hit without semantic authorization is stale state.
- Semantic reuse without a cache hit is still valid reuse.
- Replay evidence must describe the identities and obligations checked; it
  cannot be replaced by a cache-key match.
- Replacing a cache backend cannot change composition, merge, capability,
  authority or fixed-point semantics.

* Reuse receipt

The canonical reuse receipt MUST carry or commit to:

- current and predecessor generation identities;
- slot-demand identity;
- contribution-closure digest;
- contract and priority digest;
- capability and authority digest;
- dependency-footprint digest;
- reused result identity;
- SCC identity when the result belongs to a cycle;
- validation decision and causal predecessor receipts;
- replay-equivalence claim;
- incremental work and observation-budget evidence.

The receipt is a POO evidence object.  A raw cache manifest, filename, hash map
entry or log message is not the public semantic representation.

* Resumption creates a new generation

A continuable exception may authorize retry, refinement, suspension or another
bounded recovery action.  Resuming never mutates an old fixed-point result in
place.

The resumption contributes to a new generation.  Reuse from the predecessor
generation is reconsidered under the complete rules above.  This preserves the
causal relation between the failure, the authorized recovery contribution and
the new result.

#+begin_src mermaid
flowchart LR
  E["Cycle or budget exception"] -->|"offers policy-authorized recovery choices"| K["Continuation decision"]
  K -->|"adds refinement, budget or dependency evidence"| N["New contribution generation"]
  N -->|"revalidates slot and SCC identities"| Q["Incremental reuse decision"]
  Q -->|"all obligations remain equivalent"| R["Reuse with predecessor receipt"]
  Q -->|"dependency or authority changed"| X["Targeted recomputation"]
  R -->|"preserves the recovery causal chain"| O["New generation receipt"]
  X -->|"observes a fresh demand footprint"| O
#+end_src

* Performance semantics

Performance is evidence about bounded semantic work, not a promise that every
generation will be faster.

An incremental evaluation receipt SHOULD distinguish:

- candidate demands considered;
- demands invalidated;
- demands validly reused;
- acyclic slots recomputed;
- SCCs recomputed and their member counts;
- dependency edges reconfirmed, added and removed;
- cache retrievals attempted, accepted and rejected;
- observation and convergence budgets consumed;
- realization work kept outside the pure control plane.

A fast result that omits current-generation dependency validation is not a
successful optimization.

* Required failure conditions

Evaluation MUST fail or enter an explicitly authorized continuable condition
when:

- a purported reuse result lacks a current identity proof;
- a dependency receipt is stale or belongs to an incompatible generation;
- an SCC is only partially reused or recomputed;
- a suppressed contribution or retained contract is omitted from closure
  identity;
- authority or capability scope changed without invalidation;
- a cache payload does not match its semantic result identity;
- replay evidence cannot establish equivalence;
- dependency observation or fixed-point convergence exceeds its budget.

* Acceptance checklist

- [X] Slot demand is the ordinary minimum invalidation unit.
- [X] A cyclic SCC is the minimum fixed-point recomputation closure.
- [X] Dependency footprints come from actual native POO demand.
- [X] Previous footprints are scheduling hints, not current-generation proofs.
- [X] Suppressed contributions and retained contracts participate in reuse
  identity.
- [X] Semantic reuse, physical cache and replay evidence are distinct.
- [X] Resumption always enters a new contribution generation.
- [X] Reuse is authorized by POO evidence objects rather than raw cache keys.
- [X] Incremental performance receipts report semantic work.
- [ ] Validate the model with executable acyclic, branching, priority,
  submodule, SCC, authority-change, stale-cache and resumption scenarios before
  implementation begins.

#+title: POO Flow contribution module layout and build ownership

POO Flow documents the reusable module convention. Contribution repositories
own domain source, while POO Flow owns the Gerbil package namespace and build
environment. Native =std/make= owns source dependency analysis, compilation and
scheduling; POO Flow does not expose a second compiler or scheduler.

The contribution exports its domain module interfaces. It owns neither a
module-source object nor a second module list. POO Flow owns the trusted
contribution registry:
#+begin_src scheme
(make-poo-flow-contribution-registry-entry
 'lambda-episteme
 "https://github.com/tao3k/lambda-episteme.git"
 "ab31bde9cbd09465798991bd91e3a8400f651d6e"
 "packages/lambda-episteme" "modules"
 '(decision-kind diataxis healthcare ontology))
(make-poo-flow-contribution-registry-entry
 'lambda-aitia
 "https://github.com/tao3k/lambda-aitia.git"
 "9363bed3a50729cdfe08ceb5144c350eea6003b3"
 "packages/lambda-aitia" "modules"
 '(ADR assurance gitops sdlc))
#+end_src

POO Flow's default PackageSpec is the clean-image bootstrap: six stable
framework entrypoints and zero catalog targets. =build.ss= imports only ASP's
Build API because importing a =:poo-flow= loader before the package exists is a
self-dependency that fails in a hermetic Bazel image. After bootstrap, module
selection resolves through the ordered POO load path. Available
=src/modules/<module-name>/interface.ss= roots remain catalog data, so adding
100 or 1,000 unselected modules does not widen the package bootstrap.
=init-syntax.ss=, =config-discovery-syntax.ss= and =declaration-case.ss= are
registered framework source refs rather than bootstrap targets. The ordinary
=user-interface/init.ss= path uses the smaller =init-declaration-syntax.ss=
owner, so those advanced authoring and presentation sources compile only for a
consumer that imports them.
=src/user-interface/facade.ss= is likewise an advanced presentation surface,
not the owner imported by =user-interface/init.ss=, and therefore is not a
production bootstrap root.

The final =user-interface/config.ss= imports public Profiles, each
=scenarios/<name>/scenario.ss= declaration, and Profiles below each Scenario.
Case declarations and auxiliary assurance or Provider projections remain
demand-loaded.  Directory discovery therefore scales with reusable composition
inputs instead of importing every implementation file in every vertical Case.
=module-system/observability/testing-extension.ss= follows the same ownership
rule from the testing side: it is imported and compiled by the focused testing
lane, not by every production bootstrap.
User-owned and contributor-owned selections stay in their independent loading
and build lanes.
The root-owned =build-contribute= adapter applies =poo-flow-load-modules=
discovery to each direct =modules/<module-name>/= tree and therefore applies
the same reader-native owner-import admission to contributor roles. Aggregate
framework imports return the structured
=poo-flow.module-owner-import-observation.v1= diagnostic and fail with
=POO-FLOW-MODULE-E008= before a contribution reaches native compilation.
The loader admits exactly the module's public =interface.ss=; native Gerbil
imports close over its internal
roles before ASP =package-source-stage= hands the entrypoint to =std/make=.
The contribution owns no
package manager, scanner, scheduler, cache, or build framework. Its sole
=build.ss= is the native Gerbil entry and inherits ASP's PackageSpec. Core and contribution
artifacts share the package namespace while their build and test lanes remain
independent.

* Ordered POO module sources

Module selection and module location are separate. =poo-flow-modules!= emits
only POO selection objects: qualified module identity and flags. It does not
embed the repository that provides the implementation.

POO Flow constructs =module-source-collection= POO objects from registered or
explicit roots. A =module-load-path= is an immutable POO composition of those
collections. The default path contains =poo-flow-maintained=. The official
contribution path adds POO Flow's trusted registry; Lambda itself adds no
registry. Lookup stops at the first collection containing the module,
so a caller needing private overrides constructs a path with its user source
first. Collection identity, owner, module key and selected entrypoint remain on
the resulting source-ref for diagnosis.

#+begin_src scheme
(poo-flow-modules!
 :workflow (funflow +cicd)
 :custom (sdlc +nasa-7150-2d))
#+end_src

Here =sdlc= is a registered module name. Selecting the registered contribution
name loads every module in that contribution:

#+begin_src scheme
(poo-flow-modules! :custom (lambda-episteme))
#+end_src

When the pinned checkout is absent, resolution produces a =registry= source
carrying the repository, immutable revision and checkout target for the
explicit package/runtime materializer. After materialization, lookup returns to
the same source-collection discovery path.

An explicit private directory is visible in syntax:

#+begin_src scheme
(poo-flow-modules!
 :custom (@ "./modules" +doctor))
#+end_src

This =@= form names a complete modules directory. The same structural discovery
used by =poo-flow-load-modules= finds its direct child trees and admits only
their public =interface.ss= entrypoints.  =config.ss= remains an internal role
re-exported by that interface. The named single-module escape hatch remains
=(my-module @ "./modules/my-module" +doctor)=.

This adapts Doom's ordered module roots and first-match lookup to immutable POO
objects. Doom's source ordering is defined in
[[https://github.com/doomemacs/core/blob/master/lisp/doom.el][doom.el]], its lookup and declaration registry in
[[https://github.com/doomemacs/core/blob/master/lisp/doom-modules.el][doom-modules.el]], and its separately maintained community collection in
[[https://github.com/doomemacs/modules-contrib/blob/main/README.md][modules-contrib]]. POO Flow preserves the source separation without mutable
global load-path state.

* Module structure
This document describes the POO Flow-owned contract for this repository.
Each direct directory under =modules/= is an independently named module and must
provide these five roles. Extra focused implementation files and subdirectories
are permitted; the public entry remains =interface.ss=.

| File | Responsibility | Must not own |
|------+----------------+--------------|
| types.ss | Predicates and source contracts | Default activation, runtime effects |
| objects.ss | POO prototypes and default values | Configuration routing |
| funs.ss | Pure operations over native objects | User syntax or hidden I/O |
| config.ss | User selection to module/profile projection | Runtime execution |
| interface.ss | Public exports | Business logic or another DSL |

Security-sensitive modules may additionally provide =contracts.ss=.  This
optional role owns relational invariants spanning two or more already typed
objects, such as Provider/capability compatibility, identity joins, digest
bindings or handoff eligibility.  It must not duplicate the element predicates
owned by =types.ss=, construct defaults owned by =objects.ss=, or perform the
runtime effect.  The public =interface.ss= imports it explicitly when present.

An extension-bearing module uses one closed expression chain:

#+begin_example
generic protocol -> checked method bundle -> native POO/type composition
                 -> thin hygienic defrule -> public interface
#+end_example

=types.ss= owns the native classes or =define-type= carriers needed by the
domain. =objects.ss= owns protocol objects, generics and inheritable prototypes.
=funs.ss= owns pure implementation functions and the default method bundles.
=contracts.ss=, when present, owns cross-object admission and is called by the
pure projection before any runtime handoff.
An optional =syntax.ss= may expose a small =defrule= that lowers directly to one
of those ordinary bundles; it may not own dispatch, policy evaluation or a
second registry. =interface.ss= closes the chain for consumers.

This requirement applies wherever a module exposes behavior intended for
downstream extension, such as workflow providers, storage backends or policy
families. A data-only leaf module reuses its owner's protocol and native types;
it must not create an empty generic, bundle or macro merely to imitate the file
shape. Every behavior still has one protocol owner and one evaluator.

Dependencies flow from types through objects/functions to configuration and the
public interface. Same-module imports reversing those layers are rejected by
build preflight, including wrapped and relative imports. This check covers
literal top-level import declarations; std/make remains responsible for the full
Scheme dependency graph and compilation. Cross-module consumers use public
interfaces; focused internal owners may import lower-level implementation units.
Public extension is native POO derivation; do not bind type identity to a user's
chosen profile identity string. Functions validate derived inputs at boundaries.
When capturing local values inside =.o=, use names distinct from the emitted
slot names (for example =status-value= for =status:=). Native slot binding can
otherwise shadow the lexical value. Tests must read diagnostic/result slots,
not only construct the object, to expose recursive or incorrect bindings.
No contributor runtime, backend or implicit registration is installed by import.

* Closed User Interface repository shape

The contribution's =user-interface/= is a repository entry surface, not a flat
examples directory. Its Scheme-bearing top level is closed:

| Path | Owner |
|------+-------|
| =init.ss= | Module enablement only through =poo-flow!=. |
| =config.ss= | Final direct =use-composition= declarations. |
| =modules/= | User-owned =modules/<module-name>/= trees that are private or not ready for contribution. |
| =profiles/= | Reusable native POO Profile objects and their refinements. |
| =scenarios/= | Reusable scenario cases and review exercises consumed by compositions. |

This borrows Doom's fixed entry roles and the repository classification common
in NixOS configurations. Local =modules/<name>/= trees follow the normal five
module roles and are ignored by Git; the directory has no source registry or
loader file. POO Flow's internal loader constructs the user-first source path.
Promotion to the contribution's top-level =modules/= tree is an explicit
review boundary.

POO Flow also adds first-class =profiles/=
because a Scenario may reuse the same modules with several independently
inheritable Profiles. A GitHub Workflow therefore has four distinct layers:
module enablement in =init.ss=, reusable Profile objects under
=profiles/<domain>/<case>.ss=, reusable Scenario values under =scenarios/=, and
final developer/staging/production =use-composition= declarations in
=config.ss=. POO Flow discovers the two directories once per config expansion;
the user does not write an aggregate import list or wrapper form.

“Best practice” is a quality responsibility of these
Profile objects; filenames identify concrete reusable cases. A user refinement
lives under an owner namespace such as =profiles/tao3k/promotion.ss= and records
its owner and feature set on the native POO object.

The root POO Flow contributor builder validates this shape before invoking ASP.
Any other top-level =*.ss= file is rejected with =POO-FLOW-UI-E002= rather than
silently compiled as an unclassified example. Each role directory is a separate
observable ASP source stage. =init.ss= is loaded before discovered Modules,
Profiles and Scenarios; =config.ss= closes the sequence. The child repository
does not own a build script, package file, directory walker, or role registry.

* Directory build

The contribution has no =build-contribute.ss= and no =gerbil.pkg=. POO Flow's
default =build.ss= owns the core PackageSpec and =defbuild-script=. Its separate
root-level contribution adapter consumes the same POO module source objects
used by runtime loading. Shared contribution facilities and the closed User
Interface roles are explicit directory stages; direct module directories are
discovered by the core source collection,
so no hand-maintained implementation file list or =all-gerbil-modules= scan
exists. A new =types.ss=, =funs.ss=, standard leaf, or other Scheme source is
automatically included in its owning module stage.

Each stage uses the selected entrypoint's containing directory as =srcdir= and
retains the full =poo-flow/<contribution>/modules/<name>= prefix. The adapter
prints =source-stage-start= before invoking ASP and =source-stage-complete=
afterward, with elapsed time and receipt count. This makes a cold or stalled
module attributable without changing ASP or upstream =std/make=.

Contribution tests are a separate lane. POO Flow maps a selected
=t/<module-name>/= tree to one ASP stage containing its =build-root.ss= and all
recursively discovered =*-test.ss= files, or maps an exact test file to its own
stage, and delegates currentness and compilation to =std/make=.
The stage source is the selected file's directory and its install prefix retains
the complete =poo-flow/<contribution>/t/...= namespace. This prevents the
repository root from shadowing compiled production dependencies and prevents a
missing prefix from recompiling an unchanged file. No child PackageSpec,
dependency parser, scheduler, or generated list of test files is introduced.


* Qualification boundary

The package-native build and =unit-tests.ss= are the executable evidence.
Generated output enumeration and independent source-catalog receipts are not
part of this module convention.

* CLOS contracts for pure model snapshots
=contribution/model.ss= projects existing =poo-clos= class metadata onto ordinary
POO values. Contributors declare =poo-clos-class= and
=poo-clos-direct-slot-definition= values in =types.ss=. CLOS owns superclass
resolution and effective slots, including conjunction of inherited predicates.
=objects.ss= extends =poo-flow-model-prototype= with =.o= and checks the result
with =poo-flow-check-model=. Public algorithm boundaries use =poo-flow-model?=
to revalidate derived overrides. An equal kind or copied class marker never
substitutes for actual prototype ancestry.

This projection is deliberately for pure snapshots. It requires all declared
slots and does not run initforms, allocate class slots, dispatch lifecycle
hooks, or claim to create a mutable CLOS instance. Classes for this projection
should declare instance slots only and supply values explicitly. Features
requiring CLOS lifecycle state use =poo-clos-make-instance= instead. No second
class registry, slot merge algorithm, or public macro language is introduced.

SDLC supplies domain classes in the independent contribution repository; this
projection and its tests belong to POO Flow. NASA source rows remain source
catalog data rather than being turned into lifecycle instances.


* Large source catalogs and warm-build cost
Native =std/make= expands selected source modules while determining dependencies
even when no output needs recompilation. Public-entry PackageSpec projection
imports only the stable framework roots during clean-image bootstrap.
A large data catalog should use one shared POO constructor over ordinary quoted
source data, instead of emitting a full =.o= macro declaration for every row.
Atomic test builds avoid the redundant public-entry projection because their
one file is already explicitly selected. No new scheduler or cache is involved,
and =std/make= remains responsible for source currentness and compilation.

Scale receipts keep catalog size =N= distinct from selected module count =K=.
The 100 and 1,000 module cases project source-ref data without forcing a loader
and report =selected-build-target-count=0=. Timing is emitted as Observability
evidence rather than compared with a machine-specific constant in a semantic
unit test. Test observation cadence is selected by a native POO Observability
Profile, so CI and user profiles can refine heartbeat timing without editing
the observer.

Atomic tests must also keep their runtime import closure proportional to the
capability under test. A test that needs =sdlc-project= imports =objects.ss=;
it does not import the aggregate =interface.ss= merely for that constructor.
The aggregate interface remains the normal user composition surface, while
test ownership follows =t/<module-name>/...= and selects precise domain owners.
This distinction reduced the warm NASA certification atomic path to about 2.6
seconds including source observation, dynamic import observation, and its 20
assertions. Its warm source stage reports zero compile entries and about 0.16
seconds inside the ASP Build API.

Before evaluating an atomic test, POO Flow applies its strict POO slot authoring
observation to the selected module tree and exact test file, then dynamically
imports that exact compiled test before =gxtest=. Events are flushed at
=source-start=, =source-scanned=, =source-admitted=, =test-start= and
=test-complete=. The reader-native preflight never imports or compiles the test;
native =gxtest= owns that boundary. Separate budgets bound the
source/import preflight and case execution, so the last event identifies the
stalled boundary. The normal path stays lightweight. The opt-in
=observe-contribute-import-memory= path wraps import in the native POO Debug
memory monitor and terminates excessive heap or live-set growth with a typed
receipt.

* Explicit verification boundaries

=contribution/verification.ss= provides a domain-neutral host-configured adapter,
issuance, current validity and revocation operations. A contribution supplies
its typed request projection and snapshot function. The host supplies the actual
verification operation and clock. Submitted POO objects cannot authorize
themselves by adding a flag or copying a receipt's slots.

Receipt issuance and revocation are explicit effects isolated in the adapter;
contribution assessment and lifecycle transitions remain pure. Private receipt
identity, copied snapshots, interval checks and revocation define session-local
admission. This is not a persistent signature store or concurrent authority
service. No NASA field or source identifier occurs in the generic mechanism.
=t/contribution/unit/verification-test.ss= qualifies the generic boundary;
NASA request semantics and scenario tests stay in the independent contribution.

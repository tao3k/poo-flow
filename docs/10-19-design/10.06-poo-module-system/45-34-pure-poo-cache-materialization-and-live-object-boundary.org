#+title: Pure POO Cache Materialization and Live Object Boundary
#+status: Accepted
#+language: en

* Decision

A physical cache may store a canonical pure projection of an authorized POO
result.  It MUST NOT store or restore a live POO object, dynamic control extent,
runtime authority or external resource.

Retrieval produces an inert candidate artifact.  The artifact becomes a
current-generation semantic result only after the live POO context validates
its identity, contracts, dependencies, capability requirements, authority
scope and replay equivalence.

#+begin_quote
Cache materialization preserves pure semantic evidence; it never preserves
live authority.
#+end_quote

* Native POO boundary

=gerbil-poo= remains the sole implementation of POO objects, prototypes, slots
and open recursion.  POO Flow does not serialize the implementation object and
later pretend that it is the same live object.

The cache boundary MUST NOT introduce:

- a second object model;
- a record DSL that replaces native POO composition;
- a portable raw memory image of a POO object;
- serialization-defined slot semantics;
- a cache-provider API in ordinary user composition;
- automatic effect replay on retrieval.

Cache projection and retrieval are evidence operations around native POO
evaluation.

* Materialized projection, not live object

#+begin_src mermaid
flowchart LR
  O["Live native POO demand"] -->|"produces a pure validated result"| S["Canonical semantic receipt"]
  S -->|"projects only stable value and evidence identities"| A["Inert cache artifact"]
  A -->|"decodes without authority or execution"| Q["Quarantined candidate"]
  Q -->|"validates against the current POO context and generation"| V["Replay-equivalent candidate"]
  V -->|"enters canonical semantic commit"| R["Current-generation result"]
  Q -->|"identity, contract, dependency or authority check fails"| X["Rejected cache evidence"]
#+end_src

The materialized artifact does not retain object sameness.  It retains a claim
that a pure result with a particular semantic identity was previously
validated.

* Cacheability classes

| Class | Materialization rule |
|-------+----------------------|
| Canonical pure scalar or aggregate value | Cacheable when encoding and semantic identity are stable |
| Pure observed slot result | Cacheable with its complete dependency, contract and generation evidence |
| Canonical evidence receipt | Cacheable as evidence, never as current authority |
| Prototype or contract definition identity | Cacheable as a content identity or canonical descriptor, not as a process-local closure |
| Pure effect-intent description | May be retained only as inert evidence; retrieval does not restore authorization or commit eligibility |
| Continuation or resumption | Never cacheable |
| Live capability or authority handle | Never cacheable |
| Resource lease or external handle | Never cacheable |
| Mutable POO object or process-local identity | Never cacheable |

* Required cache projection

A cache artifact for a pure observed result MUST carry or commit to:

- artifact schema and canonical encoding identity;
- result semantic identity and canonical value projection;
- predecessor semantic receipt identity;
- POO object and prototype-lineage identities;
- demanded slot identity;
- complete contribution-closure identity;
- slot-contract and priority identities;
- dependency-footprint and sealed SCC identities where applicable;
- capability requirements without live capability handles;
- authority requirements without authority tokens;
- source contribution generation;
- replay-equivalence requirements;
- deterministic encoding digest.

Operational fields such as worker identity, completion order, wall-clock
duration and cache latency do not participate in the semantic artifact
identity.

* Objects that cannot cross the cache boundary

The following live values MUST NOT be encoded as reusable semantic results:

- first-class continuations;
- continuable exception resumptions;
- dynamic-wind before/after extent;
- active exception-handler stacks;
- threads, futures, mutexes and synchronization state;
- ports, sockets, file descriptors and process handles;
- resource leases and cleanup ownership;
- current capability handles;
- authority tokens, delegation handles and revocation state;
- mutable POO objects whose identity depends on process-local state;
- open transactions or effect-commit handles;
- clocks, random generators or ambient environment snapshots presented as pure
  values;
- non-canonical procedure closures with captured live state.

flowchart TD
  L["Candidate runtime value"] -->|"is a canonical pure value with complete evidence"| P["Eligible projection"]
  L -->|"captures continuation or dynamic extent"| C["Live control state"]
  L -->|"carries capability, authority or lease"| A["Live authority state"]
  L -->|"contains mutable or external handle identity"| M["Live runtime state"]
  C -->|"cannot cross the cache boundary"| N["Non-cacheable"]
  A -->|"cannot cross the cache boundary"| N
  M -->|"cannot cross the cache boundary"| N
  P -->|"strips all operational authority before encoding"| I["Inert artifact"]
#+end_src

Non-cacheable does not mean invalid.  It means the value must remain within its
live lifecycle and generation rather than being materialized for later reuse.

* Capability description is not capability authority

A pure result may state that a capability is required or that a capability
identity participated in validation.  Such a statement is evidence, not the
capability itself.

On retrieval:

- the current live context must supply the capability;
- ownership and prototype lineage must be revalidated;
- authority must be current and unrevoked;
- attenuation and delegation rules must be applied again;
- the artifact cannot mint, extend or revive a capability.

A content digest proves artifact integrity.  It does not grant authority.

* Effect-intent boundary

An effect intent may be represented as a pure declarative POO value before
realization.  Its inert description may appear in a cache artifact only when
the description is itself canonical and pure.

Retrieval MUST NOT:

- schedule the effect;
- restore an old approval;
- restore a commit token;
- claim that the external world is still in the predecessor state;
- bypass reconciliation;
- reuse a resource lease or cleanup obligation.

The retrieved intent re-enters the current generation as an inert candidate.
Current authority, suspension, handoff, reconciliation and reinjection rules
decide whether it may proceed.

  A -->|"retrieval restores description only"| I["Current-generation intent candidate"]
  I -->|"revalidates authority and external preconditions"| H["Effect-boundary handoff"]
  H -->|"current reconciliation authorizes realization"| R["Runtime effect"]
  I -->|"authority or world state differs"| X["Reject, refine or suspend"]

* Rehydration protocol

Cache retrieval follows a fail-closed evidence sequence:

1. decode the artifact into a quarantined inert representation;
2. verify schema, canonical encoding and content digest;
3. resolve the current native POO object, prototype and slot identities;
4. compare complete contribution, contract, priority and dependency identities;
5. revalidate current capability and authority requirements;
6. reject stale generation-bound control or runtime state;
7. reapply required slot contracts to the decoded pure value;
8. establish replay equivalence with the predecessor semantic receipt;
9. admit the value as a candidate to canonical semantic commit.

No step reconstructs a predecessor continuation, authority handle or external
resource.

* Rehydration does not preserve generation

The artifact records its source generation.  Retrieval occurs in a current
generation.

The current semantic receipt links to the predecessor artifact and receipt, but
it is not the predecessor generation.  Any current resumption, authority,
dependency or topology evidence belongs to the new generation.

This distinction prevents cache retrieval from reviving stale continuations or
revoked authority.

* Mutable POO values

Native POO supports effectful object operations, but mutable live objects do
not have portable cache identity merely because they are POO objects.

A cacheable projection may be derived only through an explicit pure semantic
projection that:

- observes an authorized stable boundary;
- excludes process-local identity and mutation capability;
- produces a canonical immutable value;
- records the generation and predecessor receipt;
- does not claim that rehydration restores the mutable object.

Retrieval may supply data from which current live code constructs a new native
object.  The newly constructed object has current identity and authority; it is
not the old object revived.

* Cache trust boundary

Every cache artifact is untrusted until validated, including artifacts read
from a local process cache.

POO Flow MUST distinguish:

- byte integrity;
- canonical encoding;
- provenance;
- semantic identity;
- current dependency validity;
- current authority;
- replay equivalence.

Possessing the bytes or matching one digest is insufficient to establish all
of these properties.

* Canonical and operational evidence

The canonical semantic receipt records whether predecessor semantic evidence
was validly reused.  The operational receipt records:

- physical cache backend;
- hit or miss;
- retrieval duration;
- decode failure;
- rejected stale or malformed artifact;
- storage and eviction activity.

Changing cache backend, eviction policy or storage location cannot change the
canonical POO result.

* Eviction and garbage collection

Physical cache eviction removes an optimization artifact.  It MUST NOT:

- revoke a semantic result already committed;
- revoke live authority;
- change contribution identity;
- alter fixed-point convergence;
- delete the canonical receipt required for an active causal chain.

If durable replay requires a receipt, that receipt belongs to the evidence
lifecycle rather than being treated as disposable cache data.

* Required failure conditions

Retrieval MUST fail closed when:

- an artifact contains or claims to restore a continuation or resumption;
- live capability, authority or lease material is encoded;
- a mutable object is presented as the same live object after rehydration;
- schema or canonical encoding identity is unknown;
- contribution, contract, priority, dependency or SCC identity differs;
- current capability or authority validation fails;
- an effect intent attempts to recover old approval or commit state;
- replay equivalence cannot be established;
- a cache digest is treated as authority;
- operational cache metadata changes the semantic result.

* Acceptance checklist

- [X] Cache artifacts contain canonical pure projections, not live POO objects.
- [X] Retrieval begins as quarantined inert evidence.
- [X] Current native POO identities and contracts are revalidated.
- [X] Continuations, resumptions and dynamic control extent are never cached.
- [X] Capability, authority and resource handles are never cached.
- [X] Mutable POO identity is never revived through materialization.
- [X] Pure effect-intent descriptions remain inert and regain no authorization.
- [X] Rehydration enters the current generation.
- [X] Content integrity and authority are distinct.
- [X] Cache operational evidence is separate from canonical semantic evidence.
- [X] Eviction cannot change module semantics.
- [ ] Validate the boundary with executable pure-value, stale-generation,
  capability-revocation, continuation, mutable-object, effect-intent,
  malformed-artifact and backend-variation scenarios before implementation
  begins.

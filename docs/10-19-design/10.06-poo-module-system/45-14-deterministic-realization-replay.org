#+title: Deterministic Realization Replay

* Normative responsibility

This module owns the optional POO Flow debugging and testing semantics for:

- receipt-DAG verification;
- pure re-realization in a fresh POO runtime context;
- effect-receipt replay without provider invocation;
- causal comparison and first-divergence evidence;
- replay barriers for missing, non-portable, or indeterminate evidence.

Replay is not required for correct production realization.  It is not an
active-evidence closure, runtime cache, object snapshot, scheduler recording, or
external-effect emulator.

* Ownership boundary: POO Flow semantics and GSLPH dev harness

POO Flow owns:

- the replay evidence contract;
- qualification gates;
- causal partial-order semantics;
- replay conditions and comparison receipts;
- the prohibition on effect and continuation serialization.

=gerbil-poo= remains the sole Scheme POO implementation and owns prototype
construction, demand realization, memoization, lineage, fixed-point mechanics,
and continuation-aware control.

GSLPH is a development dependency.  It may consume POO Flow replay evidence as
a policy harness and building/testing framework.  It does not:

- provide production runtime semantics;
- become a POO Flow provider;
- own replay, effect, recovery, or receipt semantics;
- enter the production dependency closure merely because replay tests exist;
- replace Gerbil package management or =gerbil-poo=.

A GSLPH test harness may instantiate explicit test policies and verify produced
receipts.  Those fixtures are test inputs, not normative production policy.

* Replay capabilities

The contract defines three distinct capabilities:

| Capability | Executes POO code | Invokes external provider | Result |
|---+---+---+---|
| receipt verification | no | no | validates receipt identities, transitions, and causal edges |
| pure re-realization | yes, in a fresh context | no | recomputes demanded pure values and compares evidence |
| effect-receipt replay | yes, in a fresh context | never | injects qualified recorded effect results at matching intents |

The capabilities may be combined, but their receipts remain distinguishable.
Receipt verification alone does not prove that current code reproduces the
recorded realization.

* Replay evidence artifact

A replay evidence artifact is a partial, demand-indexed causal DAG.  It may
contain:

- composition content and macro-lowering evidence;
- resolved =gerbil-poo= dependency revision evidence;
- demanded coordinates and POO lineage evidence;
- portable pure values or content-addressed artifacts;
- effect, recovery, provider-selection, admission, lease, cancellation, and
  resource-policy receipts;
- causal predecessor and containment edges;
- bounded diagnostic annotations.

It MUST NOT contain:

- a serialized POO runtime root;
- a closure or first-class continuation;
- an active or suspended demand cell;
- a runtime resource handle or dynamic access authority;
- a capacity permit;
- a provider process, socket, thread, or lease;
- an implicit claim about undemanded lazy slots.

The artifact is optional debugging/testing evidence.  It is not production
mutable state and is not required to remain active after realization.

* Qualification gates

Before replay, POO Flow validates:

- exact composition content and macro-lowering evidence;
- the resolved =gerbil-poo= dependency revision recorded by build/runtime
  evidence;
- Profile, Mix, provider, recovery, resource, cancellation, and admission
  policy identities;
- receipt schema, identity, causal predecessor, and transition validity;
- portable value or verified artifact evidence at every injected coordinate;
- absence of an unresolved barrier before the requested replay frontier.

This consumes resolved dependency evidence.  It does not project or redefine
=gerbil.pkg= package management.

#+begin_src mermaid
flowchart TD
  G["State: recorded causal evidence DAG"] -->|"composition + lowering qualification"| C["State: code-qualified evidence"]
  C -->|"resolved gerbil-poo + policy qualification"| P["State: environment-qualified evidence"]
  P -->|"receipt DAG + portable value qualification"| Q["State: replay-qualified frontier"]
  G -->|"missing or mismatched evidence"| M["State: structured replay-qualification condition"]
  P -->|"indeterminate external evidence"| B["State: proven replay barrier"]
  Q -->|"construct fresh root and context"| N["State: replay realization"]
  R["State: original runtime root, handle, or continuation"] -.->|"never serialized, imported, or equated"| N
#+end_src

Qualification is frontier-specific.  Evidence after an indeterminate barrier
cannot qualify an earlier unknown outcome by implication.

* Fresh runtime identity

Every pure re-realization or effect-receipt replay constructs:

- a fresh =gerbil-poo= runtime lineage root;
- a fresh realization-context identity;
- fresh demand-cell and continuation identities;
- a replay receipt linked to, but distinct from, the source evidence.

Equal source content or receipt qualification does not make the replay root
identical to the source runtime root.

Lexical Scheme names remain diagnostic attribution only.

* Causal partial order

Replay preserves semantic causality, not wall-clock interleaving.  The evidence
DAG distinguishes:

- POO dependency edges;
- boundary containment;
- explicit Mix import dependencies;
- effect-state predecessor receipts;
- recovery and policy decisions;
- suspension and reinjection;
- cancellation, lease, admission, and capacity evidence.

#+begin_src mermaid
flowchart LR
  A["State: demanded coordinate A"] -->|"POO dependency edge"| C["State: demanded coordinate C"]
  B["State: demanded coordinate B"] -->|"POO dependency edge"| C
  A -.->|"ready sibling execution order is non-authoritative"| B
  E["State: effect receipt"] -->|"verified reinjection edge"| C
  P["State: policy decision receipt"] -->|"authorizes transition"| E
  C -->|"causal result evidence"| R["State: comparison frontier"]
#+end_src

Independent ready siblings may execute in a different runtime order during
replay.  Their POO results and causal evidence must remain equivalent.
Historical scheduler timing MUST NOT become prototype refinement precedence.

Observed timing may remain a diagnostic annotation, but it is not replay
authority.

* Receipt verification

Receipt verification checks without executing POO code:

- schema and identity validity;
- causal predecessor existence;
- legal state transitions;
- boundary and generation ownership;
- provider verifier, cancellation, lease, and admission evidence;
- absence of contradictory terminal claims;
- causal-DAG acyclicity where terminal receipt ordering requires it.

Verification reports the first invalid receipt and its predecessor evidence.
It does not repair, reinterpret, or execute the recorded transition.

* Pure re-realization

Pure re-realization evaluates only demanded POO coordinates in the fresh
context.  It uses ordinary =gerbil-poo= realization and memoization.

Undemanded lazy slots remain undemanded.  Replay tooling MUST NOT traverse the
object graph eagerly to manufacture coverage.

At each demanded pure coordinate, replay compares:

- boundary and lineage evidence;
- normalized refinement provenance;
- result content evidence;
- condition and recovery-decision evidence;
- causal dependencies.

A difference produces structured first-divergence evidence rather than silently
substituting the recorded value.

* Effect-receipt replay

When replay encounters an effect intent, it MUST NOT invoke a provider.  It
matches the intent against recorded evidence:

#+begin_src mermaid
flowchart LR
  I["State: replay effect intent"] -->|"match boundary + operation + verifier evidence"| R["State: recorded effect receipt candidate"]
  R -->|"receipt and value/artifact gates pass"| V["State: evidence-linked replay value"]
  V -->|"resume fresh replay demand"| D["State: replayed POO realization"]
  R -->|"missing, stale, or mismatched receipt"| M["State: structured replay mismatch"]
  R -->|"recorded outcome is indeterminate"| B["State: replay stops at effect barrier"]
  I -.->|"never invokes live provider"| X["State: external runtime"]
#+end_src

A committed receipt qualifies only the exact intent, operation evidence,
verifier policy, and demanded coordinate it proves.  It is not a wildcard
effect stub.

Failed, cancelled, and indeterminate receipts reproduce their structured
conditions and permitted control frontier.  Replay does not invent a successful
value.

* Recovery and continuation reconstruction

Replay reconstructs control by re-executing pure Scheme paths and consuming
qualified recovery-decision receipts.  It does not serialize or restore a
captured continuation.

A recorded recovery decision qualifies only when:

- the replayed structured condition matches;
- boundary and continuation-generation evidence match;
- the same recovery authority is present;
- the decision does not require an unavailable runtime-local handle.

=dynamic-wind= access attachment is reconstructed only for fresh replay-local
resources.  Historical handles and leases are never reattached.

If a decision depends on unrecorded external input or runtime-local authority,
replay stops with missing-evidence or non-portable-authority evidence.

* Cancellation, leases, and admission

Replay verifies cancellation generation, lease, and admission receipts without
recreating their runtime authorities:

- a cancelled ordinary generation remains invalid;
- cleanup decisions reproduce only their recorded control frontier;
- released leases remain released evidence, not replay handles;
- indeterminate leases remain barriers;
- capacity permits are verified as historical receipts and never reissued;
- backpressure causal edges may be compared without reproducing wall-clock
  queue timing.

Effect, lease, cancellation, and capacity receipts can justify a portable value
or artifact only through the normal admission gates defined by their owning
RFCs.

* Replay conditions

The semantic condition families are:

- replay qualification failure;
- missing evidence;
- non-portable authority;
- first causal divergence;
- indeterminate replay barrier;
- contradictory or invalid receipt.

Exact identifiers remain API-evidence-gated.

Policy-visible recovery may inspect bounded evidence, narrow the replay
frontier, stop at the proven barrier, or abort replay.  Switching to live
external execution is a separate explicitly authorized operation, not a replay
restart.

There is no =assume-success=, =ignore-mismatch=, or =invoke-provider= replay
restart.

* Replay comparison receipt

#+begin_src mermaid
flowchart TD
  S["State: source causal DAG"] -->|"qualified evidence projection"| C["State: comparison"]
  R["State: fresh replay causal DAG"] -->|"new-root evidence projection"| C
  C -->|"equivalent demanded frontier"| E["State: replay-equivalent receipt"]
  C -->|"first mismatch"| M["State: divergence receipt"]
  C -->|"proven external uncertainty"| B["State: barrier receipt"]
  M -->|"identify coordinate + predecessor + failed gate"| D["State: bounded diagnostic"]
  B -->|"identify last proven frontier"| D
#+end_src

The comparison receipt records:

- source and fresh replay provenance identities;
- qualified frontier;
- causal partial-order comparison;
- demanded coordinates compared;
- first divergence or barrier;
- policy and verifier identities;
- no claim of runtime-root identity equivalence.

Replay evidence and comparison receipts use the canonical identity, projection,
predecessor, correction, contradiction, and redaction semantics defined by
[[file:45-15-receipt-object-canonical-evidence-projection.org][Receipt Object And Canonical Evidence Projection]].

* GSLPH harness boundary

GSLPH may provide development-only:

- harness policy fixtures;
- build/test orchestration;
- replay corpus execution;
- receipt assertions;
- deterministic test reporting.

POO Flow core emits and validates its own semantic receipts.  GSLPH does not
provide production providers, runtime handles, effect results, package
resolution, or normative policy.

Production code MUST NOT require GSLPH merely to realize a composition or
validate a runtime receipt.

Replay conformance and adversarial missing/contradictory evidence scenarios
follow
[[file:45-16-semantic-conformance-adversarial-fault-injection.org][Semantic Conformance And Adversarial Fault Injection]].  GSLPH may orchestrate
those development scenarios but does not own their oracle.

* Observability contract

Observability distinguishes receipt verification, pure re-realization,
effect-receipt injection, comparison, divergence, and barrier events.

No observability sink may:

- invoke a provider;
- alter the replay frontier;
- inject an unqualified value;
- resume a source continuation;
- reattach a source lease;
- equate source and replay runtime roots.

Diagnostic output remains bounded and follows the existing condition-first
snapshot rules.

* API evidence gate

The semantics in this module are normative.  Exact artifact, verifier,
condition, comparison, and harness identifiers remain =semantic-required=
until the relevant =gerbil-poo= and POO Flow surfaces are symbol-located,
behavior-proven, and flow-qualified.

Any generally reusable POO causal replay mechanism belongs upstream in
=gerbil-poo=.  POO Flow MUST NOT ship a shadow POO evaluator, continuation
serializer, effect emulator, or scheduler recorder.

* Explicit exclusions

This RFC does not authorize:

- live provider invocation during replay;
- serialized POO roots, closures, continuations, demand cells, handles, leases,
  or capacity permits;
- forcing undemanded lazy slots;
- wall-clock scheduler order as semantic precedence;
- continuing past an indeterminate barrier by assumption;
- replay values that bypass normal admission gates;
- GSLPH as production runtime, provider, receipt authority, or package manager;
- an active-evidence closure required by normal realization;
- a public replay DSL before the real APIs are behavior-proven.

#+title: Control Policy Profile Projection and Use-Composition Interface
#+startup: overview

* Status

Accepted architecture.

This RFC freezes how the POO-native control-policy algebra in
[[file:45-90-poo-control-policy-composition-priority-conflict-and-veto-resolution.org][45-90]]
enters the ordinary Profile composition interface.

It does not freeze unverified ~gerbil-poo~ call forms and does not authorize a
new user-facing DSL.

* Scope

This document owns:

- the ordinary user surface for selecting Profiles that contribute control
  policies;
- the higher-order Profile projection of POO-native policy objects;
- the distinction between policy presence and runtime authority;
- the pure collection of policy contributions during Profile composition;
- the preservation of the owning Profile's POO-native ~imports~ object;
- duplicate policy identity admission;
- the advanced POO extension path; and
- macro-governance constraints for this interface.

It does not own:

- the condition, decision, or capability algebra;
- policy priority resolution;
- runtime continuation primitives;
- native Profile fixed-point evaluation;
- package management;
- a hidden policy registry; or
- an additional composition language.

* Central decision

The ordinary user interface remains exactly one ~use-composition~ form whose
body is one ~(compose profiles ...)~ expression.

#+begin_src scheme
(user-composition my-system
  (compose profiles
    (use-module wendao-episteme
      production-governance)
    (use-module runtime
      distributed-runtime
      sandboxed)
    (use-module observability
      full-receipts)))
#+end_src

#+begin_src typst
$ "ordinary-surface" =
  "user-composition"("system", "compose"("profiles", p_1, dots, p_n)) $

$ "operand-kind"(p_i) in ("Profile", "ProfileBundle") $
$ "raw-ControlPolicy" notin "compose-operands" $
$ "nested-user-composition" = false $
$ "nested-compose" = false $
#+end_src

Each ~use-module~ expression produces a ProfileBundle that is admitted as a
normal higher-order Profile operand.  It is not a raw ControlPolicy, runtime
handler, or clause interpreted by ~use-composition~.

No additional wrapper is introduced:

- no nested ~use-composition~;
- no nested ~compose~;
- no ~control-policies~ clause;
- no ~initial~ form;
- no host ~if~, ~cond~, or ~case~ inside the composition;
- no keyword configuration block; and
- no runtime token dispatch.

* Two user altitudes

** Ordinary composition user

The ordinary user chooses prepared Profile values.

A prepared Profile may contribute:

- domain behavior;
- imports;
- identity constraints;
- capability requirements;
- control policies;
- observers; and
- runtime handoff declarations.

The user does not need to know how each contribution is represented internally.
Every operand remains a Profile and the composition stays flat.

An operand may be a ProfileBundle produced by the constrained ~use-module~
projection.  That bundle preserves the selected Profiles together with the
Module's ~imports~, identity, and capability objects.

The exact Module-to-ProfileBundle algebra is owned by
[[file:45-93-module-profile-selection-bundle-and-imports-closure-algebra.org][45-93]].

** Advanced policy author

An advanced author works through the POO object and prototype interface.

The author may:

- extend a ControlPolicy prototype;
- compose domain evidence prototypes;
- attenuate capability requirements;
- provide an exact-integer DecisionPriority;
- refine a prepared control Profile; or
- construct a new higher-order Profile that contributes the policy.

The advanced interface is the native POO interface adopted through
[[file:45-85-poof-proof-adoption-and-poo-flow-correspondence-obligations.org][45-85]].
It is not a second policy DSL.

Executable examples of that advanced path must wait until the exact
fixed-commit ~gerbil-poo~ call forms are revalidated.  This RFC does not invent
those call forms.

* Higher-order Profile projection

A control Profile contains a pure POO projection whose result contributes
ControlPolicy objects to the composed Profile.

The projection preserves:

- policy identity;
- policy prototype lineage;
- imports required by the policy;
- capability requirements;
- priority;
- pure evidence contracts;
- resolver compatibility; and
- provenance of the contributing Profile.

The projection does not contain:

- a live continuation;
- a runtime exception handler;
- an issuer witness;
- a mutable authority cell;
- a portable resumption capability;
- a Profile result; or
- an unresolved external effect.

The composed Profile owns a first-class immutable policy collection.  It does
not populate a global or hidden registry.

* user-composition ownership

The exact current-gap evidence and target thin-macro contract are owned by
[[file:45-92-user-composition-current-gap-and-thin-macro-contract.org][45-92]].
This section owns the higher-order Profile projection seen through that macro.

~user-composition~ is a thin hygienic module-definition macro.

It may:

- bind the final composed Profile under the requested module identity;
- establish compile-time import hygiene;
- report expansion-time structural errors; and
- project the ordinary module surface.

It must not:

- enumerate ControlPolicy objects;
- compare policy priorities;
- issue capabilities;
- install runtime handlers;
- evaluate Profiles;
- resolve control decisions;
- create a registry; or
- change semantics based on operand source order.

The macro expands once.  Runtime control does not re-enter macro expansion.

* compose and profiles ownership

~compose~ remains an ordinary pure function.

~profiles~ remains a first-class POO composition-strategy object.

Neither name is overloaded with a control-policy sublanguage.  Policy
collection follows from the semantics of the Profile operands and the
~profiles~ strategy.

The Profile composition phase:

1. admits every operand as a Profile or ProfileBundle;
2. composes the Profile prototypes;
3. preserves native Profile identity and capability constraints;
4. collects pure policy contributions by stable policy identity;
5. validates duplicate identities;
6. constructs one immutable policy collection; and
7. performs one explicit root instantiation.

It does not execute a ControlPolicy against a ControlCondition.

* Policy presence is not authority

Including a control Profile expresses policy intent and requirements.
It does not create runtime authority.

A Profile cannot grant itself:

- Continue authority;
- suspension authority;
- veto authority;
- cancellation authority;
- a live continuation capability; or
- resumption authority.

Runtime authority is issued and validated at the explicit evaluator boundary
under the identity and capability algebra in
[[file:45-89-poo-native-control-condition-decision-and-capability-algebra.org][45-89]].

A policy whose required capability is unavailable remains visible as an
inadmissible policy with an actionable receipt.  It must not disappear from the
composition and must not silently degrade to a weaker policy.

* Policy collection semantics

The immutable policy collection is keyed semantically by stable policy
identity, not by insertion position.

For two contributions with different identities:

- both remain present;
- enumeration order is canonical;
- source order has no semantic meaning; and
- runtime candidate resolution remains owned by 45-90.

For two contributions with the same identity:

- identical contributions are idempotent;
- compatible prototype refinements compose under the admitted POO laws;
- capability requirements form an intersection;
- evidence contracts accumulate canonically; and
- incompatible definitions fail Profile admission.

A duplicate conflict is not resolved by:

- last writer wins;
- Profile operand position;
- numeric DecisionPriority;
- native slot precedence that erases a constraint; or
- a macro expansion accident.

DecisionPriority applies later to decision candidates for one observed
condition.  It does not resolve Profile-definition conflicts.

* Prepared control Profiles

A library may publish prepared control Profiles for common policy bundles.

Such a Profile should:

- have one clear semantic purpose;
- expose a stable Profile identity;
- contain POO-native policy objects;
- declare capability requirements without embedding authority;
- remain pure before root instantiation;
- be composable as an ordinary Profile operand; and
- preserve the same advanced POO extension path as any other Profile.

Prepared Profiles are interface conveniences, not new package types or
registries.

The package remains ~wendao-episteme~ where that package owns the published
Profile.  This RFC does not rename it to "wendao" and does not turn a Git
submodule into a Gerbil package.

* Advanced extension path

The advanced path has four semantic steps:

1. select an existing ControlPolicy prototype;
2. compose an admitted POO refinement;
3. instantiate the refined policy object using the verified ~gerbil-poo~
   interface; and
4. contribute that object through a higher-order Profile.

#+begin_src mermaid
flowchart TD
  B["Existing ControlPolicy prototype"] -->|"compose a POO-native evidence or attenuation refinement"| X["Refined policy prototype"]
  X -->|"instantiate through the verified gerbil-poo operation"| O["Immutable ControlPolicy object"]
  O -->|"project through one higher-order Profile"| P["Ordinary Profile operand"]
  P -->|"appears beside all other Profiles"| C["One compose profiles expression"]
  C -->|"one explicit root instantiation freezes the policy collection"| R["Composed system root"]
  R -->|"later runtime admission issues separate capability authority"| E["Evaluator control boundary"]
#+end_src

No step requires a policy registry, keyword clause, nested composition form, or
host conditional.

* Selection without host conditionals

Runtime or deployment variation is represented by higher-order Profile values,
not by placing host conditionals inside ~(compose profiles ...)~.

A research, production, recovery, or observability variant is a Profile
prototype refinement.  The selected higher-order Profile is already a value
when it enters the single composition.

This preserves:

- Scheme value-level abstraction;
- POO prototype extension;
- hygienic module expansion;
- deterministic composition;
- inspectable provenance; and
- the absence of runtime syntax interpretation.

* Macro governance

No new public macro is required for ordinary control-policy composition.

The existing macro budget is sufficient:

- ~user-composition~ projects the module boundary; and
- the project Profile-definition macro may define prepared Profile values.

Any Profile-definition macro must expand to ordinary POO objects and pure
functional composition.  It may not:

- parse an open policy clause language;
- hide raw handlers;
- synthesize a mutable registry;
- reinterpret arbitrary keyword blocks;
- manufacture capabilities;
- embed runtime conditionals; or
- duplicate native POO composition.

Detailed macro rules remain governed by
[[file:44-current-project-programming-style.org][44: current project programming style]].

* Imports and phases

Policy dependencies follow the owning higher-order Profile through its
POO-native ~imports~ object.

~imports~ is a first-class immutable POO object.  It represents a recursive
module graph rather than one Gerbil import form or a flat list of source module
names.

Every higher-order Profile or Module preserves three distinct objects:

- ~imports~ owns recursive module and submodule relationships;
- identity owns stable module and composition identity; and
- capability owns the authority required to admit or activate those
  relationships.

An ~imports~ object may contain submodules whose own ~imports~ objects continue
the graph.  Composition deduplicates nodes by stable identity, intersects
capability requirements, and preserves cycles for the POO Flow fixed-point and
observability boundaries.

Ordinary users do not enumerate the recursive closure.  A prepared Profile
contributes its ~imports~ object together with its Profile semantics.

Gerbil ~import~ or load forms are phase-owned backend projections of an
admitted ~imports~ closure.  They are not the public composition interface and
are not generated by parsing the body of ~user-composition~.

  P -->|"owns stable graph identity"| D["Identity object"]
  P -->|"declares admission requirements without granting authority"| C["Capability object"]
  I -->|"submodules recursively contribute their own imports"| I
  I -->|"fixed-point evaluation deduplicates identities and observes cycles"| F["Admitted imports closure"]
  C -->|"constraints intersect along every dependency edge"| F
  D -->|"anchors nodes, revisions, and receipts"| F
  F -->|"phase-owned backend projection materializes only required boundaries"| G["Gerbil import or load boundary"]

The phases are:

| Phase | Allowed responsibility | Prohibited responsibility |
|-------+------------------------+----------------------------|
| macro expansion | hygienic module and Profile declaration projection | recursive imports evaluation |
| pure Profile composition | prototype composition, imports objects, and immutable policy collection | capability issuance |
| imports closure | recursive identity merge, capability intersection, cycle evidence, and backend projection | user-written import enumeration |
| explicit root instantiation | freeze composed identities and requirements | portable resumption |
| runtime admission | issue and validate evaluator authority | macro expansion |
| condition handling | evaluate admitted policies and apply one decision | Profile recomposition |

No runtime policy lookup performs package discovery or Gerbil package
installation.

* Error surface

User-facing failures name the owning objects and phase.

A Profile admission receipt records:

- composition identity;
- contributing Profile identity;
- policy identity;
- duplicate or refinement conflict;
- required capability class;
- missing or incompatible import;
- failing phase; and
- recommended correction boundary.

A runtime policy receipt remains owned by 45-90.

Errors must not collapse into:

- a generic macro-expansion failure;
- a Scheme stack trace without object identity;
- a silent missing policy;
- an arbitrary last-writer result; or
- a native POO failure fabricated by the control plane.

* Conservative user-surface law

For a composition whose prepared control Profiles admit all completed
evaluation:

- removing the user-interface projection yields the same composed Profile
  value;
- erasing control receipts yields the same native POO result or failure;
- policy observation forces no additional native slot;
- operand permutation does not change policy collection identity; and
- no control object becomes a Profile result.

The full conservative-extension obligations remain owned by
[[file:45-86-poo-conservative-extension-criterion-and-cross-module-obligations.org][45-86]].

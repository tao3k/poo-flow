#+title: Profile Ownership, Naming, Export Identity, and Composition Repository Boundaries
#+startup: overview

* Status

Accepted architecture decision.

This RFC fixes ownership and namespace boundaries for the minimal profile
surface defined by
[[file:45-110-recovery-observability-profile-projection-and-minimal-use-composition-surface.org][45-110]].

* Evidence state

A parser-owned ASP owner search used 45-110 as the exact owner anchor.  It
succeeded and emitted the profile-interface structure.

The receipt confirmed:

- =use-composition= is a thin hygienic top-level binding macro;
- =compose= is a pure function;
- =profiles= is the first-class POO composition strategy;
- =use-module= is a thin module/profile-selection macro;
- composition is flat at the call site;
- higher-order variation belongs in POO-native profile objects and prototype
  extension;
- missing profile-authoring operators must not be invented.

The receipt did not identify implementation owners for the new export-identity
contract.  Those owners remain =MISSING=.

* Scope

This RFC defines:

- repository, package, module, profile, revision, and composition identities;
- profile ownership;
- module-scoped profile naming;
- profile export relations;
- derived-profile ownership;
- source-pin and package-management boundaries;
- application-composition ownership;
- conflict and provenance behavior.

This RFC does not define:

- a global profile registry;
- a global profile namespace;
- package installation semantics;
- a new =gerbil.pkg= format;
- submodule build or publication ownership;
- a compatibility, migration, or deprecation policy;
- a profile-definition macro.

* Central decision

Profile identity is owned by the POO module that exports the profile.

A Git repository, Git submodule, Gerbil package, Gerbil module, POO module,
profile export, profile revision, and final composition binding are different
identities.

None of them is silently derived from another.

* Identity layers

** RepositoryIdentity

=RepositoryIdentity= identifies a source repository and revision.

It answers:

- where source is maintained;
- which source revision is pinned;
- who owns repository-level release and review.

It does not identify a Gerbil package, POO module, or profile export.

** SubmodulePinIdentity

=SubmodulePinIdentity= identifies a parent repository's source pin to a child
repository revision.

It means only:

- the parent records a child source revision;
- the parent can locate that source revision.

It does not mean:

- the child is already a Gerbil package;
- the parent owns child build, test, publication, or profile semantics;
- every child profile is automatically imported or re-exported.

** GerbilPackageIdentity

=GerbilPackageIdentity= is the package-management identity resolved through
=gerbil.pkg=.

It owns:

- package dependency declaration;
- package installation and import availability;
- the durable upstream Git dependency reference.

It does not become a POO profile namespace.

** GerbilModuleIdentity

=GerbilModuleIdentity= identifies Scheme compilation and import units.

It belongs to the Gerbil module graph.  It remains distinct from the POO
semantic module graph.

** PooModuleIdentity

=PooModuleIdentity= identifies a POO-native semantic module object.

It owns:

- semantic imports;
- capabilities;
- responsibilities;
- profile exports;
- typed relations to other POO modules.

One Gerbil package may contain many Gerbil modules and many POO module objects.

** ProfileExportIdentity

=ProfileExportIdentity= identifies a profile export owned by one
=PooModuleIdentity=.

Its identity includes:

- owner module identity;
- local export name;
- export-contract identity.

The local name alone is never globally canonical.

** ProfileRevisionIdentity

=ProfileRevisionIdentity= identifies one immutable revision of an exported
profile value.

The stable export identity and immutable revision identity remain distinct.

A composition receipt records the exact revision it resolved.

** CompositionBindingIdentity

=CompositionBindingIdentity= is the lexical binding created by
=use-composition= in the final composition repository.

It owns the application-specific assembled value.  It does not replace or
rename the identities of its contributing profiles.

* No global profile namespace

There is no global =production=, =research=, =recoverable=, or
=observability= profile.

Those names are meaningful only within:

- the exporting POO module;
- a local Scheme lexical binding;
- a resolved composition receipt that retains canonical provenance.

Two modules may both export a local profile named =production=.  Their canonical
profile identities remain different because their owner module identities
differ.

* Canonical profile identity

The canonical semantic identity is the typed relation:

#+begin_example
ProfileExportIdentity
  = OwnerPooModuleIdentity
  × LocalExportName
  × ExportContractIdentity

ResolvedProfileIdentity
  = ProfileExportIdentity
  × ProfileRevisionIdentity
#+end_example

This is an identity model, not a record DSL or a proposed concrete reader
syntax.

Content equality does not collapse two differently owned exports into one
identity.

* Ownership matrix

| Owner | Owns | Does not own |
|-------+------+--------------|
| upstream =gerbil-poo= | POO primitives, prototype and object operations | POO Flow domain profiles or application policy |
| =poo-flow-core= | generic composition protocols, typed facet prototypes, admission/debug contracts, runtime adapter contracts, canonical neutral values | Wendao domain profiles, application deployment choices, child package release paths |
| =wendao-episteme= | Wendao domain POO modules, domain responsibilities, domain profile exports, its package build/test/publication | POO Flow core protocols, final application's environment policy |
| final application composition repository | deployment-specific profile values, concrete budgets and restrictions, final =use-composition= binding | upstream package or module identity |
| parent Git repository | child source pin and parent integration boundary | child package ownership, child semantic exports, child release process |
| GSLPH | development policy harness and build/test framework behavior | production profile semantics or runtime capability provision |
| Gerbil-Bazel | build-system graph and build execution | POO module/profile semantics |
| Nix integration | environment, dependency, build, and deployment projection | POO semantic identity or profile ownership |

Dependency, build, test, and environment tools do not become profile owners
merely because they consume or verify a package.

* POO Flow core ownership

=poo-flow-core= owns the general semantic vocabulary:

- POO module and profile protocols;
- =ProfileBundle= and composition strategy contracts;
- typed recovery and observability facet prototypes;
- capability attenuation and admission contracts;
- outcome, context, receipt, and effect-intent correspondence;
- canonical typed empty and neutral values;
- bounded adapters to runtime systems.

It does not own:

- =wendao-episteme/production=;
- =wendao-episteme/research=;
- an application's production budget;
- an application's operator or principal policy;
- child package tests or releases.

Core may export a concrete profile only when that profile is truly
domain-independent and its semantics are part of the core contract.  Hidden
deployment defaults cannot be labeled as core protocol values.

* Wendao Episteme ownership

=wendao-episteme= is the package and domain owner for its own semantic modules
and profiles.

It may own profiles such as:

- a Wendao production-domain profile;
- a Wendao research-domain profile;
- domain-specific capability requirements;
- domain-specific imports and responsibilities;
- domain-specific recovery and observability constraints.

Those profile names are scoped to the exporting Wendao POO module.

The POO Flow parent may pin or consume the package.  It does not acquire
ownership of these exports.

* Application composition ownership

The final application repository owns concrete operational choices:

- environment-specific budgets;
- production-versus-research selection;
- local observability retention;
- deployment runtime selection;
- principal and operator restrictions;
- local overlays that combine several upstream modules;
- the final =use-composition= binding.

An application-derived profile receives a new application-owned identity.

It records =derived-from= relations to upstream profile revisions.  It cannot
impersonate or overwrite an upstream profile export.

* Profile export relation

A POO module exports a profile through a native POO relation that preserves:

- owner module identity;
- local export name;
- profile value identity;
- immutable profile revision;
- responsibility projection;
- reachable import requirements;
- capability requirements and attenuation;
- provenance;
- export-contract version.

The export is a POO value relation, not a macro-generated global variable
registry.

* Selection and resolution

The ordinary form:

#+begin_src scheme
(use-module wendao-episteme production)
#+end_src

means:

1. resolve the local module selection to one canonical POO module identity;
2. resolve =production= inside that module's export scope;
3. obtain the immutable profile revision;
4. retain the canonical owner and revision in the =ProfileBundle=;
5. derive reachable imports and responsibilities;
6. emit typed evidence for ambiguity, absence, or conflict.

The local syntax remains concise because canonical identity is retained in the
resolved value, not repeated by the user.

* Export resolution flow

#+begin_src mermaid
flowchart LR
  S["use-module selection"] -->|"module identifier resolves uniquely"| M["Canonical POO module identity"]
  S -->|"module identifier is absent or ambiguous"| E["Typed module-selection conflict"]
  M -->|"local profile name is found in owner scope"| X["Profile export identity"]
  M -->|"local profile name is missing or ambiguous"| N["Typed profile-export conflict"]
  X -->|"immutable export revision resolves"| R["Resolved profile identity"]
  R -->|"responsibilities and imports become reachable"| B["ProfileBundle contribution"]
  R -->|"revision or export contract conflicts"| C["Typed revision conflict"]
  B -->|"pure profiles strategy composes contributions"| P["Resolved composition"]
  P -->|"canonical provenance is retained"| O["Composition binding"]
#+end_src

No resolution edge creates a global profile name.

* Local shorthand and aliases

Scheme lexical bindings may provide local shorthand for profile values.

Local shorthand:

- does not alter canonical profile identity;
- does not remove owner provenance;
- does not create a new export;
- does not make the shorthand globally resolvable.

This RFC introduces no new =as= clause or alias macro.  If a future hygienic
alias form is necessary, it requires its own bounded macro contract.

* Multiple modules with the same local name

The following selections are not semantically ambiguous because each profile
name is scoped by its module selection:

#+begin_src scheme
(use-composition combined-system
  (compose profiles
    (use-module wendao-episteme production)
    (use-module agent production)
    application-production))
#+end_src

The two =production= exports remain distinct canonical contributions.

If an unscoped lexical binding makes them indistinguishable, composition fails
closed rather than choosing by source order.

* Derived profile identity

A derived profile has:

- a new owner;
- a new export identity when exported;
- a new immutable revision;
- explicit =derived-from= provenance;
- explicit contributed and withdrawn relations;
- no authority to rewrite its ancestors.

Prototype extension preserves ancestry evidence but never preserves ownership
by pretending the derived value is the upstream export.

* Revision and upgrade behavior

The architecture is new.  This RFC introduces no compatibility migration or
deprecation strategy.

A changed profile value produces a new immutable revision.

A live upgrade:

- resolves the new revision explicitly;
- validates its graph-wide requirements;
- creates a new composition result;
- preserves the previous composition and receipts as immutable history;
- does not mutate a prior revision in place.

* Package and profile separation

=gerbil.pkg= declares package dependencies.  It does not declare profile
selection.

The durable Git dependency identity recorded for a Gerbil package is distinct
from:

- local checkout paths;
- Git submodule pins;
- POO module identities;
- profile export identities;
- application composition bindings.

In particular, a local =.data/= checkout path is evidence location only and
cannot become a durable profile or package identity.

* Submodule boundary

Placing =wendao-episteme= below a parent =packages/= directory establishes a
source-tree relationship.

It does not:

- convert the repository into a Gerbil package automatically;
- make parent tests authoritative for the child;
- make GSLPH a production dependency;
- make Gerbil-Bazel a POO semantic layer;
- export every Wendao profile into the parent;
- grant the parent profile ownership.

Package, build, test, and semantic integration remain explicit, separate
contracts.

* Ownership graph

#+begin_src mermaid
flowchart TD
  GP["upstream gerbil-poo"] -->|"provides native POO primitives and prototype operations"| PC["poo-flow-core"]
  PC -->|"owns generic module, profile, admission, and runtime contracts"| APP["Application composition"]
  WE["wendao-episteme"] -->|"exports Wendao-owned POO modules and profile revisions"| APP
  AR["Application repository"] -->|"owns deployment profiles and final use-composition binding"| APP
  SUB["Parent Git submodule pin"] -->|"pins child source revision only"| WE
  GPKG["gerbil.pkg"] -->|"resolves package dependency identity only"| WE
  GSLPH["GSLPH dev dependency"] -.->|"tests policy and build behavior without providing runtime semantics"| WE
  GB["Gerbil-Bazel"] -.->|"builds declared targets without owning POO exports"| WE
  NIX["Nix integration"] -.->|"projects environment and deployment without becoming semantic owner"| APP
  APP -->|"retains every canonical owner and revision"| RC["Resolved composition receipt"]
#+end_src

Every edge states the ownership it grants or explicitly does not grant.

* Conflict behavior

Resolution fails closed on:

- two different owner modules claiming the same canonical module identity;
- two different profile values claiming the same export revision identity;
- an export without owner provenance;
- an application profile impersonating an upstream export;
- a package name treated as a global profile namespace;
- a submodule pin treated as semantic export authority;
- source order used to resolve an identity conflict;
- a local alias that discards canonical provenance.

Identical content under different owners remains different evidence, not a
deduplication opportunity that erases ownership.

* Explanation surface

The POO-native explanation interface can answer:

- which repository and package supplied source;
- which POO module owns the selected profile;
- which local name resolved;
- which immutable revision was composed;
- which application profile derived from it;
- which responsibility made an import reachable;
- why a name or revision conflicted;
- which build or test dependency was intentionally excluded from semantics.

Explanation does not rewrite ownership.

* Public interface boundary

Ordinary users keep the concise interface:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

Profile and framework authors use verified native =gerbil-poo= objects,
prototype operations, and typed relations.

No global registry, raw manifest DSL, profile-definition macro, or package
keyword layer is introduced.

* Invariants

- [X] Repository, submodule, package, Gerbil module, POO module, profile, and
  composition identities remain distinct.
- [X] A profile export is owned by one POO module.
- [X] Local profile names are module-scoped.
- [X] There is no global profile namespace.
- [X] Stable export identity and immutable revision identity remain distinct.
- [X] =poo-flow-core= owns generic contracts, not Wendao domain profiles.
- [X] =wendao-episteme= owns its domain profiles and package lifecycle.
- [X] The application repository owns deployment-specific composition.
- [X] A derived profile receives a new owner identity.
- [X] Source pins and package dependencies do not grant semantic ownership.
- [X] GSLPH and build systems do not provide production profile semantics.
- [X] Canonical provenance survives local shorthand and composition.
- [X] No compatibility migration or deprecation policy is introduced.

* Conformance checklist

- [ ] ASP emits parser-owned implementation owners for profile export and
  resolution.
- [ ] Every module export carries canonical owner provenance.
- [ ] Every resolved profile records an immutable revision identity.
- [ ] =use-module= resolves names only within the selected module scope.
- [ ] Two modules may safely export the same local profile name.
- [ ] Canonical identity conflicts fail closed without source-order override.
- [ ] Application-derived profiles receive new owner and revision identities.
- [ ] Package and submodule receipts remain separate from semantic receipts.
- [ ] Parent integration does not claim child build, test, or publication
  ownership.
- [ ] GSLPH, Gerbil-Bazel, and Nix adapters remain outside POO profile ownership.
- [ ] Mermaid edge labels retain explicit ownership meaning.
- [ ] No global profile registry or new profile macro appears.

* Successor contract

The separation between semantic composition receipts, =gerbil.pkg=, source
pins, build/test evidence, and runtime receipts is fixed by
[[file:45-114-resolved-composition-receipt-and-package-source-build-runtime-evidence-separation.org][45-114]].

* Implementation ownership

This section is normative and supersedes earlier audit statements that
implementation ownership was =MISSING=. Unchecked items below concern
implementation completion, not owner selection.

- [X] =poo-flow-core= owns generic module-scoped profile identity, export
  relations, conflict provenance, and composition identity contracts.
- [X] =wendao-episteme= owns its domain Module and Profile identities and their
  exports.
- [X] The final application owns the final composition identity and selected
  deployment profiles.

#+begin_src mermaid
flowchart LR
  P["upstream gerbil-poo"] -->|"owns native POO operators"| C["poo-flow-core"]
  C -->|"defines generic Module, Profile, identity, and composition contracts"| W["wendao-episteme"]
  W -->|"exports domain Modules and Profiles"| A["final application"]
  C -->|"projects admitted runtime intents and semantic receipts"| R["runtime/deployment adapters"]
  A -->|"selects Profiles and authorizes deployment policy"| R
  R -->|"returns execution and publication receipts"| A
#+end_src

- [ ] Concrete generic identity and export-relation support remain
  implementation work owned by =poo-flow-core=.

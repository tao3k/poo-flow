#+title: Profile Variant Candidate Publication, Generation Pinning, and Rollback Contract
#+startup: overview

* Status

Accepted architecture decision.

This RFC continues the immutable application profile-family contract defined by
[[file:45-116-application-profile-family-prototype-derivation-and-flat-environment-selection.org][45-116]].

* Evidence state

Two parser-owned ASP owner searches succeeded.

The 45-114 receipt confirmed:

- ordinary composition receives one already selected immutable profile value;
- application variants derive from an immutable POO prototype;
- runtime profile switching without recomposition is excluded;
- implementation ownership remains =MISSING=.

The 45-59 receipt confirmed:

- generations are immutable and content-addressed;
- active head is a versioned external selection resource;
- active-head change requires a pure proposal, authorized intent, and
  conditional runtime commit;
- concurrent publication cannot silently overwrite;
- reversion is a new head transition;
- reversion does not erase generation or effect history;

* Scope

This RFC defines:

- composition candidates;
- candidate validation;
- generation materialization;
- active-head publication;
- concurrent head transitions;
- generation pinning for contexts and continuations;
- in-flight work during publication;
- rollback and reversion;
- cohort and multi-scope behavior;
- quiescence and retirement handoff.

This RFC does not define:

- compatibility migration;
- deprecation policy;
- in-place profile mutation;
- an imperative profile-switch API;
- a second active-head protocol;
- a public publication macro;
- deletion of prior generation history.

* Central decision

Changing from one profile variant to another is publication of a new immutable
resolved composition.

It is not:

- mutation of a running profile object;
- compatibility migration;
- replacement of prior receipts;
- a host-language assignment;
- an ambient environment switch.

The normative flow is:

#+begin_example
DerivedProfile
  -> ResolvedCompositionCandidate
  -> ValidatedCandidate
  -> AuthorizedPublicationIntent
  -> ConditionalActiveHeadCommit
  -> HeadTransitionReceipt
#+end_example

* Identity model

The publication protocol distinguishes:

- =ResolvedCompositionIdentity=: immutable semantic composition content;
- =CompositionReceiptIdentity=: evidence for pure resolution;
- =CandidateIdentity=: one proposed publication of that composition;
- =GenerationIdentity=: immutable materialized runtime generation;
- =HeadScopeIdentity=: the external selection scope;
- =ObservedHeadRevision=: the version observed by the proposal;
- =HeadTransitionIdentity=: one conditional head update;
- =ActiveHeadRevision=: the new version after successful commit;
- =ValidationIdentity=: validation evidence bound to candidate and policy;
- =PublicationCapabilityIdentity=: authority to request the mutation.

Composition identity, generation identity, and active-head revision remain
different.

* ResolvedCompositionCandidate

=ResolvedCompositionCandidate= is a pure POO object.

It carries:

- resolved composition and receipt identities;
- selected application profile variant;
- selected upstream module/profile revisions;
- target head scope;
- expected current head and revision;
- validation requirements;
- rollout or cohort policy when present;
- required publication authority shape;
- runtime materialization requirements;
- candidate provenance.

It contains no live publication capability, mutable active-head handle, secret,
or runtime continuation.

* Candidate creation

Candidate creation is pure.

It cannot:

- observe current head implicitly;
- mutate the head;
- materialize runtime resources;
- cancel in-flight demands;
- grant publication authority;
- select a variant from ambient process state.

The observed head and revision enter as explicit observation evidence.

* Candidate validation

Validation proves only that the candidate is eligible to be proposed.

It checks:

- composition receipt identity;
- profile and module revisions;
- typed relation conflicts;
- responsibility and import reachability;
- capability non-escalation;
- runtime adapter requirements;
- cache and publication isolation;
- recovery and continuation constraints;
- family-wide variant invariants;
- target head scope;
- expected-head precondition shape.

Validation does not publish.

Build and GSLPH evidence may be referenced when a publication policy requires
them.  Those receipts do not become semantic facets or publication authority.

* Generation materialization

A validated candidate may be materialized as an immutable runtime generation.

Materialization binds:

- resolved composition identity;
- runtime adapter revisions;
- evaluator and policy revisions;
- runtime resource identities;
- generation-local cache namespaces;
- generation-local continuation registry scope;
- materialization receipts.

Materialization alone does not make the generation active.

An identical already-materialized generation may be reused when its full
content identity and runtime qualifications match.

* Active-head publication

The active head is an external versioned resource.

Publication requires:

1. pure candidate and validation evidence;
2. fresh principal and publication capability admission;
3. explicit target head scope;
4. explicit expected head and revision;
5. stabilized publication effect intent;
6. conditional runtime commit;
7. immutable head-transition receipt.

The commit succeeds only if the external head still matches the expected
revision.

* Publication flow

#+begin_src mermaid
flowchart LR
  P["Selected immutable profile variant"] -->|"pure compose resolves semantic graph"| C["ResolvedCompositionCandidate"]
  C -->|"typed validation and external policy gates succeed"| V["Validated candidate"]
  C -->|"semantic conflict or required evidence fails"| X["Typed candidate rejection"]
  V -->|"runtime resources materialize without activation"| G["Immutable generation"]
  G -->|"fresh publication authority and expected-head precondition bind"| I["Authorized publication intent"]
  I -->|"external head still matches observed revision"| H["Conditional head commit"]
  I -->|"head revision changed or scope mismatched"| S["Stale publication conflict"]
  H -->|"new versioned selection is recorded"| T["HeadTransitionReceipt"]
  T -->|"new admissions observe selected generation"| A["New generation active for target scope"]
  X -->|"no active-head mutation occurs"| E["Explanation evidence"]
  S -->|"candidate may be re-observed and reproposed explicitly"| E
#+end_src

No validation edge authorizes publication.

* Concurrency

Concurrent publication uses compare-and-swap semantics over the external head
revision.

When two candidates observe the same head:

- both may validate;
- both may materialize immutable generations;
- only a commit whose expected head still matches may succeed;
- a losing commit returns typed stale-head evidence;
- the loser cannot silently overwrite the winner;
- retrying publication requires a new observation and proposal.

Source order, arrival time before commit, or cached head data does not grant
priority.

* Concurrent publication sequence

#+begin_src mermaid
sequenceDiagram
  participant A as Candidate A coordinator
  participant B as Candidate B coordinator
  participant H as Versioned active head

  A->>H: observe head revision r0
  B->>H: observe head revision r0
  A->>A: validate and authorize candidate A
  B->>B: validate and authorize candidate B
  A->>H: conditional commit expected r0
  H-->>A: commit succeeds and head becomes r1
  B->>H: conditional commit expected r0
  H-->>B: stale-head conflict with observed r1
  B->>B: require explicit re-observation and new proposal
#+end_src

The failed commit produces no hidden fallback publication.

* Active head is not active evidence closure

The active head points to one selected immutable generation for one explicit
scope.

It does not:

- contain every evidence receipt;
- become a package lock;
- mutate the composition receipt;
- own build or test evidence;
- maintain an active evidence closure.

The head transition references separately owned evidence by identity.

* Generation pinning

Every admitted =EvaluationContext= records:

- generation identity;
- head scope;
- head-transition receipt observed at admission;
- composition receipt identity;
- policy and evaluator revisions.

Once admitted, the context remains pinned to that generation.

An active-head transition does not rewrite:

- existing contexts;
- running evaluations;
- child-demand receipts;
- live continuations;
- pending cleanup;
- runtime outcomes.

* Child demands

Child demands inherit the parent's generation by default.

A child cannot silently observe a newer active head.

Cross-generation work requires:

- an explicit new root demand;
- a fresh context;
- fresh admission;
- a typed relation to the originating outcome when relevant.

This prevents one evaluation tree from mixing profile semantics accidentally.

* Recovery and generation

** Live resume

A live continuation resumes only under its origin generation, runtime epoch,
context fence, and continuation fence.

A new active head cannot adopt or invoke an old generation's continuation.

** Retry

A retry of the same semantic demand targets the origin generation.

Re-executing under a different generation is a new demand or =supersedes=
relation, not the same retry.

** Replay

Replay records and targets the original generation semantics unless an explicit
counterfactual proposal requests a different generation.

Counterfactual execution remains isolated and does not publish automatically.

* In-flight work

After a successful head transition:

- new admissions for the target scope select the new generation;
- already admitted work continues under its pinned generation;
- existing live continuations remain origin-generation resources;
- existing cleanup and reconciliation finish under their origin contracts;
- cancellation requires explicit current authority and policy;
- prior outcomes remain valid immutable evidence.

Publication does not imply mass cancellation or migration.

* Quiescence

A generation becomes quiescent only when it has no:

- admitted running contexts;
- child evaluations;
- live or claimed continuations;
- pending effect graphs;
- incomplete cleanup or reconciliation;
- required runtime cache references;
- retained recovery obligations.

Quiescence is represented by an explicit receipt.

Active-head replacement alone does not prove quiescence.

* Retirement and reclamation

An inactive generation may be retired only through the existing generation
retirement and reclamation contract.

Retirement:

- requires quiescence evidence;
- preserves semantic and publication history;
- invalidates new admission to the retired generation unless explicitly
  authorized for replay or recovery;
- releases runtime materialization resources according to policy;
- does not delete immutable composition or outcome receipts.

* Rollback

Rollback is a new conditional head transition.

It:

- observes the current head and revision;
- selects a previously validated immutable generation or rematerializes an
  equivalent qualified generation;
- obtains fresh publication authority;
- commits with an expected-head precondition;
- emits a new =HeadTransitionReceipt=;
- preserves the failed or superseded generation and all effect history.

Rollback does not mutate history to pretend the newer publication never
occurred.

* Rollback identity

Rollback may point the active head back to an existing immutable
=GenerationIdentity=.

The target generation identity may therefore be old, while:

- the rollback candidate identity is new;
- the publication authorization is new;
- the head-transition identity is new;
- the active-head revision is new.

This distinction prevents head history from collapsing into generation content
identity.

* Rollback flow

#+begin_src mermaid
flowchart LR
  F["Current head selects generation B"] -->|"operator observes failure evidence and current head revision"| P["Rollback candidate targets generation A"]
  P -->|"generation A remains qualified or is safely rematerialized"| V["Validated rollback candidate"]
  P -->|"generation A is unavailable or no longer qualified"| D["Typed rollback denial"]
  V -->|"fresh publication capability is admitted"| I["Authorized rollback intent"]
  I -->|"expected head still selects generation B"| C["Conditional reversion commit"]
  I -->|"head changed concurrently"| X["Stale rollback conflict"]
  C -->|"new transition selects existing generation A"| H["New active-head revision"]
  H -->|"history retains A, B, and both transitions"| R["Append-only publication history"]
#+end_src

Rollback is not deletion.

* Cohort rollout

When rollout is cohort-scoped:

- each cohort head is an explicit scoped resource;
- each transition records its target cohort;
- one cohort's head cannot authorize another cohort's mutation;
- admission records the exact cohort and generation;
- rollout policy determines advancement or reversion;
- partial rollout is explicit rather than an accidental partial commit.

There is no implicit global head.

* Multi-scope publication

When a publication requires atomic change across several scopes, it uses the
existing multi-scope publication-barrier contract.

The candidate declares:

- all target head scopes;
- all expected revisions;
- atomicity policy;
- failure and compensation behavior.

Independent single-scope commits cannot be described afterward as an atomic
multi-scope publication.

* Cache behavior

Semantic composition caches remain keyed by immutable composition inputs.

Runtime caches are generation-scoped by default.

Cross-generation cache reuse requires explicit proof of:

- identical relevant semantic content;
- compatible evaluator and policy revisions;
- compatible observation and capability boundaries;
- compatible redaction and retention;
- absence of generation-local mutable state.

Publication itself does not promote cache entries.

Rollback does not automatically revive stale runtime cache entries.

* Secret and deployment input behavior

Generation publication references deployment and secret requirements, not
secret values.

New admissions resolve fresh runtime capabilities under the selected
generation.

An in-flight context retains its admitted handles and origin-generation
constraints until expiry, revocation, or terminal closure.

Secret rotation and active-head publication remain separate events.

* User interface boundary

The user defines immutable composition values:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

Publication consumes the bound composition value through POO-native candidate
and intent objects.

The ordinary composition form contains no:

- publication clause;
- active-head mutation;
- rollback clause;
- cohort clause;
- runtime switch callback.

No new public macro is introduced.

* Failure behavior

The system fails closed on:

- publication without a validated candidate;
- observation or cache state treated as publication authority;
- expected-head mismatch;
- wrong head scope;
- concurrent silent overwrite;
- in-place mutation of an active profile or generation;
- existing context rebound to a new generation;
- live continuation invoked under a different generation;
- same-demand retry silently moved to a new generation;
- rollback erasing generation or effect history;
- active-head replacement treated as quiescence;
- inactive generation reclaimed with live obligations;
- independent scope commits mislabeled as atomic publication.

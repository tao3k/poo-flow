#+title: Higher-Order Dispatch Evaluation POO Object and Policy-Prototype Algebra
#+author: POO Flow
#+language: en

* Status

This RFC is an accepted semantic contract.

It defines one internal higher-order =DispatchEvaluation= POO object.  It does
not introduce separate record APIs for demand, candidates, traces, or
conditions, add public syntax, or admit an implementation.

Implementation remains blocked until every consumed upstream operation path is
=ADMITTED= by RFC 45-120.

* Scope

This RFC owns:

- the required semantic slots of =DispatchEvaluation=;
- its derived dispatch responsibilities;
- policy-prototype composition;
- immutability and lazy native-slot memoization boundaries;
- inherited computation and C3 policy ordering;
- cycle, budget, cache, observability, redaction, and effect projection;
- the relation between =DispatchEvaluation= and Module-derived
  responsibilities.

It does not own:

- upstream POO object, slot, prototype, dispatch, or precedence mechanics;
- a family of project record types;
- contribution admission priority;
- runtime effects or continuation invocation;
- application deployment policy;
- an ordinary user macro or dispatch DSL.

* Central decision

=DispatchEvaluation= is one native higher-order POO value with three required
semantic slots:

- =receiver=;
- =responsibility=;
- =context=.

All other dispatch behavior is derived through native POO slot computation,
prototype extension, policy mixing, generic dispatch, C3 precedence, and
inherited computation.

The object is higher-order because its derived responsibilities select and
invoke behavior supplied by other POO values while preserving explicit context,
authority, lineage, and explanation.

* Required slot: receiver

=receiver= is one native upstream POO value.

It is not:

- a receiver identifier detached from the value;
- a raw alist, hash, record DSL, or hidden registry entry;
- a package, source checkout, process, or runtime handle.

The receiver's stable semantic identity participates in candidate identity,
cycle identity, cache identity, and explanation.  Dispatch does not mutate the
receiver to store project-owned state.

* Required slot: responsibility

=responsibility= is one semantic responsibility identity.

It may denote:

- a required Module slot;
- a Module-derived responsibility;
- an admitted generic operation;
- a domain behavior supplied by a Module or Profile prototype.

It is not a stringly typed command, clause, callback, or public method-name DSL.

The same responsibility identity must be used by candidate enumeration,
precedence, cache, outcome, and explanation.

* Required slot: context

=context= is an explicit immutable evaluation-context value or an admitted
narrowed projection.

It contains:

- capability envelope;
- execution lineage;
- active receiver/responsibility path;
- evaluation and observation budgets;
- cache namespace;
- redaction limits;
- fixed-point and suspension context.

Prototype extension and =super= may narrow this context.  They cannot widen its
capabilities, budgets, or observation authority.

Runtime handles, secret values, ambient environment state, wall-clock time, and
mutable process identity are excluded from the pure context.

* Derived responsibility algebra

The internal semantic responsibilities are:

| Responsibility | Derivation | Semantic role |
|----------------+------------+---------------|
| =sources= | receiver, responsibility, and policy graph | Enumerate admitted instance, type, and prototype sources |
| =candidates= | sources and context | Produce provider identities and structured rejection reasons |
| =precedence= | candidates and finalized prototype graph | Preserve upstream C3 dispatch order |
| =selected= | precedence and applicability | Select one provider without contribution-priority substitution |
| =next= | selected provider and inherited position | Continue =super= or next-method within one dispatch chain |
| =outcome= | selected evaluation, context, and effect boundary | Return value, condition, suspended, denied, or cancelled result |
| =explanation= | all preceding responsibilities | Project budgeted and redacted semantic evidence |

These are native POO-derived responsibilities.  They are not seven independent
record APIs and are not ordinary user-facing slot syntax.

* Base prototype

The base =DispatchEvaluation= prototype defines:

- required-slot validation;
- the default source-enumeration boundary;
- structured no-applicable-method projection;
- default evaluation-context narrowing;
- the distinction between semantic outcome and runtime effect intent;
- the minimum explanation relation.

It does not define domain providers, application contribution policy, runtime
effects, or alternative precedence.

The intended upstream authoring path uses native =.def= or =.o=.  Exact project
adapter admission remains governed by RFC 45-120.

* Policy-prototype algebra

Pure policies extend or mix into the base prototype.

The admitted policy roles are:

- capability satisfaction and attenuation;
- cycle classification and fixed-point suspension;
- evaluation and observation budgets;
- cache admission and invalidation;
- observability and redaction;
- structured condition projection;
- effect-intent projection.

A policy prototype:

- is a native POO value;
- depends only on explicit semantic inputs;
- preserves or narrows context authority;
- may use inherited computation to refine a responsibility;
- returns a semantic value or structured condition;
- never executes a runtime effect.

Policy conflicts are resolved before dispatch by contribution admission.  The
finalized policy graph is then ordered by upstream C3 precedence.

* Contribution admission and C3 boundary

Contribution priority determines which policy prototypes enter the finalized
graph and how conflicting contributions are admitted.

After finalization:

- numeric priority no longer participates;
- C3 precedence is authoritative;
- a policy cannot skip a provider by comparing priority;
- =super= follows the established inherited-computation chain;
- invalid linearization fails before evaluation.

This prevents Nickel-inspired contribution priority from becoming a second
method-dispatch algorithm.

* Native operation correspondence

The semantics-proven upstream families are:

- authoring: =.def= and =.o=;
- derivation and policy composition: =.extend=, =.mix=, and =.+=;
- responsibility projection: =.ref=, =.get=, and =.@=;
- callable and generic dispatch: =.call= and =.defgeneric=;
- inherited computation: =object/slot-spec= and computed-slot behavior;
- missing-method condition: =NoApplicableMethod=;
- precedence: =compute-precedence-list!= using upstream C3 behavior.

No POO Flow adapter is admitted merely because the upstream operation exists.

* Immutability boundary

An admitted =DispatchEvaluation= instance is immutable at the project semantic
layer.

The following upstream mutation and lifecycle operations are not admitted for
ordinary evaluation:

- =.put!= and =.set!=;
- =.putslot!= and =.setslot!=;
- =.putdefault!= and =.def!=;
- =uninstantiate-object!=.

Changing receiver, responsibility, context, policy graph, capability envelope,
redaction, or prototype generation creates a new semantic evaluation identity.

Prototype extension creates a new POO value.  It does not mutate an active
evaluation in place.

* Lazy-slot and cache boundary

Upstream object slots may compute lazily and memoize within one object
instance.  POO Flow admits that behavior only when:

- the instance is immutable at the semantic layer;
- required inputs are explicit;
- the same instance is never reused with a different context;
- cycle and budget state are explicit;
- cached outcomes preserve explanation and redaction boundaries.

Native slot memoization is local to one =DispatchEvaluation= instance.
Cross-evaluation caching is a separate POO Flow semantic cache governed by the
cache identity defined in RFC 45-122.

A cached value cannot erase:

- the selected provider;
- inherited-continuation position;
- capability attenuation;
- budget reconciliation;
- cycle classification;
- redaction decisions.

* Inherited-computation boundary

A policy may refine a derived responsibility by calling its inherited
computation.

The inherited continuation:

- remains within the current receiver, responsibility, context, and C3 path;
- advances to the next applicable provider;
- cannot restart or fork runtime execution;
- cannot widen authority;
- cannot escape as a raw continuation value.

It is not a coordinator resumption and does not use recovery authorization.

* Fixed-point and cycle behavior

Recursive Module imports may create nested =DispatchEvaluation= values.

The active evaluation path is identified by at least:

- receiver semantic identity;
- responsibility identity;
- prototype generation;
- inherited-continuation position;
- narrowed context and capability identity.

Re-entry may produce:

- a cache hit;
- a productive dependency;
- a suspended dependency;
- an unproductive cycle;
- a budget-exhausted outcome.

The policy graph classifies the re-entry.  It does not recurse silently or
delegate cycle handling to the host stack.

* Outcome and effect projection

=outcome= is a semantic result.

Pure policies may return:

- value;
- structured condition;
- suspended;
- denied;
- cancelled.

If the selected responsibility requires an effect, =outcome= contains an
admitted =EffectIntent= or =RecoveryExecutionIntent= projection.  Runtime
execution belongs to a runtime/deployment adapter.

The dispatch explanation, semantic composition receipt, and runtime execution
receipt remain distinct.

* Explanation boundary

=explanation= is a derived semantic responsibility, not a log stream.

It is demand-driven, budgeted, capability-scoped, and redacted.  It may project:

- required input identities;
- policy prototype identities;
- source and candidate identities;
- rejection reasons;
- precedence and selected-provider paths;
- inherited-computation steps;
- cache and cycle decisions;
- budget consumption;
- condition or outcome identity.

It does not expose secret values, raw continuation objects, runtime handles, or
unbounded global trace data.

* Module integration

One =DispatchEvaluation= may evaluate a Module-derived responsibility such as:

- recursive import reachability;
- capability closure;
- ProfileBundle projection;
- conflict explanation;
- provenance;
- semantic composition receipt.

The Module remains the receiver or supplies the receiver.  The derived
responsibility is not copied into required Module storage.

Domain behavior owned by =wendao-episteme= may extend admitted responsibilities
through native POO prototypes.  It cannot redefine the generic dispatch engine.

* Public-interface boundary

This RFC adds no public syntax.

The ordinary interface remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

Advanced dispatch extension uses native POO objects, prototypes, and admitted
generic operations.

* Ownership

- Upstream =gerbil-poo= owns object, slot, generic, inherited-computation, and
  C3 dispatch mechanics.
- =poo-flow-core= owns the =DispatchEvaluation= semantic contract, context,
  policies, conditions, cache identity, outcomes, and explanations.
- =wendao-episteme= owns domain behavior supplied through admitted prototypes.
- The final application owns contribution admission and selected Profiles.
- Runtime/deployment adapters own admitted effect execution.
- GSLPH remains a development policy harness and building/testing dependency.

* Admission checklist

** Object algebra

- [X] Freeze one higher-order =DispatchEvaluation= POO object.
- [X] Freeze =receiver=, =responsibility=, and =context= as its only required
  semantic slots.
- [X] Keep sources, candidates, precedence, selected provider, next-method,
  outcome, and explanation derived.
- [X] Reject separate ordinary record APIs for derived responsibilities.
- [X] Reject public dispatch syntax.

** Policy prototypes

- [X] Freeze pure capability, cycle/budget, cache, observability/redaction,
  condition, and effect-projection policy roles.
- [X] Require policy prototypes to preserve or narrow authority.
- [X] Separate contribution admission from C3 dispatch.
- [X] Preserve upstream inherited-computation behavior.
- [ ] Define exact internal prototype identities only after adapter admission.

** Immutability and cache

- [X] Reject upstream mutation operations for ordinary active evaluation.
- [X] Require new semantic identity when receiver, responsibility, context, or
  policy graph changes.
- [X] Separate local native-slot memoization from cross-evaluation caching.
- [ ] Prove lazy-slot memoization preserves outcome and explanation semantics.
- [ ] Prove cache invalidation across prototype-generation changes.

** Fixed point and effects

- [X] Require explicit cycle identity, budgets, capability, and redaction.
- [X] Separate inherited continuation from coordinator resumption.
- [X] Require effect projection instead of effect execution.
- [ ] Prove productive dependency and suspension behavior.
- [ ] Prove unproductive-cycle and budget-exhaustion behavior.
- [ ] Prove EffectIntent handoff and receipt separation.

** Implementation admission

- [ ] Admit every consumed upstream operation path in RFC 45-120.
- [ ] Implement the base prototype as a native POO value.
- [ ] Implement each policy as a native POO prototype.
- [ ] Map the first Module-derived responsibility.
- [ ] Run focused GSLPH development checks without adding a product dependency.

* Rejected alternatives

- Separate Demand, Candidate, Trace, and Condition record APIs.
- A raw alist or hash representation of dispatch evaluation.
- Mutable active dispatch evaluation.
- Reusing one evaluation instance with a different context.
- A policy registry outside the prototype graph.
- Policy priority dynamically overriding C3.
- Hidden host recursion for fixed-point behavior.
- Performing effects inside a policy slot.
- Escaping inherited computation as a recovery continuation.
- A public dispatch macro or clause language.

* Successor contract

The first concrete derived-responsibility contract should be recursive Module
import reachability.

It must exercise:

- to-B-to-C Module traversal;
- lazy dispatch;
- capability attenuation;
- productive and unproductive cycles;
- budgets and suspension;
- cache identity;
- provenance and explanation;
- ProfileBundle reachability without package dependency semantics.

It must remain an RFC semantic contract until its upstream adapter paths are
=ADMITTED=.

* Root-cause boundary

The gerbil-bazel RFC 0008 audit rejected two speculative library changes:

1. Apple Clang was approximately 95.7 percent slower than the producer
   compatible GCC 16 compiler for the same generated object input.
2. Twelve concurrent GCC object jobs completed in 11,466 ms with a peak RSS of
   4,614,832,128 bytes, so a smaller fixed macOS core cap is not justified.

A native =gxc= probe over the same sixteen Gerbil modules crossed the
90-second guard without Bazel staging or =build.ss= orchestration.  The
remaining owner is the gerbil-poo frontend workload: module dependency depth,
macro expansion, and cross-module optimization.

* Promotion decision

gerbil-bazel PR 29 must remain draft.  The POO Flow pin must not be described
as a performance improvement or promoted as a stable downstream convergence
revision while the optimized gerbil-poo package gate and the full POO Flow
compile gate fail.

The adaptive resource guard itself remains valid:

- it used Gerbil =__available-cores= as the CPU-capacity source;
- it admitted twelve cores within the observed memory budget;
- it did not apply the runnable-pressure diagnostic as a hard cap;
- it emitted complete typed receipts for both packages.

The next implementation phase belongs to the POO Flow and GSLPH Scheme build
owners.  gerbil-bazel must remain the reusable toolchain and project-action
library.  It must not compensate by parsing =build.ss=, inventing a second
package manager, or deriving a private POO-specific module graph.

* Upstream-compatible ownership boundary

Gerbil upstream already provides parallel workers in =std/make=.  Its compiler
driver also deliberately protects =optimize!= with a process-global driver
mutex, and =std/make= executes pending Gambit/C jobs after the module build
barrier.  The observed frontend serialization is therefore an upstream
execution property, not evidence that Bazel failed to pass the host CPU count.

GSLPH currently computes dependency topology layers, but
=build-requests-run!= executes package stages sequentially and each POO runtime
layer remains inside the same gxi process.  The next design must preserve the
upstream compiler and move parallelism to explicit project-owned component
boundaries:

The project or GSLPH must declare the component graph.  gerbil-bazel may
execute those declared Gerbil projects and cache their outputs, but it must not
parse Scheme source or infer POO domain ownership.  Release builds must keep
Gerbil optimization enabled, all worker limits must remain host-derived, and
promotion requires both green unit tests and end-to-end performance receipts.

* Source-ownership parity correction

The local dynamic source scan initially reported 382 runtime specs while the
hermetic Bazel receipt reported 381.  This was not a missing Bazel source.  The
module =src/contract/dependency-source-identity.ss= is intentionally owned by
the independent =dependency_source_contract_sources= package and excluded from
=scheme_runtime_sources=.  The local Scheme predicate did not express that
ownership boundary and therefore pulled the module back into the monolithic
runtime spec.

=+poo-flow-project-runtime-module-owners+= now declares both separately owned
modules as a pure module-to-owner manifest.  The runtime predicate projects
from that manifest instead of maintaining an unrelated negative list:

- =contract/dependency-source-identity.ss=, compiled by the dependency-source
  contract package;
- =modules/nono-sandbox/_nono.ss=, compiled by the C FFI stage.

The focused =cli-support-project-building-test.ss= gate passed with all checks.
The native topology projection now agrees with the hermetic receipt at exactly
381 runtime specs.

* Persistent optimized worker model

Starting one gxi process per module is rejected.  A representative import of
the GSLPH building surface costs approximately 3,715 ms before useful module
work begins.  Repeating that startup for hundreds of modules would dominate
the compile.

The required execution model is a fixed, host-derived pool of long-lived gxi
workers:

Each worker owns a separate Gerbil compiler process and therefore a separate
driver mutex.  Modules in one dependency layer may run concurrently, while the
next layer cannot start until the current layer has materialized its library
and =ssxi= artifacts.  The parent Scheme guard must monitor the complete worker
process tree and may reduce active workers from current host observations; the
worker count must never be hard-coded.

For the observed 381-module graph and twelve available workers, the 39 layers
reduce to 57 ideal equal-cost worker waves.  Using the observed runtime-stage
average of 772.3 ms per module gives a theoretical, startup-free lower bound of
approximately 44,020 ms, or 6.68 times faster than the 294,240 ms runtime
stage.  This is a feasibility bound, not a performance claim: real promotion
requires measured receipts that include skew, worker startup, artifact
barriers, RSS, and failure cancellation.

* Topology-batching correction and repeatable cold-audit receipt

The first persistent-worker candidate did not preserve the existing topology
policy boundary.  The POO Flow guard selected =topology=, not
=adaptive-window=, but =package-source-stage-request-specs/default= returned
each topology group as a separate upstream request.  The 381-module runtime
stage was therefore materialized as 40 runtime =std/make= stages, with three
additional FFI and user-interface stages.  The failure was not caused by the
persistent worker pool: every affected receipt reported
=adaptive-execution=false=.

GSLPH revision =a0ba60a15dd05d95ea89c0506f530f426d3dca1e= restores
=package-source-stage-topology-request-specs= as the =topology= batching
boundary.  Its hermetic GitHub archive digest is
=sha256:de202ddb3b204f4faa461f44df0cfeaa3bea5d77b047e46babc9a1fa51b84838=.
The focused GSLPH suite passed 11 test cases and 30 checks, including a
two-layer public-API fixture that requires one upstream package stage.

The corrected diagnostic is 25.9 percent faster than the rejected candidate,

The cold-audit runner previously created a distinct Bazel output base for
every sample.  Gerbil package action keys contain stabilized paths derived
from that output base, so the supposedly shared dependency disk cache could
not match the next sample.  The corrected runner owns one stable output base
per comparison side, invokes Bazel-native =clean= before each sample, restores
the three dependency packages from one shared dependency cache, and gives
only the root compile action a sample-local disk cache.  It also persists the
parsed receipt immediately as =SIDE-N/compile.receipt.json= before the next
clean, rather than retaining a symlink into mutable Bazel output state.

The real audit confirmed that repeated dependency seeding fell from 336.871
seconds for the first baseline side and 342.421 seconds for the first
candidate side to 4.019, 6.101, 3.714, and 5.603 seconds for subsequent
samples.  Each subsequent seed reported three disk-cache hits, a 98.2-98.9
percent reduction in repeated seed wall time.

The formal three-sample promotion gate remains blocked.  All three baseline
cold actions completed in 288.523, 313.690, and 320.398 seconds of Bazel wall
time.  Candidate samples 1 and 2 completed in 303.224 and 314.752 seconds.
Candidate sample 3 terminated after 108.226 seconds with macOS
=Bus error: 10= from =gxi=, producing exit 138.  No median comparison receipt
was emitted, so the dependency pin is not promoted by this record.

This failure also exposes an observability gap: the Scheme compile guard emits
receipts for pre-admission rejection and successful completion, but not for an
exception raised by the guarded build.  Before the formal audit is repeated,
the guard must emit a terminal failed-build receipt containing the stopped
process-tree guard observation, elapsed time, peak RSS, admission snapshot,
sample identity, and failure classification.  A retry without that evidence
would be an unqualified repetition rather than a new performance result.

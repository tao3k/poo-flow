* Root-cause boundary

The gerbil-bazel RFC 0008 audit rejected two speculative library changes:

1. Apple Clang was approximately 95.7 percent slower than the producer
   compatible GCC 16 compiler for the same generated object input.
2. Twelve concurrent GCC object jobs completed in 11,466 ms with a peak RSS of
   4,614,832,128 bytes, so a smaller fixed macOS core cap is not justified.

A native =gxc= probe over the same sixteen Gerbil modules crossed the
90-second guard without Bazel staging or =build.ss= orchestration.  The
remaining owner is the gerbil-poo frontend workload: module dependency depth,
macro expansion, and cross-module optimization.

* Promotion decision

gerbil-bazel PR 29 must remain draft.  The POO Flow pin must not be described
as a performance improvement or promoted as a stable downstream convergence
revision while the optimized gerbil-poo package gate and the full POO Flow
compile gate fail.

The adaptive resource guard itself remains valid:

- it used Gerbil =__available-cores= as the CPU-capacity source;
- it admitted twelve cores within the observed memory budget;
- it did not apply the runnable-pressure diagnostic as a hard cap;
- it emitted complete typed receipts for both packages.

The next implementation phase belongs to the POO Flow and GSLPH Scheme build
owners.  gerbil-bazel must remain the reusable toolchain and project-action
library.  It must not compensate by parsing =build.ss=, inventing a second
package manager, or deriving a private POO-specific module graph.

* Upstream-compatible ownership boundary

Gerbil upstream already provides parallel workers in =std/make=.  Its compiler
driver also deliberately protects =optimize!= with a process-global driver
mutex, and =std/make= executes pending Gambit/C jobs after the module build
barrier.  The observed frontend serialization is therefore an upstream
execution property, not evidence that Bazel failed to pass the host CPU count.

GSLPH currently computes dependency topology layers, but
=build-requests-run!= executes package stages sequentially and each POO runtime
layer remains inside the same gxi process.  The next design must preserve the
upstream compiler and move parallelism to explicit project-owned component
boundaries:

The project or GSLPH must declare the component graph.  gerbil-bazel may
execute those declared Gerbil projects and cache their outputs, but it must not
parse Scheme source or infer POO domain ownership.  Release builds must keep
Gerbil optimization enabled, all worker limits must remain host-derived, and
promotion requires both green unit tests and end-to-end performance receipts.

* Persistent optimized worker model

Starting one gxi process per module is rejected.  A representative import of
the GSLPH building surface costs approximately 3,715 ms before useful module
work begins.  Repeating that startup for hundreds of modules would dominate
the compile.

The required execution model is a fixed, host-derived pool of long-lived gxi
workers:

Each worker owns a separate Gerbil compiler process and therefore a separate
driver mutex.  Modules in one dependency layer may run concurrently, while the
next layer cannot start until the current layer has materialized its library
and =ssxi= artifacts.  The parent Scheme guard must monitor the complete worker
process tree and may reduce active workers from current host observations; the
worker count must never be hard-coded.

For the observed 381-module graph and twelve available workers, the 39 layers
reduce to 57 ideal equal-cost worker waves.  Using the observed runtime-stage
average of 772.3 ms per module gives a theoretical, startup-free lower bound of
approximately 44,020 ms, or 6.68 times faster than the 294,240 ms runtime
stage.  This is a feasibility bound, not a performance claim: real promotion
requires measured receipts that include skew, worker startup, artifact
barriers, RSS, and failure cancellation.

* Scheme supervisor boundary for fatal child termination

The observability gap is now closed at the process boundary rather than with
an exception handler inside the compiling =gxi=.  An in-process handler cannot
emit a receipt after =SIGBUS= terminates its process.  The public =compile=
entry therefore remains in a parent Scheme process, starts the existing
Scheme process-tree memory guard, and launches an internal =compile-worker=
entry as a child =gxi=.  The worker name is not advertised as a public build
entry.

The parent classifies a zero child exit as =completed= and every non-zero exit
as =child-failed=.  Because the parent survives a fatal child signal, it can
emit a terminal =poo-flow.project-compile-guard.v1= receipt before raising the
build failure.  The failed receipt carries =failure-kind=,
=failure-exit-code=, peak RSS, elapsed milliseconds, timeout state, and the
original host-admission snapshot.

All project-compile receipts now share one stable POO object shape.
=completed= and =blocked-host-pressure= receipts contain
=failure-kind=#f= and =failure-exit-code=#f=; =failed-build= replaces those
values with the process-guard classification.  JSON projection uses ordinary
POO slot access for this declared schema.  It no longer misuses =.has?=,
which does not report dynamic =.o= slots and previously erased the failure
classification.

* Audit-server lifecycle and canonical output-root correction

The first supervised formal rerun was deliberately stopped before any cold
sample receipt was accepted.  Its audit driver target finished analysis in
320.721 seconds with four action-cache hits, then the baseline output-base
server remained unavailable for more than 80 seconds.  The audit tree

A host-process audit found multiple Bazel JVMs left by earlier probe, baseline,
and candidate output bases.  Their configured idle lifetime was 10,800

invalid.  The obsolete servers were shut down through Bazel's native

The Scheme audit runner now owns two additional invariants:

1. It creates the requested output directory and resolves its physical path
   through Gerbil/Gambit's parameterized =current-directory=, which delegates
   to the operating system's =chdir/getcwd= behavior.  On Darwin this
   canonicalizes =/tmp= to =/private/tmp= without a shell parser.
2. The audit explicitly owns one stable Bazel server per side for the whole
   alternating sample sequence.  A pre-armed lifecycle receipt declares a
   =dynamic-wind= cleanup boundary, and both success and failure unwind paths
   issue Bazel's native =shutdown=.  No machine-independent idle timeout is
   hard-coded, so the opposite side's multi-minute sample cannot evict a
   server that the current audit still owns.

* Per-sample host admission

The incomplete formal observations also prove that a single audit-start
preflight is insufficient.  Runnable pressure changed from 16 to 59 while the
alternating sequence was active.  A comparison runner must therefore prove
host admissibility immediately before every baseline and candidate cold
sample, before dependency seeding or compilation consumes several minutes.

The runner now consumes the resource guard owned by gerbil-bazel through the
declared Bazel runfile =@gerbil_bazel//gerbil:resource_guard.ss=.  POO Flow
does not duplicate operating-system probes, CPU discovery, memory discovery,
or process-tree supervision.  The Bazel-resolved guard imports Gerbil
=__available-cores= and emits its normal immutable resource-guard receipt.

The comparison-only admission rule is stricter than the normal build rule:

- the upstream resource guard must report =admissionOutcome= equal to
  =ready=;
- =runnableProcessCountAvailable= must be true;
- =runnableProcessCount= must be at or below the observed

The second condition is machine-adaptive.  It contains no fixed core count,
fixed wait interval, or operating-system-specific shell probe.  Normal project
compilation still treats runnable saturation as advisory and may adapt its
worker plan.  Only the formal comparison runner rejects a sample whose timing
would not be attributable to the revision under test.

Each sample directory now owns:

- =resource-guard.receipt.json=, the upstream capability receipt;
- =host-admission.json=, the comparison-specific decision and provenance;
- =failure.context.json= with =phase= equal to =host-admission= when the
  sample is rejected.

A rejected sample never starts dependency seeding, native ABI discovery, or
the cold compile action.  The enclosing =dynamic-wind= still shuts down both
owned Bazel servers.

* POO Flow root-compile regression correction

The merged gerbil-bazel PR 29 remains the owner of fresh host observation,
package-action execution, toolchain capability, and publish-pin replay.  It
does not choose the worker count inside POO Flow's own =build.ss= supervisor.
The two boundaries must therefore be measured separately.

The last green =main= run on the same GitHub =macos-26= lane completed
=//scheme:compile= in 356 seconds.  PR 12 reached the outer 900-second timeout
in the same action.  Its newly introduced default divided the absolute RSS cap
by the configured worker count.  Because that absolute cap includes the
supervisor baseline RSS, the formula systematically reduced an admitted
=N=-worker host to at most =N - 1= workers.  That local POO Flow admission
policy, rather than the merged gerbil-bazel package-action implementation,
owned the regression.

The corrected policy combines a project safety ceiling with two
machine-derived limits:

- the absolute process cap is the smaller of
  =baseline RSS + live allocatable memory= and 5 GiB;
- the default per-worker reservation is the existing 768 MiB safety floor,
  with =POO_FLOW_BUILD_MEMORY_PER_WORKER_BYTES= retained as the explicit
  machine-calibration override.

The 5 GiB ceiling is a project safety invariant, not a machine-capacity
estimate.  Live memory may lower it but cannot raise it, and an explicit
=POO_FLOW_BUILD_MAX_RSS_BYTES= value cannot bypass it.  The worker floor reduces
parallelism only when the resulting envelope cannot admit all configured
workers.  An explicit RSS cap below =baseline + safety floor= remains blocked,
while exact coverage is admitted.

#+title: Native POO Observability Profile Definition Interface
#+status: Accepted
#+language: en

* Decision

The observability Profile surface has two presentation levels and one semantic
core:

1. ordinary users define standard observability Profiles through a bounded
   hygienic Gerbil macro;
2. advanced authors use native =gerbil-poo= objects, prototypes and operations
   directly.

Native POO object and prototype syntax is the only semantic extension
interface.  The macro is a convenience projection that expands transparently
to native =.def=, =.mix=, ==>.+= and ordinary POO values.

The macro does not introduce a runtime DSL, extension registry, provider
protocol, keyword dispatcher or alternative object model.

* User-composition remains simple

The consumer sees one named Profile:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    wendao-episteme
    production
    production-observability))
#+end_src

Retention, redaction, projection, export permission and budget internals do not
appear in =user-composition=.

There is no nested =compose=, nested =user-composition=, =initial= wrapper,
feature =if= expression or public =poo-compose= form.

* Ordinary hygienic macro surface

The standard user-facing definition has one concise named declaration and a
small set of stable domain concepts.  The following form is illustrative, not
a decision to copy another Lisp's keyword grammar:

#+begin_src scheme
(observability-profile production-observability
  (visibility operator)
  (retention 30-days)
  (redaction causal)
  (projection-budget standard)
  (export denied))
#+end_src

The design learns from mature Lisp configuration systems that a single
declarative entry, a small stable vocabulary, embedded expressions and strong
macro diagnostics can make a large system approachable.  It does not inherit
their macro names, punctuation, lifecycle phases, package model or mutable
runtime behavior.

The exact concrete syntax remains a Gerbil and POO Flow interface decision.
This RFC fixes the lowering and extension contract rather than prematurely
fixing clause punctuation.

For a stable ordinary case, the hygienic macro lifts a bounded shorthand such
as =operator=, =30-days=, =causal=, =standard= or =denied= into the
corresponding standard POO policy object.

For an advanced case, the same position accepts a native POO object expression:

#+begin_src scheme
(observability-profile production-observability
  (visibility operator)
  (retention specialized-retention)
  (redaction causal)
  (projection-budget specialized-projection-budget)
  (export denied))
#+end_src

=specialized-retention= and =specialized-projection-budget= are values created
through native POO definitions.  The user interface does not change when the
value becomes more sophisticated.

Both shorthand and advanced forms expand to POO policy objects before semantic
composition.  Raw alists, runtime keyword dispatch and open-ended enum
registries remain forbidden.

The standard macro implicitly refines =observability-policy-base=.  A user who
needs a different prototype lineage is using an advanced abstraction and
should use native POO syntax.

flowchart LR
  U["Standard observability-profile form"] -->|"hygienically validates known clauses"| M["Gerbil macro expansion"]
  M -->|"expands to native .def and nested =>.+ refinements"| P["Named POO Profile object"]
  P -->|"appears as one ordinary Profile binding"| C["compose profiles"]
  C -->|"produces the user system without exposing policy internals"| S["user-composition result"]
#+end_src

* Conceptual native expansion

The ordinary macro expands conceptually to:

#+begin_src scheme
(.def (production-observability
       self
       [observability-policy-base])

  visibility:
  =>.+ production-visibility

  retention:
  =>.+ production-retention

  redaction:
  =>.+ production-redaction

  projection-budget:
  =>.+ production-projection-budget

  export:
  =>.+ production-export-permission)
#+end_src

The final transformer must use the exact native =gerbil-poo= syntax and
hygienic bindings.  This example fixes the semantic shape, not an alternative
runtime representation.

* Why the macro is not a second language

The macro:

- has a bounded set of standard clauses;
- expands at Gerbil macro-expansion time;
- emits only native POO definitions and operations;
- preserves source provenance for invalidation explanations;
- attaches the same POO policy contracts as handwritten native syntax;
- produces an ordinary named POO object;
- disappears from runtime dispatch.

The macro does not:

- interpret clause names at runtime;
- build an alist or record DSL;
- register clause handlers;
- create a policy evaluator;
- hide a provider lookup;
- allow arbitrary callback hooks;
- define semantics not expressible through native POO.

#+begin_src mermaid
flowchart TD
  S["Surface macro syntax"] -->|"exists only for user comprehension"| E["Hygienic expansion"]
  E -->|"emits native prototype definitions"| N["Single POO semantic core"]
  A["Advanced handwritten POO syntax"] -->|"uses the same objects, contracts and operations"| N
  N -->|"drives composition, evidence and receipts"| R["One runtime semantics"]
#+end_src

* Compile-time validation

The macro SHOULD reject at expansion time:

- unknown standard clause names;
- duplicate clauses;
- missing required bindings;
- malformed clause shape;
- attempts to embed raw runtime dispatch;
- attempts to nest another =compose= or =user-composition=;
- clauses that syntactically request external effects.

POO object contracts still validate the semantic values.  Compile-time shape
checking does not replace native slot-contract validation.

Clause order does not define policy precedence.  Each standard clause targets
one hygienically bound policy slot.  Policy combination follows its POO
contract algebra.

* Bounded shorthand lifting

The ordinary interface may accept a small stable shorthand:

#+begin_src scheme
(observability-profile production-observability
  (retention 30-days)
  (redaction causal))
#+end_src

The macro expands it to the corresponding hygienically bound standard POO
objects.  The shorthand is a compile-time user convenience, not the runtime
representation.

When the standard shorthand is insufficient, the value position accepts the
advanced POO object directly:

#+begin_src scheme
(def specialized-retention
  (.mix
    incident-retention
    production-retention))

(observability-profile production-observability
  (retention specialized-retention)
  (redaction causal))
#+end_src

The macro MUST NOT accept arbitrary untyped alists or dynamically registered
tokens.  Each supported shorthand has one hygienic compile-time lowering and
one native POO contract.

* Advanced interface

Advanced authors use native POO syntax directly.

** Direct named prototype

When one Profile has one coherent policy definition, prefer one =.def=:

#+begin_src scheme
(.def (production-observability
       self
       [observability-policy-base])
  visibility: =>.+ production-visibility
  retention: =>.+ production-retention
  redaction: =>.+ production-redaction
  projection-budget: =>.+ production-projection-budget
  export: =>.+ production-export-permission)
#+end_src

** Reusable prototype composition

Use =.mix= only when policy fragments have genuine independent reuse,
prototype dependencies or higher-order extension:

#+begin_src scheme
(.def restricted-visibility
  visibility:
  =>.+ restricted-visibility-policy)

(.def bounded-retention
  retention:
  =>.+ bounded-retention-policy)

(.def causal-redaction
  redaction:
  =>.+ causal-redaction-policy)

(def production-observability
  (.mix
    causal-redaction
    bounded-retention
    restricted-visibility
    observability-policy-base))
#+end_src

This =.mix= constructs one Profile object.  The outer =compose profiles= places
that completed Profile into the user system.  They are different semantic
layers and not duplicate composition.

#+begin_src mermaid
flowchart TD
  A["restricted-visibility prototype"] -->|"provides a reusable local refinement"| M[".mix constructs one Profile"]
  B["bounded-retention prototype"] -->|"provides a reusable local refinement"| M
  C["causal-redaction prototype"] -->|"provides a reusable local refinement"| M
  M -->|"binds one stable object name"| P["production-observability"]
  P -->|"the consumer composes only the named Profile"| U["compose profiles"]
#+end_src

* Style rule for .def and .mix

Use one clear =.def= when one definition expresses the policy coherently.

Use =.mix= only when at least one of the following holds:

- the policy fragment is reused by several Profiles;
- the fragment has an independent prototype dependency;
- the fragment is independently refined by downstream Profiles;
- multiple-inheritance linearization expresses a real relationship;
- a higher-order extension needs the fragment as a first-class prototype.

Do not split a simple Profile into many mixins merely because =.mix= exists.

* Higher-order extension

Feature selection remains prototype extension rather than a runtime =if=:

#+begin_src scheme
(def audited-production-observability
  (.mix
    audit-evidence-retention
    production-observability))
#+end_src

The completed object may then be selected as the Profile binding used by the
system composition.

The public interface does not require:

#+begin_src scheme
(if audit-enabled? ...)
#+end_src

or a =+audit= token dispatcher.

* Macro boundary for new policy dimensions

The ordinary macro intentionally covers the standard, commonly understood
observability dimensions.

If an advanced author invents a new policy dimension, the extension path is:

1. define its POO contract object;
2. define or refine the corresponding native POO slot;
3. compose it through =.def=, =.mix=, ==>=, ==>.+= or another native
   =gerbil-poo= operation;
4. expose a named Profile.

The author does not register a new macro clause at runtime.

The standard macro may later gain a hygienically bound clause when the
dimension becomes a stable ordinary-user concept.  That convenience addition
does not define the underlying semantics.

* Macro identity and invalidation

The macro participates in the phase-aware identity model.

- Transformer changes invalidate expansion execution identity.
- Fresh expansion may prove that the native POO definition remains identical.
- Clause-to-expanded-slot provenance is retained for causal explanation.
- Hygienic binding changes invalidate the affected policy definition.
- Generated local alpha-renames do not change POO semantic identity.
- Opaque compile-time inputs cause cross-process reuse to fail closed.

The invalidation explanation should identify the user-facing clause and the
native expanded slot without pretending they are separate semantics.

* Design-reference boundary

Emacs and Doom Emacs are useful references for:

- a compact declarative entry point;
- a small discoverable vocabulary;
- allowing ordinary values and advanced Lisp expressions in the same
  declaration;
- macro-time normalization and validation;
- retaining source context for useful diagnostics;
- hiding internal machinery from ordinary users.

POO Flow does not copy:

- =package!=, =use-package!= or bang naming;
- =:init=, =:config=, =:custom= or another system's phase names;
- package-installation ownership;
- a mutable global editor environment;
- side-effectful configuration bodies;
- exact keyword or clause punctuation.

POO Flow reconstructs the learned principles through Gerbil hygienic macros,
native =gerbil-poo= values, fixed-point semantics and explicit effect
boundaries.

#+begin_src mermaid
flowchart LR
  C["User-facing retention clause"] -->|"macro provenance maps the clause"| S["Native retention slot refinement"]
  T["Transformer or binding delta"] -->|"forces fresh expansion"| S
  S -->|"canonical native definition changed"| I["Policy definition invalidation"]
  S -->|"canonical native definition remained equal"| R["Policy result remains reuse-eligible"]
  I -->|"explanation retains both surface and native identities"| E["Causal evidence"]
  R -->|"explanation records re-expansion without semantic change"| E
#+end_src

* Policy and business receipt separation

Whether a Profile was handwritten or produced by the macro does not affect its
semantic identity when both expand to the same canonical POO definition.

Changing only observability policy may change:

- Profile definition identity;
- observability-policy receipt;
- projection and operational receipts.

It does not change:

- canonical business values;
- evidence-kernel receipt;
- business fixed-point convergence.

* Effect boundary

The =export= clause contains a POO permission object.  It does not perform an
export.

Macro expansion, Profile composition and evidence projection remain pure.
External publication requires an inert effect intent, current authority,
runtime handoff and an operational receipt.

* Required failure conditions

The interface MUST fail closed when:

- the macro produces a non-POO runtime representation;
- an unknown or duplicate clause silently overrides another;
- clause order becomes hidden precedence;
- an unbounded raw value bypasses hygienic shorthand lowering or POO contract
  validation;
- the macro permits runtime clause registration;
- the macro hides a nested =compose= or provider lookup;
- advanced extension requires any interface other than native POO;
- a simple coherent Profile is needlessly split into accidental mixins;
- macro and handwritten definitions with equal canonical expansion receive
  different semantic meaning;
- an export permission performs an effect during composition.

* Acceptance checklist

- [X] Ordinary users receive a bounded hygienic macro surface.
- [X] The macro expands only to native =gerbil-poo= definitions and operations.
- [X] Native POO object and prototype syntax is the sole advanced semantic
  extension interface.
- [X] =user-composition= contains only one clear named Profile.
- [X] Standard clauses accept bounded shorthand or advanced POO object
  expressions and lower both to native POO policy objects.
- [X] Unknown and duplicate clauses are compile-time errors.
- [X] One coherent =.def= is preferred for a simple Profile.
- [X] =.mix= is reserved for genuine reuse, dependency or higher-order
  extension.
- [X] Inner prototype construction and outer Profile composition remain
  distinct.
- [X] New advanced dimensions do not require runtime macro-clause registration.
- [X] Macro and handwritten forms share one definition-identity model.
- [X] Export permission remains pure until the effect boundary.
- [ ] Validate the surface with executable simple-profile, macro-expansion,
  handwritten-equivalence, duplicate-clause, raw-enum rejection, reusable-mix,
  higher-order extension, phase-invalidation and export-purity scenarios before
  implementation begins.

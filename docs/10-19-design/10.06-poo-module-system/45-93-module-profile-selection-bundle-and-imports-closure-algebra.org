#+title: Module Profile Selection, ProfileBundle, and imports Closure Algebra
#+startup: overview

* Status

Accepted architecture.

This RFC freezes the algebra between a higher-order POO Module, selected
Profiles, a ProfileBundle, the recursive ~imports~ closure, and the final
composition root.

It defines the constrained ~use-module~ user projection.  It does not authorize
an alist lowering, a module registry, or a new general-purpose clause language.

* Scope

This document owns:

- the POO Module object responsibilities;
- Profile selection from one Module;
- the ProfileBundle result type;
- default and explicit module-instance identity;
- recursive imports projection from selected Profiles;
- capability attenuation along reachable dependency edges;
- selection fusion, idempotence, and instance-separation laws;
- the constrained ~use-module~ macro boundary; and
- admission of ProfileBundles by ~(compose profiles ...)~.

It does not own:

- Profile prototype evaluation;
- the implementation of ~compose~;
- the ~use-composition~ binding macro;
- package installation;
- physical Gerbil module loading;
- control-policy priority;
- a compatibility surface for the old clause parser; or
- framework-specific User Interface cases.

* Central decision

The public composition path separates four operations:

1. ~use-module~ selects exported Profiles from one Module and produces one
   ProfileBundle;
2. ~compose~ with the ~profiles~ strategy composes ProfileBundles and other
   admitted Profile values;
3. the composition root computes the recursive ~imports~ closure reachable
   from the selected Profiles; and
4. ~user-composition~ binds the result, projects stable identity, and performs
   one root instantiation.

The ordinary surface is:

#+begin_src scheme
(user-composition production-agent
  (compose profiles
    (use-module identity
      service-principal
      multi-tenant)
    (use-module agent
      planner-agent
      delegated-tools)
    (use-module wendao-episteme
      production-governance)
    (use-module runtime
      distributed-runtime
      sandboxed)
    (use-module observability
      full-receipts)))
#+end_src

No transitive module dependency is enumerated in this form.

* Core POO objects

** Module

A Module is an immutable higher-order POO object that owns:

- a stable module-definition identity;
- exported Profile identities and values;
- dependency projections for those Profiles;
- a recursive ~imports~ object;
- capability requirements;
- submodule relationships;
- revision and generation;
- pure provenance and evidence contracts; and
- the backend projection contract for admitted physical module boundaries.

A Module does not own:

- live runtime authority;
- a global registration entry;
- one mandatory deployment instance;
- a user composition root;
- package installation; or
- an implicit Profile result.

** Profile

A Profile is an immutable POO semantic value exported by a Module or constructed
through admitted native POO extension.

Every exported Profile has:

- a stable Profile identity;
- an owning Module identity;
- a dependency projection into the Module's ~imports~ graph;
- capability requirements;
- prototype lineage; and
- native Profile semantics.

Profile selection never changes the Profile definition.

** ProfileBundle

A ProfileBundle is the immutable result of selecting one or more exported
Profiles from one Module instance.

It preserves:

- Module definition identity;
- Module instance identity;
- selected Profile identities and values;
- only the dependency roots reachable from those Profiles;
- the Module and Profile capability requirements;
- revision and generation;
- provenance of the selection; and
- an admission proof that every selection belongs to the Module export
  surface.

A ProfileBundle is admitted as one higher-order Profile operand by the
~profiles~ composition strategy.

** imports

~imports~ is an immutable recursive POO dependency object.

It contains semantic dependency nodes and edges, not source strings and not a
flat list of Gerbil import forms.

Each edge preserves:

- source and target stable identity;
- the selected Profile that made the edge reachable;
- capability requirements;
- revision and generation constraints;
- phase requirements;
- optionality or mandatory status under the owning POO contract; and
- provenance for cycle and closure receipts.

** CompositionRoot

The CompositionRoot preserves:

- the final composition identity;
- the composed Profile semantics;
- admitted Module instances;
- the reachable imports closure;
- effective capability requirements;
- fixed-point and cycle evidence;
- backend module-boundary projections; and
- exactly one native root instantiation.

* use-module contract

The public forms are:

#+begin_src scheme
(use-module module-name
  exported-profile ...)

(use-module module-name as instance-name
  exported-profile ...)
#+end_src

At least one exported Profile is required.

The first form uses the Module definition identity as the default instance
identity.

The second form creates an explicitly distinct Module instance identity.

~use-module~ is a constrained hygienic value-producing macro.  It:

1. validates the optional ~as~ shape and identifiers;
2. projects the selected Profile identities from the Module export surface;
3. constructs a POO-native ProfileBundle;
4. preserves ~imports~, identity, capability, revision, and provenance; and
5. returns the bundle as an ordinary Scheme value.

It does not:

- bind a composition root;
- parse ~compose~;
- parse stages, graphs, loops, proofs, or handoffs;
- define or mutate Profiles;
- accept arbitrary keyword sections;
- lower to an alist;
- call ~object<-alist~;
- issue capabilities;
- load packages; or
- enumerate the transitive imports closure.

* Selection, not inline definition

The ordinary ~use-module~ surface only selects Profiles already exported by the
Module.

The following old pattern is not part of the target contract:

#+begin_src scheme
(use-module agent as agent
  (profile session-hardened
    :scope (session)
    :hooks (...)))
#+end_src

It mixes Profile definition, extension, selection, and Module instantiation.

Advanced authors instead:

1. extend the Profile or Module through the verified native POO interface;
2. publish the refined Profile under an explicit Module export identity; and
3. select that exported Profile through ~use-module~.

This keeps the ordinary surface finite while preserving a single advanced POO
extension interface.

* Identity model

Module definition identity and Module instance identity are distinct.

Without ~as~:

#+begin_src scheme
(use-module storage
  durable)
#+end_src

the instance identity defaults to the definition identity of ~storage~.

With ~as~:

#+begin_src scheme
(use-module storage as primary
  durable)

(use-module storage as audit
  append-only)
#+end_src

the two bundles share one Module definition but preserve different instance
identities, capability scopes, and Profile selections.

The imports closure may deduplicate immutable implementation dependencies by
definition identity.  It must not collapse the ~primary~ and ~audit~ semantic
instances.

* Selection algebra

Let ~U(M, I, P)~ denote a ProfileBundle selected from Module ~M~, instance
identity ~I~, and finite Profile identity set ~P~.

Let ~+~ denote admitted ProfileBundle composition under the ~profiles~
strategy.

#+begin_src typst
$ U(M, I, P) + U(M, I, Q) = U(M, I, P union Q) $
$ U(M, I, P) + U(M, I, P) = U(M, I, P) $
$ U(M, I, P) + U(N, J, Q) = U(N, J, Q) + U(M, I, P) $
$ I != J ==> U(M, I, P) != U(M, J, P) $
$ "imports"(U(M, I, P)) =
  "closure"("reachable-dependencies"(M, P)) $
#+end_src

** Selection fusion

For the same Module definition and instance identity:

Fusion is admitted only when revisions, generations, capabilities, and export
identities are compatible.

** Idempotence

Repeating the same selection cannot duplicate authority, imports, effects, or
evidence.

** Permutation independence

This law applies to selection collection and imports closure identity.  Native
Profile conflict semantics remain owned by the Profile composition strategy.

** Instance separation

Explicitly distinct instances never fuse merely because their Module
definition and selected Profiles are equal.

** Import projection

The import projection law is selection-sensitive: only dependencies reachable
from the selected Profiles enter the active closure.

The closure contains only dependencies reachable from the selected Profiles.
Unselected Profile subgraphs remain inactive.

** Capability attenuation

#+begin_src typst
$ "capability"(U(M, I, P)) =
  "intersect"(
    "module-requirements"(M),
    "selected-profile-requirements"(P),
    "reachable-import-requirements"(M, P),
  ) $

$ "admitted-authority"("closure"(M, P))
  subset.eq "admitted-authority"(M) $
#+end_src

Selection and closure may preserve or reduce admitted authority.  They cannot
amplify it.

* Reachability before closure

A Module may export many Profiles with different dependency roots.

For example:

#+begin_example
agent
  planner-agent
    depends on planner and long-memory
  delegated-tools
    depends on tool-schema, sandbox, and capability
  conversational-agent
    depends on prompt, model, and short-memory
  multi-agent
    depends on messaging and shared-state
#+end_example

Selecting only ~conversational-agent~ does not activate planner, sandbox,
tool-schema, messaging, or shared-state dependencies.

The root first projects reachability from selected Profiles, then computes the
recursive closure.

* Cycles and fixed-point ownership

Recursive imports may contain cycles.

~use-module~ does not reject a graph merely because a cycle exists and does not
evaluate the cycle in macro expansion.

The POO Flow fixed-point boundary owns:

- lazy recursive evaluation;
- cycle identity;
- demand budgets;
- incremental recomputation;
- cache identity;
- continuable control conditions;
- suspension and recovery;
- and cycle observability.

This RFC owns only the selection roots and imports graph projected into that
boundary.  It does not implement another fixed-point evaluator.

* Physical Gerbil projection

The active imports closure may project physical Gerbil import, load, generated
facade, or runtime handoff boundaries according to phase and implementation
requirements.

That projection:

- occurs after semantic identity and capability admission;
- is deterministic for one closure revision;
- records every projected Module identity;
- never changes the selected Profile semantics;
- never becomes a user-authored transitive import list; and
- remains separate from ~gerbil.pkg~ dependency installation.

~user-composition~ and ~use-module~ do not install packages.

* Macro governance

~use-module~ is admitted as a constrained macro because it projects one small
closed syntax family directly to ordinary POO-native values.

Its grammar owns only:

- a Module expression;
- optional ~as~ plus an instance identifier; and
- one or more exported Profile identifiers.

It may not grow clauses for:

- Profile fields;
- inline extension;
- imports declarations;
- capability issuance;
- priority;
- stages;
- graphs;
- loops;
- proof obligations;
- handoffs;
- package dependencies; or
- runtime handlers.

Any repeated internal POO construction may use bounded declarative or
procedural macros under
[[file:44-current-project-programming-style.org][44]], provided expansion
remains inspectable native POO and functional code.

* Current implementation gap

The current syntax-plan parser treats ~use-module~ as a private form in the
second operand position of ~use-composition~.

The current path:

- declares Profiles inside ~use-module~;
- repeats their alias-qualified references in a separate compose clause;
- allows inline keyword sections;
- lowers sections through alists and ~object<-alist~; and
- returns no standalone ProfileBundle value.

The target:

- makes ~use-module~ independently value-producing;
- places it directly inside ~(compose profiles ...)~;
- selects exported Profiles without defining them;
- produces a native POO ProfileBundle; and
- removes duplicate declaration and reference.

No compatibility grammar is required.

* Error and receipt contract

A selection receipt records:

- Module definition identity;
- Module instance identity;
- selected Profile identities;
- missing or duplicate export identities;
- revision and generation;
- direct dependency roots;
- capability requirements;
- fusion or separation decision;
- reachable imports closure identity; and
- source provenance.

Failures distinguish:

- unknown Module;
- unknown exported Profile;
- invalid alias identity;
- incompatible duplicate default instance;
- stale revision or generation;
- capability intersection failure;
- imports cycle budget exhaustion;
- backend projection failure; and
- package dependency failure.

These are not collapsed into a generic macro error or native POO failure.

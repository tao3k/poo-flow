#+title: Semantic Capability Evidence, Runtime Materialization, Lease, Revocation, and Receipt Contract
#+author: POO Flow
#+language: en

* Status

This RFC is an accepted runtime-boundary semantic contract.

It defines how semantic capability evidence may request runtime capability
materialization.  It does not admit a runtime adapter implementation, place
runtime handles in semantic POO values, or guarantee that semantic satisfaction
implies runtime authorization or availability.

* Scope

This RFC owns:

- projection from semantic capability closure to an EffectIntent;
- runtime authorization;
- intent stabilization and materialization claims;
- handle construction or acquisition;
- lease identity, scope, lifetime, renewal, expiration, and revocation;
- cancellation and cleanup;
- crash ambiguity and recovery;
- runtime denial and structured conditions;
- runtime receipts and redaction;
- separation of semantic closure cache from runtime handle cache.

It does not own:

- semantic capability satisfaction or closure;
- upstream POO mechanics;
- secret values;
- a global handle registry;
- application deployment policy;
- package or build dependencies;
- a public capability-materialization macro.

* Central decision

Semantic capability closure produces evidence.  Runtime materialization is an
explicit effect.

The boundary is:

1. pure dispatch projects a capability-materialization EffectIntent;
2. the intent is stabilized before any irreversible action;
3. a runtime adapter performs authorization;
4. the coordinator claims the materialization fence;
5. the adapter acquires or constructs the handle;
6. the adapter creates a lease;
7. the coordinator stabilizes a runtime receipt;
8. the handle is handed only to the authorized runtime consumer;
9. revocation, cancellation, expiration, and cleanup remain adapter-owned.

* Semantic input

The input is an admitted semantic capability-closure result from RFC 45-125.

It identifies:

- requested capability;
- satisfied requirement and provision evidence;
- requesting Module, Profile, and runtime consumer identity;
- attenuation and authorization scope;
- provenance and redaction boundary;
- semantic closure identity.

It contains no runtime handle, secret value, credential, open connection, or
mutable adapter object.

* Capability-materialization intent

The capability-materialization intent is an internal POO-native specialization
of EffectIntent.

It contains:

- stable intent identity;
- semantic capability evidence identity;
- requester and consumer identities;
- requested runtime scope;
- requested lifetime or lease policy;
- adapter-selection responsibility;
- authorization-context reference;
- idempotency and reconciliation policy;
- redaction policy;
- cancellation and cleanup requirements.

It does not contain:

- a materialized handle;
- a resolved secret;
- ambient authorization;
- an executable callback;
- a raw continuation.

The intent is immutable.  Changes create a new intent identity.

* Intent stabilization

The coordinator stabilizes the intent before runtime authorization or external
materialization.

Stabilization records:

- intent identity and semantic input identity;
- selected adapter identity or adapter-dispatch responsibility;
- execution lineage;
- authorization and redaction context references;
- materialization-fence identity;
- recovery and cleanup policy.

Intent stabilization is not proof that authorization succeeded or that a
handle exists.

* Runtime authorization

Runtime authorization is evaluated at materialization time.

It may depend on:

- current runtime authority;
- consumer identity;
- requested scope and lifetime;
- deployment policy;
- adapter availability;
- revocation state;
- runtime secret references.

Runtime authorization does not mutate semantic capability closure.

The following remain distinct:

- semantically unsatisfied;
- semantically satisfied but runtime-denied;
- authorized but runtime-unavailable;
- authorized and materialized.

* Adapter selection

Runtime adapter selection is POO-native.

An admitted adapter prototype provides the materialization responsibility for a
capability identity or family.  Selection may use upstream generic and
prototype dispatch.

There is no hidden global registry, string switch, host =case=, or package-based
adapter lookup.

Adapter dispatch happens after semantic closure and before the external effect.
It cannot rewrite semantic capability evidence.

* Materialization fence

Materialization may create a non-idempotent external resource.

The coordinator claims a fence identified by:

- stabilized intent identity;
- adapter identity;
- consumer identity;
- requested scope;
- execution lineage;
- materialization generation.

The claim prevents concurrent blind execution of the same logical intent.  It
does not prove that an interrupted external action did or did not complete.

* Handle acquisition or construction

The adapter may:

- acquire an existing authorized handle;
- construct a new handle;
- renew an existing lease;
- reconcile an externally created resource;
- deny or suspend materialization.

The handle remains inside the runtime adapter and authorized consumer boundary.
It is never inserted into Module, Profile, ProfileBundle,
=DispatchEvaluation=, semantic capability closure, or
=ResolvedCompositionReceipt=.

* Lease identity

A runtime lease identifies:

- lease identity;
- materialization intent identity;
- adapter identity;
- capability identity;
- authorized consumer;
- runtime scope;
- materialization generation;
- authorization decision identity;
- lifetime and renewal policy;
- revocation and cleanup policy.

Runtime timestamps, expiration, and process-local identities may participate in
lease behavior.  They do not enter semantic capability identity.

A lease is not a semantic provision.

* Handle delivery

The authorized runtime consumer receives an opaque adapter-owned handle or
reference.

Delivery requires:

- stable lease identity;
- matching consumer and scope;
- current authorization;
- non-revoked state;
- successful receipt stabilization or an admitted atomic handoff protocol.

The handle is not serialized into an Org receipt, semantic cache, or
composition artifact.

* Runtime handle cache

The runtime handle cache is adapter-owned.

Its identity includes:

- adapter and capability identities;
- consumer and scope;
- lease and materialization generation;
- runtime authorization identity;
- secret-reference generation when applicable;
- revocation state.

It is distinct from the semantic capability-closure cache.

A semantic cache hit cannot reuse a runtime handle.  A runtime handle-cache miss
does not invalidate semantic satisfaction.

Runtime handle reuse requires a valid lease and current authorization.

* Secret and redaction boundary

The semantic intent may carry a secret reference identity.  Secret resolution
occurs only inside the authorized runtime adapter.

The adapter must not place in receipts or explanations:

- secret values;
- raw credentials;
- bearer tokens;
- private keys;
- connection strings containing secrets;
- unredacted handle internals.

Receipts may carry redacted secret-reference identity, provider identity,
generation, and authorization evidence.

* Revocation

Revocation is a runtime transition.

It may be triggered by:

- explicit operator authorization;
- lease expiration;
- consumer termination;
- capability-policy change;
- secret rotation;
- adapter or provider revocation;
- cleanup after cancellation or recovery.

Revocation:

- prevents new authorized use;
- invalidates relevant runtime handle-cache entries;
- invokes adapter cleanup;
- produces a receipt;
- does not rewrite historical semantic closure.

A later semantic dispatch may still report that the capability contract was
satisfied while runtime materialization is currently denied or unavailable.

* Cancellation and cleanup

Cancellation before fence claim terminates the intent without external cleanup.

Cancellation after fence claim requires reconciliation.

Cancellation after handle acquisition requires revocation and cleanup before
the attempt is terminal.

Cleanup may be:

- complete;
- pending;
- retry-admitted;
- denied;
- ambiguous;
- failed with structured evidence.

The coordinator must not report final cancellation while an owned external
resource remains unaccounted for.

* Crash ambiguity

Crash ambiguity exists when execution stops after an external action may have
occurred but before a stable receipt proves the result.

Important boundaries include:

- authorization completed but fence not claimed;
- fence claimed but adapter not invoked;
- adapter invoked but completion unknown;
- handle acquired but lease receipt not stable;
- lease stable but consumer handoff unknown;
- revocation invoked but cleanup completion unknown.

Recovery must use adapter-specific query or reconciliation when available.

Blind retry is rejected when it may duplicate resource creation, authorization,
lease issuance, or cleanup.

* Recovery behavior

Recovery may:

- prove the external action did not occur and admit a new attempt;
- discover an existing resource and complete lease stabilization;
- discover an orphan and revoke or clean it up;
- prove a completed revocation;
- remain suspended for external evidence;
- return unresolved ambiguity.

RecoveryExecutionIntent owns effectful recovery.  Coordinator resumption creates
a new execution identity and claims the appropriate continuation fence.

No raw continuation is stored in a handle, lease, or receipt.

* Exactly-once logical reconciliation

The contract provides exactly-once logical reconciliation, not a universal
exactly-once external effect guarantee.

For one stabilized intent:

- one active materialization claim exists at a time;
- duplicate delivery reuses or observes the same claim;
- every external effect is reconciled to one materialization lineage;
- authorization, acquisition, lease, handoff, revocation, and cleanup receipts
  remain distinguishable;
- budget and cleanup obligations reconcile once.

Retry, replay, duplicate delivery, recovery, and renewal remain distinct.

* Materialization outcomes

Materialization may return:

- runtime authorized;
- runtime denied;
- acquired;
- renewed;
- reused under a valid lease;
- suspended;
- unavailable;
- revoked;
- expired;
- cleanup pending;
- cleanup complete;
- unresolved ambiguity;
- cancelled.

Every outcome is bound to the stabilized intent and execution lineage.

* Runtime receipt

A materialization receipt may identify:

- schema and receipt identity;
- intent and semantic capability evidence identities;
- adapter and consumer identities;
- authorization decision;
- fence claim;
- materialization generation;
- lease identity and state;
- redacted handle type or fingerprint;
- secret-reference identity and generation;
- runtime outcome;
- revocation and cleanup state;
- execution lineage;
- reconciliation evidence;
- redaction policy.

It does not contain the runtime handle or secret value.

The materialization receipt is distinct from:

- semantic capability explanation;
- =ResolvedCompositionReceipt=;
- package, source, or build evidence;
- operator proposal;
- publication receipt.

* Publication and conditional commit

If handle delivery or lease activation requires external publication, the
runtime adapter uses an authorized conditional commit.

The publication head, lease state, and consumer handoff must be reconciled
without treating =use-composition= as a publication interface.

Rollback is a new runtime transition or revocation.  It does not mutate the
semantic capability closure.

* Public-interface boundary

This RFC adds no ordinary user syntax.

The composition interface remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

Runtime materialization is initiated only by admitted effect boundaries.

* Ownership

- =poo-flow-core= owns semantic capability evidence and EffectIntent
  projection.
- Runtime/deployment adapters own authorization, handle acquisition, handle
  cache, leases, revocation, cleanup, reconciliation, and runtime receipts.
- The coordinator owns intent stabilization, claims, lineage, recovery
  admission, and exactly-once logical reconciliation.
- The final application owns deployment authorization policy.
- =wendao-episteme= owns no runtime handle lifecycle unless it explicitly owns
  a domain runtime adapter outside its semantic Profile values.
- GSLPH remains a development policy harness and building/testing dependency.
- Gerbil-Bazel, Nix, and =gerbil.pkg= do not provide runtime capability
  semantics.

* Admission checklist

** Semantic boundary

- [X] Keep semantic capability evidence free of runtime handles and secrets.
- [X] Project runtime requests through EffectIntent.
- [X] Separate semantic satisfaction, runtime denial, and runtime availability.
- [X] Keep semantic closure cache separate from runtime handle cache.
- [ ] Admit the concrete EffectIntent specialization.

** Authorization and materialization

- [X] Require runtime authorization at materialization time.
- [X] Stabilize intent before external effects.
- [X] Claim a materialization fence before adapter invocation.
- [X] Require POO-native adapter selection.
- [ ] Define concrete adapter authorization and materialization responsibilities.
- [ ] Prove idempotent and non-idempotent provider behavior.

** Lease lifecycle

- [X] Freeze lease identity, scope, consumer, generation, lifetime, and policy.
- [X] Require current authorization for delivery and reuse.
- [X] Keep handles within adapter and consumer runtime boundaries.
- [X] Require revocation and cleanup receipts.
- [ ] Define renewal, expiration, revocation, and cleanup policies as native POO
  prototypes.

** Recovery and ambiguity

- [X] Enumerate crash-ambiguity boundaries.
- [X] Reject blind retry for ambiguous non-idempotent effects.
- [X] Separate retry, replay, duplicate delivery, recovery, and renewal.
- [X] Require adapter query or reconciliation when available.
- [ ] Prove each ambiguity boundary with focused fault injection.
- [ ] Prove orphan discovery and cleanup.

** Secret and receipt boundary

- [X] Resolve secrets only inside authorized runtime adapters.
- [X] Reject secret and handle values in receipts.
- [X] Separate materialization, semantic, composition, package, and publication
  receipts.
- [ ] Prove receipt redaction and secret rotation behavior.

** Implementation admission

- [ ] Define the runtime materializer as a POO-native adapter object.
- [ ] Implement intent stabilization and fence claims.
- [ ] Implement lease, revocation, cleanup, and handle-cache behavior.
- [ ] Integrate RecoveryExecutionIntent.
- [ ] Run focused GSLPH development checks without adding a product dependency.

* Rejected alternatives

- Runtime handles stored in Module, Profile, ProfileBundle,
  =DispatchEvaluation=, or semantic capability closure.
- Semantic satisfaction treated as runtime authorization.
- A global mutable handle registry.
- Adapter selection by strings, package names, or host =case=.
- External effect before intent stabilization.
- Blind retry after ambiguous materialization.
- Reusing a handle without a valid lease and current authorization.
- Secret values or raw handles in receipts.
- Revocation rewriting historical semantic closure.
- Sharing cache identity between semantic closure and runtime handles.
- Reporting final cancellation before cleanup is reconciled.
- Runtime materialization syntax inside =use-composition=.

* Successor contract

The next RFC should define one higher-order runtime
=CapabilityMaterialization= POO object.

It should have three required semantic/runtime-boundary slots:

- =intent=;
- =adapter=;
- =runtime-context=.

Authorization, claim, materialization, lease, handoff, revocation, cleanup,
reconciliation, outcome, and receipt should remain derived responsibilities
implemented through native POO policy prototypes.

It must not expose the handle as a semantic slot or ordinary user value.

* Lean-discovered owner gap

The current owner inventory does not contain a finite crash-deferral contract
or a bounded pre-commit storage-admission contract.

The runtime watchdog owns observations:

- runtime owner and phase identity;
- metric and unit;
- observed and threshold values;
- optional process-memory attribution.

The deterministic budget owner owns only semantic and scheduling accounting.
The completion-storage owner proves atomicity after commit and carries a
storage transaction digest.

None of those structures owns:

- a recovery-scoped maximum number of crash deferrals;
- crash-deferral consumed/remaining conservation;
- a pre-commit storage capacity decision;
- a finite storage-deferral budget;
- a transition receipt that can construct the crash or storage branch of the
  existing owner-indexed recovery progress receipt.

This is a type-level absence, not merely an omitted theorem.

* Decision

Define two proof-level owner-native contracts:

1. a runtime-owner crash-deferral contract and receipt;
2. a storage-owner pre-commit admission contract and receipt.

They are not runtime implementation objects yet.  Their purpose is to state
the minimum algebra that an eventual owner implementation must satisfy before
its evidence can enter the recovery convergence proof.

The current watchdog observation and post-commit receipt remain unchanged.
They cannot be reinterpreted as either new contract.

* Runtime-owner crash-deferral accounting

Let the runtime-owner contract be:

#+begin_src typst
$ C_R = (i, r, o_R, e, f, L_R, p) $
#+end_src

where:

- =i= is the contract identity;
- =r= is the recovery identity;
- =o_R= is the runtime owner;
- =e= is the runtime epoch;
- =f= is the active fence token;
- =L_R= is the authorized maximum number of crash deferrals;
- =p= is provenance.

A receipt contains consumed and remaining coordinates:

#+begin_src typst
$ q_R = (i, r, o_R, e, f, c_R, n_R, p_R) $
#+end_src

The closure requires exact owner, recovery, epoch, fence, and contract
identity binding plus conservation:

#+begin_src typst
$ c_R + n_R = L_R $
#+end_src

The contract is finite because =L_R= is a natural number authorized once by
the runtime owner.  A transition may not change that limit or any source
coordinate.

* Crash-deferral transition

A closed deferral step advances consumed accounting once and decreases the
remaining coordinate once:

#+begin_src typst
$ c_R' = c_R + 1
  and n_R = n_R' + 1
  => n_R' < n_R $
#+end_src

The proof does not use elapsed time, process RSS, or threshold exceedance as a
substitute for this decrease.  Those remain observability evidence.

* Why the watchdog cannot determine the contract

For one current watchdog observation =W= and recovery expectation =E=, Lean
constructs two contracts with the same current-evidence projection:

#+begin_src typst
$ pi_R(C_R^0) = pi_R(C_R^1) = (r, o_R, e, f)
  and L_R^0 = 0
  and L_R^1 = 1 $
#+end_src

Therefore:

#+begin_src typst
$ op("WatchdogObservation")(W)
  and op("RecoveryExpectation")(E)
  and op("does-not-entail")(L_R) $
#+end_src

In particular:

- =thresholdValue < observedValue= is an exceeded observation, not remaining
  deferral accounting;
- watchdog =generation= is not silently redefined as recovery =runtimeEpoch=;
- =SourceBoundRuntimeWatchdogRetryAuthority= is an abstract predicate, not an
  inhabited finite retry contract.

* Storage-owner pre-commit admission accounting

Let the storage-owner contract be:

#+begin_src typst
$ C_S = (i, r, u, o_S, e, f, L_S, d, p) $
#+end_src

where:

- =u= is the exact publication identity;
- =o_S= is the storage owner;
- =L_S= is the authorized maximum number of storage deferrals;
- =d= is the required capacity;
- the remaining coordinates bind the same recovery, epoch, and fence as the
  current recovery expectation.

The owner receipt carries one decision:

#+begin_src typst
$ delta_S in { "admitted", "deferred", "rejected" } $
#+end_src

and records reserved capacity =a= plus consumed and remaining deferrals.

The decision evidence is:

#+begin_src typst
$ delta_S = "admitted" => d <= a $
$ delta_S = "deferred" => a < d and 0 < n_S $
$ delta_S = "rejected" => op("terminal-fail-closed") $
#+end_src

The receipt also closes:

#+begin_src typst
$ c_S + n_S = L_S $
#+end_src

=rejected= is terminal evidence.  It is not a permission to retry forever.

* Storage-deferral transition

Only a receipt whose prior decision is =deferred= may construct a storage
deferral transition:

#+begin_src typst
$ delta_S = "deferred"
  and c_S' = c_S + 1
  and n_S = n_S' + 1
  => n_S' < n_S $
#+end_src

The publication, recovery, storage owner, runtime epoch, active fence, and
contract identity remain stable across the transition.

* Why the commit receipt cannot determine pre-commit admission

For one recovery expectation =E= and completion commit receipt =K=, Lean
constructs two candidate contracts with the same current-evidence projection:

#+begin_src typst
$ pi_S(C_S^0) = pi_S(C_S^1) = (r, u, o_S, e, f)
  and (L_S^0, d^0) = (0, 0)
  and (L_S^1, d^1) = (1, 1) $
#+end_src

Thus:

#+begin_src typst
$ op("CompletionCommitReceipt")(K)
  and op("RecoveryExpectation")(E)
  and op("does-not-entail")((L_S, d)) $
#+end_src

The existing =storageTransactionDigest= is post-commit evidence.  It is not a
pre-commit reservation, admission decision, capacity bound, or deferral
budget.

* Projection into the existing recovery progress algebra

45-120-31 already defines:

#+begin_src typst
$ B = (n_R, n_Q, n_S)
  and rho(B) = n_R + n_Q + n_S $
#+end_src

where the coordinates are remaining crashes, scheduling deferrals, and
storage deferrals.

A closed runtime-owner transition projects to:

#+begin_src typst
$ n_R' < n_R
  and n_Q' = n_Q
  and n_S' = n_S $
#+end_src

and constructs:

=SourceBoundEffectCompletionRecoveryProgressReceipt.crashBudgetDecreased=.

A closed storage-owner transition projects to:

#+begin_src typst
$ n_R' = n_R
  and n_Q' = n_Q
  and n_S' < n_S $
#+end_src

and constructs:

=SourceBoundEffectCompletionRecoveryProgressReceipt.storageDeferralDecreased=.

The new contracts do not introduce another convergence theorem.  They supply
two previously missing constructors to the existing proof algebra.

* Architecture boundary

The public/runtime architecture remains unchanged in this RFC:

- no runtime receipt implementation is added;
- no storage adapter API is added;
- no compatibility alias or migration surface is added;
- no watchdog or commit field is overloaded;
- no JSON type is added to the core proof model;
- no provider, Cedar, authority, or continuation evidence is promoted into a
  progress receipt;
- the proof model remains native Lean structures, inductives, and
  propositions.

An implementation RFC must identify the actual runtime owner and storage
owner before these proof-level contracts become runtime artifacts.

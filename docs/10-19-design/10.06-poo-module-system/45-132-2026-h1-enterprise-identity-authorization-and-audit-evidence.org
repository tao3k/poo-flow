* Why this catalog exists

Enterprise AI is not only a module/profile/workflow/knowledge composition
problem.  A safe enterprise composition must preserve principal identity,
delegated authority, tenant and organization scope, responsibility, audit
lineage, non-repudiation, and the lifecycle of the acting session.

* Candidate evidence

** ENT-ID-2026-001: GitHub agent control plane

- Date: 2026-02-26.
- Source kind/status: official GitHub release; generally available, with the MCP
  enterprise allowlist still in public preview.
- Source:
  [[https://github.blog/changelog/2026-02-26-enterprise-ai-controls-agent-control-plane-now-generally-available/][Enterprise AI Controls and agent control plane]].
- Reported claim: audit entries distinguish an agent and the user on whose behalf
  it acts; session events record start, finish, and failure; enterprise policy
  includes canonical custom-agent definitions and an MCP registry.
- Confidence boundary: this release note describes GitHub behavior; it is not a
  proof of audit completeness or of POO Flow behavior.
- Candidate obligations:
  - acting-agent identity and represented-principal identity must remain distinct;
  - every admitted session must end in a terminal lifecycle receipt;
  - canonical agent-definition identity must be version-bound;
  - MCP registry admission must not imply per-call authorization;
  - audit projection must preserve organization and enterprise scope.
- State: open.

** ENT-ID-2026-002: shared multi-agent platform

- Date: 2026-02-26.
- Source kind/status: official GitHub release.
- Source:
  [[https://github.blog/changelog/2026-02-26-claude-and-codex-now-available-for-copilot-business-pro-users/][Claude and Codex on the shared Copilot platform]].
- Reported claim: multiple agents share governance, context, memory, repository
  material, and centralized enablement/audit controls across surfaces.
- Confidence boundary: shared-platform availability does not establish
  noninterference between models, agents, repositories, users, or organizations.
- Candidate obligations:
  - model/provider identity is part of the session identity;
  - shared context and memory preserve tenant, principal, and repository labels;
  - enterprise enablement cannot be weakened by organization or repository scope;
  - draft artifact attribution retains the responsible agent and represented user.
- State: open.

** ENT-ID-2026-003: NIST identity and authorization concept paper

- Date: 2026-02-05.
- Source kind/status: NIST NCCoE concept paper; draft consultation artifact.
- Source:
  [[https://csrc.nist.gov/pubs/other/2026/02/05/accelerating-the-adoption-of-software-and-ai-agent/ipd][AI agent identity and authorization concept paper]].
- Reported claim: identification, authorization, auditing, non-repudiation, and
  prompt-injection controls are explicit open enterprise concerns.
- Confidence boundary: a concept paper identifies a standards problem; it does
  not choose or validate the POO Flow construction.
- Candidate obligations:
  - no action receipt exists without a stable acting principal;
  - delegation binds grantor, grantee, scope, purpose, time, and evidence;
  - an audit record is non-repudiable only when it binds decision and outcome;
  - injected content cannot create or enlarge a delegation.
- State: open.

** ENT-ID-2026-004: tenant endpoints and credential mutation

- Date: 2026-05-19.
- Source kind/status: official Dify release discussion.
- Source:
  [[https://github.com/langgenius/dify/discussions/36374][Dify v1.14.2 release notes]].
- Reported claim: the release strengthened tenant-scoped sensitive endpoints,
  restricted default tool-credential updates to workspace admins/owners, and
  cleaned stale tenant credentials during key reset.
- Confidence boundary: the release notes do not prove complete tenant isolation.
- Candidate obligations:
  - tenant-labelled assets are inaccessible outside the matching tenant;
  - credential mutation requires a role capability for that workspace;
  - key rotation revokes or migrates every dependent credential;
  - stale credential cleanup has a complete, auditable closure receipt.
- State: open; routed to the existing tenant/organization isolation family.

** ENT-ID-2026-005: approval-policy correspondence reports

- Dates: 2026-04-24 and 2026-05-22.
- Source kind/status: two open user reports in the OpenAI Codex repository.
- Sources:
  [[https://github.com/openai/codex/issues/19430][repeated approval for approved MCP tools]]
  and
  [[https://github.com/openai/codex/issues/24135][non-interactive MCP authorization and sandbox coupling]].
- Reported claim: the reporters observed approval settings that did not correspond
  to MCP runtime behavior; one report describes a broad sandbox bypass as the only
  successful path for a narrowly intended tool call.
- Confidence boundary: these are reproducible-looking issue reports, not an
  independently verified product conclusion.
- Candidate obligations:
  - policy projection and runtime admission agree for the same call identity;
  - a narrow capability never requires granting a strictly broader capability;
  - approval identity includes server, tool, arguments, sandbox, scope, and lifetime;
  - absence of an interactive approver fails closed without discarding the requested
    sandbox boundary.
- State: open.

* Mathematical obligations

#+begin_src typst
$ "ActsFor"(a, u, x) =>
  "AgentId"(a) != "PrincipalId"(u)
  and "Delegated"(u, a, "Scope"(x), "Purpose"(x), "Time"(x)) $

$ "Authorized"(x) =>
  "Tenant"("Subject"(x)) = "Tenant"("Resource"(x))
  and "OrganizationScope"(x) subset.eq "DelegatedScope"(x) $

$ "AuditComplete"(x) =>
  "Binds"(
    "Actor"(x),
    "RepresentedPrincipal"(x),
    "Decision"(x),
    "Outcome"(x),
    "Session"(x),
  ) $

$ "RequestedCapability"(x) subset.eq "GrantedCapability"(x) $

$ "Narrower"(x, y) and "Requested"(x) and not "Requested"(y)
  => not "ForcedGrant"(y) $

$ "InjectedContent"(c) => not "CanIssueDelegation"(c) $
#+end_src

The fourth formula is only a well-formedness bound.  The fifth states the safety
property: a request for a narrow capability must not force a broader grant.

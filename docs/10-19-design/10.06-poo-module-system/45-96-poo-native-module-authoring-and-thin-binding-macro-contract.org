#+title: POO-Native Module Authoring and Thin Binding Macro Contract

* Status

Accepted architecture RFC.

This document records the approved Module authoring boundary. It does not
authorize implementation work and does not freeze an unverified macro name.

* Scope

This RFC defines:

- the canonical POO-native construction of a semantic =Module=;
- the contract of one thin hygienic Module binding macro;
- the relationship between a source binding and stable Module identity;
- the ownership of exports, ProfileBundles, responsibilities, and imports;
- the separation between semantic Module authoring and Gerbil module loading;
- the evidence and admission requirements for a future implementation.

This RFC does not define:

- a new object system;
- a second Module representation;
- a public clause DSL;
- a global Module registry;
- an imperative module loader;
- runtime capability issuance;
- build-system or package-manager behavior;
- compatibility, migration, or deprecation behavior.

* Evidence state

Parser-owned ASP discovery currently identifies:

- =use-composition= as a macro owner in
  =src/module-system/profile-composition-use-syntax.ss=;
- =poo-flow-composition-module-binding= as an internal helper owner in
  =src/module-system/profile-composition-builders.ss=;
- composition accessors and builders as internal implementation surfaces;
- no emitted owner for =defmodule=, =define-module=, or =module!=.

The direct selector bridge from =use-composition= to
=poo-flow-composition-module-binding= is not proven. Exact selector queries for
both owners currently fail with the exact ASP diagnostic: =current source snapshot omitted exact-selector owner bytes=.

Therefore:

- the internal helper name is not adopted as a public API;
- the future macro name remains unassigned;
- current implementation structure is evidence of an owner frontier, not proof
  of the approved contract;
- implementation requires repaired exact-owner evidence.

* Central decision

There is one canonical semantic authoring path:

#+begin_example
POO Module expression
  -> stable Module object
  -> exported ProfileBundle values
  -> reachable responsibility and imports closure
#+end_example

A single bounded hygienic macro may bind that completed Module expression to a
Gerbil source identifier.

Conceptually, the macro has exactly this shape:

#+begin_example
module-binding-form := binding-identifier + Module-expression
#+end_example

The macro does not parse the contents of the Module expression. It does not
accept graph, loop, proof, handoff, stage, imports, capability, or export
clauses.

The Module expression is semantically complete before it reaches the binding
macro.

* Why the macro name is not frozen

No parser-owned evidence currently establishes an available public name among
=defmodule=, =define-module=, or =module!=.

This RFC assigns no Scheme identifier to the public macro. The phrase "binding
macro" names its architectural role, not its Scheme spelling.

Choosing a name without checking Gerbil, project, and dependency namespaces
would create avoidable ambiguity. This RFC therefore freezes the shape and
semantics, not the spelling.

Name selection is admitted only after:

- Gerbil core and standard library bindings are checked;
- the pinned =gerbil-poo= public surface is checked;
- the POO Flow project namespace is checked;
- macro expansion and diagnostic behavior are demonstrated;
- the name does not imply that the macro owns Gerbil module loading.

* Canonical Module expression

** POO ownership

The Module is a POO object. Its semantic identity, exports, imports, capability
requirements, and responsibility reachability belong to the object and its
prototype ancestry.

The binding macro does not manufacture a Module from raw clauses.

** Stable identity

The completed Module expression carries stable Module identity.

The source binding identifier is a hygienic reference to that object. It is not
silently substituted for the object's semantic identity.

An implementation may verify a declared relation between the binding identifier
and Module identity for diagnostics, but it may not overwrite or synthesize
identity behind the object's interface.

** Exports

A Module exports stable identities whose values satisfy the Profile operand
contract. Under the current approved model, =production= denotes a
module-scoped =ProfileBundle=.

Exports are POO-owned object structure. They are not entries in a hidden global
registry and are not keywords interpreted by the binding macro.

** Responsibilities

Graph, loop, proof, handoff, stage responsibility, and recursive imports are
reachable from exported Profiles or ProfileBundles as defined by
[[file:45-95-aggregate-profile-responsibility-projection-and-bounded-macro-boundary.org][45-95]].

The binding macro neither attaches nor interprets these objects.

* Thin binding macro contract

The future binding macro may perform only the following operations:

- validate its closed two-operand surface shape;
- introduce one hygienic source binding;
- evaluate the supplied Module expression exactly once;
- verify that the result satisfies the admitted Module interface;
- retain source identity for diagnostics and evidence;
- publish the binding through the owning Gerbil module when explicitly exported;
- expand to ordinary Gerbil binding and POO-native validation code.

It may not:

- parse a nested Module DSL;
- parse exports or imports;
- build ProfileBundles from clauses;
- interpret graph, loop, proof, handoff, or stage semantics;
- issue, widen, or attenuate capabilities;
- execute a runtime handoff;
- load Gerbil modules dynamically;
- register the Module in hidden mutable state;
- duplicate evaluation of the Module expression;
- change the Module object's stable identity;
- introduce a second composition wrapper;
- treat internal builder helpers as public semantic owners.

* One expression, one evaluation

The Module expression must be evaluated once.

This law protects:

- object identity;
- prototype ancestry;
- source-to-object correspondence;
- deterministic evidence projection;
- resource ownership;
- diagnostic blame.

A macro expansion that duplicates the expression is invalid even when the
expression is expected to be pure.

* Authoring and use are different surfaces

Module authors construct a complete POO object.

Composition users select an exported ProfileBundle:

#+begin_src scheme
(use-composition crewai-system
  (compose profiles
    (use-module crewai production)))
#+end_src

The ordinary composition form does not expose Module construction.

The authoring macro does not replace =use-module=, =use-composition=, =compose=,
or =profiles=:

- the Module binding macro binds one Module object;
- =use-module= selects a stable export from a Module;
- =compose= remains a pure function;
- =profiles= remains a first-class strategy;
- =use-composition= binds one completed composition expression.

* Semantic Module and Gerbil module separation

A POO Flow =Module= is a semantic POO object.

A Gerbil module is a compilation, namespace, import, and load boundary.

The binding macro may place a semantic Module object inside a Gerbil module, but
it does not merge the two concepts.

#+begin_src mermaid
flowchart LR
  Gerbil["Gerbil module"] -->|"owns namespace and compiled binding"| Binding["hygienic source binding"]
  Expression["complete POO Module expression"] -->|"evaluates exactly once"| Object["semantic Module object"]
  Binding -->|"references without replacing identity"| Object
  Object -->|"exports stable identity"| Bundle["production ProfileBundle"]
  Bundle -->|"retains reachable semantics"| Responsibilities["responsibility objects"]
  Responsibilities -->|"contribute selected dependencies"| Imports["recursive imports closure"]
  Imports -->|"projects physical dependencies"| Loader["Gerbil import and load backend"]
#+end_src

The backend projection may cause Gerbil loading. The semantic binding macro does
not own that effect.

* Module construction layers

** Ordinary authoring

An ordinary Module author may use a constrained constructor surface after that
surface is proven to expand to canonical POO object construction.

The constructor may reduce repetition, but its result must be an inspectable
Module object before binding.

** Advanced authoring

Advanced authoring uses =gerbil-poo= objects, prototype composition, slot
operators, and object extension helpers directly.

This is the unique semantic extension path.

** Internal generation

Project-owned macros may generate repeated internal object families. They must
remain bounded, hygienic, and transparent. Generated objects retain stable
identity and source correspondence.

No internal generation helper becomes public merely because current code uses
it.

* Current helper boundary

The following names are current implementation evidence, not approved public
Module authoring APIs:

- =poo-flow-composition-module-binding=;
- =poo-flow-composition-profile-binding=;
- =poo-flow-composition-object/profile-bindings=;
- =poo-flow-composition-modules=;
- =poo-flow-composition-profiles=;
- =poo-flow-composition-stages=;
- =poo-flow-composition-stage-clauses=.

Their current alist, clause, or staging assumptions do not constrain the new
architecture.

Any future implementation may reuse, replace, or delete internal helpers after
the public POO contract is satisfied. That decision is outside this RFC.

* Binding and identity laws

** Binding reference law

The source binding refers to the Module object without redefining Module
identity.

** Single evaluation law

The Module expression is evaluated exactly once.

** POO completeness law

The bound value already satisfies the complete POO Module contract before any
consumer selects an export.

** Export stability law

Each exported identity resolves through the bound Module object to one declared
Profile operand in the current Module version.

** Responsibility preservation law

Binding cannot add, remove, or reinterpret any responsibility reachable from an
exported ProfileBundle.

** Imports preservation law

Binding cannot add, remove, or flatten the recursive POO-owned imports
structure.

** Authority neutrality law

Binding a Module object grants no capability and satisfies no admission
requirement.

** Expansion transparency law

Replacing the binding macro with its ordinary hygienic expansion preserves
Module identity, exports, reachability, evidence, and authority.

** Namespace separation law

The Gerbil source identifier, Gerbil module identity, POO Module identity, and
optional Module instance identity remain distinguishable.

* Authoring projection

#+begin_src mermaid
sequenceDiagram
  participant Author as "Module author"
  participant POO as "POO construction"
  participant Macro as "thin binding macro"
  participant Gerbil as "Gerbil namespace"
  participant User as "use-module"

  Author->>POO: "constructs complete Module value"
  POO-->>Macro: "returns stable POO object"
  Macro->>Macro: "validates closed shape and Module interface"
  Macro->>Gerbil: "introduces one hygienic binding"
  Gerbil-->>User: "exposes bound Module reference"
  User->>POO: "selects one stable ProfileBundle export"
  POO-->>User: "returns value plus projection evidence"
#+end_src

No participant between POO construction and Module selection owns a second
semantic representation.

* Error behavior

The binding form fails closed when:

- its surface shape is not exactly one identifier and one expression;
- the binding identifier is invalid or conflicts in the lexical context;
- the expression does not yield an admitted Module object;
- the Module object lacks stable identity;
- export identity is malformed or duplicated;
- an exported value does not satisfy the Profile operand contract;
- the Module expression cannot be evaluated exactly once;
- a constructor expansion hides raw mutable registry state;
- source-to-object evidence cannot be retained.

An error must identify:

- the source binding;
- the source expression;
- the observed object kind;
- the expected Module interface;
- the relevant Module or export identity when available;
- the owning macro expansion site.

The macro must not turn a semantic validation failure into a generic syntax
error.

* Evidence projection

A successful binding receipt must identify at least:

- the macro owner and version;
- the Gerbil module owner;
- the hygienic source binding identity;
- the source expression identity;
- the bound POO Module identity and version;
- the prototype ancestry or admitted Module interface identity;
- the exported identity set;
- the ProfileBundle identities reachable through those exports;
- the recursive imports projection identity;
- confirmation that the expression was evaluated once;
- confirmation that binding added no authority.

The receipt records binding. It does not prove Profile responsibilities or grant
runtime admission.

* Rejected alternatives

The following alternatives are rejected:

- a =module!= keyword DSL copied from another ecosystem;
- selecting =defmodule= or =define-module= before namespace evidence exists;
- giving the binding macro graph, loop, proof, handoff, or stage clauses;
- deriving semantic Module identity solely from the source binding;
- letting the macro build exports through a hidden registry;
- treating Gerbil module loading as POO Module semantics;
- exposing current composition builder helpers as the new public API;
- accepting raw alists or records as the ordinary Module authoring interface;
- nesting =use-composition= inside Module authoring;
- adding a compatibility wrapper around the rejected clause architecture.

* Conformance checklist

** Canonical authoring

- [ ] A Module is constructed as a POO object.
- [ ] The Module expression is complete before binding.
- [ ] The Module carries stable semantic identity.
- [ ] Exports are POO-owned structure.
- [ ] Each exported value satisfies the Profile operand contract.
- [ ] =production= denotes a module-scoped ProfileBundle.
- [ ] Responsibilities remain reachable from exported values.
- [ ] Recursive imports remain POO-owned.

** Thin macro

- [ ] The macro accepts one binding identifier and one Module expression.
- [ ] The macro evaluates the expression exactly once.
- [ ] The macro introduces one hygienic binding.
- [ ] The macro validates the admitted Module interface.
- [ ] The macro retains source identity.
- [ ] The macro does not parse Module internals.
- [ ] The macro does not create ProfileBundles from clauses.
- [ ] The macro does not interpret responsibilities.
- [ ] The macro does not issue capabilities.
- [ ] The macro does not load Gerbil modules.
- [ ] The macro does not maintain hidden mutable state.
- [ ] The macro expansion is semantically transparent.

** Identity and namespace

- [ ] Source binding and POO Module identity remain distinct.
- [ ] Gerbil module and POO Module identity remain distinct.
- [ ] Optional Module instance identity remains distinct.
- [ ] Binding cannot overwrite semantic identity.
- [ ] Binding cannot alter exports.
- [ ] Binding cannot alter responsibility reachability.
- [ ] Binding cannot alter imports.
- [ ] Binding grants no authority.

** Public surface

- [ ] No public macro name is frozen without namespace evidence.
- [ ] Current internal helper names remain internal.
- [ ] =use-module= remains the selection interface.
- [ ] =compose= remains a pure function.
- [ ] =profiles= remains a first-class strategy.
- [ ] =use-composition= remains the composition binding interface.
- [ ] Advanced extension remains POO-native.
- [ ] No parallel clause DSL is introduced.

** Evidence and failure

- [ ] Binding success produces an identity receipt.
- [ ] The receipt identifies the macro owner.
- [ ] The receipt identifies the Gerbil module owner.
- [ ] The receipt identifies the bound Module object.
- [ ] The receipt confirms single evaluation.
- [ ] The receipt confirms authority neutrality.
- [ ] Invalid Module values fail closed.
- [ ] Failures name the binding and observed object kind.

* Implementation admission gates

Implementation work is not admitted until:

- [ ] exact selector owner bytes are available for =use-composition=;
- [ ] exact selector owner bytes are available for
  =poo-flow-composition-module-binding=;
- [ ] the current bridge between those owners is proven or rejected;
- [ ] the pinned =gerbil-poo= public primitives are cited by exact identity;
- [ ] Module object construction is mapped to verified POO primitives;
- [ ] the future macro name passes namespace collision checks;
- [ ] the macro expansion is shown as ordinary Gerbil and POO-native code;
- [ ] single-evaluation behavior has a focused test;
- [ ] Module-kind validation has a focused test;
- [ ] source-to-object identity projection has a focused test;
- [ ] authority neutrality has a focused test;
- [ ] no clause parser is reachable from the new binding surface;
- [ ] the RFC set is reviewed before implementation begins.

* Consequences

Module authoring has one semantic truth: a complete POO object.

The macro surface stays small because the binding macro binds a value rather
than interpreting an architecture.

Ordinary composition remains concise, while advanced authors retain the full
power of prototype composition and POO-native extension.

Current implementation helpers remain free to change because they do not define
the public architecture.

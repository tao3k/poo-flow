* Status

Accepted architecture.

This RFC freezes the documented Gerbil and Gambit runtime correspondence for
the semantics owned by
[[file:45-87-live-continuation-capabilities-continuable-conditions-and-portable-suspension-boundary.org][45-87]].
It does not authorize implementation until the executable verification
checklists in this document are complete.

evidence required before implementation admission.  It does not assert that
the pending executable probes have already observed these behaviors.

* Scope

This document owns only the correspondence between:

- the POO Flow control semantics accepted in 45-87; and
- the continuation, condition-handler, catcher, and dynamic-extent primitives
  documented by Gerbil and Gambit.

It does not own:

- Profile composition;
- the native POO value domain;
- portable suspension descriptor contents;
- distributed demand transport;
- cache identity;
- package management; or
- a new exception or continuation subsystem.

The POO Flow public surface remains POO-native.  The primitives named here are
runtime implementation mechanisms, not a user-facing macro language.

* Central decision

POO Flow shall use the runtime primitives according to their actual control
semantics:

| POO Flow purpose | Documented runtime primitive | Required interpretation |
|------------------+------------------------------+-------------------------|
| capture a current execution point | ~call-with-current-continuation~ or Gerbil ~let/cc~ | create a process-local live continuation only |
| signal an intentionally continuable control condition | ~with-exception-handler~ and ~raise~ | a returning handler may continue the continuation of ~raise~ |
| reject continuation | ~abort~ | the original signal point is noncontinuable |
| transfer control to a catcher boundary | ~with-exception-catcher~ or Gerbil ~with-catch~ | unwind to the catcher boundary; do not model in-place resumption |
| protect dynamic exit | ~dynamic-wind~ or Gerbil ~with-unwind-protect~ | run dynamic-extent entry and exit actions under continuation transfer |
| capture diagnostic stack context | Gerbil ~:std/error~ ~StackTrace~ support | produce debugging evidence only |

The following non-correspondences are normative:

- ~with-catch~ is not a resumable safe point.
- ~with-exception-catcher~ is not a continuable handler.
- a StackTrace continuation is not a resumption capability.
- a raw continuation is not a portable suspension descriptor.
- a returning handler is not authority to resume.
- a runtime-permitted continuation invocation is not automatically admitted by
  the POO Flow capability policy.

* Documented runtime basis

** Gambit continuable and noncontinuable signaling

The Gambit exception model distinguishes two operations:

- ~raise~ invokes the current exception handler.  If the handler returns, the
  continuation of the ~raise~ call is invoked with the handler result.
- ~abort~ invokes the current exception handler as a noncontinuable signal.  A
  handler that returns cannot resume the original signal point.

~with-exception-handler~ installs the handler in the dynamic environment of
its thunk.  ~with-exception-catcher~ instead gives its handler the continuation
of the catcher call and therefore transfers control to that boundary.

The runtime correspondence consequently assigns continuable safe-point
signaling to ~with-exception-handler~ plus ~raise~, and boundary rejection to
~abort~ or a catcher.

** Gerbil catcher and cleanup conveniences

Gerbil documents ~with-catch~ as a catcher-style control boundary and
~with-unwind-protect~ as a cleanup facility for dynamic exit.

These conveniences may be used at evaluator boundaries, but ~with-catch~ must
not replace the continuable handler required at a resumable safe point.

** Gerbil diagnostic continuation capture

Gerbil ~:std/error~ documents StackTrace support that captures continuation
context for error reporting and backtraces.

That captured context belongs exclusively to the evidence plane.  It must not
be wrapped, exported, cached, delegated, or invoked as a POO Flow resumption
capability.

* Control-flow correspondence

flowchart LR
  D["Native POO demand"] -->|"enters an admitted local safe point"| H["with-exception-handler"]
  H -->|"ordinary evaluation returns a native result"| R["Native POO result"]
  H -->|"raise communicates a continuable control condition"| C["Control handler"]
  C -->|"allow returns under the same fenced dynamic context"| H
  C -->|"suspend captures local authority and projects pure metadata"| P["Portable suspension descriptor"]
  C -->|"deny, cancel, stale fence, or invalid authority invokes abort"| B["Noncontinuable boundary"]
  B -->|"with-catch records the terminal control receipt"| E["Evidence plane"]
  P -->|"coordinator later validates a distinct resumption capability"| N["New admitted demand"]
  N -->|"checkpoint or replay reconstructs a new local safe point"| H
#+end_src

This graph does not contain a remote or persistent edge back to the live
continuation.  Portable resumption constructs a new admitted local execution
context.

* Capability fence over raw continuations

A raw continuation has broader operational power than POO Flow shall expose.
The runtime layer must therefore place a POO-native capability fence around
every admitted live continuation.

The fence binds at least:

- evaluator identity;
- process identity;
- thread or worker identity;
- root identity;
- revision and generation;
- demand identity;
- dynamic-context identity;
- safe-point identity;
- lifetime and revocation state; and
- one-shot consumption state.

Even when the underlying runtime permits another invocation pattern, the
capability check remains authoritative.  In particular:

- live resumption is one-shot by default;
- cross-thread invocation is denied by default;
- cross-process invocation is impossible through the live capability;
- a stale root or generation creates a new demand rather than a resumption;
  and
- branching evaluation requires explicitly distinct demands, not repeated
  invocation of one continuation.

* Dynamic-wind discipline

Continuation transfer can leave and later re-enter dynamic extents.
~dynamic-wind~ before and after thunks can therefore run more than once across
the lifetime of a captured continuation.

Safe-point dynamic extents must obey all of the following:

- winders are limited to idempotent resource acquisition and release, or pure
  control bookkeeping;
- a winder must not commit an externally visible domain effect;
- a portable descriptor must not conceal an unresolved external effect;
- evidence emission must be idempotent or keyed by stable event identity; and
- one-shot capability consumption must be independent of cleanup repetition.

#+begin_src mermaid
sequenceDiagram
  participant E as "Evaluator"
  participant W as "dynamic-wind region"
  participant H as "Continuable handler"
  participant K as "One-shot capability fence"
  E->>W: enter under an admitted safe point
  W->>H: raise a control condition
  H->>K: request local resumption
  K-->>H: allow once under matching fences
  H-->>W: return to the raise continuation
  W-->>E: complete native evaluation
  H->>K: request the same resumption again
  K-->>H: deny because the capability is consumed
  H-->>E: abort to the terminal control boundary
#+end_src

* Handler re-entry discipline

The current exception handler remains part of the dynamic environment.
Blindly raising from inside that same handler can re-enter the handler or form
an unbounded control loop.

An implementation must make one of the following choices explicit:

- return a validated continuable decision;
- transfer a noncontinuable rejection with ~abort~;
- delegate to a proven outer handler; or
- use an internal re-entry fence before signaling again.

No handler may synthesize a Profile value merely to escape the control
protocol.  Native recovery values remain subject to the native POO value-domain
admission described by the Profile RFCs.

* POO-native public boundary

The exact POO object algebra for conditions, decisions, capabilities, and
resumption admission is owned by
[[file:45-89-poo-native-control-condition-decision-and-capability-algebra.org][45-89]].
This document owns only their projection onto Gerbil and Gambit runtime
primitives.

The public interface exposes POO objects for:

- control conditions;
- live continuation capabilities;
- portable suspension descriptors;
- resumption capabilities;
- fence identities; and
- control receipts.

It does not expose:

- raw continuation procedures;
- exception-handler installation clauses;
- runtime catcher tokens;
- mutable registries;
- raw record or alist protocols; or
- a macro DSL that mirrors Gambit exception syntax.

Public Gerbil macros may provide a small hygienic projection only when their
expansion is constrained by the POO objects above.  Advanced extension remains
ordinary POO object and prototype extension.

* Implementation import boundary

Gerbil can expose core Gambit primitives while ~:std/error~ also supplies
error-reporting behavior around raising and StackTrace capture.  Implementation
must not select a binding by name alone.

Before implementation, an executable probe must freeze:

- the exact imported binding for ~with-exception-handler~;
- the exact imported binding and behavior for continuable ~raise~;
- the exact imported binding and behavior for ~abort~;
- the relationship between Gerbil ~with-catch~ and Gambit
  ~with-exception-catcher~;
- the behavior of ~dynamic-wind~ and ~with-unwind-protect~ under continuation
  re-entry; and
- the separation between ~:std/error~ StackTrace capture and control-plane
  continuation capture.

The probe receipt must record Gerbil version, Gambit version, imports, expanded
binding identities where available, command, exit status, and observed control
trace.

* Required executable probes

These are implementation-admission tests, not new POO proofs.

** Continuable signal probe

- [ ] Install a handler with the exact Gerbil-visible
  ~with-exception-handler~ binding.
- [ ] Signal with the exact Gerbil-visible ~raise~ binding.
- [ ] Return a sentinel decision from the handler.
- [ ] Prove that execution continues immediately after the signal point.
- [ ] Record the ordered control trace.

** Noncontinuable signal probe

- [ ] Signal through the exact ~abort~ binding.
- [ ] Attempt to return from the handler.
- [ ] Prove that the original signal point is not resumed.
- [ ] Record the terminal condition and control trace.

** Catcher-boundary probe

- [ ] Exercise Gerbil ~with-catch~.
- [ ] Exercise Gambit ~with-exception-catcher~ through the selected import
  boundary.
- [ ] Prove that both tested paths transfer to a catcher boundary rather than
  resume immediately after the signal point.

** Dynamic-extent probe

- [ ] Capture a continuation inside ~dynamic-wind~.
- [ ] Leave and re-enter the dynamic extent.
- [ ] Record every before and after invocation in order.
- [ ] Repeat with Gerbil ~with-unwind-protect~ where its contract applies.
- [ ] Prove that cleanup policy remains correct when an action is repeated.

** Capability-fence probe

- [ ] Wrap the live continuation in a one-shot POO capability.
- [ ] Resume once under matching evaluator, process, root, revision,
  generation, demand, and safe-point fences.
- [ ] Deny a second invocation.
- [ ] Deny a mismatched thread or worker invocation.
- [ ] Deny stale revision and generation invocations.
- [ ] Prove that each denial reaches the noncontinuable control boundary.

** Diagnostic-separation probe

- [ ] Raise an error with Gerbil ~:std/error~ StackTrace support.
- [ ] Record the diagnostic continuation or backtrace evidence.
- [ ] Prove that no resumption capability is constructed from it.
- [ ] Prove that the diagnostic evidence is never admitted as a Profile
  operand, cache value, or distributed demand field.

* Admission criteria

Implementation may begin only when:

- [ ] the exact Gerbil and Gambit versions are recorded;
- [ ] every required primitive resolves through an explicit import;
- [ ] continuable, noncontinuable, and catcher traces match this RFC;
- [ ] dynamic-extent repetition is demonstrated;
- [ ] one-shot, thread, process, root, revision, generation, demand, and
  safe-point fences fail closed;
- [ ] StackTrace evidence is proven separate from resumption authority;
- [ ] the public surface contains only POO-native objects or constrained
  hygienic projections; and
- [ ] the full correspondence preserves the conservative-extension obligations
  in
  [[file:45-86-poo-conservative-extension-criterion-and-cross-module-obligations.org][45-86]].

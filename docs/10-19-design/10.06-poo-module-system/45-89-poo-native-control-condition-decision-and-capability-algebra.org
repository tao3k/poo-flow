#+title: POO-Native Control Condition, Decision, and Capability Algebra
#+startup: overview

* Status

Accepted architecture.

This RFC freezes the POO-native object algebra above the continuation and
condition runtime correspondence in
[[file:45-88-gerbil-gambit-continuation-and-condition-runtime-correspondence.org][45-88]].
It does not freeze unverified Gerbil call forms and does not authorize runtime
implementation before the admission checks in this document are complete.

* Formal POO control algebra

The formal surface keeps the condition family open while closing terminal
control effects to four constructors.

#+begin_src typst
#let TerminalEffect = (
  continue: "Continue",
  suspend: "Suspend",
  deny: "Deny",
  cancel: "Cancel",
)

#let handler-transition = effect => {
  if effect == TerminalEffect.continue {
    "normal-return"
  } else {
    "noncontinuable-boundary"
  }
}

$ "handler-transition"("Continue") = "normal-return" $
$ "handler-transition"("Suspend") = "noncontinuable-boundary" $
$ "handler-transition"("Deny") = "noncontinuable-boundary" $
$ "handler-transition"("Cancel") = "noncontinuable-boundary" $

$ "Resume" notin TerminalEffect $
#+end_src

Resume is later coordinator admission, not a fifth handler result.  Every
admitted decision contains exactly one terminal effect, and prototype
precedence cannot resolve a multiple-effect conflict.

#let attenuates = "attenuates"

$ attenuates(parent, child) :=
  forall effect,
    allowed(child, effect) arrow.r allowed(parent, effect) $

$ allowed(compose(a, b), effect) =
  (allowed(a, effect) and allowed(b, effect)) $

$ "child-authority" subset.eq "parent-authority" $
$ "object-shape" != "authority" $
$ "descriptor" != "live-capability" $
$ "receipt" != "authority" $
$ "decision" != "Profile-value" $

Capability composition is intersection and extension is attenuation-only.  An
issuer witness and evaluator-owned one-shot cell remain necessary even when an
object has the same visible slot shape as a capability.

* Scope

This document owns:

- the POO object families for control conditions, local control decisions, and
  control capabilities;
- the identity relationships among those objects;
- the only legal result paths from a continuable handler;
- capability attenuation and one-shot authority;
- the boundary between open prototype extension and closed control effects;
  and
- the exclusion of control objects from the native Profile value domain.

It does not own:

- raw continuation capture;
- exception-handler installation;
- portable suspension descriptor reconstruction;
- distributed evaluator transport;
- Profile composition;
- native POO evaluation;
- cache identity; or
- package installation.

The names used for object families in this RFC are project semantic names.
They are not claims that ~gerbil-poo~ exports objects with those names.

* Central decision

The control protocol consists of three distinct POO object families:

1. a ~ControlCondition~ describes why evaluation reached an admitted control
   point;
2. a ~ControlDecision~ authorizes exactly one local control effect for that
   condition; and
3. a ~ControlCapability~ proves that the deciding principal may authorize that
   effect under the current fences.

All three are immutable POO objects.  Their public extension mechanism is
prototype composition and object extension governed by the native
~gerbil-poo~ semantics adopted in
[[file:45-85-poof-proof-adoption-and-poo-flow-correspondence-obligations.org][45-85]].

The control protocol shall not be represented as:

- symbols interpreted by ~case~;
- raw alists or records;
- mutable registry entries;
- exception message strings;
- a host-language conditional embedded in Profile composition;
- runtime tokens exposed to users; or
- an open macro DSL.

* Open conditions and closed control effects

The condition family is open to higher-order prototype extension.  A domain
may add a more precise condition prototype, evidence, or capability
requirement.

The terminal control-effect family is closed to four effects:

- continue the current admitted local evaluation;
- suspend it and project a portable descriptor;
- deny the requested continuation; or
- cancel the current demand.

A decision prototype may be extended with evidence and stricter policy, but it
must refine exactly one terminal effect.  Prototype composition must not create
a fifth control-transfer effect.

This division keeps domain description extensible while keeping continuation
authority auditable.

* Control context identity

Every condition, decision, and live capability refers to one
~ControlContextIdentity~ POO object.  The identity binds:

- evaluator identity;
- process identity;
- thread or worker identity;
- root identity;
- revision;
- generation;
- demand identity;
- safe-point identity; and
- dynamic-context identity.

The identity is not reconstructed from a collection of user-provided strings.
It is issued by the admitted evaluator boundary and carries an issuer witness.

A portable suspension descriptor projects only the pure semantic identity
required by 45-87.  It never projects the process-local continuation, dynamic
context, thread authority, or issuer witness.

* ControlCondition prototype family

** Base obligations

Every admitted condition object preserves:

- the control-context identity;
- a stable condition identity;
- the originating safe point;
- pure reason evidence;
- the capability class required to decide it; and
- the native POO demand to which it belongs.

A condition does not contain:

- a raw continuation procedure;
- a mutable handler;
- a Profile result;
- a portable resumption capability;
- an unresolved external effect; or
- implicit authority derived from its object shape.

** Extensible condition prototypes

Examples of valid condition refinements include:

- budget exhaustion;
- cycle observation;
- explicit suspension request;
- missing control authority;
- stale revision or generation;
- checkpoint requirement; and
- operator-intervention requirement.

These are prototype refinements, not members of a closed enumeration.
Additional refinements may contribute evidence or require a narrower
capability, but they cannot weaken the base identity fence.

** Condition extension law

For a base condition ~C~ and an admitted prototype refinement ~P~:

- the extension preserves the identity of ~C~;
- the extension may add evidence;
- the extension may require stronger authority;
- the extension may not acquire authority;
- the extension may not erase an existing denial reason; and
- erasing the added evidence yields the original control observation.

* Local ControlDecision prototype family

Composition of multiple POO policies into one admitted ControlDecision is
owned by
[[file:45-90-poo-control-policy-composition-priority-conflict-and-veto-resolution.org][45-90]].
This section owns the final decision algebra, not multi-policy resolution.

** ContinueDecision

A ContinueDecision authorizes the current local evaluation to continue at the
same safe point.

It must:

- bind the exact condition identity;
- bind a matching live capability;
- preserve evaluator, process, thread, root, revision, generation, demand,
  safe-point, and dynamic-context fences;
- consume the one-shot authorization; and
- carry no Profile result.

This is the only local decision whose validated application permits the
installed exception handler to return normally to the continuation of
~raise~.

** SuspendDecision

A SuspendDecision authorizes projection of a pure portable suspension
descriptor.

It must:

- bind the exact condition identity;
- prove suspension authority;
- select an admitted portable safe point;
- prove that no unresolved external effect crosses the boundary;
- emit a suspension receipt; and
- terminate the current local evaluation through the noncontinuable boundary.

The handler must not return a SuspendDecision to the continuation of ~raise~.

** DenyDecision

A DenyDecision records that continuation or suspension is not authorized.

It must preserve the native failure/control distinction, emit an actionable
receipt, and terminate through the noncontinuable boundary.  It cannot replace
the rejection with a default Profile value.

** CancelDecision

A CancelDecision revokes the current demand under explicit cancellation
authority.

It emits a cancellation receipt and terminates through the noncontinuable
boundary.  Cancellation does not fabricate native POO failure and does not
silently become suspension.

** Resume is not a local handler decision

The word "resume" in the cross-module control model denotes coordinator
admission of a later demand.

A ~ResumptionAdmission~ is therefore a separate POO object family.  It
validates a portable descriptor and a resumption capability, then constructs a
new admitted local demand.  It is never returned by the handler that observed
the original condition.

* Handler contract

The runtime handler is an adapter between POO objects and the documented
Gambit control primitives.  Its semantic sequence is:

1. receive a ~ControlCondition~;
2. obtain one POO-native ~ControlDecision~ from the authorized controller;
3. validate decision identity, capability, and terminal-effect uniqueness;
4. apply the terminal control effect; and
5. emit the corresponding evidence receipt.

Only a validated ContinueDecision reaches normal handler return.
SuspendDecision, DenyDecision, and CancelDecision reach ~abort~ after their
required projections and receipts.

#+begin_src mermaid
flowchart TD
  C["ControlCondition arrives at the handler adapter"] -->|"POO controller evaluates identity and policy"| D["One ControlDecision object"]
  D -->|"prototype refines Continue and all live fences match"| V["Consume one-shot capability"]
  V -->|"validated handler return continues immediately after raise"| E["Continue native evaluation"]
  D -->|"prototype refines Suspend and safe-point projection succeeds"| S["Create pure suspension descriptor"]
  S -->|"receipt is complete, then abort unwinds"| B["Suspended boundary outcome"]
  D -->|"prototype refines Deny"| N["Emit denial receipt"]
  N -->|"abort prevents implicit recovery"| F["Denied boundary outcome"]
  D -->|"prototype refines Cancel"| K["Emit cancellation receipt"]
  K -->|"abort ends the current demand"| Z["Cancelled boundary outcome"]
  D -->|"zero or multiple terminal effects are present"| Q["Reject malformed decision"]
  Q -->|"abort fails closed with an algebra-admission receipt"| F
#+end_src

The public POO surface does not expose a raw handler callback.  Internal
functional helpers may implement this adapter, but raw
~(lambda (self super) ...)~ hooks are not the ordinary extension interface.

* Decision return-value discipline

Under Gambit semantics, the value returned by a continuable exception handler
becomes the value of ~raise~.  POO Flow must prevent that mechanism from
smuggling a control object into native evaluation.

The safe-point helper therefore owns the result of ~raise~:

- it accepts only a validated ContinueDecision acknowledgment;
- it consumes and discards that acknowledgment inside the control boundary;
- it exposes no decision value to the native Profile computation; and
- it continues the already-admitted POO demand without manufacturing a result.

No condition handler may return:

- a Profile object;
- an arbitrary domain value;
- a suspension descriptor;
- a raw continuation;
- an unvalidated capability; or
- a decision for another condition identity.

* ControlCapability algebra

** Authority is not object shape

A user-created object that resembles a capability has no authority.
Authority requires an evaluator-issued witness validated at the explicit
runtime boundary.

The capability remains a POO object, but its witness is opaque and
unforgeable.  One-shot consumption state belongs to an evaluator-owned runtime
cell behind the explicit effect boundary, not to a mutable global registry.

** Attenuation law

Prototype or object extension may attenuate authority by adding:

- a shorter lifetime;
- a narrower safe-point set;
- a smaller budget;
- a stricter root or generation fence;
- a narrower terminal-effect set; or
- an additional principal or governance requirement.

Extension may not:

- create a new issuer witness;
- expand the admitted terminal-effect set;
- remove revocation;
- lengthen expiry;
- replace one-shot authority with reusable authority;
- relax identity fences; or
- turn a portable descriptor into live authority.

** Composition law

When capability constraints are composed, effective authority is their
intersection.  Native POO slot precedence must not be used to overwrite a
stricter security constraint with a weaker one.

A composition whose constraints cannot be proven as an attenuation is rejected
at capability admission.  Rejection is a control-plane outcome, not a native
POO failure.

* Decision prototype admission

Every decision object must satisfy:

- exactly one terminal-effect prototype is present;
- the condition identity matches;
- the capability witness is valid;
- all capability constraints admit that effect;
- the capability is live and unconsumed;
- the issuer and deciding principal are admitted;
- evidence slots are pure and bounded; and
- no Profile value or raw continuation is present.

Composing ContinueDecision with SuspendDecision, DenyDecision, or
CancelDecision is invalid.  Prototype precedence cannot resolve this conflict
because terminal-effect uniqueness is a semantic invariant, not an ordinary
slot override.

* Higher-order POO extension

Advanced users may define higher-order prototypes that:

- refine a condition with domain evidence;
- attenuate a capability;
- attach additional proof obligations to a decision;
- project additional pure evidence into a receipt; or
- provide a new policy object that selects among the four terminal effects.

Every extension remains reducible to ordinary ~gerbil-poo~ prototype
composition and object instantiation.  Project macros may generate repetitive
object families only when their expansions are bounded, hygienic, inspectable,
and entirely POO-native.

The following remain forbidden:

- a macro clause for each control effect;
- hidden registration of condition kinds;
- symbol dispatch over decision tags;
- mutation of a capability object to amplify authority;
- a second prototype evaluator; and
- an independent fixed-point implementation.

* Cross-plane ownership

| Plane | Owned object or transition | Prohibited responsibility |
|-------+----------------------------+----------------------------|
| native POO semantic plane | current demand and native result/failure | interpreting control receipts as domain values |
| control plane | conditions, decisions, capabilities, and terminal control application | manufacturing Profile results |
| evidence plane | immutable receipts and bounded diagnostic evidence | owning live authority or forcing POO slots |

The conservative-extension obligations remain owned by
[[file:45-86-poo-conservative-extension-criterion-and-cross-module-obligations.org][45-86]].
The live/portable boundary remains owned by
[[file:45-87-live-continuation-capabilities-continuable-conditions-and-portable-suspension-boundary.org][45-87]].
The Gerbil/Gambit primitive correspondence remains owned by 45-88.

45-85 has already adopted the fixed ~gerbil-poo~ implementation as the only

* Required algebra tests

** Condition tests

- [ ] Prove that condition refinement preserves control-context identity.
- [ ] Prove that added evidence erases to the base condition.
- [ ] Reject an extension that weakens a capability requirement.
- [ ] Reject a condition containing a raw continuation.
- [ ] Reject a condition containing a Profile result.

** Decision tests

- [ ] Admit exactly one ContinueDecision terminal effect.
- [ ] Admit exactly one SuspendDecision terminal effect.
- [ ] Admit exactly one DenyDecision terminal effect.
- [ ] Admit exactly one CancelDecision terminal effect.
- [ ] Reject a decision with zero terminal effects.
- [ ] Reject a decision with multiple terminal effects.
- [ ] Reject a decision bound to another condition identity.
- [ ] Prove that prototype precedence cannot hide a terminal-effect conflict.

** Handler tests

- [ ] Prove that only ContinueDecision permits normal handler return.
- [ ] Prove that the safe-point helper consumes and discards the handler
  acknowledgment.
- [ ] Prove that no ControlDecision reaches the native Profile value domain.
- [ ] Prove that SuspendDecision projects a pure descriptor before ~abort~.
- [ ] Prove that DenyDecision and CancelDecision terminate through ~abort~.
- [ ] Reject handler re-entry with an already active condition identity.

** Capability tests

- [ ] Reject a structurally similar object without an issuer witness.
- [ ] Admit an authority-attenuating prototype extension.
- [ ] Reject an authority-amplifying prototype extension.
- [ ] Prove that composed constraints form an intersection.
- [ ] Consume live authority exactly once.
- [ ] Reject expired, revoked, stale, cross-thread, and cross-process authority.
- [ ] Prove that a portable descriptor carries no live witness.

** Cross-plane tests

- [ ] Prove that observers do not force additional native POO slots.
- [ ] Prove that evidence recording does not change the terminal effect.
- [ ] Prove that a control rejection remains distinct from native POO failure.
- [ ] Prove erasure to the native result or failure for every completed allowed
  execution.

* Admission criteria

Implementation may begin only when:

- [ ] exact fixed-commit ~gerbil-poo~ call forms are recorded;
- [ ] the three base object families are ordinary POO objects;
- [ ] condition extension is open without weakening identity or authority;
- [ ] the four terminal effects are closed and mutually exclusive;
- [ ] Resume is implemented as later coordinator admission, not handler return;
- [ ] capability composition is attenuation-only;
- [ ] one-shot state has no mutable global registry;
- [ ] handler return cannot inject a Profile value;
- [ ] every non-Continue decision fails closed through the noncontinuable
  boundary;
- [ ] Mermaid transitions match executable control traces; and
- [ ] the 45-86, 45-87, and 45-88 obligations remain satisfied.

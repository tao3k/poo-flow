#+title: Effect Boundary Commit And Reconciliation

* Normative responsibility

This module owns the POO Flow semantics for externally effectful realization
boundaries:

- evidence states before and after an effect attempt;
- proof requirements for commit, failure, and cancellation;
- policy-authorized retry and reconciliation;
- continuation re-entry after an effect has started or committed;
- immutable receipts that govern later realization and admission.

It does not define a generic transaction manager.  It does not add syntax to
=user-composition=, Profile, or Mix declarations.

* Ownership boundary: gerbil-poo mechanism and POO Flow governance

=gerbil-poo= remains the sole Scheme POO implementation and owns generic POO
identity, demand realization, suspension, lineage, memoization, and
continuation-aware control.

POO Flow owns:

- the POO-native effect-provider capability contract;
- the permitted evidence-state transitions;
- recovery and retry policy;
- commit, cancellation, and reconciliation receipts;
- observability and cross-context admission consequences.

The runtime or Marlin handoff performs the external operation.  POO Flow
governs the evidence and control boundary around that operation; it does not
replace the external system's native transaction, verification, or
reconciliation mechanism.

* Retry causal-link proof state

The normative retry and reconciliation rules in this RFC are represented by two
stable proof obligations:

| Obligation | Machine-checked consequence |
|-
| =EFF-006= | Retry from =failed= or =cancelled= preserves operation identity, names the prior attempt, and creates a fresh attempt. |
| =EFF-007= | A trace from =indeterminate= cannot reach a retry without beginning with provider reconciliation; a fresh retry path exists after reconciliation proves no commit. |

The Lean witnesses are =failedRetryPreservesCausalLink=,
=cancelledRetryPreservesCausalLink=,
=indeterminateRetryRequiresPriorReconciliation=, and
=reconciliationNoCommitEnablesFreshRetry=. The complete effect-boundary model
passed AXLE in =lean-4.31.0= under request
=f7dd396f-d644-4fcc-a39d-07f130f8a4f1= with zero failed declarations, errors,
or warnings.

This result proves structural causality and the reconciliation barrier.
=RecoveryPolicyAuthorization.lean= additionally proves that a bare
=RetryAuthorization.policyEvidence= cannot identify a recovery-policy root and
defines a proof-carrying =PolicyAuthorizedRetry= bound to an immutable recovery
decision receipt.

The local Lean model now establishes the formal provenance contract. Concrete
Scheme correspondence remains open: POO Flow must show that its recovery
decision receipt is constructed and validated through the exact pinned
=gerbil-poo= prototype lineage and then consumed by the effect boundary.
Independent AXLE verification is =blocked-verifier-import-boundary= because the
remote environment cannot resolve the local =PooFlowProof= import. No combined
source was exported.

* Retry capability consumption boundary

The effect boundary consumes =RetryCapability=; it does not consume a bare
=RecoveryDecisionReceipt= or =policyEvidence= value.

Before starting the next attempt, the boundary MUST validate:

- the capability refers to a committed recovery receipt;
- the receipt selected a retry-permitting recovery decision;
- receipt operation identity matches the effect operation;
- receipt prior attempt matches the current =failed= or =cancelled= attempt;
- the next attempt identity is fresh;
- receipt boundary and suspended generation match the active runtime boundary;
- the opaque runtime token is valid and unconsumed;
- the effect is not =committed=, =indeterminate=, or still =reconciling=.

Capability consumption and the transition to the fresh =in-flight= attempt MUST
share one atomic acceptance boundary. Failure consumes no retry authority and
returns structured rejection evidence. Successful consumption makes the token
permanently unusable.

#+begin_src mermaid
stateDiagram-v2
  [*] --> CapabilityProjected: committed recovery receipt permits retry
  CapabilityProjected --> Validating: effect boundary receives capability
  Validating --> Rejected: receipt, lineage, generation, or barrier mismatch
  Validating --> InFlightFresh: atomically consume token and start fresh attempt
  InFlightFresh --> InFlightFresh: duplicate delivery observes existing attempt
  InFlightFresh --> Rejected: token replay cannot start another attempt
  Rejected --> [*]: immutable rejection evidence
#+end_src

A receipt may be inspected repeatedly. A =RetryCapability= may be consumed at
most once. Observability, admission, and user composition receive no token and
therefore cannot acquire retry authority.

The Lean =RetryAuthorization= carrier is a proof-model projection, not a public
Scheme constructor. Its Scheme correspondence is the validated projection
carried by =RetryCapability=.

** Minimum Scheme/runtime correspondence contract

This contract records only consequences of the approved four-layer recovery
authorization boundary. It does not select an implementation module while the
Gerbil owner remains unresolved.

The internal projection operation MUST:

- accept only a committed =RecoveryDecisionReceipt= whose selected decision
  permits retry;
- run under the owning recovery/effect-boundary authority rather than under
  user composition or observability;
- mint or receive a runtime-local =SingleUseRuntimeToken= that cannot be
  reconstructed from serialized receipt fields;
- bind receipt identity, operation, prior attempt, fresh next attempt, boundary
  root, and generation;
- return a POO-native =RetryCapability= object;
- reject caller-supplied scalar policy evidence, caller-fabricated tokens, raw
  alists, and public mutation through =.put!=.

The internal consumption operation MUST atomically:

1. validate that the capability is =available= and belongs to the owning
   boundary/generation;
2. transition the token state from =available= to =consumed=;
3. admit exactly the fresh attempt already bound by the receipt;
4. reject replay without minting another token or attempt identity;
5. emit runtime evidence sufficient to establish correspondence with
   =RetryCapabilityStep= and the effect-state transition.

* POO-native effect-provider capability

An effect provider is a POO capability object.  Its semantic responsibilities
include:

- establishing operation evidence;
- invoking the external operation;
- verifying terminal outcomes;
- reconciling an indeterminate outcome when supported;
- cancelling an uncommitted operation when supported;
- emitting immutable receipts.

These responsibilities MUST NOT be exposed as a parallel record DSL, raw alist
protocol, or ordinary user-authored state machine.  Exact public slot and macro
names remain evidence-gated until the corresponding =gerbil-poo= API surface is
symbol-located and behavior-proven.

Idempotency and reconciliation are separate optional capabilities.  A provider
MUST NOT claim either capability merely because an invocation function can be
called again.

* Effect-boundary evidence states

Every effect operation is in exactly one evidence state:

- =declared=: the boundary and operation evidence exist, but invocation has not
  begun;
- =in-flight=: invocation began and no terminal proof is available;
- =committed=: verifier-backed evidence proves the effect committed;
- =failed=: provider evidence proves failure without an unknown commit outcome;
- =cancelled=: provider evidence proves cancellation before commit;
- =indeterminate=: invocation began, but no terminal outcome can be proved;
- =reconciling=: an authorized provider reconciliation is querying external
  state.

#+begin_src mermaid
stateDiagram-v2
  [*] --> Declared: boundary and operation evidence established
  Declared --> InFlight: provider invocation begins
  InFlight --> Committed: verifier-backed commit receipt
  InFlight --> Failed: provider proves failure without commit
  InFlight --> Cancelled: provider proves cancellation before commit
  InFlight --> Indeterminate: execution is lost without terminal proof
  InFlight --> InFlight: continuation re-entry joins or observes the active attempt

  Failed --> InFlight: policy authorizes a new retry attempt
  Cancelled --> InFlight: policy authorizes a new restart attempt
  Indeterminate --> Reconciling: provider proves reconciliation capability
  Reconciling --> Committed: external state proves commit
  Reconciling --> Failed: external state proves absence of commit
  Reconciling --> Indeterminate: terminal proof remains unavailable

  Committed --> Committed: continuation re-entry returns the prior receipt
#+end_src

No transition may be inferred from elapsed time, loss of a worker, an exception
alone, or the absence of a response.  Those observations produce
=indeterminate= unless stronger provider evidence proves another state.

* Boundary, operation, and attempt identity

The protocol distinguishes:

1. the POO runtime boundary-lineage identity;
2. the provider operation evidence identity;
3. the individual attempt identity.

The lexical Scheme binding name is diagnostic attribution only.  It MUST NOT be
an operation idempotency key.

A policy-authorized retry remains causally linked to the same declared effect
boundary, but it creates a new attempt identity.  The new attempt MUST reference
the failed or cancelled attempt receipt that authorized it.

Cross-process reconciliation uses provider operation evidence and external
verification.  It does not claim that a process-local POO runtime root has been
preserved.

* Terminal proof invariants

** Committed

A successful function return is insufficient to establish =committed=.
=committed= requires immutable provider evidence backed by an outcome verifier.
The receipt identifies the boundary, operation, attempt, verifier evidence,
external outcome identity, and causal predecessor evidence.

Once committed, the same operation MUST NOT be invoked again by continuation
re-entry.  Re-entry observes or returns the prior commit receipt.

** Failed

=failed= requires evidence that distinguishes a known failure from an unknown
external outcome.  If the provider cannot prove that distinction, the state is
=indeterminate=.

Retry from =failed= requires an immutable recovery decision and a new attempt
identity.  Retry is not an unconditional generic restart.

** Cancelled

=cancelled= requires evidence that cancellation completed before commit.
Submitting a cancellation request is not cancellation proof.

Restart from =cancelled= requires an immutable recovery decision and a new
attempt identity.

** Indeterminate

=indeterminate= is the strongest effect barrier.  Automatic retry is forbidden
because the external effect may already have occurred.

The permitted policy-visible actions are:

- inspect the bounded evidence difference;
- reconcile through a provider capability;
- abort the declared realization boundary;
- defer while preserving the barrier.

Retry becomes possible only after reconciliation proves a state whose policy
allows a new attempt.

* Continuation and restart semantics

First-class continuations remain control-flow mechanisms; they are not effect
rollback or transaction tokens.

Continuation re-entry behaves according to effect evidence:

| Current state | Re-entry behavior |
|---+---|
| =declared= | normal policy may begin the first attempt |
| =in-flight= | join, observe, or suspend on the existing attempt; never invoke a duplicate |
| =committed= | return or observe the immutable prior receipt |
| =failed= | expose only policy-authorized recovery choices |
| =cancelled= | expose only policy-authorized restart choices |
| =indeterminate= | expose inspect, reconcile, abort-boundary, or defer; never automatic retry |
| =reconciling= | join, observe, or suspend on the active reconciliation |

No continuation, closure, active demand cell, external handle, or suspended
recovery frame is serialized by this protocol.

* Atomic terminal-state arbitration

** Sole Scheme POO library invariant

=gerbil-poo= is the core and sole POO library for Scheme.  Atomic
terminal-state arbitration does not introduce another object system, POO
runtime, prototype implementation, evaluator, linearizer, fixed-point engine,
or fallback library.

The effect boundary is a higher-order POO Flow prototype/capability expressed
through =gerbil-poo= prototype, slot, refinement, demand, and composition
semantics.  POO Flow owns the higher-order effect-governance meaning; it does
not reimplement POO.

An implementation may place an atomic compare-and-transition primitive behind
the explicit runtime handoff boundary.  That primitive is synchronization
substrate, not a second POO library.  POO identity, inheritance, refinement,
demand, and continuation-aware realization remain exclusively governed by
=gerbil-poo=.

Exact Scheme constructors and slot names remain API-evidence-gated.  No local
fallback representation is authorized while the pinned =gerbil-poo= surface
is not yet =behavior-proven= and =flow-qualified=.

** Combined ownership

| Owner | Responsibility |
|---+---|
| =gerbil-poo= | the sole Scheme POO implementation: prototypes, slots, composition, demand, lineage, and continuation-aware realization |
| effect provider | external operation idempotency evidence, terminal proof, and reconciliation capability |
| POO Flow effect-boundary prototype | operation/attempt governance, atomic terminal-state acceptance, conflict condition, recovery policy, and receipt projection |
| runtime handoff substrate | execute the atomic compare-and-transition requested by the POO boundary |

The provider and POO Flow responsibilities are both required.  A callable
provider does not prove idempotency, and a verified provider receipt does not
by itself prove that two concurrent receivers cannot both accept different
terminal results.

** Arbitration key

Terminal-state arbitration is scoped by:

** Atomic decisions

#+begin_src mermaid
flowchart LR
  I["State: InFlight under one TerminalKey"] -->|"first verified receipt wins atomic compare-and-transition"| C["State: Committed(existing receipt)"]
  C -->|"same receipt and digest observed again"| D["Decision: duplicate; return existing receipt"]
  D -->|"terminal state remains immutable"| C
  C -->|"different receipt for the same TerminalKey"| X["Decision: conflicting-terminal-evidence condition"]
  X -->|"preserve existing terminal cell; open reconciliation evidence state"| R["State: reconciliation required"]
  R -->|"provider proves existing receipt"| C
  R -->|"proof remains unavailable"| U["State: qualification remains Indeterminate"]
  R -->|"provider proves contradictory terminal evidence"| F["State: provider-integrity failure; no overwrite"]
#+end_src

The atomic decision rules are:

1. =InFlight + first verified receipt= atomically becomes
   =Committed(receipt)=.
2. Repeating the identical receipt is an idempotent observation.  It returns
   the already accepted receipt and emits no second commit.
3. A different receipt for the same terminal key cannot overwrite the
   committed cell.
4. Conflicting terminal evidence raises a structured condition and opens a
   separate reconciliation evidence state.
5. While conflict reconciliation is unresolved, handoff, cross-context
   admission, and operational qualification treat the boundary as
   =Indeterminate=.
6. Reconciliation never mutates the accepted receipt silently.  Contradictory
   verified evidence is a provider-integrity failure requiring an explicit
   governance decision.

The committed effect cell and the reconciliation evidence state are distinct.
This preserves terminal-state immutability while preventing an unresolved
conflict from being presented as qualified success.

** Formal proof boundary

The Lean relation =AtomicCommitArbitration= proves:

- an identical repeated receipt is idempotent;
- conflicting same-key evidence cannot overwrite an existing receipt;
- an accepted commit cannot be accepted again by a subsequent arbitration.

The earlier same-snapshot double-commit witness remains a required negative
proof.  It demonstrates why raw concurrent =Step.commit= proposals require the
atomic arbiter.

The Lean theorem does not yet prove that a concrete runtime primitive is
linearizable.  Runtime correspondence and concurrent stress evidence remain
required before operational qualification.

* Receipt and observability contract

Every state transition emits an ordered receipt containing:

- boundary-lineage evidence;
- provider operation evidence;
- attempt identity;
- prior and next evidence states;
- transition authority and policy decision;
- verifier, cancellation, or reconciliation evidence when applicable;
- causal predecessor receipt identity.

#+begin_src mermaid
flowchart LR
  O["State: ordered transition receipt"] -->|"causal predecessor link"| P["State: previous effect evidence"]
  O -->|"provider verification projection"| V["State: commit, failure, cancellation, or reconciliation proof"]
  O -->|"governance projection"| G["State: immutable policy decision"]
  O -->|"realization projection"| R["State: boundary, operation, and attempt identities"]
  R -.->|"diagnostic attribution only; no operation authority"| L["State: lexical Scheme binding"]
  V -->|"terminal proof qualifies disposition"| D["State: artifact-backed, pure-value, context-bound, or barrier"]

Observability is read-only.  A sink may expose a bounded condition snapshot and
receipt chain, but it cannot advance the state machine, resume a continuation,
commit an effect, issue cancellation, or authorize retry.

* Relationship to realization-evidence admission

Effect evidence constrains the disposition defined by the runtime-context RFC:

- =committed= may become =artifact-backed= only when the receipt identifies a
  verified content-addressed artifact;
- a committed provider result may become =pure-value= only when independent
  portable value evidence exists;
- =in-flight=, =indeterminate=, and =reconciling= remain
  =suspended-or-uncommitted=;
- runtime handles and capabilities remain =context-bound=;
- =failed= and =cancelled= do not supply an admitted result by themselves.

Classification still passes through all content, dependency, policy, and
portability gates.  A commit receipt alone does not authorize cross-context
admission.

Pure intent construction, demand suspension, runtime handoff, coalescing, and
receipt reinjection are specified by
[[file:45-09-effect-intent-suspension-handoff-reinjection.org][Effect Intent, Suspension, Runtime Handoff, And Receipt Reinjection]].  This
module remains the sole authority for the effect evidence state machine.

Resource acquisition, release, cancellation, and reconciliation project into
the lease lifecycle specified by
[[file:45-11-resource-lease-continuation-dynamic-wind.org][Resource Lease, Continuation, And Dynamic-Wind]].  Each external resource
operation still follows this module's authoritative effect evidence states.

Boundary cancellation requests, coalesced demand authority, and cleanup
continuation generations are specified by
[[file:45-12-structured-cancellation-boundary-generations.org][Structured Cancellation And Boundary Generations]].  A provider cancellation
request remains non-terminal until this module's evidence state proves the
outcome.

Replay may consume qualified effect receipts according to
[[file:45-14-deterministic-realization-replay.org][Deterministic Realization Replay]], but it never invokes the provider or changes
the authoritative effect evidence state recorded here.

Effect receipts use the identity, projection, verifier, correction, and
contradiction semantics defined by
[[file:45-15-receipt-object-canonical-evidence-projection.org][Receipt Object And Canonical Evidence Projection]].

* Explicit exclusions

This RFC does not authorize:

- automatic retry from =indeterminate=;
- treating an exception as proof that no external effect occurred;
- treating a cancellation request as cancellation completion;
- deriving operation identity from a lexical binding name;
- serializing POO roots, closures, continuations, active demand cells, or
  external runtime handles;
- a fallback effect evaluator or transaction implementation inside POO Flow;
- a new public effect syntax before the real =gerbil-poo= capability surface is
  behavior-proven.

#+title: Module-Local Functional Kernel Governance
#+language: en

* Status

This RFC freezes the accepted governance contract for a Module-local
=func.ss=.  It defines where named pure domain functions live, how POO objects
consume them, and how generated code is prevented from creating redundant
helpers.  It does not admit an implementation or add public syntax.

* Scope

This RFC owns:

- the distinction between shared functional combinators and Module-local domain
  functions;
- the dependency direction among =types.ss=, =func.ss=, =objects.ss=, and
  =interface.ss=;
- the conditions under which a semantic Module requires or may omit =func.ss=;
- the admission evidence required for each exported function; and
- the separation of pure functions, POO dispatch, and runtime effects.

It does not own:

- the Type and Contract prototype algebra;
- upstream object, prototype, dispatch, or C3 mechanics;
- the four-slot Module semantic contract;
- runtime implementation or adapter effects; or
- a macro language for declaring functions.

* Central decision

Every non-trivial semantic Module has one Module-local functional kernel named
=func.ss=.  It contains only named, pure, Module-specific domain functions.

A purely declarative Module may omit =func.ss= only when it contains no domain
computation in any other file.  Empty placeholder =func.ss= files are rejected.

The file boundary is a code-governance boundary, not a new runtime layer and not
a second functional library.

* Two functional ownership levels

The project has two distinct functional ownership levels:

| Owner | Responsibility |
|-------+----------------|
| =src/utilities/functional.ss= | Generic reusable predicates and combinators shared across Modules. |
| =<module>/func.ss= | Pure semantic transformations specific to one Module. |

Generic map, fold, find, predicate, string, or collection combinators remain in
the shared owner.  A Module-local =func.ss= must not clone, rename, or lightly
wrap them.

#+begin_src mermaid
flowchart LR
  S["shared functional.ss"] -->|"supplies already admitted generic combinators"| F["Module-local func.ss"]
  T["Module-local types.ss"] -->|"contracts every function input, output, and semantic context"| F
  F -->|"supplies named pure responsibility implementations"| O["Module-local objects.ss"]
  O -->|"publishes selected POO values and responsibilities"| I["Module-local interface.ss"]
  I -->|"projects explicit semantic intent across the effect boundary"| R["optional runtime.ss"]
#+end_src

These arrows express semantic supply.  In Scheme import terms, =objects.ss=
imports =func.ss=, while =func.ss= never imports Module-local =objects.ss=.
=interface.ss= imports =objects.ss=, while =objects.ss= never imports
=interface.ss=.  Runtime code may consume the semantic interface, while no
semantic owner imports runtime code.

* Foundation and Module-local order

The project-wide meta-foundation and a Module-local implementation have
different but compatible orders:

#+begin_src mermaid
flowchart TB
  U["upstream gerbil-poo"] -->|"provides native POO mechanics"| CO["poo-flow-core objects foundation"]
  CO -->|"constructs Type and Contract as POO prototypes"| CT["poo-flow-core types foundation"]
  CT -->|"specializes contracts for one Module"| MT["Module-local types.ss"]
  MT -->|"constrains named pure transformations"| MF["Module-local func.ss"]
  MF -->|"is bound into responsibility implementations"| MO["Module-local objects.ss"]
  MO -->|"is projected through a deliberately small surface"| MI["Module-local interface.ss"]
#+end_src

The core object foundation precedes the core type foundation because Type and
Contract are POO values.  Inside one domain Module, its local types constrain
functions before its local objects bind those functions to responsibilities.

* =func.ss= ownership

=func.ss= may own:

- named pure domain transformations;
- total or explicitly partial functions whose failure is represented as
  semantic evidence;
- small private functions that directly support one admitted domain
  transformation;
- composition of shared functional combinators; and
- projection between already admitted semantic values.

=func.ss= must not own:

- generic helpers reusable across unrelated Modules;
- Type, Contract, or object prototype declarations;
- public hygienic macros or internal declaration macros;
- raw package, manifest, registry, or build behavior;
- POO dispatch or C3 precedence algorithms;
- environment reads, clocks, randomness, secrets, I/O, mutation, handles, or
  adapter calls; or
- compatibility shims for an older architecture.

Every dependency that would make a result impure must instead be an explicit
semantic input or cross the later EffectIntent boundary.

* Dependency direction

=func.ss= may import:

- its Module-local =types.ss=;
- the shared =src/utilities/functional.ss=;
- pure read-only operations from the admitted project object foundation; and
- other explicitly admitted pure semantic modules.

=func.ss= must not import its Module-local =objects.ss=, =interface.ss=, or
runtime owner.  This prevents object-construction cycles and makes the pure
kernel independently testable.

=objects.ss= imports =types.ss= and =func.ss=.  It binds named functions to POO
responsibilities and supplies identity, prototype composition, and dispatch
context.  It must not copy function bodies into anonymous slot implementations.

* POO and functional separation

The functional kernel and the POO object layer are complementary:

| Concern | Owner |
|---------+-------|
| Pure deterministic transformation | =func.ss= |
| Semantic identity and prototype composition | =objects.ss= |
| Polymorphic selection and inherited continuation | Native POO dispatch |
| Input, output, and responsibility obligations | =types.ss= |
| Small public composition surface | =interface.ss= |
| Effects and runtime handles | Runtime adapter boundary |

Conditional trees that select behavior by object kind are rejected when native
POO dispatch can express the variation.  Conversely, a deterministic
transformation must not be inflated into a new prototype merely to avoid
writing a small pure function.

* Function admission evidence

Every exported Module-local function must have all of the following evidence:

1. A unique Module-specific semantic responsibility.
2. Parser-owned search evidence that no equivalent shared or Module-local
   function already exists.
3. An input, output, and semantic-context Contract from =types.ss=.
4. At least one named consumer in =objects.ss=, a pure composition, or a focused
   test.
5. Referential-transparency evidence for equal admitted inputs.
6. Failure evidence that remains a pure value rather than an ambient exception
   or side effect.

An exported function without a Contract or consumer is an orphan and is
rejected.

* AI-generated code governance

The functional kernel constrains generated code by semantic ownership rather
than by an arbitrary line-count limit.

#+begin_src mermaid
flowchart TD
  C["candidate generated function"] -->|"searches parser-owned shared and local symbols first"| D{"equivalent behavior already exists?"}
  D -->|"yes: reuse the admitted function"| X["reject duplicate definition"]
  D -->|"no: classify the responsibility"| K{"what kind of behavior is it?"}
  K -->|"generic reusable combinator"| S["shared functional.ss"]
  K -->|"Module-specific pure transformation"| F["Module-local func.ss"]
  K -->|"polymorphic responsibility selection"| O["objects.ss and native POO dispatch"]
  K -->|"effect or runtime resource action"| R["runtime adapter boundary"]
  F -->|"requires Contract and named consumer"| A["admitted concise function"]
#+end_src

Generated changes are rejected when they:

- create a second spelling of an existing function;
- place Module computation in =objects.ss=, =types.ss=, or =interface.ss=;
- introduce =utils.ss=, =helpers.ss=, or another unowned catch-all file;
- encode prototype polymorphism as a host-language conditional tree;
- export an unused helper;
- combine unrelated transformations in one function; or
- hide effects behind a function that appears pure.

* Concision invariant

The semantic budget for one admitted function is:

#+begin_example
one function
  = one domain transformation
  + one Contract
  + one named consumer
  + zero effects
#+end_example

This is not a source-line limit.  A mechanically short function may still be
redundant or incoherent, while a slightly larger total transformation may remain
one precise semantic unit.

* Declarative-only Modules

A Module may omit =func.ss= only if:

- its local =types.ss= declares no function Contract;
- its =objects.ss= contains no domain computation or anonymous compute hook;
- its =interface.ss= only projects already admitted values; and
- its tests confirm that composition requires no local transformation.

If any domain function becomes necessary, =func.ss= becomes mandatory before
that function is admitted.  An empty file is not evidence of a functional
kernel.

* Macro boundary

This RFC introduces no function-declaration macro.

A future bounded internal macro may attach named =func.ss= functions to repeated
POO responsibility families only when it expands to ordinary imports, native POO
objects, and direct named function references.  It must not generate hidden
functions, a registry, or a parallel dispatch language.

* Public interface

=func.ss= is an internal semantic owner, not a new user DSL.  =interface.ss=
selectively projects POO objects and deliberately public functional
combinators.  The ordinary user composition surface remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

No =func= clause, function registry, or nested composition wrapper is added.

* Ownership

- =src/utilities/functional.ss= owns generic project-wide pure combinators.
- Each non-trivial semantic Module owns its Module-specific =func.ss=.
- =types.ss= owns POO-native function and responsibility Contracts.
- =objects.ss= owns prototype identities and responsibility binding.
- =interface.ss= owns the deliberately small projection surface.
- Runtime adapters own effects, handles, secrets, and external resources.
- GSLPH, Gerbil-Bazel, Nix, and =gerbil.pkg= own no functional-kernel semantics.

* Admission checklist

** Governance contract

- [X] Require one =func.ss= for every non-trivial semantic Module.
- [X] Reject empty placeholder files.
- [X] Keep generic combinators in the shared functional owner.
- [X] Keep Module-specific pure transformations in the Module-local owner.
- [X] Require =types.ss -> func.ss -> objects.ss -> interface.ss=.
- [X] Bind POO responsibilities to named functions rather than anonymous hooks.
- [X] Route polymorphism to POO dispatch and effects to runtime adapters.
- [X] Require duplicate-search, Contract, consumer, purity, and failure evidence.
- [X] Allow omission only for a proven declarative-only Module.
- [X] Add no public macro or user DSL.

** Implementation admission

- [ ] Admit the shared POO-native =types.ss= foundation first.
- [ ] Select one non-trivial Module as the first functional-kernel exemplar.
- [ ] Admit its local =types.ss=, =func.ss=, =objects.ss=, and =interface.ss=
  dependency direction.
- [ ] Admit duplicate-function and orphan-export checks.
- [ ] Admit purity and focused function tests.

* Rejected alternatives

- One empty =func.ss= in every directory.
- A second shared functional library under every Module.
- Module-local =utils.ss= or =helpers.ss= catch-all files.
- Anonymous function bodies embedded throughout object declarations.
- Host-language conditional dispatch that duplicates POO dispatch.
- Effectful helpers disguised as pure transformations.
- Boolean-only validation with no Contract evidence.
- Arbitrary source-line limits as a proxy for semantic concision.
- A public function-declaration macro or registry.

* Successor contract

The first implementation slice must still begin with the admitted
=types.ss= foundation.  After that foundation exists, one non-trivial Module may
serve as the functional-kernel exemplar.  The exemplar must prove the complete
local dependency direction before the convention is applied to additional
Modules.

Module debug, observability, recovery, and telemetry governance is defined
separately in =45-120-03=.  The functional kernel remains pure and must not
absorb observation publication, coordinator control, or runtime measurement.

* Accepted upstream ownership correction

The generic higher-order functional algebra belongs to the pinned
=gerbil-poo= dependency.  =gerbil-poo/fun.ss= is upstream foundation,
not a template for a second project-owned functional library.

Project-wide reusable combinators remain in
=src/utilities/functional.ss=.  A Module-local =func.ss= owns only the
small pure domain kernel that is unique to that Module and has named
consumers.  It MAY compose upstream functional values and shared
project combinators, but it MUST NOT copy or rename generic Functor,
identity, composition, traversal, or helper machinery.

The filename =func.ss= is an ownership constraint rather than a public
namespace promise.  Design vocabulary in this RFC does not
automatically authorize new exported functions, constructors, or
macros.

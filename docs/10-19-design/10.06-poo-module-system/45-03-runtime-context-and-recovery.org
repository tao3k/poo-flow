* Normative responsibility

This module exclusively owns the initialization gate, runtime context, cell
lifecycle, structured conditions, continuations, and recovery authority.

* Ownership boundary: gerbil-poo mechanism and POO Flow governance

The generic realization lifecycle described in this module is owned by
=gerbil-poo=.  Demand cells, memoization, dependency graphs, fixed-point
evaluation, continuation capture at a demand boundary, and the generic
condition/restart mechanism are not a second POO Flow runtime.

POO Flow consumes those mechanisms to define =gerbil-poo= policy objects for
Profile and Mix governance.  It owns the recovery-policy and resource-policy
roles, authority rules, runtime-handoff barriers, bounded observation
projections, receipts, and qualification requirements.

If the pinned =gerbil-poo= revision lacks a general evaluation extension point
required below, that item is a =gerbil-poo= extension requirement.  It MUST NOT
be satisfied by a shadow evaluator or local fixed-point package in POO Flow.

Consequently, references below to a realization context, demand cell,
dependency graph, or captured continuation describe either an existing
=gerbil-poo= object or a required general =gerbil-poo= extension.  POO Flow
adds domain policy and evidence around that object without replacing its
semantics.

* Recoverable fixed-point control

A runtime fixed-point failure is represented as a POO condition object rather
than an unstructured exception string.  Its normative slots include:

#+begin_export mermaid
flowchart TD
    A["Nonproductive forced cycle"] --> B["POO cycle condition"]
    B --> C["Capture demand-boundary continuation"]
    C --> D["Expose context-valid restart objects"]
    D --> E{"Recovery"}
    E --> F["Use super or supplied value"]
    E --> G["Derive lineage without a refinement"]
    E --> H["Defer while another dependency can progress"]
    E --> I["Abort current realization boundary"]
#+end_export

#+begin_example
kind
lineage
slot-path
demand-boundary
dependency-cycle
source-locations
available-restarts
continuation-capability
evaluation-receipt
#+end_example

The raw continuation is not the ordinary public interface.  It is wrapped by
a constrained POO continuation capability whose restart objects are computed
from the current evaluation context.

#+begin_export mermaid
flowchart TD
    A["Suspended demand cell"] --> B["POO condition"]
    B --> C["Recovery-policy prototype"]
    D["Evaluator authority"] --> C
    E["Waiters"] --> F["Observe or propose"]
    F --> C
    C --> G{"Commit one recovery decision"}
    G --> H["Resume the cell"]
    G --> I["Derive a new realization context"]
    G --> J["Abort the realization boundary"]
    H --> K["All waiters observe one result"]
#+end_export

The standard restart vocabulary is:

- =use-super=: continue with an inherited value when the lineage provides one;
- =use-value=: continue with an explicit value in the current realization
  overlay;
- =exclude-refinement=: derive a lineage without one selected refinement and
  resume from the demand boundary;
- =defer=: suspend only when another dependency branch can still make
  progress;
- =abort-realization=: terminate the current Submodule or user-composition
  realization boundary without terminating the Scheme process.

An unconditional =retry= restart is forbidden.  Retrying an immutable lineage
in the same evaluation context simply recreates the same cycle.  Resumption
requires a changed lineage, supplied value, or dependency state.

Recovery MUST preserve functional semantics.  It does not mutate the original
prototype: supplied values live in a realization overlay, and refinement
exclusion creates a derived lineage.  Every recovery decision emits a receipt.

A captured continuation may cross only pure POO evaluation.  Runtime handoff
to Marlin, network, filesystem, or another external effect establishes a
nonreplayable barrier unless the operation provides an idempotent receipt.
Calling the same recovery capability again MUST either be rejected or create
an explicitly distinct derived evaluation session; it MUST NOT replay effects
implicitly.

* Pure realization context and demand cells

Evaluation state MUST NOT be written back into a POO prototype.  Prototype
objects remain immutable semantic values containing slot definitions,
lineage, =super= relationships, Mix identity, imports, capabilities, lazy
computations, and declaration provenance.

#+begin_export mermaid
flowchart LR
    A["Immutable POO prototype lineage"] --> B["Realization-context POO object"]
    B --> C["Unique demand cells"]
    C --> D["Dependency and wait graphs"]
    C --> E["Memoized values"]
    C --> F["Suspended continuations"]
    C --> G["Recovery overlays"]
    B --> H["Evaluation receipts"]
#+end_export

Memoization and control state belong to an explicit realization-context POO
object.  That context owns demanded slots, evaluation cells, the dependency
and wait graphs, memoized realizations, suspended continuations, recovery
overlays, performance counters, and evaluation receipts.

The same prototype lineage may therefore be realized independently in
multiple contexts.  A failure, recovery choice, or cache entry in one context
MUST NOT mutate the prototype or contaminate another context.

** Unique demand cell

Within one realization context, the tuple:

#+begin_example
lineage-root identity
  + slot path
  + demand boundary
#+end_example

identifies one evaluation cell.  The first demander obtains evaluator
authority.  Later demanders become waiters and MUST NOT repeat the
computation.  When the cell realizes, every waiter observes the same result.

If evaluation suspends on a continuable condition, all waiters remain attached
to the same cell.  They MUST NOT independently install contradictory recovery
values into that realization.

An =evaluating= cell does not by itself prove a dependency cycle.  Independent
callers may concurrently demand the same cell and wait safely.  A cycle exists
only when the current dependency ancestry reaches the same demand key again;
the exact cycle semantics are owned by [[file:45-05-lineage-and-cycle-detection.org][45-05]].

** Memoization boundary

Memoization is local to a realization context by default.  There is no
implicit global realization cache.  Reuse across contexts requires an
explicitly imported realization snapshot or receipt whose lineage and recovery
policy match the new context.

A changed lineage or recovery policy invalidates incompatible cells.
Recovery values live in the derived context overlay rather than the original
prototype.  Lazy imports that have not been demanded MUST NOT appear in the
cache, dependency graph, or debugger snapshot.

* Recovery-policy authority and escalation

A recovery policy is a POO prototype whose pure semantic contract is:

#+begin_example
condition
  x available restart prototypes
  x bounded realization observation
  -> recovery decision prototype
#+end_example

The policy produces a decision; it does not invoke the captured continuation.
The suspended cell owns the continuation capability and atomically validates
and commits one decision.

#+begin_export mermaid
flowchart LR
    A["POO condition"] --> D["Recovery-policy prototype lineage"]
    B["Available restart prototypes"] --> D
    C["Bounded realization observation"] --> D
    D --> E["Recovery decision prototype"]
    E --> F["Single-use continuation capability"]
    F --> G["Atomic commit"]
#+end_export

Recovery governance itself follows ordinary POO lineage.  A later policy
refinement may handle a condition or delegate through =super=.  There is no
integer priority table, first-registered-handler rule, waiter vote, or global
exception-handler search.

** Authority capabilities

Recovery authority is separated into four capabilities:

- =observe= reads a bounded condition snapshot;
- =propose= submits a candidate recovery decision;
- =decide= selects or constructs the one decision to commit;
- =resume= validates the decision and invokes the single-use continuation
  capability.

An ordinary waiter has =observe= authority by default.  A trusted supervisor
may receive =propose= or =decide= authority, but =resume= remains confined to
the suspended cell.  A raw continuation MUST NOT escape through any of these
capabilities.

** Immutable recovery decisions

A recovery decision is immutable POO data, not an arbitrary effectful
callback.  Its semantic variants include:

#+begin_example
resume-with-value
resume-with-super
derive-without-refinement
defer-on-dependencies
abort-boundary
escalate-condition
#+end_example

Before commit, the cell revalidates the decision authority, restart
availability, suspended generation, effect-barrier state, lineage identity,
and dependency-graph generation.  A stale or unauthorized decision cannot
invoke the continuation.

** Boundary-scoped escalation

#+begin_export mermaid
flowchart TD
    A["Cell-local policy"] --> B{"Can decide?"}
    B -->|yes| C["Commit recovery decision"]
    B -->|no| D["Enclosing Submodule policy"]
    D --> E{"Can decide?"}
    E -->|yes| C
    E -->|no| F["User-composition supervisor"]
    F --> G{"Authorized external decision?"}
    G -->|yes| C
    G -->|no| H["Abort declared realization boundary"]
#+end_export

Escalation follows the enclosing realization-boundary lineage.  It does not
search a global handler registry.  If no boundary can make an authorized
decision, the runtime aborts the declared realization boundary rather than the
whole Scheme process.

** Recovery receipt

Every committed or rejected recovery decision records at least:

#+begin_example
condition identity
cell identity and suspended generation
recovery-policy lineage
available restart identities
selected decision
decision authority
continuation-capability identity
effect-barrier status
derived-realization identity
source provenance
#+end_example

Continuations provide the recovery mechanism, POO policy lineage provides
governance semantics, capabilities provide authority boundaries, and receipts
provide explanation and replay evidence.

** Four-layer recovery authorization object boundary

Recovery authorization is represented by four distinct POO-native objects.
They MUST NOT be collapsed into a scalar evidence field, an alist protocol, or
one object that combines observation with execution authority.

| Object | Lifetime | Semantic responsibility | Authority |
|-
| =RecoveryPolicy= | realization-boundary lineage | Purely select or construct a recovery decision from a condition, available restarts, and bounded observation. | May decide; cannot invoke a continuation or retry an effect. |
| =RecoveryDecision= | before cell commit | Immutable candidate decision containing variant, restart identity, payload evidence, and observation digest. | No execution authority. |
| =RecoveryDecisionReceipt= | durable after acceptance or rejection | Immutable evidence for cell validation, policy lineage, selected decision, generation, effect barrier, and terminal acceptance result. | Read-only; safe for bounded observation, but cannot authorize retry. |
| =RetryCapability= | runtime-local and single-use | A restricted projection of one committed recovery receipt plus an opaque one-shot runtime token. | May authorize exactly one effect-boundary retry attempt. |

The policy produces a decision; the owning cell validates and atomically
commits or rejects it. Only a committed receipt whose selected decision permits
retry may be projected into =RetryCapability=.

flowchart LR
  P["RecoveryPolicy<br/>POO governance prototype"]
  D["RecoveryDecision<br/>immutable candidate"]
  CELL["Owning demand cell<br/>authority + barrier validation"]
  R["RecoveryDecisionReceipt<br/>durable read-only evidence"]
  C["RetryCapability<br/>receipt projection + one-shot token"]
  E["Effect boundary<br/>one fresh attempt"]
  O["Bounded observability"]

  P -->|"pure decide; never resume"| D
  D -->|"submit candidate"| CELL
  CELL -->|"atomically accept or reject"| R
  R -->|"read-only projection"| O
  R -->|"only committed retry decision"| C
  C -->|"consume exactly once"| E
  O -.->|"receipt alone has no execution authority"| E
#+end_src

The durable receipt records at least:

- condition identity;
- realization boundary and cell identity;
- suspended generation;
- recovery-policy prototype root and lineage digest;
- available-restart-set digest;
- selected decision variant and decision digest;
- decision authority source;
- effect-barrier snapshot;
- accepted or rejected outcome;
- immutable rejection reason when rejected.

=RetryCapability= contains no independent copy of policy semantics. It binds:

- the committed recovery receipt identity;
- operation identity;
- prior attempt identity;
- fresh next-attempt identity;
- an opaque single-use runtime token.

The token is runtime state, not a serializable POO slot. The capability MUST NOT
be reconstructed from a receipt digest, =policyEvidence=, user input, an
observability projection, or replayed configuration.

The relation is:

#+begin_src typst
#let RetryCapability(receipt, token) = (
  receipt.outcome == committed
  and receipt.selected_decision.permits_retry
  and token.single_use
  and token.runtime_local
  and token.boundary == receipt.boundary
  and token.generation == receipt.suspended_generation
)
#+end_src

The corresponding formal boundary is owned by RFC 45-11. Local Lean now
classifies receipt, observation, and capability as distinct authorization views:
=recoveryDecisionReceiptDoesNotGrantRetryAuthority= and
=recoveryDecisionObservationDoesNotGrantRetryAuthority= reject authority for
the first two views, while =retryAuthorityRequiresCapability= proves that every
authorized view contains a =RetryCapability=. AXLE acceptance and
Scheme/runtime correspondence remain independent gates.

The ordinary Scheme implementation route is POO-native:

- hygienic =.def= or =.o= declarations for the internal object families;
- =.mix= or =.extend= for policy/capability refinement;
- =.@= for slot demand;
- =compose-proto*= only for repeated internal prototype composition.

Raw =object<-alist= construction, public mutation through =.put!=, user-authored
state machines, and new =user-composition= syntax are not ordinary interfaces.

** Retry-authorization proof projection

The effect-boundary retry authorization is not identified by an unstructured
=policyEvidence= scalar. The proof-facing projection binds a retry to an
immutable recovery decision receipt containing:

- recovery-policy prototype root;
- enclosing realization-boundary root;
- recovery-policy lineage digest and suspended generation;
- operation identity;
- prior and next attempt identities;
- policy evidence and recovery decision digest.

The projection is intentionally a subset of the normative Recovery receipt
above. It does not replace the full receipt, the POO prototype, the one-shot
continuation capability, or cell-local atomic validation.

* Resource governance, cancellation, and performance conditions

Resource control belongs to a resource-policy POO prototype in the realization
context.  It is not an unrelated watchdog and MUST NOT terminate the host
process without first producing a scoped condition and receipt.

#+begin_export mermaid
flowchart TD
    A["Realization context"] --> B["Resource-policy prototype"]
    B --> C["Structural budgets"]
    B --> D["Operational budgets"]
    B --> E["Cancellation authority"]
    C --> F["Depth, cells, edges, and continuations"]
    D --> G["CPU, wall time, memory, and external timeout"]
    F --> H["POO resource condition"]
    G --> H
    H --> I["Recovery-policy lineage"]
#+end_export

** Structural and operational budgets

Structural budgets cover dependency depth, realized or evaluating cell count,
dependency-edge count, repeated entry at one demand boundary, suspended
continuation count, and bounded condition-snapshot size.  These observations
may participate in deterministic qualification when the logical evaluation
schedule is itself controlled.

Operational budgets cover wall-clock deadlines, CPU time, memory pressure,
external-request timeout, and scheduler starvation.  They depend on the host
environment and therefore produce operational conditions with host receipts;
they MUST NOT be reported as machine-independent semantic results.

** Scoped cancellation

#+begin_export mermaid
flowchart TD
    A["Waiter cancels"] --> B["Detach that waiter"]
    B --> C{"Other waiters remain?"}
    C -->|yes| D["Shared cell continues"]
    C -->|no| E{"Boundary policy permits cancellation?"}
    E -->|yes| F["Cancel owned dependency subtree"]
    E -->|no| G["Continue or defer the cell"]
#+end_export

Waiter cancellation detaches only that waiter.  It cannot cancel a cell shared
with other waiters.  Cell cancellation requires cell-owner authority;
Submodule cancellation propagates only through the dependency subtree owned by
that boundary; realization-context cancellation terminates the derived
realization.

Cancellation of an external runtime handoff is not assumed to succeed.  The
runtime MUST return a cancellation receipt before the control plane records
the external operation as stopped.

** Budget-exhaustion condition

A budget-exhaustion condition records at least:

#+begin_example
metric identity
configured limit
observed value
resource-policy lineage
cell and realization identity
dependency snapshot
progress evidence
available restarts
effect-barrier status
host-observation receipt
#+end_example

Context-valid restarts may include =extend-budget=,
=checkpoint-and-defer=, =use-super=, =use-value=, =abort-boundary=, and
=escalate-condition=.  Only an authority that owns the resource policy may
extend a budget.  Automatic unbounded budget doubling is forbidden.

* Identity selection for realization and reuse

Runtime realization and cross-context evidence reuse operate at different
identity layers.  They MUST NOT share the lexical =user-composition= name as a
key.

#+begin_src mermaid
flowchart LR
  L["State: lexical binding name"] -.->|"diagnostic label only; never a cache key"| O["State: observability attribution"]
  R["State: gerbil-poo runtime lineage root"] -->|"root identity + context + demand coordinate"| C["State: current realization cell key"]
  C -->|"memoization and cycle observation within this realization context"| V["State: realized or suspended demand"]
  P["State: provenance/content receipt"] -->|"cross-context or cross-process evidence comparison"| A["State: reuse candidate"]
  A -->|"qualification succeeds without equating runtime roots"| N["State: evidence-linked value in a new context"]
  A -->|"qualification mismatch"| X["State: structured non-admission evidence"]
  R -.->|"runtime identity is process-local evidence, not portable content identity"| A
#+end_src

** Current-context keys

The =gerbil-poo= runtime lineage-root identity is a mandatory component of a
realization cell key.  The complete key also includes the realization context
and the demand coordinate required to distinguish slots or suspended demands.

Memoization, active-demand detection, and cycle evidence use this runtime
identity layer.  The lexical binding name is retained only as diagnostic
attribution.

** Cross-context evidence

Cross-context or cross-process reuse checks provenance/content receipts rather
than runtime root identity.  Matching evidence can qualify a value for use in
a new context; it cannot make the new context's POO root identical to the
source runtime root.

For a derived composition, the receipt links the parent root evidence,
ordered refinements, source evidence, dependency revision, and lowering
evidence.  This preserves causal explanation without turning source spelling
or lexical names into runtime authority.

** Optional realization-evidence admission

Cross-context reuse is an optional provider capability.  It is not part of the
=user-composition= grammar, and it is not required for correct realization.
When no provider is present, the new context realizes demands normally through
=gerbil-poo=.

The exchanged artifact is a realization evidence bundle, not a serialized POO
object.  A bundle is partial and demand-indexed:

- it may contain only values that were actually materialized;
- each value requires portable value or artifact evidence;
- undemanded lazy slots are absent rather than forced for export;
- runtime lineage roots, closures, continuations, active demand cells, and
  suspended recovery state MUST NOT be serialized.

#+begin_src mermaid
flowchart LR
  B["State: realization evidence candidate"] -->|"verify composition content and lowering evidence"| P["State: provenance-qualified candidate"]
  P -->|"verify resolved gerbil-poo revision and recovery/resource policy identity"| E["State: environment-qualified candidate"]
  E -->|"verify portable value evidence and no unresolved effect barrier"| A["State: admitted demand-indexed values"]
  A -->|"attach evidence to a newly constructed runtime root"| N["State: new realization context"]
  B -->|"qualification mismatch"| C["State: continuable admission condition"]
  C -->|"restart: recompute through normal realization"| N
  C -->|"restart: inspect evidence differences"| I["State: diagnostic comparison"]
  C -->|"restart: reject candidate reuse"| X["State: explicit non-admission"]
  R["State: source runtime root"] -.->|"never serialized and never equated with the new root"| N
#+end_src

Admission requires all of the following evidence:

- matching composition content and macro-lowering evidence;
- the resolved =gerbil-poo= dependency revision recorded by build/runtime
  evidence;
- matching recovery-policy and resource-policy identity;
- portable value or artifact evidence for each admitted demand coordinate;
- no unresolved effect, restart, cancellation, or active-demand barrier for an
  admitted value.

This dependency-revision check consumes already resolved build/runtime
evidence.  It does not project, replace, or redefine =gerbil.pkg= package
management.

An admitted bundle creates neither object identity nor context identity
equivalence.  The receiver constructs a new runtime root and a new realization
context, then associates qualified values with the corresponding demand
coordinates as evidence-linked realizations.

Qualification failure MUST NOT silently reuse a value.  It raises a structured
continuable admission condition whose policy-visible restart choices are:

- recompute through normal realization;
- inspect the evidence difference;
- reject reuse explicitly.

There is no unqualified =accept-anyway= restart.  Recompute is the safe default
when policy selects no reusable candidate.

*** Realization disposition classification

An admission provider classifies each candidate demand coordinate into exactly
one disposition at the time of assessment:

| Disposition | Meaning | Cross-context result |
|---+---+---|
| =pure-value= | realization has portable value/content evidence and no unresolved effect | eligible after the remaining admission gates pass |
| =artifact-backed= | realization is represented by a content-addressed artifact with verifier evidence | eligible by reference after artifact verification |
| =context-bound= | realization contains runtime-local identity or capability | never eligible; recompute or reject |
| =suspended-or-uncommitted= | effect, recovery, restart, cancellation, rollback, or active demand remains unresolved | blocked until the boundary resolves |

#+begin_src mermaid
flowchart TD
  D["State: candidate demand coordinate"] -->|"portable value evidence and no unresolved effect"| P["Disposition: pure-value"]
  D -->|"content-addressed artifact plus verifier evidence"| A["Disposition: artifact-backed"]
  D -->|"runtime handle, capability, process, socket, closure, or continuation"| C["Disposition: context-bound"]
  D -->|"effect, recovery, restart, cancellation, rollback, or demand remains active"| S["Disposition: suspended-or-uncommitted"]
  P -->|"content and policy gates pass"| I["State: admission eligible"]
  A -->|"artifact identity and verifier gates pass"| I
  C -->|"cross-context identity cannot be preserved"| R["State: recompute or explicit rejection"]
  S -->|"wait for commit, recovery, cancellation, or rollback"| B["State: admission barrier"]
  B -->|"recovery resolves with portable value evidence"| P
  B -->|"effect commits a verified content-addressed artifact"| A
  B -->|"resolution proves runtime-local identity"| C
  B -->|"cancellation, abort, or policy rejection completes"| R
#+end_src

Disposition is internal evidence, not a declared slot type, Profile case,
configuration field, or user-authored portability tag.  The provider
capability that produces it participates through the POO-native capability
surface; it MUST NOT introduce a parallel record or alist DSL.

=gerbil-poo= continues to own generic demand completion, suspension, lineage,
and continuation-aware realization.  POO Flow owns the provider qualification
policy that decides whether evidence is portable across realization contexts.

The provider MUST fail closed:

- unresolved state is =suspended-or-uncommitted=;
- proven runtime-local state is =context-bound=;
- absence of sufficient portability evidence produces structured
  non-admission rather than =pure-value= or =artifact-backed=.

Classification may change only through an observed boundary transition.  In
particular, an unresolved demand may become =pure-value= after recovery, become
=artifact-backed= after an effect commits a verified artifact, or become
=context-bound= when resolution exposes runtime-local identity.  Classification
alone never performs admission.

receipts for recovery and admission; it does not duplicate the effect state

[[file:45-09-effect-intent-suspension-handoff-reinjection.org][Effect Intent, Suspension, Runtime Handoff, And Receipt Reinjection]].  This

Runtime resource leases, continuation re-entry, and =dynamic-wind= access

[[file:45-11-resource-lease-continuation-dynamic-wind.org][Resource Lease, Continuation, And Dynamic-Wind]].  This module remains the owner
of boundary-scoped recovery decisions and receipt validation.

* Internal gate

#+begin_src text
InternalQualificationEntrypoint = ensure-qualified-core-capability!
QualificationCell               = DependencyQualificationCell
QualificationKey                = (requirementDigest, policyDigest)
QualificationCellAddress        = (runtimeContextId, QualificationKey)
#+end_src

The entrypoint is private.  There is no public =initial= syntax.  Callers supply
Requirement and Policy; POO Flow constructs Observation and Decision internally.

The entrypoint MUST reject caller-supplied Observation, DecisionReceipt,
runtime-context identity, cell identity, or recovery token.

* Bootstrap-safe control and transport substrate

The qualification control plane must operate before
=QualifiedDependencyCapability= is published.  This does not mean G0 bootstraps
Scheme or discovers =gerbil-poo= from nothing: the pinned dependency is already
loadable for POO Flow to run, while G0 qualifies the exact module bindings and
shapes required for public capability use.

The control state remains POO-native:

#+begin_src text
POO control objects:
  PooFlowRuntimeContext
  QualificationRegistry
  DependencyQualificationCell
  RecoverySet

Opaque Gerbil runtime tokens hidden behind POO slots:
  RuntimeLease
  EvaluationCommitToken
  RuntimeContinuationGuard
  RecoveryToken

Gerbil-native transport:
  structured condition delivery
  atomic token transition primitives
#+end_src

The POO control objects are internal pure-object compositions.  Effectful
mutation, synchronization, and one-shot transitions are isolated behind their
named runtime slots.  The opaque tokens are not a parallel configuration model
and are never inspected by user code.

Gerbil-native structured exceptions are used for transport because Scheme
condition delivery must remain available when the capability being qualified
is rejected.  Their semantic and diagnostic payloads remain immutable POO
values where available.

The public result of successful initialization is the POO-native
=QualifiedDependencyCapability=.  Public Mix/Profile composition never receives
the bootstrap context, registry, cell, or tokens.

#+begin_mermaid
flowchart LR
    Bootstrap["Internal POO runtime context"] --> Probe["G0 import probe"]
    Probe --> Decision["POO semantic Decision"]
    Decision -->|"pass"| Capability["QualifiedDependencyCapability<br/>public POO value"]
    Decision -->|"reject/failure"| Condition["Gerbil-native condition transport<br/>immutable POO payload"]
    Bootstrap --> Tokens["Opaque atomic runtime tokens"]
    Bootstrap -. "never public" .-> UI["user-composition"]
    Capability --> UI
#+end_mermaid

Negative qualification fixtures use controlled Observation environments.  They
do not imply that the supervisor loses the pinned POO construction substrate
used to express Requirement, Policy, and control objects.

This control/transport substrate is narrowly operational.  It does not
implement POO fixed points, replace prototype composition, define module
semantics, or manufacture capability values.

* Runtime context

The registry is scoped to a private =PooFlowRuntimeContext=, never a
process-global, Profile-local, or child-local registry.

#+begin_mermaid
stateDiagram-v2
    [*] --> created
    created --> qualifying
    qualifying --> active: G0 pass
    qualifying --> failed: rejection or failure
    active --> closing
    failed --> closing
    closing --> closed
    closed --> [*]
#+end_mermaid

G0 is eager before public composition.  A failed context cannot become active.
Retry creates a new context and cell address; it may reuse the same semantic key
when Requirement and Policy are unchanged.

One runtime context owns:

#+begin_src text
runtimeContextId
capturedImportEnvironment
lifecycleState
QualificationRegistry
activeLeaseCount
nextEvaluationId
#+end_src

=runtimeContextId= is an opaque process-local isolation token.  It never enters
Requirement, Observation, Policy, DecisionReceipt, a canonical digest, module
identity, or package identity.

The production path creates one default context per POO Flow runtime instance.
An embedding process may host multiple independent contexts.  Tests may create
fresh contexts only through POO Flow private test support; GSLPH does not create
or identify them.

The import environment is captured before the first cell enters =evaluating=
and cannot be replaced in place.  A different import environment requires a new
runtime context.

* Cell lifecycle

#+begin_src text
uninitialized
evaluating(evaluationId, evaluationLineage)
ready(QualifiedDependencyCapability)
failed(condition, optional DecisionReceipt)
#+end_src

Terminal cell outcomes are immutable.  Independent acyclic demand waits for the
single outcome.  Recursive or wait-graph cycles raise structured conditions.

Cell transition rules are:

1. =uninitialized -> evaluating= is atomic and records one evaluation owner.
2. Exactly one =EvaluationCommitToken= belongs to that evaluator.
3. Acyclic concurrent demand waits and does not start another probe.
4. The evaluator may publish exactly one =ready= or =failed= outcome.
5. Publication wakes all current waiters with the same immutable outcome.
6. =ready= and =failed= are terminal for the cell address.
7. Retrying creates a replacement context and therefore a new cell address.
8. The replacement may reuse the same QualificationKey when semantics are
   unchanged.

The registry key inside one context is =QualificationKey=.  The complete
operational address includes =runtimeContextId=.  Equal semantic keys in
different contexts do not share cells.

Cycle detection details belong to
[[file:45-05-lineage-and-cycle-detection.org][45-05]].  This module owns only
the cell transition caused by a detected cycle.

* Continuation authority

Scheme continuation recovery is guarded by:

#+begin_src text
RuntimeLease
EvaluationCommitToken
RuntimeContinuationGuard
#+end_src

Continuations may be multi-shot; commit and terminal recovery tokens are
one-shot.  Resumption cannot reopen a closed context, restore old cell state,
repeat publication, or return an arbitrary value as a capability.

Authorized recovery names are:

#+begin_src text
inspect-qualification-failure
abort-runtime-initialization
replace-runtime-context
#+end_src

There is no “continue as if qualified” recovery.

POO Flow owns an initialization supervisor around continuable condition
delivery.  A handler receives the condition plus a closed condition-specific
RecoverySet.  Returning an arbitrary procedure, POO object, boolean, or
capability is invalid.

#+begin_mermaid
flowchart TD
    Raise["Deliver continuable condition"] --> Handler["Handler + closed RecoverySet"]
    Handler --> Inspect["Inspect diagnostics"]
    Inspect --> Handler
    Handler --> Abort["AbortInitialization"]
    Handler --> Replace["ReplaceRuntimeContext"]
    Handler --> Raw["Arbitrary return value"]
    Raw --> Invalid["InvalidRecoveryResultCondition"]
    Replace --> Guard["Validate context/evaluation/recovery token"]
    Guard --> New["Create new context and rerun G0"]
#+end_mermaid

Inspection is repeatable and non-terminal.  Abort and replace tokens are
one-shot.  A multi-shot continuation can revisit inspection, but cannot consume
a terminal token or commit a cell outcome twice.

Every resumption validates:

#+begin_src text
originating runtimeContextId
originating evaluationId
current lifecycleState
commit-token state
recovery-token state
#+end_src

Resumption cannot restore an earlier context state, reopen a closed context,
move a capability across contexts, or roll back a published outcome.

* Condition hierarchy

#+begin_src text
PooFlowRuntimeCondition
├── QualificationCondition
├── EvaluationResourceLimitCondition
├── CompositionEvaluationCondition
└── RuntimeControlCondition
#+end_src

Pre-capability conditions use a bootstrap-safe Gerbil-native structured
exception substrate.  Semantic rejection carries a DecisionReceipt.  Probe
failure, cycle, stale continuation, illegal transition, and resource failure do
not manufacture one.

=InvalidMixModuleObjectCondition= is a concrete
=CompositionEvaluationCondition=. It is raised only after a value crosses the
hygienic expansion boundary and the runtime Mix-module object fails the
internal POO shape owned by [[file:45-07-user-composition-and-mix-module-interface.org][45-07]]. It is not a parser error, and 45-07
does not establish a second condition hierarchy.

Its bounded reasons are =missing-identity=, =invalid-identity=,
=missing-imports=, =invalid-imports=, =missing-capabilities=,
=invalid-capabilities=, =capability-shape-mismatch=, and
=identity-overridden=. It carries no =DecisionReceipt= because the invalid
object has not reached dependency qualification.

The bounded hierarchy is:

#+begin_src text
PooFlowRuntimeCondition
├── QualificationCondition
│   ├── QualificationRejectedCondition
│   ├── ModuleObservationFailedCondition
│   └── QualificationCycleCondition
├── EvaluationResourceLimitCondition
├── CompositionEvaluationCondition
│   └── CompositionDemandCycleCondition
└── RuntimeControlCondition
    ├── RuntimeContextClosingCondition
    ├── RuntimeContextClosedCondition
    ├── ForeignRuntimeContextCondition
    ├── EvaluationAlreadyCommittedCondition
    ├── RecoveryAlreadyConsumedCondition
    ├── IllegalRuntimeTransitionCondition
    └── InvalidRecoveryResultCondition
#+end_src

| Condition class | Continuation authority | DecisionReceipt |
|-
| semantic qualification rejection | inspect, abort, or replace context | required |
| unexpected observation failure | inspect, abort, or replace context | absent |
| G0 cycle | inspect, abort, or replace context | absent |
| active-composition cycle | inspect or abort current composition | absent |
| evaluation resource limit | determined by affected scope | absent |
| runtime-control invariant violation | non-continuable; abort current operation | absent |

Condition diagnostic payload and snapshot presentation belong to
[[file:45-04-observability-and-debugging.org][45-04]].  A condition may reference
a DecisionReceipt owned by 45-02, but it cannot create or amend one.

* Closing and replacement

Closing atomically stops new RuntimeLease issuance and enters =closing=.
Already-running operations may reach one bounded terminal publication or abort
boundary.  Dormant captured continuations hold no lease and cannot keep a
context alive indefinitely.

If close begins during qualification:

1. no new cell, waiter, or public composition starts;
2. the current evaluator may publish its one terminal outcome;
3. a passing outcome does not reactivate the closing context;
4. after active leases drain, the context becomes =closed=;
5. its operational registry is discarded.

Pure detached diagnostics and already-produced pure POO values remain
inspectable after close.  New context-bound acquisition, mutation, publication,
and recovery are forbidden.

=replace-runtime-context= closes the failed context and creates a new context.
It may preserve Requirement and Policy or accept intentionally changed ones.
It never resets the old cell.

#+begin_src text
REPLACEMENT_RUNTIME_CONTEXT_ID=always-new
REPLACEMENT_CELL_ADDRESS=always-new
REPLACEMENT_QUALIFICATION_KEY=may-be-same-or-changed
OLD_CONTEXT_REACTIVATION=forbidden
OLD_CELL_RESET=forbidden
#+end_src

* Ownership boundary

- 45-02 owns Requirement, Observation, Policy, and DecisionReceipt semantics.
- This module owns runtime gating, state, condition delivery, and recovery.
- 45-04 owns event and diagnostic presentation.
- 45-05 owns lineage and wait-graph cycle detection.
- 45-07 owns public composition; it never exposes this runtime substrate.
- GSLPH may run runtime/recovery tests but owns none of these values.

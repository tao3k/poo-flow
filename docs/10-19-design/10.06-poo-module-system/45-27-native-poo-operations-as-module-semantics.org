#+title: Native POO Operations as Module Semantics
#+startup: overview

* Status

Accepted design.

This document maps the native =gerbil-poo= operation surface catalogued by
[[file:45-26-native-gerbil-poo-operation-surface.org][45-26]] directly onto the
POO Module System.

It does not rename native operations, introduce a facade language, or model
modules as records interpreted by a runtime.

The POO-native contracts governing inherited slot combination are defined by
[[file:45-28-poo-native-slot-contracts-and-algebraic-laws.org][45-28]].

* Decision

The POO Module System is an application and extension of the native POO object
language:

- object definitions express module and policy prototypes;
- open-recursive slots express imports and mutually recursive dependencies;
- inherited slot computations express semantic refinement;
- nested POO objects express submodules;
- slot demand expresses Capability demand;
- reflection supports structural observation and MOP extension;
- native mutation crosses an explicit object-generation lifecycle boundary.

The module system adds identity, Capability, authority, condition, provenance,
observability, budget, and receipt contracts as POO slots and prototypes.  It
does not add another evaluator.

* Operation-to-semantics map

| Native operation | POO Module System meaning |
|------------------+---------------------------|
| =.o=, =.def= | Define module, policy, Capability, evidence, breakpoint, and recovery prototypes |
| =self= | Refer to the final fixed-point instance, including slots supplied by other refinements |
| direct supers | Declare prototype inheritance and mixin dependency |
| extra-slot bindings | Express lazy cross-slot requirements used by imports and Capability dependencies |
| slot override | Supply the more-specific same-lineage semantic computation |
| ==>= | Always combine an inherited slot result according to the slot contract |
| ==>.+= | Refine an inherited object-valued slot with a more-specific prototype |
| explicit inherited computation | Decide semantically when the inherited computation is demanded |
| =?= default | Supply the recursion base or structured unavailable condition |
| =.mix= | Compose prototype contributions into one higher-order object |
| =.ref= | Demand a dynamically named slot |
| =.get=, =.@= | Demand statically named or recursively nested slots |
| =.call= | Invoke a function-valued slot after the containing object is instantiated |
| =object?= | Recognize a native POO object |
| =.key?=, =.has?=, =.all-slots= | Observe structural slot availability without a parallel registry |
| native effectful operations | Perform authorized instance or prototype lifecycle transitions |

This mapping is semantic.  It does not require every slot name to be public or
every native operation to be valid at every authority boundary.

* Object definitions are module definitions

A module is a native POO object whose prototype incrementally specifies:

- identity and prototype lineage;
- imports and exported Capabilities;
- nested submodules;
- demand and convergence behavior;
- semantic evidence and conditions;
- observability projections;
- recovery and lifecycle authority.

=.o= and =.def= are therefore the primitive module-definition forms.

Gerbil hygienic macros may generate families of these native definitions, but
the expansion result is still ordinary =.o=, =.def=, slot definitions, and
=.mix= expressions.

There is no intermediate module record, manifest AST, or runtime declaration
interpreter.

* Self is the global fixed-point instance

Within a native object definition, =self= refers to the final instance produced
after all applicable prototype refinements are composed.

This is the native mechanism that allows:

- an earlier-written module to consume a Capability supplied by a later-written
  refinement;
- two module slots to depend on one another;
- a parent object to observe child results;
- a child object to use explicitly projected parent or sibling Capabilities;
- observability to project evidence generated elsewhere in the same object.

=self= is not an eagerly built environment map.  Its slots are demanded lazily
through the native fixed point.

* Supers are prototype dependencies

The direct-super part of =.o= or =.def= declares prototype inheritance.

Supers express dependency among refinements, not package-manager dependency and
not provider search order.  Native =gerbil-poo= inheritance and linearization
own their precedence semantics.

A Profile or module prototype may depend on other prototype refinements without
copying them into a registry or manually flattening their slot definitions.

Alias and re-export reachability of one canonical prototype does not create
multiple semantic contributions.

* Extra slots are lazy requirements

Extra-slot bindings provide native lazy access to slots expected from the final
instance even when the current prototype does not define them.

They are the operational basis for imports and cross-slot Capability
dependencies.  POO Flow strengthens them with:

- Capability identity;
- provider or contribution identity;
- authority and visibility scope;
- module-instance and generation identity;
- structured missing, ambiguous, or stale conditions;
- provenance.

The extra-slot binding itself is not a string-based import declaration and does
not perform provider search.

* Override is same-lineage refinement

A simple slot definition overrides the inherited computation.

In module semantics this represents a more-specific same-lineage refinement,
such as:

- replacing a default condition constructor;
- specializing a diagnostic projection;
- supplying a child-specific Capability;
- overriding an abstract or unavailable base computation.

Override does not silently resolve unrelated singleton providers.  If multiple
unrelated contributions compete for one singleton Capability, the ambiguity
rules from 45-19 apply before a value is selected.

* Inherited combination

The native ==>= slot form always demands the inherited result and supplies it
to a combining function.

It is the primary operation for incrementally accumulating:

- canonical import and export sets;
- Capability contribution sets;
- immutable condition evidence;
- dependency and cycle edges;
- diagnostic projections;
- receipt collections;
- breakpoint and policy contributions.

The combining function is determined by the slot's semantic contract.
Native ==>= does not imply list append, textual order, or commutativity by
itself.

Set-valued contracts must canonicalize identity and be insensitive to
admission order.  Ordered refinement contracts preserve explicit prototype
precedence.  Authority and budget contracts use attenuation and conservation
rather than union.

* Nested prototype refinement

The native ==>.+= slot form refines an inherited object-valued slot with an
overriding prototype.

This is the ordinary mechanism for:

- adding or refining a submodule;
- extending a nested fixed-point object;
- refining a child observability view;
- adding child policy behavior;
- specializing a nested Capability object.

It preserves the inherited nested object's other slots and prototype behavior.
It does not flatten the child into a path or replace it with an alist patch.

* General inherited computation

The native form that binds an inherited computation, conventionally named
=next=, allows a slot to decide whether and when inherited behavior is
demanded.

It supports:

- condition-specific recovery;
- authorized delegation;
- conditional fallback to an inherited same-lineage computation;
- short-circuiting after a stable resolution;
- suspending before an external handoff;
- resuming after evidence revalidation.

This is library-level native POO code.  It is not a raw
=(lambda (self super) ...)= user interface and does not authorize raw
conditionals inside =compose profiles=.

A call to =next= follows the native inherited slot chain.  It does not search
unrelated providers.

* Defaults are recursion bases

The native =?= form supplies a default value independent of =self= and
=super=.  It is the base of inherited slot recursion.

Module semantics may use defaults for:

- empty canonical contribution sets;
- empty dependency-edge sets;
- base evidence collections;
- explicit no-authority values;
- structured unavailable-condition computations;
- identity elements required by a declared slot algebra.

A default is not provider-order fallback.  It cannot choose among providers,
hide ambiguity, widen authority, or fabricate a Capability.

Defaults are overridden by more-specific defaults and participate in native
slot inheritance exactly as defined by =gerbil-poo=.

* Mix constructs the module object

=.mix= combines module and policy prototypes into one object.

The result carries both:

- the combined prototype, which remains further extensible;
- the demand-lazy fixed-point instance.

=.mix= supplies inheritance composition, but module meaning also depends on
the definitions, slot forms, demands, nested objects, reflection, identities,
and receipts surrounding it.

The fixed-point operand from 45-25 is one example of this complete operation
family.

* Slot access is the demand boundary

=.ref=, =.get=, =.@=, and =.call= are the native demand operations.

Demanding a Capability slot may:

1. identify the root, module instance, Capability, and generation;
2. force only the required native slot computation;
3. discover canonical contributions through the fixed point;
4. validate visibility and authority;
5. raise a structured continuable condition for absence, ambiguity, cycle,
   exhaustion, staleness, or denial;
6. return the demanded fixed-point value with its evidence.

These semantics are expressed by the demanded POO slots themselves.  POO Flow
does not add a =resolve-capability= evaluator in front of native access.

=.call= invokes an operation represented as a function-valued slot.  The method
therefore inherits the same object identity, lazy dependency, authority, and
condition context as other slots.

* Nested objects are submodules

An object-valued slot is a native nested module boundary.

Nested access preserves the recursive object rather than eagerly instantiating
or flattening it.  The child may contain further child objects indefinitely.

POO Flow adds canonical child prototype, embedding-edge, causal-instance,
runtime-instance, and generation identities.  Native object nesting supplies
the underlying representation and lazy computation.

Parent, child, and sibling visibility must still travel through explicit
object slots and Capability exports.  Being structurally nested does not grant
ambient authority.

* Reflection supports observation, not semantic success

=object?=, =.key?=, =.has?=, and =.all-slots= provide native structural
reflection.

They support:

- debugger and diagnostic views;
- Capability-shape inspection;
- MOP extension;
- schema and contract validation;
- nested-object navigation.

Structural presence does not prove that:

- a lazy slot converges;
- a Capability has one authorized provider;
- demanding the slot will remain within budget;
- the current observer may view its value;
- a recovery action is authorized.

Those facts require the corresponding semantic evidence and demand.

POO Flow must not copy reflected slots into a parallel registry and treat that
registry as more authoritative than the object.

* Effectful operations are lifecycle transitions

Native instance and prototype mutation remains part of the core POO language.

When an effectful operation changes state relevant to semantic identity, it
crosses the lifecycle protocol defined by 45-26:

- authorize the exact native operation;
- bind the predecessor object and generation;
- preserve mutation intent evidence;
- execute the native operation;
- invalidate affected instantiated state when required;
- close the predecessor generation;
- establish the successor generation;
- emit an immutable outcome receipt.

Mutation does not revise historical receipts or masquerade as pure inherited
refinement.

* User-interface boundary

The ordinary user interface remains:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    wendao-episteme
    <native-poo-object-expression>
    production))
#+end_src

The POO expression may use the complete native operation language through
named, reusable prototypes and hygienic macros.

The user interface does not expose:

- a parallel list of operation names;
- an alist patch language;
- string-keyed slot dispatch;
- raw provider-order fallback;
- a nested duplicate of Profile composition.

The stronger abstraction comes from native prototype and slot composition
inside one outer Profile operand.

* Replay

Replay reconstructs module semantics from canonical native-operation evidence:

- prototype and inheritance identities;
- open-recursive requirements;
- slot override and inherited-combination identities;
- nested refinements;
- default and algebra identities;
- demand paths and conditions;
- reflection evidence when retained;
- authorized lifecycle transitions.

Replay does not reinterpret source syntax or build a replacement module
evaluator.

* Runtime and ownership boundary

=gerbil-poo= owns native object and slot semantics.

POO Flow owns the module-level contracts attached to those operations:
identity, Capability, authority, condition, budget, observability, provenance,
generation, and receipts.

Gerbil hygienic macros may generate repeated native definitions and validate
their static contracts.

The runtime preserves demand and lifecycle evidence.  It does not reinterpret
or replace native POO operations.

The harness validates mapping laws and receipts.  It is not a POO operation,
Capability provider, or evaluator.

* Implementation checklist

- [ ] Define modules and policies as native =.o= or =.def= prototypes.
- [ ] Use =self= for final-instance open recursion.
- [ ] Use direct supers for prototype dependencies.
- [ ] Bind lazy cross-slot requirements through native extra slots.
- [ ] Reserve simple override for more-specific same-lineage computation.
- [ ] Assign every ==>= slot an explicit semantic combining contract.
- [ ] Use ==>.+= for nested object and submodule refinement.
- [ ] Use inherited =next= only for native same-lineage delegation.
- [ ] Use =?= only as a recursion base or declared algebra identity.
- [ ] Construct higher-order module objects with native =.mix=.
- [ ] Treat =.ref=, =.get=, =.@=, and =.call= as demand boundaries.
- [ ] Preserve nested objects as recursively extensible submodules.
- [ ] Use native reflection without creating an authoritative registry.
- [ ] Route native mutation through explicit lifecycle generations.
- [ ] Expand macros directly to the mapped native operations.
- [ ] Test every operation-to-semantics mapping against pinned =gerbil-poo=.
- [ ] Verify that Mermaid edges explain the relevant state or transition
      without mechanical label prefixes.

#+title: Provider Runtime Search Closure

* Normative responsibility

This module owns the English-only POO Flow contract for resolving the provider
capability required by an effect intent.  It defines:

- the boundary-scoped provider search closure;
- candidate identity and qualification;
- same-lineage refinement composition;
- missing-provider and ambiguous-provider outcomes;
- policy-authorized recovery and closure recomputation;
- evidence connecting provider selection to runtime handoff.

It does not own Profile or Mix authoring, effect execution, effect evidence-state
transitions, package management, build-system resolution, or generic POO cycle
evaluation.

* Ownership boundary: gerbil-poo mechanism and POO Flow governance

=gerbil-poo= remains the sole Scheme POO implementation.  It owns prototype
identity, refinement composition, lazy demand, memoization, fixed-point
mechanics, and generic lineage/cycle evidence.

POO Flow owns:

- the structural boundary from which provider resolution begins;
- the capability-space closure admitted by containment and explicit imports;
- provider qualification policy;
- the selected, missing, or ambiguous resolution result;
- recovery authority and selection receipts.

[[file:45-07-user-composition-and-mix-module-interface.org][User Composition And Mix Module Interface]] owns Profile, Mix, and capability
composition.  [[file:45-09-effect-intent-suspension-handoff-reinjection.org][Effect Intent, Suspension, Runtime Handoff, And Receipt Reinjection]]
owns suspension and handoff after resolution.  [[file:45-05-lineage-and-cycle-detection.org][Lineage And Cycle Detection]]
owns wait-graph and cycle diagnosis.

* Capability identity

An effect intent requires a POO capability prototype identity.  The required
capability is not identified by:

- a global string or symbol registry;
- a Gerbil module name;
- a =gerbil.pkg= package name;
- a Bazel or Nix target;
- registration order.

A provider candidate qualifies by satisfying the required POO capability
lineage and the boundary's governance policy.  Textual equality of names does
not establish capability identity.

The selected object is a POO provider capability.  It is not an open runtime
handle.  Runtime-local handles may be created only after authorized handoff and
remain =context-bound=.

* Boundary-scoped search closure

Resolution begins in the capability space of the structural boundary that owns
the suspended demand.  Its permitted closure contains:

1. providers contributed locally at that boundary;
2. same-root refinements composed at that boundary;
3. providers reachable through explicit lazy Mix =imports=;
4. providers reachable through an explicitly inherited parent capability
   space.

There is no implicit global fallback.  A parent scope participates only when
the child boundary inherits that capability space through the POO composition
structure.

Containment and import paths remain distinct:

- containment determines capability identity scope and parent inheritance;
- an import contributes a dependency edge without reparenting the imported
  provider;
- the same local identity under different parents remains distinct;
- unrelated capability roots do not acquire precedence from traversal order.

  I["State: immutable effect intent"] -->|"requires a POO capability root"| L["State: boundary-local capability space"]
  L -->|"normal POO refinement within the same lineage root"| C["State: qualified local candidates"]
  L -->|"follow explicit lazy Mix imports without reparenting"| E["State: imported capability candidates"]
  L -->|"follow explicitly inherited parent capability space"| P["State: parent-scope candidates"]
  C -->|"compose same-root refinements through gerbil-poo"| M["State: maximal qualified provider set"]
  E -->|"preserve imported identity and dependency path"| M
  P -->|"preserve containment scope and inheritance path"| M
  M -->|"exactly one maximal candidate"| S["State: selected POO provider capability"]
  M -->|"no qualified candidate"| N["State: continuable missing-provider condition"]
  M -->|"multiple incomparable candidates"| A["State: continuable ambiguous-provider condition"]
  S -->|"pure selection only; no runtime handle or effect"| H["State: authorized handoff candidate"]
  N -->|"restart supplies or refines capability within authority"| L
  A -->|"restart excludes or refines a candidate within authority"| L
#+end_src

The closure is a scoped candidate evidence set, not a sequential search.  The
arrows into the maximal qualified provider set are evidence projections, not
list-order precedence.  Candidate comparison uses POO lineage and the already
approved boundary-local refinement order.

* Same-root refinement and incomparable roots

Candidates sharing the required capability lineage root are normalized through
ordinary =gerbil-poo= prototype composition.  Boundary-local order is preserved
and =super= remains limited to the same lineage root.

Candidates from unrelated roots remain incomparable.  The resolver MUST NOT
invent cross-root precedence from:

- local-before-imported traversal;
- parent-before-child or child-before-parent traversal;
- registration or discovery order;
- lexical provider names;
- package or build dependency order.

If qualification yields exactly one maximal provider, resolution succeeds.  If
multiple incomparable maximal candidates remain, resolution raises a
structured continuable ambiguous-provider condition.

* Lazy imports, recursive modules, and fixed points

Mix =imports= are lazy POO dependencies.  They are not Gerbil imports,
=gerbil.pkg= dependencies, Bazel targets, or Nix module declarations.

Provider closure traversal uses =gerbil-poo= demand, memoization, fixed-point,
and cycle evidence.  POO Flow MUST NOT introduce a local linearizer, eager graph
walker, fallback evaluator, or second fixed-point implementation.

Recursive capability spaces may be productive.  A repeated lineage node alone
is not failure.  The existing lineage contract determines whether new evidence
is produced, a demand is waiting on an external boundary, or a non-productive
cycle exists.

* Resolution outcomes

** Selected provider

Selection succeeds only when one maximal qualified POO provider capability
remains.  The result includes evidence for:

- the requesting structural boundary;
- the required capability root;
- local, containment, and import paths examined;
- same-root refinement normalization;
- the selected provider identity and provenance;
- the governing policy identity.

Selection does not instantiate a runtime handle or invoke the provider.

** Missing provider

No qualified candidate produces a structured continuable missing-provider
condition.  Policy-visible recovery may:

- supply a POO provider capability within authority;
- refine an existing capability or policy;
- defer;
- abort the declared realization boundary.

There is no global registry fallback.

** Ambiguous provider

Multiple incomparable maximal candidates produce a structured continuable
ambiguous-provider condition.  Policy-visible recovery may:

- refine one candidate through normal POO composition;
- exclude a candidate within the declared boundary;
- refine the governing policy;
- inspect candidate-path evidence;
- defer or abort the boundary.

The resolver MUST NOT choose the first discovered candidate.

* Recovery and closure recomputation

Recovery supplies, refines, or excludes POO capabilities within explicit
authority.  Every recovery decision emits an immutable receipt describing the
prior closure, the authorized change, and the new closure identity.

The resolver then demands a new closure through =gerbil-poo=.  It does not
mutate a global registry or patch an already selected runtime handle.

Repeated resolution of the same unchanged closure may reuse =gerbil-poo=
memoization.  Lexical names and discovery order are never memoization keys.

* Handoff gate

A selected provider becomes a handoff candidate only after provider policy,
resource policy, verifier requirements, and effect-intent evidence are
qualified.  Search-closure success alone does not authorize execution.

#+begin_src mermaid
flowchart LR
  S["State: selected POO provider capability"] -->|"provider qualification receipt"| Q["State: policy-qualified provider"]
  Q -->|"resource + verifier + intent gates pass"| H["State: authorized runtime handoff candidate"]
  Q -->|"any gate fails"| C["State: structured handoff condition"]
  H -->|"45-09 suspends and hands off once"| E["State: 45-08 declared effect operation"]
  C -->|"authorized recovery changes closure or policy"| R["State: recomputed provider closure"]
  R -->|"new evidence; never discovery-order reuse"| S
#+end_src

45-09 owns the transition from the qualified candidate to runtime handoff.
45-08 remains the sole authority for effect operation and attempt states.
Runtime-local handle and lease semantics after handoff are specified by
[[file:45-11-resource-lease-continuation-dynamic-wind.org][Resource Lease, Continuation, And Dynamic-Wind]].
Provider-capacity admission after search-closure qualification is specified by
[[file:45-13-demand-admission-backpressure-cleanup-capacity.org][Demand Admission, Backpressure, And Cleanup Capacity]].

* Search-closure receipt

Search-closure receipts use the POO object, canonical identity, projection, and
causal predecessor semantics defined by
[[file:45-15-receipt-object-canonical-evidence-projection.org][Receipt Object And Canonical Evidence Projection]].

Each resolution emits an ordered receipt containing:

- requesting context and structural boundary evidence;
- required capability lineage-root evidence;
- containment and explicit import paths;
- candidate qualification and exclusion evidence;
- same-root normalization evidence;
- selected, missing, or ambiguous outcome;
- recovery authority and predecessor receipt when recomputed.

Receipts distinguish containment from imports and provider capability objects
from runtime-local handles.  They do not serialize POO roots, closures,
continuations, active demand cells, or external handles.

* API evidence gate

The semantic contract in this module is normative.  Exact constructor, slot,
macro, and condition identifiers remain =semantic-required= until the real
=gerbil-poo= surface is:

1. =symbol-located=;
2. =behavior-proven=;
3. =flow-qualified=.

POO Flow MUST extend =gerbil-poo= when a generally reusable POO mechanism is
missing.  It MUST NOT ship a shadow provider resolver or fallback POO runtime.

* Explicit exclusions

This RFC does not authorize:

- a global provider registry;
- strings, symbols, package names, or build targets as capability identity;
- implicit traversal of Gerbil, =gerbil.pkg=, Bazel, or Nix dependencies;
- first-discovered or list-order provider selection;
- cross-root =super= or invented precedence;
- eager import forcing;
- provider execution during resolution;
- runtime-handle creation before authorized handoff;
- a local fixed-point evaluator, linearizer, or cycle detector;
- a public provider DSL before the =gerbil-poo= API is behavior-proven.

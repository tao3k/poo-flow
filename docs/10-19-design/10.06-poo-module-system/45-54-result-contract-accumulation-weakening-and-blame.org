* RFC status

- Kind :: Normative result-contract protocol

This module defines result and interface contracts as POO objects whose obligations accumulate independently from value priority. It separates contract composition conflict from concrete value violation and requires explicit authority for weakening.

* Core decision

#+begin_quote
Result and interface contracts form an order-independent conjunction of identity-addressed POO obligations. Contract accumulation is monotonic by default. Value priority cannot remove an obligation; weakening requires an independently authorized control decision and derives a new semantic identity.
#+end_quote

* Typst formalization: monotonic accumulation and authorized weakening

Let a contract set be an identity-addressed predicate over obligations.
Accumulation is set union, while validation is conjunction over every active
obligation.

#+begin_src typst
$
  C &: "Obligation" -> "Prop" \
  (C_1 plus C_2)(o) & equiv C_1(o) or C_2(o) \
  "Valid"(C, v) & equiv
    forall o, quad C(o) => "Satisfies"(v, o) \
  (C_1 plus C_2)(o) & <=> (C_2 plus C_1)(o) \
  (C plus C)(o) & <=> C(o) \
  "Valid"(C_1 plus C_2, v) & <=>
    "Valid"(C_1, v) and "Valid"(C_2, v) \
  C_1(o) & => (C_1 plus C_2)(o) \
  C_2(o) & => (C_1 plus C_2)(o)
$
#+end_src

These laws prove order independence, identity deduplication, and monotonic
obligation retention without claiming that arbitrary Scheme predicates have a
decidable common model.

#+begin_src typst
$
  "Compatibility" &=
    "CanonicallyCompatible"
    + "ProvenIncompatible"("EvidenceIdentity")
    + "Unknown" \
  "Conflict"("Unknown") & = bot \
  "Conflict"(x) & =>
    exists e, quad x = "ProvenIncompatible"(e) \
  "AuthorizedWeakening" &=
    (C_"before", C_"after", "Authority", i_"before", i_"after", "Blame") \
  "AuthorizedWeakening"(w) & =>
    i_"after"(w) != i_"before"(w) \
  "Removed"(w, o) & =>
    "BlameIdentity"(w) = "AuthorityIdentity"(w)
$
#+end_src

Composition conflict and concrete value violation are distinct failure
constructors.  Unknown compatibility retains the accumulated set and defers
validation until a concrete value exists.

* Contract identity

Each contract has:

- =ContractAnchorIdentity=;
- =ContractRevisionIdentity=;
- contract role;
- semantic slot scope;
- pure check projection;
- declared dependency identities;
- provenance and blame role;
- evidence projection;
- optional canonical contract-algebra identity.

A raw predicate such as:

#+begin_src scheme
(lambda (value) ...)
#+end_src

is not the ordinary public contract-extension interface. An implementation may use functions internally, but the public extension path is an identity-addressed POO contract object.

* Canonical contract set

All admitted result and interface contracts for one semantic slot form a canonical set:

#+begin_src text
ContractSetIdentity =
H(
  semantic slot identity,
  canonical contract-combination policy,
  sorted distinct contract semantic identities
)
#+end_src

The semantic meaning is conjunction:

#+begin_src text
C1 AND C2 AND C3 ...
#+end_src

It is not last-wins, highest-value-priority-wins, or operand-order-wins.

Repeated contract identity is deduplicated. Sorting is used only for canonical set projection and does not define check order or semantic precedence.

#+begin_src mermaid
flowchart LR
    A["Admitted result contract A"] -->|"contribute one obligation"| S["Canonical ContractSet"]
    B["Admitted result contract B"] -->|"contribute one obligation"| S
    C["Repeated identity A"] -->|"identity-idempotent deduplication"| S
    P["Value-priority winner"] -->|"provide the active result value only"| V["Resolved value"]
    S -->|"validate every accumulated obligation"| V
    V -->|"all required contracts pass"| R["Committed semantic result"]
    V -->|"one or more contracts fail"| F["ResultContractViolation evidence"]
#+end_src

* Contract role and shadowing

Contract attachment is explicit:

- Result or interface contract :: Independently constrains the final slot result and may remain active when an implementation value is shadowed.
- Contribution implementation contract :: Validates one active contribution and is not evaluated when that implementation is shadowed.
- Admission contract :: Controls contribution participation in an admitted semantic view.
- Projection contract :: Validates pure object structure.

A contract does not inherit shadowing behavior merely because it was written near a Profile contribution. Its POO role determines whether it survives value shadowing.

Priority cannot silently delete a result or interface contract.

* Compatibility classification

Two or more contracts have one of three composition classifications:

- Canonically compatible :: Their obligations form a valid conjunction.
- Proven incompatible :: A declared contract algebra proves that no common valid value exists.
- Compatibility unknown :: No proof of incompatibility exists; retain all contracts and validate a concrete value later.

General predicate intersection is not decidable. POO Flow must not claim that arbitrary Scheme predicates have or lack a common solution.

Only verified incompatibility evidence from a declared contract algebra may produce =ContractCompositionConflict= before a value exists.

Unknown compatibility is not a conflict. It remains an accumulated contract set.

* Contract implication and redundancy

A weaker contract may be marked redundant only when a trusted contract algebra proves:

#+begin_src text
Cstrong implies Cweak
#+end_src

With canonical implication evidence:

- retain =Cstrong= as the active obligation;
- classify =Cweak= as proven redundant;
- retain provenance for both declarations;
- retain the implication proof identity.

Without proof, both contracts remain active.

Names, structural similarity, examples, or sampled executions do not prove implication.

* Monotonic accumulation

Ordinary composition can:

- add an obligation;
- preserve an obligation;
- deduplicate the same identity;
- remove only a proven redundant obligation while retaining proof and provenance.

Ordinary value priority, including =force=, cannot weaken or remove a contract.

This makes result-contract composition monotonic by default.

* Authorized contract weakening

Weakening or removing an obligation requires an explicit higher-order POO control decision, conceptually a =ContractPolicyDecision=.

The decision:

- comes from an independently admitted control Profile;
- declares the exact contract and slot scope;
- requires contract-governance authority;
- is admitted before semantic target construction;
- changes =ContractSetIdentity=;
- changes the semantic view or generation identity;
- produces a weakening receipt;
- cannot be authorized by the contribution that is being constrained.

#+begin_src mermaid
flowchart LR
    C["Accumulated ContractSet"] -->|"ordinary composition only strengthens or preserves"| S["Monotonic obligations"]
    D["ContractPolicyDecision"] -->|"explicitly request weakening"| V["Validate governance authority"]
    V -->|"authority and scope are admitted"| N["New ContractSetIdentity"]
    V -->|"self-authorized or outside scope"| F["Fail-closed contract-policy evidence"]
    N -->|"derive a changed semantic view or generation"| G["New semantic target"]
#+end_src

There is no hidden weakening through priority, resolver fallback, handler continuation, or presentation order.

* Pure contract evaluation

A semantic result contract:

- reads a resolved semantic value;
- may produce explicitly declared semantic dependency demands;
- does not read ambient clock, network, filesystem, or process state;
- holds no live capability or lease;
- performs no runtime adapter effect;
- does not depend on operand evaluation order.

An effectful health check, deployment policy, runtime validation, or observability probe belongs to the runtime plane. It is not a pure semantic result contract.

* Contract dependencies and fixed point

A contract may depend on other semantic slots. Every dependency is explicit:

#+begin_src text
value slot X
-> result contract C
-> dependency demand slot Y
#+end_src

Contract dependencies:

- have stable identities;
- enter the demand graph;
- may participate in a current-generation SCC;
- are subject to fixed-point and evaluation budgets;
- preserve contract provenance in cycle evidence;
- do not force unrelated slots;
- activate only when the related result is demanded.

A shadowed implementation contract contributes no dependency demand.

#+begin_src mermaid
flowchart LR
    X["Demanded result slot X"] -->|"activate accumulated contract set"| C["Result contract C"]
    C -->|"declare semantic dependency"| Y["Demand slot Y"]
    Y -->|"dependency may return to X"| S["Current-generation SCC evidence"]
    C -->|"must not demand unrelated slots"| N["Lazy contract boundary"]
    D["Shadowed implementation contract"] -->|"does not activate"| N
#+end_src

* Lazy structured values and coverage

Validation of a lazy structured result records =ContractCoverageProjection=.

Coverage may indicate:

- the whole value is validated;
- specific slots or paths are validated;
- validation is deferred until a sub-slot demand;
- validation is inconclusive because of an operational failure.

A partial check cannot claim whole-value validity.

Coverage identity participates in proof and cache identity. A later sub-slot demand may extend coverage without changing the business value identity.

* Contract check cache

Contract validation is independently reusable:

#+begin_src text
ContractCheckIdentity =
H(
  resolved semantic value identity,
  ContractSetIdentity,
  ContractCoverageProjection,
  contract evaluator protocol identity
)
#+end_src

Reuse requires all four identities to match.

The key excludes:

- worker or scheduler;
- runtime token or lease;
- deadline and remaining budget;
- source path and line;
- logger and evidence sink.

An operationally interrupted check does not become a passing or failing semantic contract result.

* Violation and recovery

=ResultContractViolation= is a semantic condition and may enter continuable recovery.

Legal recovery proposals may:

- replace the active contribution;
- provide a new value;
- repair a semantic dependency;
- introduce an authorized =ContractPolicyDecision= that derives a weaker contract set;
- terminate composition explicitly.

A handler cannot continue the old generation as if the invalid value satisfied the contract.

Any decision that changes value, dependency, or contract set derives a new semantic generation.

* Blame

Contract evidence identifies blame according to role:

- provider or implementation blame when an active contribution violates its declared guarantee;
- composition-policy blame when admitted contracts are proven incompatible;
- control-plane blame when an unauthorized weakening is attempted;
- runtime-owner blame for operational interruption rather than semantic violation;
- consumer or input-provider blame where a contract explicitly governs supplied input.

Blame is identity-addressed and evidence-backed. It is not inferred from source position or operand order.

* Evidence requirements

Contract evidence records:

- contract anchor and revision;
- role and semantic slot scope;
- declaring Profile and module identity;
- =ContractSetIdentity=;
- deduplication or implication proof;
- compatible, unknown, or proven-incompatible classification;
- resolved value identity;
- coverage projection;
- pass, violation, or operationally inconclusive result;
- blame identity and role;
- weakening authority and receipt;
- dependency-demand and SCC evidence.

Evidence generation remains lazy and does not force shadowed implementation values.

* Contract laws

- Identity idempotence :: Repeating one contract identity does not duplicate obligation.
- Order independence :: Declaration order does not change conjunction.
- Monotonicity :: Ordinary composition preserves or strengthens obligations.
- Proof-gated redundancy :: A contract is removed as redundant only with implication evidence.
- Proof-gated conflict :: Early incompatibility requires contract-algebra proof.
- Role preservation :: Shadowing behavior follows declared contract role.
- Pure checking :: Semantic contract evaluation performs no runtime effect.
- Coverage honesty :: Partial validation does not claim whole-value validity.
- Authority-gated weakening :: Weakening requires independent governance authority.
- Generation integrity :: Value or contract-set recovery derives a new semantic generation.

* Non-goals

- Do not let value priority or =force= remove result contracts.
- Do not guess arbitrary predicate compatibility or implication.
- Do not execute shadowed implementation contracts.
- Do not treat runtime health checks as pure semantic contracts.
- Do not accept partial validation as whole-value proof.
- Do not let a handler ignore violation in the old generation.
- Do not add a public contract macro, raw predicate DSL, or contract registry.

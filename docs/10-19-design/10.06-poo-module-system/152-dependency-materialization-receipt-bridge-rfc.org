#+title: RFC 152 - Dependency Materialization Receipt Bridge
#+status: implementation-validated-owner-publication-pending

* Decision

The identified and versioned POO dependency source contract is the sole
canonical owner of dependency identity.

The Gerbil-Bazel project receipt does not become a second identity owner.  It
records resolver observations produced while materializing the project action.
The JSON contract artifact used by a consumer validator is likewise a
deterministic projection of the compiled POO contract, not an independent
manifest.

Org authoring and governance are outside this first-layer identity boundary.

* Rejected shortcut: filling package identity

=packageIdentity= and =packageRevision= in
=gerbil-bazel.project-receipt.v1= are compatibility fields owned by the Gerbil
package layer.  Current project producers intentionally emit empty strings.

The bridge therefore does not fill either field with a Bazel label, a local
path, a POO object serialization, or a dependency list.  Such values would
collapse package identity, dependency identity, and action observation into one
ambiguous field.

* Receipt model

The outer project receipt requires:

#+begin_src json
{
  "dependencySourceResolutions": [
    {
      "schema": "gerbil-bazel.dependency-source-resolution-receipt.v1",
      "logicalPackage": "gerbil-utils",
      "resolutionMode": "hermetic-archive",
      "canonicalPackagePath": "",
      "canonicalUri": "https://github.com/mighty-gerbils/gerbil-utils",
      "expectedRevision": "...",
      "observedRevision": "...",
      "sourceSnapshotDigest": "sha256:...",
      "sourceFileCount": 106,
      "worktreeDirty": false,
      "outcome": "resolved"
    }
  ]
}
#+end_src

These entries are observations.  Their expected values are admitted only by
comparison with the POO contract artifact projection.

* Exactly-once materialization

=GerbilProjectInfo= carries a postorder depset of source-resolution receipt
files.  Each =gerbil_project_compile= action:

1. combines direct resolver receipts with transitive receipts;
2. deduplicates by Bazel artifact identity through the depset;
3. writes one deterministic manifest for the action;
4. invokes the receipt writer once when the manifest is non-empty;
5. materializes one =dependencySourceResolutions= array in the outer receipt.

The no-dependency fast path emits an explicit empty array.  It does not invoke a
second writer and it does not omit the field.

This establishes exactly-once materialization at the project-action boundary.
It does not claim that two different repository receipts with contradictory
contents are equivalent.  POO consumer validation rejects duplicate logical
packages and any mismatch against the canonical contract.

* Contract artifact projection

The canonical Scheme object now has an explicit =version= slot.  A dedicated
Gerbil project action loads the already compiled contract and writes:

- projection schema;
- contract kind;
- contract schema;
- contract version;
- the complete dependency entry fields.

The projection reads the live POO object.  No SHA, revision, URI, repository
name, strip prefix, or archive URL is duplicated in Starlark or in the consumer
validator.

The compile receipt consumer receives this artifact as an explicit injected
input.  It compares every outer resolver observation with the corresponding POO
dependency entry and fails closed on:

- missing or additional dependencies;
- duplicate logical packages;
- URI mismatch;
- expected or observed revision mismatch;
- snapshot digest mismatch;
- non-hermetic resolution;
- a local canonical path on a hermetic archive;
- dirty worktree state;
- non-positive source file count;
- an outcome other than =resolved=.

* Publication gate

The generic receipt implementation is validated in a temporary Gerbil-Bazel
owner checkout based on POO Flow's exact pinned commit
=94c31673d6702e7c65b42f74d688dfdb53e79f01=.

The implementation is not closed until all of the following hold:

1. the owner change is committed and published in =tao3k/gerbil-bazel=;
2. POO Flow pins that published owner commit without a local override;
3. the same receipt and no-op gates pass from the published pin;
4. RFC 151 records the published commit and final replay receipt.

Until then, the local override is evidence for the design and implementation,
not a distributable dependency closure.

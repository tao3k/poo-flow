* Status

This RFC records an approved proof-ownership boundary.

- [X] POO Flow adopts the POOF theory, constructions, and proofs.
- [X] =gerbil-poo= remains the only POO implementation used by POO Flow.
- [X] POO Flow does not re-prove prototype identity, composition, fixed-point,
  =self=/=super=, object construction, or multiple-inheritance semantics.
- [X] POO Flow owns only its domain projection and conservative-extension
  obligations.
- [X] Prototype primitives are classified as direct correspondence.
- [X] Slot specifications are classified as representation refinement.
- [X] Object instantiation is classified as whole-implementation refinement.
- [X] Native C3 is classified as dependency delegation.
- [X] Correspondence closure is separate from package installation, Profile
  semantics, and generation admission.
- [X] Cross-module conservative-extension criteria are delegated to
  [[file:45-86-poo-conservative-extension-criterion-and-cross-module-obligations.org][45-86]].
- [ ] Verify the exact correspondence from the pinned POOF source to the pinned
  =gerbil-poo= implementation surface.
- [ ] Record the actually resolved =gerbil-utils= identity in a build or
  correspondence-audit receipt.
- [ ] Run the upstream POOF executable checks when a Racket runtime is
  available.

This document adopts upstream semantic authority.  It does not authorize a
second POO implementation or a competing proof.

* Central decision

The POO algebra is upstream work.

POO Flow SHALL adopt the constructive theory and executable reference
construction published as POOF.  It SHALL use =gerbil-poo= as the Gerbil Scheme
implementation of that semantic foundation.

POO Flow MUST NOT:

- derive a competing fixed-point calculus;
- re-prove native prototype composition laws;
- choose between local =.mix= and =.+= lifting formulas;
- implement an object-to-prototype conversion independent of the upstream
  construction;
- replace native C3 behavior; or
- present local conformance examples as a new proof of POO.

The work remaining in POO Flow is correspondence, projection, and conservative
extension.

* Adopted upstream content

POO Flow adopts, rather than redefines, the upstream treatment of:

- the distinction among instances, prototypes, wrappers, generators, objects,
  and classes;
- fixed-point instantiation;
- prototype identity and ordered prototype composition;
- the common final =self= supplied to composed prototypes;
- inherited computation through =super=;
- pure functional construction of object systems;
- conversion from an object representation to its prototype function;
- composition of prototype lists;
- multiple inheritance and precedence construction;
- interaction between prototype specifications and instantiated targets; and
- executable examples that witness these constructions.

These semantics are not POO Flow extension points.  A disagreement must first
be resolved against the upstream theory and pinned implementation rather than
by adding a local patch language or alternate evaluator.

* Correspondence classification

The correspondence is not uniformly a lexical-name mapping.  Each row belongs
to one of four explicit categories.

** Direct prototype correspondence

The core prototype definitions are alpha-equivalent constructions:

| POOF reference | =gerbil-poo= implementation | Classification |
| =fix= / =instantiate-prototype= | =instantiate-proto= | Direct correspondence |
| =mix= / =compose-prototypes= | =compose-proto= | Direct correspondence |
| =identity-prototype= | =identity-proto= | Direct correspondence |
| =compose-prototype-list= | =compose-proto*= | Direct correspondence |

The name =mix= in the POOF paper denotes prototype composition.  It corresponds
to =compose-proto=.

It MUST NOT be mapped to the =gerbil-poo= object operation =.mix=.  The shared
English word does not place those operations at the same semantic layer.

** Slot representation refinement

POOF expresses slots as prototype functions.  =gerbil-poo= refines those
functions into explicit slot-specification variants and hygienic syntax.

| POOF role | =gerbil-poo= representation | Classification |
| Constant slot | =$constant-slot-spec= | Representation refinement |
| Delayed slot computation | =$thunk-slot-spec= | Representation refinement |
| Computation over final =self= | =$self-slot-spec= | Representation refinement |
| Computation over =self= and inherited value | =$computed-slot-spec= | Representation refinement |
| =$slot/modify= | Computed slot and ==>= surface | Syntax and representation refinement |
| =slot-ref= | =.ref= and =.@= | Lazy cached operational refinement |
| Unbound slot / bottom | =NoApplicableMethod= | Error-model refinement |

The representation is richer, but the semantic roles of final =self= and
inherited computation remain upstream POO semantics.

** Whole-object implementation refinement

POOF constructs an object result by:

#+begin_example
precedence list
  -> object-prototype-function
  -> ordered prototype-function list
  -> prototype composition
  -> fixed-point instantiation
#+end_example

=gerbil-poo= refines this as:

#+begin_example
object supers graph
  -> compute-precedence-list!
  -> compute-slot-funs!
  -> apply-slot-spec
  -> lazy .ref
#+end_example

Therefore =object-prototype-function= has no required one-name alias in
=gerbil-poo=.  Its correspondence is realized jointly by:

- the =object= representation;
- =instantiate-object!=;
- =compute-precedence-list!=;
- =compute-slot-funs!=;
- =apply-slot-spec=; and
- =.ref=.

This is an implementation refinement of the adopted object/prototype
construction.  It is not a new proof and not a POO Flow extension point.

** Object-level operations

The native operations =.mix=, =.extend=, and =.+= belong to the
=gerbil-poo= object API:

- =.mix= constructs an object from multiple supers;
- =.extend= constructs an object with one base and direct slot
  specifications; and
- =.+= applies an override object's slots, defaults, and supers to a base.

They are derived object-representation operations above the prototype
primitives.  They MUST NOT participate in a competition to redefine POOF
=mix=.

** C3 dependency delegation

At the pinned =gerbil-poo= revision, =compute-precedence-list!= delegates the
linearization algorithm to:

#+begin_example

#+end_example

The pinned =gerbil.pkg= declares:

The source declaration identifies the dependency repository but does not record
a resolved revision in that file.  A correspondence or build receipt MUST
therefore include the actual resolved =gerbil-utils= identity used to supply

This evidence requirement does not transfer ownership of =gerbil-utils=,
=clan/list=, their build, or their publication to POO Flow.  POO Flow records
the resolved dependency boundary only when making a verified correspondence
claim.  An absent identity leaves that claim incomplete; it does not create a
runtime Git-identity gate.

* Minimal correspondence receipt

The correspondence receipt is a low-frequency proof-source record.  It is not
a package manifest, lockfile, dependency resolver, module graph, runtime
capability, Profile operand, or generation-admission input.

The minimal receipt contains only:

| Field | Meaning |
| Theory source | POOF repository and commit |
| Implementation source | =gerbil-poo= repository and commit |
| Delegated implementation source | Resolved =gerbil-utils= identity supplying =:clan/list= |
| Correspondence result | Completion of the four correspondence classifications |
| Unresolved blocker | Exact fact that prevents a complete correspondence claim |

The receipt is an ordinary POO evidence value serialized by the existing
evidence machinery.  This RFC does not introduce a receipt DSL, receipt macro,
or dependency schema.

The receipt may be produced only for:

- an architecture correspondence audit;
- a release-evidence refresh; or
- a change to an adopted theory or implementation revision.

It MUST NOT be produced or consulted for:

- each =compose profiles= evaluation;
- slot projection;
- Profile semantic admission;
- generation publication;
- module loading; or
- =gerbil.pkg= dependency installation.

The receipt excludes package closure, Merkle closure, installation plans,
filesystem paths, build-system policy, and non-deterministic timestamps.

** Three independent outcomes

The following outcomes MUST remain distinct:

| Outcome | Owner and effect |
| Package, compile, or module-load failure | Gerbil and =gerbil.pkg= expose the operational failure |
| Incomplete correspondence evidence | A verified correspondence claim cannot be made |
| Profile semantic admission failure | The Profile contract rejects the semantic value |

One outcome MUST NOT be projected into either of the other two.

In particular, a missing resolved =gerbil-utils= identity does not prohibit an
otherwise working native POO runtime.  An actually incompatible dependency is
exposed by its real package, load, compile, or test boundary.

** Racket test blocker

The missing local Racket runtime prevents refreshing the executable POOF test
receipt.  It does not invalidate the published theory, make Racket a POO Flow
dependency, prevent use of =gerbil-poo=, or close Profile generation
admission.

* POOF to gerbil-poo correspondence obligation

POO Flow depends on =gerbil-poo= rather than executing the Racket reference.
Therefore one bounded implementation-correspondence obligation remains.

The correspondence review MUST verify the four classifications recorded above:

- direct prototype correspondence;
- slot representation refinement;
- whole-object implementation refinement; and
- C3 dependency delegation with a resolved =gerbil-utils= identity.

This review verifies lineage and implementation correspondence.  It does not
repeat the denotational proof.

If an exact correspondence cannot be established, the correspondence claim
remains incomplete and the discrepancy belongs first to the pinned
implementation boundary.  Ordinary runtime admission is not decided by this
audit.

* POO Flow Profile projection obligations

POO Flow introduces domain meaning through POO slots and composition strategy.
It must establish only the following projection properties.

** Domain-slot projection

Profile identity, imports, capabilities, requirements, contributions, and
policies MUST remain ordinary POO values and slots.

Projection MUST NOT require:

- a raw alist or record DSL;
- a symbolic operand kind;
- a package or filesystem search;
- a global provider registry; or
- a second object model.

** Operand correspondence

A normal Profile object and a higher-order Profile extension MUST enter the
adopted upstream composition path without reordering or category batching.

POO Flow may expose named, pure helpers, but those helpers MUST project to the
pinned native operations.  They cannot define new POO algebra.

** Root correspondence

The user composition MUST produce one native fixed-point root.  Module reload,
Profile revision changes, observability, or governance decisions cannot
silently instantiate a second root inside the same generation.

** Failure correspondence

Native structural failures remain native structural failures.  POO Flow may
attach identity, path, generation, and evidence context, but MUST NOT turn an
inheritance error into a successful Profile or a resumable semantic recursion.

* Conservative-extension delegation

POO Flow adds operational capabilities above the adopted POO semantics, but
the cross-module correctness criterion is not owned by this proof-adoption
RFC.

[[file:45-86-poo-conservative-extension-criterion-and-cross-module-obligations.org][45-86]] owns the erasure law, result and failure preservation, budget
restriction, resumption continuity, cache equivalence, observation
non-interference, and single-root preservation.

This RFC supplies only the adopted POO semantic baseline against which those
obligations are evaluated.

* Conformance tests are not replacement proofs

POO Flow SHOULD retain a small set of correspondence witnesses that protect the
pinned integration from drift.

Appropriate local witnesses include:

- the pinned POOF and =gerbil-poo= identities;
- the mapping between their core constructions;
- one ordinary Profile object composition;
- one higher-order Profile extension;
- one mixed ordered composition;
- one native structural failure with attached POO Flow context; and
- one observation or suspension that leaves the native result unchanged.

These tests demonstrate that POO Flow is connected to the adopted semantics.
They do not re-establish the general POO proof.

* Prohibited duplication

The following work is outside the approved architecture:

- a local proof of =fix= or =mix=;
- a local proof of prototype identity or associativity;
- a new object-to-prototype algebra;
- a =.mix=-versus-=.+= candidate competition;
- a replacement C3 implementation;
- copying the full upstream test suite into POO Flow;
- claiming that local examples supersede the POOF source;
- calling unexecuted upstream checks green; or
- treating a missing Racket runtime as a failing upstream theorem.

#+title: Thin Use-Composition, Use-Module, and Profile Projection
#+startup: overview

* Status

The architecture in this RFC is accepted.

This acceptance freezes expansion responsibility for the already
accepted public surface.  It does not introduce a new form, broaden
either macro, or replace the existing User Interface RFCs.

* Scope

This RFC defines the thin phase projection of:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    resilient-production))
#+end_src

It separates:

- hygienic binding and selection syntax;
- ordinary pure functional composition;
- first-class POO strategy and profile values;
- evaluation, authority, observability, and runtime responsibilities.

* Central decision

=use-composition= and =use-module= are the only macro projections in
this expression.

=compose= is an ordinary pure function.  =profiles= is a first-class
native POO strategy value.  Module selections, profile values, and the
resulting composition remain ordinary native POO values.

The macros provide necessary hygienic binding and phase semantics only.
They do not own Module evaluation, import closure, fixed points, profile
merge policy, capability authority, observability, recovery, package
management, build behavior, or runtime effects.

* use-composition responsibility

=use-composition= accepts one user-visible binding identity and one
ordinary composition expression.

Its semantic responsibility is to:

- establish the binding hygienically in the admitted definition
  context;
- preserve the expression as an ordinary value computation;
- associate expansion evidence and source mapping with the user call
  site;
- report binding or expansion failure at that call site.

It does not:

- create a global registry;
- initialize a runtime;
- install or discover packages;
- evaluate a Module closure at macro phase;
- publish deployment state;
- add an implicit =initial= or lifecycle phase;
- wrap the expression in another composition object.

The exact Gerbil core binding form used by an implementation is an
implementation detail as long as the admitted binding and evidence
semantics are preserved.

* use-module responsibility

=use-module= hygienically resolves an already available native Module
binding and an admitted profile selector.

It projects that selection to an ordinary native Module/Profile POO
value suitable for =compose=.  It preserves source mapping for both the
Module binding and selector.

It does not:

- import a Gerbil package;
- traverse the Module =imports= closure;
- compute a fixed point;
- inspect or materialize capabilities;
- run profile composition;
- execute build or test tools;
- initialize providers or adapters;
- create runtime handles;
- perform recovery or telemetry effects.

Module import reachability and recursive closure are semantic
evaluation responsibilities after expansion.  They are not Gerbil macro
import behavior.

* compose and profiles responsibility

=compose= remains an ordinary pure function that accepts a composition
strategy and ordinary values.

=profiles= is a first-class native POO strategy.  It owns the pure
ProfileBundle composition semantics admitted by the relevant Module and
profile RFCs.

The strategy may use native =gerbil-poo= prototype composition,
dispatch, slot operations, priority evidence, and functional
combinators.  It does not require a macro wrapper.

An advanced POO profile value participates directly:

#+begin_src scheme
(use-composition research-system
  (compose profiles
    (use-module wendao-episteme research)
    research-observability-policy
    application-research))
#+end_src

The advanced values carry their own admitted POO evidence.  The public
composition syntax does not grow a clause language for them.

* Expansion and evaluation boundary

#+begin_src mermaid
flowchart LR
  U["use-module source syntax"] -->|"hygienically resolves Module and profile-selection bindings"| M["Native Module/Profile POO value"]
  M -->|"enters composition as an ordinary value"| C["Pure compose function"]
  P["First-class profiles POO strategy"] -->|"defines admitted ProfileBundle composition"| C
  A["Advanced native POO profile values"] -->|"participate without new syntax"| C
  C -->|"returns one pure composed POO value"| V["Composition value"]
  B["use-composition source syntax"] -->|"hygienically binds the ordinary expression result"| V
  V -->|"is evaluated later by Module, authority, and observability semantics"| E["POO Flow evaluator"]
#+end_src

Macro expansion ends before the evaluator begins.  The evaluator
receives ordinary POO values and evidence rather than a private macro
AST or configuration DSL.

* Phase-aware expansion evidence

Both macros satisfy
[[file:45-120-12-phase-aware-macro-expansion-evidence-source-mapping-and-receipt-schema.org][45-120-12]].

Expansion evidence identifies source syntax, macro binding, phase,
hygienic scope, dependency evidence, expander/compiler schema, expanded
ordinary code, source mapping, and receipt.

A cache hit at macro phase does not cache ProfileBundle evaluation,
authority closure, fixed-point results, runtime materialization, or
telemetry.

* Failure projection

Expansion failures identify the user-owned form and exact responsibility:

- unresolved composition binding;
- unresolved Module binding;
- invalid profile selector syntax or binding;
- phase or hygiene mismatch;
- incomplete macro dependency evidence;
- expansion Contract failure.

Failures discovered after expansion retain the source mapping but remain
owned by their semantic layer:

- profile composition failure belongs to the =profiles= strategy;
- Module closure failure belongs to the evaluator;
- authority denial belongs to capability and Contract refinement;
- runtime materialization failure belongs to the coordinator or
  adapter.

The macro MUST NOT catch and reclassify those later failures as generic
syntax errors.

* Rejected surface and hidden behavior

The following are rejected:

- =user-composition= as a redundant outer wrapper;
- =initial= as an implicit phase;
- =poo-compose= as a wrapper around native POO composition;
- host-language =if= for profile-policy extension;
- recovery, observability, build, package, or provider clauses;
- hidden registry mutation;
- macro-phase import-closure or fixed-point evaluation;
- a macro-only ProfileBundle representation.

Higher-order policy variation is represented by native POO objects,
prototypes, dispatch, and functional values.

* Implementation admission checklist

- [ ] Keep =use-composition= limited to hygienic binding of one ordinary
  composition expression.
- [ ] Keep =use-module= limited to hygienic Module/profile selection
  projection.
- [ ] Keep =compose= an ordinary pure function.
- [ ] Keep =profiles= a first-class native POO strategy.
- [ ] Return ordinary native POO values from expansion.
- [ ] Keep ProfileBundle, authority, fixed-point, observability,
  recovery, and runtime behavior after macro expansion.
- [ ] Prevent macro-phase package discovery, import traversal, build,
  testing, provider initialization, and effects.
- [ ] Preserve call-site source mapping and phase-aware expansion
  receipts.
- [ ] Attribute post-expansion failures to their actual semantic owner.
- [ ] Accept advanced native POO profile values without adding syntax.
- [ ] Add no registry, initialization, lifecycle, or private macro AST.
- [ ] Reject =user-composition=, =initial=, =poo-compose=, host =if=,
  and recovery or infrastructure clauses.
- [ ] Apply the macro governance in
  [[file:44-current-project-programming-style.org][44]].
- [ ] Apply the phase-aware evidence contract in
  [[file:45-120-12-phase-aware-macro-expansion-evidence-source-mapping-and-receipt-schema.org][45-120-12]].
- [ ] Apply the Git source, Gerbil package, binding visibility, and POO
  Module import boundary in
  [[file:45-120-14-git-source-gerbil-package-binding-and-poo-import-closure.org][45-120-14]].

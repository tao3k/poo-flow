#+title: Module Domain Prototype Minimal Projection and Derived Closure Contract

* Status

Accepted architecture RFC.

This document fixes the minimal semantic contract of the POO Flow Module
prototype. It does not authorize implementation work and does not approve the
current prototype body without exact owner evidence.

* Scope

This RFC defines:

- Module conformance through native prototype ancestry and behavior;
- the minimal direct projections owned by every Module;
- canonical empty POO values for optional direct relations;
- values that must be derived through reachability rather than stored;
- the role of kind labels, schemas, and metadata;
- extension, evidence, and failure laws;
- the macro-governance boundary for Module declarations.

This RFC does not define:

- a fixed record schema;
- a required alist shape;
- conformance by string kind alone;
- a centralized responsibility slot;
- stored recursive imports;
- stored effective capabilities;
- a second prototype hierarchy;
- compatibility, migration, or deprecation behavior;
- implementation edits.

* Durable POO identity

The prototype and every conforming Module remain native objects of:

#+begin_example
github.com/mighty-gerbils/gerbil-poo@1c3225637525400341a09e958296962c10184ead
#+end_example

POO Flow owns the Module domain contract. =gerbil-poo= owns object identity,
slots, prototype ancestry, extension, composition, delegation, super, and
precedence.

Parser-owned evidence currently identifies:

- =poo-flow-module-interface-prototype= as a project-owned domain prototype
  candidate;
- =poo-flow-module-kind=?= as a plain kind-label equality comparison;
- interface identity, schemas, metadata, import kind, and option-policy
  selector families;
- generic object slot checks and default projections;
- native upstream object, projection, ancestry, and composition operations.

The exact body query for =poo-flow-module-interface-prototype= is blocked with:

#+begin_example
direct exact-selector provider failed: status=Some(2) stderr=
#+end_example

No current owner evidence proves that the existing prototype enforces the
minimal exports, direct imports, capability, or behavioral contract specified
here.

Therefore:

- the semantic Module prototype concept is accepted;
- the current prototype body remains unadmitted;
- the current kind comparator is diagnostic only;
- current slot-shape helpers do not prove Module conformance;
- implementation must map this RFC to verified native POO operations.

* Central decision

A Module conforms through:

#+begin_example
native POO object
  + admitted Module prototype ancestry
  + required behavioral projections
  + projection value validation
#+end_example

Conformance is not:

#+begin_example
kind string equality
  or
presence of an arbitrary slot list
  or
conversion to a matching alist
#+end_example

The minimal direct projections are:

1. stable Module identity;
2. an exports POO object;
3. a direct imports POO object;
4. a capability requirements POO object.

Everything else is either reachable through those objects, derived by semantic
evaluation, or optional diagnostic metadata.

* Behavioral prototype contract

The Module prototype defines behavior and defaults through native POO ancestry.
It is not a record declaration.

A conforming Module must:

- be a native =gerbil-poo= object;
- inherit from or otherwise satisfy the admitted Module prototype relation;
- expose stable identity through the approved identity projection;
- expose exports as a native POO object;
- expose direct imports as a native POO object;
- expose capability requirements as a native POO object;
- preserve native precedence and ancestry inspection;
- support domain validation without converting to another authoritative
  representation.

The exact upstream call forms and slot spellings remain implementation evidence,
not architecture assumptions.

* Minimal direct projections

** Stable Module identity

Module identity is required and has no implicit default.

It distinguishes:

- semantic Module identity;
- Gerbil source binding identity;
- Gerbil module identity;
- repository and package identity;
- optional Module instance identity;
- export identity.

A constructor, macro, alias, path, or kind label cannot silently replace
semantic identity.

The identity projection may contain version or provenance components defined by
their owning RFCs. This RFC does not duplicate them as independent required
slots.

** Exports object

Every Module projects an exports POO object.

The exports object may be empty for an internal Module, but selection of a
missing export fails closed.

Each export relation preserves:

- owning Module identity;
- export identity;
- Profile operand identity;
- ProfileBundle and low-level Profile identity;
- native prototype ancestry;
- responsibility reachability.

=production= is an ordinary module-scoped export identity whose value is a
ProfileBundle. It is not a required universal slot on every Module.

** Direct imports object

Every Module projects a direct imports POO object.

The Module prototype may provide a canonical empty native POO object. It may
not use a raw empty list, alist, or missing-slot default as semantic truth.

Direct imports record only immediate semantic relationships. They do not store
the recursive active imports closure.

** Capability requirements object

Every Module projects a capability requirements POO object.

The Module prototype may provide a canonical empty native POO object.

Capability requirements describe conditions; they do not issue grants.
Prototype extension and composition preserve or attenuate authority and cannot
widen it.

* Derived projections

The following values are derived and must not become independent authoritative
slots:

- selected Profile and ProfileBundle closure;
- recursive active imports closure;
- graph, loop, proof, handoff, stage, and observability responsibility closure;
- effective capability requirements after attenuation;
- capability grants admitted by an external authority;
- proof satisfaction state;
- handoff eligibility;
- runtime execution plan;
- physical Gerbil import and load projection;
- evaluation trace and evidence receipt;
- fixed-point observation state.

Derived values may be cached with identity and invalidation evidence. A cache is
an operational projection, not semantic ownership.

* Why responsibilities are derived

Responsibility objects belong to Profiles, ProfileBundles, graphs, policies, or
other reachable POO objects.

Adding a centralized =responsibilities= slot to Module would:

- duplicate the reachable object graph;
- create synchronization and stale-cache problems;
- erase local ownership;
- invite a second registry;
- make selection-insensitive closure too easy;
- conceal prototype precedence.

The Module provides roots. Reachability provides the closure.

#+begin_src mermaid
flowchart LR
  Prototype["admitted Module prototype"] -->|"provides behavior and canonical empty values"| Module["native Module object"]
  Module -->|"projects required stable value"| Identity["Module identity"]
  Module -->|"projects direct POO relation"| Exports["exports object"]
  Module -->|"projects direct POO relation"| Imports["direct imports object"]
  Module -->|"projects direct POO requirement"| CapReq["capability requirements"]
  Exports -->|"selects Profile operand"| Bundle["ProfileBundle"]
  Bundle -->|"reaches owned semantic facts"| Responsibility["responsibility objects"]
  Imports -->|"expands only from selected roots"| Recursive["recursive imports closure"]
  Responsibility -->|"contributes qualified dependencies"| Recursive
  CapReq -->|"attenuates through selected graph"| Effective["effective requirements"]
  Recursive -->|"supports evidence projection"| Receipt["admission receipt"]
  Effective -->|"supports evidence projection"| Receipt
#+end_src

Only the first four projections are direct Module contract values. The remaining
nodes are selected or derived.

* Kind labels

A kind label may help diagnostics, presentation, dispatch at a bounded adapter,
or evidence serialization.

Kind equality does not prove:

- native object identity;
- Module prototype ancestry;
- exports validity;
- direct imports validity;
- capability requirement validity;
- responsibility completeness;
- authority.

=poo-flow-module-kind=?= therefore cannot be the conformance predicate for the
new architecture.

A kind label may remain an optional diagnostic projection after it is separated
from authority and conformance.

* Schemas and metadata

Schemas and metadata are optional POO projections or bounded evidence.

They are not part of the minimal Module contract unless another RFC gives one a
specific semantic responsibility.

Metadata cannot:

- provide Module identity;
- define exports or imports;
- grant capability;
- override native precedence;
- repair an invalid Module;
- become a registry key that replaces object identity.

A schema may validate a projection but cannot become the canonical Module
representation.

* Canonical empty objects

The Module prototype may supply canonical empty POO objects for:

- exports;
- direct imports;
- capability requirements.

These defaults exist through prototype ancestry and remain native POO values.

They avoid:

- missing-slot convenience logic;
- raw empty lists;
- ambiguous absence;
- repeated allocation without identity;
- special cases in user composition.

An extension replaces or composes a canonical empty value through verified
native POO semantics. It does not patch a record field.

* Extension contract

** Identity

Extension preserves Module identity unless the operation explicitly constructs
a distinct Module with a distinct admitted identity.

** Exports

Export extension returns an exports POO object.

Duplicate export identities resolve through an admitted native ancestry rule
with evidence or fail closed. Source order and alist overwrite are invalid.

** Direct imports

Direct import extension returns a direct imports POO object.

It preserves import identity and does not materialize the transitive closure.

** Capability requirements

Capability extension returns a capability requirements POO object.

It may preserve or narrow authority. It cannot manufacture a grant or discard
an independent requirement.

** Optional projections

Optional metadata, schemas, presentation, or diagnostics may be extended only
when they remain non-authoritative and identity-preserving.

* Conformance function

Module conformance is expressed as a pure function over native POO values.

Conceptually:

#+begin_example
native object
  -> ancestry qualification
  -> required projection validation
  -> value-kind validation
  -> conformance evidence or actionable rejection
#+end_example

The conformance function:

- performs no runtime handoff;
- grants no authority;
- installs no package;
- loads no hidden registry;
- mutates no shared Module input;
- does not convert the Module to an authoritative alist;
- does not depend on a public macro.

Macros may invoke this function in a bounded compile-time or binding projection,
but they do not own its semantics.

* Macro governance

Functions and native POO objects are the default abstractions.

The small public macro surface may:

- bind one completed Module expression hygienically;
- retain source identity;
- invoke the pure conformance function;
- report phase-appropriate diagnostics;
- expand to ordinary POO-native and functional code.

It may not:

- declare a fixed slot schema;
- parse required projection clauses;
- synthesize recursive closures;
- interpret capability authority;
- manufacture prototype ancestry;
- replace behavioral conformance with syntax acceptance.

* Selection and derivation sequence

#+begin_src mermaid
sequenceDiagram
  participant Bind as "thin Module binding"
  participant Check as "pure conformance function"
  participant Module as "native Module object"
  participant Select as "use-module"
  participant Derive as "reachability evaluator"
  participant Admit as "admission boundary"

  Bind->>Check: "submits one completed POO value"
  Check->>Module: "verifies ancestry and direct projections"
  Module-->>Bind: "returns conformance evidence"
  Select->>Module: "requests one export identity"
  Module-->>Select: "returns ProfileBundle value"
  Select->>Derive: "supplies selected roots"
  Derive->>Derive: "computes responsibility, imports, and requirements"
  Derive->>Admit: "submits derived closure and evidence"
  Admit-->>Select: "returns admitted receipt or rejection"
#+end_src

The binding phase validates direct projections. Selection and evaluation derive
the active closure.

* Minimal projection laws

** Native ancestry law

Module conformance requires admitted native prototype ancestry or its exact
approved behavioral equivalent.

** Explicit identity law

Module identity has no implicit default.

** Native projection law

Exports, direct imports, and capability requirements are native POO values.

** Canonical empty law

Optional direct relations use canonical empty POO objects through prototype
ancestry.

** No missing-slot default law

Missing-slot convenience cannot define Module semantics.

** Derived closure law

Recursive imports, responsibilities, and effective capabilities are derived
from selected roots.

** Selection sensitivity law

Unselected exports and unreachable objects do not enter the active closure.

** No duplication law

A derived closure is not stored as a second authoritative Module projection.

** Kind non-authority law

Kind equality grants no conformance or authority.

** Macro transparency law

Replacing a bounded binding macro with its functional expansion preserves
conformance, identity, projection, and authority results.

* Evidence projection

A Module conformance receipt must identify:

- durable =gerbil-poo= dependency identity;
- Module object identity;
- admitted Module prototype identity;
- native precedence and ancestry identity;
- identity projection owner;
- exports object identity;
- direct imports object identity;
- capability requirements object identity;
- canonical empty objects inherited from the prototype;
- optional kind, schema, and metadata projections;
- source binding and owner identity;
- validation function identity;
- confirmation that no derived closure was treated as direct truth;
- confirmation that conformance granted no authority.

A derived closure receipt additionally identifies:

- selected export and ProfileBundle;
- reachable low-level Profiles;
- reachable responsibility objects;
- recursive imports closure;
- effective capability requirements;
- proof and handoff state;
- evaluation observation identity.

The receipts remain distinct because direct conformance and derived admission
are different judgments.

* Failure behavior

Direct conformance fails closed when:

- the value is not a native POO object;
- admitted prototype ancestry is absent;
- Module identity is absent;
- exports are absent or not a native POO object;
- direct imports are absent or not a native POO object;
- capability requirements are absent or not a native POO object;
- a kind label is used as the only conformance proof;
- a raw alist or schema is treated as the Module;
- a canonical empty relation is represented by ambiguous absence;
- validation would widen authority.

Derived admission fails closed when:

- a selected export is absent;
- an exported value is not a Profile operand;
- responsibility reachability is incomplete;
- recursive imports cannot be closed;
- capability attenuation cannot be established;
- proof or handoff evidence is missing;
- a cached closure lacks identity or invalidation evidence.

Every failure identifies the owning object, projection, prototype ancestry,
expected value kind, and missing evidence.

* Rejected alternatives

The following alternatives are rejected:

- treating a string kind as Module type;
- treating a list of slots as conformance;
- fixing the Module contract as a record schema;
- making metadata or schema authoritative;
- defaulting missing projections through generic convenience wrappers;
- storing recursive imports on every Module;
- storing a centralized responsibility closure;
- storing effective capabilities as independent truth;
- making a macro parse identity, exports, imports, or capabilities;
- creating new wrapper APIs for native slot mechanics;
- preserving current prototype behavior without exact owner evidence;
- adding compatibility aliases for the new contract.

- [ ] Every Module is a native =gerbil-poo= object.
- [ ] Module conformance verifies admitted prototype ancestry.
- [ ] Module identity is explicit.
- [ ] Module identity has no default.
- [ ] Source binding and Module identity remain distinct.
- [ ] Gerbil module and semantic Module identity remain distinct.
- [ ] Kind equality is not conformance.
- [ ] Slot presence alone is not conformance.

** Direct projections

- [ ] Every Module projects an exports POO object.
- [ ] Every Module projects a direct imports POO object.
- [ ] Every Module projects a capability requirements POO object.
- [ ] Empty direct relations are canonical POO objects.
- [ ] =production= is not a universal required slot.
- [ ] Exports preserve Profile operand identity.
- [ ] Direct imports preserve import identity.
- [ ] Capability requirements grant no authority.

** Derived values

- [ ] Recursive imports are derived.
- [ ] Responsibility closure is derived.
- [ ] Effective capability requirements are derived.
- [ ] Capability grants remain externally admitted.
- [ ] Proof satisfaction state is derived.
- [ ] Handoff eligibility is derived.
- [ ] Runtime plans are derived.
- [ ] Fixed-point observations are derived.
- [ ] Derived caches carry identity and invalidation evidence.

** Extension

- [ ] Extension preserves native object representation.
- [ ] Extension preserves Module identity by default.
- [ ] Export conflicts use admitted native precedence or fail closed.
- [ ] Direct import extension does not materialize recursive closure.
- [ ] Capability extension cannot widen authority.
- [ ] Optional metadata remains non-authoritative.
- [ ] No raw record patch operation is introduced.

** Functional and macro governance

- [ ] Conformance is a pure function.
- [ ] Conformance mutates no shared Module input.
- [ ] Conformance grants no authority.
- [ ] The binding macro accepts one completed Module value.
- [ ] The binding macro invokes functional conformance.
- [ ] The binding macro does not parse projection clauses.
- [ ] The binding macro does not synthesize closures.
- [ ] Macro expansion yields ordinary POO-native and functional code.

** Evidence

- [ ] Conformance receipts identify native prototype ancestry.
- [ ] Receipts identify all direct projection objects.
- [ ] Receipts identify canonical empty objects.
- [ ] Receipts distinguish kind labels from conformance.
- [ ] Derived receipts identify selected roots.
- [ ] Derived receipts identify recursive closure.
- [ ] Direct and derived receipts remain distinct.
- [ ] Failures identify the owning projection and missing evidence.

Implementation work is not admitted until:

- [ ] exact native ancestry checks are mapped to pinned =gerbil-poo=;
- [ ] identity projection semantics are verified;
- [ ] exports object semantics are verified;
- [ ] direct imports object semantics are verified;
- [ ] capability requirements object semantics are verified;
- [ ] canonical empty POO objects are specified;
- [ ] the pure conformance function is specified;
- [ ] kind-only and slot-only false-positive tests are specified;
- [ ] derived-closure non-duplication tests are specified;
- [ ] macro expansion evidence is specified;
- [ ] authority-neutrality tests are specified;
- [ ] the RFC set is reviewed before implementation begins.

* Consequences

The Module prototype remains small because it owns only stable direct
projections and behavior.

The architecture remains powerful because recursive imports, responsibilities,
capabilities, proof, handoff, and fixed-point observations are derived through
the selected POO object graph.

Kind labels, schemas, metadata, macros, receipts, and caches remain useful
projections without becoming semantic owners.

* Status

Proof-backed v1 refinement.

This document stabilizes effect replay safety after an authorized
latest-checkpoint restore.  It reuses the existing source-bound effect event and
trace receipt.  It does not publish a v2 event schema, a second effect universe,
or an implicit retry authority.

* Context

=SourceBoundEffectExecutionEvent= already binds an =effectId= to the exact
=ownerSubject=.  =SourceBoundEffectExecutionTraceReceipt= already binds the
transaction, fence token, registry digest, and ordered event projection.

Those facts prove declared effect ownership.  They do not prove:

- which events fall after the restored checkpoint;
- that every replay observation has a ledger entry;
- that an executable observation has a stable idempotency identity;
- that completed effects are suppressed rather than executed again;
- that non-idempotent pending effects are rejected;
- that retry authority covers the exact replay window, ledger, plan, epoch, and
  active fence token.

An authorized restore therefore does not imply a safe replay.

* Decision

The existing source-bound effect event remains the event owner.

Replay safety is expressed as five independently closed values:

1. a replay observation wraps the existing event with a trace sequence;
2. a replay window binds the restore request, canonical root, runtime epoch,
   active fence, checkpoint sequence, effect frontier, and source trace;
3. a ledger covers the observations exactly, names its idempotency provider,
   validates every key through that provider, and classifies every entry as
   completed or replay-safe pending work;
4. a plan covers the same observations exactly and maps completed entries to
   =suppressCompleted= and safe pending entries to =execute=;
5. a Cedadr retry-authority receipt binds the complete window, ledger, and plan
   values together with the restore request, epoch, and active fence.

The authority binds complete values rather than only =windowId=, =ledgerId=, or
=planId=.  Matching opaque identifiers cannot authorize substituted content.

* Mathematical model

A replay observation is:

#+begin_src typst
$ o_i = (s_i, "event"_i) $
#+end_src

For checkpoint sequence $s_c$ and effect frontier $s_F$, a closed window
requires:

#+begin_src typst
$ O = [o_1, dots, o_n] $

$ "map"("event", O) = T."events" $

$ forall i: s_c < s_i and s_i <= s_F $

$ forall i != j: s_i != s_j $
#+end_src

A ledger entry is:

#+begin_src typst
$ l_i = (o_i, k_i, c_i, r_i, "completionReceipt"_i) $
#+end_src

Exact ledger coverage and stable identity require:

#+begin_src typst
$ "map"("observation", L) = O $

$ forall i: k_i != "" $

$ forall i != j: k_i != k_j $

$ forall i: "KeyValid"_"provider"(o_i, k_i) $
#+end_src

Every entry must satisfy one branch:

#+begin_src typst
$ "EntryClosed"(l_i) =
  (c_i = "true" and "completionReceipt"_i != "")
  or (c_i = "false" and r_i = "true") $
#+end_src

The plan action is determined by the matching ledger entry:

#+begin_src typst
$ c_i = "true" => "action"_i = "suppressCompleted" $

$ c_i = "false" and r_i = "true" => "action"_i = "execute" $
#+end_src

Retry authority binds the complete proof values:

#+begin_src typst
$ A = (q, W, L, P, e, f, "allow") $

$ "RetryAuthorityClosed" =>
  A.W = W and A.L = L and A.P = P $
#+end_src

The full replay obligation is:

#+begin_src typst
$ "ReplayClosed" =
  "RestoreClosed"
  and "WindowClosed"
  and "LedgerClosed"
  and "PlanClosed"
  and "RetryAuthorityClosed" $
#+end_src

* Proof findings

The Lean model found and closes these v1 defects:

1. existing effect events have no trace sequence, so a wrapper observation is
   required to define the replay window without replacing the event schema;
2. restore authorization alone has no ledger coverage;
3. a nonempty idempotency key is insufficient unless the provider validates its
   stable observation binding and different observations have different keys
   inside the window;
4. an opaque ledger or plan identity cannot prevent content substitution;
5. completed effects must map to suppression, while pending execution requires
   an explicit replay-safe classification;
6. retry authority is independent from restore authorization;
7. the restore frontier itself had to bind the existing effect trace's active
   fence-token owner before replay could be modeled safely.

The empty-ledger and empty-idempotency-key cases are executable Lean
counterexamples.

* Ownership boundaries

| Owner | Owns | Does not own |
|-
| Existing source-bound effect trace | Exact subject/effect identity, transaction, source fence, registry, event order | Replay sequence, idempotency, or retry authority |
| Replay window | Checkpoint-to-effect-frontier observations and current restore coordinates | Ledger classification |
| Idempotency provider | Stable observation-to-key validity | Ledger coverage or retry authority |
| Effect ledger | Exact coverage, provider-validated unique keys, completion evidence, replay-safe classification | Policy allow decision |
| Replay plan | Execute-versus-suppress action for every observation | Runtime execution result |
| Cedadr retry authority | Allow decision over the exact window, ledger, plan, epoch, and active fence | Effect ownership or runtime completion |
| Replay executor | Fail-closed consumption of all closed owners | Inventing keys, retry authority, or completion evidence |

No Rust owner, Cedar semantic adapter, or new effect provider is introduced.
Cedadr remains the policy owner; the proof core consumes its abstract validity
predicate.

* Remaining proof obligations

This closure proves that a replay plan is safe to authorize.  It does not prove
that the runtime executed that plan or durably recorded its outcome.

The next independent proof must address:

- execution receipts for every =execute= and =suppressCompleted= step;
- exact projection from the authorized plan to completion receipts;
- atomic publication of the updated ledger and effect frontier;
- rejection of a second completion for the same idempotency identity;
- whether replay completion advances the checkpoint history or publishes a
  separate runtime frontier receipt.

Rollback replay remains outside ordinary latest-checkpoint resume and still
requires explicit rollback authority and epoch rotation.

* Normative responsibility

This module exclusively owns operational events, bootstrap diagnostics,
condition-first snapshots, runtime diagnostic limits, and their separation from
semantic receipts.

* Three distinct forms

| Form | Authority |
|-
| structured condition | dynamic control and authorized recovery |
| observability event | context-local operational timeline |
| DecisionReceipt | canonical semantic decision |

Neither condition nor event can be promoted into a DecisionReceipt.

#+begin_mermaid
flowchart LR
    Decision["Pure Decision"] --> Receipt["DecisionReceipt"]
    Transition["Runtime transition"] --> Event["Observability event"]
    Transition --> Condition["Structured condition"]
    Event -. "may carry receipt digest" .-> Receipt
    Condition -. "may reference rejection receipt" .-> Receipt
    Event -. "cannot alter" .-> Receipt
#+end_mermaid

Correlation is one-way:

- an event may contain =decisionReceiptDigest=;
- a rejection condition may reference the immutable DecisionReceipt;
- a diagnostic snapshot may contain semantic digest links;
- a DecisionReceipt never contains event, condition, snapshot, runtime-context,
  timestamp, sequence, sink, or GSLPH identity.

* Three-plane observability contract

Observability spans three distinct POO planes:

#+begin_export mermaid
flowchart LR
    A["Semantic plane: prototype, slot, lineage"] --> B["Evaluation plane: demand, dependency, fixed point"]
    B --> C["Control and observation plane: condition, continuation, trace"]
    C -. "recovery decision" .-> B
    B -. "realized value" .-> A
#+end_export

The semantic plane reports which prototype and refinement owns a slot.  The
evaluation plane reports demand state, dependency edges, fixed-point progress,
and suspension.  The control and observation plane reports conditions,
available restart objects, continuation boundaries, recovery choices, and
receipts.

A cycle or performance anomaly MUST be visible when the runtime first detects
the blocked demand boundary.  Its snapshot includes the ordered lineage, slot
path, dependency cycle, source location for each edge, current depth and
repetition count, pending unforced dependencies, available restarts, and any
external-effect barrier.

Tracing MUST NOT force lazy imports, capability values, or nested POO slots.
The debugger observes registered evaluation events and bounded snapshots; it
does not discover state by recursively realizing the object graph.

* Bootstrap diagnostics

Before the POO capability is ready, a bounded Gerbil-native buffer retains the
fixed event schema.  After activation, events are projected into the existing
POO Flow observability boundary.

- Sequence is strictly increasing within one runtime context.
- Cross-context events have no implicit total order.
- External sink failure cannot change Decision or cell publication.
- Overflow coalesces repetitive events, counts drops, and retains critical
  cycle/failure/closing events.

The fixed event schema is:

#+begin_src text
eventSequence
eventKind
monotonicTime
runtimeContextId
lifecycleState
qualificationKey          ; optional
evaluationId              ; optional
evaluationLineage         ; optional
conditionKind             ; optional
decisionReceiptDigest     ; optional
droppedEventCount
#+end_src

The bounded event kinds are:

#+begin_src text
runtime-context-created
qualification-started
module-observation-started
module-observation-completed
decision-produced
cell-ready
cell-failed
cycle-detected
qualification-slow
resource-limit-reached
condition-delivered
recovery-selected
runtime-context-active
runtime-context-closing
runtime-context-closed
diagnostic-overflow
#+end_src

Arbitrary attribute maps and printed Scheme exception text are not normative
event fields.  Original causes belong to structured condition transport.

The bootstrap buffer is an early transport adapter, not another event bus.  It
uses the same bounded event identities and projects each retained event once
into the existing observability boundary after activation.

If initialization fails before activation, the buffer remains available to the
detached diagnostic snapshot until the originating context closes.  Failure
does not require an observability sink to be installed.

Under pressure, the buffer may coalesce repetitive non-terminal events.  It
MUST retain the most recent =cycle-detected=, =cell-failed=,
=runtime-context-closing=, and =runtime-context-closed= events, increment
=droppedEventCount=, and expose one =diagnostic-overflow= marker rather than
allocate without bound.

* Event ordering

Within one runtime context:

#+begin_src text
pass:
  runtime-context-created
  < qualification-started
  < module-observation-started
  < module-observation-completed
  < decision-produced
  < cell-ready
  < runtime-context-active

semantic rejection:
  module-observation-completed
  < decision-produced
  < cell-failed
  < condition-delivered

unexpected observation failure:
  module-observation-started
  < cell-failed
  < condition-delivered
  and no decision-produced

cycle:
  qualification-started
  < cycle-detected
  < cell-failed
  < condition-delivered
  and no decision-produced
#+end_src

POO Flow commits or detects the runtime transition, assigns the next local
sequence, records the local event, and only then delivers the condition or wakes
waiters.  External export may batch later without changing local order.

Waiter-specific =condition-delivered= events may repeat.  They reference one
immutable owner outcome and do not become additional semantic evidence.

* Condition-first snapshot

=inspect-qualification-failure= returns a detached immutable
=QualificationDiagnosticSnapshot=:

#+begin_src text
snapshotVersion
summary
semanticLinks
causalChain
runtimeMeasures
retainedTimeline
recoveryNames
truncation
#+end_src

It contains no continuation, lease, commit token, recovery token, or mutable
runtime reference.  It remains inspectable after context close.

=summary= contains condition kind, phase, lifecycle state, and a bounded
sanitized cause summary.  =semanticLinks= contains only available canonical
digests.  =recoveryNames= contains names, never executable recovery tokens.

The causal chain is owned by
[[file:45-05-lineage-and-cycle-detection.org][45-05]].  This module owns its
bounded snapshot projection, truncation marker, and presentation.

Snapshot construction order is:

#+begin_src text
detect terminal failure
< record critical local event
< freeze bounded causal chain and measures
< construct detached snapshot
< construct condition
< deliver condition
#+end_src

This guarantees that the first handler can inspect the event that caused its
condition even when the external sink is unavailable.

* Cross-context realization-evidence admission

Observability MUST present cross-context reuse as evidence admission, not as
POO object restoration or runtime-root identity preservation.  The event model
spans the existing three planes:

| Plane | Required observation |
|---+---|
| definition | declared optional admission capability and portable value/artifact evidence |
| realization | candidate, qualification gates, admitted demand coordinates, and recomputation |
| governance | policy identity, structured non-admission condition, selected restart, and receipt |

#+begin_src mermaid
flowchart LR
  C["State: candidate observed"] -->|"definition evidence: content + lowering"| P["State: provenance gate passed"]
  P -->|"realization evidence: resolved dependency + policy identities"| E["State: environment gate passed"]
  E -->|"realization evidence: portable demanded value + no active barrier"| A["State: demand coordinate admitted"]
  A -->|"governance receipt links source evidence to new context"| R["State: admission receipt emitted"]
  C -->|"any gate mismatch"| N["State: structured non-admission condition"]
  N -->|"restart selected: recompute"| Q["State: normal realization observed"]
  N -->|"restart selected: inspect"| D["State: bounded evidence difference"]
  N -->|"restart selected: reject"| X["State: rejection receipt emitted"]
  O["State: source root, closure, continuation, or active cell"] -.->|"non-portable boundary; identity is observed but never serialized"| C
#+end_src

The realization plane emits enough ordered evidence to distinguish:

- no provider was present, so normal realization proceeded;
- no candidate was found;
- a candidate failed a named qualification gate;
- individual demand coordinates were admitted;
- policy selected recompute, inspect, or reject;
- realization continued in a newly constructed context.

Receipts MUST identify the failed or passed gate without exposing arbitrary
captured continuation state.  Evidence-difference output is bounded and follows
the existing truncation rules.  Lexical composition names may appear as
diagnostic attribution, but runtime lineage roots and provenance/content
identities remain distinct fields.

No event may state that the source and receiving runtime roots are identical.
No observability sink may reconstruct or serialize a closure, first-class
continuation, active demand cell, or suspended recovery state.

** Disposition events and barrier transitions

For every candidate demand coordinate, the realization plane records the
current disposition as one of =pure-value=, =artifact-backed=,
=context-bound=, or =suspended-or-uncommitted=.  This is an observed evidence
classification, not a user declaration.

#+begin_src mermaid
flowchart LR
  O["Event: disposition assessment started"] -->|"portable content evidence observed"| P["Event: pure-value classified"]
  O -->|"artifact identity and verifier observed"| A["Event: artifact-backed classified"]
  O -->|"runtime-local identity observed"| C["Event: context-bound classified"]
  O -->|"unresolved boundary observed"| S["Event: suspended-or-uncommitted classified"]
  S -->|"recovery resolves to portable value"| P
  S -->|"effect commits verified artifact"| A
  S -->|"resolution exposes runtime-local identity"| C
  P -->|"remaining admission gates pass"| I["Event: demand coordinate admitted"]
  A -->|"artifact verification and remaining gates pass"| I
  C -->|"policy selects recompute or reject"| X["Event: non-admission receipt"]
  S -->|"barrier remains active"| B["Event: bounded barrier snapshot"]
  B -.->|"observation only; does not advance or resume the continuation"| S
#+end_src

Disposition events MUST include:

- the demand coordinate and receiving realization-context identity;
- the disposition and its evidence references;
- the named boundary transition when a disposition changes;
- the admission gate or barrier that remains;
- the policy decision and restart receipt when reuse is not admitted.

Events for a single demand coordinate are ordered by the normal event sequence.
A sink may report a bounded condition or barrier snapshot, but observation MUST
NOT resume, replay, serialize, or otherwise mutate a continuation or effect.

Unknown or insufficient evidence is never emitted as an eligible disposition.
It is reported as an unresolved barrier or structured non-admission.  Artifact
events contain artifact identity and verifier evidence, not an open handle to
the artifact-producing runtime.

The authoritative effect transition and receipt semantics are defined by
[[file:45-08-effect-boundary-commit-reconciliation.org][Effect Boundary Commit And Reconciliation]].  This module owns their read-only
projection into the three observability planes.

Structured cancellation event ordering and clean/indeterminate terminal
receipts follow
[[file:45-12-structured-cancellation-boundary-generations.org][Structured Cancellation And Boundary Generations]].  This module owns only
their bounded, read-only observability projection.

Admission, backpressure, budget, cleanup-capacity, and starvation evidence
follow
[[file:45-13-demand-admission-backpressure-cleanup-capacity.org][Demand Admission, Backpressure, And Cleanup Capacity]].  This module owns only
their three-plane observability projection.

Replay verification, comparison, divergence, and barrier events follow
[[file:45-14-deterministic-realization-replay.org][Deterministic Realization Replay]].  This module owns only their bounded
condition-first observability projection.

Receipt identity, correction, contradiction, redaction, and diagnostic
annotation boundaries follow
[[file:45-15-receipt-object-canonical-evidence-projection.org][Receipt Object And Canonical Evidence Projection]].  This module owns only their
read-only observability projection.

* Diagnostic limits

#+begin_src text
maxEvaluationLineageDepth
maxActiveEvaluationCells
maxWaitersPerCell
bootstrapEventCapacity
slowEvaluationThreshold
#+end_src

Limits are runtime safety inputs, not QualificationPolicy.  Slow threshold emits
an event only.  Hard limits produce operational conditions scoped to the
affected evaluation, cell request, or waiter request.

| Limit | Runtime effect |
|-
| =slowEvaluationThreshold= | emit one =qualification-slow= event; continue unchanged |
| =maxEvaluationLineageDepth= | fail the owning evaluation with an operational condition |
| =maxActiveEvaluationCells= | reject only the additional cell request |
| =maxWaitersPerCell= | reject only the additional waiter request |
| =bootstrapEventCapacity= | coalesce/drop diagnostics and emit overflow marker; continue qualification |

The owning phase determines recovery for lineage-depth failure: G0 may abort or
replace context; active composition may only abort the current composition.

Runtime measures are bounded scalars:

#+begin_src text
elapsedMonotonic
lineageDepth
activeEvaluationCells
waiterCount
retainedEventCount
droppedEventCount
#+end_src

No heap traversal, global stack dump, unbounded object-graph capture, or
sampling profiler runs on the failure path.

* Relationship to observability performance gates

[[file:80-observability-performance-gates.org][80]] owns benchmark,
construction-count, build-cache, and GSLPH performance-gate policy.  This module
does not redefine those gates.

| Concern | Owner |
|-
| runtime event schema and ordering | 45-04 |
| bootstrap diagnostic buffer | 45-04 |
| detached failure snapshot and runtime safety limits | 45-04 |
| construction-count = 1 gate | 80 |
| benchmark and build-cache gate policy | 80 |
| GSLPH policy-scenario declaration | 80 / project testing declaration |

Measured results from 80 may inform future default runtime limit values.  They
do not become QualificationPolicy, DecisionReceipt fields, or runtime event
authority.

GSLPH may execute event-order, overflow, snapshot, and sink-failure scenarios
through the project testing policy.  It does not emit runtime events, retain the
buffer, assign sequences, construct snapshots, or certify receipts.

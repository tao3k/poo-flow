#+title: Phase-Aware Macro Expansion Evidence, Source Mapping, and Receipt Schema
#+startup: overview

* Status

The architecture in this RFC is accepted.

This acceptance freezes evidence for an already admitted macro
expansion.  It does not admit a new macro, broaden the public macro
surface, or replace the governance in
[[file:44-current-project-programming-style.org][Current Project Programming Style]].

* Scope

This RFC defines phase-aware macro expansion identity, explicit
compile-time dependencies, expansion receipts, caching, replay, source
mapping, and diagnostics.

It does not define permission to use a macro.  Macro admission remains
owned by the project programming-style and macro-governance RFCs.

* Central decision

Functions and native POO objects remain the default abstractions.

When a macro has already been admitted because necessary syntax or
phase semantics cannot be represented adequately by those defaults,
each expansion becomes a phase-aware semantic derivation.

The derivation identifies its source syntax, macro binding, phase,
hygienic context, dependencies, expander semantics, and output.  Hygiene
supports binding correctness, but it does not by itself establish
semantic identity, determinism, cache soundness, or replayability.

* Governance inherited from the programming style

This RFC inherits without redefining these rules:

- public macros are a small RFC-reviewed surface;
- public extension and Module semantics remain POO-native;
- business and domain logic belongs in functions and POO values;
- internal macros may generate structurally repetitive POO object
  families, Contract projections, and declarations;
- expansion produces ordinary POO-native or functional code;
- a macro that merely renames or wraps a native POO operation is
  rejected as redundant.

This document supplies evidence for admitted expansions.  It cannot be
used to justify a macro that fails those rules.

* Expansion request evidence

An expansion request identifies:

- canonical source-syntax evidence;
- source Module, owner, and call-site identity;
- macro binding and defining Module identity;
- Gerbil phase;
- admitted hygienic scope and binding context;
- compile-time dependency evidence identities;
- expander, compiler, and language semantic schema identities;
- declared compile-time provider input identities and receipts;
- applicable macro Contract and admission RFC identity.

Raw syntax-object address, generated-symbol printout, process identity,
current directory, ambient environment, and expansion-cache location do
not define expansion identity.

* Compile-time input boundary

Time, randomness, network responses, filesystem state, environment
variables, process data, and undeclared provider results cannot become
hidden expansion inputs.

Source and dependency files participate through exact source-snapshot
evidence.  A necessary external compile-time input requires an
explicitly admitted provider capability, provider and request identity,
input schema and purpose, immutable result evidence or receipt, and
defined failure and redaction behavior.

The expansion consumes recorded provider evidence.  Pure replay does
not repeat the provider effect.

If a required compile-time input cannot provide stable semantic
evidence, the expansion fails closed rather than embedding the ambient
value.

* Expansion result evidence

An admitted result identifies:

- canonical expanded syntax or ordinary generated-code evidence;
- expansion-request identity;
- generated binding and phase evidence;
- complete result-affecting dependency identities;
- source mapping;
- diagnostics produced during expansion;
- provider receipts consumed by the derivation;
- output Contract and canonical identity schema;
- an expansion receipt linking input and output evidence.

Expansion output remains ordinary POO-native or functional code.  The
receipt does not establish a second runtime object model or macro-only
semantic layer.

* Phase-aware expansion cache

An expansion cache key includes source syntax, macro binding, phase,
hygienic context, dependencies, provider results, expander and compiler
schemas, and macro Contract and admission identity.

A match at another phase, lexical scope, provider generation, compiler
schema, or dependency generation is a miss.

#+begin_src mermaid
flowchart LR
  R["Expansion request evidence"] -->|"derives one complete phase-aware cache key"| K["Expansion cache key"]
  K -->|"matches every semantic identity exactly"| H["Admitted expansion cache hit"]
  K -->|"differs, lacks evidence, or conflicts"| X["Pure macro expansion"]
  X -->|"produces ordinary code and an immutable receipt"| E["Expansion result evidence"]
  H -->|"returns the same verified result evidence"| E
  E -->|"may populate a disposable cache without changing semantics"| C["Expansion cache"]
#+end_src

The cache is disposable.  Removing it may reduce build performance but
cannot change expansion semantics.

* Pure expansion replay

Pure replay re-expands or verifies the result from complete request and
dependency evidence.

It does not repeat network, filesystem, time, randomness, provider, or
other compile-time effects.  Recorded provider result evidence is an
input to replay.

Replay emits a matching receipt, a mismatch receipt with complete
counter-evidence, or a fail-closed receipt naming missing, stale,
ambiguous, or conflicting evidence.

It does not repair a mismatch by selecting a newer compiler, changing
phase, using ambient environment state, or accepting printer-equivalent
syntax.

* Source mapping

Expansion evidence maps generated syntax and bindings to the user call
site, macro definition, responsible expansion step, and relevant source
and phase identities.

Diagnostics prefer the most actionable user-owned source location while
preserving a trace to generated evidence and the macro owner.

Source mapping is semantic derivation evidence, not display-only line
metadata.  File line ranges alone do not define macro identity.

* Structured expansion diagnostics

Expansion failure emits structured evidence containing source owner,
call site, phase, macro binding and owner, exact failed responsibility,
dependency and provider disposition, expected and observed Contract
evidence, safe partial generated evidence, source mapping, and admitted
next actions.

A renderer may show a concise user-level explanation or a deeper macro
trace from the same evidence.  It may not parse free-form compiler logs
as the source of truth.

Changing dependencies, phase evidence, provider evidence, compiler
schema, or macro source creates a new semantic generation.  Pure
inspection of the diagnostic does not.

* Public and advanced extension boundary

The ordinary public Module interface remains =use-composition=,
=compose profiles=, and =use-module=.

An advanced author implements domain behavior with native POO values and
functions.  An admitted macro projects only the necessary syntax or
phase semantics and expands to those ordinary foundations.

This RFC admits no =poo-compose= wrapper, raw macro hook, macro-only
object model, compile-time patch language, or generic declaration DSL.

* Implementation admission checklist

- [ ] Apply the macro-admission rules in
  [[file:44-current-project-programming-style.org][44]] before applying
  this evidence contract.
- [ ] Keep functions and native POO values as the default abstractions.
- [ ] Keep the public macro surface small and separately RFC-admitted.
- [ ] Expand to ordinary POO-native or functional code.
- [ ] Identify source syntax, macro binding, phase, hygienic context,
  dependencies, providers, expander, compiler, and Contract.
- [ ] Exclude ambient environment, time, randomness, filesystem state,
  network results, runtime addresses, and cache location from hidden
  identity.
- [ ] Represent source and dependency files by exact source-snapshot
  evidence.
- [ ] Require explicit provider capability, identity, schema, purpose,
  and receipt for necessary external compile-time inputs.
- [ ] Give every expansion a canonical result identity, source mapping,
  and receipt.
- [ ] Require a complete phase-aware identity for cache hits.
- [ ] Keep the expansion cache disposable.
- [ ] Keep replay pure and prevent compile-time effect replay.
- [ ] Map diagnostics to actionable user source while preserving macro
  and generated-evidence lineage.
- [ ] Treat hygiene as necessary binding evidence, not sufficient macro
  justification.
- [ ] Reject redundant wrappers around native POO operations.
- [ ] Add no public macro without a separate RFC admission.
- [ ] Apply the thin public composition projection boundary in
  [[file:45-120-13-thin-use-composition-use-module-profile-projection.org][45-120-13]].

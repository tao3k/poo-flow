* 40 Module Registry Scale Architecture
** 40.10 Problem
The module-system facade became the largest build hotspot because it acted as a compile-time fan-in point. A public facade that imports concrete modules, large POO object owners, presentation code, and loader behavior will grow slower as the module catalog grows. A Doom Emacs sized catalog cannot depend on a facade that recompiles the world whenever the catalog gets wider.

The root fix is an architectural boundary, not another local import trim:
- module catalog expansion is data;
- loading is an explicit action;
- the facade is a stable public API surface, not a concrete module aggregator.

** 40.20 Boundary
The module-system path is split into three layers.

1. =src/module-system/loader/registry.ss=

This owner stores source-ref metadata and static module-tree manifests. It imports only =src/module-system/loader/source=. It must not import loaders, resolvers, extension graphs, concrete =src/modules/*= packages, or POO object owners. Expanding the catalog to hundreds of modules should only expand data and string/source-ref mapping.

2. =src/module-system/loader/tree.ss=

This owner consumes registry source refs and turns them into lazy-load plans, auto-import graphs, and strict load/catalog operations. Loader behavior stays here because it is an action boundary. Registry users can inspect module sources without forcing descriptor realization.

3. =src/module-system/facade.ss=

The facade re-exports stable module-system contracts only. Concrete workflow, sandbox, profile, presentation, and object modules should be imported from their real owner by callers that need them. The facade must not be used as a convenience import for downstream implementation modules.

4. =src/user-interface/facade.ss=

The User Interface facade follows the same bounded rule. It owns stable
entrypoint, presentation, and observation mechanics. Module System loading is
imported from its own interface by the consumer that needs it. A concrete capability is
exported by =src/modules/<module-name>/interface.ss= and is loaded only when a
configuration selects that module. In particular, durable memory behavior is
owned by =src/modules/memory-core/interface.ss= and session lifecycle behavior
is owned by =src/modules/session/interface.ss=; neither is re-exported by the
global User Interface facade.

The facade is an advanced presentation owner and is not the production
User Interface bootstrap. Top-level =user-interface/init.ss= imports the
lightweight =src/user-interface/init-declaration-syntax.ss= owner directly.
The PackageSpec follows that real import edge, so it does not initialize the
presentation graph for a declaration-only user entry.

** 40.30 Growth Rule
Adding a new concrete module should follow this shape:
#+begin_src scheme
(def poo-flow-src-module-tree-entrypoints
  '(("agent-sandbox" config)
    ("new-module" objects config)))
#+end_src

The registry entry declares source refs. It does not load the files. If a caller needs the descriptor, it must pass the source refs through =loader-tree= with an explicit backend. If a test or implementation needs a concrete function, it must import the owning module directly.

This keeps catalog growth close to O(n) data expansion while preventing O(n) compile fan-in through the facade.

** 40.40 Guardrail
=t/module-system-lazy-loader-test.ss= now includes the scenario:

The scenario builds 500 synthetic module roots, expands them into 1000 source refs, checks stable source-ref values, and requires the best internal registry mapping time to stay below 50ms. This is the performance gate for the architecture boundary: large manifests must remain millisecond-level data work and must not force loader calls.

** 40.50 Evidence
Focused receipts after the split:
- =direnv exec . true=: real 3.58s
- =gxpkg env gxi -e '(display "ok") (newline)'=: real 26.68s
- historical compiled CLI experiments validated that bypassing package-env startup matters, but the current focused test gate is native =gxtest=.
- =gxtest t/module-system-lazy-loader-test.ss=: validates native focused tests, =real 8.94s=.

The clean Bazel bootstrap was also reduced from ten roots to seven by removing
the three framework sources already governed as lazy registry entries:
=init-syntax.ss=, =config-discovery-syntax.ss= and =declaration-case.ss=. In the
same checkout, the ten-root Gerbil action used 107.456 seconds and peaked at
5,363,187,712 bytes. The seven-root action used 23.746 seconds and peaked at
2,872,836,096 bytes; total Bazel wall time was 44.836 seconds. Focused consumers
then imported and exercised all three lazy owners successfully. This receipt
measures one cold comparison and establishes the ownership correction; future
performance claims use repeated scenario statistics.

The testing Observability extension was then removed from the production
BuildSpec, leaving six framework roots. Its focused test explicitly imports and
compiles the owner in the independent testing lane. After the User Interface
root was corrected to the actual init declaration owner, the exact six-root
cold Gerbil action completed in 22.457 seconds with a 2,784,985,088-byte peak
process-tree footprint. Runnable process count was 6 under the native core limit
7, and total Bazel wall time was 41.443 seconds.

Module admission also performs a reader-native owner-import inspection over
every =.ss= file below each module root. An implementation role importing an
aggregate framework surface emits
=poo-flow.module-owner-import-observation.v1= and fails admission with
=POO-FLOW-MODULE-E008=. The check reads datums only and never expands or
evaluates module source. Its repository gate covers all maintained module role
files, including nonstandard private helpers below the canonical role owners.

The native unit-test entrypoint does not rely on the production PackageSpec to
publish test-only owners. =unit-tests.ss= imports
=observability/testing-extension.ss= through its relative source owner, so the
extension is expanded only inside the test process. No test BuildSpec, alternate
builder, or added production root is needed.

The package-env receipt is the removed cost center. Native runner startup is sub-second; focused tests remain bounded by =gxtest= and the module/test load graph, while the millisecond gate lives inside the registry scenario so the test distinguishes module catalog expansion from runner startup and Gerbil compilation work.

** 40.55 Fast Gate Entrypoint
Focused module-system gates must not be run through =gxpkg env=. Native =gxtest= owns focused single-file tests:
#+begin_src sh
gxtest t/module-system-lazy-loader-test.ss
#+end_src

This removes the 20s+ package-env startup from focused agent checks. Full package builds remain package-graph work and should use =gxpkg build -g= for normal CI/development parity; reserve =gxpkg build -R -O= for an explicitly requested release/optimization gate. The Gerbil package build file =build.ss= is not an agent fast-gate interface.

Build-cache fast gates must also follow the receipts in [[file:39-gerbil-build-optimization-audit.org::*10.06.39.70 Warm Build Cache Incident (2026-07-02)][10.06.39.70]]: local warm-path checks use =GERBIL_PATH=.gerbil gxi build.ss compile --debug=, one =touch build.ss= run validates the retouch path, and =gxpkg build -g= remains package-manager/CI parity.
** 40.60 Regression Rule
Reject future changes that do any of the following:
- import =src/modules/*= from =src/module-system/facade.ss=;
- import =src/modules/*= from =src/user-interface/facade.ss=;
- import or re-export the aggregate =src/module-system/facade.ss= from
  =src/user-interface/facade.ss=;
- promote a registry-owned lazy framework source into the package bootstrap
  without an explicit consumer and a cold-build receipt;
- promote a testing extension into the production bootstrap merely so focused
  tests can import it;
- move loader backends, resolver activation, or extension graph logic into =module-registry.ss=;
- use filesystem scans as the default registry expansion path;
- make tests pass by relying on facade to leak concrete owner symbols.

When a new module family is needed, add manifest data to =module-registry.ss=, add loader/action behavior to =loader-tree.ss= or the real owner, and keep facade imports bounded to stable module-system contracts.

** 40.70 Native build profiles

The package build exposes two projections from the same ASP PackageSpec and
the same =std/make= executor.  The default =library= profile contains the three
stable framework entry interfaces.  The =release= profile is selected with
=POO_FLOW_BUILD_PROFILE=release= by CI and Bazel; it adds every maintained
=src/modules/<name>/interface.ss= plus the explicit Bundle v1, runtime-load,
Nono binding, and contribution product entries.  It does not enumerate role
implementation files and does not call =all-gerbil-modules=.

Native unit CI selects the separate =test= profile.  That PackageSpec inherits
ASP's standard package source catalog so test-only direct imports cannot widen
the =library= or =release= closure.  Test execution remains owned by the ASP
Testing Interface in =unit-tests.ss=; the profile only prepares its isolated
compiled source image and does not introduce another runner or scheduler.

With =GERBIL_BUILD_VERBOSE=1= the package emits =spec-start= before ASP import
projection and =spec-projected= with profile, target count, and elapsed
nanoseconds before handing the result to =std/make=.  On the 2026-09-15 Darwin
receipt, the unchanged =library= profile projected 48 targets in 0.58 seconds
and completed in 2.39 seconds with zero compile jobs.  The isolated Bazel
=release= action projected 318 targets, completed in 101.385 seconds, peaked at
3,902,980,096 bytes, and successfully produced both Bundle v1 variants and the
wheel smoke projection artifact.

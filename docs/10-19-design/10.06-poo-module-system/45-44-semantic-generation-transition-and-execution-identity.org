#+title: Semantic Generation, Transition, Authorization, and Execution Identity
#+subtitle: Content-addressed POO state, convergent recovery history, and cache boundaries
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative design module

This module separates the identity of a pure semantic composition state from the identities of the transitions, authorization events, and runtime executions that reach or evaluate that state.

* Core decision

#+begin_quote
A semantic generation is a content-addressed pure POO composition state. Transition, authorization, and execution identities explain how that state was reached and evaluated, but they do not contaminate its semantic identity.
#+end_quote

POO Flow distinguishes at least:

#+begin_src text
SemanticGenerationIdentity
TransitionIdentity
AuthorizationEventIdentity
EvaluationExecutionIdentity
#+end_src

These identities have different projection, retention, cache, and replay rules.

* Semantic generation identity

The conceptual identity is:

#+begin_src text
H(
  semantic-generation schema identity,
  composition-strategy semantic identity,
  canonical active POO composition root,
  active priority and admission-policy projections,
  active resolver-policy identities,
  semantic evaluator protocol identity
)
#+end_src

The exact hashing and projection format is an implementation contract to be defined separately. The invariant is that only pure inputs capable of changing semantic behavior participate.

Semantic generation identity includes:

- the =profiles= strategy semantic identity;
- canonical Profile operand and POO prototype identities;
- slot-contribution values and priorities;
- contracts and capability requirements;
- import and submodule semantic identities;
- active admission-policy projections;
- active resolver-policy identities;
- a semantic evaluator protocol identity when protocol changes can alter results.

Semantic generation identity excludes:

- predecessor generation identity;
- transition and recovery history;
- wall-clock time;
- worker, thread, process, scheduler, or host identity;
- cache hits, misses, and materialization location;
- live capability tokens, leases, and recovery portals;
- continuations and resumptions;
- handler process identity;
- source path, line number, and log location;
- remaining operational recovery budget;
- derived current-generation SCC topology.

SCC topology is derived evaluation evidence for a semantic generation. Including it in the generation identity would create an identity cycle.

* Transition identity

Recovery history is represented by a separate content-addressed transition:

#+begin_src text
TransitionIdentity =
H(
  predecessor SemanticGenerationIdentity,
  ConflictEvidence identity,
  admitted RecoveryDecision semantic identity,
  successor SemanticGenerationIdentity
)
#+end_src

This separation guarantees:

- the same predecessor and semantic decision converge to the same successor semantic identity;
- different authorization events may authorize the same semantic transition;
- different predecessors may converge to the same semantic state;
- each causal recovery path retains its own transition receipt;
- semantic cache reuse does not depend on historical path.

* Convergent generation graph

The generation structure is a Merkle DAG, not a mutable global counter:

#+begin_src mermaid
flowchart LR
    A["Semantic generation A"] -->|"transition receipt T1"| C["Semantic generation C"]
    B["Semantic generation B"] -->|"transition receipt T2"| C
    A -->|"repeat the same semantic decision"| C
    C -->|"share one content identity"| K["Shared semantic cache namespace"]
    U1["Authorization event U1"] -->|"authorize transition T1 without changing C"| A
    U2["Authorization event U2"] -->|"authorize transition T2 without changing C"| B
#+end_src

The notation =G+1= means "the successor relative to one transition." It is not a globally allocated integer identity and does not require a generation registry.

* Recovery decision projections

An admitted recovery decision has two distinct projections:

- Semantic projection :: The pure priority, operand, resolver, admission, or other composition change that affects the successor state.
- Authorization receipt :: Evidence that a handler with an admitted capability authorized that proposal in a live scope.

Only the semantic projection affects the successor semantic generation identity. The authorization receipt proves that the transition was allowed, but it does not alter business semantics.

Two different authorized operators that admit the same semantic proposal therefore produce:

#+begin_src text
the same successor SemanticGenerationIdentity
different AuthorizationEventIdentities
separate authorization receipts
#+end_src

They may also produce distinct transition receipts when their predecessor, conflict, or admitted-decision evidence differs.

* Capability admission projection

Capability information crosses the identity boundary as follows:

- Capability requirements and authority-scope policy are pure semantic inputs.
- Live tokens, leases, secrets, and validation handles are operational resources.
- The canonical pure admission result may participate in the evaluated composition projection.
- Token identity and secret material remain outside semantic content identity.
- Different valid tokens proving the same canonical authority scope must not create different semantic generations.

An admission projection must be sufficient to prove which candidates participate without serializing the authority resource that proved admission.

* Authorization event identity

An authorization event identifies the live act that admitted or rejected a proposal. Its receipt may record:

- recovery portal scope identity without serializing the portal;
- capability and authority evidence permitted for disclosure;
- handler identity permitted for disclosure;
- proposal and conflict identities;
- admission or rejection;
- consumed recovery budget;
- related transition identity when admitted.

Authorization event identity is not a semantic cache key and cannot be reused as authority.

* Evaluation execution identity

Every concrete evaluation has an operational execution identity. Its receipt may include:

- worker, process, scheduler, and host;
- cache lookup and materialization behavior;
- timing and resource budgets;
- operational retry;
- continuation allocation and consumption;
- runtime and Marlin handoff;
- commit and publication attempts.

Multiple execution identities may evaluate the same semantic generation. They share semantic result identities while retaining separate operational receipts.

#+begin_src mermaid
flowchart LR
    G["One SemanticGenerationIdentity"] -->|"evaluated by worker execution E1"| R1["Operational receipt E1"]
    G -->|"evaluated by worker execution E2"| R2["Operational receipt E2"]
    G -->|"addresses demanded slot cache"| K["Shared semantic result"]
    R1 -->|"records cache hit, timing, and runtime path"| K
    R2 -->|"records independent retry and timing"| K
#+end_src

* Semantic cache boundary

A semantic result cache key is conceptually:

#+begin_src text
SemanticGenerationIdentity
+ demanded semantic slot identity
+ semantic evaluator protocol identity
#+end_src

The protocol identity may be omitted as a separate component only when it is already unambiguously included in =SemanticGenerationIdentity=.

The key must not include:

- transition identity;
- authorization event identity;
- handler or portal identity;
- scheduler or worker identity;
- operational timing;
- cache materialization path.

Pure result reuse never reuses live authority, continuation, or operational success evidence.

* History-dependent resolver policy

A resolver must not read hidden recovery history. If history affects its proposal, the required history must be provided as an explicit pure policy-context projection.

That context:

- participates in resolver evaluation identity and cache keys;
- is canonical and bounded;
- excludes live portal and capability state;
- records only history that the policy declares semantically relevant;
- cannot be inferred from mutable global state.

The successor semantic generation includes only the semantic effects that persist in the resulting composition. Historical explanation remains in transition receipts unless history is itself an explicit active policy input.

* Implementation checklist

- [ ] Define canonical schemas for semantic generation, transition, authorization event, and execution identity.
- [ ] Build semantic generation identity only from pure behavior-affecting projections.
- [ ] Exclude predecessor and recovery history from semantic generation identity.
- [ ] Exclude source locations, timing, scheduler state, and live authority resources.
- [ ] Keep current-generation SCC topology as derived evidence outside the generation hash.
- [ ] Define transition identity over predecessor, conflict, semantic decision, and successor identities.
- [ ] Verify that the same semantic state reached through different paths has one semantic identity.
- [ ] Verify that repeated equivalent decisions converge to the same successor.
- [ ] Preserve separate transition and authorization receipts for convergent paths.
- [ ] Separate RecoveryDecision semantic projection from authorization evidence.
- [ ] Canonicalize capability admission without serializing live tokens or secrets.
- [ ] Define independent operational evaluation execution identities.
- [ ] Key semantic result caches by semantic generation and demanded slot identity.
- [ ] Prevent authorization, transition, and execution identities from contaminating semantic cache keys.
- [ ] Require explicit pure policy context for history-dependent resolver behavior.
- [ ] Validate Merkle DAG convergence and collision-domain separation.

* Non-goals

- Do not allocate semantic generations from a mutable global counter.
- Do not include predecessor identity merely to make each state historically unique.
- Do not hash live tokens, leases, portals, continuations, or secrets into semantic state.
- Do not let source paths or line numbers invalidate semantic caches.
- Do not treat operational success as semantic proof.
- Do not discard transition history when multiple paths converge.
- Do not create a generation registry.

#+title: POO Flow Capability Gradient and Default Expression Surface
#+date: [2026-09-23]
#+property: SDD_KIND architecture-decision
#+property: STATUS accepted-normative-surface-contract

* Decision

POO Flow MAY have a high capability ceiling without imposing the same height
on its default expression surface.  The ordinary interface is the native
=gerbil-poo= object, prototype and slot algebra: users declare values, extend
maintained prototypes, compose named values, and inspect the resulting
effective object.  It is not a Jsonnet-inspired language, a JSON-like model,
or a second functional-object DSL.  Generic dispatch, CLOS, C4, macros and
the MOP remain available at progressively deeper extension boundaries, but
they are not ordinary configuration concepts.

The short contract is:

#+begin_quote
Objects are ordinary values.  Extension is ordinary composition.  Abstraction
is optional.  Meta-abstraction is exceptional.
#+end_quote

Equivalently:

#+begin_example
Value first
Composition second
Abstraction on demand
Meta-programming last
#+end_example

This RFC constrains every public Module, Profile, Scenario, Case, Policy and
Flow interface.  More specialized implementation and conformance RFCs MUST
follow this surface contract.

* Normative reading order

The current authority order is:

1. this RFC for the default expression surface and capability disclosure;
2. RFC 29 for native =gerbil-poo= operators and prototype discipline;
3. RFC 44 as the modular router for repository roles, dispatch, Query,
   formal-assurance, build and testing style;
4. RFC 45-92 for the thin =user-composition= binding boundary;
5. RFC 45-93 for =use-module= selection and ProfileBundle algebra; and
6. RFC 45-95 for aggregate Profile responsibility reachability.

An older RFC, receipt, example or README that shows =use-composition= as a
clause parser, exposes =stage/graph/loop/prove/handoff= in root config, or
introduces a parallel command-slot vocabulary is historical evidence and
cannot override this order.

* Five mechanism constraints

The following five constraints are normative together.  A Scenario or Case
that uses native noun slots but violates dispatch, type, macro or
root-composition ownership is not POO-native.

1. Profile behavior with one independently extensible receiver family MUST use
   native =gerbil-poo= slot dispatch through =.defgeneric=.  A descendant
   specializes behavior by replacing or refining the method slot through
   native prototype inheritance.  A symbolic dispatcher, registry or class
   simulation is not an equivalent implementation.
2. A Provider or executor crossed with a Profile, Scenario, Case or contract
   kind MUST use the POO CLOS generic, class/eql specializers and an owned
   method bundle when both axes grow independently.  CLOS is not the ordinary
   declaration surface and MUST NOT be introduced for a single receiver axis.
3. =define-type= admits boundary values, shapes and invariants such as change,
   check, decision, receipt and projection contracts.  It MUST NOT simulate a
   class hierarchy, Profile inheritance or Scenario behavior.
4. =defrule= or =defrules= MAY remove repeated static Profile declaration
   framing only when the expansion is ordinary native POO construction.  It
   MUST NOT own behavior, precedence, stage semantics or a second object
   language.
5. A root =config.ss= composes already maintained Profiles and Standards.  It
   MUST NOT declare or parse a parallel stage, graph, loop, proof, handoff,
   Provider or runtime DSL.  Those responsibilities remain reachable native
   POO values owned by the selected Profiles and their extension modules.

These constraints define module mechanism ownership, not five public concepts.
They complement rather than replace the object-level slot algebra
below.  The ordinary author still sees native POO values, slots, prototype
extension and composition.

* Module Interface authoring Contract

Every loaded POO Module has one native POO =Interface= object as its public
entry.  The Interface carries an =authoring= Profile whose =types=, =objects=,
=funs=, =config= and =interface= slots contain extensible source-role Contract
objects.  These objects describe recommended responsibility, forbidden
competing surface forms, native repair operators and the freedom retained by
the module owner.  They do not define a closed grammar and do not parse or
execute a second language.

The loader MUST read each stable role as inert Scheme datums and admit it
through that Interface Profile before exposing its entrypoint.  A vertical
module MAY refine a role Profile or contribute a method bundle; it MUST NOT
replace the native POO object model with an external rule table.

Cross-role admission is a real open crossing and therefore dispatches on
=AuthoringExecutor x SourceRole x ModuleInterface=.  Native POO prototypes use
the explicit CLOS prototype specializer; CLOS classes use the class
specializer.  A native prototype MUST NOT masquerade as a CLOS class, and no
duplicate marker-class hierarchy may be manufactured only to obtain dispatch.

The default Contract is deliberately bounded.  It rejects competing public
command-slot vocabulary and top-level stage/runtime DSL forms, while leaving
ordinary functions, internal algorithms and vertical-domain implementation
open.  Diagnostics must name the module, role, violated rule, subject, native
repair operators and retained freedom so an agent can repair the source rather
than merely suppress the gate.

The same admission MUST reject a lazy POO slot initializer that references
its own slot name before the object is realized.  It reuses Observability's
inert-source slot observation and reports the slot, rule and repair hint;
runtime memory sampling is not a substitute for this pre-execution check.
The Testing Interface owns test-worker memory Profiles and batching; the
build script does not create a process for each test or claim to observe each
child worker's heap from the parent process.  Every worker gets the inherited
managed-heap limit.  POO Flow's =poo-flow-test-case= projects to native
=std/test= and adds a default Case execution-span Profile; the corresponding
=poo-flow-test-case/with= form inherits the POO prototype and overrides Case
slots such as memory policy and maximum duration.  It does not replace
=gxtest=, its assertions, or its reporting.  Existing native =test-case=
declarations retain worker-level protection but are not silently instrumented
per Case; they must migrate to the POO declaration for Case-span evidence.
Gambit heap counters are process-wide.  A Case keeps its assertions on the
native harness thread while a sampler thread monitors and may interrupt it.
Therefore a Case receipt is execution-span evidence, not a
thread-local hard heap quota or CPU attribution.  Automatic instrumentation
of unmodified =std/test= declarations still requires an upstream callback.

* Capability height is not expression height

POO Flow has two independent axes.

| Axis | Question | Progression |
|------+----------+-------------|
| capability height | What can the implementation express? | POO value -> prototype composition -> higher-order function -> generic/CLOS dispatch -> MOP |
| expression height | What must this author understand? | object -> extend -> compose -> define behavior -> change meta-semantics |

Adding an implementation capability MUST NOT automatically raise the
expression height of a user-facing declaration.  A Module may internally use
CLOS to cross a Provider and a Profile while the user still selects one named
Profile and supplies ordinary slot values.

Complexity SHOULD become visible as diagnostics, provenance or an explicit
advanced extension interface.  It MUST NOT become an unavoidable syntax tax.

* One semantic model, three surfaces

The three surfaces below are progressive views of one Gerbil POO semantic
model.  They are not three languages and MUST NOT produce parallel config,
class or runtime object hierarchies.

** Default value surface

The default surface serves application users and vertical-domain authors, but
those two owners do not receive the same amount of construction syntax.  Its
concept budget is deliberately small:

- object;
- slot;
- extend;
- compose.

A Profile, Scenario, Case, Policy or Flow is first an ordinary named POO value.
An extension means a base value plus declared differences.  Composition means
selecting maintained named values and allowing the kernel to derive one
deterministic effective object.

There are two views of that one object model:

1. the ordinary root =user-interface/config.ss= selects and composes maintained
   values; it MUST NOT require =.o=, =.def= or nested Stage construction;
2. the maintainer or vertical owner MAY publish an advanced Profile whose
   =stages= slot is a =PooFlowStageSpace= POO object.  Each named Stage slot may
   be either an inert direct value or another POO object that opts into native
   inheritance and override.

This is progressive disclosure, not a data-versus-object compatibility mode.
Both views reach the same ProfileBundle and StageSpace Contract, projection
and runtime handoff.  Module System admission distinguishes the root owner from
the maintainer owner before projection; it does not guess from data shape at
runtime and does not manufacture an object on the user's behalf.

The default surface MAY use native Gerbil POO declaration forms or a thin,
hygienic domain declaration that lowers directly to them.  A thin declaration
MUST preserve object identity, native slot semantics, source locations,
provenance and ordinary POO extension.  It MUST NOT introduce a second AST,
record DSL, JSON language, evaluator or merge algebra.

Default examples and ordinary UI MUST NOT require the author to understand:

- class versus instance;
- constructor, factory or builder patterns;
- specializers, applicable methods or method combination;
- MRO, C4 or linearization algorithms;
- slot metaobjects, class metaobjects or MOP lifecycle;
- raw =(lambda (self super) ...)= behavior hooks.

** Extension surface

The extension surface serves Module, Provider and framework-extension authors.
It MAY use named higher-order functions, slot generics, CLOS generics,
specializers, method bundles, contracts and projections.

Every advanced extension MUST name its owner and answer an admission question:

| Candidate mechanism | Required evidence |
|---------------------+-------------------|
| named function | data-dependent or reusable pure behavior |
| higher-order constructor/combinator | a reusable family that produces ordinary POO values or functions |
| slot generic | one receiver family whose descendants replace one behavior |
| CLOS generic | two or more independently extensible axes and an owner for every method bundle |
| bounded macro | repeated static declaration structure that lowers to ordinary POO or functional code |

If the same behavior is expressible as a slot value, prototype extension or
named pure function, an extension author MUST NOT raise it to CLOS or MOP.

** Meta surface

The meta surface serves POO Flow kernel maintainers.  It owns linearization,
slot resolution, method selection and combination, metaobject lifecycle,
macro-expansion infrastructure and controlled instrumentation.

The meta surface is opt-in.  It MUST NOT be imported transitively by the
default Module facade, used as ordinary Profile configuration, or presented as
the first explanation of a composition failure.  Meta-level changes require a
dedicated owner, positive and negative semantic evidence, and a demonstrated
need that native POO values, functions and the extension surface cannot meet.

* Single semantic model law

Object, Entity and Element are not three competing storage models.  A native
POO Object is the carrier; an Entity is an identity-bearing domain role of that
Object; an Element is an Entity, Relation or inert Value admitted into one
Contract/Scenario observation space.  Implementations MUST preserve one object
identity and project roles from it.  They MUST NOT copy the same facts into
parallel =objects=, =entities= and =elements= registries with independent
merge or authority rules.

A Query is an immutable, identity-bearing, bounded, read-only POO object.  Its
facets, predicates, traversal policy, completeness, evidence requirements,
redaction request and result Contract remain native slots.  Raw GQL strings,
alist query rows, anonymous query lambdas and provider-specific ASTs MUST NOT
be the public Query value.  GQL is an optional Provider projection/execution
surface: parser and runtime receipts bind its source and result back to the
same POO Query and Contract identities.

Query results are Evidence and never acquire authority merely because they
were returned by a Provider.  Query admission intersects requested scope,
budget and visibility with the owning Contract.  Empty results over an
incomplete Element space remain unknown rather than evidence of absence.

The executable Module Interface authoring Contract enforces the mechanically
decidable part of this law.  Query-named public slots reject raw strings,
lists, vectors and anonymous lambdas and report
=poo-query-must-be-native-object= with the repair
=bind-named-poo-query-or-provider-projection=.  Pure algorithms in =funs.ss=
and named Provider source projections remain open.  The Contract deliberately
does not infer semantic duplication merely from domain vocabulary.

Every accepted declaration follows one authority flow:

#+begin_export mermaid
flowchart LR
    D["Default object declaration"] -->|"native value or thin lowering"| V["POO value"]
    V -->|"prototype extension and composition"| E["Effective object"]
    E -->|"named operation or admitted generic"| R["Receipt or behavior result"]
    R -->|"explicit projection"| H["Runtime or proof handoff"]
    E -. "inspect" .-> P["Provenance and composition explanation"]
    M["MOP and linearization"] -. "internal semantics only" .-> E
#+end_export

The following are forbidden:

- a simple-user object model beside an advanced-user object model;
- a CLOS-facing configuration DSL beside the POO value declaration;
- a Provider-specific option map that owns semantics already present in a
  Profile or Case;
- a proof, ABI or runtime record that becomes a second user-facing contract;
- a macro or MOP facility that silently changes authority, performs effects or
  hides composition provenance.

Cedar, Lean, TLA+, MRR, Rust, Python and other runtimes consume projections or
receipts bound to the admitted effective object.  They do not replace it.

* Default expression laws

** Value-first law

The user names or receives a value.  A default declaration MUST NOT require a
class definition followed by construction, a factory, a builder or an explicit
instance lifecycle merely to express configuration.

** Composition-second law

Ordinary specialization is base plus differences.  Reusable Profiles and
CaseComponents MAY supply maintained behavior and defaults; a user selects and
extends them.  Composition order is deterministic and inspectable, but its
linearization algorithm remains an implementation detail until a conflict must
be explained.

** Behavior-on-demand law

Not every slot is a configurable function.  Pure algorithms remain named
functions.  One-receiver replacement uses a slot generic.  CLOS is reserved
for real open crossings.  Raw closures and symbolic dispatch tables are not
ordinary domain declarations.

An Interface MAY own a derived index or another inert projection slot when the
projection is constructed once from the Interface's effective noun slots and
is reused by multiple consumers.  The public API exposes domain lookup or
validation behavior; the mutable hash table, vector or cache representation is
not itself a user-configurable concept.  Cross-object traversal remains a
named pure algorithm unless one receiver family genuinely requires overridable
slot dispatch.

** Meta-last law

Ordinary users MUST NOT configure a linearizer, slot resolver, method cache,
method combination or class lifecycle.  A meta extension is admitted only when
it changes how domain objects are defined or combined rather than defining one
more domain object.

* Native slot algebra contract

User-facing declarations MUST use the native Gerbil POO slot algebra documented
by =gerbil-poo/doc/poo.md=.  Domain slots name values such as =events=,
=edges=, =profiles= and =sources=.  The base prototype supplies a default
computation and a descendant refines the inherited nested object with ===>.+=.
POO Flow MUST not place a second command vocabulary, action AST or patch
language around those slots.

| Declaration intent | Native slot form | Required semantics |
|--------------------+------------------+--------------------|
| replace one value | =(slot value)= | the child deliberately overrides the inherited computation |
| provide a fallback | =(slot ? default)= | the default participates in native inherited-default selection |
| transform an inherited value | =(slot => named-combiner arguments ...)= | a named pure function receives the inherited value and returns the refined value |
| refine a nested POO value | =(slot =>.+ overriding-object)= | the overriding object extends the inherited slot object through native POO composition |
| conditionally inherit | =(slot (next) expression)= | exceptional implementation surface with an explicit need and tests |

The declaration vocabulary follows these laws:

- collection slots use domain nouns such as =events=, =edges=, =trajectories=,
  =authorizations=, =sources=, =profiles= and =capabilities=;
- composition operations remain in the slot form: ===>.+= means nested POO
  refinement, ===>= means functional refinement, =?= means inherited default,
  and a plain slot definition means replacement;
- a parallel command-slot vocabulary is forbidden because native slot forms
  already own replacement, defaults and inherited refinement;
- a domain slot MUST NOT be reinterpreted by a central symbolic dispatcher,
  action registry, clause parser or Case-specific patch evaluator;
- an ordered list accumulation MUST use ===>= with a named pure combiner and a
  documented ordering law; repeated =append= hidden in an evaluator is not a
  slot algebra;
- a runtime effect remains a method or explicit effect request; declaring a
  noun slot never executes that effect.

Base prototypes SHOULD declare empty collection fallbacks with =?= rather than
ordinary overriding constants.  For example:

#+begin_src scheme
(.def OntologyCase
  (events ? (.o)))

(.def (PrescriptionCase @ OntologyCase)
  (events =>.+
    (.o prescription: PrescriptionEvent)))

(.def (ReviewedPrescriptionCase @ PrescriptionCase)
  (events =>.+
    (.o prescription: ReviewedPrescriptionEvent
        review: ClinicalReviewEvent)))
#+end_src

The slot remains declarative: accessing the effective =events= slot
returns the composed nested POO value and does not perform a runtime action.
The reviewed Case replaces the named =prescription= contribution, adds
=review=, retains every other inherited contribution and never mutates either
parent prototype.

Derived projections such as =events=, =trajectories= and =compositions= MAY
materialize ordered lists for validation or runtime handoff.  They MUST be lazy
projections of the effective noun-slot object and MUST NOT become a second
source of merge semantics.

** Exclusion, revocation and removal

Native POO provides override, default and inherited refinement, but it does not
publish an ordinary pure slot-deletion operator.  POO Flow MUST keep exclusion
explicit instead of inventing a generic declaration vocabulary for deletion.

Configuration selection MAY exclude an inherited identity through ===>= and a
named pure exclusion function or through an explicit exclusion value.  The
result MUST preserve the parent, source identity and an observable exclusion
receipt.

Identity-bearing facts are not configuration entries.  An observed Event,
Authorization, Prescription or trajectory fact MUST NOT disappear from a
derived object.  A vertical domain expresses =revoked=, =superseded=,
=invalidated= or =remediated= with a new identity-bound fact and relation.
Removal of a prototype definition itself belongs to the controlled meta or
maintenance surface, never to ordinary domain authoring.

Mutation forms such as =.put!=, =.set!=, =.putslot!=, =.setslot!=, =.def!= and
=.putdefault!= are forbidden in default declarations.  They remain controlled
runtime, instrumentation or REPL capabilities and cannot implement ordinary
Profile or Case composition.

* Presentation and observability order

The default presentation begins with the effective object, not its mechanism.
The required disclosure order is:

#+begin_example
Effective result
  -> field or slot provenance
  -> composition and override chain
  -> advanced dispatch or linearization details
  -> source declaration
#+end_example

For example, a user first sees that =retries= is =5=.  The next view explains
that =ProductionProfile= overrides =BaseProfile=.  Only an explicit advanced
view exposes the C4 precedence or the source-level POO form.

The public =poo-flow-native-slot-presentation= follows that order with
=default=, =provenance=, =composition=, =advanced= and =source= levels.  The
default level needs only the effective native POO object and slot name; it
uses upstream =.ref= and does not require source metadata.  Detailed levels
require a maintainer-authored POO source registry keyed by stable labels.
Each entry binds the actual prototype object to =source-path= and
=source-line=; duplicate objects, missing ancestors and malformed locations
fail closed.  This registry is a declaration claim, not independent proof
that the named file and line produced a runtime value.

The composition view reports native direct-slot shapes as =default=,
=replacement= or =super-aware=.  In particular, =super-aware= means the slot
specification /can/ call the inherited computation; it does not prove that
the inherited result was used.  The declaration lineage must never be
presented as an effect trace or exact causal provenance.  No second POO
evaluator is permitted to manufacture such a claim.

Composition diagnostics MUST identify the conflicting named values,
constraints and source locations.  They MAY attach advanced C4 or method
selection evidence, but the ordinary message MUST remain understandable
without those concepts.

=compose profiles= reports identity collisions and incompatible selected
revisions through =PooFlowProfileCompositionConflict=.  Its default POO
presentation names the Profile identity, conflict reason, constraint and
both declared source locations; =advanced= additionally exposes the two
original values or selection proofs.  A missing maintainer source claim is
reported as =undeclared=, never fabricated from a runtime object.  Authors
who need source-complete conflict receipts must put a =source-path= and
=source-line= POO value in Profile or export provenance.

* Source ownership and visibility

A stable Module entrypoint does not imply that every exported capability is an
equally ordinary authoring concept.  The default interface MUST remain cheap
and value-oriented.  Advanced Provider or CLOS owners MAY expose explicit
opt-in extension interfaces, but they MUST NOT be imported or re-exported by
the default user facade merely for completeness.

Directories named =user-interface= and maintained introductory examples are
part of the default expression surface.  They SHOULD contain declared objects,
slot values, maintained constructors and composition.  A raw behavior lambda,
direct CLOS declaration, MOP import or low-level graph/proof/runtime constructor
in those locations requires an explicit exception and a migration issue; file
placement alone does not waive the surface contract.

* Review admission questions

Every new public construct is reviewed in this order:

1. Is the author defining a domain value or changing how values are defined?
2. Can a maintained object, slot or prototype extension express it?
3. If behavior is required, can a named pure function own it?
4. If dispatch is required, how many axes grow independently?
5. Why must the ordinary user see this mechanism?
6. What effective-value and provenance view explains the result?

Failure to answer question 5 keeps the mechanism outside the default surface.

* Executable acceptance

The surface contract is complete only when it has executable evidence.  The
policy MUST be syntax-aware; a regex ban on names is insufficient.

- A positive fixture declares, extends and composes a realistic Profile and
  Case using only the default concept budget.
- The effective object and its slot provenance have deterministic golden
  projections.
- A composition conflict has a default diagnostic and a separate advanced
  explanation.
- Negative fixtures reject a raw MOP import, a direct CLOS declaration and a
  raw behavior hook from a default user-interface owner unless an explicit
  reviewed exception is present.
- Native slot-algebra fixtures prove that noun-valued collection slots retain
  inherited named declarations, override only matching identities and never
  mutate their parents.  The focused executable owner is
  =t/poo-native-slot-algebra-test.ss=.
- Extension fixtures prove that slot dispatch and Provider/Profile CLOS consume
  the same POO values used by the default fixture.
- Runtime fixtures prove that an ABI or proof projection cannot become an
  alternate semantic owner.
- A real vertical Case is readable and safely editable without knowledge of
  CLOS, C4, MOP or runtime projection details.

The first real vertical acceptance owner is the Healthcare AI-assisted
prescription Case.  Its user-facing declaration is not accepted merely because
it compiles; it must satisfy the default concept budget while retaining the
same Governance, Temporal Causality and Cedar behavior.

* Migration rule

Migration is direct.  Do not preserve a lower-quality default surface through
compatibility aliases or a parallel legacy interface.  Move reusable behavior
into maintained Profiles, CaseComponents, named functions or Provider method
bundles, then leave the user declaration as values and composition.

Migration MUST retain semantic and performance evidence:

- effective-object equality at the declared boundary;
- stable identity and provenance;
- the same positive and negative Governance/authorization results;
- no eager import of the advanced CLOS/MOP closure;
- no repeated traversal, duplicate index construction or asymptotic
  regression.

* Rejected designs

- advertising the complete POO/CLOS/MOP capability map as the default UI;
- creating separate simple, advanced and meta DSLs;
- requiring a class for every Profile or Case;
- exposing C4 or method combination as routine configuration;
- replacing native POO values with raw alists, records or JSON rows;
- hiding runtime effects, authority changes or merge policy behind a friendly
  declaration macro;
- calling an interface simple while its ordinary examples require raw lambdas,
  graph constructors, specializers or proof-engine payloads.

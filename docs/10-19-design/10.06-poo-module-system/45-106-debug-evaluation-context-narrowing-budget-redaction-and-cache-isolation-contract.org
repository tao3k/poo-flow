#+title: DebugEvaluationContext Narrowing, Budget, Redaction, and Cache Isolation Contract

* Status

Accepted architecture RFC.

This document fixes the minimal POO contract of DebugEvaluationContext. It does
not authorize implementation work.

* Scope

This RFC defines:

- immutable live DebugEvaluationContext values;
- pure context narrowing for child DebugDemands;
- capability attenuation;
- redaction intersection;
- functional budget reservation, consumption, and reconciliation;
- admitted and simulation cache isolation;
- session, replay, retention, and portability boundaries;
- condition and macro governance.

This RFC does not define:

- an ambient global context;
- mutable global budget counters;
- capability widening;
- redaction weakening;
- simulation cache promotion;
- commit authority;
- serializable live capabilities;
- a context clause DSL;
- compatibility, migration, or deprecation behavior;
- implementation edits.

* Evidence state

Parser-owned discovery of the current Module interface is blocked by:

#+begin_example
provider owner-search-stdin failed: status=exit status: 2 stderr=
#+end_example

The route emits no verified current owner for:

- evaluation context;
- live context;
- narrowing;
- principal or session scope;
- capability attenuation;
- budget ledger;
- redaction;
- retention;
- cache namespace;
- replay.

Current representation, ambient parameter use, mutation, serialization, and
cache behavior remain =MISSING=.

This RFC defines the target context contract without preserving an unverified
current API.

* Central decision

DebugEvaluationContext is an immutable, identity-bearing, process-local POO
value.

Evaluation is functional state threading:

#+begin_example
DebugEvaluationContext + DebugDemand
  -> EvaluationOutcome + successor DebugEvaluationContext
#+end_example

Child contexts are derived by pure narrowing:

#+begin_example
parent context + child demand
  -> child context + budget reservation receipt
#+end_example

No child can widen authority, visibility, retention, observations, budgets, or
cache publication rights.

* Live context projections

A live DebugEvaluationContext projects:

- context identity and revision;
- parent context identity when derived;
- principal identity;
- session identity;
- demand and root-demand identities;
- admitted read capability;
- admitted simulation capability;
- optional continuation capability;
- explicit absence of commit authority;
- redaction policy;
- retention policy;
- budget ledger;
- observation boundary;
- evaluator and policy versions;
- admitted read cache namespace;
- isolated simulation cache namespace when applicable;
- source and admission evidence.

The context remains a native POO object.

* Identity separation

The following identities remain distinct:

- principal;
- session;
- live context;
- context revision;
- parent context;
- root demand;
- child demand;
- semantic snapshot;
- capability;
- cache namespace;
- portable context descriptor.

No one identity silently substitutes for another.

* Explicit context

The semantic evaluator receives context explicitly.

There is no semantic dependency on:

- a global current context;
- a dynamically scoped unrestricted principal;
- a process-wide current snapshot;
- an implicit simulation mode;
- a global mutable cache namespace;
- terminal or REPL state.

An owning functional closure may close over an admitted context, but the closed
context identity remains visible in receipts and cannot be serialized as live
authority.

* Capability attenuation

Child capability scope is the intersection of:

- parent admitted capability;
- child demand requirements;
- evaluator policy;
- current semantic object and evidence scope;
- redaction and retention boundaries.

The result may preserve or narrow authority. It cannot widen it.

Read, simulation, continuation, and commit capabilities remain distinct.

DebugEvaluationContext contains no commit capability. A continuation capability
does not imply simulation or commit authority.

Capability shape is not authority. Admission validates the actual capability
object, issuer, scope, revision, expiration, and attenuation evidence.

* Redaction intersection

Effective child visibility is the greatest restriction imposed by:

- parent redaction policy;
- capability scope;
- child query request;
- evidence owner policy;
- retention and disclosure policy.

A child cannot:

- reveal a parent-redacted value;
- reinterpret redaction as absence;
- suppress redaction evidence;
- use simulation to bypass visibility;
- use diff to infer a protected value;
- retain evidence longer than the parent policy.

Redaction intersection returns a new policy identity and a narrowing receipt.

* Retention narrowing

Child retention is no broader or longer than parent retention.

RetentionPolicy identifies:

- permitted evidence classes;
- maximum lifetime;
- checkpoint behavior;
- redaction and erasure obligations;
- allowed renderers and transports;
- session and principal scope.

Released budget does not authorize longer retention.

Replay requires a newly admitted retention policy.

* BudgetLedger

BudgetLedger is an immutable POO value.

It accounts for named dimensions such as:

- evaluation steps;
- visited nodes and edges;
- ancestry and causal depth;
- predicate executions;
- explanation edges;
- diff comparisons;
- proposal precondition checks;
- fixed-point revisits;
- result volume;
- redaction projections;
- cache reads and writes;
- continuations and retries;
- explicit time observations when admitted.

There is no unlimited sentinel.

* Root-cost accounting

Root demand cost includes:

- every descendant demand;
- retries;
- rejected proposals;
- verifier and aggregation work;
- redaction;
- condition construction;
- continuation inspection;
- cache qualification;
- failed evaluation.

Splitting a query or proposal cannot evade root accounting.

* Budget reservation

Before a child demand runs, the parent creates a BudgetReservation POO object.

The reservation identifies:

- parent and child context identities;
- root and child demand identities;
- reserved dimensions;
- current parent ledger revision;
- expiration or cancellation conditions;
- authority and policy owner;
- source evidence.

Reserved capacity is unavailable to siblings until reconciliation.

Overlapping reservations cannot exceed the parent remaining budget.

* Budget consumption

Child evaluation returns a BudgetConsumption receipt.

It records:

- reserved amount;
- actual consumption;
- rejected and failed work;
- descendant consumption;
- remaining reservation;
- observation dependencies;
- evaluator version.

Historical consumed cost never decreases.

* Budget reconciliation

Reconciliation is a pure function:

#+begin_example
parent ledger + reservation + child consumption
  -> successor parent ledger + reconciliation receipt
#+end_example

Unused reservation may return to the parent's available pool.

Returning unused reservation does not:

- erase historical reservation or consumption;
- reset retry counts;
- increase capacity beyond the original parent limit;
- transfer capability;
- extend retention;
- alter sibling receipts.

* Context narrowing

A child context is derived from:

- one parent context revision;
- one child DebugDemand;
- one capability attenuation result;
- one redaction intersection;
- one retention narrowing;
- one BudgetReservation;
- one observation boundary;
- one cache namespace decision.

#+begin_src mermaid
flowchart LR
  Parent["parent DebugEvaluationContext"] -->|"attenuates capability"| Capability["child capability scope"]
  Parent -->|"intersects visibility"| Redaction["child redaction policy"]
  Parent -->|"narrows lifetime and evidence classes"| Retention["child retention policy"]
  Parent -->|"reserves aggregate resources"| Budget["BudgetReservation"]
  Demand["child DebugDemand"] -->|"declares requirements and requested bounds"| Capability
  Demand -->|"declares requested visibility"| Redaction
  Demand -->|"declares requested resources"| Budget
  Capability -->|"combines into immutable revision"| Child["child DebugEvaluationContext"]
  Redaction -->|"combines into immutable revision"| Child
  Retention -->|"combines into immutable revision"| Child
  Budget -->|"combines into immutable revision"| Child
  Child -->|"returns consumption and outcome"| Reconcile["successor parent context"]
#+end_src

Every edge is narrowing or reconciliation, never widening.

* Child and sibling isolation

Sibling contexts:

- have distinct context identities;
- have distinct budget reservations;
- cannot observe each other's unredacted evidence;
- cannot reuse each other's continuation capability;
- cannot write each other's simulation cache;
- cannot mutate the parent context;
- reconcile independently through the parent ledger.

One child failure cannot corrupt another child's context or receipts.

* Observation boundary

ObservationBoundary is a POO value that declares:

- semantic snapshot identities;
- permitted clock and entropy observations;
- external evidence versions;
- cache currentness boundary;
- fixed-point observation scope;
- replay inputs.

A child boundary is equal to or narrower than the parent boundary.

New external observations require a new context revision and receipt.

* Admitted read cache

The admitted read cache contains only results evaluated under:

- admitted semantic snapshots;
- admitted read capability;
- explicit redaction policy;
- complete cache identity;
- current evaluator and policy versions.

Cache keys include context-relevant capability, redaction, retention,
observation, and budget qualification identities.

Two contexts may share a cached semantic core only when visibility and authority
projections remain separately derived and no protected value leaks.

* Simulation cache

Every simulation uses an isolated cache namespace.

Simulation cache entries:

- identify the base snapshot and proposal;
- identify simulation context and capability;
- remain non-authoritative;
- cannot publish into the admitted read or execution cache;
- cannot satisfy proof, handoff, or commit requirements;
- expire under simulation retention policy.

There is no cache promotion operation.

A later admitted revision reevaluates through the normal admitted cache path.

* Continuation context

A live continuation capability may appear only in a process-local live context.

It is:

- opaque;
- scoped to one condition or demand;
- one-shot by default;
- narrowed for child recovery;
- absent from portable descriptors;
- consumed or retained only through an explicit receipt.

Inspection of a condition does not silently consume the capability.

* Portable context descriptor

PortableContextDescriptor is pure data and contains:

- context and parent descriptor identities;
- principal and session references;
- demand and snapshot identities;
- required capability descriptions;
- redaction and retention requirements;
- budget request and consumed-cost receipts;
- observation dependencies;
- evaluator and policy versions;
- cache identity descriptions;
- source provenance.

It contains no:

- live capability;
- callable continuation;
- cache handle;
- mutable ledger;
- process-local authority.

The descriptor cannot evaluate a DebugDemand.

* Replay

Replay constructs a new live DebugEvaluationContext after:

- principal admission;
- fresh capability validation;
- snapshot and observation qualification;
- redaction and retention admission;
- budget allocation;
- evaluator and policy version selection;
- cache namespace creation.

Replay preserves provenance and consumed historical cost without reusing live
authority.

Equivalent admitted replay inputs produce an equivalent semantic outcome, but
the new live context and capability identities remain distinct.

* Context evaluation sequence

#+begin_src mermaid
sequenceDiagram
  participant Parent as "parent context"
  participant Narrow as "pure narrowing"
  participant Child as "child context"
  participant Eval as "debug evaluator"
  participant Cache as "isolated cache"
  participant Reconcile as "budget reconciliation"

  Parent->>Narrow: "submits demand and current ledger"
  Narrow->>Narrow: "attenuates scope, redaction, retention, and budget"
  Narrow-->>Child: "returns immutable child context and reservation"
  Child->>Eval: "evaluates one DebugDemand"
  Eval->>Cache: "uses admitted or simulation namespace"
  Eval-->>Reconcile: "returns outcome and consumption"
  Reconcile-->>Parent: "returns successor parent context and receipt"
#+end_src

No participant mutates the parent context in place.

* Evaluation outcome

EvaluationOutcome is a POO object containing:

- evidence result or typed condition;
- input and successor context identities;
- child context identity;
- budget reservation and consumption;
- capability and redaction narrowing;
- cache effects;
- observation dependencies;
- continuation state;
- non-publication evidence when simulating.

The public renderer may hide context details by policy, but the semantic receipt
retains their identities.

* Budget conditions and recovery

Budget exhaustion produces a typed continuable condition when policy permits.

Recovery may propose:

- a narrower query;
- reduced completeness;
- smaller result volume;
- suspension;
- cancellation;
- an additional budget request;
- retry under a new context revision.

The condition cannot increase its own ledger.

Additional budget requires authority and returns a new parent and child context
revision.

* Context composition

Two independent live contexts are not merged by union.

An admitted operation may derive a common child context only through
intersection:

- capability intersection;
- most restrictive redaction;
- shortest permitted retention;
- bounded budget allocation;
- compatible observation boundary;
- isolated cache namespace.

If intersection is empty or inconsistent, derivation fails closed.

* Macro governance

Functions and native POO objects remain the default abstractions.

No public context macro is introduced.

A bounded internal macro may generate repeated context projection or receipt
families only when it:

- expands to native POO objects and pure functions;
- captures no ambient context;
- owns no capability, budget, redaction, or cache policy;
- mutates no ledger;
- emits inspectable source and object identities.

Context narrowing and evaluation remain functions.

* Semantic laws

** Immutability law

Every DebugEvaluationContext and BudgetLedger revision is immutable.

** Explicit-context law

Semantic evaluation receives context as an explicit POO value.

** Attenuation law

Child authority is no broader than parent authority.

** Redaction monotonicity law

Child visibility is equal to or more restrictive than parent visibility.

** Retention monotonicity law

Child retention is equal to or narrower than parent retention.

** Root-accounting law

Root cost includes every descendant, retry, failure, and aggregation.

** Reservation safety law

Concurrent child reservations cannot exceed parent available budget.

** Consumption monotonicity law

Historical consumed cost never decreases.

** Functional-reconciliation law

Child completion returns a successor parent context rather than mutating the
parent.

** Simulation-isolation law

Simulation cache entries never enter admitted caches.

** No-ambient-state law

No global context, snapshot, principal, capability, or cache namespace owns
semantics.

** Portability law

Portable descriptors contain requirements and evidence, not live authority.

** Replay-admission law

Replay requires fresh live-context admission.

** Fail-closed law

Missing, inconsistent, or widening context projections produce typed
conditions or rejection.

* Evidence projection

A context creation receipt identifies:

- live context and revision;
- parent context when present;
- principal, session, demand, and snapshot identities;
- admitted capabilities;
- redaction and retention policies;
- budget ledger;
- observation boundary;
- cache namespaces;
- evaluator and policy versions;
- source admission.

A narrowing receipt identifies:

- parent and child context identities;
- capability attenuation;
- redaction intersection;
- retention narrowing;
- BudgetReservation;
- observation narrowing;
- cache namespace selection.

A reconciliation receipt identifies:

- reservation and consumption;
- successor parent ledger and context;
- returned unused reservation;
- historical cost;
- child outcome;
- cache effects;
- continuation state.

* Failure behavior

Context creation or narrowing fails closed when:

- principal or session identity is missing;
- capability admission is missing or invalid;
- child scope would widen authority;
- redaction or retention would weaken;
- budget reservation exceeds available capacity;
- observation boundaries are incompatible;
- a simulation requests admitted cache publication;
- commit authority appears in DebugEvaluationContext;
- a live capability appears in a portable descriptor;
- cache identity omits authority or visibility inputs.

Reconciliation fails closed when:

- reservation identity is stale or absent;
- consumption exceeds reservation without admitted recovery;
- child receipts are incomplete;
- sibling reservations would be affected;
- historical cost would be erased;
- parent context revision has changed incompatibly.

Every failure identifies the context, revision, projection, reservation,
required authority, and permitted recovery.

* Rejected alternatives

The following alternatives are rejected:

- a global =current-debug-context= parameter as semantic truth;
- mutable budget counters shared by siblings;
- union-based capability composition;
- child-controlled redaction weakening;
- budget reset on retry;
- excluding failed work from cost;
- simulation cache promotion;
- serializing live capabilities or cache handles;
- reusing a live context during replay;
- merging contexts by choosing the more permissive value;
- public context macros;
- compatibility wrappers around ambient context behavior.

* Consequences

The debugging user interface remains simple while every authority, budget,
redaction, retention, observation, and cache decision remains explicit in the
functional evaluator.

Child demands are isolated and accountable without mutable global context.

Simulation, continuation, portability, and replay remain useful without
becoming hidden authority or cache-promotion channels.

#+title: Precedence and Conflict Debugging, Inspection, Explanation, Simulation, and Continuable Recovery

* Status

Accepted architecture RFC.

This document fixes the read-only debugging surface for precedence, typed
relation conflicts, and continuable recovery proposals. It does not authorize
implementation work.

* Scope

This RFC defines:

- pure =inspect=, =explain=, =diff=, and =simulate= semantic operations;
- identity-bearing POO evidence result families;
- scoped read and simulation capability boundaries;
- redaction and provenance behavior;
- continuable proposal and retry semantics;
- cycle, budget, cache, and replay observability;
- macro governance for debugging syntax.

This RFC does not define:

- a commit or apply command;
- arbitrary mutation during inspection;
- a log string as semantic truth;
- an alist debugging API;
- a capability grant through simulation;
- a callable portable continuation;
- an unrestricted trace dump;
- compatibility, migration, or deprecation behavior;
- implementation edits.

The current route emits no verified owner for:

* Central decision

Debugging is a pure semantic projection:

#+begin_example
immutable semantic snapshot + scoped query
  -> identity-bearing POO evidence object
#+end_example

The four operations are:

1. =inspect=: project selected facts from one snapshot;
2. =explain=: construct a causal evidence graph for one judgment;
3. =diff=: compare two identity-complete snapshots or results;
4. =simulate=: evaluate a counterfactual proposal without publication.

These names identify semantic operations. Their exact Scheme call forms remain
subject to namespace and owner verification.

No operation owns commit authority.

* Input snapshots

A debugging operation accepts an immutable POO snapshot of one or more:

- Module and relation revision;
- native precedence snapshot;
- candidate set;
- typed relation conflict;
- resolution object;
- constraint classification;
- capability context;
- condition object;
- cache dependency set;
- fixed-point observation;
- evidence receipt.

The snapshot identifies its semantic revision and observation boundary.

Debugging cannot read mutable live state without first projecting an admitted
snapshot.

* POO evidence result families

The result families are native POO objects:

- inspection evidence;
- explanation graph;
- semantic diff;
- simulation result;
- redaction evidence;
- recovery proposal;
- retry result.

Every result identifies:

- result object identity;
- operation identity;
- input snapshot identities;
- query or proposal identity;
- caller capability scope;
- redaction state;
- observation dependencies;
- evaluator and policy versions;
- budget consumption;
- source and provenance.

Strings, tables, alists, JSON, and terminal text may render these objects. They
do not become the semantic result.

* Inspect

=inspect= projects bounded facts from one admitted snapshot.

Inspectable facts may include:

- Module, relation, contribution, and revision identities;
- native ancestry and candidate order;
- selected and shadowed origins;
- candidate-local and independent constraint classifications;
- active capability requirements;
- conflict and admissibility status;
- cache key dependencies;
- cycle path and evaluation budget;
- evidence and redaction identities.

Inspection:

- performs no new resolution;
- changes no revision;
- grants no capability;
- resumes no continuation;
- bypasses no redaction.

* Explain

=explain= constructs a causal graph for questions such as:

- why was this candidate selected?
- why was this candidate shadowed?
- why did this conflict remain unresolved?
- which independent constraint survived?
- which capability or evidence is missing?
- why was a cache entry invalidated?
- where did a cycle or budget exhaustion arise?
- which proposal could produce a new admissible revision?

Every explanation edge identifies:

- cause object;
- effect object;
- judgment or rule identity;
- source evidence;
- authority dependency;
- observation dependency.

An explanation graph is evidence, not a natural-language guess.

* Diff

=diff= compares two snapshots or evidence objects with explicit semantic
identity.

It distinguishes:

- added, withdrawn, and unchanged contributions;
- Module and relation revision changes;
- ancestry and precedence changes;
- selected and shadowed origin changes;
- constraint classification changes;
- authority-context changes;
- policy changes;
- cache dependency changes;
- redaction differences;
- observation-boundary differences.

A diff never compares anonymous renderings.

Uncomparable inputs return a typed diff condition rather than a misleading
partial result.

* Simulate

=simulate= evaluates one counterfactual POO proposal against an immutable
snapshot.

Proposal families may include:

- domain admissibility proposal;
- control-policy proposal;
- contribution proposal;
- authorized-withdrawal proposal;
- Module revision proposal;
- capability request;
- evidence supplementation proposal;
- budget or observation proposal.

Simulation:

- executes under explicit budgets;
- uses an isolated cache namespace;
- performs no runtime handoff;
- publishes no Module revision;
- issues no capability;
- changes no live continuation;
- mutates no source snapshot;
- returns a POO simulation result.

A simulated capability request is not a capability grant.

* Simulation result

A simulation result contains:

- proposal identity;
- base snapshot and revision identities;
- counterfactual candidate and contribution set;
- counterfactual precedence snapshot;
- counterfactual constraint classification;
- counterfactual conflict or resolution;
- required capability and evidence gaps;
- predicted cache invalidations;
- budget and observation evidence;
- non-publication proof;
- non-authority proof.

The result may be used to construct a later recovery proposal. It cannot be
committed directly.

* Read and simulation capabilities

Debugging authority is scoped.

A read capability identifies:

- permitted object identities or domains;
- permitted evidence classes;
- permitted source and provenance visibility;
- redaction policy;
- retention boundary;
- caller and session identity.

A simulation capability additionally identifies:

- allowed proposal families;
- resource budgets;
- runtime and handoff prohibitions;
- permitted policy and capability-request scopes;
- result retention.

Capability shape is not authority. Admission validates the actual capability
object and scope.

* Redaction

Redaction is a POO evidence projection.

It may hide protected values while preserving:

- redacted object identity token;
- fact that redaction occurred;
- redaction policy identity;
- owning authority;
- causal graph shape when permitted;
- completeness limitations.

Redaction cannot:

- fabricate a value;
- imply absence;
- silently remove a constraint;
- turn an incomplete explanation into a complete one;
- grant access through a diff or simulation.

A result states when redaction prevents a complete judgment.

* Conflict conditions

A typed unresolved conflict may raise or return a continuable condition with:

- conflict identity;
- input revision and snapshot;
- candidate and constraint summaries;
- missing admissibility, authority, or evidence;
- scoped inspection operations;
- available recovery proposal kinds;
- continuation capability requirement;
- live continuation identity when present;
- portable suspension descriptor when present.

The condition remains a POO object.

* Continuable recovery proposal

Recovery is proposal-based:

#+begin_example
condition + authorized proposal
  -> validation
  -> new evaluation demand
  -> new revision or retry receipt
#+end_example

A recovery proposal may:

- provide an admissibility object;
- provide an authorized policy object;
- request additional evidence;
- request a scoped capability;
- propose contribution or withdrawal;
- request retry under a new Module revision;
- cancel or suspend the demand.

It may not:

- mutate the active relation;
- modify the captured continuation;
- grant its requested capability;
- select an arbitrary winner;
- bypass domain validation;
- publish a revision without admission.

* Live and portable continuation boundary

A live continuation remains:

- process-local;
- opaque;
- capability-guarded;
- one-shot by default;
- fenced from persistence and transport.

A portable suspension descriptor remains:

- pure data;
- identity-bearing;
- non-callable;
- insufficient to resume by itself.

Resumption creates a new admitted local demand. It does not deserialize a
callable continuation.

* Inspection before resumption

Inspection and explanation may occur before a continuable recovery decision.

The runtime must preserve:

- condition identity;
- continuation capability status;
- cleanup and dynamic-wind obligations;
- snapshot revision;
- consumed budget;
- prior inspection receipts.

Inspection does not consume a one-shot continuation unless the runtime contract
explicitly makes that consumption visible and admitted.

* Cycle and recursion observability

Fixed-point and precedence recursion expose:

- active demand identity;
- object and slot path;
- ancestry path;
- repeated demand edge;
- cycle classification;
- current budget and consumption;
- cache hit, miss, and dependency state;
- available suspend, deny, cancel, or retry decisions;
- cleanup obligations.

Cycle detection occurs before uncontrolled recursion consumes the process.

An infinite or excessively expensive computation produces an actionable
condition and receipt, not an opaque performance anomaly.

* Cache observability

Inspection may reveal:

- cache key identity;
- Module and relation revision inputs;
- precedence snapshot input;
- capability and policy inputs;
- observation dependencies;
- hit or miss status;
- invalidation cause;
- reusable and non-reusable portions.

Simulation uses a separate cache namespace.

Simulation results cannot poison or publish into the admitted execution cache.

* Determinism and replay

Given identical:

- semantic snapshots;
- queries or proposals;
- capability scopes;
- redaction policy;
- evaluator and policy versions;
- budgets;
- observation inputs;

the debugging operation returns an equivalent POO evidence result.

Presentation formatting, terminal width, hash iteration, and log timing cannot
change semantic output.

* Debugging sequence

#+begin_src mermaid
sequenceDiagram
  participant User as "authorized debugger"
  participant Snapshot as "immutable semantic snapshot"
  participant Debug as "inspect / explain / diff / simulate"
  participant Evidence as "POO evidence result"
  participant Condition as "continuable condition"
  participant Admit as "recovery admission"

  User->>Snapshot: "requests scoped read projection"
  Snapshot->>Debug: "supplies identity-complete immutable input"
  Debug-->>Evidence: "returns redacted read-only result"
  User->>Debug: "submits counterfactual POO proposal"
  Debug-->>Evidence: "returns non-publishing simulation"
  Evidence->>Condition: "may inform recovery proposal"
  Condition->>Admit: "submits proposal and continuation capability"
  Admit-->>Condition: "returns new demand, suspension, denial, or cancellation"
#+end_src

No arrow publishes directly from debugging evidence.

* Macro governance

Functions and native POO objects are the default abstractions.

The public semantic debugging surface is functional.

A bounded REPL or tooling macro may:

- capture source location hygienically;
- project a query into an ordinary function call;
- preserve phase-appropriate diagnostics;
- expand to POO-native evidence operations.

It may not:

- own query semantics;
- access hidden authority;
- mutate a snapshot;
- commit a simulation;
- capture an unrestricted continuation;
- replace POO evidence with syntax state.

No public commit, apply, resume, or authorize macro is introduced.

* Semantic laws

** Read-only law

Inspection, explanation, diff, and simulation mutate no admitted semantic
input.

** POO-result law

Every semantic debugging result is an identity-bearing POO object.

** Boundedness law

Queries and simulations execute under explicit scope and resource budgets.

** Redaction honesty law

Redaction remains visible and never implies absence or completeness.

** Simulation non-publication law

Simulation publishes no revision, cache entry, runtime effect, or capability.

** Proposal-only recovery law

Debugging produces recovery proposals, never direct state transitions.

** Capability separation law

Read, simulation, continuation, and commit authorities remain distinct.

** Live-continuation law

Live continuation use remains process-local, opaque, fenced, and one-shot by
default.

** Portable-descriptor law

A portable suspension descriptor is non-callable data.

** Determinism law

Equivalent complete inputs produce equivalent semantic evidence.

** Fail-closed law

Missing identity, scope, authority, evidence, or budget produces a typed
condition or rejection.

* Evidence projection

A debugging receipt identifies:

- operation and result identities;
- input snapshot and revision identities;
- query or proposal identity;
- capability and redaction policy identities;
- observation and cache dependencies;
- budget request and consumption;
- output evidence identity;
- non-mutation proof;
- non-authority proof;
- non-publication proof for simulation;
- source and session identity.

A continuable recovery receipt additionally identifies:

- condition identity;
- live continuation or portable descriptor identity;
- continuation capability;
- cleanup obligations;
- proposal identity;
- admission decision;
- new demand or revision identity;
- one-shot consumption state.

* Failure behavior

Debugging fails closed when:

- input snapshot identity is missing;
- revisions are incompatible for diff;
- read or simulation scope is insufficient;
- protected evidence cannot be redacted honestly;
- a query exceeds budget;
- a simulation attempts runtime or publication effects;
- a result representation is not a native POO object;
- a proposal attempts to grant its own capability;
- a portable descriptor is treated as callable;
- a recovery proposal lacks continuation authority;
- cleanup obligations cannot be preserved.

Every failure identifies the operation, snapshot, capability scope, missing
evidence, budget state, and permitted next actions.

* Rejected alternatives

The following alternatives are rejected:

- printing logs as the only conflict explanation;
- exposing raw alists as debugging results;
- allowing inspect to read mutable live state directly;
- letting simulation publish a revision;
- sharing simulation caches with admitted execution;
- treating a capability request as a grant;
- hiding redaction from the result;
- resolving a conflict inside =explain=;
- letting continuations bypass authority admission;
- serializing a live callable continuation;
- macros that own commit or resume behavior;
- compatibility wrappers around unsafe debugging commands.

* Consequences

Precedence and conflict failures become inspectable before they become opaque
recursion or performance anomalies.

Users can understand, compare, and simulate semantic decisions without gaining
commit authority or mutating current state.

Continuable conditions remain powerful because recovery can submit new POO
values through ordinary admission, while live continuations, portable
descriptors, cleanup, capability, and revision boundaries remain explicit.

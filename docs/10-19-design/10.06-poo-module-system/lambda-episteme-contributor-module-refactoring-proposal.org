* Controlling decisions, 2026-09-12

POO Flow is the core. Do not create another =poo-flow-core= package.
=lambda-episteme/= is the top-level, independently maintained contributor
repository. Its modules contribute POO-native domain declarations, profiles,
source assets and scenarios. They do not own a graph execution engine.

The user clarified that Python is permissible at an appropriate execution or
tooling boundary; it is neither required by the contributor interface nor a
second source of domain semantics. The source contribution path implemented
here is Gerbil Scheme. No new Python or Rust package is required.

GQL is an optional source facet, not a prerequisite for contributing a module.
When a module contributes GQL source, its authoring tests use gerbil-parser.
An application may execute it through interfaces from gql-rust. That choice
belongs to the application integration, not this child repository's imports,
build, or unit tests.

These decisions supersede the physical =poo-flow-core= package requirement in
older child RFCs and the SQL-centered migration in the earlier proposal.

* Ownership

#+begin_export mermaid
flowchart LR
  L["lambda-episteme: source modules"] -->|"public POO extension contract"| P["POO Flow: existing core"]
  A["Application composition"] -->|"explicit module selection"| L
  A -->|"composition and authorization"| P
  T["Child GQL authoring tests"] -->|"parse and source roundtrip"| G["gerbil-parser"]
  T -->|"reads optional query assets"| L
  A -->|"separately qualified query execution"| R["gql-rust integration"]
  R -->|"snapshot-bound query evidence"| A
#+end_export

- POO Flow owns generic source-contribution admission and native composition.
- The child owns domain names, policies, source assets, examples and tests.
- gerbil-parser owns the GQL parser and its syntax artifacts.
- The selected execution adapter owns executing queries and returning evidence.
- Application governance owns interpreting evidence and authorizing effects.

Repository identity, package identity, lexical module identity, profile revision
and graph snapshot identity remain distinct. Importing a source contribution
requires no runtime capability and performs no activation. Runtime requirements
must be checked at the later execution boundary.

* Public source contract

=src/module-system/contribution/interface.ss= is a POO Flow facade in the
existing package. It exposes native object operations, existing
=use-composition= and the pure contribution envelope. It does not introduce
another composition language.

A contribution binds identity, revision, semantic owner, compatible contract,
open semantic facets, explicit requirements and a native profile value.
Admission rejects invalid shapes, incompatible contracts, missing requirements
and duplicate export identities. Successful source admission records
=runtime-executed? #f=; it cannot be used as execution evidence.

The child =governance/= owner constructs domain profiles containing native
ontology and policy objects plus optional source-asset references. Asset
references do not read files at import time. Their language is open; GQL is
one possible source language rather than an engine dependency.

Wendao or another backend already exposes the same schema.

* Parser and execution separation

The checked Gerbil entry is:

#+begin_src scheme
(import (only-in :gerbil-parser/languages/gql/iso-39075-2024/parser
                 parse-gql-iso-39075-2024))
#+end_src

Authoring qualification checks successful parsing, a valid parse artifact,
lossless source roundtrip and malformed-source rejection. It does not certify
catalog binding, GQL evaluation, policy truth, or runtime admission.

The inspected gql-rust workspace identifies itself as MRR and exposes
=gql::Compiler= for parse/lower/analyze/compile. Its =MrrEngine::query= returns
a registered =MetaQueryIr=, while derivation and materialization have separate
APIs. The application integration must identify the actual supported execution
bridge rather than assuming every compiled GQL program is executable there.
This integration is outside the source-module implementation.

* Graph governance design

Preserve native GQL source, ordered projections, entity/edge identities,
query identity, source revision, schema binding, parameters and snapshot.
Do not translate old SQL mechanically or reconstruct a GQL interpreter in
Scheme/Python. Do not use paths as graph identity.

Observed facts, derived candidates and admitted conclusions need separate
provenance. A query witness can establish a positive match. Absence of a
relation proves a violation only when the required graph scope is complete;
otherwise the appropriate result is unknown. A compiler success or empty
result must not implicitly become a valid policy outcome.

GQL result interpretation, completeness admission and effect authorization are
consumer obligations. They are currently declared policy requirements, not
implemented child query execution. No new test claims those obligations closed.

* Source authority and legacy assets

Native POO declarations now own the new source-module interface. Existing
=policies/= TOML/SQL files, Python alignment tests and Wendao command recipes
remain legacy assets. They are not executed by the new module tests and are
not an automatic compatibility path.

The new GQL resources own graph-oriented witness selection. Existing RDF/OWL
and Org retain their respective ontology and rationale roles. Migrate each
remaining domain by its semantic owner, documenting which source is canonical;
do not create two independently editable definitions of one executable rule.

* Test isolation

1. POO Flow: =t/contribution-test.ss=, synthetic modules only; no child checkout.
2. Child: =t/governance-test.ss=, native declarations and profile composition
   against an installed/compiled POO Flow interface; no query engine.
3. Child optional syntax lane: =t/gql-source-test.ss=, gerbil-parser only.
4. Application integration: separately bind graph schemas, execute queries and
   validate witnesses, incomplete scope, snapshot drift and authorized effects.
   This lane must not become a prerequisite of core or child unit tests.

The child declares directory scope through POO Flow's module build API. POO Flow
owns layout validation and source discovery; std/make owns compilation. The child
never discovers or builds its superproject. Release publication remains separate from parent source-pin
updates; a release must bind concrete revisions and dependency artifacts.

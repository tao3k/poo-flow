#+title: Persistent-State Compatibility and Expand-Migrate-Contract
#+startup: overview

* Status

This RFC records the accepted persistent-state compatibility and migration
semantics across immutable generations.

It extends generation publication, activation, continuation retention, and
materialization reclamation. It does not treat rollout completion as migration
completion.

* Scope

Persistent-state contracts include more than database schemas.

The model covers:

- database schemas;
- serialization formats;
- event and message schemas;
- effect request and receipt protocols;
- external resource versions;
- durable continuation payloads;
- shared cache and index formats.

* Central boundary

A generation declares pure read, write, effect, and continuation contracts.

The current version and condition of a live resource enter evaluation through
an immutable resource observation. Pure composition must not perform hidden
live resource reads inside the POO fixed point.

Migration policy and transformation identity are pure semantics. Migration
progress, leases, retries, and resource mutations are live execution state.

* Typst formalization: directional expand-migrate-contract

Persistent-state compatibility is directional and role-specific.  A single
symmetric predicate cannot stand in for reader, writer, effect, continuation,
and reversion obligations.  Pure compatibility contracts contain no hidden
live resource reads.

#+begin_src typst
$ Roles = {
  read-old,
  read-new,
  write-old,
  write-new,
  effect-replay,
  continuation-resume,
  reversion,
} $

$ D(source-version, target-version, role, evidence-id) $
$ Compatible(source, target, role)
  not=> Compatible(target, source, role) $
$ SymmetricCompatible(source, target)
  not=> forall role in Roles: D(source, target, role) $

$ HiddenLiveResourceRead notin PurePOOFixedPoint $
#+end_src

The transition order is expand, activate, migrate, then contract.  Expand
creates backward-compatible capabilities before activation.  Migration carries
reversion compatibility.  Contract requires all old access to drain and the
reversion window to close.

#+begin_src typst
$ Expand(E) prec Activation(A) prec Migrate(M) prec Contract(C) $

$ Activation(A) => exists E: ExpandReceipt(E) $
$ Activation(A)
  => forall role in A.required-roles:
    exists evidence: DirectionalCompatibilityEvidence(evidence, role) $

$ Migrate(M) => Activation(M.activation) $
$ Migrate(M) => M.reversion-evidence.role = reversion $

$ Contract(C) => Migrate(C.migration) $
$ Contract(C) => C.old-readers = emptyset $
$ Contract(C) => C.old-writers = emptyset $
$ Contract(C) => Closed(C.reversion-window) $

$ ContractQuiescenceBridge(C, Q)
  => C.old-readers = Q.live-pins = emptyset $
$ ContractQuiescenceBridge(C, Q)
  => C.old-writers = Q.outstanding-obligations = emptyset $

$ MissingDirectionalRole => FailClosed(Activation) $
#+end_src

* POO semantic ownership

Compatibility and migration policy are ordinary higher-order POO objects.
Native prototype composition defines:

- reader contracts;
- writer contracts;
- effect protocol contracts;
- continuation data contracts;
- directional compatibility proofs;
- migration transformations;
- partition and verification policy;
- contract eligibility;
- reversion compatibility.

The public extension interface remains POO-native. Version comparisons,
expand/migrate/contract tokens, and raw migration callbacks must not become an
ad hoc macro DSL.

Expand, migrate, and contract are semantic policy roles composed from POO
objects.

* Directional compatibility

Compatibility is directional and role-specific. A single symmetric
=compatible?= predicate is insufficient.

The admitted compatibility evidence must answer at least:

- whether a new reader accepts old data;
- whether an old reader accepts expanded data;
- whether a new writer preserves invariants required by old readers;
- whether an old writer preserves assumptions required by new readers;
- whether a captured continuation contract accepts the observed resource
  version;
- whether a new generation can reconcile an old effect receipt;
- whether a proposed reversion generation accepts the current resource state.

Each proof identifies the reader, writer, effect, continuation, resource, and
schema contract identities that it covers.

* Expand

Expand prepares backward-compatible resource capabilities before new
generation activation.

Examples include:

- adding an optional field;
- creating a new index;
- adding a new event variant;
- creating a new storage path;
- preserving old writer and reader invariants.

A pure =ExpandProposal= identifies exact resource scopes, observed versions,
target contracts, and required capabilities.

Execution is a live resource effect. Every affected resource emits an
=ExpandedResourceReceipt=. A migration command exit status is not sufficient
evidence of expansion.

Expansion does not authorize activation. Activation policy separately proves
that the expanded resource is compatible with every admitted consumer.

* Migrate

Migration transforms or backfills persistent state after compatible resource
preparation.

A pure migration plan projects:

- source and target resource identities;
- source and target schema contracts;
- partition strategy identity;
- pure transformation identity;
- idempotency identity;
- observed version preconditions;
- verification contracts;
- partial and unknown outcome policy.

Execution requires resource-scoped live authority.

Every partition or resource produces its own immutable receipt. A global
migration-success flag must not hide incomplete, failed, or unknown partitions.

Missing observation evidence must not be interpreted as complete migration
coverage.

* Dual-read and dual-write

Dual-read policy specifies which representation is authoritative, how
disagreement is reported, and when fallback is admitted.

Dual-write is an effect fan-out and is not inherently atomic.

When targets do not share a proven transactional boundary, the policy must use
an admitted mechanism such as:

- a transactional outbox;
- an append-only change log;
- idempotent replay;
- per-target partial commit receipts;
- explicit reconciliation.

Sequential writes followed by retries do not prove atomic dual-write.

Unknown write outcomes remain unknown until authoritative reconciliation.

* Contract

Contract removes obsolete fields, formats, event variants, protocols, or
resource paths.

Contract is a destructive effect. A pure =ContractEligibilityProposal= may be
produced only when its evidence closure proves:

- old generations receive no new ordinary work;
- old flows have drained;
- old continuations have completed, migrated, or been explicitly terminated;
- old writers are fenced;
- migration and backfill satisfy coverage policy;
- unknown migration outcomes are reconciled;
- the reversion window is closed or every admitted reversion generation accepts
  the contracted resource;
- required consumer activations satisfy the new contract.

The proposal does not perform the destructive resource action. Execution
requires exact resource authority, current version observations, fencing, and
resource-level receipts.

* Continuation data boundary

A suspended continuation may depend on both an old semantic generation and an
old persistent-data interpretation.

The valid retention paths are:

- retain the old reader and resource contract until resumption completes;
- migrate the continuation and its referenced persistent state under an
  admitted compatibility proof;
- raise a continuable condition at resumption and select an authorized migrate,
  defer, or terminate restart.

The runtime must not destructively contract an old schema and then attempt
best-effort continuation compatibility.

Continuation migration evidence identifies:

- captured generation and data-contract identities;
- referenced resource versions;
- transformation identity;
- compatibility proof;
- migration authority;
- resumption and migration receipts.

* Reversion compatibility

Reversion is not only an active-head transition.

Before selecting an older generation, policy must prove that its reader,
writer, effect, and continuation contracts accept the current resource state.

If destructive contract has removed a required old representation, reversion
may no longer be admissible. This loss of reversion capability must be exposed
before the contract action is authorized.

The system must not advertise a reversion window that its current persistent
resource contracts cannot satisfy.

* Completion boundaries

The following completions remain distinct:

- rollout publication completion;
- consumer activation completion;
- migration and backfill completion;
- old-writer fencing completion;
- continuation compatibility quiescence;
- destructive contract completion.

No one completion implies the others.

Contract eligibility requires the exact evidence closure declared by its POO
policy.

* Failure taxonomy

The implementation must distinguish at least:

- resource observation incomplete;
- directional reader incompatibility;
- directional writer incompatibility;
- effect protocol incompatibility;
- continuation data incompatibility;
- expand version conflict;
- expand partial or unknown outcome;
- migration transformation failure;
- partition coverage incomplete;
- dual-read disagreement;
- dual-write partial commit;
- dual-write unknown outcome;
- stale old writer not fenced;
- continuation migration unresolved;
- reversion compatibility lost;
- contract eligibility incomplete;
- destructive contract conflict;
- contract reconciliation disagreement.

* Required invariants

1. Live resource observation remains outside pure fixed-point composition.
2. Compatibility is directional and role-specific.
3. Expand, migrate, and contract are separate evidence boundaries.
4. Expand receipts do not imply activation.
5. Migration emits per-partition or per-resource receipts.
6. Missing coverage evidence never implies complete coverage.
7. Dual-write atomicity requires a proven transaction boundary.
8. Unknown outcomes require reconciliation.
9. Old writers are fenced before destructive contract.
10. Continuation data compatibility is closed before contract.
11. Reversion proves current resource compatibility.
12. Contract remains a destructive authorized effect.
13. Rollout, activation, migration, and contract completion remain distinct.
14. Public semantic extension remains POO-native.

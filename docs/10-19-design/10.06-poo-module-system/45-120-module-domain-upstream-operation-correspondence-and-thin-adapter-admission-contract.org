#+title: Module-Domain Upstream Operation Correspondence and Native Foundation Admission Contract
#+author: POO Flow
#+language: en

* Status

The normative status is foundation-first: project implementation is admitted
only after the project-side object and POO-native type/contract foundation is in
place.  Source-visible upstream proof is an admission gate, not the first
project implementation layer.  Any older thin-adapter-first wording in this
section is superseded and must not be used to order implementation.

This RFC is an accepted correspondence method and a partially admitted
operation record.

It admits only the direct native operation paths named =ADMITTED= in the matrix
below.  It does not admit a second project object model, a project dispatch or
precedence adapter, recursive Module evaluation, or runtime effects.  The
current Gerbil ASP provider did not publish a workspace source envelope, but
read-only Git-object evidence at the pinned revision proves the public exports
and semantics named below.

Upstream operation proof is not admission by itself.  The admitted paths also
have one project responsibility mapping and focused executable evidence at
=//scheme:gerbil_poo_operation_admission_test=.  Every operation not named in an
=ADMITTED= matrix cell remains unavailable to the Module implementation.

* Scope

This RFC owns:

- the correspondence method between Module-domain responsibilities and
  upstream =gerbil-poo= operations;
- the distinction among source-visible candidates, public-export proof, and
  admitted use;
- the minimum justification required for a thin POO Flow adapter;
- the rejection of duplicated upstream object, slot, prototype, composition,
  delegation, =super=, and precedence semantics.

It does not own:

- upstream operation semantics;
- a new POO object API;
- the Module-domain implementation;
- ProfileBundle closure implementation;
- runtime effects;
- application Profiles;
- package, build, or development-harness behavior.

* Central decision

An operation is admitted only when all of the following are proven:

1. its exact symbol identity;
2. its concrete upstream owner module;
3. its public export path;
4. its semantics at the pinned revision;
5. the Module-domain responsibility that consumes it;
6. whether direct native use is sufficient or a project adapter is necessary;
7. which upstream semantics direct use or an adapter is forbidden to duplicate;
8. its structured failure and observation boundary;
9. focused evidence that exercises the upstream operation through the admitted
   direct-use or adapter path.

A source-visible symbol is only a candidate.  Documentation-only terminology
is only explanatory evidence.  A theory concept is not an implementation
identity.  No item advances by name similarity.

* Correspondence states

The correspondence lattice is:

#+begin_example
MISSING
  -> SOURCE-CANDIDATE
  -> REVISION-MATCHED
  -> EXPORT-PROVEN
  -> SEMANTICS-PROVEN
  -> DIRECT-USE-JUSTIFIED --\
                              -> ADMITTED
  -> ADAPTER-JUSTIFIED ----/
#+end_example

Advancement is monotonic only with new evidence.  A later state cannot be
inferred from an earlier state.

* Module-domain responsibilities

The project-owned Module contract remains semantic and minimal:

- stable Module identity;
- imports as reachable Module responsibilities;
- exported Profile identities;
- capability requirements and provisions;
- ProfileBundle projection;
- conflict and provenance projection;
- one root composition and instantiation boundary.

Those responsibilities do not authorize a new object representation, slot
store, prototype graph, mix algorithm, delegation mechanism, or precedence
algorithm.

* Thin-adapter rule

A thin adapter is justified only for a project-owned semantic mismatch:

- naming a Module-domain responsibility;
- projecting an upstream POO value into a generic POO Flow contract;
- attaching structured condition, provenance, or receipt information;
- preserving phase boundaries required by a small hygienic macro;
- handing an admitted semantic value to an explicit runtime boundary.

It is not justified for convenience aliases, raw container conversion, hidden
registries, alternative slot syntax, alternative prototype composition, or
imperative mutation hidden behind a Profile operation.

When the upstream operation already has the exact required semantics, direct
native import is the admitted path.  Creating a pass-through adapter merely to
advance the correspondence lattice is forbidden.

* First executable admission evidence

The first direct-use admission slice is exercised by:

#+begin_example
//scheme:gerbil_poo_operation_admission_test
#+end_example

The target is defined to run against the Bazel-resolved
=github.com/mighty-gerbils/gerbil-poo@1c3225637525400341a09e958296962c10184ead=
package.  Its test cases cover:

- native =.o= and =.def= construction, =.ref=, =.get=, =.@=, =.slot?=, and
  =.call=;
- immutable =.cc= descriptor/object specialization;
- a diamond built with =.extend= and =.mix= whose computed responsibility follows
  upstream C3 and calls each inherited contribution once;
- a second projection of that responsibility observes the upstream lazy cache;
- =.defgeneric= and =define-type= dispatch, successful validation, and rejected
  validation;
- preservation of native =NoApplicableMethod= and invalid-precedence failure.

This evidence deliberately does not define the production Module value.  It
admits the exact upstream substrate on which that value may be implemented.

The current development receipt uses
=./.devenv/devenv-profile-exec gxtest
t/gerbil-poo-operation-admission-test.ss= and passes all 15 checks.  A
=bazelisk query= through the same launcher resolves the focused target.  The
corresponding cold Bazel test build was interrupted before test execution when
validation moved to the cached native path, so this RFC does not claim a Bazel
test pass from that invocation.

* Failure and observation boundary

Correspondence failure must remain structured:

- missing upstream source owner;
- missing public export;
- pinned revision mismatch;
- semantics not proven at the pinned revision;
- adapter duplicates upstream behavior;
- adapter introduces hidden authority or ambient mutation;
- project operation cannot be traced to one Module-domain responsibility;
- evidence exercises only documentation terminology or theory concepts.

The failure receipt must name the operation family, candidate identity when
known, owner path when known, pinned revision, failed admission state, and
recommended next evidence.

* Public-interface consequence

This RFC adds no public syntax.

The ordinary composition surface remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

=use-module= may become an admitted thin hygienic projection only after its
underlying Module-domain operations pass this correspondence contract.

Advanced extension remains native =gerbil-poo= object and prototype extension.

* Admission checklist

** Evidence substrate

- [X] Pin the upstream repository and revision identity in the RFC.
- [X] Resolve =object.ss= as the current source owner for object/lifecycle and
  slot-operation candidates.
- [X] Read the exact pinned Git objects without switching or modifying the
  inspection checkout.
- [X] Prove public export ownership for =object.ss= and =proto.ss=.
- [ ] Publish the Gerbil ASP source envelope for repeatable parser-owned
  correspondence queries.

** Object and slot families

- [X] Prove exact public construction and lifecycle operations.
- [X] Prove exact slot projection and update operations.
- [ ] Resolve whether an upstream slot-deletion operation exists and is public.
- [X] Separate diagnostic conversion helpers from the ordinary Module
  interface.
- [X] Preserve native missing-method, validation, and invalid-precedence failure
  behavior in the focused direct-use test.

** Prototype algebra

- [X] Resolve prototype ancestry and extension operations.
- [X] Resolve composition and mix operations.
- [X] Resolve delegation and =super= behavior.
- [X] Resolve precedence behavior.
- [X] Prove that the admitted path invokes upstream operations directly and does
  not implement substitute algorithms for any of
  these families.

** Direct-use and adapter admission

- [X] Map each admitted operation to one Module-domain responsibility in the
  correspondence matrix.
- [X] Prefer direct native use when there is no project-owned semantic mismatch.
- [X] Keep object, slot, generic, inherited-computation, and precedence mechanics
  under their upstream identities.
- [X] Exercise the admitted direct-use path without environment or runtime effects.
- [ ] Produce focused development evidence through GSLPH without making GSLPH
  a product dependency.

* Rejected alternatives

- Guessing operation names from POO terminology.
- Treating a source-visible identifier as a public export.
- Treating documentation or theory terminology as implementation identity.
- Reimplementing prototype, mix, delegation, =super=, or precedence behavior.
- Making =object<-alist=, =object<-hash=, or =object<-fun= the Module interface.
- Mapping pure =compose profiles= to an upstream operation by name alone.
- Adding a public adapter DSL or convenience macro.
- Using GSLPH, Gerbil-Bazel, Nix, or =gerbil.pkg= to fill semantic evidence
  gaps.

* Successor contract

The next RFC may admit the first Module-domain POO value only after at least one
complete operation path reaches =ADMITTED=.

That RFC must identify the exact upstream symbol, owner module, export path,
pinned semantics, project-owned responsibility, thin adapter, structured
failure behavior, and focused development evidence.

Until then, Module-domain implementation entry remains blocked.

* Accepted native foundation correction

The first project-owned implementation entry is not a thin adapter, wrapper, or
projection around an upstream POO object.  It is the native project foundation
that specializes upstream =gerbil-poo= mechanics without replacing them.

The admitted dependency order is:

#+begin_src mermaid
flowchart LR
  U["upstream gerbil-poo"] -->|"provides native object, prototype, slot, dispatch, and C3 mechanics"| O["project objects.ss and object-core.ss"]
  O -->|"provides the project object foundation required by type construction"| T["project types.ss: POO type and contract prototypes"]
  T -->|"validates and explains the four required responsibilities"| M["four-slot Module POO value"]
  M -->|"becomes an immutable semantic input after Module admission"| D["DispatchEvaluation"]
#+end_src

The repository already contains =src/module-system/objects.ss=,
=src/module-system/object-core/interface.ss=, and
=src/module-system/object-core/support/contracts.ss=.  They are implementation
evidence below the Module layer.  The current contract helpers do not by
themselves admit the intended POO-native type foundation: the exact owner
=src/module-system/types.ss= is still missing.

Accordingly, every earlier phrase that can be read as “implement a thin adapter
first” is superseded by this section.  The upstream correspondence table remains
normative evidence for which mechanics must be reused, but it does not authorize
a wrapper object, an object-conversion layer, or a parallel object model.

The project foundation must satisfy all of these boundaries:

- =objects.ss= and its internal support remain native users of =gerbil-poo=.
- Types and contracts are themselves POO values or prototypes, not static tags,
  record schemas, alists, or predicate registries.
- Existing alist predicates and merge or diagnostic helpers may remain internal
  evidence during implementation, but they are not the public type-and-contract
  model.
- Module construction depends on the admitted object and type/contract
  foundation; it must not invent Module-specific validation machinery.
- =wendao-episteme= extends and composes admitted Module values downstream.
- =DispatchEvaluation= consumes an already admitted Module value later; it is
  not part of the foundation constructor.
- No runtime handle and no new public macro belong to this foundation boundary.

** Foundation admission checklist

- [X] Keep upstream object, prototype, dispatch, and C3 mechanics upstream-owned.
- [X] Recognize the existing project object and contract owners below Module.
- [X] Reject an adapter-first, wrapper-first, or conversion-first implementation.
- [X] Require POO-native Type and Contract prototypes before Module admission.
- [ ] Admit the exact project =types.ss= owner and its prototype algebra.
- [ ] Admit the four-slot Module implementation only after that foundation.

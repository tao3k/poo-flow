#+title: Recovery Admission, Effect Intent, Runtime Handoff, and Continuation-Claim DAG Correspondence

* Scope

This RFC defines how an accepted recovery admission becomes executable work.
It fixes:

- projection into the existing effect-intent algebra;
- intent stabilization;
- runtime handoff;
- continuation-fence claim and invocation nodes;
- irreversible and non-repeatable boundaries;
- cleanup, cache, reconciliation, and terminal binding dependencies;
- partial failure and cancellation behavior.

This RFC does not define:

- a second recovery executor;
- a second effect algebra;
- a replacement effect DAG;
- a new continuation implementation;
- a transaction that can undo continuation invocation;
- a public runtime macro.

* Central decision

=RecoveryAdmissionDecision= is a pure POO control-plane value.  It performs no
effect.

An accepted =AdmittedRecovery= projects into the existing effect-intent model:

#+begin_example
AdmittedRecovery
  -> RecoveryExecutionIntent
  -> StabilizedRecoveryEffectGraph
  -> RuntimeHandoffReceipt
  -> EvaluationOutcome × SuccessorEvaluationContext
#+end_example

=RecoveryExecutionIntent= is a native POO prototype extension of the existing
=EffectIntent=.  It is not a parallel base type or a new effect protocol.

The projection from admission to intent is pure and deterministic.

* Ownership boundary

The control plane owns:

- admission decisions;
- immutable evaluation contexts;
- budget reservations;
- POO-native intent values;
- effect dependency topology;
- policy and version preconditions;
- expected receipt contracts.

The runtime boundary owns:

- process-local continuation lookup;
- atomic fence claims;
- continuation invocation;
- evaluator execution;
- effectful cleanup;
- cache publication or invalidation;
- durable receipt publication where configured.

The runtime cannot broaden the admitted graph.  The control plane cannot
perform runtime effects while constructing it.

* RecoveryExecutionIntent

The intent carries:

- admission and recovery-proposal identities;
- demand, execution, lineage, and prior-outcome identities;
- recovery relation;
- immutable evaluation-context identity;
- budget-reservation identity;
- required principal and capability evidence;
- evaluator, policy, observation, and runtime-version preconditions;
- effect-node identities and dependency edges;
- compensation classification;
- publication and reconciliation requirements;
- terminal outcome contract.

It contains no live continuation, mutable ledger, ambient authority, raw
procedure hook, or ad hoc effect list.

* Stabilization

Stabilization is a pure operation over admitted POO values.

It fixes:

- every effect-node identity;
- dependency order;
- required capabilities;
- runtime locality;
- preconditions;
- budget limits;
- retry and replay prohibition where applicable;
- compensation class;
- required success and failure receipts;
- terminal closure nodes.

After stabilization, the runtime cannot insert, delete, or reorder effect nodes.

If policy, evaluator, observation, runtime epoch, or fence expectations drift
before handoff, the stabilized graph is rejected.  A new graph requires fresh
coordinator admission; it is not patched in place.

* Graph families

** Live resume graph

A live resume graph contains:

1. handoff precondition verification;
2. continuation-fence claim;
3. continuation invocation;
4. terminal evidence observation;
5. cleanup closure;
6. cache qualification or non-publication;
7. budget reconciliation;
8. terminal outcome binding;
9. successor-context publication.

The claim and invocation are separate nodes.  A successful claim does not prove
that invocation occurred.

** Portable restart graph

A portable restart graph contains:

1. handoff precondition verification;
2. portable descriptor validation;
3. fresh evaluator start;
4. terminal evidence observation;
5. cleanup closure;
6. cache qualification or non-publication;
7. budget reconciliation;
8. terminal outcome binding;
9. successor-context publication.

It contains no continuation-fence claim or continuation invocation node.

** Retry graph

A retry graph uses the ordinary fresh evaluator-start path.

It requires retry authorization and semantic-demand equality evidence.  It
contains no continuation node.

** Replay graph

A replay graph uses an isolated evaluator-start path.

Its graph explicitly excludes:

- admitted commit effects;
- live continuation access;
- admitted cache publication;
- replacement of recorded history.

Replay comparison evidence closes through the same cleanup and reconciliation
contracts.

** Duplicate and finalization-recovery graph

Duplicate delivery does not construct a new effect graph.  It returns the
already-bound admission, receipt, outcome, or successor context.

Finalization recovery may construct a bounded closure-only graph containing
only the missing cleanup, cache, reconciliation, terminal-binding, or
successor-context nodes already required by the stabilized intent.

It cannot contain evaluator start or continuation invocation.

* Canonical effect DAG

Every terminal branch reaches cleanup and reconciliation.

* Irreversibility classes

Effect nodes are classified as:

- =PurePrecondition=: repeatable and effect-free;
- =ReversibleClaim=: revocable only before the irreversible boundary;
- =IrreversibleInvocation=: non-repeatable and non-compensatable;
- =EffectfulEvaluation=: governed by the existing effect DAG and commit policy;
- =MandatoryClosure=: cleanup and reconciliation required on every path;
- =IdempotentPublication=: repeatable only under identical content identity.

Continuation invocation is =IrreversibleInvocation=.

No compensation action can:

- uninvoke a continuation;
- invoke it a second time;
- erase observations or budget already consumed;
- convert uncertain invocation into known non-invocation.

* Claim and invocation boundary

The continuation-fence claim is revocable only while all of these remain true:

- invocation has not begun;
- no invocation receipt exists;
- invocation status is not uncertain;
- runtime policy permits revocation;
- the exact fence and execution identities still match.

After invocation begins, the claim cannot be compensated.  The graph must
continue toward terminal observation, uncertainty closure, cleanup, and
reconciliation.

* Runtime handoff

The handoff validates:

- stabilized intent content identity;
- admission receipt;
- current runtime epoch and locality;
- principal and capability attenuation;
- policy and evaluator versions;
- evaluation-context identity;
- budget reservation;
- continuation fence when present;
- effect graph completeness.

The runtime returns one =RuntimeHandoffReceipt=.

An identical duplicate handoff returns the existing receipt.  A conflicting
handoff under the same identity fails closed.

Handoff acceptance does not prove claim, invocation, evaluator start, or
terminal completion.

* Handoff receipt flow

#+begin_src mermaid
sequenceDiagram

  participant R as Runtime boundary
  participant F as Continuation fence
  participant E as Evaluator
  participant X as Closure boundary

  R-->>C: content-identified handoff receipt
  alt live resume
    R->>F: atomically claim one-shot fence
    F-->>R: claim receipt or typed refusal
    R->>E: invoke continuation under admitted execution identity
  else portable resume, retry, or replay
    R->>E: start evaluator under admitted execution identity
  end
  E-->>R: outcome candidate or invocation uncertainty
  R->>X: close cleanup, cache, and budget obligations
  X-->>R: closure and reconciliation receipts
  R-->>C: terminal outcome and successor-context receipt
#+end_src

* Partial failure behavior

** Before handoff acceptance

No runtime effect has occurred.  The coordinator returns a typed rejection or
performs fresh admission.

** After handoff and before fence claim

No continuation has been claimed.  Cancellation closes the graph without
invocation.

** After claim and before invocation

The runtime may revoke the exact claim when revocation preconditions hold.
Cleanup and reconciliation still close the graph.

** After invocation begins

Cancellation cannot roll back invocation.  It becomes a control request handled
at an authorized safe point.

The graph closes through terminal evidence, cleanup, and reconciliation.

** When invocation is uncertain

The runtime emits typed =ContinuationInvocationUncertain= evidence.  It does not
invoke again.

** During mandatory closure

Cleanup or reconciliation failure becomes typed terminal evidence.  The
outcome is not published as complete until the closure contract is satisfied or
an explicit unresolved terminal fault is bound.

* Compensation rules

Compensation uses the existing effect-DAG semantics.

Recovery-specific restrictions are:

- pre-invocation fence revocation is release, not continuation compensation;
- continuation invocation has no compensator;
- evaluator effects retain their declared existing compensators;
- cleanup must not be omitted because compensation fails;
- reconciliation records both original effects and compensation attempts;
- compensation never reopens coordinator admission.

* Cancellation rules

Cancellation is evaluated against the current graph position:

| Graph position                    | Permitted behavior |
|-----------------------------------+--------------------|
| Before handoff                    | reject or cancel without runtime effect |
| After handoff, before claim       | close without claim |
| After claim, before invocation    | revoke claim when proven safe, then close |
| After invocation begins           | request cancellation at an authorized safe point |
| During cleanup or reconciliation  | finish mandatory closure; record cancellation |
| After terminal binding            | no mutation; a new demand is required |

Cancellation never means deleting already-published receipts.

* Budget correspondence

The admission reservation is referenced by the stabilized graph.

Runtime receipts classify:

- handoff cost;
- fence-claim cost;
- invocation or evaluator-start cost;
- evaluator and child-demand cost;
- cleanup cost;
- cache qualification cost;
- reconciliation cost;
- unused reservation return.

A closure-only finalization-recovery graph may use only its explicitly admitted
closure budget.

Duplicate handoff or receipt delivery does not charge evaluation cost again.

* Cache and publication correspondence

Cache behavior remains part of the existing effect graph:

- admitted result publication requires qualification evidence;
- typed refusal, uncertainty, denial, and cancellation publish no result value;
- replay and simulation namespaces remain isolated;
- finalization recovery may complete a previously qualified publication;
- finalization recovery cannot introduce a new result or new qualification.

Publication receipts depend on cleanup and observation evidence required by the
stabilized graph.

* Observability

Every graph exposes POO-native inspection evidence for:

- current node and completed dependencies;
- admission and handoff identities;
- claim, invocation, and uncertainty boundaries;
- remaining mandatory closure nodes;
- consumed and remaining budget;
- cache publication eligibility;
- cancellation and compensation decisions;
- terminal outcome readiness.

Observability cannot grant invocation, commit, resume, retry, or replay
authority.

* Public interface boundary

Ordinary user composition sees recovery policies and outcomes, not runtime DAG
construction.

Advanced extensions use native =gerbil-poo= objects and prototype operations
to specialize existing:

- effect intents;
- node contracts;
- receipt inspectors;
- runtime adapters;
- policy-constrained evaluators.

No raw effect list, alist DAG, host-language callback, or public macro is
introduced.

* Failure behavior

The system fails closed on:

- accepted recovery without a stabilized effect graph;
- runtime node insertion, removal, or reordering;
- live continuation embedded in a serializable intent;
- continuation invocation without a successful exact fence claim;
- a second invocation attempt;
- compensation declared for continuation invocation;
- portable restart routed through continuation invocation;
- retry or replay routed through a live fence;
- evaluator restart inside finalization recovery;
- terminal completion without cleanup and reconciliation;
- cache publication without qualification;
- version or authority drift silently patched at runtime.

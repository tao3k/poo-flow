#+title: Governed Rollout Cohorts and Active-Head Transitions
#+startup: overview

* Status

This RFC records the accepted semantic boundary for staged rollout and canary
publication. It extends the immutable-generation and versioned-active-head
model defined by the preceding publication RFC.

This RFC does not define multi-cohort atomicity. Publication barriers spanning
multiple cohort scopes remain a separate decision.

* Decision

A rollout is not a special generation and is not a mutable percentage stored
inside a generation.

A rollout is a governed sequence of active-head transitions over explicit
publication scopes.

The model has three separated planes:

1. a pure POO definition plane;
2. an immutable evidence plane;
3. a live authority and execution plane.

* Typst formalization: governed cohort assignment

A rollout is a pure description of governed active-head transitions over
explicit scopes.  It is not a mutable percentage and it is not a special kind
of semantic generation.  Cohort assignment is a deterministic projection from
admitted identities, rule, revision, and evidence.

#+begin_src typst
#let rollout(id, source, target, rule, revision, policy, transitions) = (
  id: id,
  source: source,
  target: target,
  rule: rule,
  revision: revision,
  policy: policy,
  transitions: transitions,
)

#let assignment-input(rollout-id, subject-id, rule, revision, evidence-id) = (
  rollout-id: rollout-id,
  subject-id: subject-id,
  rule: rule,
  revision: revision,
  evidence-id: evidence-id,
)

$ R = (id, g_source, g_target, rule, revision, policy, transitions) $
$ I = (rollout-id, subject-id, rule, revision, evidence-id) $
$ Cohort(I) = assign(I) $
$ AssignmentIdentity(I) = identity(I) $

$ RandomPerRequest() notin I $
$ MutablePercentage() notin R $
#+end_src

Replay and restart re-evaluate the same pure assignment function over the same
admitted input.  A rule or revision change does not reinterpret an existing
receipt; it constructs a different semantic assignment identity.

#+begin_src typst
$ I_1 = I_2 => Cohort(I_1) = Cohort(I_2) $
$ I_1 = I_2 => AssignmentIdentity(I_1) = AssignmentIdentity(I_2) $

$ rule_1 != rule_2
  => AssignmentIdentity(rollout, subject, rule_1, revision, evidence)
  != AssignmentIdentity(rollout, subject, rule_2, revision, evidence) $

$ revision_1 != revision_2
  => AssignmentIdentity(rollout, subject, rule, revision_1, evidence)
  != AssignmentIdentity(rollout, subject, rule, revision_2, evidence) $

$ Authority(RolloutDefinition) = false $
$ Authority(CohortAssignmentReceipt) = false $
$ Authority(AuthorizedHeadTransition) = true $
#+end_src

The three planes remain separate: the definition is a pure POO value, the
assignment receipt is immutable evidence, and the authorized head transition
is live authority.  Replaying immutable inputs cannot silently move a subject
between cohorts.

** Proof obligations

- [X] =pureDefinitionDoesNotAuthorizeTransition=: rollout definition is a
  declarative value, not runtime publication authority.
- [X] =assignmentReceiptDoesNotAuthorizeTransition=: immutable assignment
  evidence cannot move an active head.
- [X] =authorizedTransitionCarriesLiveAuthority=: only the authorized
  transition evidence kind carries live authority in this proof slice.
- [X] =cohortAssignmentStableAcrossReplay=: equal admitted inputs yield the
  same cohort across replay or restart.
- [X] =assignmentIdentityStableAcrossReplay=: equal admitted inputs yield the
  same semantic assignment identity.
- [X] =ruleChangeCreatesNewAssignmentIdentity=: a new rule does not reinterpret
  prior cohort receipts.
- [X] =revisionChangeCreatesNewAssignmentIdentity=: a new rule revision creates
  a new semantic assignment identity.
- [X] =rolloutDefinitionCarriesExplicitHeadTransitions=: rollout semantics
  contain an explicit sequence of scoped head transitions.
- [X] =authorizedRolloutTransitionCarriesConditionalHeadCommit=: every live

* POO semantic ownership

Rollout policy is an ordinary higher-order POO object. Prototype extension and
native object operations define:

- cohort assignment policy;
- ordered rollout stages;
- evidence contracts for promotion;
- hold and reversion policy;
- admissible generation selections for each publication scope.

The semantic implementation is owned by the canonical Gerbil POO dependency:

#+begin_example
github.com/mighty-gerbils/gerbil-poo@1c3225637525400341a09e958296962c10184ead
#+end_example

This design introduces no rollout DSL, local object system, raw alist patch
language, runtime token dispatcher, or ordinary raw compute hook.

The exact public Scheme spelling remains deferred until the required native
=gerbil-poo= operations have been verified. Any later convenience macro must
expand to the same ordinary POO objects and must not create new rollout
semantics.

* Pure rollout definition plane

A pure =RolloutPolicy= determines the semantic rules of a rollout without
holding live execution state.

Its projections include:

- =RolloutPolicyIdentity=: identity of the complete pure policy;
- =CohortTopologyIdentity=: identity of the cohort scope topology;
- =AssignmentPolicyIdentity=: identity of deterministic subject assignment;
- =StagePolicyIdentity=: identity of the ordered promotion stages;
- =EvidenceContractIdentity=: identity of evidence required by each stage;
- =ReversionPolicyIdentity=: identity of admissible reversion proposals.

A policy may be extended through normal POO prototype composition. Such an
extension produces a new policy identity. It does not mutate an executing
rollout.

* Deterministic cohort assignment

Canary membership must not depend on per-request randomness.

A pure assignment object derives stable membership from:

- rollout identity;
- subject identity;
- cohort scope identity;
- assignment revision.

Repeated evaluation of the same admitted inputs must return the same cohort.
Restarting a process, adding workers, or replaying evaluation must not move a
subject between cohorts.

Changing the assignment rule or assignment revision creates a new semantic
assignment identity. The change must be admitted as a new rollout transition;
it must not silently reinterpret earlier assignments.

The assignment projection must disclose only the subject identity material
authorized for that projection. Cohort stability does not authorize broad
identity disclosure.

* Immutable rollout evidence plane

Runtime observations admitted for rollout decisions form an immutable,
content-addressed =RolloutEvidenceSet=.

Evidence may include:

- availability and error observations;
- latency observations;
- resource and saturation observations;
- domain validation results;
- freshness and snapshot-consistency receipts;
- evidence contract coverage.

A pure rollout policy evaluates an admitted evidence set and produces exactly
one of the following proposal roles:

- =PromotionProposal=;
- =HoldProposal=;
- =ReversionProposal=.

A proposal is evidence, not authority. It cannot publish a generation, mutate
an active head, acquire a lease, or commit an effect.

* Live authority plane

Only a live context holding the required publication capability may authorize
a proposal.

Authorization produces a =HeadUpdateIntent= bound to:

- the proposal identity;
- the observed active-head version;
- the target publication scope;
- the selected immutable generation;
- the authorizing capability scope;
- the execution identity.

The head update uses compare-and-swap against the observed active-head version.
A conflicting version requires a fresh observation and a new pure proposal.
The old proposal must not be replayed against a newly observed head.

An unknown commit outcome enters reconciliation. It must not be treated as
success or failure until the external active head has been observed again.

Every successful promotion or reversion emits an immutable head-transition
receipt.

* State placement

The following ownership boundary is normative:

| Concern | Semantic location |
|-
| System meaning | Immutable generation |
| Rollout governance rules | Pure =RolloutPolicy= POO object |
| Cohort membership rule | Pure deterministic assignment object |
| Admitted health observations | Immutable =RolloutEvidenceSet= |
| Current selected generation | Versioned active head |
| Execution progress | Live rollout execution state |
| Lease and fencing data | Live authority context |
| Publication result | Immutable head-transition receipt |

Live rollout execution state may contain stage progress, leases, fencing
tokens, observed head versions, pending intents, and reconciliation status. It
must not become a hidden source of generation semantics.

* Promotion and reversion

Promotion selects an immutable generation for a wider or different publication
scope through a new authorized head transition.

Reversion selects a previously known or newly composed immutable generation
through another new authorized head transition.

Reversion is not:

- deletion of the failed generation;
- mutation of the failed generation;
- erasure of head-transition history;
- restoration of an earlier unversioned mutable snapshot.

Both promotion and reversion remain visible in the same append-only transition
history.

* Failure taxonomy

The implementation must distinguish at least:

- incomplete or stale rollout evidence;
- evidence contract failure;
- unstable or unauthorized cohort assignment;
- proposal policy rejection;
- missing publication capability;
- active-head compare-and-swap conflict;
- expired lease or stale fencing token;
- unknown publication outcome;
- reconciliation disagreement;
- transition receipt publication failure.

These failures must not collapse into a generic rollout failure.

* Required invariants

1. A generation is immutable before, during, and after rollout.
2. A rollout stage never mutates a percentage inside a generation.
3. Cohort assignment is deterministic for the same admitted identity inputs.
4. A pure proposal has no publication authority.
5. Every active-head change is capability-authorized and version-checked.
6. A compare-and-swap conflict requires reevaluation from fresh evidence.
7. Unknown outcomes enter reconciliation.
8. Promotion and reversion append new transition history.
9. Live progress state does not become hidden semantic configuration.
10. Public extension remains POO-native.

* Status

Proof-backed v1 refinement.

This document stabilizes the existing source-bound fingerprint history model.
It does not authorize a v2 schema, a second checkpoint model, or a competing
history path.

* Context

=SourceBoundSemanticFingerprintHistory= already closes the relationship among a
progress receipt, its subject evidence, and the typed checkpoint history used
to justify oscillation.  That closure still leaves two different questions:

1. Does the history identity change when checkpoint content or its predecessor
   changes?
2. Does a concrete digest provider attest the same canonical history root?

A nonempty =provenanceDigest= does not answer the first question.  Two
checkpoints can carry the same nonempty provenance string while their semantic
fingerprints differ.  Likewise, an arbitrary digest function can return one
constant value for two different canonical roots.

The v1 repair must therefore separate logical content binding from external
cryptographic validation.

* Decision

The canonical checkpoint payload is the existing complete
=SourceBoundSemanticFingerprintCheckpoint=.  No field projection and no
parallel schema are introduced.

The logical identity is an inductive value:

- =genesis(payload)= binds the first complete checkpoint;
- =successor(previous, payload)= binds both the preceding identity and the next
  complete checkpoint;
- the canonical history root binds the existing =historyId= and the final
  checkpoint identity;
- a provider receipt names that canonical root and carries the external digest;
- a provider-owned validity predicate is a separate proof obligation.

Lean proves constructor injectivity, chain closure, root binding, receipt/root
agreement, and nonempty receipt identities.  Lean does not claim that SHA-256,
BLAKE3, or any other external digest algorithm is collision resistant.  That
claim remains provider-owned evidence.

* Proof findings

The proof found and closed four v1 gaps:

1. =provenanceDigest != ""= is only presence evidence; it does not bind the
   checkpoint fields.
2. A digest string alone cannot determine a canonical root; a constant function
   is a valid logical counterexample.
3. A checkpoint identity that omits its predecessor cannot bind history order
   or prefix.
4. Digest validity cannot be silently assumed by the Lean model; it requires an
   explicit provider-owned predicate.

These are v1 completeness defects.  Their repair adds proof objects around the
existing checkpoint/history model and does not require a migration or
deprecation policy.

* Ownership boundaries

| Owner | Owns | Does not own |
|-
| Lean enterprise proof | Complete checkpoint projection, recursive logical identity, chain closure, canonical root, receipt/root agreement | Cryptographic implementation or provider runtime |
| Fingerprint digest provider | Digest algorithm, provider identity, provenance, algorithm-specific validity evidence | Progress semantics or history reconstruction |
| Progress/history owner | Subject evidence, typed checkpoint order, oscillation witness | Digest algorithm correctness |
| Runtime | Persisting and transporting the closed receipt | Weakening any failed proof obligation |

The external provider may be implemented by
=agent-semantic-content-identity= or another registered provider, but the core
proof names only the provider contract.  No provider implementation becomes a
POO Flow semantic owner.

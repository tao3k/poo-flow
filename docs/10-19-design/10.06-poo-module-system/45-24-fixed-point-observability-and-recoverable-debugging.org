#+title: Fixed-Point Observability and Recoverable Debugging
#+startup: overview

* Status

Accepted design.

This document defines the observability and live recovery model for POO
fixed-point evaluation.  It builds on:

- [[file:45-20-fixed-point-convergence-observation-budget.org][45-20]] for
  cycle, progress-budget, and host-resource conditions;
- [[file:45-22-continuation-resumption-and-budget-generation.org][45-22]] for
  live continuation recovery and cross-generation rebase;
- [[file:45-23-resumption-contribution-generation-closure.org][45-23]] for
  resumption-contribution closure and ambiguity.

The design uses Scheme continuable exceptions and first-class continuations
without placing host control objects inside canonical POO evidence.

* Decision

Fixed-point diagnostics are divided into three planes:

- the semantic plane creates immutable condition and transition evidence;
- the recovery control plane owns live continuations and authorized recovery
  actions;
- the observability plane derives inspectable diagnostic views and transports
  telemetry.

The semantic plane records a problem before any handler may recover from it.
The observability plane cannot change semantic identity.  The recovery control
plane cannot act merely because it can observe.

* Semantic plane

The semantic plane owns:

- root, module-instance, Capability, lineage, and generation identities;
- predecessor and successor observation identities;
- cycle and semantic-progress evidence;
- resumption candidate closures;
- ambiguity, fork, stale-generation, and cancellation evidence;
- immutable transition, resolution, rebase, and consumption receipts.

Condition evidence is created synchronously with semantic detection.  A handler
never receives only an exception string whose supporting state has already
been discarded.

Every diagnostic condition binds the smallest sufficient causal slice:

- the demanded Capability and module instance;
- the current predecessor state and generation;
- the relevant candidate, dependency, or cycle identities;
- the observation-budget state;
- provenance and phase;
- the permitted recovery-condition kind.

Stack addresses, object pointers, log sequence numbers, UI session identifiers,
and wall-clock timestamps are not semantic identity.

* First-visible anomaly boundary

When evaluation detects an anomaly, it performs these semantic steps in order:

1. construct immutable condition evidence;
2. derive the condition identity from canonical causal inputs;
3. publish the evidence to the local condition boundary;
4. expose the live continuable exception and recovery position;
5. permit independent observability projection and authorized recovery.

The exception handler cannot erase step 1 by immediately resuming.  Recovery
creates successor evidence; it does not rewrite the original condition.

* Observability plane

The observability plane is a pure projection over semantic evidence.  A
diagnostic view may include:

- root and module-instance lineage;
- the demanded Capability and import path;
- predecessor and attempted successor identities;
- dependency or cycle edges;
- observation-budget grant, delegation, and consumption state;
- resumption generation and closed candidate set;
- competing contribution or successor identities;
- condition and recovery provenance;
- source locations when available as non-authoritative metadata.

Views may be rendered as structured objects, traces, graphs, debugger panels,
or logs.  Presentation shape is not the semantic evidence format.

Diagnostic projection must be deterministic for the same evidence and view
Profile.  It must not demand new providers, resume continuations, allocate
budget, resolve ambiguity, or extend the fixed point.

* Semantic evidence versus telemetry delivery

Semantic evidence and telemetry-delivery receipts are different objects.

Semantic evidence cannot be replaced by a statement that a log message was
sent.  Telemetry delivery, sampling, coalescing, transport retry, and consumer
acknowledgement do not change fixed-point identity.

A telemetry sink may:

- receive a diagnostic projection;
- acknowledge or reject delivery;
- coalesce repeated presentation events that reference the same condition
  identity;
- apply presentation-level sampling.

It may not discard the underlying semantic condition object, fabricate
semantic success, or convert delivery order into causal order.

If an explicitly configured durable-evidence policy requires external
persistence before a boundary may advance, failure to persist produces its own
runtime or admission condition.  It does not silently become successful
semantic evaluation.

* Non-interference and backpressure

Ordinary telemetry transport does not block fixed-point evaluation.  A slow or
failed observer cannot hold a continuation merely by subscribing to events.

Transport queues, retry delays, dropped presentation events, and UI
disconnection are observability states.  They do not consume semantic
observation units and do not count as fixed-point progress.

Host memory or runnable-process pressure caused by observability infrastructure
remains subject to the host-resource guard from 45-20.  That guard reports a
host capacity condition; it does not reclassify telemetry activity as semantic
divergence.

Intentional debugger suspension is separate and requires an explicit
=debug-suspend= Capability and recovery-control authority.

* Recovery control plane

The recovery control plane owns ephemeral live control state:

- captured continuations;
- live condition-handler extent;
- opaque debugger session handles;
- authorized recovery operations;
- handoff state for external decisions.

These values are never canonical semantic identities and are not serialized
for replay.

The control plane may offer these semantic dispositions when authorized:

- resume against the unchanged generation;
- rebase into an explicitly authorized successor generation;
- select one candidate from a closed ambiguity set;
- decline recovery and propagate the condition;
- cancel through a separately authorized cancellation path;
- request explicit debugger suspension.

Every successful disposition produces immutable recovery evidence and
revalidates the condition, candidate set, predecessor, budget generation, and
authority scope.

* Observer and recovery authority

Observation authority and recovery authority are distinct Capabilities.

Observation authority may be attenuated by:

- root or submodule scope;
- Capability and condition kinds;
- lineage visibility;
- provenance-field visibility;
- diagnostic-view detail;
- generation range.

Recovery authority is additionally scoped by:

- the exact condition identity;
- the permitted disposition set;
- the candidate or successor identities it may select;
- the budget and resumption generations;
- expiry through causal successor state.

Possessing a diagnostic view, telemetry receipt, debugger handle, or historical
recovery receipt grants no recovery authority.

Submodules may export attenuated diagnostic views without exporting control
over their continuations.

* Semantic breakpoints

A breakpoint is a composable POO policy over semantic evidence, not a global
mutable table and not merely a source file and line number.

Breakpoint predicates may match:

- a Capability demand;
- module-instance or prototype lineage;
- condition kind;
- cycle or dependency identity;
- observation-budget threshold;
- resumption or fixed-point generation;
- contribution, candidate-set, or successor identity;
- provenance predicates.

Source location may refine presentation but is not required for semantic
matching.

A matched breakpoint produces an immutable breakpoint-hit condition.  It
becomes a live suspension only when an authorized =debug-suspend= policy is
present.  An observation-only breakpoint emits a diagnostic view and allows
evaluation to continue.

* Native POO composition

Fixed-point core, observability, breakpoint, durable-evidence, and
recovery-control behavior are native POO prototypes.  They are composed with
=gerbil-poo= =.mix= into one higher-order fixed-point object.

That object participates as one operand in the existing =compose profiles=
interface.  The outer Profile composition and inner prototype inheritance are
distinct semantic layers.

The concrete public shape is defined by
[[file:45-25-native-poo-fixed-point-operand-composition.org][45-25]].

This document introduces no fixed-point category selectors, =defobserver=,
=defdebugger=, handler registry, string-keyed configuration table, or raw
callback DSL.

* Continuations and external debugger handoff

A live debugger may receive an opaque handle to a suspended control boundary.
The handle refers to runtime state but is not itself condition evidence or
recovery authority.

External interaction follows:

1. pure semantic condition evidence;
2. pure diagnostic projection;
3. explicit runtime handoff intent;
4. external debugger response;
5. immutable response receipt;
6. authority and generation revalidation;
7. authorized recovery disposition.

Disconnect and timeout are not =decline=.  They preserve the suspended
condition until a separately authorized policy cancels, propagates, or
continues it.

* Replay

Replay reconstructs:

- the semantic anomaly and its causal evidence;
- diagnostic-view identities and delivery receipts when retained;
- breakpoint matches;
- debugger suspension and handoff receipts;
- external response evidence;
- selected recovery disposition;
- the resulting successor generation.

Replay does not recreate debugger sessions, reconnect telemetry consumers,
invoke handlers, or reconstruct live continuations.

Historical observation authority controls disclosure during replay.  Historical
recovery authority is evidence only and cannot authorize a live action.

* Runtime and ownership boundary

Gerbil supplies continuable exceptions, first-class continuations, condition
handling, and hygienic macro facilities.

Native =gerbil-poo= remains the sole POO evaluation mechanism.  POO Flow defines
semantic evidence, diagnostic projections, authority scopes, breakpoint
meaning, recovery dispositions, and receipts.

The runtime preserves live control state and transports explicit handoffs.  It
does not invent semantic recovery decisions.

The harness validates observability non-interference, diagnostic determinism,
authority attenuation, breakpoint matching, recovery receipts, and replay.  It
is not an observer, recovery provider, or debugger authority.

* Implementation checklist

- [ ] Create immutable condition evidence before exposing live recovery.
- [ ] Keep semantic, recovery control, and observability planes distinct.
- [ ] Derive deterministic diagnostic views from semantic evidence.
- [ ] Separate semantic receipts from telemetry-delivery receipts.
- [ ] Prevent sampling, coalescing, retries, and backpressure from changing
      fixed-point identity.
- [ ] Require explicit =debug-suspend= authority for intentional debugger
      suspension.
- [ ] Separate observation and recovery Capabilities.
- [ ] Attenuate diagnostic visibility at root and submodule boundaries.
- [ ] Bind every recovery action to condition, generation, candidate, budget,
      and authority evidence.
- [ ] Define semantic POO breakpoint predicates.
- [ ] Keep source location optional and non-authoritative.
- [ ] Preserve opaque live debugger handles outside canonical evidence.
- [ ] Treat disconnect and timeout separately from decline.
- [ ] Compose fixed-point observability and recovery through native POO
      prototypes and pass the resulting object as one Profile operand.
- [ ] Replay diagnostic and recovery receipts without live continuations,
      handlers, or debugger sessions.
- [ ] Test immediate evidence creation, fast resume, observer failure,
      backpressure, authority denial, breakpoint modes, handoff, disconnect,
      recovery, and replay.
- [ ] Verify that Mermaid edges explain the relevant state or transition
      without mechanical label prefixes.

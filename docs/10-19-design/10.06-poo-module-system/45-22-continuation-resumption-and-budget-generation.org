#+title: Continuation Resumption and Observation-Budget Generations
#+startup: overview

* Status

Accepted design.

This document connects Scheme continuations and continuable exceptions to the
fixed-point observation model defined by
[[file:45-20-fixed-point-convergence-observation-budget.org][45-20]] and the
submodule budget delegation model defined by
[[file:45-21-submodule-observation-budget-delegation.org][45-21]].
Resumption-contribution candidate closure is defined separately by
[[file:45-23-resumption-contribution-generation-closure.org][45-23]].

It preserves multi-shot continuation semantics.  It does not turn a
continuation into budget authority, a mutable transaction, or a second
fixed-point evaluator.

* Decision

A continuation represents a recoverable control position.  It does not grant
semantic observation units and it does not carry authority to extend,
reallocate, or rebase an observation budget.

A live suspension binds:

- the root and module-instance identities;
- the Capability demand identity;
- the budget Capability identity and generation;
- the predecessor observation-state identity;
- the captured control position;
- causal provenance for the suspension.

The captured host continuation is live control state.  It is not part of
canonical POO identity, is not serialized into receipts, and is never replayed.

* Observation commit boundary

Suspension and observation are distinct states.

If evaluation suspends before a canonical semantic successor exists, no
observation unit has been consumed.  If a canonical successor and its
consumption receipt already exist, later continuation invocation cannot consume
the same transition again.

The immutable predecessor-to-successor receipt is the commit evidence.  Stack
return, handler return, wall-clock completion, allocation, and continuation
invocation are not commit evidence.

* Multi-shot continuation semantics

Scheme may invoke the same continuation more than once.  POO Flow preserves
that language capability; it does not wrap the continuation in a hidden
one-shot mutable cell.

Each invocation first produces an immutable resumption contribution governed
by 45-23.  Invocations do not race to commit semantic successors.  All
contributions admitted to one resumption generation share the same suspension
identity, budget generation, and predecessor observation identity.

Repeated contributions with the same canonical identity coalesce before
evaluation.  Distinct contribution identities produce
=resumption-ambiguity= for a singleton demand and must be resolved over the
closed candidate set.

Only one selected canonical contribution may evaluate a singleton demand.  If
that contribution then claims different canonical successors for the same
predecessor, the result is an =observation-fork= condition.  Runtime scheduling
order, first completion, pointer identity, and handler order cannot select the
winner.

The resumption-ambiguity condition carries the closed contribution set.  The
fork condition carries the selected contribution identity, suspension
identity, predecessor identity, competing successor identities, budget
generation, and provenance.  Both are semantic continuable conditions.  Any
resolution must be an explicit higher-order POO policy; no default
first-writer rule is provided.

* Generation revalidation

Every invocation revalidates the budget generation captured by the suspension.
Resumption proceeds directly only when:

- the named budget generation remains current for the demand;
- the predecessor observation state remains current;
- the allocation still authorizes the observation;
- no conflicting canonical successor has been committed.

If reconciliation, redistribution, extension, or cancellation has created a
successor budget generation, direct invocation produces
=stale-continuation-generation=.  The old continuation cannot silently consume
the new allocation.

* Explicit rebase proof

Resuming a suspended demand under a successor budget generation requires an
explicit POO-native rebase proof.  The proof binds:

- the original suspension and predecessor identities;
- the closed budget generation;
- the successor budget Capability and generation;
- the reconciliation or extension receipt;
- the authority that permits the demand to continue;
- the successor demand identity.

Rebase derives a new authorized resumption state.  It does not mutate the old
suspension, rewrite its continuation, transfer unused allocation implicitly, or
make the historical budget current again.

Possession of the continuation, a consumption receipt, an unused remainder, or
a reconciliation receipt alone is insufficient rebase authority.

* Continuable conditions and recovery

The runtime may expose these conditions through Gerbil continuable exceptions:

- =resumption-ambiguity=: one closed generation contains multiple canonical
  inputs for a singleton demand;
- =observation-fork=: one predecessor has competing canonical successors;
- =stale-continuation-generation=: the captured generation is no longer
  current;
- =continuation-rebase-required=: a successor generation exists but no valid
  rebase proof authorizes resumption;
- =continuation-predecessor-stale=: another committed transition has already
  advanced the demanded semantic state.

A live handler may:

- resume against the unchanged generation;
- supply an authorized rebase proof;
- decline recovery and propagate the condition;
- cancel through a separately authorized cancellation path.

Handling a condition does not itself select a successor, allocate units, widen
authority, or commit progress.  The resumed computation must still produce
canonical POO transition evidence.

* Cancellation

Cancellation closes the live suspension through an immutable cancellation
receipt.  It neither consumes a semantic observation unit nor returns unused
allocation automatically.

Invoking the captured continuation after cancellation produces stale
suspension evidence.  Reopening the demand requires explicit successor
authority; cancellation is not undone by retaining a host continuation.

* Replay

Replay includes suspension, consumption, fork, rebase, and cancellation
receipts as historical evidence.  It does not serialize, reconstruct, invoke,
or approximate a live continuation.

Replay verifies:

- whether suspension occurred before or after semantic commit;
- whether repeated results coalesced under one canonical successor;
- whether competing successors produced fork evidence;
- whether every cross-generation resumption had a valid rebase proof;
- whether cancellation and successor generations were respected.

Missing live control state is expected during replay and is not repaired by
calling a handler, requesting authority, or restarting the demand.

* Runtime and ownership boundary

Gerbil supplies first-class continuations, =call/cc=, and continuable exception
mechanisms.  POO Flow defines the semantic identities, conditions, receipts,
and authority rules around their use.

Native =gerbil-poo= demand-lazy evaluation remains the sole POO evaluation
mechanism.  This design adds no continuation scheduler, promise layer,
provider registry, mutable commit flag, or local fixed-point implementation.

The harness may test resumption, fork detection, generation staleness, and
replay.  It does not provide budget authority or choose a semantic successor.

* Implementation checklist

- [ ] Represent live suspension metadata without placing host continuation
      identity in canonical POO identity.
- [ ] Treat immutable predecessor-to-successor evidence as the observation
      commit boundary.
- [ ] Preserve Scheme multi-shot continuation invocation.
- [ ] Coalesce identical canonical successors into one consumption receipt.
- [ ] Raise =observation-fork= for competing successors from one predecessor.
- [ ] Revalidate budget generation and predecessor state on every invocation.
- [ ] Reject direct use of a continuation after generation advancement.
- [ ] Define a POO-native rebase proof with explicit successor authority.
- [ ] Keep cancellation separate from observation consumption and allocation
      return.
- [ ] Expose live recovery through continuable Gerbil conditions.
- [ ] Replay receipts without serializing or invoking continuations.
- [ ] Test identical multi-shot results, competing successors, stale
      generations, authorized rebase, unauthorized rebase, cancellation, and
      replay.
- [ ] Verify that Mermaid edges explain the relevant state or transition
      without mechanical label prefixes.

* Decision

Governance is a POO Flow core module.  It is not infrastructure privately owned
by Lambda Episteme and it is not synonymous with the Cedar evaluator.

POO Flow owns the engine-neutral Governance Profile, Source, pre-threat,
Threat Model, Assessment and Contribution contracts under
=src/modules/governance/=.  POO Flow's engine-neutral authorization protocol
lives under =src/modules/authorization/=, while Cedar is its explicitly selected
Provider under =src/modules/authorization/providers/cedar/=.  Lambda Episteme consumes those
contracts to publish vertical-industry Profiles, Scenarios, Cases, policies and
Sources.  Cedar is one explicitly selected authorization Provider.  The final
application binds an admitted domain composition to that Provider.

No reverse dependency from POO Flow to Lambda Episteme is permitted.

* Ownership

| Owner | Responsibility | Must not own |
|-------+----------------+--------------|
| POO Flow Governance core | Profile, Source, pre-threat, Threat Model and Assessment contracts; semantic admission | Industry vocabulary; implicit authorization |
| Lambda Episteme | Industry/standard Profiles, Scenarios, Cases, policies, Sources and evidence | Core Governance prototype; Cedar execution |
| POO Flow Authorization core | Provider and Capability types plus cross-object contracts | Selecting an ambient Provider; industry vocabulary |
| Cedar Provider | Exact Case/Profile/assessment/proof identity projection | Industry-policy interpretation; effect execution |
| Cedar Runtime Host | One bounded Rust+Lean dual-engine evaluation and signed runtime evidence | Domain composition or Profile mutation |
| Application | Profile/Case selection, Provider selection and effect authorization | Reinterpreting failed admission as success |

* Dependency and authority flow

The semantic arrow and the runtime-authority arrow are deliberately separate.
A valid Governance Profile is not an authorization decision.  A Cedar snapshot
with =runtime-executed? #f= is not a permit.  Only the independently qualified
Runtime Host can produce the dual-engine execution evidence consumed by the
authority boundary.

* Core API and MOP model

The implemented core provides:

- =PooFlowGovernanceProfile.= as an abstract POO prototype;
- six =define-type= descriptors for Profile, Source, pre-threat condition,
  Threat, Threat Model and Assessment values;
- =poo-flow-governance-source= for explicit Source ownership and
  =poo-flow-governance-precondition= for evidence-bound observations;
- =poo-flow-governance-threat= and =poo-flow-governance-threat-model= for
  typed threat lifecycle and severity declarations;
- =.assess-threats= and =.assess-governance= as open =.defgeneric= slots;
- =poo-flow-governance-evaluate= for single-dispatch Profile assessment;
- =poo-flow-governance-contribution= for inert semantic contributions;
- =PooFlowAuthorizationProvider= and =PooFlowAuthorizationCapability= as the
  engine-neutral authorization contract;
- optional =contracts.ss= roles for Provider/Capability and
  Governance/Cedar relational admission;
- =poo-flow-cedar-governance-snapshot= as the aggregate Case-level Cedar
  Provider projection.

The abstract Profile has no default contributor identity, revision or owner.
Every concrete contributor must state those values.  This prevents a core
prototype from silently assigning Lambda Episteme ownership to unrelated
downstream Profiles.

An observed pre-threat condition must carry an evidence identity.  A mitigated
Threat must name at least one mitigation, and an accepted residual Threat must
name its acceptance authority.  Exposed or realized high/critical Threats make
the typed Assessment ineligible for Provider handoff.

The Cedar Provider rejects unresolved Threats, incomplete Profile/Assessment
joins, assessment-digest drift, and proof bindings whose composition or Profile
identities differ from the selected Case.  The exact Case graph and vertical
authorization declaration are bound through =subject-snapshot-digest=.  It
performs no policy evaluation and does not provide an alternate in-process
engine.

The first vertical slice is Healthcare medication administration.  Lambda owns
the =administerMedication= elevated Capability, standard Cedar policy Sources,
Healthcare schema, Case graph and declarative Provider/Patient/Encounter/Order
subject.  The core adapter projects them without interpreting clinical meaning.
The independent Runtime Host evaluates the exact same protobuf through
=cedar-rust= and the AOT =Cedar.Spec= Lean engine.  Allow, default deny and
revoked-order forbid are qualified with per-request strict-lockstep witnesses.

* Scenario relations and Temporal Causality boundary

Lambda's accepted POO composition is also the authority for enterprise
relation reasoning.  It is projected into the existing POO Flow Graph with
typed Scenario-to-Case, Case-to-composition, composition-to-Profile,
Profile-import, Source, Threat and Capability edges.  The projection does not
introduce a second ontology store or require Cases to maintain reverse indexes.

Structural Impact Analysis is computed from the reverse dependency cone of
that graph.  It is one operation of the POO Flow =Temporal Causality= core,
not the core module's name.  Therefore
a changed Profile, Source, Threat or Capability identifies every affected Case
from current accepted declarations rather than a handwritten =IMPACTS= list.
GQL Sources may express the corresponding relation and Impact questions, but
GQL parser admission proves syntax and lossless source only.  Until an admitted
GQL executor is integrated, native Scheme graph construction and Impact
receipts remain the executable boundary.  Neither path grants Cedar authority.
Past, present, future and counterfactual causal trajectories are specified
separately in RFC 161; a structural receipt explicitly makes no temporal claim.

* Enterprise security assurance

The core model is necessary but not by itself sufficient for the intended
enterprise user.  The Lean module
=PooFlowProof.Enterprise.GovernanceThreatAssuranceClosure= composes the core
Governance admission and Provider-handoff proof with:

- a closed typed security-relation graph;
- explicit threat-intelligence and evidence-snapshot identities;
- proposer/approver/executor separation of duties;
- the invariant that Governance evidence never carries action authority.

An active critical Threat is a constructive counterexample to enterprise
assurance: it makes =ProviderHandoffEligible= impossible.  This connects the
existing Enterprise security proof family to Governance without re-proving the
Cedar evaluator.  Cedar request, policy, evaluation and response semantics
remain owned by the upstream Cedar specification and its Lean proof.

* TLA+ transition model and parser authority

=packages/proof/tla/GovernanceCore.tla= models the temporal boundary from
pre-threat observation through assessment, Governance admission, enterprise
evidence closure and Provider handoff.  Its invariants require evidence for an
observed precondition, closed enterprise assurance before handoff, explicit
authority evidence for accepted residual risk, and absence of Governance
action authority.

Syntax qualification uses =gerbil-parser='s native
=tla-plus.native-core.v1= parser.  POO Flow does not contain a second TLA+
parser and does not add =gerbil-parser= as a production dependency.  The
=just check-governance-tla= lane first establishes a local =gxpkg link= from
the parser's isolated package environment to this POO Flow checkout, builds
the parser through its own PackageSpec, then requires a valid, successful,
byte-exact ParseArtifact.  This direction is required because =gerbil-parser=
itself consumes POO Flow; reversing the package edge would create a cycle.

The native v1 parser deliberately excludes multiline layout, PlusCal and full
proof syntax.  Therefore this receipt proves admitted TLA+ syntax and
losslessness, not temporal semantics.  TLC remains the owner of state-space
model checking.  The TLA+ language pack owns one public
=qualify-tla-plus-model= API that composes, without conflating, both owners:
it obtains the native parser acceptance and then runs the official Nixpkgs
=tlaplus= distribution over the same source.  POO Flow's
=just check-governance-model= is only a model-selection adapter over that API;
it contains no TLC-output parser or receipt implementation.  The versioned
Gerbil receipt binds the specification and configuration SHA-256 identities,
resolved tool identity and SHA-256, worker policy, exit status,
generated/distinct/remaining state
counts and complete graph depth.  A zero process status alone is insufficient:
admission also requires TLC's explicit completion result and an empty queue.
The bounded Governance model intentionally uses one worker: its 42-state graph
does not benefit from distributed search, while deterministic small-model
receipts do benefit from avoiding parallel exploration variance.

* Lambda Episteme migration

The former top-level =lambda-episteme/governance/= directory combined a base
Profile, Source constructor and Contribution wrapper outside the ordinary
module contract.  It is removed.  Lambda modules now import the POO Flow core
roles directly and state their own owner, revision and semantic facet.

Lambda Episteme retains domain governance content.  For example, SDLC may own
lifecycle and standards meaning, Ontology may own semantic relations, and a
Healthcare Case may select privacy or evidence Profiles.  None of those values
redefines the core Governance contract or invokes Cedar during import.

* Extension rule

Single-axis Profile behavior remains POO slot dispatch.  A future combination
of independently extensible Governance Profile/Case and authorization Provider
axes must use the existing POO Flow CLOS generic, class-specializer and method
bundle mechanism.  It must be justified by at least two real Providers or two
real domain specializers; a speculative dispatch framework is not admitted.

Until that scenario exists, the Cedar bridge is an explicit pure function.  It
is smaller, testable and does not manufacture a second provider framework.

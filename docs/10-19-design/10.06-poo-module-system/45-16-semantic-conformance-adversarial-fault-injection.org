#+title: Semantic Conformance And Adversarial Fault Injection

* Normative responsibility

This module owns the evidence contract for moving POO Flow semantics from
=semantic-required= through =behavior-proven= and =flow-qualified=.

It defines:

- POO-native conformance scenarios;
- semantic oracles owned by =poo-flow-core=;
- adversarial fault windows;
- causal and schedule-independent assertions;
- qualification receipts;
- an Org checklist that reports actual conformance evidence.

It is not an implementation plan, migration schedule, compatibility matrix, or
downstream distribution-test mandate.

* Ownership boundary

POO Flow owns:

- normative scenario semantics;
- expected POO values, conditions, transitions, and receipts;
- the conformance oracle;
- qualification-state transitions.

=gerbil-poo= remains the sole Scheme POO implementation and owns the generic POO
and continuation mechanisms exercised by the scenarios.

GSLPH is a development dependency.  It may provide harness policy, fault
injection orchestration, building/testing workflow, and reporting.  It does not
become:

- a production runtime dependency;
- a provider;
- the semantic oracle;
- receipt authority;
- the owner of POO Flow policy.

Gerbil-Bazel is a build system.  Stable declared test targets may use it without
creating a frequently changing semantic adapter contract.

=gerbil.pkg= remains Gerbil package management.  It is not a test-evidence
projection or provider-resolution service.

* Project and downstream boundary

The parent project owns conformance of =poo-flow-core=.

It does not own =wendao-episteme= distribution or integration testing merely
because that package is composed through POO Flow.  Downstream packages own
their own Profile, Mix, provider, packaging, and distribution qualification.

The parent may provide reusable semantic fixtures and receipt verifiers.
Downstream projects consume them under their own test authority.

* POO-native scenario model

A conformance scenario is a POO object assembled from ordinary POO prototypes
and functional Scheme helpers.  It may contribute:

- composition and demanded-coordinate setup;
- provider and policy test capabilities;
- expected value, condition, transition, and receipt evidence;
- fault-window capabilities;
- deterministic generator and shrinker functions;
- qualification assertions.

It MUST NOT use a raw alist scenario DSL, record command language, string-keyed
patch format, or arbitrary =(lambda (self super) ...)= as the ordinary author
interface.

Exact scenario prototypes, helpers, and macros remain API-evidence-gated.

  F -->|"exercise poo-flow-core semantics"| R["State: runtime receipts and conditions"]
  R -->|"POO Flow-owned semantic oracle"| O["State: conformance result"]

  B["State: Gerbil-Bazel build system"] -.->|"builds stable declared targets"| F
  P["State: gerbil.pkg"] -.->|"provides package dependency management only"| F
  O -->|"exact behavior evidence"| E["State: API qualification transition"]
  G -.->|"never becomes provider, receipt authority, or semantic oracle"| O
#+end_src

* Four conformance layers

** Pure POO semantics

Scenarios verify:

- Profile, Mix, and boundary-local composition;
- same-root refinement and =super=;
- unrelated-root non-precedence;
- lazy demand and memoization;
- productive recursion versus non-productive cycles;
- lineage and progress evidence;
- pure macro expansion, normalization, and graph inspection;
- absence of effect execution in every pure phase.

** Runtime boundary semantics

Scenarios verify:

- POO effect-intent construction;
- demand suspension and one-demand/one-attempt coalescing;
- boundary-scoped provider search closure;
- selected, missing, and ambiguous provider outcomes;
- authorized handoff;
- committed, failed, cancelled, indeterminate, and reconciling effect evidence;
- validated receipt reinjection;
- duplicate and stale receipt rejection;
- continuation re-entry without duplicate external invocation.

** Governance semantics

Scenarios verify:

- runtime-local lease acquisition and release proof;
- =dynamic-wind= authority attachment/detachment without repeated acquire or
  release;
- expired and indeterminate resource recovery;
- containment-scoped cancellation propagation;
- ordinary and cleanup continuation generations;
- coalesced demand-authority withdrawal;
- admission, hierarchical budgets, backpressure, and cleanup reserve;
- clean versus indeterminate boundary termination.

** Evidence semantics

Scenarios verify:

- POO-native receipt objects;
- canonical causal identity and external outcome identity separation;
- typed predecessor edges;
- immutable correction and contradiction;
- redaction and verifier coverage;
- deterministic receipt verification;
- pure re-realization and effect-receipt replay;
- first-divergence and proven-barrier evidence;
- absence of live provider execution during replay.

* Adversarial fault windows

Every externally meaningful transition is exercised at the semantic windows
before, during, and after terminal proof:

#+begin_src mermaid
flowchart TD
  A["Before provider invocation"] -->|"inject cancellation or capacity loss"| C1["Expected: no external attempt"]
  B["After invocation, before terminal receipt"] -->|"lose worker or response"| C2["Expected: indeterminate barrier"]
  C["After commit proof, before reinjection"] -->|"resume continuation repeatedly"| C3["Expected: one realized value and no duplicate effect"]
  D["During resource release"] -->|"lose release receipt"| C4["Expected: indeterminate lease"]
  E["During parent cancellation"] -->|"child or sibling stalls"| C5["Expected: containment-scoped evidence"]
  F["During replay"] -->|"remove or contradict predecessor receipt"| C6["Expected: first divergence or missing evidence"]
#+end_src

Required fault families include:

- cancellation before provider invocation;
- process loss after external invocation;
- provider success without verifier evidence;
- duplicate terminal receipts;
- contradictory terminal receipts;
- stale continuation generation;
- repeated continuation re-entry;
- lost resource-release response;
- cancellation of one coalesced waiter;
- zero ordinary capacity;
- exhausted cleanup reserve;
- missing and ambiguous providers;
- productive and non-productive recursive provider imports;
- missing, redacted, or contradictory replay predecessors.

Fault injection controls harness behavior.  It does not bypass the real POO Flow
condition, receipt, or verifier path.

* Transition outcome matrix

Each owned transition is tested against at least:

| Outcome class | Required assertion |
|---+---|
| success | qualified terminal receipt and expected value/state |
| proved failure | failure receipt distinct from indeterminacy |
| cancellation | request, provider proof, resource proof, and boundary proof remain distinct |
| indeterminate | no automatic retry and a preserved reconciliation barrier |
| duplicate | idempotent observation or structured duplicate condition; no repeated effect |
| contradiction | both immutable receipts preserved and verifier condition emitted |

Not every transition supports every outcome.  An inapplicable matrix cell is
recorded explicitly by the owning semantic contract rather than silently
omitted.

* Continuation adversaries

Continuation scenarios exercise:

- capture before, inside, and after effect/resource boundaries;
- multiple invocation of the same captured continuation;
- exit and re-entry across =dynamic-wind=;
- re-entry after lease release;
- re-entry after boundary generation invalidation;
- cleanup-generation confinement;
- mismatch between receipt and suspended continuation.

The oracle asserts that continuation behavior never duplicates a committed
effect, resurrects a released lease, restores invalidated ordinary authority,
or bypasses receipt validation.

* Schedule-independent properties

Independent sibling demands may be permuted by the harness:

#+begin_src mermaid
flowchart LR
  S["State: one POO scenario"] -->|"schedule permutation A"| A["State: causal result A"]
  S -->|"schedule permutation B"| B["State: causal result B"]
  A -->|"compare POO value + receipt partial order"| C["State: semantic equivalence result"]
  B -->|"compare POO value + receipt partial order"| C
  A -.->|"wall-clock ordering is diagnostic only"| B
  C -->|"mismatch identifies first causal divergence"| D["State: conformance failure receipt"]
#+end_src

The oracle compares:

- normalized POO values;
- boundary and lineage identities;
- demanded-coordinate evidence;
- typed causal predecessor relationships;
- policy and verifier outcomes.

It does not require equal timestamps, thread ids, process ids, queue timing, or
independent sibling interleaving.

* Property generation and shrinking

Property-based scenarios may generate:

- recursive structural-boundary trees;
- local and imported capability spaces;
- same-root refinements and unrelated roots;
- demand graphs and productive recursion;
- provider outcomes and fault windows;
- continuation capture/re-entry sequences;
- budget and cancellation trees;
- receipt predecessor DAGs.

Generation and shrinking are pure functional values.  A conformance failure
receipt records the generator identity, seed, shrink path, final scenario
identity, and first semantic divergence.

Shrinking MUST preserve the failing semantic invariant.  A smaller scenario
that no longer reproduces the receipt/condition mismatch is not evidence.

* Semantic oracle

The oracle belongs to POO Flow and evaluates semantic receipts, not harness exit
status alone.

A passing command is insufficient unless its qualification receipt identifies:

- exact test target and scenario identity;
- source and resolved dependency evidence;
- runtime/provider fixture identity;
- generator seed or explicit fault schedule;
- assertions executed and counted;
- passed, failed, skipped, and inapplicable outcomes;
- first failure receipt when present.

A timeout, worker loss, or missing receipt is not a passing result.

* GSLPH harness contract

GSLPH may:

- build and invoke declared conformance targets;
- provide development harness policies;
- inject declared faults;
- collect stdout/stderr and semantic receipts;
- aggregate deterministic reports.

GSLPH MUST NOT:

- fabricate a POO Flow receipt;
- translate a missing receipt into success;
- become a runtime provider;
- supply production policy implicitly;
- run downstream distribution tests on behalf of the parent;
- redefine =gerbil.pkg= or Gerbil-Bazel semantics.

Harness success and semantic conformance are separate evidence fields.

* Qualification transitions

A public or internal API element advances only with matching evidence:

#+begin_src mermaid
stateDiagram-v2
  [*] --> SemanticRequired: normative semantic obligation exists
  SemanticRequired --> SymbolLocated: exact gerbil-poo or POO Flow identifier located
  SymbolLocated --> BehaviorProven: focused conformance scenarios pass with semantic receipts
  BehaviorProven --> FlowQualified: integration inside poo-flow-core passes owned boundary scenarios
  FlowQualified --> BehaviorProven: later contradiction or regression invalidates flow qualification
  BehaviorProven --> SymbolLocated: later evidence invalidates behavior proof
#+end_src

An RFC approval establishes =semantic-required=.  It does not establish
=symbol-located=, =behavior-proven=, or =flow-qualified=.

* Normative conformance evidence checklist

This checklist reports evidence state; it is not an implementation plan.  An
item is checked only when a qualification receipt names the exact command,
target, dependency revision, scenario/fault identity, assertion counts, and
result.

** Pure POO

- [ ] Composition and same-root refinement behavior-proven.
- [ ] Unrelated-root non-precedence behavior-proven.
- [ ] Lazy memoization and productive recursion behavior-proven.
- [ ] Non-productive cycle and first-demand evidence behavior-proven.
- [ ] Macro expansion, normalization, and graph inspection proven effect-free.

** Runtime boundary

- [ ] Intent suspension and one-demand/one-attempt behavior-proven.
- [ ] Provider selected/missing/ambiguous outcomes behavior-proven.
- [ ] Effect terminal and indeterminate transitions behavior-proven.
- [ ] Receipt reinjection and duplicate/stale rejection behavior-proven.
- [ ] Repeated continuation re-entry proven not to duplicate effects.

** Governance

- [ ] =dynamic-wind= attachment proven not to acquire/release resources.
- [ ] Lease release and indeterminate reconciliation behavior-proven.
- [ ] Containment cancellation and import isolation behavior-proven.
- [ ] Coalesced waiter cancellation behavior-proven.
- [ ] Backpressure and bounded cleanup capacity behavior-proven.

** Evidence and replay

- [ ] Receipt identity separation and canonical projection behavior-proven.
- [ ] Correction, contradiction, and redaction behavior-proven.
- [ ] Receipt-DAG verification behavior-proven.
- [ ] Pure re-realization behavior-proven.
- [ ] Effect-receipt replay proven not to invoke providers.
- [ ] Schedule permutations proven causally equivalent.

** Ownership boundaries

- [ ] GSLPH proven to remain a dev-harness consumer only.
- [ ] Gerbil-Bazel targets proven to remain build-system targets only.
- [ ] =gerbil.pkg= proven to remain package management only.
- [ ] Parent suite proven scoped to =poo-flow-core=.
- [ ] Downstream distribution/integration ownership remains downstream.

* Receipt and observability contract

Every conformance execution emits:

- harness execution evidence;
- semantic-oracle receipt;
- scenario and fault identity;
- assertion counts;
- qualification-state result;
- causal predecessor links to source, dependency, and policy evidence.

The receipt follows
[[file:45-15-receipt-object-canonical-evidence-projection.org][Receipt Object And Canonical Evidence Projection]].  Replay scenarios follow
[[file:45-14-deterministic-realization-replay.org][Deterministic Realization Replay]].

Observability may report progress and bounded failure diagnostics.  It cannot
mark checklist items, advance API qualification, or replace a missing semantic
receipt.

* API evidence gate

Exact scenario prototypes, generators, fault capabilities, oracle APIs,
qualification receipt schemas, GSLPH harness commands, and Gerbil-Bazel targets
remain =semantic-required= until they are symbol-located and behavior-proven.

The current checklist intentionally remains unchecked until implementation
evidence exists.

* Explicit exclusions

This RFC does not authorize:

- checking conformance items from RFC approval alone;
- harness exit status as the semantic oracle;
- GSLPH as production provider, runtime, or receipt authority;
- parent-owned =wendao-episteme= distribution/integration tests;
- a raw alist/record scenario DSL;
- a shadow POO evaluator or scheduler;
- wall-clock ordering as semantic equivalence;
- skipped, timed-out, or missing-receipt scenarios counted as passing;
- a compatibility, migration, deprecation, or implementation plan.

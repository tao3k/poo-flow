#+title: Incremental Fixed-Point Reevaluation and Cache Correctness
#+startup: overview

* Status

This RFC records the accepted incremental reevaluation and cache-correctness
semantics for POO Flow.

It extends graph-wide compatibility closure and SCC evidence. Cache reuse is an
optimization over canonical POO semantics; it is not an alternative semantic
path.

* Typst formalization: identity-driven incremental reevaluation

The following equations are the semantic boundary of cache reuse.  A cache hit
is not itself evidence: semantic reuse is admitted only when the complete
identity and the freshness contract both match the current graph cut.

#+begin_src typst
#let cache-id(input, dependency, cut, policy) = (
  input,
  dependency,
  cut,
  policy,
)

#let admits-reuse(entry, current) = (
  entry.identity == cache-id(
    current.input,
    current.dependency,
    current.cut,
    current.policy,
  )
  and entry.fresh
  and entry.graph-closure-proof != none
)

$ admits-reuse(e, c)
  ==> e.identity = cache-id(c.input, c.dependency, c.cut, c.policy)
  and fresh(e)
  and graph-closure-proof(e) $
#+end_src

A changed identity invalidates only the reachable demand frontier, but SCC
membership changes the scheduling granularity: once one member is affected,
the entire SCC is reevaluated and committed as one unit.

#+begin_src typst
#let frontier(changed, reaches) = {
  n | exists(i in changed, reaches(i, n))
}

#let affected-sccs(changed, reaches, sccs) = {
  component |
  component in sccs
  and exists(n in component.nodes, n in frontier(changed, reaches))
}

$ n in frontier(Delta I, reaches)
  ==> exists(C in affected-sccs(Delta I, reaches, SCC(G)), n in C.nodes) $

$ C in affected-sccs(Delta I, reaches, SCC(G))
  ==> scheduled(C) = C.nodes and not partial-commit(C) $

$ suspended(kappa, cut)
  ==> continuation(kappa, cut) and not publish(incomplete(kappa)) $
#+end_src

* Central decision

Incremental evaluation is identity-driven reuse.

An unchanged immutable input identity may reuse a previously admitted result.
A new input identity reevaluates only the reachable dependent demand frontier.

The implementation must not mutate an old semantic result in place or use a
single undifferentiated global memo table.

* POO and evaluator ownership

Pure object and prototype semantics remain owned by the canonical
=gerbil-poo= dependency.

POO Flow records demand dependencies, SCC evaluation, cache identities,
budgets, suspensions, continuations, invalidation, and observability over those
objects.

Cache implementation must not introduce a second POO object model, hidden
provider registry, runtime token dispatcher, or alternative compatibility
evaluator.

* Cache classes

At least four cache classes remain separate:

1. semantic value cache;
2. compatibility and evidence cache;
3. execution-work cache;
4. materialization cache.

Their identities, lifetimes, authority boundaries, and admissible reuse are not
interchangeable.

* Semantic value cache

The semantic value cache stores pure POO demand results such as:

- resolved slots;
- prototype projections;
- pure transformations;
- pure strategy results.

Its cache identity contains:

#+begin_example
composition-root revision
+ demanded object and slot identities
+ composition-strategy identity
+ pure input identities
#+end_example

Live capabilities, execution attempts, threads, clocks, leases, and budgets do
not enter pure semantic value identity.

An implementation may associate operational metadata with a cache entry, but
that metadata must not change the identity or meaning of the cached value.

* Compatibility and evidence cache

The evidence cache stores:

- =CompatibilityProof=;
- =CompatibilityViolation=;
- =CompatibilitySuspension=;
- other immutable closure evidence.

Its identity includes:

- graph and SCC identities;
- dependency evidence manifest identity;
- resource observation-set identity;
- compatibility policy identity;
- freshness contract identity;
- semantic closure input identity.

A cached proof is not permanently admitted. Every live use reevaluates current
freshness and admission requirements against an authoritative time or resource
observation.

A matching content digest must not bypass freshness.

* Execution-work cache

The execution-work cache stores live evaluator state such as:

- running evaluation attempts;
- demand continuations;
- scheduling tasks;
- budget consumption;
- single-flight coordination;
- waiter cancellation state.

Execution-work state is not semantic evidence and must not authorize
activation, migration, contract, reversion, or effect commit.

Loss of execution-work state after process restart may require recomputation.
It must not change the canonical pure result.

* Materialization cache

The materialization cache stores compiled artifacts and local runtime
representations.

Its identity includes semantic materialization identity and admitted platform,
toolchain, and target identities.

Materialization reuse remains subject to:

- resource capability;
- content verification;
- retention policy;
- reclamation policy;
- local runtime compatibility.

A materialization cache hit does not imply semantic admission or disclosure
authority.

* Dynamic demand dependencies

Every canonical evaluation records the dependency manifest actually demanded
by that evaluation.

This is required because higher-order POO composition and slot resolution may
change which dependency edges are demanded.

Reuse verifies:

- definition revision identity;
- strategy identity;
- every dependency input identity;
- dependency-selection evidence;
- dependency manifest identity.

If any item changes, the old entry cannot prove that all currently demanded
dependencies were evaluated.

* Incremental invalidation

#+begin_src mermaid
flowchart LR
    I["Changed Definition or Observation Identity"] -->|"locates exact reverse dependencies"| D["Affected Demand Frontier"]
    D -->|"changes an internal or incoming edge"| S["Affected SCC Reevaluation"]
    S -->|"produces the same output evidence identity"| K["Stop Downstream Propagation"]
    S -->|"produces a new output evidence identity"| N["Invalidate Downstream Dependents"]
    C["Unchanged Dependency Manifest"] -->|"permits proof-aware reuse"| H["Cache Reuse Receipt"]
    F["Freshness scope or disclosure check fails"] -->|"rejects an otherwise matching entry"| R["Fresh Evaluation or Admission"]
    U["New Missing Evidence Arrives"] -->|"wakes only matching suspended demands"| S
#+end_src

An immutable identity change starts at the exact reverse-dependency frontier.

For an SCC:

- any changed internal edge invalidates the SCC result;
- any changed incoming evidence identity invalidates the SCC result;
- the SCC reevaluates as one joint obligation;
- downstream invalidation propagates only if the SCC output evidence identity
  changes.

If reevaluation produces the same output evidence identity, propagation stops
at that boundary.

* Suspension cache

A =CompatibilitySuspension= may be reused as a bounded negative cache entry.

It records:

- missing evidence identities or roles;
- dependency wake set;
- budget exhaustion location;
- causal demand path;
- retry or expiry boundary;
- freshness contract;
- suspension identity.

Arrival of matching evidence wakes only the affected suspended demands.

A suspension cache hit remains a suspension. It must never be promoted to a
proof because no work was retried.

* Violation cache

A violation may be reused while the complete semantic cut remains unchanged.

A change to any of the following creates a new judgment boundary:

- composition root;
- definition or prototype revision;
- slot priority or resolution evidence;
- compatibility policy;
- resource observation set;
- contract identity;
- graph or SCC identity.

Violation caching must not suppress evaluation of a newly composed proposal.

* Capability and disclosure isolation

Computation reuse, evidence disclosure, and live action authority are separate
decisions.

A semantic cache hit does not grant the requester permission to observe the
result or its supporting evidence.

Reuse performs a disclosure projection for the requesting scope. Restricted
values are either:

- projected to an admitted public or limited view;
- isolated by confidentiality domain;
- withheld with explicit evidence.

Capability tokens do not enter semantic cache keys. A result computed for a
high-authority caller must not leak to a lower-authority caller through cache
reuse.

Live action authority is always reacquired after semantic or evidence reuse.

* Concurrent single-flight evaluation

Equivalent semantic demands may share one pure evaluation attempt.

Every waiter retains its own:

- disclosure scope;
- completion budget;
- cancellation scope;
- admission context;
- receipt destination.

One waiter cancellation must not cancel work still demanded by other admitted
waiters.

Shared execution ends when no live demand owner remains or when the evaluator
reaches a terminal evidence result.

Child budget and cancellation scopes must not amplify the parent resources.

* Evaluator continuation resumption

A suspended evaluator continuation is bound to:

- semantic cut identity;
- demand identity;
- dependency manifest identity;
- evaluation attempt identity;
- consumed and remaining budget evidence;
- resume capability scope.

Resumption may continue the same attempt only if the semantic cut and
dependency assumptions remain valid.

If the cut changed, the runtime creates a new evaluation attempt. The old
suspension remains diagnostic and causal evidence; it is not resumed against
new semantics.

Continuable exceptions may acquire evidence or budget under authority. They
must not mutate prototype, priority, policy, or revision identities in place.

* Cache reuse receipts

Every proof-relevant cache reuse emits a lightweight =CacheReuseReceipt=
containing:

- reused value or evidence identity;
- cache class;
- dependency manifest identity;
- dependency validation result;
- freshness admission result;
- disclosure projection identity;
- requesting scope;
- invalidation propagation decision;
- source evaluation receipt identity.

Observability must distinguish cache lookup, semantic reuse, freshness
admission, disclosure admission, and live authority acquisition.

* Failure taxonomy

The implementation must distinguish at least:

- semantic cache-key mismatch;
- dependency manifest mismatch;
- dynamic dependency selection changed;
- SCC incoming evidence changed;
- freshness admission failed;
- disclosure denied;
- confidentiality-domain mismatch;
- suspension wake evidence incomplete;
- stale violation cache entry;
- single-flight waiter scope mismatch;
- evaluation budget exhausted;
- continuation semantic cut changed;
- materialization verification failed;
- cache reuse receipt incomplete.

* Required invariants

1. Cache reuse preserves canonical pure POO semantics.
2. Cache classes remain separate.
3. Live execution metadata does not enter semantic value identity.
4. Dynamic dependency manifests are validated before reuse.
5. An affected SCC reevaluates as one joint obligation.
6. Downstream propagation stops only on unchanged output evidence identity.
7. Freshness is readmitted for every proof use.
8. Suspension never becomes proof through cache reuse.
9. Capability tokens do not become semantic cache keys.
10. Computation reuse does not grant disclosure or live action authority.
11. Waiter cancellation remains scoped.
12. Evaluator continuation resumption preserves its semantic cut.
13. Proof-relevant reuse emits a cache reuse receipt.
14. Native POO semantics remain owned by =gerbil-poo=.

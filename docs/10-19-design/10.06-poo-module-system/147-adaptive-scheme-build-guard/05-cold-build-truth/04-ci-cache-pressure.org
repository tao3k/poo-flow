* CI cache generations and pressure admission

GitHub's cache store is immutable, while =setup-bazel= derives its disk-cache
key from BUILD-file content.  A Scheme source change can therefore create a new
Bazel action result without changing the surrounding GitHub cache key.  An
exact restore then suppresses the post-job save and strands that new action
result on the ephemeral runner.

CI now materializes the pull-request merge commit as an ignored synthetic
=.ci/bazel-cache-generation/BUILD.bazel= before =setup-bazel=.  Each commit gets
a new exact generation, but the stable runner/toolchain prefix restores the
latest preceding disk cache.  Bazel reuses every valid CAS/action entry, runs
only actual misses, and the post step publishes the merged cache under the new
generation.  Reruns of the same commit remain exact hits.  This is a GitHub
cache-store adapter only; it does not enter =build.ss= or Building Framework.

CPU and memory pressure have different safety semantics.  The Scheme guard
records an instantaneous runnable-process saturation observation as an
=admission-advisories= value, but it does not treat that noisy system-wide
sample as a hard failure or override the detected/configured worker capability.
Exact physical memory is not a semantic compiled-tree input.  The POO Flow
guard probes it only when an action executes.  The pinned external
=gerbil-bazel= toolchain, however, still copies
=GERBIL_BAZEL_MEMORY_BYTES=, =GERBIL_BAZEL_CPU_COUNT=, and
=GERBIL_BUILD_CORES= into the =GerbilProjectCompile= action environment.
Those nonsemantic host-capacity values remain an upstream action-key defect.
The process-tree RSS cap remains active throughout compilation.  Admission
still fails closed when available memory cannot cover caller headroom plus the
minimum guarded RSS floor.  A cached Scheme receipt describes the producer
execution of that cached artifact, while the CI phase receipt describes the
current cache consumer.

** Downstream CI package ownership correction

Pull-request run =33673613151= exposed a downstream ownership violation after
the ASP dependency revision changed.  POO Flow CI invoked
=@local_gerbil//:install_dependencies= and then built
=//scheme:dependency_packages=.  The first command is the explicit developer
=gxpkg deps --install= side effect; the second is the declared Bazel artifact
graph.  Running both compiled the same dependency closure through two owners.

The duplicate developer action cost =148 s= on Linux and =392 s= on macOS
before the Bazel dependency graph began.  The Linux job completed in =11 min 05
s= and the macOS job in =19 min 01 s=, so both exceeded the =8 min= and =10
min= promotion limits.  Runtime-WASM run =33673613015= failed at its =8 min=
step limit while executing the same redundant developer action; its ASP guard
receipt reported =146925 ms= for that package build, =3= configured workers,
=1496350720 B= peak RSS, and no memory-based worker reduction.

POO Flow CI now uses only =//scheme:dependency_packages=.  Bazel owns the
isolated dependency artifacts and reverse invalidation closure, while
=@local_gerbil//:install_dependencies= remains available solely as an explicit
developer workspace operation.  The correction removes duplicate compilation;
it does not relax a timeout or hide the remaining cold-action cost.

*** Capability and package readiness are separate receipts

Run =33681435600= proved that removing the developer installation side effect
also invalidated an old test assumption.  All three declared package actions
completed, but =shared_gerbil_capability_test= required the immutable
=@local_gerbil= toolchain receipt to report those packages as installed in its
prefix.  Its =dependencyState= correctly remained =missing=: Bazel package
outputs live in isolated project roots and must not mutate the toolchain.

The corrected gate assigns one authority to each receipt:

- the local or prebuilt toolchain receipt proves compiler capability, declared
  dependency policy, platform, and tool paths;
- each =gerbil-bazel.project-receipt.v1= proves that one Bazel-owned package
  action completed and that every observed source revision equals its expected
  revision;
- a successful child exit does not excuse a memory anomaly: any package
  receipt with =peakRssBytes >= 5 GiB= fails downstream acceptance.

The final memory check is deliberately a receipt gate, not a worker limiter.
The upstream Scheme guard remains responsible for detecting a rapid RSS rise
while preserving available CPU parallelism.

** Dedicated external-module action-key audit

Run =30034465973= job =89298795259= successfully restored the preceding
=setup-bazel= disk archive through prefix fallback.  The archive layer
therefore supplied its prior entries.  The subsequent =370.618 s= build still
ran all four =GerbilProjectCompile= actions in =processwrapper-sandbox=; only
the receipt-validation test later reported one disk-cache hit.  This is a
Bazel action-key miss, not a GitHub archive-restore miss.

The external fixture had created a fresh =--output_user_root= below =mktemp=
for every invocation.  The pinned =gerbil-bazel= prebuilt toolchain
materializes absolute paths derived from that root as =GERBIL_GCC=,
=GERBIL_GSC=, and related generated-wrapper and toolchain-environment values.
=GerbilProjectCompile= copies those values into its action environment, so the
changing absolute paths changed the action key for all four compile actions.

POO Flow now accepts an optional, validated absolute
=POO_FLOW_EXTERNAL_BAZEL_OUTPUT_BASE=.  The dedicated full external-module job
binds it to a stable =runner.temp= path; the missing-root-override probe and the
native analysis lanes retain their isolated random user roots.  This is a
fixture-level cache mitigation, not the durable rule fix.  The upstream
=gerbil-bazel= follow-up must make tool and wrapper locations
execroot/runfiles-relative and remove nonsemantic host-capacity values from the
compile action environment.

The Runtime-WASM namespace now advances the same ignored BUILD generation,
declares =cache-version: 1= explicitly, and enables the same fork-safe saver.
Pushes and same-repository pull requests may publish the new generation; fork
pull requests remain restore-only.

No warm compile hit is accepted for the stable-output-base mitigation yet.
The first post-change job may need to populate stable-path action keys because
the restored archive contains keys derived from earlier random roots.  The
required acceptance is therefore a completed population job with a successful
post-save followed by a same-input or documentation-only job that restores
that generation, serves all four =GerbilProjectCompile= actions from the disk
cache without =processwrapper-sandbox= execution, validates the external
receipt, and records the warm wall time.

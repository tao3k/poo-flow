* Declarative Just command surface

The repository maintains one root =justfile= as the human and CI command
catalog above Bazel.  It is intentionally a thin declarative layer: variables
name stable Bazel targets, recipe groups expose discovery, build, test, and
check intents, and recipe dependencies compose those intents.  The Just layer
does not inspect the host OS, rewrite SDK variables, locate Gerbil binaries,
construct runfiles, invoke =gxi= or =gxc=, parse receipts, or reproduce any
=build.ss= or Building Framework policy.

The maintained surface is:

- =just query= for the complete Bazel target graph;
- =just build= for =//scheme:compile=;
- =just build-runtime-c= and =just build-bundle-v1= for their declared C
  library targets;
- =just toolchain= for explicit registered-toolchain resolution evidence;
- =just test= for the ordinary =//scheme:tests= acceptance suite;
- =just test-runtime-c= and =just test-bundle-v1= for their ordinary suites;
- =just test-runtime-c-sanitizers= and =just test-runtime-c-leaks= for explicit
  native diagnostic gates;
- =just test-performance= for the separately visible performance gate; and
- =just check= as the dependency composition =query -> build -> test=.

=BAZEL= may select the Bazel executable without changing recipe semantics.
Every target, platform decision, cache key, sandbox, and output remains
Bazel-owned.  Every Scheme topology, scheduling, compilation, guard, and
receipt decision remains =build.ss= and Building Framework-owned.  A recipe is
therefore a maintained command alias and dependency edge, never a third build
implementation.

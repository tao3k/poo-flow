* Versioned build-source identity and comparable performance receipts

Performance measurement uses the native Gerbil package lifecycle.  POO Flow no
longer owns a Scheme runner that recursively starts Bazel servers, performs
=clean/cquery/build/shutdown=, or simulates Bazel in shell.  Bazel remains an
integration and hermeticity gate; it is not the cold/warm observer.

#+begin_src mermaid
flowchart LR
    R["Exact git revision + gerbil.pkg"] --> D["gxpkg deps --install"]
    D --> Clean["Cold: gxpkg clean"]
    Clean --> Cold["Native gxpkg build -g"]
    Cold --> Warm["Warm: unchanged gxpkg build -g"]
    Cold --> O["Building Framework observability receipt"]
    Warm --> O
    O --> C["Pure POO performance-budget comparison"]
    C --> V{"Comparable identity and median budget"}
    V -->|accepted| A["Performance evidence"]
    V -->|rejected| F["Regression or incomparable run"]
#+end_src

The native measurement coordinates are:

- exact baseline and candidate revisions;
- tracked =gerbil.pkg= dependency revisions;
- Gerbil native ABI and Building Framework revision;
- host/session identity and logical CPU count;
- effective build-core count from the native observability receipt;
- native cold/warm classification and Gerbil artifact state;
- elapsed time, process RSS, and Building Framework stage summary.

The pure comparison API in
=src/build-api/project-compile-performance-budget.ss= remains independent of
Bazel.  Its unit test receives immutable observations as values; it never
launches a build.  A CI or operator collecting a controlled A/B invokes the
native =gxpkg= lifecycle for each revision and then supplies the resulting
typed evidence to the comparison API.  Bazel may compile and test this pure
policy module without becoming the measurement source.

Removed interfaces have no compatibility route:

- =//scheme:compile_performance_audit=;
- =//scheme:compile_performance_audit_test=;
- =//scheme:validate_compile_performance_budget=;
- =just audit-scheme-compile=;
- the reusable =scheme-compile-performance-audit.yml= workflow;
- fake-Bazel and shell launcher fixtures.

This keeps the responsibility split precise: native =gxpkg= and Building
Framework expose Gerbil cold/warm facts, Bazel tests the declared integration,
and POO Flow only decides whether two explicit observations satisfy its
comparison policy.

* 2026-09-01 native cold/warm observation

The dependency install was completed before sampling and is not included in
the cold value.  Both samples used the same Darwin host, Apple
=/usr/bin/clang=, no =SDKROOT= or =DEVELOPER_DIR= injection, twelve logical
CPUs, and the adaptive twelve-worker policy.

| Sample | Native transition | Wall time | Maximum resident set size | Outcome |
|--------+-------------------+-----------+---------------------------+---------|
| cold | =gxpkg clean=, then =gxpkg build -g= | 218.74 s | 2,766,733,312 B | completed |
| warm | unchanged =gxpkg build -g= | 19.98 s | 2,026,995,712 B | completed |

The warm Building Framework receipt reported one compiled stage and two skipped
stages.  Its top-level capacity facts were =logical-cpu-count: 12=,
=worker-count: 12=, and =execution-policy: adaptive=.  This proves that the
warm result used the available parallel worker capacity; the stage-local
=adaptive-execution: false= means no nested adaptive runner was introduced.

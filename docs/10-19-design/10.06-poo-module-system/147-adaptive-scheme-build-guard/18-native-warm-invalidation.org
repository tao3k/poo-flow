* Native warm invalidation at the =std/make= boundary

** Decision

The current performance blocker is not a missing Bazel cache and must not be
worked around in POO Flow with a second scheduler, a shared global
=build-deps= directory, or project-local compiler flags.  The same package
graph exceeds the time gate under the native =build.ss= entry point.

The repair owner is the Gerbil =std/make= and compiler scheduling boundary.
Its outer dependency workers and deferred native compiler jobs must preserve a
completed dependency generation before a dependent is admitted.  POO Flow
remains a declarative consumer of the ASP package profile.

#+begin_src mermaid
flowchart TD
  P[POO Flow package spec] --> M[Gerbil std/make dependency workers]
  M --> C[compile-module with parallel native jobs]
  C --> Q[Deferred native compile queue]
  M --> D[Dependent module admitted]
  Q --> O[Dependency static output written later]
  D --> R[Dependent output may be older than dependency]
  O --> R
  R --> W[Next invocation rebuilds a non-empty wave]

  F[Required fix] --> S[Preserve outer worker parallelism]
  F --> T[Complete dependency native outputs before dependent release]
  S --> N[Stable no-op warm build]
  T --> N
#+end_src

** Reproduction receipts

All durations include explicit seconds and terminal state.  Stopped runs are
not successful baselines.

| Observation | Terminal state | Elapsed seconds | Evidence |

| Bazel POO Flow development-profile cold action | stopped at gate | 624.704 s | root owner still running |

The native dependency bootstrap exposed two costs that are not POO Flow
compile time:

1. A plain =gxpkg deps --install= inherited the Nix Darwin =SDKROOT= before
   the ASP build entry point could sanitize it and failed in the upstream
   =gerbil-utils= package.  Native bootstrap must establish the toolchain
   environment before invoking dependency build scripts.
2. =gxpkg update= spent approximately six minutes in
   =gxtags clan gslph git.cons.io github.com=.  Observed RSS varied from about
   1.1 GiB to 4.4 GiB.  Package tagging is an independent package-manager
   action and must not be reported as project compilation.

Gerbil 0.18.2 also exposes a tagged-update defect: =pkg-update= strips the
=@tag= for checkout, but =update-pkgs= subsequently passes the original tagged
string to =pkg-install-deps=.  The checkout succeeds and dependency discovery
then fails with =bad package; missing gerbil.pkg=.  The safe recovery used the
public =gxpkg build <package>= command after the exact checkout.  No
=gxpkg uninstall= operation is permitted.

** Native-unit evidence

The observed native artifact tree contained:

| Projection | Count |
|-
| Base generated modules | 394 |
| Generated =.scm= units | 853 |
| Modules with =~0.scm= | 337 |
| Modules with =~1.scm= | 122 |
| Modules with both =~0.scm= and =~1.scm= | 100 |

One ordinary owner, =src/core/runtime-adapter.ss=, accumulated object
generations =.o1= through =.o8=.  A stopped warm candidate rewrote 235
generated Scheme units across contract, core, graph, loops, module-system,
session, memory, tool, and user-interface owners.  This is executable evidence
of repeated invalidation, not an expected no-op warm result.

The relevant upstream source boundary is =std/make.ss=:

- =make-build= admits dependents after a build worker completes a spec;
- =gxc-compile= passes =parallel: #t= whenever the outer worker count is
  greater than one;
- =execute-pending-compile-jobs!= runs after =make-build= returns;
- freshness compares dependency library timestamps with every declared output.

This combination permits dependency native outputs to be finalized after a
dependent was already admitted.  A later invocation can therefore observe a
newer dependency timestamp and rebuild another wave.

** Promotion gates

The ASP revision pin and POO Flow profile declaration remain a candidate until
the scheduling owner is repaired.  Promotion requires all of the following:

1. one completed native cold build under the 10-minute gate;
2. three consecutive native warm builds in at most 30 seconds each;
3. zero =compile= and zero =execute compile job= lines in every warm build;
4. no new object generation for an unchanged module owner;
5. Bazel =//scheme:compile= and the ordinary Scheme suite pass with the same
   package profile;
6. peak process-tree RSS remains below 5 GiB;
7. the cross-platform tracked =MODULE.bazel.lock= is refreshed and verified on
   both Linux amd64 and Darwin arm64.

Until these gates pass, no commit or CI result may describe the warm
invalidation phase as closed.

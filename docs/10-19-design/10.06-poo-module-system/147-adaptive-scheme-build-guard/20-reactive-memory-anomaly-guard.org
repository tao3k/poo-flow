#+title: Reactive Memory Anomaly Guard
#+language: en

* 2026-09-11 downstream convergence

POO Flow owns no memory guard implementation.  The root package build and POO
CLOS qualification invoke
=call-with-framework-native-build-memory-anomaly-guard= from the pinned public
ASP Gerbil Scheme Build API around downstream-owned work.  They must not copy
its process-table reader, Gambit heap sampler, rolling-window classifier,
worker policy, trace emitter, or termination behavior.

The upstream evidence has two distinct schemas:

- =asp-gerbil-scheme.build-trace.v1= identifies phases as build-lease,
  std-make admission, native compiler activity, or Scheme
  expansion/dependency analysis, with elapsed time, RSS, CPU, and active
  compiler-job observations;
- =asp-gerbil-scheme.memory-anomaly-guard.v1= records the terminal outcome,
  measurement source, peak process-tree memory, maximum window growth and
  rate, compiler activity, observer coverage, and pre/post-native timing.

These receipts can establish a hard-limit breach, a rapid-growth anomaly, a
degraded observer, or whether native compiler activity was observed.  They do
not currently prove object retention, assign a peak to a Scheme or native heap
owner, or prove a generic "heap takeover" condition: that would require a
phase-correlated structured sample series or another upstream-owned ownership
signal.  POO Flow therefore must not invent a downstream verdict from the
current aggregate fields.  If that diagnosis becomes required, the receipt is
extended and validated upstream first; POO Flow then consumes the new field or
projection without adding another sampler.

The obsolete local =process-memory-guard-complete.ss= fixture was removed with
this convergence.  Product runtime memory policies and module-system debug
observations remain separate POO Flow semantics; they do not supervise builds
and are not replacements for the upstream guard.

* Corrected responsibility

The memory guard protects a normal parallel build from abnormal memory growth.
It is not a capacity estimator.  In particular, dividing currently available
memory by a fixed per-worker reservation and then lowering
=GERBIL_BUILD_CORES= confuses safety observation with compiler scheduling.

The receipt with =configured-worker-count=12= and =worker-count=3= is therefore
rejected as policy evidence.  Its approximately =1.25 GiB= observed peak and
=25.255 s= successful compile do not justify removing nine workers before the
build starts.  A stable resident set below the hard boundary is normal even
when its absolute value is relatively high.

The public ASP Building Framework owns the reusable Scheme implementation.
POO Flow declares its PackageSpec and consumes that implementation;
=std/make= remains the only compiler scheduler.

* Detection contract

Normal concurrency is:

#+begin_example
worker-count = positive GERBIL_BUILD_CORES, otherwise logical CPU count
#+end_example

When no positive override exists, the ASP Build API publishes the host CPU
count before Gerbil imports =compiler/base=.  Memory never participates in
this calculation, and the receipt must report
=worker-count-limited-by-memory=false=.

The Scheme observer retains a rolling ten-second RSS sample window over the
complete build process tree.  Its initial rapid-growth boundary is one fifth
of the five-GiB hard line, or one GiB of positive growth inside that window.
One observation moves the state to =suspect=; a second consecutive observation
trips =rapid-rss-growth= only after another one-GiB growth quantum. Re-sampling
the same plateau cannot count one startup jump twice. Falling back inside the
envelope resets the state to =normal=. Reaching five GiB trips
=hard-limit-exceeded= immediately.

This is a trajectory rule, not a high-water allocation rule:

- stable =3 GiB -> 3 GiB= is normal;
- =1 GiB -> 2 GiB= inside ten seconds is suspicious;
- confirmed continued rapid growth is abnormal;
- any sample at or above five GiB is abnormal.

* Upstream boundary

Gerbil =std/make= does not expose a supported mid-flight worker-resize or
admission-pause hook.  The Framework must not claim dynamic throttling that the
upstream scheduler cannot perform.  A confirmed anomaly therefore emits a
typed JSON receipt and fails closed.  Any future pause/resume behavior requires
an upstream scheduler capability first; it cannot be simulated with a second
downstream scheduler or compile windows.

* Executable gates

- A twelve-core configuration remains twelve workers regardless of an
  estimated per-worker memory cost.
- Stable RSS below five GiB never trips or reduces workers.
- One-GiB positive growth inside ten seconds first becomes =suspect=.
- Another one-GiB growth quantum in the same ten-second window confirms the
  anomaly and trips with reason =rapid-rss-growth=.
- Five GiB trips immediately with reason =hard-limit-exceeded=.
- Every terminal receipt includes configured/effective worker equality,
  maximum rolling-window growth bytes and rate, peak RSS, elapsed milliseconds,
  maximum and average active compiler jobs, compiler sample and saturation
  counts, and =worker-count-limited-by-memory=false=. A later stable window
  cannot erase an earlier recovered spike from the terminal evidence.

* Focused implementation receipt

The first source-bootstrapped clean build completed without importing a
previously compiled guard module. Memory remained inside the envelope and did
not reduce the declared twelve-worker capacity, but the 727.198-second elapsed
time is a failed performance gate relative to the 6--7 minute CI baseline:

That receipt predated direct scheduler-frontier sampling, so it cannot prove
the number of simultaneously active compiler jobs. The immediately following
instrumented incremental build rebuilt =memory-anomaly-guard= and
=building/facade= and produced this scheduler receipt:

Two ready owners explain the maximum of two for this incremental graph; the
receipt does not claim that the configured worker pool was capped at two. The
76.214-second warm result still fails the 30-second promotion gate, so build
performance remains open even though static memory-based admission is removed.

The pure Scheme classifier and scheduler-frontier suite passed five of five
cases. The generic source-closure suite passed two of two cases. This closes
the bootstrap and twelve-to-three admission regressions while keeping the
rolling-window and hard-line failure paths executable. The same acceptance
removed the obsolete ASP-owned =poo-flow= component catalog and manifest
command; the only remaining closure API derives a generic downstream package
prefix from that package's own =gerbil.pkg=.

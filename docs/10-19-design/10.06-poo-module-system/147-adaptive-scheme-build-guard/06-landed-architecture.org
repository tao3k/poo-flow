* Landed architecture

POO Flow is a downstream Gerbil project.  It does not own a second build
scheduler, process supervisor, RSS sampler, package resolver, or static-link
driver.

** Owner boundaries

- =gerbil.pkg= is the only POO Flow package/dependency declaration.  The ASP
  dependency is fixed to PR #3 revision
  =e8d00f54294ead9fead051ef1f618a53dd177640=.
- The top-level =build.ss= is the only native package build declaration.  It
  consumes =asp-gerbil-scheme-package-spec!=,
  =asp-gerbil-scheme-package-native-spec=, =defbuild-script=, and
  =framework-build-bindir= from ASP PR #3.
- Gerbil =std/build-script= and =std/make= retain compiler graph and scheduling
  authority.  POO Flow does not start another =gxi= or =gxc= to supervise a
  build.
- =gerbil-bazel= owns toolchain selection, Darwin/Linux environment projection,
  sandboxing, cache keys, adaptive resource admission, process-tree
  observation, termination, and canonical build receipts.
- =scheme/BUILD.bazel= is a downstream declaration of source sets, package
  dependencies, compile targets, and test roots.  It must use the public
  =@gerbil_bazel//gerbil:defs.bzl= rules without copying their implementation.
- =justfile= is a declarative catalog of stable Bazel targets.  It does not
  configure compilers, cores, SDKs, package installation, or resource limits.
- =src/qualification/runner.ss= is now pure: it binds externally produced
  action evidence to gate declaration digests and source revisions, then
  verifies completeness.  It never executes a command.

** Removed downstream owners

The following designs are intentionally absent and have no compatibility
surface:

- POO Flow build-stage macros and project-build CLI commands;
- local =ps= or =/proc= process-tree sampling;
- nested GXI memory-guard launchers;
- local adaptive compile windows or worker-count policy;
- POO Flow project compile guard receipts;
- Scheme tools that execute Bazel, Python, Lean, or C qualification commands.

Any future static-build or feature-selection declaration must first exist as a
reviewed ASP PR #3 Build API.  POO Flow may consume that API by changing its
package declaration and pinned revision; it must not predict or reimplement the
interface locally.

#+title: Application Environment Profile Purity and Capability-Scoped Deployment/Runtime Input Boundary
#+startup: overview

* Status

Accepted architecture decision.

This RFC continues the evidence-plane separation defined by
[[file:45-114-resolved-composition-receipt-and-package-source-build-runtime-evidence-separation.org][45-114]].

* Evidence state

A parser-owned ASP owner search used 45-112 as the exact owner anchor.  It
succeeded.

The receipt confirmed:

- the ordinary surface remains =use-composition=, =compose=, =profiles=, and
  =use-module=;
- =ResolvedCompositionReceipt= is immutable evidence from pure POO-profile
  resolution;
- semantic composition does not fetch source, install packages, run builds or
  tests, grant runtime authority, or activate a composition globally;
- package, build, semantic, admission, and runtime evidence remain separate;
- implementation ownership remains =MISSING=.

The receipt did not identify implementation owners for deployment-input or
secret-provider adapters.  Those owners remain =MISSING=.

* Scope

This RFC defines:

- purity of application-owned profiles;
- explicit static semantic inputs;
- deployment references;
- runtime observation requirements;
- secret references and capability-scoped access;
- environment-variable and filesystem boundaries;
- explicit time and entropy boundaries;
- deployment adapter ownership;
- cache, receipt, and redaction behavior.

This RFC does not define:

- a new environment-variable DSL;
- a secret-store implementation;
- a filesystem abstraction;
- a Nix-to-POO configuration translation language;
- ambient process-state access;
- a public input macro;
- a replacement runtime observation system.

* Central decision

=compose= with =profiles= is pure.

No profile resolution may implicitly read:

- process environment variables;
- current working directory;
- filesystem contents;
- current time;
- randomness or entropy;
- network state;
- secret values;
- mutable deployment state.

An application profile may:

- consume an explicit immutable non-secret POO value;
- carry an opaque deployment reference;
- declare a typed runtime observation requirement;
- declare a typed secret capability requirement.

It cannot perform the observation while being composed.

* Input classes

** StaticSemanticInput

=StaticSemanticInput= is:

- explicit;
- immutable;
- non-secret;
- portable;
- content-identified;
- safe to include in semantic composition identity;
- supplied before pure profile derivation.

Examples include:

- a declared feature set;
- a bounded non-secret policy constant;
- a selected domain mode;
- an explicit immutable resource class.

If the value changes semantic graph shape or policy, its identity contributes
to the derived profile revision and composition receipt.

** DeploymentReference

=DeploymentReference= is an opaque POO-native reference to a deployment-owned
resource.

It may identify:

- a secret provider entry;
- a runtime filesystem resource;
- an external service endpoint;
- a clock or entropy provider;
- a deployment-local capability source.

The reference is not the resource value.  It grants no authority by itself.

** RuntimeObservationRequirement

=RuntimeObservationRequirement= declares an observation that must occur only
after admission.

Examples include:

- current time in an admitted clock domain;
- entropy under an admitted derivation policy;
- filesystem content under a scoped read capability;
- network response under an explicit effect intent;
- current secret generation under a secret capability.

The requirement contributes policy and capability shape, not observed data.

** SecretRequirement

=SecretRequirement= is a specialized runtime requirement.

It contains:

- provider-scoped reference identity;
- required use purpose;
- allowed operation;
- principal and resource scope;
- retention and redaction constraints;
- version or freshness policy.

It contains no secret bytes.

* Classification rule

An input belongs in semantic composition only when all of these are true:

- it is non-secret;
- it is immutable for that composition;
- it is explicitly supplied;
- it changes semantic graph or policy;
- it is safe for explanation and content identity;
- it does not require a runtime effect to observe.

Otherwise it remains a deployment reference or runtime observation requirement.

* Application-owned profile

The application repository may own a derived profile that combines:

- domain profiles exported by =wendao-episteme=;
- application policy;
- explicit static semantic inputs;
- deployment references;
- runtime observation requirements;
- secret requirements.

The derived profile remains a pure POO value.

It does not contain:

- resolved secret values;
- open files;
- sockets;
- environment lookup procedures;
- clock procedures;
- random generators;
- mutable provider clients;
- live capabilities.

* Higher-order profile derivation

A profile author may derive a profile through a pure higher-order POO
operation:

#+begin_example
base profile value
  × explicit StaticSemanticInput
  × deployment and runtime requirements
  -> derived application-owned profile value
#+end_example

This is a semantic equation, not a new reader form or macro.

Exact authoring syntax must use verified native =gerbil-poo= operations.  This
RFC does not invent an application-profile DSL.

* Environment-variable boundary

Process environment variables are ambient mutable state.

They cannot be read:

- by =compose=;
- by =profiles=;
- by =use-module= expansion;
- by =use-composition= expansion;
- by a POO profile slot during semantic resolution.

When an environment value is truly static, non-secret, and semantic:

1. a deployment adapter reads it outside composition;
2. the adapter validates and normalizes it;
3. the adapter produces an immutable POO =StaticSemanticInput=;
4. pure profile derivation consumes that value;
5. the input identity appears in the composition receipt.

When the value is secret or operationally dynamic, it remains a runtime
reference and is not captured into semantic composition.

* Filesystem boundary

A local file path is not durable semantic identity.

Reading a file is an effect and cannot occur during profile composition.

An external input adapter may:

- read a declared file under explicit authority;
- parse and validate non-secret content;
- project safe content into an immutable POO semantic input;
- retain a separately owned input receipt.

Secret files, mutable files, sockets, devices, and runtime state remain behind
admitted capability boundaries.

The semantic receipt never stores local checkout paths or secret file content.

* Time boundary

Current time is an observation, not a pure profile input.

A profile may declare:

- an admitted clock domain;
- freshness requirements;
- deadlines;
- retention durations;
- replay-time policy.

It cannot call the clock during composition.

Time-dependent admission or evaluation receives an explicit time observation
and receipt from the authorized clock boundary.

Replay uses recorded or explicitly supplied replay-time observations.  It does
not silently call the live clock.

* Entropy boundary

Randomness and entropy are explicit runtime inputs.

A profile may declare:

- deterministic derivation policy;
- an entropy capability requirement;
- permitted operational randomness;
- replay requirements.

It cannot instantiate or call a random generator during composition.

Deterministic identifiers derive from explicit content identities.  Operational
randomness remains behind runtime admission and produces typed observation
evidence.

* Secret boundary

Secret plaintext never enters:

- profile values;
- profile revisions;
- =ResolvedCompositionReceipt=;
- semantic composition cache keys;
- explanation output;
- conflict output;
- build or test logs;
- portable suspension descriptors.

The runtime receives an attenuated =SecretCapability= only after:

- principal authentication;
- policy intersection;
- purpose validation;
- provider and resource-scope validation;
- retention and redaction admission;
- budget admission.

The capability is opaque, process-scoped when required, non-serializable, and
non-transferable by default.

* Secret observation

A secret provider returns:

- the secret only to the authorized runtime consumer;
- a redacted =SecretObservationReceipt=;
- an opaque provider revision or freshness identity;
- use-purpose and scope evidence;
- expiry and cleanup obligations.

The receipt cannot reconstruct the secret.

Provider revision evidence must not expose a plaintext-derived digest when that
digest would leak useful information.

* Secret rotation

Secret rotation does not automatically change semantic composition identity.

The semantic profile still refers to the same secret requirement unless its
reference or policy changes.

Rotation may invalidate:

- a live secret capability;
- a runtime observation;
- a qualified runtime cache entry;
- a pending runtime handoff.

It does not rewrite a prior profile revision or composition receipt.

* Deployment adapter boundary

Deployment adapters own effectful acquisition and binding.

They may:

- read deployment configuration;
- validate declared inputs;
- create safe static semantic POO values;
- create opaque deployment references;
- bind references to capability providers;
- emit deployment-input receipts.

They may not:

- construct hidden profile facets from ambient state;
- inject authority into a profile object;
- place secret values in semantic receipts;
- reinterpret package or build evidence as runtime capability;
- change a profile after its revision identity is fixed.

* Nix boundary

Nix may provision:

- source and package environments;
- build artifacts;
- deployment adapter configuration;
- secret-provider references;
- runtime service bindings.

A Nix attribute set is not a POO profile or POO module.

Nix does not become semantic owner merely because it supplies deployment
inputs.

The adapter boundary must explicitly project permitted non-secret values or
opaque references into native POO values.

* Deployment input receipt

=DeploymentInputReceipt= remains separate from
=ResolvedCompositionReceipt=.

It records:

- input-adapter identity and revision;
- declared input source class;
- validation outcome;
- produced static-input or deployment-reference identities;
- redaction and retention policy;
- separately owned provenance.

It does not record secret plaintext or grant runtime authority.

When a static semantic input contributes to composition, the semantic receipt
references only its safe immutable identity.

* Pure and effectful flow

#+begin_src mermaid
flowchart LR
  ENV["Environment, file, deployment, or secret source"] -->|"explicit adapter reads under deployment authority"| D["Deployment input adapter"]
  D -->|"validated non-secret immutable value is produced"| S["StaticSemanticInput"]
  D -->|"dynamic or sensitive resource remains opaque"| R["DeploymentReference"]
  S -->|"pure higher-order POO derivation fixes application profile revision"| P["Application-owned profile"]
  P -->|"pure compose with profiles strategy resolves"| C["Resolved composition"]
  C -->|"semantic identity and provenance are recorded"| CR["ResolvedCompositionReceipt"]
  R -->|"profile declares capability shape without resolving value"| Q["Runtime observation requirement"]
  Q -->|"fresh principal, policy, scope, and budget intersect"| A["Coordinator admission"]
  A -->|"attenuated capability is issued"| H["Runtime input handle"]
  H -->|"authorized observation occurs at explicit boundary"| O["Runtime observation receipt"]
  O -->|"observation qualifies evaluation and cache"| E["Runtime evaluation"]
#+end_src

No edge carries an ambient value directly into profile composition.

* Secret access flow

#+begin_src mermaid
sequenceDiagram
  participant P as Pure profile composition
  participant C as Coordinator
  participant S as Secret provider
  participant R as Runtime consumer

  P-->>C: secret requirement and opaque reference only
  C->>C: intersect principal, policy, purpose, scope, and budget
  C-->>R: attenuated non-serializable secret capability
  R->>S: resolve reference under admitted capability
  S-->>R: secret value through protected runtime channel
  S-->>C: redacted observation receipt and opaque revision
  R-->>C: cleanup and use-purpose completion evidence
  C-->>C: reconcile budget, retention, and runtime cache qualification
#+end_src

The secret value never returns to the semantic composition plane.

* Admission boundary

A profile requirement becomes a live handle only through fresh coordinator
admission.

Admission validates:

- principal and session;
- application composition identity;
- requirement identity;
- deployment-provider binding;
- capability scope;
- purpose;
- current policy;
- redaction and retention;
- freshness;
- budget;
- runtime locality.

A requirement has capability shape but no authority.

* Runtime observation context

Runtime observations are added to the immutable
=EvaluationContext= through explicit successor-context transitions.

They are:

- scoped to the admitted demand;
- content- or provider-revision identified when safe;
- redacted according to policy;
- retained only within admitted bounds;
- excluded from unrelated sibling contexts;
- unavailable to pure profile resolution.

* Cache separation

** Semantic cache

The semantic composition cache may include identities of safe
=StaticSemanticInput= values.

It excludes:

- environment lookup state;
- file handles and local paths;
- clock observations;
- entropy;
- secret references when not semantically relevant;
- secret values and secret-derived plaintext digests;
- live runtime capabilities.

** Runtime cache

Runtime cache qualification may include:

- admitted observation identities;
- opaque secret-provider revision;
- runtime context and policy revisions;
- evaluator identity;
- redaction and retention bounds.

Secret rotation invalidates affected runtime entries without invalidating
unrelated semantic composition entries.

Replay and simulation caches remain isolated.

* Explanation and redaction

Semantic explanation may state:

- which requirement exists;
- which application profile declared it;
- which provider class is expected;
- which policy narrowed it;
- why admission accepted or rejected it.

It cannot reveal:

- secret value;
- hidden environment content;
- protected file content;
- live capability handle;
- provider-internal locator;
- redacted observation.

* User interface

The ordinary surface remains unchanged:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

=application-production= is already a pure POO profile value.

The ordinary composition form contains no:

- =getenv=;
- file load;
- secret clause;
- clock clause;
- random clause;
- Nix attribute set;
- capability token;
- runtime callback.

* Macro governance

No environment, deployment, or secret macro is introduced.

The approved thin macros do not inspect ambient state at expansion time or
runtime.

Any future phase-specific projection must still expand to explicit pure POO
values or explicit runtime-boundary calls, with authority and effects visible
in the expanded contract.

* Failure behavior

The system fails closed on:

- ambient environment lookup during composition;
- filesystem read during profile resolution;
- live clock or entropy call during composition;
- secret value stored in a profile or semantic receipt;
- secret-derived digest that leaks useful information;
- local path used as durable semantic identity;
- deployment adapter manufacturing capability authority;
- Nix value treated directly as a POO module or profile;
- hidden runtime observation used to choose a profile;
- secret rotation rewriting prior semantic receipts;
- runtime observation promoted into a semantic composition cache;
- explanation revealing protected input.

- [X] Profile composition remains pure.
- [X] Static semantic inputs are explicit, immutable, non-secret POO values.
- [X] Ambient environment and filesystem state are never composition inputs.
- [X] Time and entropy are explicit runtime observations.
- [X] Profiles declare secret requirements but never contain secret values.
- [X] A requirement has capability shape but no authority.
- [X] Deployment adapters own effectful acquisition and binding.
- [X] Nix does not become POO semantic owner.
- [X] Deployment and semantic receipts remain separate.
- [X] Secret rotation invalidates runtime state without rewriting semantic
  history.
- [X] Semantic and runtime caches remain isolated.
- [X] The ordinary user surface remains unchanged.
- [X] No new public macro is introduced.

* Conformance checklist

- [ ] ASP emits parser-owned implementation owners for input and secret
  adapters.
- [ ] Profile resolution performs no environment, filesystem, clock, entropy,
  network, or secret effects.
- [ ] Static semantic inputs are native POO values with safe content identity.
- [ ] Deployment references are opaque and grant no authority.
- [ ] Secret requirements contain no secret bytes.
- [ ] Secret capabilities are attenuated, non-serializable, and purpose-scoped.
- [ ] Secret observation receipts are redacted and non-reconstructive.
- [ ] Deployment receipts remain separate from composition receipts.
- [ ] Runtime observations enter only through successor-context transitions.
- [ ] Secret rotation invalidates qualified runtime cache entries.

- [ ] Mermaid edge labels preserve pure/effectful transitions.

* Implementation ownership

This section is normative and supersedes earlier audit statements that
implementation ownership was =MISSING=. Unchecked items below concern
implementation completion, not owner selection.

- [X] The final application owns pure application Profiles and explicit static
  semantic inputs.
- [X] Runtime/deployment adapters own environment, filesystem, time, entropy,
  secret resolution, redaction, and capability-scoped observation.
- [X] =poo-flow-core= owns the contract that prevents those runtime
  observations from entering pure Profile evaluation.
- [ ] Deployment-input and secret-provider adapters remain runtime/deployment
  implementation work.

#+title: Profile Revisions, Live Upgrade, and Module-Reload Boundaries
#+startup: overview

* Status

This RFC records the accepted profile-revision and live-upgrade semantics.

It extends module/profile identity, immutable generations, active-head
publication, activation, drain, continuations, and incremental cache
invalidation.

* Typst formalization: immutable revision upgrade

Stable module paths and lexical bindings do not imply mutable profile values.
Every upgrade creates a new module artifact, profile revision, composition-root
revision, immutable generation, and active-head transition.

#+begin_src typst
#let upgrade(source, previous) = (
  module-artifact: new-module-artifact-id(source),
  profile-revision: new-profile-revision-id(source),
  root-revision: new-root-revision-id(source),
  generation: new-generation-id(source),
  active-head: new-active-head-transition(previous),
)

$ upgrade(source, previous)
  ==> immutable(upgrade(source, previous).profile-revision)
  and immutable(upgrade(source, previous).generation) $

$ stable-module-path(binding)
  ==> not dynamically-resolve-newest-revision(running-root(binding)) $

$ in-place-profile-mutation or module-reload-rewrites-root
  ==> rejected(upgrade) $
#+end_src

Semantic equivalence may permit cache or SCC-proof reuse, but it never merges
revision identities, reuses old approval or capability, or aliases generation
identity.  Continuations and effects remain bound to the revision that created
them.

#+begin_src typst
$ equivalent(revision-a, revision-b)
  ==> may-reuse-semantic-cache(revision-a, revision-b)
  and may-reuse-unchanged-scc-proof(revision-a, revision-b)
  and revision-a.identity != revision-b.identity
  and not reuse-old-approval(revision-b)
  and not reuse-old-capability(revision-b) $

$ continuation(k)
  ==> bound(k, k.generation)
  and bound(k, k.root-revision)
  and bound(k, k.profile-revisions)
  and not silently-rebind(k) $

$ source-pin-a != source-pin-b
  ==> profile-revision(source-pin-a) != profile-revision(source-pin-b) $

$ revert(target-generation)
  ==> new-active-head-transition(target-generation)
  and reprove-current-compatibility(target-generation)
  and reprove-artifact-availability(target-generation)
  and reprove-current-governance(target-generation)
  and not reuse-stale-capability(target-generation) $
#+end_src

* Central decision

Module paths and ordinary lexical binding names may remain stable.

Every exported profile revision is immutable.

An upgrade creates:

- a new module artifact identity;
- a new profile revision;
- a new composition-root revision;
- a new immutable generation;
- a new active-head transition.

It does not mutate an existing profile value or composition root.

* Stable names and immutable revisions

The ordinary user may continue to compose:

#+begin_src scheme
wendao-episteme
#+end_src

One build may bind that name to Profile Revision A, and a later build may bind
the same lexical name to Profile Revision B.

A running composition root retains its exact revision A reference.

It does not become revision B merely because the module path or exported name
is unchanged.

* Profile revision identity

A profile revision identity includes at least:

- profile anchor;
- exporting module identity;
- module source and build identities;
- macro-expansion and provenance identities;
- POO construction identity;
- source-pin provenance;
- contract projection identity;
- required capability-contract identity;
- strategy and schema identities.

A change to any identity creates a new revision boundary.

The lexical name is not the revision identity.

* Prohibited in-place upgrade

Upgrade must not use:

- =set!= on an exported profile;
- replacement of a global registry entry;
- import side effects that mutate existing objects;
- mutation of shared prototype slots;
- module reload that rewrites a composition root;
- cache aliasing between old and new revisions;
- reuse of one generation identity for different code.

Mutable compatibility shims may exist only behind explicit live resource
boundaries. They do not make profile semantics mutable.

* Module resolution times

Module resolution has two different boundaries.

** Build and deployment resolution

The build resolves a module path to exact:

- source identity;
- macro expansion;
- dependency closure;
- toolchain identity;
- compiled artifact identity.

The module exports a new immutable profile value.

** Running composition resolution

A completed composition root holds exact profile revision identities.

Runtime demand evaluation does not repeatedly resolve a stable module path to
the newest available artifact.

One fixed-point attempt must not use revision A for one demand and revision B
for another demand under the same root identity.

* Concurrent old and new revisions

A runtime hosting old and new generations concurrently isolates their module
and profile artifacts.

Possible execution strategies include:

- distinct loader namespaces;
- distinct processes;
- distinct artifact handles;
- another runtime mechanism with equivalent isolation evidence.

If the Gerbil runtime cannot safely load two revisions of one module path in a
single process, process-level rollout is the default execution strategy.

This implementation constraint does not change revision semantics.

* Profile revision delta

Upgrade analysis produces an immutable =ProfileRevisionDelta= comparing:

- added, removed, and changed slot contributions;
- prototype lineage;
- priorities;
- semantic requirements and contributions;
- capability contracts;
- reader, writer, and effect contracts;
- migration policy;
- governance policy;
- retention and disclosure policy;
- nested module and submodule scope identities;
- source and build provenance.

A text diff is not semantic revision evidence.

Identical text with changed dependencies, macro expansion, toolchain, or source
provenance may produce a new revision.

Different text may produce semantically equivalent POO results, but equivalence
must be proven.

* Semantic equivalence

A =ProfileRevisionEquivalenceProof= may allow:

- semantic value-cache reuse;
- unchanged SCC-proof reuse;
- downstream invalidation to stop;
- avoidance of unnecessary runtime materialization.

Equivalence does not:

- erase either revision;
- rename revision B as revision A;
- bypass build and provenance admission;
- reuse approval or capability bound to the old proposal;
- reuse one generation identity for both revisions.

Revision identity and proven semantic equivalence remain separate facts.

* Upgrade phases

The normative upgrade sequence is:

1. build a new module artifact;
2. construct a new profile revision;
3. compose a new root revision;
4. close the structural and semantic graph;
5. produce revision-delta and compatibility evidence;
6. build a new immutable generation;
7. obtain governance and publish a new active-head transition;
8. activate consumers and drain old work;
9. retire and reclaim the old generation when admitted.

No phase mutates the output of an earlier deployment.

* Source-submodule pin updates

Changing the =wendao-episteme= submodule commit:

- changes source provenance;
- reconstructs the core-owned thin projection;
- creates a new profile revision;
- requires new provenance and equivalence evidence;
- does not transfer child build or test ownership to the parent.

Even when projected contracts appear unchanged, the new source provenance
remains visible.

The parent verifies only its own projection contract.

* Continuations and in-flight work

A continuation remains bound to:

- generation identity;
- composition-root revision;
- profile revisions;
- causal and resource evidence;
- pending effect obligations.

Changing a module path or active profile binding does not change the captured
revision.

Migration to a new profile revision requires explicit compatibility,
migration proposal, authority, and receipts.

Effects produced under revision A remain interpreted under revision A.

* Cache invalidation

Cache keys include exact profile and root revisions.

A changed profile revision invalidates the reachable demand and SCC frontier.

An unchanged incoming identity may permit SCC reuse.

A semantic-equivalence proof may stop downstream propagation after canonical
reevaluation.

Module path or lexical-name equality is never sufficient cache-reuse evidence.

* Development REPL

Interactive redefinition creates:

- an ephemeral module artifact identity;
- an ephemeral profile revision;
- session provenance;
- non-production trust classification.

A convenient active REPL binding may select the newest ephemeral revision.

It must not mutate historical roots or present interactive evidence as a
production build receipt.

Promoting an interactive result to production requires a reproducible build,
provenance closure, and new production revision.

* Reversion

Reversion is not module reload.

It uses a new active-head transition to select an existing immutable
generation.

Before reversion, policy reproves:

- current resource and schema compatibility;
- profile and module artifact availability;
- continuation and effect compatibility;
- current governance authority.

Old approval, capability, and activation receipts do not automatically become
current.

* Failure taxonomy

The implementation must distinguish at least:

- exported profile mutated in place;
- module reload rewrote a root;
- profile revision identity incomplete;
- old and new artifacts not isolated;
- text diff treated as semantic proof;
- equivalence proof incomplete;
- old approval reused for new revision;
- module path used as cache identity;
- continuation silently rebound;
- source pin changed without new revision;
- REPL revision treated as production;
- reversion artifact unavailable;
- reversion resource contract incompatible.

* Required invariants

1. Stable names do not imply mutable profile values.
2. Every profile revision is immutable.
3. Upgrade creates a new root and generation.
4. Running roots do not dynamically resolve newest module revisions.
5. Old and new artifacts remain isolated during overlap.
6. Text diff does not replace semantic revision evidence.
7. Revision identity and semantic equivalence remain separate.
8. Source-pin change produces a new revision boundary.
9. Continuations and effects remain bound to original revisions.
10. Cache reuse requires exact identity or equivalence proof.
11. REPL redefinition produces ephemeral revisions.
12. Reversion is a new active-head transition.
13. No reload mechanism mutates an existing composition root.
14. Public upgrade policy extension remains POO-native.

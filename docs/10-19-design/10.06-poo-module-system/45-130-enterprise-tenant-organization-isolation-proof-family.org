* Purpose

This RFC owns the Enterprise Tenant/Organization proof subfamily referenced by
=45-129-enterprise-assurance-proof-module-family.org= and the multi-tenant
assurance scenario in
=45-128-real-world-ai-assurance-scenarios-and-adapter-governance.org=.

The proof objective is not to encode one company’s organization chart.  It is
to prove that organization, tenant, project, principal, resource, cache, and
evidence scopes cannot be silently confused.

* Open-world organization model

Organization topology remains policy/profile data.  The Lean core quantifies
over:

- =Organization=;
- =Tenant=;
- =Project=;
- =Principal=;
- =Resource=;
- =Evidence=.

It receives explicit relations:

- tenant belongs to organization;
- project belongs to tenant;
- principal belongs to tenant;
- resource belongs to project;
- evidence supports the exact organization/tenant/project/principal/resource
  closure.

This permits trees, DAGs, federated organizations, personal tenants, service
accounts, temporary projects, and industry-specific structures without
changing the POO Flow theorem vocabulary.

* Reused generic owners

- =CapabilityRoleIsolation= proves that requirements, canonical scopes, and
  receipts do not themselves grant runtime execution authority.
- =DistributedCacheAdmission= owns independent provenance, semantic-key,
  freshness, confidentiality, revocation, and determinism checks for remote
  cache candidates.
- =CrossDomainFederation= owns federation compatibility, capability
  attenuation, disclosure projection, responsibility allocation, and
  revocation.
- =Enterprise.Admission= owns enterprise governance admission before tenant
  refinement.
- =CedarAuthorizationSemantics= owns the exact
  =Cedar.Spec.Request/Entities/Policies/Response= definitional interface.
- =CedarResponseArbitrationBridge= owns complete comparable outcomes and
  fail-closed input-identity disagreement.

The Tenant/Organization subfamily consumes these semantics.  It does not
redefine them or create a global organization owner.

* Locally checked results

- complete scope witnesses carry every membership relation and exact scope
  evidence;
- organization or tenant changes cannot alias the same scoped identity;
- different tenants cannot alias the same semantic cache key;
- tenant cache admission requires provenance, freshness, confidentiality, and
  revocation checks;
- evidence disclosure requires policy permission and redaction;
- cross-tenant disclosure requires federation evidence;
- scoped tenant admission refines Enterprise admission;
- tenant mismatch blocks admission;
- a cache key without tenant binding blocks admission;
- missing Tenant/Organization isolation blocks
  =Enterprise.Assurance.Admitted=.
- every admitted Cedar projection contains organization, tenant, project,
  principal, and resource entities;
- the actual =Cedar.Spec.Request=, =Entities=, and =Policies= values are bound
  through explicit projections to the canonical input identity;
- missing principal/resource/tenant entities, stale entity-store revisions, or
  unexpected cross-tenant entities block projection before arbitration;
- tenant or entity-store identity changes change canonical Cedar input
  identity;
- different Cedar input identities fail closed as dual-engine disagreement.
- Tenant CedarAdapter admission requires the entity closure to be admitted;
- the expected comparable outcome and adapter receipt both use the canonical
  tenant input identity;
- the expected and receipt responses equal the full definitional
  =Cedar.Spec.isAuthorized= response, including determining and erroring policy
  sets;
- the adapter receipt carries an executable digest;
- admitted entity-qualified adapters reuse the existing strict dual-witness
  theorem;
- missing closure, expected-input mismatch, or full-response mismatch blocks
  Tenant CedarAdapter admission.

* Open submodules

The first Lean core intentionally leaves the following as separate future
owners:

- hierarchical and multi-parent organization membership;
- tenant merge, split, migration, suspension, and deletion;
- service-account and workload-identity lifecycle;
- shared resources with explicit multi-tenant ownership;
- tenant-specific encryption/key ownership;
- data residency and jurisdiction;
- tenant policy inheritance and local override;
- cross-tenant incident response and disclosure responsibility;
- runtime cache-key and storage-partition refinement;
- recursive Cedar entity-parent closure and richer organization-graph
  completeness beyond the initial exact scope projection.

These MUST remain modular.  They are not grounds for expanding
=TenantOrganization/Admission.lean= into a monolith.

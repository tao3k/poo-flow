#+title: Resource Scope, Version Preconditions, and Concurrency Control
#+subtitle: Pure conflict analysis, TOCTOU safety, optimistic updates, leases, fencing, and multi-resource commits
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative external-resource concurrency protocol
- Semantic core :: Pure POO resource projections and explicit live concurrency boundaries
- Related modules :: =45-55-effect-intent-stabilization-runtime-handoff-and-reconciliation.org= and =45-56-effect-dag-partial-commit-compensation-and-atomicity.org=

This module separates pure resource scope and concurrency policy from live locks, leases, transactions, and authority. It prevents unchecked resource-name heuristics and non-atomic check-then-write sequences from being reported as safe concurrency control.

* Core decision

#+begin_quote
Effect plans analyze concurrency with pure ResourceScopeProjection values, represent external versions with content-addressed ResourceVersionObservation values, and declare commit requirements through ConcurrencyPrecondition. Live locks, leases, transactions, and fencing exist only at the runtime boundary. A system that cannot atomically enforce a required precondition cannot claim TOCTOU safety.
#+end_quote

The four distinct artifacts are:

#+begin_src text
ResourceScopeProjection
ResourceVersionObservation
ConcurrencyPrecondition
LiveResourceLease
#+end_src

* Typst formalization: resource scope, version precondition, and atomic enforcement

The formal boundary separates pure, portable POO declarations from live
runtime synchronization authority.  A resource name or path does not imply an
access role, and neither a version observation nor a concurrency precondition
is itself permission to commit.

#+begin_src typst
#let resource-scope(resource-id, scope, role, policy-id) = (
  resource-id: resource-id,
  scope: scope,
  role: role,
  policy-id: policy-id,
)

#let version-observation(resource-id, version, digest, observation-id, generation) = (
  resource-id: resource-id,
  version: version,
  digest: digest,
  observation-id: observation-id,
  generation: generation,
)

$ S = (r, s, a, p) $
$ O = (r, v, d, o, g) $
$ P(S, O) = (S.r = O.r) and (v_expected = O.v) and (g_expected = O.g) $

$ a in {
  "observe/read",
  "write/replace",
  "append",
  "commutative update",
  "compare-and-swap",
  "exclusive commit",
} $

$ S notin {"lock handle", "lease token", "transaction handle", "connection"} $
#+end_src

Atomic enforcement is a single runtime relation over the precondition, the
authoritative current state, and the mutation.  It is not a reusable value
produced by an earlier observation.

#+begin_src typst
$ AtomicEnforce(P, state_before, mutation) := $
$ quad state_before.resource = P.resource $
$ and state_before.scope = P.scope $
$ and state_before.version = P.expected-version $
$ and state_before.generation = P.expected-generation $
$ and commit(mutation) $

$ Commit(mutation) => exists a: AtomicEnforcement(a, mutation) $
$ state_before.version != P.expected-version => not Commit(mutation) $
$ state_before.generation != P.expected-generation => not Commit(mutation) $
$ state_before.resource != P.resource => not Commit(mutation) $
$ state_before.scope != P.scope => not Commit(mutation) $

$ Authority(O) = false $
$ Authority(P) = false $
$ Authority(AtomicEnforce(P, state_before, mutation)) = true $

$ Check(P, state_(t_0)) and Write(mutation, state_(t_1))
  not=> TOCTOUSafe(mutation) $
#+end_src

The dashed edges are exclusions.  They make the TOCTOU boundary visible:
portable evidence may describe what must be checked, while only the live
atomic runtime relation can authorize a mutation.

** Proof obligations

- [X] =versionObservationDoesNotGrantCommitAuthority=: a content-addressed
  observation is evidence, not mutation authority.
- [X] =preconditionDoesNotGrantCommitAuthority=: a pure precondition is not a
  lock, lease, transaction, or fencing token.
- [X] =atomicEnforcementGrantsCommitAuthority=: the runtime atomic relation is
  the sole authority constructor in this proof slice.
- [X] =commitRequiresAtomicEnforcement=: every admitted mutation commit carries
  its atomic enforcement witness.
- [X] =staleVersionCannotCommit= and =staleGenerationCannotCommit=: stale
  observations cannot inhabit the admitted commit relation.
- [X] =wrongResourceCannotCommit= and =wrongScopeCannotCommit=: identity and
  scope mismatches cannot inhabit the admitted commit relation.
- [X] =committedMutationAdvancesGeneration=: a successful commit advances the
  authoritative generation.
- [X] =detachedCheckThenWriteDoesNotEstablishSafety=: check-then-write without
  an atomic relation does not establish TOCTOU safety.
- [ ] Refine these propositions through native =gerbil-poo= resource-scope
  objects and runtime lock, lease, transaction, or fencing implementations.
- [ ] Replay the synchronized Lean and Typst claims through external AXLE.

* Resource scope projection

A pure =ResourceScopeProjection= is conceptually derived from:

#+begin_src text
adapter protocol identity
+ external resource namespace
+ canonical resource selector
+ access-role identity
+ conflict-policy identity
#+end_src

It contains no:

- live capability token;
- lock or lease handle;
- connection;
- transaction handle;
- current mutable version;
- worker identity.

Resource scope participates in =EffectIntent= and =EffectPlan= identity and supports pure conflict analysis.

* Access roles

Normative access roles include:

- Observe or read;
- Write or replace;
- Append;
- Commutative update;
- Compare-and-swap;
- Exclusive commit.

These roles may be extensible POO prototypes rather than a closed enumeration. Every role declares:

- conflict relation with other roles;
- required version precondition;
- parallel-execution rule;
- transaction or lease requirement;
- commutativity evidence;
- authoritative outcome protocol.

Operation name alone does not establish access semantics.

* Canonical resource relation

An adapter protocol projects one of:

#+begin_src text
disjoint
same resource
parent contains child
overlapping range
unknown
#+end_src

The relation must not be inferred from:

- path prefix;
- URI string prefix;
- display name;
- identity sorting;
- source module name.

An unknown relation prohibits unsafe parallel commit. The runtime may conservatively serialize only when serialization itself is sufficient. Otherwise it fails closed with =ResourceConflictRelationUnknown=.

#+begin_src mermaid
flowchart LR
    A["EffectIntent A resource scope"] -->|"project a canonical overlap relation"| V["Resource conflict analysis"]
    B["EffectIntent B resource scope"] -->|"project a canonical overlap relation"| V
    V -->|"scopes are disjoint"| P["Parallel execution may proceed"]
    V -->|"same scope with explicit commutativity proof"| P
    V -->|"overlap requires order"| S["Use an explicit dependency or transaction"]
    V -->|"relation is unknown"| F["Conservative serialization or fail closed"]
#+end_src

* Resource version observation

External version is represented as a content-addressed observation:

#+begin_src text
ResourceVersionObservationIdentity =
H(
  resource scope identity,
  authoritative version, ETag, digest, or sequence,
  observation protocol identity
)
#+end_src

When a plan depends on a version:

- the observation enters the semantic generation;
- the effect intent references the observation identity;
- version change changes the intent revision;
- commit revalidates the declared concurrency precondition.

The version must not exist only in mutable adapter memory.

* Concurrency precondition

A pure =ConcurrencyPrecondition= may declare:

- expected version;
- expected absence;
- expected digest;
- minimum or maximum sequence;
- compare-and-swap condition;
- transaction snapshot identity;
- explicit no-precondition policy and risk boundary.

The precondition enters effect-intent semantic projection.

An implicit:

#+begin_src text
observe once
then write later
#+end_src

does not provide concurrency safety.

* Atomic TOCTOU boundary

The safe sequence is:

#+begin_src text
stabilize intent
-> validate runtime capability
-> acquire transaction or lease if required
-> atomically validate precondition and commit
-> obtain authoritative receipt
#+end_src

If an adapter checks a version and later writes outside one atomic boundary, it cannot claim that the precondition protected the commit.

Required safety uses:

- adapter-supported compare-and-swap;
- transaction;
- lease with fencing;
- another adapter protocol with equivalent atomic evidence.

#+begin_src mermaid
flowchart LR
    O["ResourceVersionObservation"] -->|"derive an expected-version precondition"| P["Stable commit intent"]
    P -->|"submit a conditional commit"| A["Adapter atomic boundary"]
    A -->|"version still matches and commit succeeds"| C["Authoritative commit receipt"]
    A -->|"version changed before commit"| M["ConcurrentModificationDetected"]
    A -->|"adapter cannot enforce atomically"| F["AtomicPreconditionUnsupported"]
    M -->|"obtain a new observation artifact"| N["New semantic generation"]
#+end_src

* Optimistic concurrency

Optimistic mode uses authoritative version checks, compare-and-swap, or conditional update.

=ConcurrentModificationDetected= means that an external semantic input changed:

#+begin_src text
old intent invalid
-> observe current state
-> content-address the observation
-> derive a new semantic generation
-> recompute the intent
#+end_src

It is not an ordinary transport retry against the old intent.

* Pessimistic concurrency

Pessimistic mode uses a live lease or transaction handle:

- acquisition is operational;
- lease identity does not enter semantic result identity;
- lease scope remains within runtime capability scope;
- child context receives a lease only through explicit delegation;
- an expired lease cannot authorize commit;
- a receipt cannot revive a lease.

The lease protocol includes fencing when stale writers are possible.

* Fencing

Each lease acquisition may carry a monotonic fencing value. The adapter rejects a commit made with a fencing value older than the currently admitted value.

Without adapter-enforced fencing, lease expiry alone does not prove that an old holder cannot still write.

Fencing values and live lease handles are operational resources. Receipts may record redacted fencing evidence without turning it into future authority.

* Read and write relations

The baseline relations are:

- read/read :: Parallel execution may be safe; snapshot consistency remains a separate proof.
- read/write :: Requires snapshot or version policy.
- write/write :: Requires explicit order, commutativity proof, or transaction.
- append/append :: Parallel only when adapter semantics and invariants support it.
- commutative update :: Requires operation-level proof over the actual adapter protocol.
- exclusive commit :: Requires valid exclusive scope or transaction.

Mathematical commutativity of values is insufficient when notifications, billing, audit order, or other external effects are not commutative.

* Multi-resource commits

For multiple resources:

- atomicity is reported only when one transaction protocol covers all scopes;
- lock acquisition order may be an operational deadlock-avoidance policy;
- canonical identity order may be used for lock acquisition only when it does not alter business semantics;
- business commit order remains defined by explicit effect-DAG edges;
- deadlock retry is allowed only after proving that no effect committed;
- an in-doubt transaction enters reconciliation.

Operational lock order and semantic commit order are separate identities and receipts.

* Live lease and shared evaluation

Subscriber leases and capabilities are not unioned.

A shared worker:

- uses independently authorized minimum execution scope;
- does not borrow one subscriber's lease for another;
- preserves separate disclosure authorization;
- treats lease expiry as an execution event;
- may reuse an already pure result after new authorization.

* Failure taxonomy

The normative resource-concurrency failures include:

#+begin_src text
ResourceScopeProjectionFailure
ResourceConflictRelationUnknown
LeaseAcquisitionFailure
LeaseExpired
StaleFencingToken
ConcurrentModificationDetected
AtomicPreconditionUnsupported
DeadlockDetected
UnknownCommitOutcome
#+end_src

Ownership:

- scope projection is structural;
- unknown conflict relation may be plan conflict;
- lease and deadlock are operational;
- concurrent modification requires new observation and generation;
- unsupported atomic precondition fails closed before an unsafe commit;
- unknown outcome requires reconciliation.

* Cache and identity boundaries

Pure cacheable values include:

- resource-scope projection;
- conflict relation;
- version observation;
- concurrency precondition;
- commutativity or transaction proof;
- authoritative commit or reconciliation receipt.

Non-cacheable live resources include:

- capability token;
- lock and lease handle;
- transaction handle;
- connection;
- active fencing authority;
- worker state.

A cached scope or receipt does not grant resource authority.

* Evidence requirements

Resource-concurrency evidence records:

- resource-scope identity;
- access role;
- canonical overlap relation;
- version-observation identity;
- concurrency precondition;
- runtime-capability validation;
- lease acquisition, expiry, and fencing;
- atomic-precondition result;
- commit receipt;
- concurrent modification;
- deadlock or unknown outcome;
- successor observation and generation.

Live token, secret, connection, and lock handles are never serialized.

* Implementation checklist

- [ ] Define POO-native =ResourceScopeProjection=.
- [ ] Define extensible access-role prototypes and conflict relations.
- [ ] Require adapter-defined canonical resource overlap.
- [ ] Fail closed or conservatively serialize unknown relations.
- [ ] Define content-addressed =ResourceVersionObservation=.
- [ ] Define pure =ConcurrencyPrecondition=.
- [ ] Require atomic adapter enforcement for strong preconditions.
- [ ] Treat concurrent modification as new observation and generation input.
- [ ] Define live lease and transaction boundaries.
- [ ] Require adapter-enforced fencing where stale writers are possible.
- [ ] Separate operational lock order from semantic commit order.
- [ ] Report multi-resource atomicity only under one covering transaction protocol.
- [ ] Prevent subscriber capability and lease union.
- [ ] Enforce the normative failure taxonomy.
- [ ] Generate scope, version, precondition, lease, fencing, and commit evidence.
- [ ] Validate final resource operations against real adapter and =gerbil-poo= primitives.

* Non-goals

- Do not treat a resource-scope declaration as a live lock or authority.
- Do not infer overlap from string prefixes or display names.
- Do not call check-then-write TOCTOU-safe without an atomic adapter boundary.
- Do not retry concurrent modification as a transport failure.
- Do not claim lease safety without fencing where stale writers are possible.
- Do not conflate lock acquisition order with business commit order.
- Do not union subscriber leases or capabilities.
- Do not introduce a resource registry, lock DSL, or raw callback protocol.

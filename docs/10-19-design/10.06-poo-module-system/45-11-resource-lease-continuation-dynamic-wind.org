#+title: Resource Lease, Continuation, And Dynamic-Wind

* Normative responsibility

This module owns the POO Flow semantics for runtime-local resource leases across
first-class continuation capture, dynamic extent exit, re-entry, cancellation,
and realization-boundary termination.

It distinguishes:

1. the physical lease lifecycle governed by provider receipts;
2. the dynamic attachment of access authority governed by =dynamic-wind=.

These are orthogonal state spaces.  Entering or leaving a dynamic extent MUST
NOT implicitly repeat an external acquire or release operation.

* Ownership boundary: gerbil-poo mechanism and POO Flow governance

=gerbil-poo= owns generic POO identity, demand realization, suspension,
memoization, lineage, and continuation-aware control.

Gerbil Scheme owns the language semantics of first-class continuations,
continuable exceptions, and =dynamic-wind=.

POO Flow owns:

- the POO-native resource-provider capability contract;
- lease identity, policy, and realization-boundary scope;
- dynamic access-authority validation;
- cancellation and release governance;
- expired and indeterminate resource conditions;
- acquisition, release, reconciliation, and leak-diagnostic receipts.

Provider selection is defined by
[[file:45-10-provider-runtime-search-closure.org][Provider Runtime Search Closure]].  Runtime handoff is defined by
[[file:45-09-effect-intent-suspension-handoff-reinjection.org][Effect Intent, Suspension, Runtime Handoff, And Receipt Reinjection]].
Each external acquire, release, cancellation, or reconciliation operation obeys
[[file:45-08-effect-boundary-commit-reconciliation.org][Effect Boundary Commit And Reconciliation]].

* Runtime-local lease invariant

A runtime resource handle is always =context-bound=.  It MUST NOT appear in:

- a portable POO value;
- a realization evidence bundle;
- a cross-context admission receipt;
- a serialized continuation;
- an observability snapshot;
- a global resource registry.

Continuation capture may retain only context-local lease authority evidence.
It does not capture or serialize the raw handle.

* Physical lease lifecycle

The lease lifecycle is a resource-state projection derived from provider
operation receipts:

#+begin_src mermaid
stateDiagram-v2
  [*] --> Declared: qualified provider and lease declaration exist
  Declared --> Acquiring: authorized acquisition handoff
  Acquiring --> Active: acquisition receipt is verified
  Acquiring --> Failed: provider proves acquisition failure
  Acquiring --> Indeterminate: acquisition outcome cannot be proved

  Active --> Releasing: boundary terminates or cancellation authorizes release
  Releasing --> Released: release receipt is verified
  Releasing --> Indeterminate: release outcome cannot be proved

  Indeterminate --> Reconciling: provider proves reconciliation capability
  Reconciling --> Active: external state proves the lease active
  Reconciling --> Released: external state proves the lease released
  Reconciling --> Indeterminate: terminal proof remains unavailable
#+end_src

This lifecycle does not replace the 45-08 effect evidence state machine.
Acquisition, release, and reconciliation are separate provider operations, each
with their own operation and attempt evidence.  The lease lifecycle projects
their verified outcomes into resource availability.

A provider function returning normally is not acquisition or release proof.
Only a verifier-backed immutable receipt advances the lease to =active= or
=released=.

* Dynamic access attachment

=dynamic-wind= manages whether the current dynamic extent may access an active
lease.  Its before and after thunks operate on context-local access authority,
not on the external resource:

#+begin_src mermaid
stateDiagram-v2
  [*] --> Detached: no dynamic access authority installed
  Detached --> Attached: before thunk validates active lease and attaches authority
  Attached --> Detached: after thunk revokes local authority
  Detached --> ExpiredCondition: re-entry observes released lease
  Detached --> BarrierCondition: re-entry observes indeterminate or reconciling lease
  ExpiredCondition --> Detached: recovery defers or aborts
  ExpiredCondition --> Attached: policy authorizes and verifies replacement lease
  BarrierCondition --> Detached: recovery defers or aborts
  BarrierCondition --> Attached: reconciliation proves active lease
#+end_src

The before thunk:

- validates realization-context and boundary identity;
- checks the current lease evidence state;
- attaches a bounded dynamic access authority when the lease is active;
- raises a structured condition when the lease is released, indeterminate, or
  no longer belongs to the current context.

The after thunk:

- revokes the dynamic access authority;
- emits scope-exit evidence;
- does not release, cancel, or reacquire the physical resource.

The dynamic authority is not the resource handle.  Provider-specific access
remains behind the qualified POO capability boundary.

* Continuation capture, exit, and re-entry

Capturing a continuation inside an attached resource scope records the
continuation's context-local authority relationship.  It does not extend the
lease lifetime and does not prevent boundary-governed release.

When control exits the dynamic extent, =dynamic-wind= revokes local access.
The physical lease remains governed by its realization boundary.

When a captured continuation re-enters:

| Lease evidence | Re-entry result |
|---+---|
| =active= in the same context and boundary | validate and reattach dynamic access authority |
| =released= | raise a continuable expired-resource condition |
| =indeterminate= or =reconciling= | raise a continuable resource-barrier condition |
| belongs to another or invalidated context | reject re-entry for that resource authority |

Continuation re-entry MUST NOT:

- reacquire automatically;
- resurrect a released handle;
- repeat a committed acquisition;
- bypass cancellation or release policy;
- attach authority from another realization context.

* Expired-resource recovery

An expired-resource condition may expose only policy-authorized recovery:

- obtain a replacement through a new qualified acquisition operation;
- use a portable value or verified artifact that no longer requires the handle;
- defer;
- abort the declared realization boundary.

A replacement lease has a new lease identity and new acquisition operation
evidence.  It does not impersonate or revive the released lease.

There is no unconditional =reacquire= restart.

* Indeterminate-resource recovery

An indeterminate resource outcome is a barrier.  Automatic acquisition,
release, or retry is forbidden because the external resource state is unknown.

Recovery may:

- inspect bounded evidence;
- reconcile through a provider capability;
- defer while preserving the barrier;
- abort the declared realization boundary.

If reconciliation proves the lease active, dynamic access may be attached after
normal validation.  If it proves the lease released, the expired-resource
contract applies.

* Boundary termination and cancellation

Physical release is authorized by realization-boundary termination, explicit
resource policy, or boundary-scoped cancellation.  Exiting an arbitrary dynamic
extent is not sufficient authority.

#+begin_src mermaid
flowchart LR
  B["State: realization boundary terminating"] -->|"immutable release decision"| R["State: authorized release operation"]
  C["State: boundary cancellation requested"] -->|"request is not release proof"| R
  R -->|"45-08 provider operation"| P["State: release receipt candidate"]
  P -->|"verifier proves release"| X["State: lease released"]
  P -->|"outcome cannot be proved"| I["State: indeterminate resource barrier"]
  A["State: attached dynamic access scope"] -->|"dynamic-wind after revokes authority"| D["State: local access detached"]
  D -.->|"scope exit does not prove physical release"| X
#+end_src

Cancellation request, provider interruption, worker loss, and exception
propagation do not prove release.  Without terminal evidence, the lease becomes
indeterminate and requires reconciliation.

Boundary cancellation propagation, cleanup continuation generations, and the
proof required for clean cancellation are specified by
[[file:45-12-structured-cancellation-boundary-generations.org][Structured Cancellation And Boundary Generations]].  This module remains the
authority for physical lease and dynamic access state.

Bounded cleanup admission and resource-provider capacity follow
[[file:45-13-demand-admission-backpressure-cleanup-capacity.org][Demand Admission, Backpressure, And Cleanup Capacity]].  This module remains
the authority for release proof and dynamic access attachment.

* Nested boundaries and submodules

Each nested structural boundary owns its lease identities within its
containment scope.  The same local resource name under different parents does
not imply the same lease.

A child boundary may use a parent-provided resource capability only through
explicitly inherited POO capability space and policy authority.  Access does
not transfer physical lease ownership unless an explicit lease-sharing
capability and receipt establish that relationship.

An imported Mix dependency does not reparent a lease.  Containment and import
paths remain separately observable.

* Receipt contract

The resource receipt chain records:

- realization context and structural boundary;
- resource-provider capability and lease identity;
- acquisition, release, cancellation, and reconciliation operation evidence;
- physical lease-state transitions;
- dynamic access attach/detach events;
- continuation re-entry validation;
- policy authority and causal predecessor receipt.

#+begin_src mermaid
flowchart TD
  L["State: physical lease receipt"] -->|"resource-state projection"| S["State: declared, active, released, or indeterminate"]
  A["State: dynamic attachment receipt"] -->|"scope-local authority projection"| D["State: attached or detached"]
  C["State: continuation re-entry evidence"] -->|"validates both state spaces"| V["State: access allowed or structured condition"]
  S -->|"lease evidence gate"| V
  D -->|"dynamic authority gate"| V
  V -->|"ordered causal link"| R["State: recovery or access receipt"]
#+end_src

Observability may expose bounded evidence from both state spaces.  It cannot
attach authority, release a resource, resume a continuation, or reconcile an
indeterminate lease.

* Finalizers and leak diagnostics

Finalizers are diagnostic fallbacks only.  Correct release MUST NOT depend on
garbage collection timing or finalizer execution.

If a finalizer observes an unreleased lease, it may:

- emit a leak diagnostic;
- request policy-governed cleanup through the normal provider boundary;
- preserve indeterminate evidence when cleanup outcome cannot be proved.

It MUST NOT silently claim release or mutate an immutable receipt chain.

Replay verifies historical lease receipts according to
[[file:45-14-deterministic-realization-replay.org][Deterministic Realization Replay]].  It never recreates or reattaches a source
runtime handle, lease, or dynamic access authority.

Lease and dynamic-access receipts use the identity, projection, verifier, and
redaction semantics defined by
[[file:45-15-receipt-object-canonical-evidence-projection.org][Receipt Object And Canonical Evidence Projection]].

* API evidence gate

The semantics in this module are normative.  Exact macros, slots, condition
names, and =dynamic-wind= helpers remain =semantic-required= until the relevant
=gerbil-poo= and Gerbil behavior is symbol-located, behavior-proven, and
flow-qualified.

Any generally reusable continuation-aware lease mechanism belongs upstream in
=gerbil-poo=.  POO Flow MUST NOT ship a shadow continuation runtime, fallback
resource evaluator, or private replacement for Scheme =dynamic-wind=.

* Explicit exclusions

This RFC does not authorize:

- acquire or release directly inside =dynamic-wind= before/after thunks;
- automatic reacquisition on continuation re-entry;
- resurrection of a released handle;
- automatic retry of an indeterminate acquire or release;
- release correctness based on finalizers;
- cross-context serialization of handles or lease authority;
- a global resource registry;
- implicit lease ownership transfer through Mix imports;
- a new public resource DSL before the real API is behavior-proven.

* Status

This document is the formal companion of the approved POO module-system RFC
cluster.  It records the mathematical types, machine-checked theorems,
verification receipts, and proof gaps without redefining the public Scheme
interface.

The initial proof baseline is implemented in Lean 4.31.0 and independently
checked by AXLE in the Lean 4.31.0 environment.

This is a proof-obligation RFC, not an implementation plan and not a
compatibility or migration document.

The execution programme is maintained separately in
[[../../90-99-operations/90.03-rfc-proof-verification-and-gap-closure-plan.org][RFC Proof Verification And Gap Closure Plan]].

* Effect-boundary atomic arbitration proof checkpoint

The final =EffectBoundary.lean= model distinguishes the abstract safety theorem
from concrete runtime qualification.

| Lean declaration | Machine-checked result |
|-
| =sameSnapshotDoubleCommitCounterexample= | Two distinct raw commits may be derived from the same =in-flight= snapshot when no atomic arbiter is present. |
| =repeatedReceiptIsIdempotent= | Repeating the same receipt produces =duplicate= and preserves the committed cell. |
| =conflictingReceiptCannotOverwrite= | Different terminal evidence for the same operation and attempt cannot replace the existing commit. |
| =arbitrationNeverOverwritesCommitted= | Every admissible arbitration beginning from =committed= preserves that receipt. |
| =acceptedCommitCannotBeAcceptedAgain= | No second =accepted= transition follows an accepted commit. |
| =runtimeArbitrationReceiptProvidesLinearization= | A concrete receipt that carries the refinement witness supplies an =AtomicCommitArbitration= linearization point. |
| =acceptedRuntimeReceiptCommitsProposal= | An accepted runtime receipt ends in the proposed committed receipt. |
| =duplicateRuntimeReceiptPreservesCommittedState= | A duplicate runtime receipt preserves the existing committed state. |
| =conflictingRuntimeReceiptCannotOverwrite= | A conflicting runtime receipt cannot overwrite the existing committed state. |
| =failedRetryPreservesCausalLink= | Retry from =failed= preserves operation identity, references the prior attempt, creates a fresh attempt, and enters that attempt. |
| =cancelledRetryPreservesCausalLink= | Restart from =cancelled= preserves operation identity, references the cancelled attempt, creates a fresh attempt, and enters that attempt. |
| =indeterminateRetryRequiresPriorReconciliation= | Any trace from =indeterminate= that later contains retry starts with a provider reconciliation request. |
| =reconciliationNoCommitEnablesFreshRetry= | A reconciliation proof of no commit permits the policy-authorized fresh retry path. |

** Retry causal linkage and reconciliation barrier

=EFF-006= is the structural retry-causality proposition:

#+begin_src typst
#let EFF_006(operation, prior, authorization, target) = (
  authorization.operation == operation
  and authorization.prior_attempt == prior
  and authorization.next_attempt != prior
  and target == in_flight(operation, authorization.next_attempt)
)
#+end_src

It applies independently to retry from =failed= and restart from =cancelled=.
The operation/boundary identity remains stable while the attempt identity is
fresh.

=EFF-007= is the reconciliation-barrier proposition:

#+begin_src typst
#let EFF_007(operation, attempt, events, authorization) = (
  policy_retry(authorization) in events
  and trace(indeterminate(operation, attempt), events)
) implies (
  exists(capability, remaining,
    events == (
      request_reconciliation(capability),
      ..remaining,
    )
    and policy_retry(authorization) in remaining
  )
)
#+end_src

#+begin_src mermaid
stateDiagram-v2
  Failed --> RetryAuthorization: policy evidence names prior attempt
  Cancelled --> RetryAuthorization: restart evidence names prior attempt
  RetryAuthorization --> InFlight: same operation / fresh attempt
  Indeterminate --> Reconciling: provider reconciliation required first
  Reconciling --> Failed: reconciliation proves no commit
  Failed --> InFlight: authorized fresh retry
  Reconciling --> Indeterminate: unknown / retry remains forbidden
  Reconciling --> Committed: commit proved / retry remains forbidden
#+end_src

The four theorems establish the identity linkage, freshness, forbidden direct
path, and permitted no-commit path. They do not establish that
=RetryAuthorization.policyEvidence= was issued by an authorized recovery-policy
object. Policy-evidence provenance remains a separate open correspondence
obligation and MUST NOT be inferred from the presence of a numeric evidence
field in the Lean carrier.

** Four-layer recovery authorization model

The approved internal model distinguishes:

#+begin_src typst
#let RecoveryAuthorizationModel = (
  policy: RecoveryPolicy,
  decision: RecoveryDecision,
  receipt: RecoveryDecisionReceipt,
  capability: RetryCapability,
)
#+end_src

The construction chain is:

#+begin_src typst
#let decide(policy, condition, restarts, observation) = decision

#let commit(cell, decision) = receipt

#let project_retry(receipt, token) = capability

#let consume(effect_boundary, capability) = fresh_attempt
#+end_src

subject to:

#+begin_src typst
#let ValidRetryCapability(receipt, capability) = (
  receipt.outcome == committed
  and receipt.selected_decision.permits_retry
  and capability.receipt_identity == receipt.identity
  and capability.operation == receipt.operation
  and capability.prior_attempt == receipt.prior_attempt
  and capability.next_attempt != receipt.prior_attempt
  and capability.token.single_use
  and capability.token.runtime_local
)
#+end_src

The authority separation theorem obligations are:

#+begin_src typst
#let ReceiptCannotRetry = forall(receipt,
  not has_retry_authority(receipt)
)

#let ObservationCannotRetry = forall(observation,
  not has_retry_authority(observation)
)

#let CapabilityAtMostOnce = forall(capability,
  successful_consumptions(capability) <= 1
)
#+end_src

The current Lean =PolicyAuthorizedRetry= is the proof-facing product of
authorization data and recovery receipt refinement. It corresponds to the
evidence portion of =RetryCapability=. The opaque one-shot runtime token and its
atomic consumption remain separate proof obligations; they MUST NOT be modeled
as a serializable receipt field.

** Recovery-policy authorization projection

The raw field counterexample is:

#+begin_src typst
#let bare_policy_evidence_insufficient = (
  exists(left, right,
    left.policy_evidence == right.policy_evidence
    and left.policy_root != right.policy_root
  )
)
#+end_src

Therefore policy authority is represented by a proof-carrying product:

#+begin_src typst
#let PolicyAuthorizedRetry = (
  authorization: RetryAuthorization,
  receipt: RecoveryDecisionReceipt,
  refinement: (
    authorization.operation == receipt.operation
    and authorization.prior_attempt == receipt.prior_attempt
    and authorization.next_attempt == receipt.next_attempt
    and authorization.policy_evidence == receipt.policy_evidence
    and receipt.next_attempt != receipt.prior_attempt
  ),
)
#+end_src

*** Typst--Lean--AXLE synchronization contract

The earlier statement that token semantics remained open described the
pre-synchronization proof state. Local Lean now models the token-bearing
capability and its abstract single-use transition. The token remains a
runtime-local proof carrier and MUST NOT become a serializable receipt field.
Scheme/runtime correspondence and AXLE modular verification remain separate
gates.

The Typst model is not an explanatory shadow of the Lean source. Every named
Typst object below MUST map to one exact Lean declaration, and each proof claim
MUST report local Lean and AXLE status independently.

The synchronization rule is bidirectional:

- a Lean declaration or theorem that changes the recovery authorization model
  MUST update the corresponding Typst object or proposition in the same proof
  tranche;
- a Typst proposition has no =proven= status until an exact Lean declaration
  exists and the pinned local Lean kernel accepts it;
- local Lean acceptance MUST NOT be promoted to AXLE acceptance while the
  verifier cannot resolve the project-local import graph;
- Scheme/runtime qualification MUST bind its object and transition evidence to
  these exact names rather than to an informal analogue.

* Formal universe

Let:

#+begin_src typst
$

& R := "RuntimeRoot" \
& C := "ContentIdentity" \
& X := "RealizationContext" \
& Q := "DemandCoordinate"
$
#+end_src

The current Lean model represents opaque identities with small carrier types
such as =Nat=.  The carrier is not the production representation.  The
theorems depend on separation and equality properties, not on numeric
identity.

* Composition identity model

** Product type

A composition identity is a product of three independent projections:

#+begin_src typst
$
"Identity" := L times R times C
$
#+end_src

For

#+begin_src typst
$
i = (ell, r, c)
$
#+end_src

rename changes only the lexical projection:

#+begin_src typst
$
rho(i, ell') := (ell', r, c)
$
#+end_src

Therefore:

#+begin_src typst
$
pi_R(rho(i, ell')) = pi_R(i)
$
#+end_src

and

#+begin_src typst
$
pi_C(rho(i, ell')) = pi_C(i)
$
#+end_src

The demand-cell key is:

#+begin_src typst
$
"DemandKey"(x, i, q)
  := (x, pi_R(i), q)
  in X times R times Q
$
#+end_src

It follows that rename preserves the demand-cell key:

#+begin_src typst
$
"DemandKey"(x, rho(i, ell'), q)
  = "DemandKey"(x, i, q)
$
#+end_src

** Content identity does not imply runtime identity

The model constructs a witness for:

#+begin_src typst
$
exists i_1, i_2.
  pi_C(i_1) = pi_C(i_2)
  and
  pi_R(i_1) != pi_R(i_2)
$
#+end_src

This proves that equal content evidence cannot identify two runtime POO roots.

** Derived composition

For parent identity =i= and fresh runtime root =r'=, derivation returns:

#+begin_src typst
$
"derive"(i, r', "orderedRefinements", c', v, m)
  = (i', "receipt")
$
#+end_src

where:

#+begin_src typst
$
pi_R(i') = r'
$
#+end_src

and:

#+begin_src typst
$
"receipt.parentRoot" = pi_R(i)
$
#+end_src

The ordered refinement sequence, dependency revision, and lowering evidence
remain explicit receipt fields.

The fresh-root theorem currently assumes:

#+begin_src typst
$
r' != pi_R(i)
$
#+end_src

Root-allocation freshness itself remains an open proof obligation.

* Realization admission model

** Disposition sum type

The disposition type is the disjoint sum:

#+begin_src typst
$
"Disposition"
  := "pureValue"
   | "artifactBacked"
   | "contextBound"
   | "suspendedOrUncommitted"
$
#+end_src

Admission evidence is a product of propositions:

#+begin_src typst
$
e := (C, L, D, P, V, A, B)
$
#+end_src

where:

- =C=: content identity matches;
- =L=: lowering evidence matches;
- =D=: resolved dependency evidence matches;
- =P=: policy identity matches;
- =V=: portable value evidence exists;
- =A=: artifact verifier evidence exists;
- \(B\): no unresolved barrier exists.

Eligibility has exactly two constructors:

#+begin_src typst
$
C and L and D and P and V and B
  => "Eligible"("pureValue", e)
$
#+end_src

and:

#+begin_src typst
$
C and L and D and P and A and B
  => "Eligible"("artifactBacked", e)
$
#+end_src

There is no constructor for =contextBound= or
=suspendedOrUncommitted=.  Their non-admissibility follows by empty-constructor
elimination rather than by a runtime Boolean convention.

** Portable payload relation

Portable payload is:

#+begin_src typst
$
"Payload"
  := "valueContent"(c)
   | "artifactReference"(a, v)
$
#+end_src

Eligibility alone is insufficient because it does not relate the disposition
to the payload.  The proof model therefore defines the dependent relation:

#+begin_src typst
$
"PayloadCompatible"
  : "Disposition" -> "Payload" -> "Prop"
$
#+end_src

with only:

#+begin_src typst
$
"PayloadCompatible"("pureValue", "valueContent"(c))
$
#+end_src

and:

#+begin_src typst
$
"PayloadCompatible"("artifactBacked", "artifactReference"(a, v))
$
#+end_src

This relation closes a gap discovered during formalization: without it, an
eligible =pure-value= result could carry an artifact payload, or vice versa.

** Receiving context separation

An admitted result contains:

#+begin_src typst
$
("disposition", e, r_s, r_n, p,
  "Eligible", "PayloadCompatible", r_s != r_n)
$
#+end_src

Thus admission preserves evidence while requiring a receiving root distinct
from the source root.  It never restores or equates the source POO object.

* Effect-boundary transition system

** State and event types

Let:

#+begin_src typst

#+begin_src typst

=CommitReceipt= carries operation identity, attempt identity, and verifier

* EFF-005C concurrent snapshot counterexample

The finite-trace theorem does not by itself prove that a concurrent runtime
execution is linearizable.  The current transition relation admits the
following witness.

#+begin_src typst
$
& s := "InFlight"(11, 5) \
& r_L := "CommitReceipt"(11, 5, 1) \
& r_R := "CommitReceipt"(11, 5, 2) \
& r_L != r_R \
& "Step"(s, "verifiedCommit"(r_L), "Committed"(r_L)) \
& "Step"(s, "verifiedCommit"(r_R), "Committed"(r_R))
$
#+end_src

Both transitions are individually valid because the current commit rule checks
operation and attempt identity but contains no atomic arbitration witness and
no theorem that the verifier can issue only one receipt.

#+begin_src mermaid
flowchart LR
  S["State: shared InFlight(operation 11, attempt 5) snapshot"] -->|"thread L validates receipt with verifier evidence 1"| L["Candidate: commit receipt L"]
  S -->|"thread R validates receipt with verifier evidence 2"| R["Candidate: commit receipt R"]
  L -->|"current Step.commit premises pass"| CL["State: Committed(receipt L)"]
  R -->|"current Step.commit premises pass"| CR["State: Committed(receipt R)"]
  CL -.->|"cannot coexist in one valid finite Trace; arbitration premise missing"| CR
#+end_src

The unconditional claim “all concurrent executions accept at most one commit”
is therefore false in the current model.  The conditional theorem is proven:

#+begin_src typst
$
"LinearizableExecution"(x)
  => "commitCount"(x."events") <= 1
$
#+end_src

The counterexample was classified as =missing-premise= with architecture
impact.  The owning =45-08= discussion approved the combined rule:

1. =gerbil-poo= remains the sole Scheme POO implementation;
2. the provider owns external idempotency, terminal proof, and reconciliation;
3. the POO Flow effect-boundary prototype owns atomic terminal-state
   acceptance and conflict governance;
4. an explicit runtime substrate performs the requested atomic
   compare-and-transition without becoming another POO library.

The formal counterexample remains valid for raw, unarbitrated commit proposals
and is retained as a negative proof.  =AtomicCommitArbitration= closes the
model-level gap.  Runtime linearizability and provider-evidence correspondence
remain open, so operational at-most-once qualification is not yet claimed.

* Proof boundary

The accepted theorems establish properties of the formal model.  They do not
yet prove that:

- Gerbil macro lowering implements the modeled constructors;
- =gerbil-poo= runtime roots satisfy the modeled identity laws;
- runtime/provider receipts inhabit the modeled evidence types;
- the Scheme, C, or Python runtimes refine the Lean transition relation.

Those claims require explicit correspondence theorems and generated/runtime
evidence.  They MUST NOT be inferred merely from a green Lean build.

* Current conclusion

The first formal slice supports the approved architectural direction:

1. lexical rename is observational with respect to runtime identity and demand
   keys;
2. content identity cannot stand in for runtime POO identity;
3. only portable dispositions can construct admission evidence;
4. admission creates a distinct receiving root;
5. function return cannot establish effect commit;
6. indeterminate effects require reconciliation capability;
7. committed continuation re-entry preserves the original receipt;
8. every valid finite trace accepts at most one commit event.

The largest remaining risk is no longer the shape of these local invariants.
It is the unproved correspondence from hygienic Scheme macro expansion and
=gerbil-poo= runtime behavior to the Lean constructors and evidence types.

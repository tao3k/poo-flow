This section refines G0 in the qualification matrix.  Dependency declaration,
source materialization, runtime consumption, and an ambient development
checkout are different identities and MUST NOT be collapsed into one
successful import observation.

The word =closure= names three different contracts and MUST NOT erase their
owner boundaries:

| Closure kind              | Owner                                  | Meaning                                                       |
|---------------------------+----------------------------------------+---------------------------------------------------------------|
| build artifact closure    | selected build/materialization backend | artifacts required by one reproducible build or test action   |
| Gerbil module-load closure | Gerbil module system and runtime loader | modules traversed and resolved by Gerbil import semantics      |

Gerbil-Bazel is the build backend used by the 2026-07-25 G0 observation.  It
is replaceable by another evidence-producing backend without changing
=clan/poo= or POO Flow semantics.  Its =GerbilProjectInfo= provider is a build
projection, not a POO object and not a semantic module-system interface.

POO Flow owns the backend-neutral G0 requirement, runtime-import observation
receipt, mismatch rejection, and final decision.  GSLPH remains a dependency
from which POO Flow uses harness policy and building/testing framework
capabilities.  GSLPH does not own the receipt schema, runtime closure,
semantic requirement, or G0 decision and MUST NOT appear as their durable
owner.

*** Shared evidence notation

| Name | Meaning | Owner |
|------+---------+-------|
| =R= | =DependencyQualificationRequirement= | POO Flow |
| =M= | =ModuleImportObservation= digest reference | POO Flow |
| =D= | =DependencyQualificationDecisionReceipt= | POO Flow |

Every matrix case starts from a syntactically valid, schema-valid evidence
envelope containing =R= and =M= under the selected =QualificationPolicy=. A
missing digest, an unreadable object, a schema mismatch, a stale reference, or
inconsistent identity is an input-envelope failure and MUST NOT produce =D=.

*** Pure POO decision cases

These cases invoke no Gerbil loader, build tool, filesystem discovery, or
ambient package registry. Each case supplies immutable POO objects to the same
pure decision function.

| ID | Evidence mutation relative to canonical pass | Expected decision | Produce =D= |
|----+----------------------------------------------+-------------------+-------------|
| P0 | =R/M= agree on provider package, modules, bindings, and shapes | =pass= | yes |
| P1 | =M= records that the required Gerbil module cannot be resolved | =module-not-found= | yes |
| P2 | the selected module lacks one binding required by =R= | =required-binding-missing= | yes |
| P3 | every binding exists, but one required shape predicate fails | =required-binding-shape-mismatch= | yes |

When more than one *compatible* failure condition is present, the previously
defined deterministic rejection precedence selects exactly one reason code.
Precedence fixtures are parameterizations of P1--P3 and do not increase
=G0_REQUIRED_PURE_DECISION_CASES=. Logically impossible observation states MUST
remain invalid evidence envelopes; they MUST NOT be manufactured merely to
obtain every mathematical pair of reason codes.

*** Rejection precedence fixture family

The rejection order is an evaluation-stage order, not permission to place
contradictory facts in =M=. For example, =module-not-found= cannot coexist with
an observation claiming that a binding in that module was inspected and had an
incompatible shape.

The required family therefore contains:

- =G0_REQUIRED_PRECEDENCE_BOUNDARY_CASES=2=: one valid fixture for every
  adjacent boundary in the three-reason order;
- =G0_REQUIRED_PRECEDENCE_SENTINEL_CASES=1=: one valid fixture in which the
  earliest failing stage is combined with requirements and sentinels that
  would fail at every downstream stage if evaluation reached them.

An adjacent-boundary fixture proves that the higher stage dominates the next
stage without falsifying observation history:

| Boundary | Higher-stage condition | Lower-stage condition or sentinel | Expected reason |
|----------+------------------------+-----------------------------------+-----------------|
| B1 | required module does not resolve | a not-evaluated sentinel would inspect bindings only after successful import | =module-not-found= |
| B2 | one required binding is absent | a different existing binding fails its required shape predicate | =required-binding-missing= |

For B1, the lower-stage value is a sentinel describing what would be tested
only after the higher gate succeeds; it MUST NOT be serialized as a false claim
that the lower observation already occurred. A not-evaluated sentinel is a
harness assertion, not a field of =M=, not a qualification-domain object, and
not a public API. The pure fixture builder must preserve that distinction.

The sentinel fixture combines the P1 module-not-found result with downstream
requirements/sentinels derived from P2--P3 and MUST yield
=module-not-found=. It proves whole-pipeline short-circuiting without
creating an internally inconsistent =ModuleImportObservation=.

The G0 release execution gate is therefore:

- semantic decisions: =4/4=;
- adjacent precedence boundaries: =2/2=;
- whole-pipeline sentinel: =1/1=;
- isolated Gerbil live witnesses: =4/4=.

This is 11 required execution instances over 8 named semantic/live cases. The
extra three instances validate precedence only; they introduce no new reason
code, semantic case, public object, or public macro.

*** Isolated Gerbil live witnesses

Live witnesses test only the boundary between the Gerbil module system and
=ModuleImportObservation=. They MUST NOT directly emit =D= and MUST NOT invoke
Gerbil-Bazel to rebuild an artifact.

| ID | Isolated loader input | Required observation | Expected pure decision after observation |
|----+-----------------------+----------------------+------------------------------------------|
| L0 | normal Gerbil module import for =:clan/poo/proto= | exact semantic identity, module, required bindings, and valid shapes | =pass= |
| L1 | required Gerbil module cannot be resolved | exact unresolved direct/transitive module identity | =module-not-found= |

L1 must record the missing direct/transitive module identity rather than
collapsing it into a generic process failure.

** G0 evidence identity, canonical digest, and freshness

G0 evidence is content-addressed. Freshness is a relation between immutable
evidence and the qualification context in which it is being considered; it is
not a mutable status stored back into a receipt.

*** Ownership of digest production

- POO Flow owns canonicalization for the four POO Flow semantic roots:
  =DependencyQualificationRequirement=, =ModuleImportObservation=, the
  qualification policy value, and =DependencyQualificationDecisionReceipt=.
- Package-manager metadata, Gerbil-Bazel receipts, and source-resolution
  receipts remain outside the semantic envelope. POO Flow does not project,
  wrap, or require them to decide import/capability qualification.

*** Canonical POO Flow semantic bytes

For G0, POO Flow-owned semantic digests use =sha256:= over the UTF-8 bytes of a
canonical S-expression projection. The projection is a pure value and contains
only schema-declared semantic slots.

Canonicalization MUST obey all of the following:

- schema identity and schema version are the first two projected values;
- slot names are ordered by their UTF-8 byte sequence, never by construction or
  hash-table iteration order;
- strings are UTF-8 NFC; booleans, exact integers, symbols, byte strings, lists,
  and vectors have distinct tagged encodings;
- ordered collections preserve order; semantic sets are sorted by the canonical
  bytes of their members;
- absent, explicit false, empty collection, and empty string remain distinct;
- nested POO objects are projected recursively by their declared schema;
- prototype identity, procedure identity, allocation address, hash-table order,
  cwd, wall-clock time, mtime, and host environment are excluded;
- an artifact location is encoded as an attested logical root identity plus a
  normalized relative POSIX path; an absolute host path is diagnostic only and
  excluded from semantic identity;
- unknown slots are rejected rather than silently dropped or included.

Two semantically equal POO values MUST produce identical canonical bytes and
digest across processes and hosts. A schema-version change MUST change the
canonical bytes even when all remaining slot values are equal.

*** Canonical byte grammar

The canonical form is a length-framed S-expression, not Gerbil source text and
not the implementation-dependent output of =write=. A document contains
exactly one =value=, with no BOM, leading/trailing whitespace, or final newline.

#+begin_example
value   = absent / boolean / integer / symbol / string / bytes
        / list / vector / set / object

absent  = "(A)"
false   = "(B0)"
true    = "(B1)"
integer = "(I" canonical-signed-decimal ")"
symbol  = "(Y" utf8-byte-count ":" nfc-utf8-bytes ")"
string  = "(S" utf8-byte-count ":" nfc-utf8-bytes ")"
bytes   = "(X" raw-byte-count ":" raw-bytes ")"
list    = "(L" element-count ":" value... ")"
vector  = "(V" element-count ":" value... ")"
set     = "(E" element-count ":" value... ")"
object  = "(O" schema-symbol schema-version slot-count ":" slot... ")"
slot    = "(P" slot-name-symbol value ")"
#+end_example

All grammar punctuation and decimal counts are ASCII. Counts are unsigned base
10 with no leading zero except =0=. Exact integers use base 10, no leading =+=,
no leading zero, and =0= rather than =-0=. A length counts payload bytes, not
Unicode scalar values or grapheme clusters.

=schema-symbol= and =slot-name-symbol= use the =symbol= production.
=schema-version= uses a non-negative =integer=. Slot pairs are sorted by the
UTF-8 bytes of the normalized slot name, and duplicate slot names are invalid.
Every slot declared by the schema is encoded exactly once; an optional slot
without a value is encoded with =absent= rather than omitted.

List and vector elements retain semantic order. Set members are sorted by their
complete canonical byte strings using unsigned lexicographic byte ordering;
duplicate canonical members are invalid. Raw byte payloads are not escaped:
their explicit byte count determines where the payload ends.

The decoder MUST consume the complete document and MUST reject:

- a count that does not match the number or byte length of encoded values;
- a non-canonical decimal spelling;
- non-NFC symbol or string payloads;
- an unknown type tag;
- trailing bytes;
- duplicate or incorrectly ordered object slots or set members;
- a POO object slot that is absent from its declared schema;
- a declared schema slot that is missing from the object projection.

*** Qualification policy identity

The pure decision semantics are themselves an input. G0 names the initial
policy =poo-flow.g0-qualification-policy.v1= and computes its digest using the
same POO Flow canonical rules.

=DependencyQualificationDecisionReceipt= therefore includes:

- =qualificationPolicyId=;
- =qualificationPolicyDigest=;
- =requirementDigest=;
- =moduleObservationDigest=;
- =decision=;
- =reasonCode=.

This eight-field list is the normative complete G0 identity projection. Any
abbreviated field summary elsewhere in this RFC that omits
=qualificationPolicyId= or =qualificationPolicyDigest= is non-normative and
MUST NOT define receipt identity.

Without policy identity, the same requirement and observation digests could incorrectly reuse
an old decision after the decision rules change. The policy digest describes
the pure semantic policy value, not a Gerbil-Bazel binary, test harness, source
checkout path, or GSLPH implementation artifact.

*** Freshness relation

Let the qualification context be the exact tuple

#+begin_example
(policy-digest
 requirement-digest
 module-observation-digest)
#+end_example

A decision receipt is =current= only when all three references exactly match the
context and every referenced artifact is content-authenticated by its tagged
digest.

#+begin_src mermaid
stateDiagram-v2
  [*] --> Current: all references authenticate and match context
  Current --> Superseded: current context selects a different valid digest
  [*] --> Unresolvable: referenced artifact is unavailable
  [*] --> Invalid: bytes, schema identity, or digest do not authenticate
#+end_src

The states have distinct meanings:

| State | Meaning | May reuse decision? |
|-------+---------+---------------------|
| =current= | all referenced immutable evidence authenticates and equals the active context | yes |
| =superseded= | receipt is valid for an older context, but at least one active context digest differs | no |
| =unresolvable= | a referenced immutable artifact cannot currently be obtained | no |
| =invalid= | retrieved bytes do not authenticate, schema identity is wrong, or internal reference identities conflict | no |

=superseded= does not mean corrupt. The old receipt remains valid historical
evidence for its original input tuple. =unresolvable= also does not authorize
rebuilding or substituting evidence under the same digest.

*** What freshness is not

Freshness MUST NOT depend on:

- wall-clock age or a TTL;
- filesystem mtime;
- whether a checkout happens to be the newest branch head;
- the currently active ambient =gxpkg= installation;
- the most recently built Gerbil-Bazel output;
- the time order in which receipts were discovered.

A newer failing receipt does not invalidate an older passing receipt as
historical evidence. It only becomes the current qualification input when the
caller explicitly selects its digest in the active context.

*** Observation binding

=ModuleImportObservation= MUST bind to:

- the requirement digest whose imports and binding shapes were observed;
- the observed provider identity, module identity, artifact digest, bindings,
  and shape-predicate results;
- its own observation schema identity and version.

An observation created for a different requirement is not fresh for the active
context. It cannot be “refreshed” by editing metadata; the loader must produce
a new immutable observation.

*** Invalid envelope versus superseded decision

These conditions are evaluated before qualification:

| Condition | Classification | Produce a new decision receipt? |
|-----------+----------------+---------------------------------|
| referenced bytes authenticate but context selects a different digest | superseded prior decision | no; evaluate the selected context instead |
| referenced artifact is unavailable | unresolvable envelope | no |
| digest mismatch or wrong schema identity | invalid envelope | no |
| internal receipt references disagree | invalid envelope | no |
| all references authenticate and match, but qualification finds a semantic failure | valid envelope with rejection decision | yes |

Thus freshness checking never manufactures a semantic reason code such as
=source-identity-mismatch=. Envelope authentication/classification happens
first; only a valid current envelope enters the pure qualification policy.

** G0 normative root schema projections

G0 has exactly four independently addressable POO semantic roots:

1. =DependencyQualificationRequirement=;
2. =ModuleImportObservation=;
3. =QualificationPolicy=;
4. =DependencyQualificationDecisionReceipt=.

Identity, import, binding, capability, artifact-root, provider, and result values
below are closed nested POO projections. They have schema identities so that
canonicalization is total, but they have no independent lifecycle, receipt,
digest reference, loader entry point, or public user interface.

*** Common projection rules

- Every root and nested projection is a pure Gerbil POO object.
- Tables in this section specify canonical slots, not an alist, record, JSON
  schema, constructor argument list, or public DSL.
- The canonical slot set is closed. Prototype methods and cached/diagnostic
  slots may exist at runtime but are excluded from the semantic projection.
- A slot marked =required= appears exactly once. An =optional= slot also appears
  exactly once and uses canonical =absent= when no value exists.
- =set<T>= means canonical byte-sorted semantic set. =vector<T>= means ordered
  semantic sequence.
- A =digest-ref<schema>= is an algorithm-tagged digest string whose field
  contract fixes the referenced schema. It is not a generic reference object.

*** Runtime transaction

The runtime transaction is:

1. POO Flow receives a =DependencyQualificationRequirement=;
2. the POO Flow-owned probe invokes the Gerbil module system;
3. the probe normalizes the result through an internal
   =ModuleImportObservation= constructor;
4. the pure =QualificationPolicy= consumes Requirement plus Observation;
5. POO Flow produces =DependencyQualificationDecisionReceipt=.

No GSLPH process, execution record, receipt, callback, or service participates
in this transaction. Gerbil-Bazel may build runtime artifacts but has no
semantic role.

*** Internal Observation constructor authority

=ModuleImportObservation= remains a POO-native pure object, but its ordinary
constructor is internal to the POO Flow probe boundary. Runtime callers provide
a Requirement; they do not provide an arbitrary Observation or Decision.

The internal constructor:

- binds the exact =requirementDigest=;
- records module resolution status;
- records required binding lookup status;
- records named shape results;
- applies canonical normalization before the pure decision.

This is module encapsulation, not a cryptographic signature or external
attestation service. Content addressing proves semantic equality and supports
golden tests; constructor ownership establishes the runtime data flow.

*** Runtime failure boundary

Expected Gerbil conditions produce normal semantic observations:

- module import failure becomes =module-not-found=;
- missing binding becomes =required-binding-missing=;
- a named shape predicate returning false becomes
  =required-binding-shape-mismatch=.

Unexpected Scheme conditions, canonicalization failures, or internal invariant
violations abort the qualification transaction and produce no Decision receipt.
They are not converted into semantic rejection reasons.

Continuable exceptions or named restarts may be used inside the POO Flow probe
to collect independent binding results. Continuations, exception objects,
procedure identities, stack frames, and restart closures never enter canonical
Observation bytes.

*** Expected versus runtime-produced values

The RFC vectors are expected canonical values. At runtime, POO Flow constructs
the Observation directly from the Gerbil module result and immediately feeds it
to the pure policy in the same qualification transaction.

A runtime-produced Observation is not “authenticated by GSLPH”. There is no
=live-qualified= state, GSLPH stdout digest gate, or external execution
attestation prerequisite. A current Decision means it was produced through the
POO Flow runtime transaction over the current Requirement, Policy, and internal
Observation.

*** Initialization ownership

POO Flow core owns exactly one internal initialization cell for the G0
requirement/policy identity. The cell is not part of the public composition
syntax.

| State | Meaning |
|-------+---------|
| =uninitialized= | no qualification transaction has started |
| =evaluating= | the internal probe/policy transaction is in progress |
| =ready= | a current pass Decision and qualified capability object exist |
| =failed= | initialization produced a semantic rejection or unexpected failure |

The cell prevents duplicate work and gives recursion/observability code one
stable state to inspect. It is a POO Flow lifecycle cell, not a new fixed-point
implementation; clan/poo continues to own prototype/fixed-point semantics.

*** Eager, once-per-identity rule

Initialization runs once for the exact tuple

#+begin_example

#+end_example

Changing Requirement or Policy identity selects a different initialization
cell; it does not mutate or “refresh” the old one.

- constructing an individual Mix;
- selecting a Profile;
- invoking =use-composition=;
- composing a downstream submodule;
- loading the child =wendao-episteme= package;
- running a GSLPH test.

- Profiles remain POO objects under =profiles=;

Downstream modules import POO Flow core and receive the same initialized
capability object through the parent module boundary. A child may add its own
Profile/Mix objects, but it does not:

- re-import and requalify clan/poo independently;
- repeat G0 fixtures;
- own the initialization cell;
- depend on GSLPH at runtime;
- construct another Decision receipt for the same Requirement/Policy identity.

This is the initial-time integration benefit: the downstream module system sees
one stable, already-qualified parent capability rather than an initialization
protocol that each child must reproduce.

*** Failure and recovery

A =failed= cell is observable and immutable for its Requirement/Policy tuple.
POO Flow emits a structured Scheme condition containing the semantic reason and
the relevant root digests.

Named continuable recovery may:

- inspect the failed cell and its Observation;
- abort the current composition attempt;
- retry by selecting a *new* Requirement/Policy identity after the external
  problem has been corrected.

Recovery MUST NOT mutate a failed cell into =ready=, substitute an Observation,
or let one composition bypass the gate. A continuation does not cross into
canonical receipt identity.

Unexpected Gerbil/module/runtime failures produce an initialization failure
condition but no semantic Decision receipt. Semantic rejections produce a
reject Decision and a failed cell.

*** Cycle and re-entrancy detection

Re-entering the same cell while it is =evaluating= is an initialization cycle,
not a request to start a second probe. POO Flow reports a structured cycle
condition with the Requirement/Policy tuple and evaluation path.

The runtime must distinguish:

- direct self re-entry;
- multi-module re-entry through downstream imports;
- a different Requirement/Policy tuple that is legitimately evaluated in the
  same process.

The cycle condition is observable before stack overflow or unbounded
allocation. Recovery may inspect or abort; it may not fabricate a pass Decision.

before =user-composition=, =use-composition=, or =compose= can consume its core

Only =active= permits new public composition work.  =failed= is terminal with
respect to activation: it preserves the failure for inspection but cannot be
changed into =active=.  Recovery that needs another attempt constructs a new
context with a new =runtimeContextId=; it does not reset the old context or its
cell.  The replacement may reuse the same canonical Requirement and Policy when
their semantics are unchanged.

The runtime context owns two kinds of private control token:

#+begin_src text
RuntimeLease
EvaluationCommitToken
#+end_src

A running context-bound operation holds a =RuntimeLease=.  Closing atomically
stops issuance of new leases, enters =closing=, and lets already-running
operations reach a bounded terminal publication or abort boundary.  Dormant
captured continuations do not retain leases and therefore cannot prevent
shutdown indefinitely.

Every cell evaluation owns exactly one =EvaluationCommitToken=.  Scheme
continuations may be multi-shot, but the token is one-shot: exactly one dynamic
path may publish =ready= or =failed=.  A later resumption that reaches the same
commit boundary receives a structured =evaluation-already-committed= condition
and cannot publish, overwrite, or wake waiters a second time.

If closing is requested during =qualifying=:

1. No new qualification cell or public composition work may start.
2. The current evaluator may publish its one terminal cell outcome so existing
   waiters receive deterministic evidence.
3. A passing outcome does not reactivate the closing context.
4. After the evaluator releases its lease, the context becomes =closed= and its
   operational registry is discarded.

Continuation capture never snapshots or rolls back context state.  Every
resumption of a context-bound continuation rechecks a private
=RuntimeContinuationGuard= containing the originating =runtimeContextId= and
evaluation identity.

A continuation captured during qualification or failure handling cannot:

- reopen a =closed= context;
- change =failed= to =active=;
- restore an earlier registry or cell state;
- move a capability into another context;
- repeat a committed Observation or Decision publication;
- bypass Requirement or Policy identity by resuming an older evaluator.

“Controlled-continuable” does not mean that an arbitrary Scheme handler return
value becomes the value of the failed qualification expression.  POO Flow owns
an initialization supervisor around =raise-continuable= and first-class
continuation capture.

The handler receives a closed =RecoverySet= containing only the named operations
permitted by that condition.  =inspect-qualification-failure= is repeatable and
non-terminal: it returns detached immutable diagnostics and then leaves the
handler inside the recovery decision boundary.  The terminal choices are
=AbortInitialization= and =ReplaceRuntimeContext=.

A terminal recovery decision carries private =runtimeContextId=,
=evaluationId=, and recovery-token identity.  The supervisor validates these
against the current =RuntimeContinuationGuard=.  A raw capability, boolean,
procedure, arbitrary object, or recovery token from another condition is
rejected with =InvalidRecoveryResultCondition=.

The terminal recovery token is one-shot.  A multi-shot continuation may inspect
the condition repeatedly, but it cannot abort, replace, or commit more than
once.  Reusing a consumed recovery token produces
=RecoveryAlreadyConsumedCondition= and does not re-enter the probe.  Reaching a
cell publication boundary after its =EvaluationCommitToken= was consumed is the
separate =EvaluationAlreadyCommittedCondition=.

The supervisor continuation is captured outside the probe's publication
boundary.  Resumption transfers only an authorized recovery decision; it does
not reinstate earlier mutable cell or context state.  This preserves Scheme's
first-class control flow without granting a continuation authority to rewrite
qualification history.

Non-continuable runtime-control conditions are still ordinary structured Scheme
conditions and may be caught by an outer diagnostic boundary.  Catching them
does not authorize resuming the failed operation.  Their purpose is to expose
stale continuations, double commits, foreign contexts, and illegal lifecycle
transitions immediately rather than allowing recursion, silent corruption, or
performance collapse.

Waiters on one =DependencyQualificationCell= receive the same immutable
semantic outcome.  Each waiter may receive its own condition delivery, but all
=QualificationRejectedCondition= deliveries reference the same
DecisionReceipt.  A handler for one waiter cannot change the outcome observed by
another.

GSLPH may execute the condition and recovery test matrix as a development
harness.  It does not define the hierarchy, install handlers, issue recovery
tokens, validate continuations, or attest outcomes.

*** Condition, observability event, and DecisionReceipt boundaries

Condition delivery, observability, and semantic evidence have different
authorities.  They MUST NOT be collapsed into one object or used as substitutes
for one another.

| Form | Purpose | Lifetime | Canonical semantic evidence |
|-
| structured condition | dynamic control transfer and authorized recovery | one failure delivery | no |
| observability event | ordered operational diagnosis | runtime-context timeline | no |
| DecisionReceipt | stable result of Requirement + Observation + Policy | independent of runtime timeline | yes |

A condition answers “what must this dynamic control path do now?”.  An event
answers “what happened, and in what runtime order?”.  A DecisionReceipt answers
“what semantic decision was produced from these canonical inputs?”.

#+begin_mermaid
flowchart LR
    ROP["Requirement + Observation + Policy"] --> Decision["Pure Decision"]
    Decision --> Receipt["DecisionReceipt<br/>canonical semantic evidence"]
    Decision --> Transition["Runtime cell transition"]
    Transition --> Event["Observability event<br/>operational timeline"]
    Transition -->|"reject/failure"| Condition["Structured condition<br/>control transfer"]
    Receipt -. "digest may be referenced by" .-> Event
    Receipt -. "object may be referenced by rejection" .-> Condition
    Event -. "never changes" .-> Receipt
    Condition -. "never manufactures" .-> Receipt
#+end_mermaid

The DecisionReceipt is constructed only when a complete Observation reaches the
pure Decision function.  It contains no timestamp, runtime context identity,
event sequence, condition delivery identity, GSLPH execution identity, build
identity, or logging metadata.  Neither a condition nor an event can attest,
replace, amend, or invalidate it.

An observability event is an immutable operational value emitted through the
existing POO Flow observability boundary.  This RFC does not introduce a new
event bus, storage system, active evidence closure, or receipt family.

The bounded event fields are:

decisionReceiptDigest     ; optional

across contexts.  Events from different runtime contexts have no implicit total

Arbitrary open-ended attribute maps are not part of the normative event
contract.  Original Scheme exceptions remain attached to structured conditions;
events carry only the bounded =conditionKind= and correlation identities.  This
prevents exception text, secrets, stack data, or unstable printer output from
silently becoming an event schema.

G0 also needs observability before =clan/poo= is qualified.  The initialization
supervisor therefore owns a minimal Gerbil-native bootstrap diagnostic buffer.
It has only the fixed event schema above and does not depend on the qualified

When the context becomes =active=, buffered events are projected once into the
existing POO Flow observability boundary.  When initialization fails, the
buffer remains available through detached failure inspection until that context
is closed.  It is never persisted as semantic evidence and never becomes a
DecisionReceipt.

The bootstrap buffer is bounded.  Repetitive non-terminal events may be
coalesced.  On pressure it increments =droppedEventCount= and retains the most
recent critical event: =cycle-detected=, =cell-failed=,
=runtime-context-closing=, or =runtime-context-closed=.  It emits or exposes one
=diagnostic-overflow= marker rather than allocating without bound.

Observability delivery is outside the qualification transaction.  A slow,
missing, or failing external sink cannot change the Decision, reset a cell,
block waiter publication, or turn pass into reject.  Sink degradation is
reported by the existing observability subsystem; G0 does not create a semantic
policy reason for it.

detects the transition, assigns the next =eventSequence=, records the local

External export may occur later and may batch events without changing their
context-local sequence.

A passing DecisionReceipt produces no condition.  A rejecting DecisionReceipt
is referenced by =QualificationRejectedCondition=.  Unexpected probe failure,
cycle detection, stale continuation, double commit, and shutdown control
conditions produce events and conditions but no new DecisionReceipt.

Waiter-specific =condition-delivered= events may be repeated, but all waiters on
one rejected cell reference the same DecisionReceipt digest.  Delivery count is
operational telemetry, not additional semantic evidence.

may be reported as an operational correlation by the runtime supervisor, but
it does not enter either context's =QualificationKey= or DecisionReceipt.

runtime lease, commit token, recovery token, mutable registry reference, or

**** Runtime measures and safety limits

Each =PooFlowRuntimeContext= freezes a private =RuntimeDiagnosticLimits= value
at creation:

| Limit | Delivery and recovery | Existing work |
|-

*** Evaluation lineage across Mix, Profile, and recursive submodules

=EvaluationLineage= is an immutable, path-local diagnostic and control value.
It records how the current demand was reached.  It is not the POO object graph,
not a global dependency graph, not canonical semantic input, and not a
fixed-point implementation.

One root runtime request creates one lineage root.  Entering a Mix, applying a
Profile, descending into a submodule, forcing a capability, or waiting for an
in-flight cell derives a new frame from the current lineage:

#+begin_src text

             branchId,
             compositionPath,
             moduleIdentity,
             targetIdentity,
             operationKind)
  -> childLineage
#+end_src

The parent lineage is never mutated.  Arbitrary to-B-to-C nesting therefore
produces a bounded causal path rather than a shared mutable stack.

#+begin_mermaid
flowchart TD
    Root["Root composition request<br/>lineage L0"]
    Root --> ProfileA["Profile A<br/>L0/A"]
    ProfileA --> MixB["Mix B<br/>L0/A/B"]
    MixB --> SubC["Submodule C<br/>L0/A/B/C"]
    SubC --> SubD["Submodule D<br/>L0/A/B/C/D"]
    Root --> ProfileX["Concurrent Profile X<br/>L0/X"]
    ProfileX --> Shared["Demand shared target K"]
    SubD --> Shared

=compositionPath= is an opaque runtime path that distinguishes two applications
of the same Mix or Profile in different branches.  It is diagnostic identity,
not package identity or canonical profile identity.  A child package does not
perform G0 merely because it contributes another path segment.

The internal runtime dynamically binds the current lineage around POO Flow
composition combinators.  A synchronous nested call derives directly from the
current frame.  A spawned concurrent branch receives an explicit lineage fork
with a new =branchId=; it MUST NOT depend on accidental thread-parameter
inheritance.

A captured Scheme continuation retains its lineage identity, but every
resumption still validates =RuntimeContinuationGuard=.  Resumption does not
restore an earlier wait graph, cell state, or context lifecycle state.

Recursive POO structure is permitted.  A prototype may refer to =self=,
=super=, another Mix, or a descendant module without being a failure.  POO Flow
reports a cycle only when evaluation forms a strict demand cycle in which no
participant can publish a value.

composition combinators.  It does not intercept arbitrary POO slot lookup,
calculate the pure-object fixed point, replace prototype composition, or
implement another memoization engine.

**** Context-local wait graph

Same-lineage ancestor lookup detects direct recursive demand quickly, but it is
not sufficient for concurrent branches.  The runtime context therefore owns a
bounded =RuntimeWaitGraph=.

Its nodes and edges are operational:

#+begin_src text
evaluation(evaluationId)
module-capability-cell(targetIdentity)
evaluation --owns--> module-capability-cell
evaluation --waits-for--> module-capability-cell
#+end_src

Before an evaluator waits for an existing =evaluating= cell, POO Flow
atomically proposes the =waits-for= edge and checks whether the combined
=owns=/=waits-for= graph would become cyclic.

#+begin_mermaid
flowchart LR
    EvalA["Evaluation A"] -->|"owns"| CellA["Cell A"]
    EvalB["Evaluation B"] -->|"owns"| CellB["Cell B"]
    EvalA -->|"waits for"| CellB
    EvalB -. "proposed wait for" .-> CellA
    CellA -. "would close A ↔ B cycle" .-> Reject["Reject proposed edge<br/>CompositionDemandCycleCondition"]
#+end_mermaid

The rules are:

1. A POO Flow-owned module-capability target already present in the current
   lineage ancestry is an immediate strict-demand cycle.
2. A target =ready= or =failed= is observed directly and creates no wait edge.
3. A target owned by another lineage may be awaited only if the proposed edge
   leaves =RuntimeWaitGraph= acyclic.
4. If the edge would close a cycle, the proposing evaluation is the
   deterministic cycle breaker.  The edge is not installed.
5. The cycle breaker records =cycle-detected=, freezes the discovered graph
   path, and receives =QualificationCycleCondition= during G0 or
   =CompositionDemandCycleCondition= during active composition.
6. Other cells are not forcefully rewritten.  Normal unwinding publishes the
   breaker evaluation's operational failure and wakes dependent waiters.
7. Installed wait edges are removed when the waiter wakes, aborts, or its
   context begins closing.
8. Wait-graph inspection and edge insertion are serialized inside the private
   runtime boundary, so two simultaneous proposed edges cannot both evade the
   cycle check.

Different lineages are therefore waiters only when their actual wait
dependencies remain acyclic.  “Different lineage” by itself is not proof of
independence.

The cycle snapshot includes both the lineage path and, when necessary, the
minimal discovered wait-graph path.  Graph search is bounded by
=maxActiveEvaluationCells= and the lineage-depth limit; exceeding either
uses the already-defined resource-limit condition rather than allocating
without bound.

**** The internal higher-order object

The Mix module is one higher-order POO object with exactly three semantic
projections:

#+begin_src text
MixModuleObject
  identity
  imports
  capabilities
#+end_src

These are POO slots, not record fields or user DSL clauses.

=identity= is an immutable POO value naming the module's semantic identity.
The local =ALIAS= chosen by =use-module= does not replace or rewrite it.  Two
aliases may refer to the same module identity without creating two module
definitions.

=imports= is a POO object whose slots are lazy module-capability computations.
Each computation is generated by the module/Profile macros and routed
internally through =resolve-module-capability=.  The user never writes a raw
dependency edge or cell address.

=capabilities= is a POO object whose slots are the values made available for
Profile composition.  A capability may itself be another POO object, a
functional combinator, or a nested Mix module capability.  It is not required
to be flattened into a package-level manifest.

The object is higher-order because its import slots compute capability objects,
its capability slots may themselves be composable POO objects, and its Profile
prototypes may extend the resulting object through =self=/=super= composition.

**** Alias, identity, and capability resolution

Alias resolution has a deliberately small contract:

#+begin_src text

  MODULE -> locate the module binding
  ALIAS  -> establish a composition-local name
  result -> internal MixModuleObject binding
#+end_src

The alias is composition-local presentation identity.  It MUST NOT enter:

- =MixModuleObject.identity=;
- =QualificationKey=;
- Requirement, Observation, Policy, or Decision;
- DecisionReceipt;
- package identity;
- runtime-context identity.

When a selected Profile demands a capability:

#+begin_src text

  -> alias-bound MixModuleObject
  -> capabilities slot
  -> imports slot when required
  -> resolve-module-capability
  -> existing gerbil-poo computation
#+end_src

=resolve-module-capability= is absent from macro surface, Profile syntax, and
normal error messages.  Structured diagnostics may name the failing module and
capability, but users never invoke the resolver directly.

This RFC records the agreed architecture for consuming =clan/poo= Mix objects
through the existing POO Flow Profile and =use-composition= contracts.

Architecture approval does not authorize Scheme implementation, package
publication, public API changes, or release.

* Decision summary

- =clan/poo= permanently owns prototype composition, =mix=, =fix=,
  =self/super=, lazy slot access, and pure-object fixed-point semantics.
- POO Flow MUST NOT implement an alternate fixed-point evaluator.
- A Mix object is consumed as an existing reusable Profile object.
- The public =profiles -> use-composition -> compose= surface is unchanged.
- =identity=, recursive =imports=, and =capability= remain private Mix Profile
  semantics unless a future approved case proves that a public projection is
  necessary.
- Structural import cycles are arranged before one closure is handed to
  =clan/poo=; semantic slot recursion remains entirely upstream-owned.
- Capability authority never grows by merging import paths.
- Continuable recovery is a target control-plane capability at declared pure
  safe points. It is not an existing baseline capability.

* Recursive imports and cycle semantics

** Two different forms of recursion

Structural import recursion and semantic slot recursion MUST NOT be conflated.

| Recursion | Example | Owner |
|-----------+---------+-------|
| Structural import cycle | =A imports B; B imports A= | registry/resolver/loader plus graph adapter |
| Semantic slot recursion | slots in A and B refer to final =self= | =clan/poo= |

** Structural closure

The registry/resolver/loader chain does not currently expose a module-system
cycle or component adapter. This is a real private implementation gap.

The adapter MUST:

1. project resolved module identities and import edges into the existing graph
   representation;
2. preserve source and profile identity;
3. obtain cycle paths, ordering, and condensation evidence from
   =graph/algorithms.ss=;
4. deduplicate a diamond import by semantic identity;
5. arrange each recursive component as one set of prototype contributions;
6. emit a lazy load plan and load receipt through existing loader contracts;
7. hand the arranged contribution set to =clan/poo= for pure closure.

It MUST NOT become a new public graph API.

The private POO plan contract carries:

- immutable registry snapshot identity;
- resolved module identities and import edges;
- the existing =compose= precedence projection;
- source and contribution references;
- strongly connected components;
- condensation edges and component order;
- finite cycle paths;
- deterministic materialization groups;
- path-scoped capability requirements;
- safe observations and graph-analysis status.

Import reachability MUST NOT determine =super= precedence. Precedence originates
in the existing =compose= semantics and is only normalized by the plan.

Components organize loading and diagnostics. They do not cause per-component
fixed-point evaluation. All materialized contributions in one root composition
form one global pure-object closure.

** Cycle result

A structural cycle is not automatically an error. A valid recursive component
shares one pure-object composition closure.

A component fails closed when:

- identity is ambiguous;
- a source conflict cannot be resolved deterministically;
- capability constraints are inconsistent;
- materialization fails;
- the resulting pure object is invalid or tainted.

* Canonical upstream prototype handoff

The canonical pure handoff uses the upstream =clan/poo= prototype owner:

#+begin_src scheme
;; Internal semantic projection, not a public API.
(define composed-root-prototype
  (compose-proto* ordered-materialized-contributions))

(define root-profile-object
  (instantiate-proto composed-root-prototype))
#+end_src

- =compose-proto*= is invoked once for the complete ordered root contribution
  vector.
- =instantiate-proto= is invoked once for the composed root prototype.
- =instantiate-protos= may be used only after an equivalence qualification
  proves the same ordering and receipt semantics.
- =.mix=, =instantiate-object!=, and =uninstantiate-object!= are excluded from
  the canonical root closure path.
- Existing kernel/root Profile composition supplies the base contribution.
- The adapter MUST NOT invent a new empty base object.
- Receipts record identities, order, digests, stage, and result status. They do
  not serialize a prototype or live object.

Before implementation, the parent build/package owner MUST prove a reproducible
=clan/poo= dependency, exact source identity, and installed-artifact resolution
of the pure =proto= API. The local =.data/gerbil-poo= checkout is evidence, not
production dependency authority.

* Capability semantics

Capability declaration and capability authority are distinct.

- A Mix Profile may carry capability requirements and delegation constraints.
- Capability tokens do not participate in pure Profile composition.
- Capability tokens do not enter =clan/poo= fixed-point evaluation.
- The same semantic Profile reached through multiple import paths contributes
  once.
- Authorities from multiple paths MUST NOT be unioned.
- Effect execution checks authority against action provenance and the exact
  delegation path.
- Capability failures are fail-closed and cannot be ignored by a restart.

** Decision-first path check

The action selects one concrete finite authorization path. Cedar authorizes
that exact path, and the resulting token binds:

- action digest;
- root execution identity;
- import-path witness digest;
- capability requirement;
- Cedar decision digest.

Strict mediation is the only validation and consumption gateway.

- A diamond import cannot combine two insufficient paths.
- A valid circular-component witness is finite: root-to-component path,
  component identity, and member identity.
- Repeated traversal of a cycle cannot increase authority.
- The token is single-use.
- A deny produces no execution receipt.

Safe diagnostics may expose requirement identity, selected path digest,
permit/deny, decision digest, token identity, and consumed status. They MUST NOT
expose the token body, nonce, bearer authority, or full private path.

** Safe points

A future continuation may be captured only at a declared pure safe point.

- SP1: after Profile selection, before import resolution.
- SP2: after import graph construction, before component materialization.
- SP3: after component planning, before forcing the load plan.
- SP4: after pure closure returns, before effect-plan commitment.

** Restart discipline

A restart may:

- retry from a new immutable registry or resolver snapshot;
- select an explicitly approved alternate source;
- retry materialization;
- return to an earlier pure safe point;
- abort and emit doctor plus durable recovery receipts.

A restart may not:

- ignore an identity conflict;
- widen capability authority;
- accept a tainted result;
- serialize a live continuation;
- continue from an arbitrary =clan/poo= slot frame;
- cross the external-effect gateway.

** Upstream hook boundary

Current evidence does not show a generic =call/cc=, condition, restart,
=compute-slot=, or MOP interception owner.

POO Flow therefore cannot promise recovery from an arbitrary slot recursion,
stack overflow, or divergence inside =clan/poo=.

If per-slot observability or recovery becomes necessary, the generic hook
belongs upstream in =clan/poo=. POO Flow MUST NOT implement a shadow evaluator.

** Private recoverable-control owner

The approved private source owner is:

#+begin_example
src/core/recoverable-control.ss
#+end_example

It defines two internal POO-native values:

| Value | Carries |
|-------+---------|
| SafePointCondition | condition identity, safe point, control-plane failure, immutable snapshot identity, allowed restart descriptors, deterministic attempt budget, taint state |
| RestartDecision | retry, resume-with-new-input, abort, or handoff as a pure decision value |

A live continuation exists only in dynamic execution scope. It is never stored
in either object, a Profile, an observation, or a receipt.

The control protocol is:

1. a pure phase produces an existing =control-plane-failure=;
2. the private owner projects it to a SafePointCondition;
3. restart policy returns a POO-native RestartDecision;
4. a pure retry invokes the live continuation with a new immutable input;
5. every retry increments a deterministic attempt counter;
6. repeated condition/input/decision identity or exhausted budget fails closed;
7. an effectful repair terminates the continuation and emits a
   =handoff-required= durable recovery scenario;
8. repair starts a new execution and obtains new authorization.

Only a pure retry may resume the current continuation. Token consumption or
external effect initiation permanently closes that continuation boundary.

The following receipts remain distinct:

| Receipt | Proves | Does not prove |
|---------+--------+----------------|
| Compile receipt | Syntax expansion and pure plan construction | Effects executed |

* Rejected alternatives

** Implement another fixed-point evaluator

Rejected because =clan/poo= already owns the complete semantic mechanism.

** Add =user-composition=, =initial=, or public =mix-module= forms

Rejected because the existing =profiles/use-composition/compose= surface is
already sufficient.

** Treat every import cycle as an error

Rejected because a valid recursive component can be closed through the upstream
pure-object semantics.

** Union capability authority across import paths

Rejected because diamond and cyclic imports would become privilege-escalation
channels.

** Capture continuations across effects

Rejected because external effects cannot be safely replayed or rolled back by a
Scheme continuation.

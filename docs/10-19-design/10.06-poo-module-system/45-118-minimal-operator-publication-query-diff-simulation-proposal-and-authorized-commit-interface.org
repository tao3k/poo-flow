#+title: Minimal Operator Publication Query, Diff, Simulation, Proposal, and Authorized Commit Interface
#+startup: overview

* Status

Accepted architecture decision.

This RFC defines the operator interface over the publication contract fixed by
[[file:45-117-profile-variant-candidate-publication-generation-pinning-and-rollback-contract.org][45-117]].

* Evidence state

A parser-owned ASP owner search used 45-115 as the exact owner anchor.  It
succeeded.

The receipt confirmed:

- generations are immutable and content-addressed;
- active head is a versioned external selection resource;
- head change requires a pure proposal, authorized intent, and conditional
  runtime commit;
- concurrent publication cannot silently overwrite;
- reversion is a new head transition and preserves generation/effect history;
- generation pinning, in-flight work, cohorts, rollback, quiescence, and
  retirement are part of the publication boundary;
- there is no imperative profile-switch API or public publication macro.

Implementation ownership for the operator adapter remains =MISSING=.

* Scope

This RFC defines:

- operator inspection;
- candidate-to-head diff;
- isolated publication simulation;
- publication and rollback proposals;
- fresh admission;
- authorized conditional commit;
- stale-head conflict and recovery;
- idempotency;
- adapter boundaries for CLI, Emacs, Web, and agents.

This RFC does not define:

- publication syntax inside =use-composition=;
- a CLI command language;
- a JSON patch protocol;
- a public publication macro;
- ambient operator authority;
- automatic commit after simulation;
- automatic stale-head retry;
- an alternative active-head implementation.

* Central decision

The operator interface is a sequence of POO-native demands and results:

#+begin_example
Inspect
  -> Diff
  -> Simulate
  -> Propose
  -> Fresh Admission
  -> Authorized Conditional Commit
  -> Receipt or Typed Conflict
#+end_example

No earlier stage implies or authorizes a later stage.

The ordinary application composition surface remains unchanged.

* Operator demand algebra

The advanced operator surface uses native POO objects for:

- =HeadInspectionDemand=;
- =CompositionDiffDemand=;
- =PublicationSimulationDemand=;
- =PublicationProposal=;
- =RollbackProposal=;
- =PublicationCommitDemand=;
- =PublicationExplanationDemand=.

These names identify semantic object families.  They do not introduce reader
forms, macros, or a record DSL.

Exact construction and extension syntax must use verified native
=gerbil-poo= operations.

* Capability separation

The operator capability model distinguishes:

- head observation;
- composition inspection;
- diff inspection;
- simulation;
- proposal creation;
- publication commit;
- rollback commit;
- cohort or multi-scope commit;
- cancellation.

Capability shape is not authority.

Each live capability is:

- explicitly admitted;
- attenuated to principal, scope, operation, candidate, and expected head;
- bounded by policy, expiry, and budget;
- non-transferable by default;
- absent from portable proposal values.

Read, simulation, proposal, publication, and rollback authority never collapse
into one ambient operator role.

* Inspect

=HeadInspectionDemand= asks for an explicitly scoped active-head observation.

The result may include:

- head scope;
- active-head revision;
- selected generation;
- composition receipt identity;
- profile variant identity;
- current rollout cohort;
- materialization and quiescence summary;
- redacted in-flight generation summary.

Inspection:

- performs no mutation;
- grants no publication authority;
- returns completeness and redaction evidence;
- cannot be used as an implicit cached commit precondition.

* Diff

=CompositionDiffDemand= compares:

- a candidate composition;
- an explicitly observed head revision and generation.

The POO-native diff may explain:

- module and profile revision changes;
- application variant changes;
- contribution and withdrawal changes;
- responsibility and import changes;
- capability attenuation changes;
- recovery and observability changes;
- budget, redaction, and retention changes;
- runtime adapter requirements;
- cache-isolation consequences;
- affected head scopes and cohorts;
- old-generation in-flight obligations;
- rollback target availability.

Diff is evidence, not a patch to apply.

* Diff completeness

A diff result records:

- compared identities;
- included semantic facets;
- omitted or redacted facets;
- traversal and budget limits;
- evaluator and policy versions;
- completeness classification.

A partial diff cannot be presented as complete.

Publication policy may reject a proposal whose required diff facets are
missing.

* Simulation

=PublicationSimulationDemand= evaluates the proposed transition in an isolated
context.

Simulation may evaluate:

- candidate validation;
- expected-head preconditions;
- cohort and multi-scope topology;
- affected new admissions;
- generation pinning consequences;
- retirement and rollback readiness;
- cache invalidation;
- runtime adapter availability;
- policy and capability requirements.

Simulation cannot:

- mutate active head;
- claim publication capability;
- materialize live continuations;
- publish runtime cache entries;
- cancel in-flight work;
- guarantee that a future commit will succeed.

The simulated head snapshot may become stale immediately.

* Simulation outcome

=PublicationSimulationOutcome= records:

- candidate and observed-head identities;
- simulated transition graph;
- predicted validation outcome;
- predicted affected scopes and cohorts;
- predicted in-flight and quiescence effects;
- unresolved conditions;
- simulation budget;
- isolation evidence;
- non-publication evidence.

It is not a commit token.

* PublicationProposal

=PublicationProposal= is a pure POO object.

It binds:

- candidate identity;
- target head scopes;
- expected head revisions;
- requested rollout policy;
- required validation evidence;
- required diff and simulation identities when policy demands them;
- proposal provenance;
- proposal idempotency identity.

It contains no live capability, mutable head handle, commit callback, or secret.

Proposal creation does not imply approval.

* RollbackProposal

=RollbackProposal= is a specialized publication proposal that additionally
identifies:

- current observed head;
- target prior generation;
- failure or operator reason evidence;
- target-generation qualification;
- rematerialization requirements when needed;
- history-preservation obligation.

Rollback remains a new conditional publication.

It is not a command to delete or rewrite history.

* Proposal composition

When several scopes or policy conditions must move together, proposals compose
through the existing POO proposal algebra.

Composition produces:

- a valid =ProposalBundle= with explicit dependency edges; or
- a typed proposal conflict.

Proposal composition cannot manufacture publication authority or weaken an
independent constraint.

* Fresh admission

Commit begins only after fresh admission of the exact proposal.

Admission verifies:

- principal and session;
- proposal identity;
- candidate and validation identities;
- target scopes;
- expected head revisions;
- publication or rollback operation;
- rollout and atomicity policy;
- capability attenuation;
- expiry and budget;
- current policy and runtime adapter versions.

The admitted capability is bound to this proposal.  It cannot commit a
different candidate or scope.

* PublicationCommitDemand

=PublicationCommitDemand= combines:

- the immutable admitted proposal;
- the live attenuated commit capability;
- the stabilized publication effect intent;
- the exact expected-head preconditions;
- an idempotency identity.

The runtime performs the existing conditional head commit.

The result is:

- a =HeadTransitionReceipt=; or
- a typed control condition such as stale head, wrong scope, expired
  capability, policy denial, or runtime failure.

* Operator flow

#+begin_src mermaid
flowchart LR
  O["Operator"] -->|"read capability admits scoped observation"| I["Head inspection"]
  I -->|"candidate and observed head are compared"| D["Composition diff"]
  D -->|"isolated policy requests counterfactual evaluation"| S["Publication simulation"]
  D -->|"operator may proceed without simulation only when policy permits"| P["PublicationProposal"]
  S -->|"simulation evidence satisfies proposal policy"| P
  I -->|"operator may abandon without mutation"| A["No-op explanation receipt"]
  P -->|"fresh principal, scope, candidate, and expected-head authority intersect"| C["Admitted commit demand"]
  P -->|"authority or policy rejects proposal"| R["Typed admission refusal"]
  C -->|"external head still matches every precondition"| H["Conditional head commit"]
  C -->|"head, scope, policy, or capability changed"| X["Typed commit conflict"]
  H -->|"append-only transition is recorded"| T["HeadTransitionReceipt"]
#+end_src

No inspection, diff, or simulation edge bypasses admission.

* Commit idempotency

Commit idempotency covers:

- proposal identity;
- candidate identity;
- target scopes;
- expected head revisions;
- publication operation;
- admitted capability binding;
- stabilized intent identity.

An identical duplicate commit returns the already-bound transition receipt.

A conflicting duplicate under the same idempotency identity fails closed.

Idempotency does not allow a stale proposal to target a new head revision.

* Stale-head condition

When the expected head no longer matches, the runtime returns a typed
=StaleHeadCondition=.

It contains:

- proposal and candidate identities;
- target scope;
- expected head revision;
- newly observed head reference when disclosure is authorized;
- failed commit receipt;
- safe recovery-demand descriptions;
- redaction and completeness evidence.

It contains no live commit capability or automatic retry instruction.

* Continuable stale-head recovery

A stale-head condition may be continuable at an operator safe point.

Permitted recovery actions are new POO demands:

- refresh head observation;
- recompute diff;
- rerun simulation;
- construct a new proposal;
- abandon the operation.

The original commit capability cannot be resumed against a different head.

=Resume= remains coordinator admission of a new demand.  A local handler does
not return a magic retry value.

* Stale-head recovery flow

#+begin_src mermaid
flowchart TD
  C["Conditional commit"] -->|"expected head no longer matches"| S["StaleHeadCondition"]
  S -->|"operator requests fresh read admission"| I["New head inspection"]
  S -->|"operator ends workflow without mutation"| A["Abandoned proposal receipt"]
  I -->|"new head changes semantic comparison"| D["Recomputed diff"]
  D -->|"policy requires new counterfactual evidence"| M["New simulation"]
  D -->|"operator constructs proposal with new expected revision"| P["New PublicationProposal"]
  M -->|"simulation remains isolated"| P
  P -->|"fresh commit authority is admitted"| N["New conditional commit demand"]
#+end_src

There is no edge that mutates the expected revision inside the old proposal.

* Rollback operator flow

Rollback uses the same stages:

1. inspect current head;
2. inspect the target prior generation;
3. diff current and rollback target;
4. simulate reversion when policy requires;
5. create a =RollbackProposal=;
6. obtain fresh rollback authority;
7. commit conditionally;
8. receive a new =HeadTransitionReceipt=.

Rollback authority is distinct from ordinary publication authority when policy
requires.

* Cohort and multi-scope operations

Operator demands retain explicit target scope for every observation, diff,
simulation, proposal, and commit.

Multi-scope proposals enumerate:

- every target head;
- every expected revision;
- atomicity requirement;
- dependency edges;
- rollback or failure behavior.

One scope's observation or capability cannot authorize another scope.

* Redaction and secrets

Operator results preserve:

- profile and generation identities;
- policy explanations;
- redacted requirement summaries;
- typed conflicts.

They exclude:

- secret plaintext;
- live secret capability;
- protected environment content;
- continuation handles;
- hidden runtime provider locators;
- unapproved principal or cohort data.

A publication diff describes secret-requirement changes, not secret values.

* Audit and receipts

Every stage has an immutable POO receipt:

- inspection receipt;
- diff receipt;
- simulation outcome;
- proposal receipt;
- admission receipt;
- runtime handoff receipt;
- transition or conflict receipt;
- explanation receipt.

Receipts preserve actor, scope, candidate, head revision, policy, budget, and
redaction provenance according to authority.

Earlier receipts are not rewritten after commit.

* Adapter boundary

CLI, Emacs, Web, and agent interfaces are adapters.

An adapter may:

- render POO demand/result objects;
- collect explicit operator input;
- construct demands through approved native constructors;
- submit demands;
- display typed conditions and receipts.

An adapter may not:

- define a parallel publication state machine;
- treat textual output as canonical identity;
- send raw record patches directly to active head;
- hide commit behind inspection;
- retain ambient publication authority;
- reinterpret stale-head conflict as automatic retry.

CLI flags, Web forms, and editor commands are non-normative presentation
choices.

* Ordinary user surface

Application composition remains:

#+begin_src scheme
(use-composition production-system
  (compose profiles
    (use-module wendao-episteme production)
    application-production))
#+end_src

No publication, rollback, operator, diff, simulation, or approval clause enters
this form.

* Macro governance

No operator macro is introduced.

The operator protocol is advanced POO object composition and functional demand
evaluation.

Any convenience syntax in an adapter must remain an adapter projection.  It
cannot become a hidden semantic macro in the core.

* Failure behavior

The system fails closed on:

- inspection treated as publication authority;
- diff treated as an executable patch;
- simulation treated as commit approval;
- proposal containing a live capability;
- commit capability used for a different candidate or scope;
- expected-head revision silently updated;
- stale-head condition automatically retried;
- rollback deleting history;
- cross-scope capability reuse;
- secret value exposed in operator evidence;
- CLI or editor adapter owning a parallel publication protocol;
- textual command identity replacing POO content identity.

* Invariants

- [X] Inspect, diff, simulation, proposal, admission, and commit remain distinct.
- [X] Earlier stages grant no authority for later stages.
- [X] Proposal and simulation are pure or isolated and non-mutating.
- [X] Commit requires fresh proposal-bound authority.
- [X] Expected-head preconditions remain immutable.
- [X] Duplicate identical commit is idempotent.
- [X] Conflicting duplicate commit fails closed.
- [X] Stale-head recovery creates new demands and proposal.
- [X] Rollback uses the same conditional publication protocol.
- [X] Operator evidence remains redacted.
- [X] CLI, Emacs, Web, and agents are adapters only.
- [X] Ordinary =use-composition= remains unchanged.
- [X] No new public macro or CLI DSL is introduced.

  adapters.

- [ ] Diff exposes completeness and redaction evidence.

#+title: Phased Slot Resolution, Contract Roles, and Failure Taxonomy
#+subtitle: Structural projection, semantic admission, priority, lazy evaluation, runtime effects, and disclosure
#+startup: overview

* RFC status

- Status :: Accepted design
- Kind :: Normative slot-resolution protocol
- Semantic core :: Native POO composition and demand-driven POO Flow evaluation
- Related modules :: =45-41-poo-profile-slot-contribution-priority.org= and =45-52-capability-roles-admission-scope-and-cache-isolation.org=

This module defines an explicit phase pipeline for slot resolution. It prevents metadata inspection from forcing business values, runtime authorization failure from becoming semantic conflict, and disclosure policy from changing business identity.

* Core decision

#+begin_quote
Slot resolution is an explicit phase pipeline. Structural projection, semantic admission, priority, canonical combination, contract assembly, semantic evaluation, runtime authorization, and disclosure have separate responsibilities and failure classes. Only active semantic definitions are evaluated; shadowed contributions remain lazy.
#+end_quote

The normative order is:

#+begin_src text
0. Structural projection
1. Semantic admission
2. Priority resolution
3. Canonical combination and contract assembly
4. Demand-driven semantic evaluation
5. Runtime effect authorization
6. Evidence projection and disclosure authorization
#+end_src

Runtime effect authorization occurs at each explicit effect boundary encountered during semantic evaluation. It is not one global step after evaluation.

* Typst formalization: typed phase witnesses

Each phase produces the only witness accepted by the following phase.  A phase
number alone is insufficient because it could be forged without carrying the
required prior evidence.

#+begin_src typst
$

  S_1 & = "SemanticAdmission"(S_0, "AdmittedViewIdentity") \
  S_2 & = "PriorityResolution"(S_1, "Active", "Shadowed") \
  S_3 & = "CanonicalCombination"(S_2, "Combined") \
  S_4 & = "ContractAssembly"(S_3, "Contract") \
  S_5 & = "SemanticEvaluation"(S_4, "Value") \
  S_6 & = "RuntimeAuthorization"(S_5, "EffectBoundary", "Receipt") \
  S_7 & = "Disclosure"(S_6, "Projection") \

#+end_src

The absence of =Value= from phases zero through four means structural
inspection, admission, priority, combination, and contract assembly cannot
force a business value.  Shadowed candidates remain values of the priority
stage rather than evaluated business results.

* Phase 0: structural projection

Structural projection verifies pure structure:

- strategy-facet coherence;
- the operand's POO Profile projection;
- canonical definition anchor and revision;
- exact ordered priority metadata;
- declared capability role;
- declared contract role and phase;
- resolver control-plane coherence;
- absence of forbidden live captures in a pure semantic closure.

This phase may inspect metadata. It must not:

- select a priority winner;
- evaluate a business slot;
- validate a live token;
- create a continuation;
- perform a runtime effect.

Failure is =StructuralProjectionFailure=. It is not a business-value conflict.

* Phase 1: semantic admission

Semantic admission evaluates pure requirements against canonical admission scope:

- identity scope;
- submodule and provider scope;
- semantic admission capability;
- admission contracts;
- required admission or explicit filtering semantics.

It produces:

#+begin_src text
AdmittedSemanticView
+ rejected or excluded contribution evidence
#+end_src

Business values remain unevaluated.

Required-admission failure fails closed. Explicit filtering produces a different admitted-view identity.

* Phase 2: priority resolution

Priority resolution operates only over admitted candidates:

- read =default=, exact numeric priority, or =force=;
- select the highest-priority layer;
- retain lower-priority candidates as dormant or shadowed;
- deduplicate repeated contribution identity;
- preserve operand-order independence;
- avoid forcing business values;
- avoid runtime capability checks for shadowed implementation values.

#+begin_src mermaid
flowchart LR
    S["Structurally projectable contributions"] -->|"validate semantic admission scope"| A["Admitted candidate set"]
    S -->|"required admission fails"| F["Semantic admission failure"]
    S -->|"explicit filtering excludes a candidate"| X["Excluded-candidate evidence"]
    A -->|"compare exact priority metadata"| H["Highest-priority layer"]
    A -->|"retain lower priorities without forcing values"| D["Dormant contributions"]
    H -->|"contains one candidate"| W["Active contribution"]
    H -->|"contains equal-priority candidates"| C["Canonical combination phase"]
#+end_src

Priority does not bypass identity, admission, capability, or contract policy.

* Phase 3: canonical combination

The highest-priority layer is resolved as follows:

- one candidate becomes the active definition;
- repeated identical contribution identity is idempotently deduplicated;
- equal-priority candidates use a native POO operation only when that operation is canonical for the current values;
- directional or non-confluent operations are not selected by operand order or identity sorting;
- absence of a canonical combination produces structured =CanonicalCombinationConflict=.

Directional prototype construction remains explicit before =compose profiles= resolution.

* Contract roles

Every contract declares its role. Contracts are not one undifferentiated final check.

** Projection contract

Validates whether an object can enter a strategy projection.

- Evaluated in Phase 0.
- Does not evaluate business values.
- Failure is structural.

** Admission contract

Validates whether a contribution may enter an admitted semantic view.

- Evaluated in Phase 1.
- Uses pure metadata and canonical scope.
- Failure is semantic admission failure or explicit filtering according to policy.

** Result or interface contract

Constrains the final resolved slot value.

- May accumulate from multiple admitted definitions.
- Remains active independently from a shadowed implementation value when declared as a separate interface requirement.
- Is assembled before result commit.
- Incompatible accumulated contracts produce =ContractCompositionConflict=.

** Contribution implementation contract

Validates the value produced by one active contribution.

- Runs only when that contribution becomes active and is evaluated.
- Does not run for a dormant or shadowed implementation value.
- Failure produces =ResultContractViolation=.

Priority cannot silently delete an accumulated result or interface contract.

* Phase 4: demand-driven semantic evaluation

The evaluator creates demands only for the active or canonically combined definition:

- slot computation;
- dependency-demand expansion;
- fixed-point evaluation;
- current-generation SCC discovery;
- semantic result-cache reuse;
- continuable semantic conditions;
- active implementation contracts;
- assembled result and interface contracts.

Dormant business values remain unevaluated.

If priority or semantic admission changes and a dormant definition becomes active:

- a new semantic target or generation is derived;
- the definition is activated in that new semantic state;
- the affected slot and downstream current-generation SCCs are invalidated;
- the old generation is not mutated.

* Phase 5: runtime effect authorization

When active semantic evaluation reaches an explicit runtime effect boundary:

1. Validate the current runtime-execution capability.
2. Validate lease lifetime and adapter scope.
3. Confirm child-context delegation.
4. Execute the effect.
5. Record authorization and effect receipts.

Failures include:

#+begin_src text
RuntimeAuthorizationFailure
RuntimeAdapterFailure
OperationalBudgetExhaustion
#+end_src

They are operational. They are not cached as a business slot conflict.

A new live proof for the same runtime scope may permit operational retry against the same semantic target. Changing semantic admission scope derives a new admitted view.

* Phase 6: evidence and disclosure

After semantic result and correctness evidence are available:

- the business value enters the semantic result namespace;
- correctness evidence enters the evidence namespace;
- retention and redaction follow the evidence projection;
- every subscriber validates disclosure capability before delivery;
- denied disclosure does not change semantic result identity;
- missing evidence may require operational reevaluation without creating a new business value.

#+begin_src mermaid
flowchart LR
    C["Canonical active definition and assembled contracts"] -->|"demand the business value"| E["Semantic evaluation"]
    E -->|"encounter an explicit runtime effect"| A["Runtime authorization"]
    A -->|"current capability is valid"| E
    A -->|"authorization or adapter fails"| O["Operational failure receipt"]
    E -->|"produce a value satisfying result contracts"| R["Semantic result"]
    E -->|"value violates an active contract"| V["ResultContractViolation"]
    R -->|"materialize correctness evidence"| P["Evidence projection"]
    P -->|"subscriber passes disclosure authorization"| D["Authorized delivery"]
    P -->|"subscriber lacks disclosure authority"| X["Redacted or denied delivery receipt"]
#+end_src

* Failure taxonomy

The normative failure classes are:

#+begin_src text
StructuralProjectionFailure
SemanticAdmissionFailure
CanonicalCombinationConflict
ContractCompositionConflict
ResultContractViolation
SemanticEvaluationCondition
FixedPointCycleCondition
RuntimeAuthorizationFailure
RuntimeAdapterFailure
OperationalBudgetExhaustion
DisclosureDenied
#+end_src

Only semantic conflict and condition classes may enter semantic resolver and recovery protocols.

Runtime authorization, adapter, budget, cancellation, and disclosure failures remain in their live execution or delivery boundary. A resolver must not reinterpret them as Profile merge conflicts.

* Failure ownership

- =StructuralProjectionFailure= belongs to construction and strategy admission.
- =SemanticAdmissionFailure= belongs to admitted-view formation.
- =CanonicalCombinationConflict= belongs to same-priority semantic resolution.
- =ContractCompositionConflict= belongs to result-contract assembly.
- =ResultContractViolation= belongs to active semantic value validation.
- =SemanticEvaluationCondition= and =FixedPointCycleCondition= belong to demand-driven evaluation.
- Runtime failures belong to live execution context and adapters.
- =DisclosureDenied= belongs to per-subscriber delivery authorization.

A phase cannot silently relabel a failure owned by another phase.

* Cache boundaries

Pure cacheable artifacts include:

- structural projection;
- admitted semantic view;
- priority-resolution projection;
- canonical combination plan;
- contract assembly;
- semantic result;
- pure correctness evidence.

Operational artifacts include:

- live capability validation;
- effect execution;
- budget and cancellation;
- worker retry;
- disclosure delivery.

An operational failure does not populate a semantic result cache entry. A disclosure failure does not invalidate a semantic result.

* Phase invariants

- Metadata may be projected early; business values remain lazy.
- Semantic admission precedes priority-winner selection.
- Priority resolution precedes active-value evaluation.
- Shadowed implementation values and runtime capabilities are not forced.
- Result and interface contracts are assembled before result commit.
- Runtime capability is checked at every explicit effect boundary.
- Disclosure capability is checked at every delivery boundary.
- Operational failure does not become semantic cache content.
- Failure ownership remains stable across phase boundaries.
- A phase transition emits evidence identifying its input and output projection.

* Evidence requirements

Phase evidence records:

- phase identity and protocol version;
- input and output projection identities;
- structural admission or rejection;
- admitted, filtered, and rejected candidate identities;
- priority winner and dormant candidates;
- canonical operation or conflict identity;
- contract roles and assembled result contracts;
- active-demand and SCC evidence;
- runtime authorization and effect receipts;
- semantic result commit;
- disclosure authorization and projection;
- exact failure class and owning phase.

Evidence generation must not force dormant business values.

* Implementation checklist

- [ ] Implement the explicit phase pipeline and transition evidence.
- [ ] Separate metadata projection from business-value evaluation.
- [ ] Complete semantic admission before priority selection.
- [ ] Keep dormant values and implementation contracts unevaluated.
- [ ] Admit equal-priority combination only through a canonical native POO operation.
- [ ] Define projection, admission, result/interface, and implementation contract roles.
- [ ] Accumulate declared result contracts independently from implementation priority.
- [ ] Fail closed on incompatible result-contract composition.
- [ ] Validate active implementation and result contracts before commit.
- [ ] Derive a new semantic state when admission or priority activates a dormant definition.
- [ ] Validate runtime capability at every effect boundary.
- [ ] Keep runtime and budget failures out of semantic result caches.
- [ ] Validate disclosure capability at every delivery boundary.
- [ ] Enforce the normative failure taxonomy and phase ownership.
- [ ] Prevent resolver handling of operational and disclosure failures as semantic conflicts.
- [ ] Validate final phase operations against real =gerbil-poo= and Gerbil runtime primitives.

* Non-goals

- Do not implement slot resolution as one undifferentiated merge.
- Do not force all contribution values before priority resolution.
- Do not run shadowed implementation contracts.
- Do not let priority erase accumulated result contracts.
- Do not treat runtime authorization, budget, or disclosure failure as semantic conflict.
- Do not let a later phase silently reinterpret an earlier failure.
- Do not create a phase registry, contract DSL, or callback table.

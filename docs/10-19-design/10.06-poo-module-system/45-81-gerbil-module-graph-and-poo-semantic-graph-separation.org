#+title: Gerbil Module Graph and POO Semantic Graph Separation
#+startup: overview

* Status

This RFC records the accepted separation between the Gerbil module import graph
and the POO semantic definition graph.

It extends the module/profile ownership and namespace RFCs. It permits lazy
semantic fixed points without redefining Gerbil module loading or relying on
circular module initialization.

* Typst formalization: distinct graph roles and failure ownership

The Gerbil module graph and the POO semantic graph have different nodes, edges,
phases, identities, cycles, failure modes, and owners.  A module import edge is
a lexical code dependency; a profile requirement edge is a semantic dependency
inside an explicit composition root.

#+begin_src typst
#let gerbil-edge(module-a, module-b) = (
  role: "GerbilModuleImportEdge",
  source: module-a,
  target: module-b,
  phase: expansion-or-load-phase(module-a, module-b),
)

#let semantic-edge(profile-a, profile-b) = (
  role: "ProfileSemanticRequirementEdge",
  source: profile-a,
  target: profile-b,
  requirement: semantic-contract(profile-a, profile-b),
)

$ lexical-code-dependency(gerbil-edge(a, b))
  and not semantic-requirement(gerbil-edge(a, b)) $

$ semantic-requirement(semantic-edge(p, q))
  and not lexical-code-dependency(semantic-edge(p, q)) $

$ gerbil-edge(a, b) ==> not implicitly-create(semantic-edge(a, b)) $
$ semantic-edge(p, q) ==> not implicitly-create(gerbil-edge(p, q)) $
#+end_src

The semantic graph is constructed only after the required Gerbil modules have
loaded and the user calls =compose profiles=.  Lazy SCC/fixed-point cycles are
owned by the semantic graph; macro-phase and circular module-initialization
failures remain owned by Gerbil.

#+begin_src typst
$ construct-semantic-graph(receipt)
  ==> required-modules-loaded(receipt)
  and compose-profiles-invoked(receipt) $

$ lazy-fixed-point(cycle)
  ==> graph-role(cycle) = "poo-semantic-definition" $

$ circular-module-initialization(failure)
  ==> owner(failure) = "gerbil-module-graph"
  and not resolved-by-poo-fixed-point(failure) $

$ semantic-fixed-point-divergence(failure)
  ==> owner(failure) = "poo-semantic-graph" $

$ profiles-a != profiles-b or policy-a != policy-b
  ==> semantic-graph-id(profiles-a, policy-a)
  != semantic-graph-id(profiles-b, policy-b) $
#+end_src

* Central decision

The Gerbil module import graph answers how code is expanded, compiled, loaded,
and bound lexically.

The POO semantic definition graph answers how system objects compose, depend
on one another, and reach a semantic fixed point.

They are different graphs with different identities, phases, cycles, failures,
and owners.

* Gerbil module import graph

The Gerbil module graph contains:

- module paths;
- import and export edges;
- macro and expander dependencies;
- compile and load dependencies;
- lexical bindings;
- module initialization order.

It is governed by Gerbil module and phase semantics.

POO Flow must not redefine module loading, macro-phase dependency, or circular
module initialization behavior.

* POO semantic definition graph

The POO semantic graph contains:

- profile anchors and revisions;
- prototype relations;
- slot contributions;
- semantic requirements;
- identities;
- capabilities;
- contracts;
- resource and effect dependencies;
- nested submodule scopes;
- lazy demands;
- SCC and fixed-point edges.

It is constructed from first-class POO values after the required Gerbil modules
have loaded and the user calls =compose profiles=.

* Two edge roles

The term =import= must not obscure the graph boundary.

=GerbilModuleImportEdge= means a lexical code dependency created through the
Gerbil module system.

=ProfileSemanticRequirementEdge= means a semantic identity, contract, or
capability requirement inside the explicit POO composition root.

RFCs, receipts, diagnostics, and implementation types should use these complete
roles rather than one ambiguous =import= label.

    R["Root Gerbil Module"] -->|"lexically imports both profile bindings"| M1

* Cross-profile dependency

When Profile A requires a contract provided by Profile B:

- Module A exports a pure Profile A value;
- Module B exports a pure Profile B value;
- Profile A declares a semantic requirement;
- Profile B declares a provider projection;
- the root module explicitly imports both lexical bindings;
- =compose profiles= receives both values;
- structural closure resolves the semantic edge;
- POO Flow evaluates any resulting SCC.

Module A and Module B do not need to import one another circularly.

The Gerbil modules may both import common core constructors and contract
definitions through ordinary acyclic module dependencies.

* Explicit operand closure

Semantic requirement resolution is limited to:

- profiles explicitly supplied to the composition root;
- POO objects explicitly contained by those profiles;
- nested submodule objects explicitly reachable from those operands.

The evaluator must not scan:

- all loaded Gerbil modules;
- all installed Gerbil packages;
- the filesystem;
- Git submodules;
- a global provider registry.

Resolution occurs inside one canonical composition-root closure.

* Phase separation

The complete lifecycle has six phases.

** Expansion phase

Hygienic macros expand to ordinary POO-native and functional code.

Expansion must not query live runtime evidence or evaluate the global POO fixed
point.

** Module compile and load phase

Gerbil resolves module bindings and constructs finite profile values.

Module loading obeys Gerbil semantics and does not wait on POO semantic
closure.

** Root composition phase

=compose profiles= receives explicit first-class operands and produces one
canonical composition-root value.

** Structural closure phase

POO Flow resolves:

- anchors and revisions;
- semantic requirement edges;
- capability providers;
- prototype and slot contributions;
- nested scope paths;
- SCC partition.

** Demand evaluation phase

POO Flow evaluates lazy demands and semantic SCC fixed points with budgets,
cycle evidence, caching, continuations, and observability.

** Live handoff phase

Pure proposals cross explicit capability and authority boundaries before
runtime actions occur.

No earlier phase silently performs a later phase.

* Finite module initialization

A profile module constructs a finite, pure, reusable POO definition fragment.

Module initialization must not:

- evaluate a global POO fixed point;
- access live resources;
- wait for another profile's runtime value;
- start workers;
- register semantic providers by side effect;
- build a cache tied to one current composition root;
- acquire capabilities.

Importing the same profile module for multiple roots must not share hidden
mutable semantic state.

* Prohibited mutable cycle construction

POO cycles must not be built through:

- an initial =#f= placeholder;
- later =set!= mutation;
- module initialization ordering;
- global boxes;
- import-time registries;
- ordinary raw =lambda (self super)= compute hooks.

Semantic cycles use verified native =gerbil-poo= object, prototype, and demand
semantics.

Exact native operator spelling remains deferred until verified against the real
library.

* Graph identities

A =GerbilModuleGraphIdentity= may include:

- module source and build identities;
- import and export bindings;
- macro-phase dependencies;
- compiled artifact identities.

A =POOSemanticGraphIdentity= includes:

- composition-root revision;
- profile revisions;
- prototype and slot resolution;
- semantic requirement edges;
- capabilities and contracts;
- nested scope paths;
- SCC partition.

The same loaded module graph may construct multiple semantic graphs for
different composition roots.

Module-graph equality does not imply semantic-graph equality.

* Macro phase boundary

Macros may generate:

- profile definitions;
- POO object families;
- contract projections;
- manifests and schemas;
- syntax provenance.

Macros must not:

- evaluate the global POO fixed point;
- query the active head;
- access runtime capabilities;
- change expansion from live evidence;
- depend on module initialization side effects;
- convert expansion order into semantic priority.

Compile-time expansion remains deterministic from source and explicit
compile-time inputs.

* Nested B2B2C composition

Each module exports pure profile fragments.

The root or a higher-order profile explicitly composes nested domain objects.

Every nesting level contributes a scope path to semantic identity.

Cross-layer semantic cycles form POO SCCs.

They do not require multi-layer circular Gerbil imports.

* Failure classification

The implementation and diagnostics keep separate:

- Gerbil module missing or import cycle;
- macro or expander phase failure;
- profile-value construction failure;
- semantic requirement unresolved;
- structural closure violation;
- POO SCC suspension or violation;
- non-productive Scheme recursion;
- live resource deadlock or execution failure.

A generic circular-dependency error is insufficient.

The receipt identifies which graph and phase failed.

* User interface

The ordinary interface remains:

#+begin_src scheme
(user-composition my-system
  (compose profiles
    base
    wendao-episteme
    production))
#+end_src

The Gerbil module system first supplies the three lexical values.

The POO composition system then interprets their semantic dependencies.

The user does not encode semantic cycles through module imports.

* Required invariants

1. Gerbil module and POO semantic graphs remain separate.
2. Gerbil import edges and profile requirement edges use distinct roles.
3. Module loading does not evaluate semantic fixed points.
4. Composition uses explicit lexical operands.
5. Semantic resolution is limited to the operand closure.
6. No global provider discovery or import-time registry is used.
7. Profile modules construct finite pure values.
8. Mutable placeholders do not encode POO cycles.
9. Semantic SCCs use verified =gerbil-poo= and POO Flow semantics.
10. Module and semantic graph identities remain distinct.
11. Macros do not query live semantic or runtime state.
12. Nested B2B2C cycles remain semantic SCCs.
13. Diagnostics identify exact graph and phase.
14. Public semantic extension remains POO-native.
